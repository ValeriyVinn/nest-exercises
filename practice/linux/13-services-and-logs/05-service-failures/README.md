# 05. Service Failures — діагностика та усунення помилок служб у Linux

`Service Failures` — це тема про пошук причин, через які служби Linux не запускаються, аварійно завершуються, зависають або не виконують свої функції.

У сучасних дистрибутивах Linux, зокрема Ubuntu, для керування системними службами зазвичай використовується `systemd`. Основні інструменти діагностики — `systemctl`, `journalctl`, а також команди для перевірки процесів, мережі, файлів і прав доступу.

Мета діагностики — не просто перезапустити службу, а **знайти причину помилки, усунути її та перевірити результат**.

## 1. Основи помилок служб

### 1.1. Що таке Service Failure

Service failure — це ситуація, коли служба не може нормально запуститися, завершує роботу з помилкою або не виконує очікуваних функцій.

Наприклад:
- SSH-сервер не запускається;
- PostgreSQL завершується з помилкою;
- вебсервер не може зайняти порт;
- служба не має доступу до конфігураційного файлу;
- програма не знаходить необхідну бібліотеку;
- служба залежить від іншого компонента, який не працює;
- процес працює, але не відповідає на запити.

### 1.2. Типові причини помилок

✔ Неправильна конфігурація.

✔ Відсутній файл або каталог.

✔ Неправильні права доступу.

✔ Порт уже зайнятий іншим процесом.

✔ Не запущена необхідна залежність.

✔ Проблеми з дисковим простором.

✔ Недостатньо оперативної пам'яті.

✔ Помилки в параметрах запуску.

✔ Проблеми з мережею або DNS.

✔ Помилка самої програми.

✔ Некоректний systemd unit-файл.

✔ Вичерпано ліміт перезапусків служби.

### 1.3. Основні інструменти

    systemctl status назва.service

Перевірка стану служби.

    journalctl -u назва.service -b

Перегляд журналу служби за поточне завантаження.

    systemctl --failed

Пошук units, які перебувають у стані `failed`.

    systemctl show назва.service

Перегляд властивостей служби.

    systemctl cat назва.service

Перегляд unit-файлу та відповідних додаткових фрагментів.

    ps aux

Перегляд процесів.

    ss -lntup

Перевірка TCP- та UDP-сокетів, які відображаються в системі.

    df -h

Перевірка вільного місця на файлових системах.

## 2. Алгоритм діагностики служби

Коли служба не працює, важливо дотримуватися послідовності дій.

### 2.1. Крок 1 — перевірити статус

    systemctl status назва.service

Зверніть увагу на:
- `Loaded` — чи знайдено unit-файл;
- `Active` — поточний стан служби;
- `Result` — результат останньої операції, якщо відображається;
- `Main PID` — ідентифікатор основного процесу, якщо він є;
- останні повідомлення журналу.

### 2.2. Крок 2 — переглянути журнал

    journalctl -u назва.service -b -n 100

Показує останні 100 записів служби за поточне завантаження.

Якщо потрібні лише помилки:

    journalctl -u назва.service -b -p err

Важливо: параметр `-p err` показує повідомлення рівня `err` та серйозніших рівнів. Він не гарантує, що всі причини помилки будуть позначені саме таким пріоритетом.

### 2.3. Крок 3 — визначити тип проблеми

Після перегляду журналу сформулюйте гіпотезу.

Наприклад:
- `Permission denied` — проблема з правами доступу;
- `Address already in use` — порт зайнятий;
- `No such file or directory` — відсутній файл або каталог;
- `Connection refused` — з'єднання відхилено;
- `No space left on device` — немає доступного простору або вичерпано інший ресурс файлової системи;
- `Dependency failed` — не виконалася необхідна залежність;
- `Start request repeated too quickly` — systemd припинив повторні спроби запуску через установлені обмеження.

Це підказки, а не остаточний діагноз. Потрібно враховувати контекст повідомлення.

### 2.4. Крок 4 — перевірити відповідний ресурс

Залежно від помилки перевірте:
- конфігураційний файл;
- права доступу;
- доступність каталогу;
- вільне місце;
- зайняті порти;
- залежності;
- стан процесів;
- налаштування мережі.

### 2.5. Крок 5 — усунути причину

Виправляйте лише те, що підтверджено результатами діагностики.

Не змінюйте права доступу, порти або конфігурацію навмання.

### 2.6. Крок 6 — повторно перевірити службу

    sudo systemctl restart назва.service

Після цього:

    systemctl status назва.service

І перегляньте нові записи:

    journalctl -u назва.service -b -n 50

**Правило:** спочатку діагностика, потім виправлення, після цього перевірка.

## 3. Стани failed, inactive та activating

### 3.1. Стан failed

Приклад:

    Active: failed (Result: exit-code)

Systemd зафіксував невдалий стан служби.

Можливі причини:
- програма завершилася з ненульовим кодом;
- перевірка конфігурації завершилася помилкою;
- не знайдено необхідний файл;
- процес не зміг отримати потрібний ресурс;
- служба неодноразово завершувалася з помилкою.

Перевірка:

    systemctl status назва.service
    journalctl -u назва.service -b -n 100

### 3.2. Стан inactive

Приклад:

    Active: inactive (dead)

Служба зараз не активна.

Це не завжди помилка. Деякі units запускаються лише за потреби або виконують одноразові завдання.

Перевірте, чи повинна ця служба працювати постійно.

### 3.3. Стан activating

Служба перебуває в процесі запуску.

Якщо запуск триває надто довго:

    systemctl status назва.service
    journalctl -u назва.service -b

Можливі причини:
- довга ініціалізація;
- очікування залежності;
- проблема з мережею;
- зависання програми;
- невідповідні параметри `TimeoutStartSec`.

Не змінюйте тайм-аути, доки не з'ясуєте, чому запуск затримується.

### 3.4. Стан deactivating

Служба перебуває в процесі зупинки.

Якщо зупинка затягнулася, перевірте журнал та процеси:

    systemctl status назва.service
    journalctl -u назва.service -b -n 100
    ps aux

Не завершуйте процес примусово, якщо не розумієте наслідків для даних і залежних служб.

### 3.5. Стан active (exited)

Приклад:

    Active: active (exited)

Це може бути нормальним для одноразових служб, які виконали роботу й завершилися.

Не кожна служба повинна постійно мати процес зі станом `running`.

## 4. Читання повідомлень про помилки

Журнал часто містить головну підказку щодо причини несправності.

### 4.1. Перегляд останніх повідомлень

    journalctl -u назва.service -n 50

### 4.2. Перегляд повідомлень за поточне завантаження

    journalctl -u назва.service -b

### 4.3. Повідомлення за останні 30 хвилин

    journalctl -u назва.service --since "30 minutes ago"

### 4.4. Перегляд у реальному часі

    journalctl -u назва.service -f

Зупинити перегляд можна через `Ctrl + C`.

### 4.5. Пошук типових повідомлень

    journalctl -u назва.service --no-pager | grep -Ei "error|failed|denied|timeout"

Команда шукає рядки з відповідними словами.

Проте не кожна помилка містить слово `error`, тому пошук через `grep` не замінює повного аналізу журналу.

### 4.6. Як читати журнал правильно

Знайдіть не лише останній рядок, а й повідомлення безпосередньо перед ним.

Наприклад:

    Configuration file is invalid
    Failed to initialize application
    Main process exited, code=exited, status=1/FAILURE

У такій послідовності перший рядок може вказувати на справжню причину, а наступні — бути її наслідками.

## 5. Помилка Permission denied

### 5.1. Що означає Permission denied

Повідомлення означає, що процес не має необхідного доступу до файлу, каталогу, сокета або іншого ресурсу.

Наприклад:

    Failed to open configuration file: Permission denied

Можливі причини:
- неправильний власник файлу;
- недостатні права доступу;
- відсутні права на один із батьківських каталогів;
- служба працює від іншого користувача;
- обмеження безпеки, наприклад AppArmor.

### 5.2. Перевірка прав доступу

    ls -l /шлях/до/файлу

Приклад:

    ls -l /etc/example/example.conf

Перевірте власника, групу та права.

### 5.3. Перевірка каталогів

    namei -l /etc/example/example.conf

Команда показує компоненти шляху та права доступу до них, якщо `namei` доступна в системі.

Процес повинен мати змогу пройти через усі батьківські каталоги.

### 5.4. Перевірка користувача служби

    systemctl show -p User -p Group назва.service

Це показує значення параметрів `User` і `Group`, якщо вони задані у відповідній конфігурації.

Якщо `User` не заданий, для системної служби це часто означає запуск від root, але потрібно враховувати тип unit і його налаштування.

### 5.5. Не використовуйте chmod 777 як універсальне виправлення

Неправильний підхід:

    sudo chmod -R 777 /etc/example

Це може зробити конфігурацію доступною для зміни стороннім користувачам і створити серйозну проблему безпеки.

Правильний підхід:
1. визначити, якому користувачеві потрібен доступ;
2. перевірити власника та групу;
3. надати лише необхідні права;
4. повторно перевірити службу.

## 6. Помилка Address already in use

### 6.1. Що означає ця помилка

Повідомлення `Address already in use` означає, що програма не може прив'язатися до адреси або порту, оскільки відповідний ресурс уже зайнятий або конфліктує з наявним налаштуванням.

Наприклад, вебсервер намагається слухати порт `8080`, але інший процес уже використовує його.

### 6.2. Перевірка TCP-портів

    sudo ss -lntp

Показує TCP-сокети, які перебувають у стані прослуховування, та інформацію про процеси, якщо вона доступна.

### 6.3. Перевірка конкретного порту

    sudo ss -lntp 'sport = :8080'

Перевіряє TCP-сокети, що слухають порт `8080`.

Для UDP:

    sudo ss -lnup 'sport = :8080'

### 6.4. Що робити далі

Якщо порт зайнятий:
1. визначте процес, який використовує порт;
2. перевірте, чи є він потрібним;
3. перевірте конфігурацію обох служб;
4. вирішіть, яка служба повинна використовувати цей порт;
5. змініть конфігурацію або зупиніть непотрібний процес лише після перевірки.

Не завершуйте знайдений процес автоматично: він може обслуговувати іншу важливу службу.

## 7. Помилка No such file or directory

### 7.1. Причини

Програма або systemd не може знайти файл чи каталог.

Можливі причини:
- неправильний шлях;
- файл видалено;
- пакет установлено неповністю;
- файл має іншу назву;
- служба запускається раніше, ніж стає доступним потрібний ресурс;
- unit-файл посилається на неправильний виконуваний файл.

### 7.2. Перевірка існування файлу

    ls -l /шлях/до/файлу

Наприклад:

    ls -l /usr/bin/example

Якщо файл відсутній, не створюйте порожню заміну без розуміння його призначення.

### 7.3. Перевірка виконуваної команди

    systemctl cat назва.service

Знайдіть рядок `ExecStart`.

Приклад:

    ExecStart=/usr/bin/example --config /etc/example/config.conf

Перевірте існування виконуваного файлу та конфігурації:

    ls -l /usr/bin/example
    ls -l /etc/example/config.conf

### 7.4. Перевірка пакетів

На Ubuntu можна перевірити, який пакет володіє файлом:

    dpkg -S /usr/bin/example

Це працює, якщо файл належить установленому пакету.

Не використовуйте прикладову назву буквально: замініть її реальним шляхом із журналу або unit-файлу.

## 8. Помилка конфігурації

### 8.1. Типові причини

- синтаксична помилка;
- неправильна назва параметра;
- некоректне значення;
- відсутній обов'язковий параметр;
- неправильний шлях до сертифіката або ключа;
- несумісні параметри;
- зміна формату конфігурації після оновлення програми.

### 8.2. Знайти файл конфігурації

Перевірте журнал:

    journalctl -u назва.service -b -n 100

Потім перегляньте unit-файл:

    systemctl cat назва.service

Зверніть увагу на параметри `ExecStart`, `Environment`, `EnvironmentFile` та інші директиви, які можуть впливати на запуск.

### 8.3. Використовуйте перевірку конфігурації програми

Багато серверних програм мають спеціальний режим перевірки конфігурації.

Наприклад, для Nginx:

    sudo nginx -t

Команда перевіряє конфігурацію Nginx, якщо він установлений.

Для інших програм використовуйте їхні власні інструменти перевірки та документацію.

### 8.4. Після виправлення

    sudo systemctl restart назва.service
    systemctl status назва.service

Потім перевірте журнал:

    journalctl -u назва.service -b -n 50

Якщо служба використовує `reload` і підтримує його, у деяких випадках можна застосувати зміни без повного перезапуску.

## 9. Помилка Dependency failed

### 9.1. Що означає ця помилка

Служба не може запуститися або завершити потрібну операцію, оскільки одна з її залежностей не виконала необхідну умову.

Залежність може бути:
- іншою службою;
- точкою монтування;
- мережевим ресурсом;
- іншим systemd unit;
- системним ресурсом, необхідним для запуску.

### 9.2. Перевірка залежностей

    systemctl list-dependencies назва.service

Показує залежності служби.

### 9.3. Перегляд зворотних залежностей

    systemctl list-dependencies --reverse назва.service

Допомагає побачити units, які залежать від зазначеного unit.

### 9.4. Перевірка стану залежності

    systemctl status залежність.service

### 9.5. Перегляд журналу залежності

    journalctl -u залежність.service -b -n 100

Якщо залежність не працює, спочатку дослідіть її причину.

Не запускайте всі залежності вручну навмання: systemd може керувати ними через спеціальні правила активації.

---

## 10. Помилка Start request repeated too quickly

### 10.1. Що означає повідомлення

Приклад:

    Start request repeated too quickly

Systemd припинив нові спроби запуску, оскільки служба неодноразово завершувалася з помилкою в межах установлених обмежень.

Це часто пов'язано з параметрами:
- `Restart=`;
- `RestartSec=`;
- `StartLimitIntervalSec=`;
- `StartLimitBurst=`.

### 10.2. Спочатку знайдіть першопричину

    systemctl status назва.service
    journalctl -u назва.service -b -n 100

Не починайте з очищення стану `failed`. Спочатку з'ясуйте, чому служба постійно завершується.

### 10.3. Перегляд налаштувань

    systemctl cat назва.service

Можна також перевірити окремі властивості:

    systemctl show -p Restart -p RestartUSec -p StartLimitIntervalUSec -p StartLimitBurst назва.service

Назви властивостей, які відображаються, залежать від версії systemd.

### 10.4. Скидання стану failed

Після усунення причини:

    sudo systemctl reset-failed назва.service

Потім спробуйте запустити службу:

    sudo systemctl start назва.service

І перевірте результат:

    systemctl status назва.service

`reset-failed` очищає збережений стан помилки та лічильник обмежень запуску, де це застосовно. Команда не виправляє причину аварійного завершення.

### 10.5. Не збільшуйте ліміти без аналізу

Якщо програма постійно завершується через помилку конфігурації, збільшення ліміту запуску не вирішить проблему.

Спочатку виправте першопричину, а потім за потреби переглядайте політику перезапуску.

## 11. Помилка Timeout

### 11.1. Що означає Timeout

Timeout означає, що очікувана операція не завершилася в межах установленого часу.

Це може трапитися:
- під час запуску служби;
- під час зупинки;
- під час очікування залежності;
- під час мережевого з'єднання;
- під час виконання операції самої програми.

### 11.2. Перегляд журналу

    journalctl -u назва.service -b -n 100

Знайдіть, яка саме операція перевищила час очікування.

### 11.3. Перевірка параметрів systemd

    systemctl cat назва.service

Зверніть увагу на:
- `TimeoutStartSec=`;
- `TimeoutStopSec=`;
- `ExecStart=`;
- `ExecStop=`;
- `Type=`.

### 11.4. Що робити

1. Визначте, на якій операції виникає затримка.
2. Перевірте залежності.
3. Перевірте доступність потрібних ресурсів.
4. З'ясуйте, чи зависає сама програма.
5. Лише після цього вирішуйте, чи потрібно змінювати тайм-аут.

Збільшення тайм-ауту не є універсальним виправленням.

---

## 12. Немає місця на диску

### 12.1. Типове повідомлення

    No space left on device

Це означає, що операція не може використати потрібний файловий простір або інший обмежений ресурс файлової системи.

Причиною можуть бути:
- заповнений диск;
- вичерпання inode;
- обмеження квоти;
- заповнення окремої файлової системи.

### 12.2. Перевірка файлових систем

    df -h

Показує використання дискового простору у зручному форматі.

### 12.3. Перевірка inode

    df -i

Якщо inode вичерпано, система може не створювати нові файли навіть за наявності вільного місця.

### 12.4. Перевірка журналів systemd

    journalctl --disk-usage

Показує, скільки місця займають журнали systemd.

### 12.5. Пошук великих каталогів

    sudo du -xhd1 /var 2>/dev/null

Показує приблизний розмір каталогів першого рівня в `/var`, залишаючись у межах тієї самої файлової системи.

Параметри `-d` та `-x` підтримуються GNU `du`, що використовується в Ubuntu.

### 12.6. Обережне очищення

Не видаляйте файли навмання з `/var/lib`, `/var/log` або інших системних каталогів.

Спочатку визначте, які дані займають місце, і використовуйте інструменти відповідної програми для безпечного очищення.

Для очищення старих архівних журналів systemd існує:

    sudo journalctl --vacuum-time=7d

Ця команда видаляє старі архівні журнали відповідно до вказаного строку. Використовуйте її лише тоді, коли старі журнали більше не потрібні.

---

## 13. Служба активна, але не працює правильно

### 13.1. Чому active не гарантує справність

Команда:

    systemctl is-active назва.service

може повернути:

    active

Це означає, що systemd вважає unit активним. Проте програма може:
- не відповідати на запити;
- слухати неправильний порт;
- не мати доступу до бази даних;
- мати проблеми з DNS;
- обробляти запити з помилками;
- перебувати в частково несправному стані.

### 13.2. Перевірка процесу

    systemctl status назва.service
    ps aux

### 13.3. Перевірка портів

    sudo ss -lntup

Перевірте, чи слухає програма очікуваний порт.

### 13.4. Перевірка HTTP-сервісу

Для локального HTTP-сервера можна використати:

    curl -I http://127.0.0.1:8080/

Замініть порт на той, який використовує ваша програма.

Команда перевіряє HTTP-відповідь. Відсутність відповіді або помилка не завжди означає, що systemd-служба зупинена: причиною можуть бути налаштування мережі, протоколу, маршруту або застосунку.

### 13.5. Перевірка журналу

    journalctl -u назва.service --since "10 minutes ago"

Поєднуйте системний статус із перевіркою реальної функції програми.

---

## 14. Перевірка мережевих проблем

Якщо служба залежить від мережі або надає мережевий сервіс, перевірте її мережевий стан.

### 14.1. Перевірка мережевих інтерфейсів

    ip addr

Показує мережеві інтерфейси та призначені їм адреси.

### 14.2. Перевірка маршрутів

    ip route

Показує таблицю маршрутів IPv4.

### 14.3. Перевірка DNS

    getent hosts example.com

Перевіряє, чи може система отримати адресу для вказаного імені через налаштовані механізми резолюції.

### 14.4. Перевірка доступності порту

    nc -vz 127.0.0.1 5432

Перевіряє TCP-з'єднання з локальним портом `5432`, якщо `nc` установлено.

Це типовий порт PostgreSQL, але він може бути змінений.

### 14.5. Перевірка служби та мережі

    systemctl status назва.service
    journalctl -u назва.service -b -n 100
    ip addr
    ip route

Використовуйте лише ті мережеві перевірки, які відповідають конкретній проблемі.

---

## 15. Перевірка ресурсів системи

Служба може завершуватися через нестачу ресурсів або обмеження.

### 15.1. Перевірка оперативної пам'яті

    free -h

Показує загальну інформацію про пам'ять і swap.

### 15.2. Перегляд навантаження

    uptime

Показує час роботи системи, кількість користувачів і середнє навантаження.

### 15.3. Перегляд процесів

    top

Показує процеси та поточне використання ресурсів.

Вийти можна через `q`.

### 15.4. Перевірка повідомлень ядра про OOM

OOM (Out Of Memory) — ситуація, коли система не може задовольнити потреби в пам'яті й може завершити процес.

Перегляньте повідомлення ядра:

    journalctl -k -b | grep -Ei "out of memory|oom|killed process"

Якщо доступ до всіх повідомлень обмежений, може знадобитися `sudo`.

### 15.5. Що робити

1. Перевірити використання пам'яті.
2. Знайти процеси, які споживають багато ресурсів.
3. Перевірити журнали служби та ядра.
4. З'ясувати, чи проблема повторюється під навантаженням.
5. Усунути першопричину, а не просто постійно перезапускати службу.

---

## 16. Проблеми з systemd unit-файлом

### 16.1. Перегляд unit-файлу

    systemctl cat назва.service

### 16.2. Перевірка шляху до файлу

    systemctl show -p FragmentPath назва.service

### 16.3. Пошук параметрів запуску

У unit-файлі зверніть увагу на:
- `ExecStart=`;
- `ExecStartPre=`;
- `ExecStartPost=`;
- `WorkingDirectory=`;
- `User=`;
- `Group=`;
- `Environment=`;
- `EnvironmentFile=`;
- `Restart=`;
- `TimeoutStartSec=`.

### 16.4. Перевірка синтаксису unit-файлів

Після зміни unit-файлу можна виконати:

    sudo systemd-analyze verify /etc/systemd/system/example.service

Замініть шлях на фактичний шлях до файлу.

Команда перевіряє unit-файл та виявляє деякі помилки конфігурації. Вона не гарантує, що сама програма запуститься успішно.

### 16.5. Перечитування конфігурації systemd

Після зміни unit-файлу:

    sudo systemctl daemon-reload

Це змушує systemd перечитати визначення units.

### 16.6. Перезапуск служби

    sudo systemctl restart example.service

Після цього перевірте:

    systemctl status example.service
    journalctl -u example.service -b -n 50

`daemon-reload` не виправляє конфігурацію самої програми. Він потрібен, коли змінено визначення unit для systemd.

---

## 17. Служба не запускається після перезавантаження

### 17.1. Перевірка автозапуску

    systemctl is-enabled назва.service

### 17.2. Перевірка поточного стану

    systemctl status назва.service

### 17.3. Перегляд журналу поточного завантаження

    journalctl -u назва.service -b

### 17.4. Перевірка попереднього завантаження

    journalctl -u назва.service -b -1

Ця команда покаже записи попереднього завантаження, якщо вони збереглися.

### 17.5. Можливі причини

- автозапуск не налаштовано;
- служба не призначена для прямого `enable`;
- запуск залежить від мережі або іншого ресурсу;
- конфігурація містить помилку;
- служба неодноразово завершилася з помилкою;
- запуск відбувається лише через socket, timer або інший unit.

### 17.6. Увімкнення автозапуску

Якщо служба призначена для автоматичного запуску:

    sudo systemctl enable назва.service

Щоб увімкнути автозапуск і запустити службу зараз:

    sudo systemctl enable --now назва.service

Не використовуйте `enable` для кожного unit без перевірки його призначення.

---

## 18. Проблеми з залежностями

### 18.1. Перегляд залежностей

    systemctl list-dependencies назва.service

### 18.2. Перевірка конкретної залежності

    systemctl status залежність.service

### 18.3. Перегляд журналу залежності

    journalctl -u залежність.service -b -n 100

### 18.4. Приклад

Уявімо, що застосунок потребує PostgreSQL. Застосунок може не запуститися, якщо база даних не працює або недоступна.

Перевірте:

    systemctl status postgresql.service
    journalctl -u postgresql.service -b -n 100

Назва PostgreSQL unit залежить від способу встановлення та конфігурації. На деяких системах доступні додаткові units для конкретних кластерів або версій.

### 18.5. Не плутайте залежність systemd із логічною залежністю програми

Навіть якщо unit не має формальної залежності від іншої служби, програма може логічно потребувати бази даних, мережі або зовнішнього API.

Тому перевіряйте як залежності systemd, так і фактичні вимоги застосунку.

## 19. Типові помилки під час діагностики

### Помилка 1. Перезапускати службу без читання журналу

Неправильний підхід:

    sudo systemctl restart назва.service

і на цьому зупинитися.

Краще:

    systemctl status назва.service
    journalctl -u назва.service -b -n 100

Спочатку визначте ймовірну причину.

### Помилка 2. Використовувати chmod 777

Надмірні права можуть створити проблему безпеки. Надавайте лише необхідний доступ конкретному користувачеві або групі.

### Помилка 3. Видаляти конфігурацію

Не видаляйте конфігураційний файл, щоб перевірити, чи запуститься служба. Спочатку зробіть резервну копію та перевірте синтаксис за документацією програми.

### Помилка 4. Вимикати залежності

Зупинка мережевої, системної або базової служби може вплинути на інші компоненти.

### Помилка 5. Вважати, що failed завжди означає пошкодження Linux

Помилка часто стосується лише конкретного сервісу. Досліджуйте unit, який має проблему, та його залежності.

### Помилка 6. Ігнорувати точний час помилки

Якщо служба працювала вранці, а зупинилася ввечері, перевіряйте журнал саме за відповідний проміжок часу.

### Помилка 7. Збільшувати тайм-аути без причини

Довший тайм-аут може лише відкласти появу помилки, якщо програма зависає або не має доступу до потрібного ресурсу.

### Помилка 8. Скидати failed до аналізу

Команда `reset-failed` очищає стан помилки, але не пояснює, чому вона виникла. Спочатку збережіть і проаналізуйте важливі записи.

### Помилка 9. Плутати проблему процесу з проблемою застосунку

Процес може працювати, але не надавати потрібний сервіс. Перевіряйте також порти, запити та журнали.

### Помилка 10. Копіювати команди без заміни прикладів

Назви `example.service`, `назва.service` та шляхи `/etc/example/` є умовними. Перед виконанням замініть їх на фактичні назви та шляхи у вашій системі.

## 20. Практичні вправи

### Вправа 1. Перевірити проблемні служби

Виконайте:

    systemctl --failed

Завдання:
- з'ясуйте, чи є units зі станом `failed`;
- якщо є, перегляньте їхній статус;
- якщо список порожній, поясніть, що це означає.

Не потрібно спеціально створювати помилку.

### Вправа 2. Дослідити журнал служби

Виберіть службу, яка існує у вашій системі.

    systemctl status назва.service
    journalctl -u назва.service -b -n 50

Завдання:
- знайдіть поточний стан;
- визначте, чи є попередження або помилки;
- запишіть час останніх повідомлень.

### Вправа 3. Знайти помилки за останню годину

    journalctl -u назва.service --since "1 hour ago"

Завдання:
- знайдіть повідомлення, пов'язані з проблемою;
- порівняйте їх із поточним статусом;
- визначте можливу причину.

### Вправа 4. Перевірити вільне місце

    df -h
    df -i
    journalctl --disk-usage

Завдання:
- визначте, чи достатньо місця на файлових системах;
- перевірте, чи не вичерпано inode;
- порівняйте розмір журналів із загальним використанням диска.

### Вправа 5. Перевірити порти

    sudo ss -lntup

Завдання:
- знайдіть порти, які слухаються;
- визначте, який процес використовує потрібний порт, якщо інформація доступна;
- поясніть, чому дві програми можуть конфліктувати через один порт.

### Вправа 6. Перевірити unit-файл

    systemctl cat назва.service
    systemctl show -p FragmentPath назва.service

Завдання:
- знайдіть шлях до unit-файлу;
- перегляньте параметри запуску;
- визначте, який виконуваний файл запускає служба.

### Вправа 7. Перевірити стан після перезапуску

Виконуйте лише для безпечної служби, яку можна перезапустити без порушення роботи системи.

    sudo systemctl restart назва.service
    systemctl status назва.service
    journalctl -u назва.service -b -n 30

Завдання:
- перевірте, чи успішно завершився запуск;
- перегляньте нові повідомлення;
- визначте, чи змінився стан служби.

## 21. Мініпроєкт: діагностика несправної служби

Мета — відпрацювати послідовний пошук першопричини помилки.

### Крок 1. Вибрати службу

Перегляньте доступні служби:

    systemctl list-unit-files --type=service

Виберіть службу, яку можна безпечно дослідити.

### Крок 2. Зафіксувати поточний стан

    systemctl status назва.service

Запишіть:
- назву;
- стан `Active`;
- результат останньої операції, якщо він показаний;
- PID, якщо він є;
- останні повідомлення.

### Крок 3. Зібрати журнал

    journalctl -u назва.service -b -n 100

Знайдіть перше повідомлення, яке може вказувати на першопричину.

### Крок 4. Визначити категорію проблеми

Виберіть найбільш відповідну категорію:
- конфігурація;
- права доступу;
- відсутній файл;
- конфлікт порту;
- залежність;
- нестача ресурсів;
- тайм-аут;
- інша причина.

### Крок 5. Перевірити гіпотезу

Використайте відповідні команди, наприклад:

    ls -l /шлях/до/файлу
    df -h
    df -i
    sudo ss -lntup
    systemctl list-dependencies назва.service

Не виконуйте всі команди без розбору. Вибирайте лише ті, які допомагають перевірити вашу гіпотезу.

### Крок 6. Усунути причину

Внесіть мінімальну обґрунтовану зміну. Якщо проблема не підтверджена, не змінюйте систему навмання.

### Крок 7. Перевірити результат

    systemctl status назва.service
    journalctl -u назва.service -b -n 50

Переконайтеся, що:
- служба перебуває в очікуваному стані;
- нових помилок не з'явилося;
- потрібна функція справді працює.

### Крок 8. Написати короткий звіт

    Назва служби:
    Симптом:
    Початковий стан:
    Повідомлення журналу:
    Виявлена причина:
    Виконане виправлення:
    Результат:
    Що варто перевірити додатково:

Такий звіт корисний для особистої документації та майбутнього пошуку аналогічних помилок.

## 22. Рівні знань: Core → Junior → Middle → Senior

### Core — основи

Потрібно вміти:

- пояснити, що таке systemd service;
- перевіряти стан через `systemctl status`;
- знаходити проблемні units через `systemctl --failed`;
- переглядати журнали через `journalctl`;
- розрізняти `active`, `inactive` і `failed`;
- розуміти, чому перезапуск не завжди усуває причину проблеми.

### Junior — практична діагностика

Потрібно вміти:

- аналізувати помилки в журналах;
- знаходити проблеми з правами доступу;
- перевіряти існування файлів;
- виявляти конфлікти портів;
- перевіряти місце на диску;
- знаходити проблемні залежності;
- перевіряти результат після виправлення.

### Middle — системний аналіз

Потрібно вміти:

- аналізувати параметри systemd unit-файлів;
- розбиратися в обмеженнях повторного запуску;
- діагностувати тайм-аути;
- досліджувати проблеми з пам'яттю;
- відрізняти помилку systemd від помилки застосунку;
- аналізувати мережеві залежності;
- використовувати системні інструменти для підтвердження гіпотез.

### Senior — експлуатація та надійність

Потрібно розуміти:

- вплив перезапуску служб на доступність системи;
- правила безпечного усунення несправностей у production;
- залежності складних системних сервісів;
- політики автоматичного перезапуску;
- обмеження ресурсів і механізми ізоляції;
- моніторинг, журналювання та пошук першопричини;
- документування інцидентів і запобігання повторенню помилок.

## 23. Шпаргалка основних команд

### Загальна діагностика

    systemctl status назва.service
    systemctl --failed
    systemctl is-active назва.service
    systemctl is-enabled назва.service
    systemctl show назва.service
    systemctl cat назва.service

### Перегляд журналу

    journalctl -u назва.service -b
    journalctl -u назва.service -b -n 100
    journalctl -u назва.service -p err
    journalctl -u назва.service --since "1 hour ago"
    journalctl -u назва.service -f

### Перевірка файлів і прав

    ls -l /шлях/до/файлу
    namei -l /шлях/до/файлу
    systemctl show -p User -p Group назва.service

### Перевірка портів і процесів

    ps aux
    pgrep -a назва
    sudo ss -lntup

### Перевірка ресурсів

    df -h
    df -i
    free -h
    uptime
    top
    journalctl --disk-usage

### Перевірка залежностей

    systemctl list-dependencies назва.service
    systemctl list-dependencies --reverse назва.service

### Перевірка unit-файлів

    systemctl cat назва.service
    systemctl show -p FragmentPath назва.service
    sudo systemd-analyze verify /etc/systemd/system/example.service
    sudo systemctl daemon-reload

### Після усунення причини

    sudo systemctl restart назва.service
    systemctl status назва.service
    journalctl -u назва.service -b -n 50

### Скидання стану помилки

    sudo systemctl reset-failed назва.service

Використовуйте цю команду після аналізу проблеми. Вона не замінює виправлення першопричини.

## 25. Рекомендований порядок вивчення

1. `systemctl status` — перевірка загального стану.
2. `systemctl --failed` — пошук проблемних служб.
3. `journalctl -u` — перегляд повідомлень.
4. Аналіз `Permission denied` — права доступу.
5. Аналіз `No such file or directory` — відсутні файли.
6. Аналіз `Address already in use` — конфлікти портів.
7. Перевірка залежностей — `list-dependencies`.
8. Перевірка диска та пам'яті — `df`, `free`, `top`.
9. Аналіз `Timeout` і `Start request repeated too quickly`.
10. Перевірка unit-файлів — `systemctl cat`, `systemctl show`.
11. Перевірка результату після виправлення.
12. Документування причини та рішення.

## 26. Що потрібно запам'ятати

1. `systemctl status` — перша команда для перевірки служби.
2. `systemctl --failed` допомагає знайти units із помилковим станом.
3. `journalctl -u назва.service -b` — основна команда для пошуку причини.
4. Повідомлення в журналі потрібно аналізувати разом із контекстом.
5. `Permission denied` вимагає перевірки прав, власника та доступу до всіх компонентів шляху.
6. `Address already in use` вимагає перевірки зайнятого порту або адреси.
7. `No such file or directory` вимагає перевірки фактичного шляху та наявності файлу.
8. `Dependency failed` вимагає перевірки залежного unit або ресурсу.
9. `Start request repeated too quickly` означає, що спроби запуску обмежено після повторних невдач.
10. `Timeout` означає, що операція не завершилася вчасно; причину потрібно знайти до зміни тайм-ауту.
11. `df -h` показує використання диска, а `df -i` — використання inode.
12. `ss -lntup` допомагає перевірити мережеві сокети та зайняті порти.
13. `systemctl reset-failed` очищає стан помилки, але не виправляє причину.
14. `systemctl daemon-reload` потрібен після зміни unit-файлів systemd.
15. Перезапускайте службу після діагностики, а не замість неї.
16. Після виправлення завжди перевіряйте стан служби, журнал і фактичну роботу програми.

**Головна ідея:** правильна діагностика служби в Linux — це послідовний пошук першопричини: перевірити стан, прочитати журнал, перевірити ресурси та залежності, усунути підтверджену проблему й перевірити результат.
