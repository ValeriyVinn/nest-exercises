# Git from Terminal — Git у терміналі

Git from Terminal — це робота з Git через командний рядок Linux: перевірка стану репозиторію, перегляд історії, створення комітів, синхронізація з GitHub, робота з гілками та розв’язання конфліктів.

Для розробника термінал дає змогу швидко керувати змінами у проєкті, розуміти стан локального репозиторію та синхронізувати роботу між різними комп’ютерами.

Мета цієї теми — навчитися впевнено використовувати Git у Linux для щоденної розробки JavaScript / TypeScript / Node.js / React / Next.js / NestJS-проєктів.

---

## 1. Що потрібно знати

✔ Git — система контролю версій.

✔ Repository (репозиторій) — проєкт, історію змін якого відстежує Git.

✔ Working tree — поточні файли проєкту, з якими ти працюєш.

✔ Staging area — область підготовлених змін, які потраплять до наступного коміту.

✔ Commit — збережений знімок змін в історії Git.

✔ Branch — окрема гілка розробки.

✔ Remote — віддалений репозиторій, наприклад на GitHub.

✔ `origin` — стандартна назва віддаленого репозиторію.

✔ `main` — поширена назва основної гілки.

✔ `fetch` — завантажує інформацію про зміни з віддаленого репозиторію, але не змінює твою поточну гілку.

✔ `pull` — отримує віддалені зміни та інтегрує їх у поточну гілку.

✔ `push` — відправляє локальні коміти до віддаленого репозиторію.

✔ `HEAD` — посилання на поточний коміт або поточний стан гілки.

✔ `origin/main` — локальне відображення стану гілки `main` на віддаленому репозиторії `origin`.

✔ `.git` — прихований каталог із даними локального репозиторію.

## 2. Як Git зберігає зміни

Основний робочий процес Git:

    Working tree → Staging area → Local repository → Remote repository
         │                │               │                  │
      git status        git add        git commit           git push

### 2.1. Working tree

Це звичайні файли проєкту, які ти створюєш або редагуєш.

Наприклад, змінив файл:

    src/app/page.tsx

Git може показати, що цей файл має незбережені в історії зміни.

Перевірити стан:

    git status

### 2.2. Staging area

Перед створенням коміту ти вибираєш зміни, які мають до нього потрапити.

    git add src/app/page.tsx

Тепер зміни цього файлу підготовлені до коміту.

### 2.3. Local repository

Команда `git commit` створює коміт у локальній історії.

    git commit -m "Update home page"

Коміт зберігається локально. Він ще не обов'язково є на GitHub.

### 2.4. Remote repository

Команда `git push` передає коміти до віддаленого репозиторію.

    git push

Після успішного виконання коміти доступні у віддаленому репозиторії.

**Важливо:** `git add` не завантажує файли на GitHub, а `git commit` не відправляє їх на GitHub. Для цього зазвичай потрібен `git push`.

## 3. Перевірка встановленого Git

### 3.1. Версія Git

    git --version

Приклад результату:

    git version 2.x.x

Точна версія залежить від встановленого пакета.

### 3.2. Шлях до виконуваного файлу

    which git

Або:

    command -v git

Команда `command -v` — вбудована команда Bash, яка показує, як оболонка знаходить команду.

### 3.3. Перевірка налаштувань

    git config --list

Показує налаштування Git, які застосовуються до поточного середовища.

Щоб побачити також джерела налаштувань:

    git config --list --show-origin

Не публікуй цей вивід без перевірки: у конфігурації можуть бути приватні адреси репозиторіїв або інша інформація, яку не варто розголошувати.

## 4. Налаштування Git

### 4.1. Ім'я користувача

    git config --global user.name "Your Name"

Це ім'я записуватиметься в авторство нових комітів.

### 4.2. Email

    git config --global user.email "your-email@example.com"

Бажано використовувати адресу, пов'язану з GitHub, або спеціальну приватну адресу GitHub, якщо не хочеш показувати особистий email у публічних комітах.

### 4.3. Перевірка імені та email

    git config --global user.name
    git config --global user.email

### 4.4. Різниця між локальними та глобальними налаштуваннями

Глобальне налаштування діє для поточного користувача Linux:

    git config --global user.name "Your Name"

Локальне налаштування діє лише для конкретного репозиторію. Його потрібно виконувати всередині цього репозиторію:

    git config user.name "Project Author"

Перевірити налаштування:

    git config --list --show-origin

Локальні налаштування репозиторію мають вищий пріоритет за глобальні.

### 4.5. Рівні конфігурації

- `--system` — системні налаштування.
- `--global` — налаштування користувача.
- `--local` — налаштування поточного репозиторію.

Приклади:

    git config --system --list
    git config --global --list
    git config --local --list

Команда `--local` має сенс усередині Git-репозиторію.

## 5. Перехід до проєкту

Для навчальних проєктів можна використовувати каталог `~/projects`.

Перейти до нього:

    cd ~/projects

Подивитися вміст:

    ls

Перейти до проєкту:

    cd ~/projects/nest-exercises

Перевірити поточний каталог:

    pwd

Переглянути приховані файли:

    ls -la

Якщо каталог є Git-репозиторієм, у ньому зазвичай буде прихований каталог `.git`.

Перевірити корінь репозиторію:

    git rev-parse --show-toplevel

Ця команда виводить шлях до кореня репозиторію, навіть якщо ти перебуваєш у вкладеному каталозі.

## 6. Перевірка репозиторію

### 6.1. Статус робочого дерева

    git status

Це одна з найважливіших команд Git.

Вона показує:

- поточну гілку;
- зміни у файлах;
- підготовлені до коміту зміни;
- непідготовлені зміни;
- невідстежувані файли;
- інформацію про розбіжність із віддаленою гілкою, якщо вона доступна.

### 6.2. Короткий статус

    git status --short

Приклад:

    M  src/app/page.tsx
     M src/app/globals.css
    ?? practice/linux/README.md

Позначення:

- `M` — змінений файл.
- `A` — новий файл, доданий до staging area.
- `D` — видалений файл.
- `??` — невідстежуваний файл.

У короткому форматі перший символ відповідає staging area, а другий — змінам у робочому дереві.

Наприклад:

    M  file.txt

Файл змінений і підготовлений до коміту.

    MM file.txt

Файл має підготовлені зміни, а після `git add` його додатково змінили.

    ?? file.txt

Git ще не відстежує цей файл.

### 6.3. Перевірка кореня репозиторію

    git rev-parse --show-toplevel

### 6.4. Перевірка поточної гілки

    git branch --show-current

### 6.5. Перевірка віддалених репозиторіїв

    git remote -v

Приклад:

    origin  git@github.com:username/nest-exercises.git (fetch)
    origin  git@github.com:username/nest-exercises.git (push)

Адреса залежить від твого репозиторію та способу автентифікації.

## 7. Основні команди для щоденної роботи

### 7.1. Переглянути зміни

    git diff

Показує зміни в робочому дереві, які ще не додані до staging area.

### 7.2. Переглянути підготовлені зміни

    git diff --staged

Показує зміни, які вже додані через `git add` і потраплять до наступного коміту.

### 7.3. Додати один файл

    git add README.md

### 7.4. Додати конкретний каталог

    git add practice/linux/12-developer-workflow/

Git підготує відповідні зміни в каталозі, зокрема нові файли, якщо вони не виключені правилами `.gitignore`.

### 7.5. Додати всі зміни

    git add .

Команда додає зміни в поточному каталозі та його підкаталогах.

Перед використанням перевір, що саме буде додано:

    git status

Для навчальних проєктів `git add .` зручний, але не варто використовувати його автоматично, не перевіривши статус.

### 7.6. Створити коміт

    git commit -m "Add Linux Git notes"

Повідомлення коміту має коротко описувати внесені зміни.

### 7.7. Переглянути історію

    git log --oneline

### 7.8. Відправити коміти на GitHub

    git push

Якщо гілка ще не пов'язана з віддаленою гілкою, може знадобитися:

    git push -u origin main

Тут `main` — назва гілки. Якщо ти працюєш в іншій гілці, вкажи її назву.

## 8. Робочий цикл Git

Для щоденної роботи можна використовувати такий порядок.

### Крок 1. Перевірити поточний стан

    git status

### Крок 2. Отримати інформацію про віддалені зміни

    git fetch origin

Це завантажує інформацію з `origin`, але не зливає зміни в поточну гілку.

### Крок 3. Перевірити локальні та віддалені коміти

    git status -sb

### Крок 4. Внести зміни у файли

Наприклад:

    practice/linux/12-developer-workflow/03-git-from-terminal/README.md

### Крок 5. Перевірити зміни

    git diff

### Крок 6. Додати потрібні файли

    git add practice/linux/12-developer-workflow/03-git-from-terminal/README.md

### Крок 7. Перевірити підготовлені зміни

    git diff --staged

### Крок 8. Створити коміт

    git commit -m "Add Git terminal cheat sheet"

### Крок 9. Відправити коміт

    git push

Цей цикл підходить для звичайної роботи, якщо локальна гілка не відстає від віддаленої та немає конфліктів.

**Важливо:** якщо `git fetch` показав нові віддалені коміти, перед `push` перевір, чи потрібно інтегрувати їх у свою гілку.

## 9. Git і GitHub: локальний та віддалений стан

Git і GitHub — не одне й те саме.

Git — програма для контролю версій. GitHub — сервіс, на якому можна зберігати віддалені Git-репозиторії.

У звичайному проєкті є кілька різних станів:

- робочі файли на диску;
- staging area;
- локальні коміти;
- віддалені коміти, про які Git уже знає;
- актуальний стан репозиторію на GitHub.

### 9.1. Що таке `origin`

`origin` — лише стандартна назва віддаленого репозиторію.

Подивитися адресу:

    git remote -v

Подивитися детальнішу інформацію:

    git remote show origin

### 9.2. Що таке `origin/main`

`origin/main` — remote-tracking branch, тобто локальне посилання на стан гілки `main` на віддаленому репозиторії, який Git востаннє отримав через `fetch`, `pull` або іншу відповідну операцію.

Це не безпосередній перегляд GitHub у реальному часі.

### 9.3. Що таке `origin/HEAD`

`origin/HEAD` зазвичай вказує на гілку, яку віддалений репозиторій визначив як свою типову.

Перевірити:

    git symbolic-ref refs/remotes/origin/HEAD

Можливий результат:

    refs/remotes/origin/main

Якщо посилання не налаштоване, команда може завершитися помилкою.

Подивитися гілки:

    git branch -a

Приклад:

    * main
      remotes/origin/HEAD -> origin/main
      remotes/origin/main

Позначення:

- `main` — локальна гілка.
- `origin/main` — локальне відображення віддаленої гілки.
- `origin/HEAD -> origin/main` — вказівник на типову віддалену гілку.

## 10. `git fetch`, `git pull` і `git push`

Ці три команди виконують різні завдання.

### 10.1. `git fetch`

    git fetch origin

Отримує нові об'єкти та оновлює інформацію про віддалені гілки.

Команда не змінює автоматично файли твоєї поточної гілки.

Після цього можна порівняти гілки:

    git log --oneline main..origin/main

Команда показує коміти, які є в `origin/main`, але відсутні в локальній `main`.

Щоб переглянути коміти, які є в локальній `main`, але відсутні в `origin/main`:

    git log --oneline origin/main..main

Ці приклади припускають, що локальна гілка називається `main`.

### 10.2. `git pull`

    git pull

Отримує зміни з віддаленої гілки, налаштованої для поточної гілки, та інтегрує їх.

Зазвичай інтеграція відбувається через merge або rebase — залежно від конфігурації та параметрів команди.

Якщо потрібно явно вказати джерело:

    git pull origin main

Ця команда інтегрує зміни з `origin/main` у поточну гілку. Перед використанням перевір, чи саме цього ти хочеш.

### 10.3. `git push`

    git push

Відправляє локальні коміти до віддаленого репозиторію для налаштованої upstream-гілки.

Якщо upstream ще не налаштований:

    git push -u origin main

Параметр `-u` налаштовує upstream для подальшої роботи.

### 10.4. Коротке порівняння

| Команда | Призначення |
|---|---|
| `git fetch` | Отримати інформацію про віддалені зміни |
| `git pull` | Отримати та інтегрувати віддалені зміни |
| `git push` | Відправити локальні коміти на сервер |

**Що запам'ятати:** `fetch` дає змогу спочатку перевірити віддалені зміни, а вже потім вирішувати, як їх інтегрувати.

## 11. Робота з гілками

Гілки дають змогу розробляти окремі функції, не змішуючи їх одразу з основною гілкою.

### 11.1. Переглянути локальні гілки

    git branch

### 11.2. Переглянути всі гілки

    git branch -a

### 11.3. Створити гілку

    git branch feature/linux-notes

### 11.4. Перейти до гілки

    git switch feature/linux-notes

### 11.5. Створити гілку та перейти до неї

    git switch -c feature/linux-notes

### 11.6. Повернутися до основної гілки

    git switch main

### 11.7. Відправити нову гілку на GitHub

    git push -u origin feature/linux-notes

### 11.8. Видалити локальну гілку

    git branch -d feature/linux-notes

Git відмовиться видаляти гілку, якщо в ній є незлиті зміни, які він вважає важливими для збереження.

Примусове видалення:

    git branch -D feature/linux-notes

Використовуй `-D` лише тоді, коли впевнений, що зміни не потрібні.

### 11.9. Видалити віддалену гілку

    git push origin --delete feature/linux-notes

Це видаляє гілку на віддаленому репозиторії. Перед виконанням переконайся, що її більше не потрібно зберігати.

## 12. Перегляд історії комітів

### 12.1. Коротка історія

    git log --oneline

Приклад:

    a1b2c3d Add Git terminal cheat sheet
    d4e5f6a Update Linux README
    123abcd Initial commit

### 12.2. Історія з графом гілок

    git log --oneline --graph --decorate --all

Ця команда зручна для перегляду історії та взаємного розташування гілок.

### 12.3. Останні п'ять комітів

    git log -5 --oneline

### 12.4. Інформація про останній коміт

    git show

### 12.5. Інформація про конкретний коміт

    git show a1b2c3d

Використовуй фактичний хеш коміту зі своєї історії.

### 12.6. Порівняти дві гілки

    git log --oneline main..origin/main

Показує коміти, доступні в `origin/main`, але відсутні в `main`.

### 12.7. Переглянути зміни між гілками

    git diff main..origin/main

Це порівнює кінцеві стани дерев файлів двох посилань. Для перегляду різниці між комітами, а не лише кінцевими файлами, варто розуміти різницю між `git diff A..B` та `git diff A...B`.

## 13. Скасування та виправлення змін

Під час роботи важливо розуміти, де саме перебувають зміни: у робочому дереві, staging area чи вже в коміті.

### 13.1. Прибрати файл зі staging area

    git restore --staged README.md

Зміни залишаться у файлі, але перестануть бути підготовленими до коміту.

### 13.2. Відновити файл із останнього коміту

    git restore README.md

Це відкидає непідготовлені зміни у файлі та відновлює його зі стану, який Git використовує як джерело для цієї операції.

**Увага:** непідготовлені зміни можуть бути втрачені.

### 13.3. Відкотити коміт без переписування історії

    git revert <commit-hash>

Створює новий коміт, який скасовує зміни вибраного коміту. Зазвичай це безпечніший варіант для комітів, які вже опубліковані.

### 13.4. Виправити останній коміт

    git commit --amend

Відкриває редактор повідомлення або дозволяє змінити останній коміт. Це може переписати його ідентифікатор.

Якщо коміт уже відправлений на GitHub, не переписуй його без розуміння наслідків для інших учасників.

### 13.5. Чим відрізняються `restore`, `revert` і `reset`

- `git restore` — відновлює файли або змінює їхній стан щодо staging area.
- `git revert` — створює новий коміт, що скасовує попередні зміни.
- `git reset` — пересуває поточний `HEAD` і може змінювати стан індексу та робочих файлів залежно від параметрів.

Перед використанням `git reset --hard` обов'язково перевір, чи немає змін, які потрібно зберегти.

## 14. `.gitignore`

Файл `.gitignore` визначає, які невідстежувані файли Git має ігнорувати.

Приклад для JavaScript / Node.js-проєкту:

    node_modules/
    .next/
    dist/
    coverage/
    .env
    .env.local
    .env.*.local

У проєктах правила потрібно адаптувати до фактичної структури.

### 14.1. Перевірити, чи файл ігнорується

    git check-ignore -v .env.local

Команда показує правило, через яке файл ігнорується, якщо воно є.

### 14.2. Важливий нюанс

`.gitignore` не припиняє відстежувати файл, який уже доданий до Git.

Якщо `.env` уже відстежується, додавання його до `.gitignore` не прибере його з репозиторію.

Щоб прибрати файл з індексу, але залишити локально:

    git rm --cached .env

Потім створи коміт із цими змінами.

**Безпека:** якщо секретний ключ уже потрапив до коміту або на GitHub, простого додавання до `.gitignore` недостатньо. Потрібно відкликати або змінити секрет і, за потреби, окремо очищати історію.

## 15. Конфлікти Git

Конфлікт виникає, коли Git не може автоматично об'єднати зміни, наприклад коли різні коміти змінюють ті самі рядки файлу.

### 15.1. Перевірити стан

    git status

Git покаже файли, які потребують розв'язання конфліктів.

### 15.2. Знайти конфліктні маркери

У файлі можна побачити приблизно такий фрагмент:

    <<<<<<< HEAD
    Локальний варіант
    =======
    Віддалений варіант
    >>>>>>> branch-name

Ці маркери є службовими. Їх потрібно прибрати після вибору правильного вмісту.

### 15.3. Розв'язати конфлікт

1. Відкрий конфліктний файл.
2. Вибери потрібний код або об'єднай обидва варіанти.
3. Видали конфліктні маркери.
4. Перевір результат.
5. Додай виправлений файл до staging area.
6. Заверши merge або rebase відповідно до поточної операції.

Наприклад, після розв'язання конфлікту під час merge:

    git add path/to/file
    git status
    git commit

Після розв'язання конфлікту під час rebase:

    git add path/to/file
    git rebase --continue

Не використовуй команди завершення merge та rebase навмання: спочатку перевір `git status`, щоб зрозуміти, яка операція триває.

### 15.4. Скасувати merge

Якщо merge ще не завершено:

    git merge --abort

### 15.5. Скасувати rebase

Якщо rebase ще триває:

    git rebase --abort

Ці команди можуть не спрацювати, якщо відповідна операція не виконується.

## 16. Робота з Git на двох комп'ютерах

Якщо один репозиторій використовується на Windows та Ubuntu, важливо синхронізувати зміни між пристроями.

### 16.1. На комп'ютері, де потрібно отримати зміни

Перейди до проєкту:

    cd ~/projects/nest-exercises

Перевір стан:

    git status

Отримай інформацію з GitHub:

    git fetch origin

Перевір різницю:

    git log --oneline main..origin/main

Якщо локальна гілка `main` не має незбережених змін і потрібно інтегрувати віддалені коміти:

    git pull --ff-only origin main

Параметр `--ff-only` дозволяє оновити гілку лише тоді, коли це можна зробити без створення merge-коміту. Якщо гілки розійшлися, команда відмовиться виконувати оновлення.

### 16.2. Перед переходом на інший комп'ютер

На першому комп'ютері:

    git status
    git add .
    git diff --staged
    git commit -m "Update Linux learning notes"
    git push

На другому комп'ютері:

    git status
    git fetch origin
    git pull --ff-only

Остання команда використовує налаштовану upstream-гілку. Якщо upstream не налаштований, вкажи віддалений репозиторій і назву гілки явно.

### 16.3. Чому не можна просто копіювати `.git`

Каталог `.git` містить локальну історію, посилання, налаштування та інші службові дані Git.

Зазвичай не потрібно вручну копіювати `.git` між комп'ютерами. Правильний спосіб синхронізації — `fetch`, `pull` і `push` через віддалений репозиторій.

## 17. SSH для GitHub

Для роботи через SSH локальний комп'ютер має бути налаштований, а відкритий SSH-ключ — доданий до GitHub.

### 17.1. Перевірити SSH-з'єднання

    ssh -T git@github.com

За успішної автентифікації GitHub повідомить, що розпізнав твій обліковий запис. SSH-доступ для Git не надає звичайної інтерактивної оболонки на серверах GitHub.

### 17.2. Перевірити адресу віддаленого репозиторію

    git remote -v

SSH-адреса зазвичай має вигляд:

    git@github.com:username/repository.git

HTTPS-адреса зазвичай має вигляд:

    https://github.com/username/repository.git

### 17.3. Перевірити доступ до репозиторію

    git ls-remote origin

Команда запитує посилання та хеші віддаленого репозиторію. Для приватного репозиторію потрібна відповідна автентифікація та доступ.

## 19. Типові помилки

### Помилка 1. Виконав `git commit`, але змін немає на GitHub

Причина: коміт створено лише локально.

Рішення:

    git status
    git push

### Помилка 2. Виконав `git add .`, але не всі потрібні файли додано

Причина може бути в `.gitignore`, у тому, що файли розташовані за межами поточного каталогу, або в тому, що зміни вже були підготовлені раніше.

Перевір:

    git status --short
    git check-ignore -v path/to/file

### Помилка 3. `git push` відхилено через нові віддалені коміти

Спочатку отримай інформацію:

    git fetch origin
    git status -sb
    git log --oneline main..origin/main

Після перевірки виріши, як інтегрувати віддалені зміни. Не застосовуй примусовий push автоматично.

### Помилка 4. `git pull` створює несподіваний merge-коміт

Причина: локальна та віддалена історії розійшлися, а конфігурація дозволяє merge.

Перед інтеграцією перевір:

    git fetch origin
    git status -sb
    git log --oneline --graph --decorate --all

Для простого оновлення без merge-коміту можна використовувати `git pull --ff-only`, якщо історія дозволяє.

### Помилка 5. Git не бачить файл

Перевір:

    git status --short
    git check-ignore -v path/to/file
    git ls-files --error-unmatch path/to/file

Остання команда перевіряє, чи відстежується конкретний файл. Якщо файл не відстежується, команда завершиться помилкою.

### Помилка 6. `fatal: not a git repository`

Причина: поточний каталог не є Git-репозиторієм і не розташований усередині нього.

Перевір:

    pwd
    ls -la
    git rev-parse --show-toplevel

Перейди до правильного каталогу.

### Помилка 7. `Author identity unknown`

Причина: Git не налаштований на ім'я та email автора.

Виправлення:

    git config --global user.name "Your Name"
    git config --global user.email "your-email@example.com"

### Помилка 8. Випадково додав `.env`

Перевір статус і прибери файл зі staging area, якщо коміт ще не створений:

    git restore --staged .env

Потім додай `.env` до `.gitignore`.

Якщо файл уже відстежується в репозиторії, може знадобитися:

    git rm --cached .env

Якщо секрет уже потрапив до віддаленого репозиторію, відклич або заміни його.

### Помилка 9. Немає upstream-гілки

Якщо Git повідомляє, що поточна гілка не має upstream:

    git push -u origin main

Заміни `main` на фактичну назву поточної гілки.

### Помилка 10. Зміни зникли після `git restore`

Команда могла відкинути непідготовлені зміни. Перед відновленням файлів завжди перевір:

    git status
    git diff

Якщо зміни вже втрачені, можливості відновлення залежать від того, чи зберіг їх Git в інших об'єктах або комітах. Не можна гарантувати, що незакомічені зміни вдасться відновити.

## 20. Безпечний алгоритм перед комітом

Перед створенням коміту виконуй перевірку:

    git status
    git diff
    git add path/to/file
    git diff --staged
    git commit -m "Describe the change"

Якщо потрібно додати всі зміни:

    git status
    git add .
    git diff --staged
    git commit -m "Describe the changes"

Перевір, що до коміту не потрапили:

- `.env` та інші файли із секретами;
- `node_modules/`;
- `.next/`;
- згенеровані файли, які не мають зберігатися в репозиторії;
- випадкові тимчасові файли;
- незавершені або непотрібні зміни.

**Головне правило:** перед `git commit` перевіряй саме staging area за допомогою `git diff --staged`.

## 23. Що потрібно пам'ятати

✔ Git працює локально, навіть коли немає інтернету.

✔ GitHub — віддалений сервіс, а Git — система контролю версій.

✔ `git add` готує зміни до коміту.

✔ `git commit` записує зміни в локальну історію.

✔ `git push` відправляє коміти на віддалений репозиторій.

✔ `git fetch` оновлює інформацію про віддалені гілки без автоматичної інтеграції у поточну гілку.

✔ `git pull` отримує та інтегрує зміни.

✔ `origin/main` — локальне відображення віддаленої гілки, а не окрема копія файлів на GitHub.

✔ `git status` — перша команда для діагностики більшості проблем.

✔ `git diff` показує непідготовлені зміни, а `git diff --staged` — підготовлені.

✔ `.gitignore` не припиняє відстежувати файли, які вже додані до Git.

✔ Перед `git push` важливо розуміти, чи не з'явилися нові віддалені коміти.

✔ Не використовуй `git reset --hard` і примусовий `git push`, не розуміючи наслідків.

✔ Перед комітом перевіряй, що саме потрапляє до staging area.

✔ Для роботи на Windows та Ubuntu синхронізуй репозиторій через GitHub, а не копіюй вручну каталог `.git`.

## 26. Головне

Для щоденної розробки на Linux достатньо спочатку впевнено засвоїти основний цикл:

    git status
    git fetch origin
    git status -sb
    git diff
    git add .
    git diff --staged
    git commit -m "Describe the changes"
    git push

Не потрібно механічно виконувати всі команди щоразу. Перевіряй стан репозиторію та обирай команди відповідно до ситуації.

**Найважливіше правило:** розумій, де перебувають твої зміни — у робочому дереві, staging area, локальному коміті чи на віддаленому репозиторії. Це допоможе уникнути більшості типових помилок Git.
