# Environment Files — файли змінних середовища

Файли змінних середовища (`.env`, `.env.local`, `.env.development`, `.env.production`) використовуються для зберігання конфігурації застосунку окремо від вихідного коду.

Вони дозволяють налаштовувати різні середовища запуску, зберігати секрети поза кодом і передавати параметри до Node.js, Express, NestJS та інших застосунків.

---

## 1. Що таке environment variables

**Змінні середовища (environment variables)** — це пари `KEY=value`, які процес отримує під час запуску.

Наприклад:

    NODE_ENV=development
    PORT=3000
    DATABASE_URL=postgresql://localhost:5432/my_database

У Node.js ці значення зазвичай доступні через об'єкт `process.env`.

    console.log(process.env.NODE_ENV);
    console.log(process.env.PORT);

Зверни увагу: значення змінних середовища в Node.js зазвичай представлені як рядки (`string`), навіть якщо вони виглядають як числа або логічні значення.

    PORT=3000

    // process.env.PORT — це рядок "3000", а не число 3000.

    const port = Number(process.env.PORT);

### Навіщо потрібні environment variables

- ✔ Зберігати конфігурацію окремо від коду.
- ✔ Налаштовувати застосунок для різних середовищ.
- ✔ Не записувати паролі та API-ключі безпосередньо в код.
- ✔ Змінювати порт, адресу бази даних та інші параметри без редагування програми.
- ✔ Використовувати різні налаштування локально, на тестовому сервері та в production.
- ✔ Передавати конфігурацію через термінал, Docker або платформу хостингу.

## 2. Основні поняття

### 2.1. Environment variable

Змінна середовища, доступна процесу під час виконання.

    NODE_ENV=development
    PORT=3000

### 2.2. Environment file

Текстовий файл, у якому записують змінні середовища.

    .env

Сам по собі файл `.env` не є універсальним механізмом операційної системи. Програма або інструмент має прочитати його й передати значення до середовища процесу.

### 2.3. Configuration

Конфігурація — параметри, які визначають поведінку застосунку.

Наприклад:

    PORT=3000
    NODE_ENV=development
    LOG_LEVEL=debug

### 2.4. Secret

Секрет — конфіденційне значення, наприклад пароль, токен або приватний ключ.

    DATABASE_URL=postgresql://user:password@localhost:5432/app

Цей приклад показує структуру URL, але реальні паролі не потрібно зберігати в коді, комітах або публічних файлах.

### 2.5. Development і production

- `development` — середовище розробки.
- `test` — середовище тестування.
- `production` — середовище реального використання застосунку.

Для кожного середовища можуть використовуватися різні конфігурації.

## 3. Файли `.env`

### 3.1. Основний файл `.env`

Файл `.env` зазвичай містить змінні для локального запуску застосунку.

    # Application
    NODE_ENV=development
    PORT=3000

    # Database
    DATABASE_URL=postgresql://localhost:5432/my_database

    # Logging
    LOG_LEVEL=debug

Рядки, що починаються з `#`, використовуються як коментарі.

Важливо: формат і підтримка коментарів залежать від програми або бібліотеки, яка читає файл. Для типових Node.js проєктів із підтримкою dotenv наведений синтаксис є звичним.

### 3.2. `.env.example`

Файл-приклад, який показує, які змінні потрібні застосунку.

    NODE_ENV=development
    PORT=3000
    DATABASE_URL=
    API_KEY=

Він не повинен містити справжніх паролів, токенів або інших секретів.

Призначення:

- ✔ Пояснює структуру конфігурації.
- ✔ Допомагає іншому розробнику налаштувати проєкт.
- ✔ Може зберігатися в Git.
- ✔ Спрощує запуск проєкту на іншому комп'ютері.

Типовий порядок роботи:

    cp .env.example .env

Після цього відкрий `.env` і заповни потрібні значення.

### 3.3. `.env.local`

Файл для локальних налаштувань конкретного розробника.

    PORT=3001
    LOG_LEVEL=debug

У різних фреймворках правила завантаження `.env.local` відрізняються. Не припускай, що Node.js автоматично прочитає цей файл: спосіб завантаження потрібно налаштувати.

### 3.4. `.env.development` і `.env.production`

Приклади файлів для різних середовищ.

`.env.development`:

    NODE_ENV=development
    PORT=3000
    LOG_LEVEL=debug

`.env.production`:

    NODE_ENV=production
    PORT=8080
    LOG_LEVEL=error

Назви файлів самі по собі не гарантують автоматичного завантаження. Поведінка залежить від Node.js, бібліотеки конфігурації, фреймворку та команди запуску.

Для production-середовища секрети зазвичай краще зберігати в захищених налаштуваннях платформи хостингу або в спеціальному сховищі секретів.

## 4. Створення та перегляд `.env` у Linux

### 4.1. Перейти до проєкту

    cd ~/projects/nest-exercises

Перевірити поточну директорію:

    pwd

Переглянути файли:

    ls -la

Опція `-a` показує також приховані файли, назви яких починаються з крапки.

### 4.2. Створити `.env`

    touch .env

Перевірити наявність файлу:

    ls -la .env

Відкрити його у VS Code:

    code .env

Якщо команда `code` не працює, можна відкрити проєкт у VS Code і створити файл через файловий менеджер редактора.

### 4.3. Додати змінні

Наприклад, у файлі `.env`:

    NODE_ENV=development
    PORT=3000
    LOG_LEVEL=debug

Для редагування можна використати `nano`:

    nano .env

Основні комбінації клавіш `nano`:

- `Ctrl + O` — записати файл.
- `Enter` — підтвердити назву.
- `Ctrl + X` — вийти.

### 4.4. Переглянути файл

    cat .env

Або:

    less .env

**Увага:** не використовуй `cat .env` у спільних терміналах, записах екрана чи логах, якщо файл містить секрети. Для перевірки наявності файлу достатньо `ls -la`.

### 4.5. Перевірити, чи існує файл

    test -f .env && echo "Файл існує"

Перевірити, чи файл відсутній:

    test ! -f .env && echo "Файлу немає"

Перевірити права доступу:

    ls -l .env

## 5. Приховані файли та права доступу

У Linux ім'я, яке починається з крапки, позначає прихований файл у звичайному перегляді каталогу.

    .env
    .gitignore
    .bashrc

Прихований файл не є автоматично захищеним. Крапка в назві лише впливає на відображення.

### 5.1. Перевірити права

    ls -l .env

Наприклад:

    -rw------- 1 user user 120 Oct 19 10:00 .env

Права `rw-------` означають, що власник може читати й записувати файл, а інші користувачі не мають таких прав.

### 5.2. Обмежити доступ

    chmod 600 .env

Це встановлює права:

- власник — читання та запис;
- група — без доступу;
- інші користувачі — без доступу.

Перевірка:

    ls -l .env

Права `600` корисні для локального файлу із секретами, але не замінюють загальної безпеки системи.

## 6. Змінні середовища в Bash

Перед роботою з `.env` потрібно розрізняти змінні оболонки Bash і змінні середовища процесу.

### 6.1. Створити змінну Bash

    APP_NAME=my-app

Переглянути значення:

    echo "$APP_NAME"

Така змінна існує в поточній оболонці, але не обов'язково передається дочірнім процесам.

### 6.2. Експортувати змінну

    export APP_NAME=my-app

Тепер дочірні процеси можуть отримати цю змінну у своєму середовищі.

Перевірити:

    printenv APP_NAME

Результат:

    my-app

### 6.3. Передати змінну лише одній команді

    PORT=3001 node server.js

Змінна `PORT` передається процесу `node` для цього запуску, але не стає постійною змінною поточної оболонки.

Перевірити іншим прикладом:

    APP_MODE=development printenv APP_MODE

Результат:

    development

Після завершення команди:

    printenv APP_MODE

Якщо `APP_MODE` раніше не була експортована, команда нічого не виведе.

### 6.4. Переглянути змінні середовища

    printenv

Або:

    env

Обидві команди можуть показати конфіденційні значення. Не публікуй повний вивід у повідомленнях, логах або скриншотах.

Перевірити конкретну змінну:

    printenv NODE_ENV

Якщо змінна не встановлена, команда зазвичай нічого не виведе.

### 6.5. Видалити змінну Bash

    unset APP_NAME

Перевірити:

    printenv APP_NAME

`unset` видаляє змінну з поточної оболонки. Він не редагує файл `.env` і не змінює середовище вже запущених процесів.

### 6.6. Встановити змінну на час сеансу

    export NODE_ENV=development
    export PORT=3000

Ці значення діятимуть у поточній оболонці та передаватимуться дочірнім процесам, які запускаються з неї.

Після закриття оболонки ці налаштування зазвичай зникають, якщо вони не були збережені в конфігураційних файлах оболонки.

## 7. Чи може Bash автоматично прочитати `.env`

Звичайний Bash не завантажує файл `.env` автоматично.

Наприклад, команда:

    node server.js

не гарантує, що змінні з `.env` стануть доступними програмі.

Є кілька способів передати значення:

1. Установити змінні безпосередньо в команді.
2. Експортувати їх у Bash.
3. Завантажити `.env` засобами Node.js.
4. Використати бібліотеку конфігурації.
5. Передати змінні через Docker або платформу хостингу.

### 7.1. Варіант для простого `.env` у Bash

Для простого файлу з коректними рядками `KEY=value`, без складних конструкцій shell, можна використати:

    set -a
    source .env
    set +a

Що відбувається:

- `set -a` — автоматично експортує змінні, які створюються або змінюються.
- `source .env` — виконує вміст файлу в поточній оболонці.
- `set +a` — вимикає автоматичне експортування.

**Важливо:** `source` виконує файл як Bash-код. Не застосовуй цей спосіб до невідомого або ненадійного `.env`. Файли для `dotenv` не завжди є коректними shell-скриптами, особливо якщо містять пробіли, лапки, `$`, командні підстановки або інший спеціальний синтаксис.

Для Node.js-проєктів зазвичай краще застосовувати вбудовану підтримку `.env` або бібліотеку, призначену для цього формату.

## 8. `.env` у Node.js

Node.js має вбудовану підтримку файлів середовища в сучасних версіях. Установлювати додаткову бібліотеку для базового завантаження `.env` не завжди потрібно.

### 8.1. Варіант 1 — параметр `--env-file`

Припустимо, структура проєкту така:

    my-app/
    ├── .env
    ├── package.json
    └── server.js

Файл `.env`:

    NODE_ENV=development
    PORT=3000

Файл `server.js`:

    console.log("Environment:", process.env.NODE_ENV);
    console.log("Port:", process.env.PORT);

Запуск:

    node --env-file=.env server.js

Очікуваний результат:

    Environment: development
    Port: 3000

Параметр `--env-file` завантажує змінні з указаного файлу для запуску Node.js. Він доступний у сучасних версіях Node.js, зокрема у версії 24.

Перевірити версію:

    node --version

### 8.2. Варіант 2 — передати шлях через `package.json`

У `package.json` можна додати команду запуску:

    {
      "scripts": {
        "dev": "node --env-file=.env server.js"
      }
    }

Запуск:

    npm run dev

Тепер команда завантажує `.env` перед виконанням `server.js`.

Якщо проєкт уже має поле `scripts`, додай або зміни лише потрібний запис, не видаляючи інші команди.

### 8.3. Варіант 3 — використовувати `--env-file-if-exists`

Якщо файл необов'язковий, сучасні версії Node.js підтримують параметр `--env-file-if-exists`.

    node --env-file-if-exists=.env server.js

Це дозволяє запустити застосунок, навіть якщо файл відсутній. Однак потрібні змінні все одно можуть бути відсутніми, тому застосунок має перевіряти обов'язкові налаштування.

### 8.4. Пріоритет змінних

Якщо значення змінної вже передано через середовище оболонки, воно має пріоритет над значенням із `--env-file`.

Наприклад, у `.env`:

    PORT=3000

Запуск:

    PORT=4000 node --env-file=.env server.js

Програма отримає:

    process.env.PORT === "4000"

Це корисно для тимчасового перевизначення конфігурації без редагування файлу.

## 9. Перевірка змінних у Node.js

### 9.1. Прочитати значення

    console.log(process.env.PORT);

### 9.2. Перевірити наявність змінної

    if (process.env.PORT === undefined) {
      console.error("PORT is not configured");
      process.exit(1);
    }

Перевірка через `=== undefined` дає змогу відрізнити відсутню змінну від порожнього рядка.

### 9.3. Значення за замовчуванням

    const port = Number(process.env.PORT ?? 3000);

Оператор `??` використовує значення праворуч, якщо ліворуч `null` або `undefined`.

Він не замінює порожній рядок `""`, тому для надійної конфігурації потрібна додаткова валідація.

### 9.4. Перевірити числове значення

    const portValue = process.env.PORT ?? "3000";
    const port = Number(portValue);

    if (!Number.isInteger(port) || port < 1 || port > 65535) {
      throw new Error("PORT must be an integer between 1 and 65535");
    }

Не варто покладатися на автоматичне перетворення рядків у числа без перевірки.

### 9.5. Не використовувати `any` у TypeScript

Якщо працюєш із TypeScript, не потрібно оголошувати `process.env` як `any`.

    const databaseUrl = process.env.DATABASE_URL;

Тип такого значення зазвичай `string | undefined`, тому перед використанням потрібно перевірити його наявність.

    const databaseUrl = process.env.DATABASE_URL;

    if (!databaseUrl) {
      throw new Error("DATABASE_URL is required");
    }

    // Після перевірки databaseUrl має тип string.

## 10. `.gitignore` і захист секретів

Файл `.env` із реальними секретами зазвичай не повинен потрапляти до Git.

У `.gitignore` додай:

    # Environment files
    .env
    .env.*
    !.env.example

Цей шаблон ігнорує `.env` та файли на кшталт `.env.local`, `.env.development` і `.env.production`, але дозволяє відстежувати `.env.example`.

Якщо певні `.env.*` файли мають бути в репозиторії, переглянь правила ігнорування та залиш лише потрібні винятки.

### 10.1. Перевірити статус Git

    git status

### 10.2. Переконатися, що `.env` ігнорується

    git check-ignore -v .env

Якщо правило спрацьовує, Git покаже файл і рядок правила, що його ігнорує.

### 10.3. Якщо `.env` уже відстежується Git

Додавання файлу до `.gitignore` не припиняє відстеження вже доданого файлу.

Прибрати його з індексу, залишивши локальну копію:

    git rm --cached .env

Потім зафіксувати зміну:

    git add .gitignore
    git commit -m "Stop tracking environment file"

**Важливо:** якщо секрет уже потрапив у коміт або опублікований репозиторій, одного видалення файлу недостатньо. Секрет потрібно замінити або відкликати. За потреби також очищають історію Git і перевіряють усі місця, де він міг бути оприлюднений.

### 10.4. Перевірити `.env.example`

Приклад без секретів:

    NODE_ENV=development
    PORT=3000
    DATABASE_URL=
    API_KEY=

Документуй назви змінних і призначення значень, але не вставляй справжні паролі.

## 11. Типові змінні середовища для розробника

| Змінна | Призначення | Приклад |
|---|---|---|
| `NODE_ENV` | Середовище Node.js | `development` |
| `PORT` | Порт HTTP-сервера | `3000` |
| `DATABASE_URL` | Адреса підключення до БД | `postgresql://localhost:5432/app` |
| `LOG_LEVEL` | Рівень логування | `debug` |
| `API_KEY` | Ключ доступу до API | Не зберігати реальний ключ у Git |
| `JWT_SECRET` | Секрет для підпису токенів | Не використовувати слабке значення |
| `HOST` | Адреса, на якій слухає сервер | `127.0.0.1` |

Це приклади назв, а не універсальний стандарт. Конкретний застосунок може використовувати інші змінні.

### Важливо про `NODE_ENV`

Значення `NODE_ENV` часто бувають `development`, `test` і `production`.

    NODE_ENV=development node --env-file=.env server.js

Не припускай, що Node.js автоматично вибирає потрібний `.env` за значенням `NODE_ENV`. Файл потрібно завантажити відповідним інструментом або налаштуванням.

## 12. Безпечна робота з `.env`

### 12.1. Не записуй секрети безпосередньо в код

Погано:

    const password = "my-real-password";

Краще:

    const password = process.env.DB_PASSWORD;

Перед використанням перевір, що змінну задано.

### 12.2. Не виводь секрети в консоль

Не роби так:

    console.log(process.env.DATABASE_URL);

У URL бази даних можуть бути логін і пароль.

Краще перевірити лише наявність:

    console.log(
      process.env.DATABASE_URL
        ? "DATABASE_URL is configured"
        : "DATABASE_URL is missing"
    );

### 12.3. Не передавай секрети у відкритих повідомленнях

Не публікуй `.env` у GitHub, чатах, скриншотах, навчальних README або логах CI/CD.

### 12.4. Не використовуй секрети в клієнтському коді

У Next.js та інших frontend-фреймворках частина змінних може спеціально передаватися у браузер. Такі змінні не повинні містити паролів, приватних ключів або інших секретів.

Наприклад, у Next.js змінні з префіксом `NEXT_PUBLIC_` призначені для публічного використання на клієнті.

    NEXT_PUBLIC_APP_NAME=Parish

Не роби так:

    NEXT_PUBLIC_DATABASE_PASSWORD=secret

Усе, що передається клієнтському коду, потрібно вважати доступним користувачеві.

### 12.5. `.env` — не сховище секретів із повним захистом

`.env` — це звичайний текстовий файл. Його безпека залежить від прав доступу, налаштувань Git, системи та способу розгортання застосунку.

Для production використовуй захищені змінні середовища платформи хостингу або спеціальне сховище секретів, коли це доречно.

## 13. Типові помилки

### Помилка 1. `process.env.PORT` повертає `undefined`

Можливі причини:

- змінну не задано;
- `.env` не завантажено;
- шлях до файлу неправильний;
- змінна має іншу назву;
- застосунок запущено з іншого середовища.

Перевір:

    printenv PORT

Потім запусти Node.js із явним завантаженням файлу:

    node --env-file=.env server.js

### Помилка 2. `PORT` сприймається як рядок

Причина: змінні середовища передаються як текст.

    const port = Number(process.env.PORT);

Перевір значення до використання, щоб уникнути `NaN` або некоректного порту.

### Помилка 3. `.env` не видно в `ls`

Причина: це прихований файл.

    ls -la

### Помилка 4. `.env` випадково потрапив у Git

Причина: файл не був доданий до `.gitignore` або вже відстежувався Git.

Перевір:

    git status
    git check-ignore -v .env

Якщо секрет опубліковано, заміни або відклич його.

### Помилка 5. `source .env` не працює

Причина: файл може містити синтаксис, який не відповідає Bash.

Наприклад, `.env` для спеціальної бібліотеки не обов'язково є коректним shell-скриптом.

Рішення: використовуй призначений для формату спосіб завантаження, наприклад:

    node --env-file=.env server.js

### Помилка 6. Файл `.env` є, але змінні не завантажуються

Наявність файлу не означає, що будь-яка програма прочитає його автоматично.

Перевір команду запуску, робочу директорію та спосіб завантаження конфігурації.

### Помилка 7. Значення з `.env` не використовується

Можливо, змінну перевизначає вже встановлена змінна середовища. Для Node.js змінні, передані процесу ззовні, мають пріоритет над значеннями з `--env-file`.

Перевір:

    printenv PORT

Не публікуй значення, якщо воно містить секрет.

## 14. Практична робота: створюємо Node.js застосунок

Мета — навчитися створювати `.env`, передавати його змінні до Node.js та перевіряти конфігурацію.

### Крок 1. Створи директорію

    mkdir env-practice
    cd env-practice

### Крок 2. Ініціалізуй npm-проєкт

    npm init -y

### Крок 3. Створи `.env`

    touch .env

Додай у файл:

    NODE_ENV=development
    PORT=3000
    APP_NAME=Environment Practice

### Крок 4. Створи `server.js`

    const appName = process.env.APP_NAME;
    const environment = process.env.NODE_ENV;
    const port = Number(process.env.PORT);

    if (!appName) {
      throw new Error("APP_NAME is required");
    }

    if (!environment) {
      throw new Error("NODE_ENV is required");
    }

    if (!Number.isInteger(port) || port < 1 || port > 65535) {
      throw new Error("PORT must be a valid port number");
    }

    console.log(`Application: ${appName}`);
    console.log(`Environment: ${environment}`);
    console.log(`Port: ${port}`);

### Крок 5. Запусти застосунок

    node --env-file=.env server.js

Очікуваний результат:

    Application: Environment Practice
    Environment: development
    Port: 3000

### Крок 6. Перевір перевизначення змінної

    PORT=4000 node --env-file=.env server.js

Очікуваний результат:

    Application: Environment Practice
    Environment: development
    Port: 4000

Це демонструє, як змінна, передана командою, перевизначає значення з `.env`.

### Крок 7. Додай `.gitignore`

Створи файл `.gitignore`:

    .env
    .env.*
    !.env.example

Перевір:

    git check-ignore -v .env

Якщо директорія ще не є Git-репозиторієм, команда `git check-ignore` може все одно перевірити правила, але для повноцінної практики можна ініціалізувати Git:

    git init

### Крок 8. Створи `.env.example`

    NODE_ENV=development
    PORT=3000
    APP_NAME=Environment Practice

Цей файл можна зберігати в репозиторії, оскільки він не містить секретів.

## 15. Додаткові практичні вправи

### Вправа 1. Перевірка змінних

- Створи `.env` із `APP_NAME` та `PORT`.
- Виведи значення в Node.js.
- Запусти програму без `--env-file`.
- Порівняй результати.

### Вправа 2. Перевизначення значення

- У `.env` установи `PORT=3000`.
- Запусти програму з `PORT=4000`.
- Поясни, чому програма отримала `4000`.

### Вправа 3. Перевірка відсутніх значень

- Видали `APP_NAME` із `.env`.
- Додай перевірку обов'язкової змінної.
- Переконайся, що програма завершується з помилкою конфігурації.

### Вправа 4. Захист конфігурації

- Додай `.env` до `.gitignore`.
- Створи `.env.example`.
- Перевір, що Git ігнорує `.env`, але дозволяє відстежувати `.env.example`.

### Вправа 5. Різні середовища

Створи файли:

    .env.development
    .env.production

Запусти застосунок із кожним файлом окремо:

    node --env-file=.env.development server.js

    node --env-file=.env.production server.js

Порівняй результати. Пам'ятай, що назва файлу сама по собі не змінює `NODE_ENV`: його значення потрібно визначити у файлі або передати окремо.

## 16. Коли використовувати різні інструменти

| Інструмент | Для чого потрібен |
|---|---|
| `printenv` | Перегляд змінних середовища |
| `export` | Передавання змінної дочірнім процесам |
| `unset` | Видалення змінної з поточної оболонки |
| `source .env` | Виконання файлу в поточному Bash; лише для довіреного shell-сумісного файлу |
| `node --env-file=.env` | Завантаження `.env` під час запуску Node.js |
| `.gitignore` | Виключення файлів із відстеження Git |
| `chmod 600 .env` | Обмеження доступу до файлу власником |
| `.env.example` | Документування потрібних змінних без секретів |

## 19. Мінішпаргалка

Створити файл:

    touch .env

Відкрити файл:

    code .env

Переглянути приховані файли:

    ls -la

Переглянути права доступу:

    ls -l .env

Обмежити доступ до файлу:

    chmod 600 .env

Установити змінну в Bash:

    export PORT=3000

Перевірити змінну:

    printenv PORT

Видалити змінну:

    unset PORT

Передати змінну одній команді:

    PORT=4000 node server.js

Завантажити `.env` у Node.js:

    node --env-file=.env server.js

Перевірити ігнорування Git:

    git check-ignore -v .env

Створити локальний файл із прикладу:

    cp .env.example .env

Припинити відстеження `.env`, залишивши файл локально:

    git rm --cached .env

## 20. Що потрібно запам'ятати

- **Environment variables** — це змінні середовища, доступні процесу під час виконання.
- `.env` — текстовий файл конфігурації, який потрібно явно завантажити.
- У Linux файли з крапкою на початку назви приховані під час звичайного перегляду.
- `printenv` показує змінні середовища, а `export` передає змінні дочірнім процесам.
- `process.env` у Node.js дає доступ до змінних середовища; значення зазвичай є рядками або `undefined`.
- У сучасному Node.js можна використовувати `node --env-file=.env server.js`.
- `.env` із секретами потрібно виключати з Git і захищати правами доступу.
- `.env.example` допомагає документувати потрібні змінні без публікації секретів.
- Змінні з префіксом `NEXT_PUBLIC_` у Next.js не можна використовувати для секретів.
- Для production краще використовувати захищене керування секретами й конфігурацію платформи розгортання.

**Головна ідея:** код визначає, як працює застосунок, а змінні середовища визначають, з якими параметрами він запускається.
