# Node.js and npm — Node.js та npm у Linux

Node.js and npm — це робота з JavaScript поза браузером за допомогою Node.js та керування залежностями й командами проєкту за допомогою npm.

Node.js дає змогу запускати JavaScript на сервері, створювати API, працювати з файлами, запускати інструменти розробки та виконувати JavaScript-програми з термінала. npm допомагає встановлювати бібліотеки, керувати залежностями та запускати скрипти, визначені в `package.json`.

Мета цієї теми — навчитися перевіряти Node.js і npm в Ubuntu, керувати версіями Node.js, створювати JavaScript-проєкти, встановлювати залежності, запускати скрипти та діагностувати типові проблеми під час розробки Node.js / Express / NestJS / Next.js-застосунків.

---

## 1. Що потрібно знати

✔ **Node.js** — середовище виконання JavaScript поза браузером.

✔ **npm** — менеджер пакетів, який постачається разом із типовою інсталяцією Node.js.

✔ **Package** — пакет програмного забезпечення, який можна встановити та використати у проєкті.

✔ **Dependency** — залежність, необхідна для роботи проєкту.

✔ **Development dependency** — залежність, потрібна переважно для розробки, тестування або збирання.

✔ **`node`** — команда для запуску JavaScript-файлів через Node.js.

✔ **`npm`** — команда для керування пакетами та npm-скриптами.

✔ **`npx`** — інструмент для запуску виконуваних команд із пакетів, зокрема тих, які доступні локально в проєкті.

✔ **`package.json`** — файл із метаданими проєкту, залежностями та скриптами.

✔ **`package-lock.json`** — файл, який фіксує конкретне дерево залежностей для відтворюваного встановлення.

✔ **`node_modules/`** — каталог, у якому npm зазвичай розміщує встановлені залежності.

✔ **`npm install`** — встановлює залежності та може оновлювати lock-файл.

✔ **`npm ci`** — встановлює залежності відповідно до lock-файла, якщо він узгоджений із `package.json`.

✔ **`npm run`** — показує доступні npm-скрипти.

✔ **`npm run dev`** — запускає скрипт `dev`, якщо він визначений у `package.json`.

✔ **`npm run build`** — запускає скрипт `build`, якщо він визначений у `package.json`.

✔ **`nvm`** — менеджер версій Node.js, який дає змогу встановлювати й перемикати версії Node.js для поточного користувача.

✔ **`PATH`** — змінна середовища, у якій перелічено каталоги для пошуку виконуваних команд.

## 2. Як працюють Node.js і npm

Типовий процес роботи з Node.js-проєктом:

    Встановлення Node.js
            ↓
    Створення package.json
            ↓
    Встановлення залежностей
            ↓
    Написання коду
            ↓
    Запуск npm-скриптів
            ↓
    Тестування та збирання проєкту

Наприклад, Node.js може виконувати файл:

    node app.js

А npm може запускати визначений у `package.json` скрипт:

    npm run dev

Різниця:

- `node` безпосередньо запускає JavaScript-файл або інший підтримуваний Node.js-вхід.
- `npm` керує залежностями та виконує скрипти проєкту.
- `npx` допомагає запускати команди пакетів без необхідності глобально встановлювати кожен інструмент.

## 3. Перевірка встановленого Node.js

### 3.1. Перевірити версію Node.js

    node --version

Або:

    node -v

Приклад результату:

    v24.21.0

Точна версія залежить від встановленого середовища.

### 3.2. Перевірити шлях до Node.js

    command -v node

Ця команда показує, який виконуваний файл знайде поточна оболонка.

Приклад можливого результату:

    /home/user/.nvm/versions/node/v24.21.0/bin/node

Якщо Node.js встановлений через `nvm`, шлях зазвичай містить `.nvm/versions/node/`.

### 3.3. Перевірити npm

    npm --version

Або:

    npm -v

### 3.4. Перевірити шлях до npm

    command -v npm

### 3.5. Перевірити npx

    npx --version

У сучасних версіях npm `npx` постачається разом із npm.

### 3.6. Перевірити всі три команди

    node --version
    npm --version
    npx --version

Якщо всі команди працюють, основні інструменти доступні в поточному терміналі.

## 4. Перевірка середовища Node.js

### 4.1. Переглянути інформацію про Node.js

    node -p "process.version"

### 4.2. Перевірити платформу та архітектуру

    node -p "process.platform"
    node -p "process.arch"

Приклади можливих результатів:

    linux
    x64

### 4.3. Переглянути каталоги модулів

    npm root
    npm root -g

`npm root` показує каталог локальних залежностей для поточного npm-контексту.

`npm root -g` показує каталог глобально встановлених пакетів.

### 4.4. Переглянути конфігурацію npm

    npm config list

Щоб побачити джерела налаштувань:

    npm config list --long

Не публікуй вивід без перевірки: конфігурація може містити приватні адреси реєстрів або інші дані, які не варто розголошувати.

### 4.5. Перевірити змінну PATH

    echo "$PATH"

Перевірити, звідки запускаються команди:

    command -v node
    command -v npm

Якщо встановлено кілька версій Node.js, ці команди допоможуть зрозуміти, яка версія використовується зараз.

## 5. Встановлення Node.js в Ubuntu

Для розробки бажано використовувати менеджер версій Node.js, наприклад `nvm`, особливо якщо різні проєкти потребують різних версій.

Є кілька способів установлення Node.js:

- через системний менеджер пакетів;
- через менеджер версій, наприклад `nvm`;
- через інші офіційні дистрибутиви Node.js.

Не варто без потреби змішувати різні способи встановлення, оскільки це може призвести до плутанини з `PATH` та версіями.

### 5.1. Перевірити системний пакет

    apt policy nodejs npm

Команда показує доступну та встановлену версію пакетів з APT-репозиторіїв.

Версія Node.js у стандартному репозиторії Ubuntu може відрізнятися від версії, потрібної для сучасних проєктів.

### 5.2. Чому варто розглянути nvm

`nvm` дозволяє:

- встановлювати кілька версій Node.js;
- перемикатися між версіями;
- вибирати версію для поточної оболонки;
- не вимагати `sudo` для звичайного встановлення Node.js у домашній каталог.

Якщо Node.js уже встановлено через `nvm` і він працює, не потрібно повторно встановлювати його через APT без конкретної причини.

## 6. Робота з nvm

`nvm` — менеджер версій Node.js для користувача. Він зазвичай встановлюється в домашній каталог і підключається до Bash через конфігурацію оболонки.

### 6.1. Перевірити, чи встановлений nvm

    command -v nvm

Якщо команда нічого не виводить, це не завжди означає, що `nvm` відсутній. `nvm` зазвичай є функцією оболонки, тому перевір також:

    type nvm

### 6.2. Переглянути встановлені версії Node.js

    nvm ls

### 6.3. Переглянути доступні для встановлення версії

    nvm ls-remote

Команда отримує список доступних версій. Для цього потрібне мережеве з'єднання.

### 6.4. Встановити LTS-версію

    nvm install --lts

LTS означає Long-Term Support — версію з тривалою підтримкою.

Для навчальних і робочих проєктів зазвичай доцільно використовувати підтримувану LTS-версію, якщо проєкт не вимагає іншої.

### 6.5. Перемкнутися на LTS

    nvm use --lts

### 6.6. Вибрати конкретну встановлену версію

Наприклад:

    nvm use 24

Це вибирає відповідну встановлену версію гілки Node.js 24, якщо вона доступна у твоєму `nvm`.

### 6.7. Зробити версію типовою

    nvm alias default 24

Після відкриття нової оболонки `nvm` зазвичай використовуватиме цю версію за замовчуванням.

### 6.8. Перевірити результат

    node --version
    npm --version
    command -v node

### 6.9. Видалити непотрібну версію

    nvm uninstall 22

Це приклад. Перед видаленням перевір, чи не потрібна ця версія для іншого проєкту.

**Важливо:** не видаляй системний Node.js навмання, якщо не розумієш, який пакет або інструмент від нього залежить.

## 7. Версія Node.js для конкретного проєкту

Різні проєкти можуть використовувати різні версії Node.js.

Наприклад:

    ~/projects/
    ├── next-exercises/
    ├── nest-exercises/
    └── parish/

Не обов'язково всі проєкти мають однакові вимоги до Node.js.

### 7.1. Файл `.nvmrc`

У корені проєкту можна створити файл:

    .nvmrc

Наприклад, його вміст:

    24

Після переходу до каталогу проєкту можна виконати:

    nvm use

`nvm` прочитає версію з `.nvmrc`.

### 7.2. Створити `.nvmrc` через термінал

У корені проєкту:

    printf '24\n' > .nvmrc

Використовуй номер версії, який відповідає вимогам проєкту та встановлений у твоєму середовищі.

### 7.3. Перевірити версію після перемикання

    nvm use
    node --version

### 7.4. `.nvmrc` не встановлює Node.js автоматично

Файл `.nvmrc` лише вказує бажану версію для інструментів, які вміють його читати.

Якщо потрібної версії немає, спочатку встанови її:

    nvm install

Після цього:

    nvm use

### 7.5. Перевіряти вимоги проєкту

Версія Node.js може бути зазначена в:

- `.nvmrc`;
- `package.json` у полі `engines`;
- документації проєкту;
- CI-конфігурації;
- Docker-конфігурації, якщо проєкт використовує Docker.

## 8. Створення Node.js-проєкту

### 8.1. Створити каталог

    mkdir node-practice
    cd node-practice

### 8.2. Ініціалізувати npm-проєкт

    npm init -y

Команда створює початковий `package.json` з типовими значеннями.

### 8.3. Переглянути package.json

    cat package.json

Приклад структури:

    {
        "name": "node-practice",
        "version": "1.0.0",
        "description": "",
        "main": "index.js",
        "scripts": {
            "test": "echo \"Error: no test specified\" && exit 1"
        },
        "keywords": [],
        "author": "",
        "license": "ISC"
    }

Фактичний вміст залежить від версії npm та параметрів ініціалізації.

### 8.4. Створити JavaScript-файл

    touch app.js

Відкрити його у VS Code:

    code app.js

Додати код:

    "use strict";

    console.log("Hello from Node.js!");

### 8.5. Запустити файл

    node app.js

Результат:

    Hello from Node.js!

### 8.6. Запустити файл за абсолютним або відносним шляхом

    node ./app.js

Node.js запускає файл, вказаний у команді.

## 9. Модулі JavaScript у Node.js

Node.js підтримує CommonJS і ECMAScript Modules (ESM).

### 9.1. CommonJS

Приклад:

    const path = require("node:path");

    console.log(path.basename("/home/user/projects/app.js"));

CommonJS використовує `require()` та `module.exports`.

### 9.2. ECMAScript Modules (ESM)

Приклад:

    import path from "node:path";

    console.log(path.basename("/home/user/projects/app.js"));

ESM використовує `import` та `export`.

### 9.3. Увімкнути ESM у package.json

У `package.json`:

    {
        "type": "module"
    }

Якщо `package.json` уже містить інші поля, додай `"type": "module"` до наявного об'єкта, не замінюючи весь файл.

### 9.4. Файли `.mjs` і `.cjs`

- `.mjs` явно позначає файл як ECMAScript Module.
- `.cjs` явно позначає файл як CommonJS.

Це може бути корисно, коли потрібно використовувати різні системи модулів в одному проєкті.

### 9.5. Важливо

Не змішуй синтаксис модулів навмання. Спосіб інтерпретації `.js` залежить, зокрема, від поля `"type"` у найближчому `package.json`.

## 10. Основи package.json

`package.json` — один із центральних файлів Node.js-проєкту.

### 10.1. Основні поля

- `name` — назва пакета.
- `version` — версія пакета.
- `description` — короткий опис.
- `type` — система модулів для файлів `.js`.
- `scripts` — команди проєкту.
- `dependencies` — залежності для роботи застосунку.
- `devDependencies` — залежності для розробки.
- `engines` — заявлені вимоги до середовища, наприклад Node.js.
- `private` — забороняє випадкову публікацію пакета в npm registry, якщо має значення `true`.

### 10.2. Приклад package.json

    {
        "name": "node-practice",
        "version": "1.0.0",
        "private": true,
        "type": "module",
        "scripts": {
            "start": "node app.js",
            "dev": "node --watch app.js"
        }
    }

Це приклад невеликого Node.js-проєкту.

### 10.3. Запустити скрипт start

    npm start

Для скрипта з назвою `start` команда `npm start` є скороченим способом запуску.

### 10.4. Запустити скрипт dev

    npm run dev

У наведеному прикладі `node --watch` перезапускає програму після виявлення змін у файлах, за якими стежить Node.js.

### 10.5. Перевірити доступні скрипти

    npm run

### 10.6. Переглянути конкретне поле package.json

    npm pkg get name
    npm pkg get scripts
    npm pkg get dependencies

Це зручніше, ніж вручну читати весь файл, коли потрібно швидко перевірити певну секцію.

## 11. npm-скрипти

npm-скрипти дозволяють визначати короткі команди для типових задач проєкту.

### 11.1. Приклад scripts

    {
        "scripts": {
            "start": "node app.js",
            "dev": "node --watch app.js",
            "check": "node --check app.js"
        }
    }

Це лише секція `scripts`. У реальному `package.json` вона має бути частиною одного JSON-об'єкта.

### 11.2. Запустити скрипт

    npm run check

### 11.3. Запустити скрипт start

    npm start

### 11.4. Передати аргументи npm-скрипту

    npm run check -- --some-flag

Подвійний дефіс `--` відокремлює аргументи, які npm має передати скрипту, від параметрів самого npm. Конкретні аргументи залежать від команди, яку запускає скрипт.

### 11.5. Навіщо використовувати scripts

Замість запам'ятовування довгих команд можна використовувати зрозумілі назви:

    npm run dev
    npm run build
    npm run test
    npm run lint

Кожен скрипт повинен бути визначений у `package.json`, інакше npm повідомить, що такої команди немає.

## 12. Встановлення залежностей

npm допомагає встановлювати пакети, які потрібні проєкту.

### 12.1. Встановити залежність

Наприклад, Express:

    npm install express

Ця команда встановлює пакет і зазвичай додає його до `dependencies` у `package.json`.

### 12.2. Встановити залежність для розробки

Наприклад, TypeScript:

    npm install --save-dev typescript

Залежність буде записана до `devDependencies`.

### 12.3. Скорочений синтаксис

    npm install express
    npm i express

Обидві команди встановлюють пакет.

### 12.4. Встановити залежності наявного проєкту

Якщо є `package.json`:

    npm install

npm встановить залежності та за потреби оновить `package-lock.json`.

### 12.5. Перевірити встановлені пакети

    npm ls

### 12.6. Переглянути пакети верхнього рівня

    npm ls --depth=0

Ця команда показує прямі залежності проєкту без повного дерева вкладених залежностей.

### 12.7. Видалити пакет

    npm uninstall express

Пакет буде видалений із залежностей проєкту та з відповідних записів npm.

### 12.8. Перевірити інформацію про пакет

    npm view express version

Команда показує інформацію з npm registry. Для виконання потрібне мережеве з'єднання.

## 13. dependencies і devDependencies

У Node.js-проєктах важливо розрізняти залежності застосунку та інструменти розробки.

### 13.1. dependencies

Зазвичай містить пакети, потрібні застосунку для виконання.

Приклад:

    npm install express

### 13.2. devDependencies

Зазвичай містить інструменти для розробки, перевірки та збирання.

Приклад:

    npm install --save-dev typescript

### 13.3. Переглянути залежності

    npm pkg get dependencies
    npm pkg get devDependencies

### 13.4. Чому це важливо

У production-середовищі може бути достатньо лише залежностей, потрібних для виконання застосунку. Інструменти тестування, форматування та збирання можуть бути не потрібні після завершення build-процесу.

Однак конкретний поділ залежить від архітектури застосунку та процесу розгортання.

## 14. package-lock.json

`package-lock.json` фіксує точні версії пакетів і структуру залежностей, які npm має встановлювати.

### 14.1. Для чого потрібен lock-файл

Він допомагає:

- відтворювати встановлення залежностей;
- узгоджувати середовище між комп'ютерами;
- зменшувати відмінності між локальним запуском і CI;
- відстежувати зміни у дереві залежностей.

### 14.2. Чи потрібно додавати package-lock.json до Git

Для звичайних застосунків, які використовують npm, `package-lock.json` зазвичай потрібно комітити.

Він дозволяє іншим розробникам отримувати узгоджений набір залежностей.

### 14.3. Чи потрібно комітити node_modules

Зазвичай ні.

У `.gitignore` часто додають:

    node_modules/

Після клонування проєкту залежності можна відновити за допомогою npm.

### 14.4. Що запам'ятати

- `package.json` описує залежності та скрипти.
- `package-lock.json` фіксує конкретне дерево залежностей.
- `node_modules/` містить встановлені файли пакетів.

---

## 15. npm install і npm ci

Ці команди схожі, але призначені для різних сценаріїв.

### 15.1. npm install

    npm install

Застосовується для встановлення залежностей під час звичайної розробки. Може оновити lock-файл, якщо цього вимагають зміни або стан залежностей.

### 15.2. npm ci

    npm ci

Призначений для чистого та відтворюваного встановлення залежностей за lock-файлом.

Особливості `npm ci`:

- вимагає наявного `package-lock.json` або іншого підтримуваного npm lock-файла;
- завершується помилкою, якщо lock-файл не узгоджений із `package.json`;
- видаляє наявний `node_modules` перед установленням;
- не призначений для оновлення lock-файла.

### 15.3. Коли використовувати npm ci

Наприклад, після клонування проєкту:

    git clone <repository-url>
    cd <repository-directory>
    npm ci

У цьому прикладі заміни значення в кутових дужках на фактичні адресу репозиторію та назву каталогу.

`npm ci` особливо корисний у CI-системах і в проєктах, де важлива відтворюваність середовища.

## 16. npx

`npx` дозволяє запускати команди пакетів, не обов'язково встановлюючи їх глобально.

### 16.1. Запустити локальний інструмент

Якщо пакет містить виконувану команду, її часто можна запускати через:

    npx <command>

Конкретна команда залежить від пакета.

### 16.2. Приклад запуску TypeScript

Якщо TypeScript встановлено локально:

    npx tsc --version

### 16.3. Запуск пакета без локального встановлення

Для деяких пакетів `npx` може запропонувати завантажити пакет, якщо він не знайдений локально.

Перед підтвердженням перевір назву пакета та його джерело.

### 16.4. Чому не потрібно встановлювати все глобально

Локальні залежності:

- можуть мати різні версії в різних проєктах;
- зазвичай фіксуються в `package.json` та lock-файлі;
- дозволяють команді використовувати узгоджені інструменти;
- не вимагають глобальної інсталяції кожного інструмента.

## 17. Глобальні пакети npm

Глобальне встановлення робить команду доступною поза межами одного конкретного проєкту, якщо каталог виконуваних файлів є в `PATH`.

### 17.1. Переглянути глобальні пакети

    npm ls -g --depth=0

### 17.2. Встановити пакет глобально

    npm install -g <package-name>

Заміни `<package-name>` на назву пакета, який справді потрібно встановити.

### 17.3. Перевірити глобальний каталог

    npm root -g
    npm prefix -g

### 17.4. Коли глобальне встановлення доречне

Глобально можна встановлювати інструменти, які мають бути доступні як команди на рівні користувача.

Однак для більшості інструментів, що використовуються конкретним проєктом, локальна установка є кращою, оскільки версія інструмента зберігається в залежностях проєкту.

### 17.5. Чи потрібно використовувати sudo

Якщо Node.js встановлений через `nvm`, глобальні пакети зазвичай встановлюються в каталог користувача, тому `sudo` для `npm install -g` не потрібен.

Якщо npm встановлений системно, глобальне встановлення може вимагати іншого налаштування прав. Не використовуй `sudo npm install -g` автоматично: спочатку перевір, як встановлено Node.js і де npm зберігає глобальні пакети.

## 18. Оновлення та перевірка залежностей

### 18.1. Перевірити застарілі залежності

    npm outdated

Команда показує залежності, для яких доступні новіші версії відповідно до інформації з npm registry та діапазонів версій.

### 18.2. Перевірити дерево залежностей

    npm ls

### 18.3. Перевірити вразливості

    npm audit

Команда аналізує залежності за відомими повідомленнями про вразливості, доступними npm.

### 18.4. Переглянути запропоновані виправлення

    npm audit fix

Ця команда може змінити встановлені залежності та lock-файл. Перед запуском у важливому проєкті перевір поточний стан Git і ознайомся з результатами `npm audit`.

Не запускай `npm audit fix --force` автоматично: він може встановлювати версії, які містять несумісні зміни.

### 18.5. Безпечний порядок роботи

    git status
    npm outdated
    npm audit
    git diff

Після оновлення залежностей перевір, що змінилося, та запусти тести або інші перевірки проєкту.

## 19. Змінні середовища в Node.js

Змінні середовища дають змогу передавати налаштування програмі без жорсткого запису їх у код.

Наприклад:

- порт сервера;
- адреса бази даних;
- режим запуску;
- зовнішні API-адреси;
- секрети й токени.

### 19.1. Переглянути змінну середовища

    echo "$NODE_ENV"

Якщо змінна не задана, команда може нічого не вивести.

### 19.2. Тимчасово задати змінну для команди

    NODE_ENV=development node app.js

Змінна діятиме для цього процесу та його дочірніх процесів, якщо вони успадковують середовище.

### 19.3. Прочитати змінну в Node.js

    console.log(process.env.NODE_ENV);

### 19.4. Задати порт

    PORT=3000 node app.js

У коді:

    const port = process.env.PORT ?? 3000;

У цьому прикладі використано синтаксис ECMAScript Modules / сучасного JavaScript. Якщо проєкт використовує TypeScript, перевір типи та налаштування середовища.

### 19.5. Чому не можна комітити секрети

Не записуй паролі, API-ключі та приватні токени безпосередньо в код або у файли, які потрапляють до Git.

Для локального проєкту можна використовувати `.env` і відповідний механізм завантаження змінних середовища.

Додай приватні файли до `.gitignore`, наприклад:

    .env
    .env.local
    .env.*.local

Уточни правила для свого проєкту: деякі шаблонні файли на кшталт `.env.example` можуть бути корисними для команди й можуть комітитися без секретних значень.

## 20. Node.js і файли .env

Node.js-проєкти часто використовують `.env` для локальної конфігурації.

### 20.1. Приклад .env

    PORT=3000
    NODE_ENV=development

Цей файл має містити реальні значення лише локально, якщо вони не призначені для публікації.

### 20.2. Підтримка .env у сучасному Node.js

У сучасних версіях Node.js можна використовувати параметр:

    node --env-file=.env app.js

Команда завантажує змінні з `.env` у середовище процесу перед запуском програми. Доступність цього параметра залежить від версії Node.js, тому перевір документацію для встановленої версії.

### 20.3. Перевірити значення в коді

    console.log(process.env.PORT);

### 20.4. Важливо

- Не виводь секрети в консоль без потреби.
- Не коміть `.env` з приватними значеннями.
- Не вважай `.env` безпечним сховищем секретів: це звичайний текстовий файл.
- У production-середовищі змінні часто задають через конфігурацію хостингу або інший механізм керування секретами.

## 23. Робота з Node.js-проєктами на двох комп'ютерах

Якщо використовуєш один репозиторій на Windows та Ubuntu, потрібно розділяти код проєкту та локальні залежності.

### 23.1. Що зазвичай комітять

- вихідний код;
- `package.json`;
- `package-lock.json`;
- конфігураційні файли проєкту;
- документацію;
- необхідні міграції та інші файли, які є частиною проєкту.

### 23.2. Що зазвичай не комітять

- `node_modules/`;
- секретний `.env`;
- локальні тимчасові файли;
- згенеровані каталоги, якщо вони не потрібні для роботи репозиторію.

Приклад `.gitignore`:

    node_modules/
    .env
    .env.local
    .env.*.local
    .next/
    dist/
    coverage/

Адаптуй список під фактичну структуру проєкту.

### 23.3. На новому комп'ютері

Після отримання змін:

    git pull
    npm ci

`npm ci` встановлює залежності локально для поточного середовища. Каталог `node_modules` не потрібно переносити вручну між Windows і Linux.

### 23.4. Чому це важливо

Деякі залежності містять платформозалежні бінарні файли або запускають різні сценарії встановлення залежно від операційної системи.

Тому краще відновлювати залежності на кожному комп'ютері окремо.

## 24. Типові помилки та їх вирішення

### Помилка 1. `node: command not found`

Причина: Node.js не встановлений або його каталог відсутній у `PATH`.

Перевір:

    command -v node
    echo "$PATH"

Якщо використовуєш `nvm`:

    type nvm
    nvm ls
    nvm use --lts

Якщо `nvm` не завантажується, перевір конфігурацію Bash і відкрий новий термінал.

### Помилка 2. `npm: command not found`

Перевір:

    command -v npm
    node --version
    npm --version

У типовому середовищі npm встановлюється разом із Node.js. Якщо Node.js доступний, але npm — ні, перевір спосіб установлення Node.js і стан `PATH`.

### Помилка 3. Неправильна версія Node.js

Перевір:

    node --version
    command -v node
    nvm ls

Якщо проєкт містить `.nvmrc`:

    nvm use

### Помилка 4. `npm run dev` повідомляє, що скрипт відсутній

Переглянь скрипти:

    npm run

Перевір `package.json`:

    npm pkg get scripts

Можливо, проєкт використовує іншу команду запуску, наприклад `npm start`.

### Помилка 5. `Cannot find module`

Можливі причини:

- залежності не встановлено;
- неправильний шлях до файла;
- імпорт не відповідає структурі проєкту;
- проблема із системою модулів.

Перевір:

    npm ls --depth=0
    pwd
    ls -la

Якщо залежності потрібні, а `node_modules` відсутній, виконай відповідну команду встановлення.

### Помилка 6. `EACCES: permission denied`

Причина може бути в правах доступу до каталогу або файлу.

Перевір:

    ls -ld .
    ls -l

Якщо помилка стосується глобального встановлення npm, спочатку перевір спосіб установлення Node.js. Не виправляй проблему автоматично через `sudo npm install -g`.

### Помилка 7. `EADDRINUSE`

Це означає, що потрібний порт уже зайнятий іншим процесом.

Перевір, який процес слухає порт. Наприклад, для порту `3000`:

    ss -ltnp

Команда покаже TCP-сокети, що перебувають у стані прослуховування. Для перегляду процесів можуть знадобитися додаткові права або інші інструменти.

Якщо можеш змінити порт застосунку, задай інший порт через відповідну змінну середовища або налаштування проєкту.

### Помилка 8. `npm ci` завершується помилкою

Перевір, чи є обидва файли:

    ls -l package.json package-lock.json

Якщо `package-lock.json` не узгоджений із `package.json`, потрібно з'ясувати, чому файли розходяться. Не видаляй lock-файл автоматично в командному проєкті: спочатку перевір зміни Git і домовленості проєкту.

### Помилка 9. Пакет не встановлюється

Перевір:

    node --version
    npm --version
    npm config get registry

Можливі причини:

- проблеми з мережею;
- неправильна адреса registry;
- несумісна версія Node.js;
- проблеми з правами;
- помилка у назві пакета;
- несумісність залежностей.

### Помилка 10. Після перемикання Node.js npm працює інакше

Перевір:

    command -v node
    command -v npm
    node --version
    npm --version

Різні версії Node.js, встановлені через `nvm`, можуть використовувати різні версії npm.

### Помилка 11. Node.js працює у звичайному терміналі, але не у VS Code

Перевір:

    ps -p $$ -o comm=
    echo "$PATH"
    command -v node
    command -v npm

Створи новий інтегрований термінал після зміни конфігурації оболонки. Якщо використовуєш `nvm`, перевір, чи ініціалізується він у Bash.

### Помилка 12. Залежності працюють на Windows, але не на Ubuntu

Не копіюй `node_modules` між різними операційними системами.

У каталозі проєкту виконай:

    npm ci

Якщо проблема залишається, перевір повідомлення про помилку, версію Node.js та документацію конкретного пакета.

## 25. Безпека під час роботи з npm

npm спрощує використання сторонніх пакетів, але залежності можуть виконувати код під час встановлення або запуску.

✔ Перевіряй назву пакета перед установленням.

✔ Використовуй пакети з надійних джерел.

✔ Не запускай незнайомі команди з інтернету без розуміння їхнього призначення.

✔ Не коміть секрети та приватні токени.

✔ Переглядай зміни `package.json` і `package-lock.json`.

✔ Використовуй `npm audit` як один із засобів перевірки безпеки залежностей.

✔ Не вважай результат `npm audit` гарантією повної безпеки.

✔ Не використовуй `sudo` для npm-команд автоматично.

✔ Перед запуском скриптів перевіряй, що вони роблять.

Переглянути скрипти:

    npm pkg get scripts

Переглянути залежності:

    npm ls --depth=0

Переглянути зміни файлів:

    git diff

## 29. Що потрібно пам'ятати

✔ Node.js запускає JavaScript поза браузером.

✔ npm керує пакетами, залежностями та скриптами проєкту.

✔ `node app.js` запускає файл безпосередньо.

✔ `npm run dev` запускає скрипт `dev`, визначений у `package.json`.

✔ `package.json` описує проєкт, його залежності та скрипти.

✔ `package-lock.json` допомагає відтворювати дерево залежностей.

✔ `node_modules/` зазвичай не потрібно комітити до Git.

✔ `npm ci` підходить для відтворюваного встановлення залежностей за lock-файлом.

✔ `npm install` використовують для звичайного встановлення та керування залежностями.

✔ `dependencies` зазвичай містить пакети для роботи застосунку.

✔ `devDependencies` зазвичай містить інструменти для розробки.

✔ `npx` дозволяє запускати команди пакетів без обов'язкового глобального встановлення.

✔ `nvm` дозволяє перемикатися між версіями Node.js.

✔ `.nvmrc` допомагає вказати бажану версію Node.js для проєкту.

✔ `command -v node` і `command -v npm` допомагають визначити, які команди використовує оболонка.

✔ Не встановлюй глобальні пакети через `sudo` автоматично.

✔ Перед оновленням залежностей перевіряй стан Git.

✔ Не коміть секрети у `package.json`, `.env` або вихідний код.

## 32. Головне

Для щоденної роботи з Node.js у Linux достатньо впевнено використовувати такий цикл:

    cd ~/projects/nest-exercises
    node --version
    npm --version
    npm ci
    npm run dev

Це базовий приклад: він передбачає, що каталог є Node.js-проєктом, має узгоджений lock-файл і містить скрипт `dev`.

Якщо потрібно створити просту JavaScript-програму з нуля:

    mkdir node-practice
    cd node-practice
    npm init -y
    touch app.js
    node app.js

**Найважливіше правило:** розумій, яка версія Node.js використовується, звідки запускаються `node` і `npm`, які залежності потрібні проєкту та які команди визначені в `package.json`. Це основа стабільної роботи з Node.js, Express, NestJS і Next.js у Linux.
