# 04. Ports and Sockets

Порти (ports) і сокети (sockets) — фундаментальні поняття мережевої взаємодії в Linux. Вони допомагають зрозуміти, як операційна система спрямовує мережеві з'єднання до потрібних програм, як працюють вебсервери та API, а також як знаходити проблеми, коли застосунок не може запуститися або приймати запити.

Для Full Stack JavaScript-розробника ця тема особливо важлива під час роботи з Node.js, Express, NestJS, PostgreSQL, локальними серверами та розгортанням застосунків.

## 1. Що потрібно знати

✔ **IP-адреса** — адреса мережевого інтерфейсу, яка допомагає визначити вузол у мережі.

✔ **Порт (port)** — числовий ідентифікатор кінцевої точки транспортного рівня, який використовується TCP або UDP для розрізнення сервісів і з'єднань.

✔ **Сокет (socket)** — програмний об'єкт, через який процес взаємодіє з мережею або, у ширшому значенні, з іншим процесом.

✔ **TCP** — транспортний протокол зі встановленням з'єднання та надійним упорядкованим передаванням байтів.

✔ **UDP** — транспортний протокол без встановлення з'єднання, який передає окремі датаграми без гарантії доставки.

✔ **Listening socket** — сокет, який очікує на вхідні з'єднання або датаграми відповідно до протоколу й режиму роботи.

✔ **Local port** — локальний порт, який використовує програма.

✔ **Remote port** — порт віддаленого сервісу, до якого підключається клієнт.

✔ **Port conflict** — ситуація, коли програма не може прив'язати сокет до потрібної адреси та порту через конфлікт або інше обмеження.

✔ **Loopback** — локальний мережевий інтерфейс, зазвичай `lo`, доступний через адреси `127.0.0.1` та `::1`.

✔ **Firewall** — механізм фільтрації мережевого трафіку.

✔ `ss` — основна сучасна Linux-утиліта для перегляду сокетів і мережевих з'єднань.

✔ `lsof` — утиліта для перегляду відкритих файлів і ресурсів процесів, включно з мережевими сокетами.

## 2. Що таке порт

Порт допомагає операційній системі визначити, якому сервісу або процесу передати мережеві дані.

Наприклад, один комп'ютер може одночасно запускати:

- вебсервер на порту `3000`;
- інший вебсервер на порту `4000`;
- PostgreSQL на порту `5432`;
- SSH-сервер на порту `22`.

Усі ці програми можуть використовувати одну IP-адресу, але приймати з'єднання на різних портах.

### 2.1. IP-адреса та порт

Приклад адреси:

    192.168.1.10:3000

Тут:

- `192.168.1.10` — IP-адреса вузла;
- `3000` — порт сервісу.

Для IPv4 запис `IP:port` є поширеним способом позначення адреси сервісу.

Для IPv6 адреси зазвичай записують у квадратних дужках, щоб відокремити адресу від порту:

    [2001:db8::10]:3000

`2001:db8::10` тут є прикладом IPv6-адреси з документаційного діапазону, а не реальною адресою сервера.

### 2.2. Діапазон портів

TCP і UDP використовують 16-бітні номери портів: від `0` до `65535`.

| Діапазон | Назва | Призначення |
|---|---|---|
| `0–1023` | Well-known ports | Загальновідомі порти системних і стандартних сервісів |
| `1024–49151` | Registered ports | Зареєстровані порти програм і сервісів |
| `49152–65535` | Dynamic/private ports | Динамічні та приватні порти, часто використовуються клієнтами |

Цей поділ описує стандартні категорії IANA. На практиці конкретна програма може використовувати й інші доступні порти, якщо це дозволяють система та конфігурація.

### 2.3. Популярні порти

| Порт | Протокол або сервіс | Призначення |
|---:|---|---|
| `20/21` | FTP | Передавання файлів у традиційному FTP |
| `22` | SSH | Захищене віддалене адміністрування |
| `25` | SMTP | Передавання електронної пошти між серверами |
| `53` | DNS | Розв'язання доменних імен |
| `67/68` | DHCP | Отримання мережевих налаштувань через IPv4 |
| `80` | HTTP | Незашифрований вебтрафік |
| `110` | POP3 | Отримання електронної пошти |
| `123` | NTP | Синхронізація часу |
| `143` | IMAP | Доступ до поштових скриньок |
| `443` | HTTPS | Зашифрований вебтрафік |
| `5432` | PostgreSQL | Типовий порт PostgreSQL |
| `3306` | MySQL | Типовий порт MySQL |
| `6379` | Redis | Типовий порт Redis |
| `27017` | MongoDB | Типовий порт MongoDB |
| `3000` | Часто dev-сервери | Поширений, але не зарезервований спеціально для Node.js |
| `5173` | Часто Vite | Типовий порт Vite dev-сервера |

**Важливо:** номер порту сам по собі не доводить, яка саме програма його використовує. Наприклад, порт `5432` може бути зайнятий не PostgreSQL, а іншим процесом.

## 3. Що таке сокет

Сокет — це механізм, через який програма обмінюється даними з іншими програмами або вузлами.

У мережевому програмуванні сокет зазвичай пов'язаний із такими параметрами:

- адреса локального вузла;
- локальний порт;
- транспортний протокол;
- за наявності з'єднання — адреса та порт віддаленого вузла.

Для TCP-з'єднання комбінація локальної адреси й порту та віддаленої адреси й порту разом із протоколом допомагає ідентифікувати конкретне з'єднання.

### 3.1. TCP-сокет

TCP-сокет використовується для надійного передавання потоку байтів між двома кінцевими точками.

Приклади:

- браузер підключається до вебсервера;
- `curl` надсилає HTTP-запит;
- Node.js API приймає запит клієнта;
- застосунок підключається до PostgreSQL через TCP.

TCP встановлює з'єднання перед передаванням даних.

### 3.2. UDP-сокет

UDP-сокет використовується для передавання датаграм без попереднього встановлення TCP-подібного з'єднання.

Приклади використання UDP:

- DNS-запити;
- голосовий і відеозв'язок;
- деякі ігрові мережеві протоколи;
- DHCP;
- певні режими передавання медіа.

UDP не гарантує доставку, порядок або відсутність повторів датаграм. Програми, яким потрібні такі гарантії, мають реалізовувати відповідну логіку самостійно або використовувати інший протокол.

### 3.3. Unix domain sockets

Не всі сокети використовують IP-адреси та TCP/UDP-порти.

Unix domain sockets забезпечують взаємодію процесів на одному комп'ютері. Часто вони представлені файловим шляхом, наприклад:

    /run/example/app.sock

Їх використовують деякі вебсервери, бази даних і локальні сервіси.

Переглянути Unix-сокети:

    ss -lx

Unix domain socket не є TCP-портом. Для його роботи не потрібна IP-адреса.

## 4. Як працюють клієнт і сервер

Типова взаємодія через TCP відбувається так:

1. Сервер запускається та прив'язується до IP-адреси й порту.
2. Сервер переходить у режим очікування вхідних з'єднань.
3. Клієнт підключається до адреси й порту сервера.
4. TCP встановлює з'єднання.
5. Клієнт і сервер передають дані.
6. Після завершення з'єднання закриваються відповідні сокети.

Наприклад:

    Client: 192.168.1.20:51524
        |
        | TCP connection
        v
    Server: 192.168.1.10:3000

`51524` — приклад тимчасового клієнтського порту. Він може відрізнятися під час кожного з'єднання.

### 4.1. Listening socket

Listening socket — сокет, який очікує на нові вхідні TCP-з'єднання.

Наприклад, Node.js-сервер може слухати порт `3000`:

    server.listen(3000, () => {
      console.log("Server is running on port 3000");
    });

Цей приклад показує основну ідею API Node.js. У реальному застосунку `server` має бути створений відповідним способом, а сам сервер — запущений.

### 4.2. Established connection

Коли TCP-з'єднання вже встановлено, у виводі `ss` його стан зазвичай позначається як `ESTAB`.

Наприклад:

    ESTAB 0 0 192.168.1.10:3000 192.168.1.20:51524

Точний формат виводу залежить від команди, версії системи та протоколу.

### 4.3. Чому один порт може мати багато з'єднань

Вебсервер може слухати порт `3000` і водночас обслуговувати багато клієнтів.

Наприклад:

    Server: 192.168.1.10:3000
        |
        +---- Client A: 192.168.1.20:51524
        |
        +---- Client B: 192.168.1.21:51525
        |
        +---- Client C: 192.168.1.22:51526

Серверний listening socket приймає нові з'єднання, а встановлені TCP-з'єднання розрізняються за локальними й віддаленими адресами та портами.

## 5. Перевірка сокетів за допомогою ss

`ss` — основна утиліта для перегляду мережевих сокетів у сучасному Linux.

### 5.1. Показати TCP-сокети, що слухають

    ss -lt

Пояснення:

- `-l` — показати listening sockets;
- `-t` — показати TCP-сокети.

Команда допомагає знайти TCP-порти, на яких система очікує з'єднання.

### 5.2. Показати UDP-сокети

    ss -lu

Параметри:

- `-l` — listening sockets;
- `-u` — UDP-сокети.

UDP не має TCP-подібного стану `LISTEN`, але `ss -lu` показує UDP-сокети, прив'язані до локальних адрес і портів.

### 5.3. Показати всі TCP-з'єднання

    ss -ta

Параметри:

- `-t` — TCP;
- `-a` — усі відповідні сокети, а не лише listening.

Залежно від стану системи можна побачити `LISTEN`, `ESTAB`, `TIME-WAIT` та інші TCP-стани.

### 5.4. Показати всі TCP- та UDP-сокети

    ss -tua

Це зручна команда для загального огляду TCP- і UDP-сокетів.

### 5.5. Показати процеси, пов'язані із сокетами

    sudo ss -tulpn

Параметри:

- `-t` — TCP;
- `-u` — UDP;
- `-l` — listening sockets;
- `-p` — інформація про процеси;
- `-n` — числові адреси та порти без перетворення на назви.

`sudo` допомагає отримати інформацію про процеси, для яких звичайному користувачеві бракує прав.

Приклад умовного виводу:

    Netid State  Local Address:Port  Peer Address:Port Process
    tcp   LISTEN 0.0.0.0:3000         0.0.0.0:*       users:(("node",pid=1234,fd=20))
    tcp   LISTEN 127.0.0.1:5432       0.0.0.0:*       users:(("postgres",pid=5678,fd=7))

Це лише ілюстрація. Реальні процеси, адреси та PID у твоїй системі будуть іншими.

### 5.6. Показати числові адреси та порти

    ss -tn

Параметр `-n` не перетворює номери портів на назви сервісів і не виконує зайві спроби визначення імен.

Для діагностики це часто зручніше, ніж текстові назви.

### 5.7. Показати статистику сокетів

    ss -s

Команда показує узагальнену статистику мережевих сокетів.

Вона корисна для швидкого огляду системи, але не замінює аналіз конкретного порту або процесу.

## 6. Перевірка конкретного порту через ss

### 6.1. Перевірити порт 3000

    ss -ltn 'sport = :3000'

Команда показує TCP-сокети, що слухають локальний порт `3000`.

Пояснення:

- `-l` — listening;
- `-t` — TCP;
- `-n` — числовий формат;
- `sport = :3000` — фільтр за локальним портом джерела сокета в синтаксисі `ss`.

Якщо команда нічого не виводить, це зазвичай означає, що відповідного listening TCP-сокета не знайдено. Але це не доводить, що порт абсолютно ніде не використовується: програма може використовувати іншу адресу, інший протокол або інший мережевий простір імен.

### 6.2. Перевірити UDP-порт 53

    ss -lun 'sport = :53'

Команда показує UDP-сокети, прив'язані до локального порту `53`.

### 6.3. Перевірити порт у всіх станах

    ss -tan 'sport = :3000'

Це показує TCP-сокети, пов'язані з локальним портом `3000`, незалежно від того, чи є вони listening, чи перебувають в іншому стані.

## 7. Перевірка процесів через lsof

`lsof` означає List Open Files. У Linux мережеві сокети також відображаються як відкриті ресурси процесів.

### 7.1. Перевірити, який процес використовує порт 3000

    sudo lsof -i :3000

Команда показує процеси, які використовують мережеві сокети, пов'язані з портом `3000`.

Приклад умовного виводу:

    COMMAND  PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
    node    1234 valer  20u  IPv4  ...        0t0  TCP *:3000 (LISTEN)

Основні поля:

- `COMMAND` — назва команди;
- `PID` — ідентифікатор процесу;
- `USER` — користувач процесу;
- `FD` — файловий дескриптор;
- `TYPE` — тип ресурсу;
- `NAME` — адреса, порт і стан сокета.

### 7.2. Перевірити TCP-порт

    sudo lsof -iTCP:3000 -sTCP:LISTEN

Ця команда звужує пошук до TCP-сокетів у стані прослуховування порту `3000`.

### 7.3. Якщо lsof не встановлено

    sudo apt update
    sudo apt install lsof

Після встановлення:

    lsof -v

У багатьох випадках `ss` уже достатньо, тому `lsof` — корисний додатковий інструмент, а не обов'язкова заміна `ss`.

## 8. Перевірка порту через nc

`nc` (netcat) — інструмент для роботи з TCP- і UDP-з'єднаннями. Його часто використовують для перевірки доступності TCP-порту.

### 8.1. Перевірити локальний TCP-порт

    nc -vz localhost 3000

Параметри:

- `-v` — докладний вивід;
- `-z` — перевірка без передавання звичайних даних.

Якщо порт приймає TCP-з'єднання, команда зазвичай повідомить про успішне підключення.

Якщо порт недоступний, можна отримати повідомлення про відмову або тайм-аут.

### 8.2. Перевірити віддалений порт

    nc -vz example.com 443

Команда перевіряє, чи вдається встановити TCP-з'єднання з портом `443` на вказаному хості.

Успішна перевірка не гарантує, що HTTPS-сервіс правильно працює на прикладному рівні. Вона підтверджує лише успішність відповідної TCP-перевірки.

### 8.3. Задати тайм-аут

    nc -vz -w 3 example.com 443

Параметр `-w 3` задає тайм-аут у секундах для відповідних операцій netcat.

Поведінка окремих параметрів може відрізнятися між реалізаціями `nc`, наприклад OpenBSD netcat і Ncat.

### 8.4. Якщо nc не встановлено

    sudo apt update
    sudo apt install netcat-openbsd

Перевірити доступність команди:

    nc -h

### 8.5. Важливе застереження

Якщо TCP-порт недоступний, це не завжди означає, що програма не запущена.

Можливі причини:

- сервіс не слухає цей порт;
- сервіс слухає лише `127.0.0.1`;
- використано неправильну IP-адресу;
- firewall відкидає або відхиляє пакети;
- мережевий маршрут недоступний;
- сервіс слухає UDP, а перевіряється TCP.

## 9. localhost, 127.0.0.1 і 0.0.0.0

Ці адреси часто зустрічаються під час запуску локальних серверів.

### 9.1. localhost

    curl http://localhost:3000

`localhost` — ім'я, яке зазвичай розв'язується в локальні loopback-адреси, зокрема `127.0.0.1` для IPv4 і `::1` для IPv6.

Конкретний результат залежить від конфігурації системи.

### 9.2. 127.0.0.1

    curl http://127.0.0.1:3000

Це IPv4 loopback-адреса. З'єднання спрямовується до локального комп'ютера.

Інші комп'ютери в мережі не можуть використовувати `127.0.0.1` для доступу до твого сервера: для кожного комп'ютера це його власний loopback.

### 9.3. ::1

    curl -g 'http://[::1]:3000'

`::1` — IPv6 loopback-адреса.

Квадратні дужки потрібні для запису IPv6-адреси разом із портом в URL.

### 9.4. 0.0.0.0

`0.0.0.0` у контексті прослуховування IPv4 означає прив'язку до всіх локальних IPv4-адрес, доступних у відповідному мережевому просторі.

Наприклад, Node.js може слухати:

    server.listen(3000, "0.0.0.0");

Це дозволяє приймати IPv4-з'єднання через доступні мережеві інтерфейси, якщо це не блокують firewall та інші налаштування.

**Важливо:** `0.0.0.0` — адреса прив'язки, а не адреса, яку зазвичай вводять у браузері для доступу до сервера з іншого пристрою. Для такого доступу використовують реальну IP-адресу комп'ютера в локальній мережі.

### 9.5. Порівняння адрес

| Адреса | Значення |
|---|---|
| `127.0.0.1` | IPv4 loopback |
| `::1` | IPv6 loopback |
| `0.0.0.0` | Усі відповідні локальні IPv4-адреси під час прив'язки |
| `localhost` | Ім'я, яке зазвичай розв'язується в loopback-адреси |
| `192.168.x.x` | Типовий приклад приватної IPv4-адреси локальної мережі |

## 10. Проблема: Address already in use

Одна з найчастіших помилок під час розробки backend — спроба запустити сервер на порту, який уже зайнятий.

Приклад повідомлення Node.js:

    Error: listen EADDRINUSE: address already in use :::3000

Це означає, що прив'язати сокет до вказаної адреси й порту не вдалося, оскільки адреса вже використовується або виник інший конфлікт прив'язки.

### 10.1. Знайти процес на порту

    sudo ss -ltnp 'sport = :3000'

Або:

    sudo lsof -iTCP:3000 -sTCP:LISTEN

Знайди PID процесу, який використовує порт.

### 10.2. Зрозуміти, що це за процес

    ps -p 1234 -o pid,ppid,user,stat,cmd

Заміни `1234` на фактичний PID.

Команда покаже ідентифікатор процесу, батьківський PID, користувача, стан і команду запуску.

### 10.3. Коректно зупинити процес

Якщо процес запущено у твоєму терміналі, спробуй натиснути:

    Ctrl+C

Якщо процес керується системним сервісом, зупиняй його відповідною командою керування сервісом, а не завершуй навмання.

Для власного процесу, який потрібно зупинити:

    kill 1234

Заміни `1234` на перевірений PID. `kill` за замовчуванням надсилає процесу сигнал `SIGTERM`, даючи йому можливість завершитися коректно.

Перевір порт ще раз:

    ss -ltn 'sport = :3000'

### 10.4. Коли використовувати kill -9

    kill -9 1234

`SIGKILL` примусово завершує процес без можливості виконати звичайне очищення.

Використовуй його лише тоді, коли процес не завершується звичайним способом і ти впевнився, що це потрібний процес.

Не застосовуй `kill -9` автоматично до кожного процесу, який використовує порт.

### 10.5. Альтернатива — змінити порт

У багатьох навчальних проєктах можна просто вибрати інший вільний порт, наприклад `3001`.

    PORT=3001 node server.js

Це спрацює лише тоді, коли код застосунку читає змінну середовища `PORT`.

Приклад у Node.js:

    const port = Number(process.env.PORT ?? 3000);

    server.listen(port, () => {
      console.log(`Server is running on port ${port}`);
    });

Значення `3001` не гарантує, що порт вільний. За потреби перевір його через `ss`.

## 11. Чому порт може бути недоступним

Якщо `curl` або `nc` не можуть підключитися до сервісу, потрібно розрізняти кілька ситуацій.

### 11.1. На порту нічого не слухає

Перевір:

    ss -ltnp 'sport = :3000'

Якщо відповідного сокета немає, можливо, сервер не запущений або використовує інший порт чи протокол.

### 11.2. Сервер слухає тільки loopback

Приклад:

    127.0.0.1:3000

Це означає, що сервер прив'язаний до IPv4 loopback. З інших пристроїв локальної мережі напряму підключитися до цього сокета не вийде.

Якщо потрібен доступ із мережі, перевір конфігурацію прив'язки до адреси, наприклад `0.0.0.0`, та налаштування безпеки.

### 11.3. Сервер слухає всі IPv4-адреси

Приклад:

    0.0.0.0:3000

Сервер слухає відповідні локальні IPv4-адреси, але це не означає, що порт автоматично доступний з Інтернету.

Доступ можуть обмежувати:

- firewall на комп'ютері;
- маршрутизатор;
- мережеві правила;
- контейнерна ізоляція;
- хмарні security groups;
- конфігурація сервісу.

### 11.4. Firewall блокує з'єднання

Для огляду статусу UFW в Ubuntu:

    sudo ufw status verbose

Якщо UFW неактивний, це не гарантує відсутності інших правил фільтрації. У системі можуть бути правила `nftables`, налаштування маршрутизатора або зовнішнього firewall.

Не відкривай порти без розуміння, кому потрібен доступ і з якої мережі.

### 11.5. TCP і UDP — різні протоколи

TCP-сокет на порту `3000` не означає, що UDP-порт `3000` також відкритий.

Перевіряй потрібний протокол:

    ss -ltn 'sport = :3000'
    ss -lun 'sport = :3000'

Перша команда шукає TCP listening sockets, друга — UDP-сокети.

## 12. Порт, процес і firewall — це різні речі

Не плутай три поняття:

**Процес:** програма, що виконується, наприклад Node.js.

**Сокет:** мережевий ресурс, через який програма приймає або передає дані.

**Firewall:** правила, які дозволяють або блокують мережевий трафік.

Наприклад, Node.js може працювати, але не слухати порт `3000`. Порт може бути вільним, але firewall може блокувати вхідні з'єднання. А порт може слухатися, проте застосунок може повертати HTTP-помилки.

Для діагностики потрібно перевіряти кожен рівень окремо.

## 13. Практичний сценарій: перевірка Node.js backend

Припустимо, твій навчальний застосунок запускається на Ubuntu та має слухати порт `3000`.

### Крок 1. Запусти застосунок

    node server.js

Якщо все гаразд, програма може вивести повідомлення про запуск сервера.

### Крок 2. Перевір listening socket

В іншому терміналі:

    ss -ltnp 'sport = :3000'

Переконайся, що порт прослуховується.

### Крок 3. Перевір HTTP-відповідь

    curl -i http://localhost:3000

Якщо застосунок має конкретний endpoint, перевір його:

    curl -i http://localhost:3000/api

### Крок 4. Перевір TCP-підключення

    nc -vz localhost 3000

Це перевіряє можливість встановити TCP-з'єднання, але не правильність HTTP-маршруту.

### Крок 5. Перевір процес

    ps -ef | grep '[n]ode'

Це допомагає знайти процеси Node.js, хоча для точного зіставлення з портом краще використовувати `ss -p` або `lsof`.

### Крок 6. Якщо порт зайнятий

    sudo lsof -iTCP:3000 -sTCP:LISTEN

Перевір PID і команду процесу. Зупини його коректно або зміни порт у власному застосунку.

## 14. Практичний сценарій: доступ до PostgreSQL

PostgreSQL часто використовує TCP-порт `5432` за замовчуванням.

### 14.1. Перевірити, чи слухає PostgreSQL

    ss -ltnp 'sport = :5432'

Якщо є відповідний сокет, це свідчить, що TCP-порт прослуховується. Але це ще не доводить, що автентифікація та підключення до бази працюють.

### 14.2. Перевірити TCP-з'єднання

    nc -vz localhost 5432

Успішний результат підтверджує можливість установити TCP-з'єднання з цим портом.

### 14.3. Перевірити реальне підключення

Якщо встановлено PostgreSQL-клієнт:

    psql -h localhost -p 5432 -U taubu -d educational

У цій команді:

- `-h localhost` — адреса сервера;
- `-p 5432` — порт;
- `-U taubu` — ім'я користувача;
- `-d educational` — назва бази даних.

Заміни параметри відповідно до власної конфігурації.

**Важливо:** відкритий порт не гарантує успішного входу в PostgreSQL. Також мають бути правильними ім'я користувача, пароль, назва бази, налаштування `pg_hba.conf` та конфігурація прослуховування.

## 15. Безпека мережевих портів

Відкритий порт може надавати доступ до сервісу з інших систем. Тому під час налаштування сервера потрібно враховувати безпеку.

Основні правила:

- відкривай тільки ті порти, які справді потрібні;
- не виставляй бази даних у публічну мережу без вагомої причини;
- обмежуй доступ до адміністративних сервісів;
- використовуй автентифікацію та шифрування, коли вони потрібні;
- перевіряй, на яких IP-адресах слухає сервіс;
- перевіряй firewall і зовнішні мережеві правила;
- не заверши́й невідомі процеси лише через те, що вони займають порт;
- не вважай відкритий порт доказом безпечності або вразливості сервісу без додаткового аналізу.

### 15.1. Прослуховування лише localhost

Для локальної бази даних або dev-сервера часто достатньо прив'язки до loopback:

    127.0.0.1:5432

Це зменшує доступність сервісу з інших мережевих інтерфейсів, але не замінює автентифікацію та інші заходи безпеки.

### 15.2. Прослуховування всіх інтерфейсів

    0.0.0.0:3000

Така прив'язка може бути потрібна для доступу з локальної мережі, контейнера або іншого вузла. Водночас перевір, чи справді потрібна доступність з усіх IPv4-інтерфейсів.

Для IPv6 окремо перевіряй відповідні адреси та правила. Поведінка dual-stack залежить від конфігурації сокета й системи.

## 16. Типові помилки початківців

### Помилка 1. Вважати, що порт — це окремий процес

Порт — це числовий ідентифікатор кінцевої точки транспортного рівня, а процес може мати кілька сокетів і використовувати кілька портів.

### Помилка 2. Вважати, що відкритий порт гарантує роботу API

TCP-з'єднання може встановлюватися, але HTTP-маршрут може повертати `404`, `401` або `500`.

Перевіряй і порт, і HTTP-відповідь.

### Помилка 3. Плутати localhost із IP-адресою комп'ютера в мережі

`127.0.0.1` означає поточний комп'ютер. Інший пристрій не використовує цю адресу для доступу до твого комп'ютера.

### Помилка 4. Запускати кілька серверів на одному порту без розуміння конфігурації

Якщо сервер уже слухає порт, другий процес може отримати `EADDRINUSE`.

Перевір порт через `ss` і знайди власника через `lsof`.

### Помилка 5. Вважати, що відсутність результату ss означає абсолютну відсутність використання порту

Потрібно враховувати протокол, IP-адресу, мережевий простір імен, права доступу та тип сокета.

### Помилка 6. Плутати TCP і UDP

TCP і UDP використовують окремі простори портів. TCP-сокет на `3000` не підтверджує наявність UDP-сервісу на тому самому номері.

### Помилка 7. Завершувати процес через kill -9 без перевірки

Спочатку визнач процес і спробуй коректне завершення. Примусове завершення може призвести до втрати незбережених даних або некоректного завершення операцій.

### Помилка 8. Відкривати всі порти у firewall

Не потрібно відкривати порти «про всяк випадок». Дозволяй лише потрібний трафік.

## 17. Корисні команди — коротка таблиця

| Команда | Призначення |
|---|---|
| `ss -lt` | TCP-сокети, що слухають |
| `ss -lu` | UDP-сокети, що слухають |
| `ss -ta` | Усі TCP-сокети |
| `ss -tua` | TCP- та UDP-сокети |
| `sudo ss -tulpn` | Listening TCP/UDP-сокети з інформацією про процеси |
| `ss -ltn 'sport = :3000'` | Перевірка TCP-порту `3000` |
| `ss -lun 'sport = :53'` | Перевірка UDP-порту `53` |
| `ss -s` | Загальна статистика сокетів |
| `sudo lsof -i :3000` | Процеси, пов'язані з портом `3000` |
| `sudo lsof -iTCP:3000 -sTCP:LISTEN` | Процеси, що слухають TCP-порт `3000` |
| `nc -vz localhost 3000` | Перевірка TCP-підключення до локального порту |
| `nc -vz -w 3 example.com 443` | TCP-перевірка віддаленого порту з тайм-аутом |
| `ps -p PID -o pid,ppid,user,stat,cmd` | Інформація про процес за PID |
| `kill PID` | Надіслати процесу SIGTERM |
| `sudo ufw status verbose` | Перевірити статус UFW |
| `curl -i http://localhost:3000` | Перевірити HTTP-відповідь локального сервера |

У командах, де написано `PID`, потрібно підставити реальний ідентифікатор процесу. Не вводь слово `PID` буквально, якщо команда очікує число.

## 20. Мінішпаргалка

    # TCP-порти, що слухають
    ss -lt

    # UDP-сокети, що слухають
    ss -lu

    # Усі TCP-з'єднання та сокети
    ss -ta

    # TCP та UDP
    ss -tua

    # Listening sockets із процесами
    sudo ss -tulpn

    # Перевірити TCP-порт 3000
    ss -ltn 'sport = :3000'

    # Знайти процес на порту 3000
    sudo lsof -i :3000

    # Знайти процес, що слухає TCP-порт
    sudo lsof -iTCP:3000 -sTCP:LISTEN

    # Перевірити TCP-з'єднання з локальним портом
    nc -vz localhost 3000

    # Перевірити віддалений HTTPS-порт
    nc -vz -w 3 example.com 443

    # Перевірити HTTP-відповідь
    curl -i http://localhost:3000

    # Перевірити PostgreSQL-порт
    ss -ltn 'sport = :5432'

    # Перевірити статус UFW
    sudo ufw status verbose

    # Подивитися інформацію про процес
    ps -p 1234 -o pid,ppid,user,stat,cmd

    # Коректно попросити процес завершитися
    kill 1234

## 21. Що потрібно пам'ятати

- Порт допомагає операційній системі спрямовувати мережевий трафік до потрібного сервісу.
- Сокет — програмний механізм мережевої взаємодії; він не обов'язково використовує IP-адресу та TCP/UDP-порт.
- TCP і UDP мають окремі простори портів.
- Один listening TCP-порт може обслуговувати багато клієнтських з'єднань.
- `ss` — основний інструмент Linux для огляду сокетів і з'єднань.
- `lsof` допомагає визначити процес, пов'язаний із мережевим портом.
- `nc` перевіряє можливість встановити мережеве з'єднання, але не підтверджує правильність роботи прикладного API.
- `127.0.0.1` — loopback, а `0.0.0.0` під час прив'язки означає всі відповідні локальні IPv4-адреси.
- `EADDRINUSE` зазвичай вказує на конфлікт прив'язки до адреси й порту.
- Відкритий порт не гарантує, що сервіс працює правильно або доступний з Інтернету.
- Для діагностики перевіряй процес, сокет, адресу прив'язки, протокол і firewall окремо.
- Не заверши́й невідомі процеси й не відкривай порти без розуміння наслідків.

**Головна ідея:** щоб зрозуміти, чому мережевий застосунок не працює, потрібно визначити, який процес запущений, який сокет він використовує, на якій адресі й порту він слухає та чи дозволяє мережа встановити з'єднання.
