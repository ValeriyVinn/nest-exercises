# 03. curl and wget

`curl` і `wget` — це командні інструменти Linux для роботи з мережевими ресурсами. Вони дозволяють отримувати дані з вебсерверів, завантажувати файли, перевіряти HTTP/HTTPS-з'єднання та взаємодіяти з API.

`curl` особливо корисний для розробників: за його допомогою можна надсилати HTTP-запити до backend-сервера, перевіряти API, передавати заголовки й дані та аналізувати HTTP-відповіді.

`wget` насамперед призначений для завантаження файлів і може продовжувати перерване завантаження.

## 1. Що потрібно знати

✔ `curl` — інструмент для передавання даних за URL; підтримує HTTP, HTTPS та багато інших протоколів.

✔ `wget` — інструмент для завантаження файлів із мережі.

✔ URL — адреса ресурсу, наприклад `https://example.com`.

✔ HTTP — протокол обміну даними між клієнтом і вебсервером.

✔ HTTPS — HTTP із шифруванням за допомогою TLS.

✔ HTTP-методи — `GET`, `POST`, `PUT`, `PATCH`, `DELETE` та інші.

✔ HTTP-статус — код, який описує результат запиту: наприклад, `200`, `404`, `500`.

✔ HTTP-заголовки — додаткова інформація про запит або відповідь.

✔ Тіло запиту (request body) — дані, які клієнт надсилає серверу, наприклад JSON.

✔ API — інтерфейс, через який програми обмінюються даними.

✔ `curl` і `wget` не є повноцінними браузерами: вони отримують ресурси, але зазвичай не відображають сторінки та не виконують JavaScript так, як браузер.

## 2. Перевірка встановлення

### Перевірити версію curl

    curl --version

Команда показує версію `curl`, підтримувані протоколи та можливості бібліотеки TLS.

### Перевірити версію wget

    wget --version

### Перевірити наявність команд

    command -v curl
    command -v wget

Якщо команда повертає шлях, наприклад `/usr/bin/curl`, інструмент доступний у системі.

### Встановлення в Ubuntu

    sudo apt update
    sudo apt install curl wget

Перевірити після встановлення:

    curl --version
    wget --version

## 3. Основи curl

### 3.1. Найпростіший HTTP-запит

    curl https://example.com

За замовчуванням `curl` виконує HTTP GET-запит і виводить тіло відповіді в термінал.

Наприклад, для HTML-сторінки результатом буде HTML-код, а не оформлена вебсторінка.

### 3.2. Отримати лише заголовки відповіді

    curl -I https://example.com

Параметр `-I` надсилає HTTP HEAD-запит, щоб отримати заголовки без звичайного тіла відповіді.

Приклад результату:

    HTTP/2 200
    content-type: text/html
    content-length: 1256

Фактичні заголовки й статус залежать від сервера.

**Важливо:** HEAD-запит не завжди обробляється сервером так само, як GET. Якщо потрібно перевірити саме GET, використовуйте інші параметри.

### 3.3. Показати заголовки та тіло відповіді

    curl -i https://example.com

Різниця:

- `-I` — запит HEAD, показує заголовки.
- `-i` — виконує звичайний запит і додає заголовки до виведеного тіла відповіді.

### 3.4. Показати деталі з'єднання

    curl -v https://example.com

Параметр `-v` (verbose) показує додаткову інформацію:

- встановлення з'єднання;
- узгодження TLS для HTTPS;
- HTTP-запит;
- заголовки відповіді;
- помилки підключення.

Використовуй `-v`, коли потрібно з'ясувати, на якому етапі виникає проблема.

**Увага:** докладний вивід може містити чутливі заголовки або інші дані. Перевіряй його перед публікацією.

### 3.5. Показати тільки HTTP-статус

    curl -s -o /dev/null -w "%{http_code}\n" https://example.com

Пояснення:

- `-s` — приховує звичайний індикатор прогресу та частину повідомлень;
- `-o /dev/null` — відкидає тіло відповіді;
- `-w` — виводить додаткову інформацію після запиту;
- `%{http_code}` — HTTP-статус відповіді.

На Linux `/dev/null` — спеціальний пристрій, який відкидає записані в нього дані.

Цей прийом зручний для швидкої перевірки HTTP-статусу.

### 3.6. Приховати зайвий вивід

    curl -s https://example.com

Параметр `-s` означає silent mode.

Щоб зберегти повідомлення про помилки, але приховати індикатор прогресу:

    curl -sS https://example.com

`-S` дозволяє показувати повідомлення про помилки разом із `-s`.

## 4. Основи wget

### 4.1. Завантажити файл

    wget https://example.com/file.zip

За замовчуванням `wget` завантажує ресурс і зберігає його в поточному каталозі під відповідним ім'ям файлу.

Перевірити поточний каталог:

    pwd
    ls -lh

### 4.2. Задати ім'я завантаженого файлу

    wget -O archive.zip https://example.com/file.zip

Параметр `-O` (output document) дозволяє вказати ім'я файлу.

**Увага:** якщо `archive.zip` уже існує, `wget -O` може перезаписати його.

### 4.3. Продовжити перерване завантаження

    wget -c https://example.com/large-file.zip

Параметр `-c` (continue) просить `wget` продовжити завантаження з місця зупинки, якщо сервер підтримує відповідний механізм.

Якщо сервер не підтримує відновлення або ресурс змінився, продовження може не спрацювати належним чином.

### 4.4. Завантажити файл у певний каталог

    wget -P ~/Downloads https://example.com/file.zip

Параметр `-P` задає каталог для збереження.

Перевірити результат:

    ls -lh ~/Downloads

### 4.5. Завантажити файл без індикатора прогресу

    wget -q https://example.com/file.zip

Параметр `-q` (quiet) приховує більшість повідомлень.

Для навчання краще спочатку використовувати звичайний режим, щоб бачити хід завантаження та можливі помилки.

### 4.6. Обмежити швидкість завантаження

    wget --limit-rate=500k https://example.com/large-file.zip

Команда обмежує швидкість завантаження приблизно до 500 KB/s.

Це корисно, коли не потрібно повністю використовувати доступну пропускну здатність мережі.

### 4.7. Завантажити файл у фоновому режимі

    wget -b https://example.com/large-file.zip

Параметр `-b` запускає завантаження у фоновому режимі. Повідомлення про виконання зазвичай записуються у файл журналу `wget-log`.

Перевірити журнал:

    tail -f wget-log

Натисни `Ctrl+C`, щоб припинити перегляд журналу. Це не обов'язково зупиняє саме завантаження.

## 5. Порівняння curl і wget

| Можливість | `curl` | `wget` |
|---|---|---|
| Отримання HTTP-відповіді | Так | Так |
| Завантаження файлів | Так | Так |
| Перегляд HTTP-заголовків | Зручно | Можливо, але менш гнучко |
| Надсилання POST-запитів | Зручно | Підтримується |
| Робота з JSON API | Особливо зручно | Можливо |
| Продовження завантаження | Залежить від режиму та сервера | `-c` |
| Обмеження швидкості | Можливо через параметри | `--limit-rate` |
| Рекурсивне завантаження сайтів | Не основне призначення | Підтримується |
| Детальна діагностика HTTP/TLS | `-v` | `-d` для налагодження |
| Основне призначення | Передавання даних і тестування запитів | Завантаження ресурсів |

**Запам'ятай:** для перевірки API та HTTP-запитів зазвичай починай із `curl`. Для простого завантаження файлів зручно використовувати `wget`.

## 6. HTTP-статуси

HTTP-статус допомагає зрозуміти, як сервер обробив запит.

### 6.1. Основні групи статусів

| Діапазон | Значення |
|---|---|
| `1xx` | Інформаційні відповіді |
| `2xx` | Запит успішно оброблено |
| `3xx` | Перенаправлення |
| `4xx` | Помилка запиту або доступу з боку клієнта |
| `5xx` | Помилка на боці сервера |

### 6.2. Найважливіші коди

- `200 OK` — запит успішний.
- `201 Created` — ресурс створено.
- `204 No Content` — запит успішний, але тіла відповіді немає.
- `301 Moved Permanently` — постійне перенаправлення.
- `302 Found` — тимчасове перенаправлення.
- `304 Not Modified` — ресурс не змінився відносно умовного запиту.
- `400 Bad Request` — некоректний запит.
- `401 Unauthorized` — потрібна автентифікація.
- `403 Forbidden` — доступ заборонено.
- `404 Not Found` — ресурс не знайдено.
- `405 Method Not Allowed` — HTTP-метод не підтримується для цього ресурсу.
- `429 Too Many Requests` — забагато запитів за певний період.
- `500 Internal Server Error` — внутрішня помилка сервера.
- `502 Bad Gateway` — некоректна відповідь від сервера-посередника.
- `503 Service Unavailable` — сервіс тимчасово недоступний.
- `504 Gateway Timeout` — сервер-посередник не дочекався відповіді вчасно.

**Важливо:** отримання статусу `404` або `500` означає, що HTTP-відповідь надійшла. Це не те саме, що помилка DNS або неможливість установити з'єднання.

## 7. Перенаправлення

### 7.1. Обробити перенаправлення в curl

    curl -L https://example.com

Параметр `-L` дозволяє `curl` переходити за HTTP-перенаправленнями.

Без нього команда може показати відповідь `301` або `302`, не завантажуючи кінцевий ресурс.

### 7.2. Перенаправлення у wget

    wget https://example.com

`wget` зазвичай автоматично обробляє стандартні HTTP-перенаправлення.

### 7.3. Показати кінцевий URL у curl

    curl -sS -L -o /dev/null -w "%{url_effective}\n" https://example.com

`%{url_effective}` показує URL, який використовувався для кінцевої відповіді після перенаправлень.

## 8. Тайм-аути та швидкість відповіді

### 8.1. Обмежити час очікування

    curl --max-time 10 https://example.com

`--max-time 10` обмежує загальну тривалість операції приблизно 10 секундами.

Якщо за цей час запит не завершиться, `curl` припинить операцію з помилкою тайм-ауту.

### 8.2. Обмежити час установлення з'єднання

    curl --connect-timeout 5 https://example.com

Команда обмежує час установлення з'єднання приблизно п'ятьма секундами.

Це не те саме, що загальний тайм-аут: після встановлення з'єднання передавання даних може тривати довше.

### 8.3. Виміряти час запиту

    curl -sS -o /dev/null -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nFirst byte: %{time_starttransfer}s\nTotal: %{time_total}s\n" https://example.com

Основні показники:

- `time_namelookup` — час до завершення пошуку адреси імені хоста;
- `time_connect` — час до встановлення з'єднання;
- `time_appconnect` — час до завершення TLS-рукостискання для HTTPS;
- `time_starttransfer` — час до отримання першого байта відповіді;
- `time_total` — загальна тривалість операції.

Ці значення накопичувальні від початку операції, а не завжди незалежні проміжки часу. Їх можна використовувати для первинної діагностики повільного запиту.

## 9. HTTP-методи

HTTP-метод визначає, яку дію клієнт просить виконати.

### 9.1. GET — отримати дані

    curl https://api.example.com/users

`GET` використовується для отримання даних. У `curl` це метод за замовчуванням для звичайного HTTP-запиту.

### 9.2. POST — надіслати дані

    curl -X POST https://api.example.com/users \
      -H "Content-Type: application/json" \
      -d '{"name":"Valeriy","role":"student"}'

Пояснення:

- `-X POST` — задає HTTP-метод POST;
- `-H` — додає HTTP-заголовок;
- `Content-Type: application/json` — повідомляє серверу, що тіло запиту містить JSON;
- `-d` — передає тіло запиту.

Під час використання `-d` для HTTP-запиту `curl` зазвичай автоматично вибирає POST, тому `-X POST` тут можна опустити.

**Увага:** наведений URL є прикладом. Для реального запиту потрібен API, який підтримує цей endpoint і формат даних.

### 9.3. PUT — замінити ресурс

    curl -X PUT https://api.example.com/users/42 \
      -H "Content-Type: application/json" \
      -d '{"name":"Valeriy","role":"developer"}'

`PUT` зазвичай використовують для створення або повного оновлення ресурсу за певною адресою. Точна поведінка визначається API.

### 9.4. PATCH — частково оновити ресурс

    curl -X PATCH https://api.example.com/users/42 \
      -H "Content-Type: application/json" \
      -d '{"role":"developer"}'

`PATCH` зазвичай використовується для часткового оновлення.

### 9.5. DELETE — видалити ресурс

    curl -X DELETE https://api.example.com/users/42

`DELETE` просить сервер видалити ресурс.

**Важливо:** `PUT`, `PATCH` і `DELETE` можуть змінювати реальні дані. Не виконуй їх на production-сервері без дозволу та розуміння наслідків.

## 10. Робота з JSON API

Для Full Stack JavaScript-розробника це один із найважливіших способів використання `curl`.

### 10.1. Отримати JSON

    curl https://api.example.com/users

Якщо сервер повертає JSON, `curl` покаже його в терміналі.

### 10.2. Додати заголовок Accept

    curl https://api.example.com/users \
      -H "Accept: application/json"

`Accept` повідомляє серверу, який формат відповіді бажає отримати клієнт.

### 10.3. Надіслати JSON

    curl https://api.example.com/users \
      -H "Content-Type: application/json" \
      -d '{"name":"Valeriy"}'

У цьому прикладі `curl` зазвичай використає POST, оскільки передано тіло через `-d`.

### 10.4. Передати токен авторизації

    curl https://api.example.com/profile \
      -H "Authorization: Bearer YOUR_TOKEN"

Заміни `YOUR_TOKEN` на дійсний токен, якщо він потрібен цьому API.

Не публікуй реальні токени, паролі чи інші секрети в README, GitHub або повідомленнях.

### 10.5. Зберегти відповідь API у файл

    curl -o users.json https://api.example.com/users

Після запиту перевір файл:

    ls -lh users.json
    cat users.json

Якщо файл великий, для перегляду зручніше використовувати:

    less users.json

## 11. Робота з локальним backend-сервером

Під час розробки Node.js, Express або NestJS можна перевіряти API через `curl`, не відкриваючи браузер.

### 11.1. Перевірити локальний сервер

Припустимо, backend працює на порту `3000`:

    curl -i http://localhost:3000

`localhost` означає поточний комп'ютер.

Якщо застосунок використовує інший маршрут, потрібно вказати його, наприклад:

    curl -i http://localhost:3000/api/users

Маршрут `/api/users` — лише приклад. Він має існувати у твоєму застосунку.

### 11.2. Перевірити POST-запит до Express

    curl -i http://localhost:3000/api/users \
      -H "Content-Type: application/json" \
      -d '{"name":"Test User"}'

Щоб запит спрацював, сервер має:

- слухати порт `3000`;
- мати маршрут `POST /api/users`;
- уміти обробляти JSON;
- повертати відповідь для цього запиту.

В Express для розбору JSON зазвичай використовують middleware:

    app.use(express.json());

Якщо потрібного маршруту немає, сервер може повернути `404`. Якщо маршрут існує, але виникла помилка, можна отримати `4xx` або `5xx` залежно від реалізації.

### 11.3. Перевірити статус без виведення JSON

    curl -sS -o /dev/null -w "HTTP %{http_code}\n" http://localhost:3000/api/users

Це корисно для швидкої перевірки endpoint під час розробки.

### 11.4. Якщо curl не може підключитися

Приклад повідомлення:

    curl: (7) Failed to connect to localhost port 3000

Перевір:

    curl -v http://localhost:3000
    ip addr
    ip route

Також переконайся, що backend запущений і слухає потрібний порт.

Можливі причини:

- сервер не запущений;
- використовується неправильний порт;
- endpoint або адреса вказані неправильно;
- застосунок слухає інший мережевий інтерфейс;
- з'єднання блокується правилами мережі.

Для локального застосунку насамперед перевір, чи запущений процес і чи збігається порт із конфігурацією.

## 12. Завантаження файлів через curl

### 12.1. Зберегти ресурс у файл

    curl -o page.html https://example.com

`-o` задає ім'я файлу, у який буде записано тіло відповіді.

### 12.2. Зберегти ресурс під назвою з URL

    curl -O https://example.com/file.zip

Велика літера `-O` наказує використовувати ім'я файлу з URL.

### 12.3. Показувати прогрес завантаження

    curl -# -O https://example.com/file.zip

Параметр `-#` показує спрощений індикатор прогресу.

### 12.4. Продовжити завантаження

    curl -C - -O https://example.com/large-file.zip

`-C -` просить `curl` продовжити передавання з відповідної позиції, якщо це підтримується сервером.

Якщо файл уже існує, `curl` використовує його розмір як відправну точку для продовження.

## 13. Завантаження та перевірка ресурсів через wget

### 13.1. Завантажити сторінку

    wget https://example.com

Зазвичай `wget` збереже HTML у файл, названий відповідно до URL, наприклад `index.html`.

### 13.2. Перевірити HTTP-відповідь

    wget -S --spider https://example.com

Пояснення:

- `-S` — показує HTTP-заголовки відповіді;
- `--spider` — перевіряє ресурс без звичайного збереження його вмісту.

`--spider` не є повною заміною всіх можливостей HEAD-запиту: поведінка залежить від ресурсу та сервера.

### 13.3. Обмежити кількість повторних спроб

    wget --tries=3 https://example.com/file.zip

Команда обмежує кількість спроб завантаження.

### 13.4. Встановити тайм-аут очікування

    wget --timeout=10 https://example.com/file.zip

Параметр `--timeout` задає тайм-аут мережевих операцій. Конкретна поведінка залежить від типу операції; це не завжди є жорстким обмеженням загального часу всього завантаження.

### 13.5. Завантажити файл лише за наявності змін

    wget -N https://example.com/file.zip

`-N` (timestamping) дозволяє `wget` порівнювати часові мітки локального та віддаленого файлів і за певних умов не завантажувати незмінений ресурс.

Поведінка залежить від підтримки відповідних метаданих сервером.

## 14. HTTPS, TLS і сертифікати

### 14.1. Звичайний HTTPS-запит

    curl -v https://example.com

Під час HTTPS клієнт перевіряє сертифікат сервера відповідно до налаштувань довіри та імені хоста.

### 14.2. Типова помилка сертифіката

Можливе повідомлення:

    curl: (60) SSL certificate problem

Це означає, що перевірка сертифіката не пройшла. Можливі причини:

- сертифікат прострочений;
- ім'я хоста не відповідає сертифікату;
- відсутній довірений кореневий сертифікат;
- неправильно налаштований ланцюжок сертифікатів;
- локальне сховище сертифікатів застаріло.

### 14.3. Чому не варто використовувати -k без потреби

    curl -k https://example.com

Параметр `-k` (або `--insecure`) вимикає перевірку сертифіката сервера.

Це може бути корисним для тимчасової діагностики в контрольованому тестовому середовищі, але не є безпечним виправленням проблеми.

**Не використовуй `-k` для звичайної роботи з реальними сервісами:** без належної перевірки сертифіката клієнт не може надійно підтвердити ідентичність сервера.

Краще перевірити системні сертифікати, дату й час, ім'я хоста та конфігурацію сервера.

## 15. Різниця між мережевою помилкою та HTTP-помилкою

Це одна з найважливіших тем для діагностики.

### 15.1. Не вдалося встановити з'єднання

    curl: (7) Failed to connect

Можливі причини:

- сервер не запущений;
- порт закритий;
- неправильна IP-адреса або порт;
- з'єднання блокується firewall;
- мережевий маршрут недоступний.

### 15.2. Помилка DNS

Можливе повідомлення:

    curl: (6) Could not resolve host

Клієнт не зміг перетворити ім'я хоста на IP-адресу.

Перевірити розв'язання імені можна окремою командою:

    getent hosts example.com

### 15.3. HTTP 404

    curl -i https://example.com/nonexistent-page

Якщо сервер відповідає `404 Not Found`, це означає, що HTTP-запит дістався сервера, але потрібний ресурс не знайдено.

### 15.4. HTTP 500

    curl -i https://example.com/api

Статус `500 Internal Server Error` означає, що сервер повернув HTTP-відповідь із повідомленням про внутрішню помилку.

Причину потрібно шукати в логах і коді сервера або в залежностях, від яких він залежить.

### 15.5. Короткий алгоритм діагностики

1. Перевір, чи правильний URL.
2. Перевір DNS, якщо використовується домен.
3. Перевір з'єднання та порт.
4. Використай `curl -v`, щоб побачити етап, на якому виникає помилка.
5. Якщо є HTTP-статус, проаналізуй його.
6. Якщо сервер повертає `5xx`, перевір його логи.
7. Якщо це локальний backend, переконайся, що сервер запущений і маршрут існує.

## 18. Типові помилки початківців

### Помилка 1. Вважати, що curl — це браузер

    curl https://example.com

Команда виводить HTML-код, але не відображає оформлену сторінку.

**Правильно:** використовуй браузер для візуального перегляду, а `curl` — для запитів, діагностики та тестування API.

### Помилка 2. Плутати HTTP-статус і код завершення команди

    curl https://example.com/nonexistent-page
    echo $?

HTTP `404` не обов'язково означає, що команда `curl` завершилася з ненульовим кодом.

За замовчуванням `curl` може успішно отримати HTTP-відповідь зі статусом `404` або `500`.

Щоб трактувати HTTP-статуси `400` і вище як помилки для відповідних сценаріїв, можна використати:

    curl --fail https://example.com/nonexistent-page

`--fail` змінює поведінку обробки HTTP-помилок, але не замінює аналіз статусу й тіла відповіді.

Для докладнішої діагностики:

    curl --fail-with-body https://example.com/api

`--fail-with-body` намагається зберегти тіло HTTP-відповіді навіть тоді, коли статус свідчить про помилку.

### Помилка 3. Забувати про лапки в JSON

Ненадійний приклад:

    curl -d {"name":"Test User"} https://api.example.com/users

Shell може неправильно інтерпретувати спеціальні символи та пробіли.

Краще:

    curl -H "Content-Type: application/json" \
      -d '{"name":"Test User"}' \
      https://api.example.com/users

Для складного JSON зручно використовувати файл:

    curl -H "Content-Type: application/json" \
      --data-binary @request.json \
      https://api.example.com/users

### Помилка 4. Використовувати неправильний HTTP-метод

Маршрут може підтримувати `GET`, але не `POST`, або навпаки.

Перевір документацію API, маршрут у коді backend і статус відповіді.

### Помилка 5. Вважати, що ping і curl перевіряють одне й те саме

    ping -c 4 example.com
    curl -I https://example.com

`ping` перевіряє відповіді на ICMP Echo Request, а `curl` перевіряє доступність конкретного ресурсу через підтримуваний протокол.

Сервер може не відповідати на `ping`, але успішно обслуговувати HTTPS. Також можливий зворотний випадок.

### Помилка 6. Не перевіряти перенаправлення

    curl -I http://example.com

Якщо сервер повернув `301` або `302`, спробуй:

    curl -IL http://example.com

`-L` дозволяє пройти ланцюжок перенаправлень, а `-I` запитує заголовки.

### Помилка 7. Вимикати перевірку TLS без причини

    curl -k https://example.com

Не використовуй цю команду як постійне рішення. Краще з'ясувати причину помилки сертифіката.

### Помилка 8. Публікувати секрети

    curl https://api.example.com/profile \
      -H "Authorization: Bearer SECRET_TOKEN"

Не вставляй справжні токени в публічні приклади, історію Git або відкриті логи.

### Помилка 9. Завантажувати файл і не перевіряти результат

    wget https://example.com/file.zip

Після завантаження перевір файл:

    ls -lh file.zip
    file file.zip

Наявність файлу не гарантує, що його вміст правильний або що це справжній ZIP-архів. Сервер може повернути HTML-сторінку помилки.

## 19. Практика для Linux і Full Stack JavaScript

### Завдання 1. Перевірити вебресурс

Виконай:

    curl -I https://example.com

Визнач:

- який HTTP-статус повернув сервер;
- який тип вмісту вказано;
- чи встановлюється HTTPS-з'єднання.

### Завдання 2. Перевірити перенаправлення

    curl -IL http://example.com

Порівняй результат із командою без `-L`.

### Завдання 3. Виміряти час запиту

    curl -sS -o /dev/null \
      -w "HTTP: %{http_code}\nTotal: %{time_total}s\n" \
      https://example.com

Запиши HTTP-статус і загальний час запиту.

Повтори команду кілька разів і порівняй результати. Зважай, що час залежить від мережі, сервера та кешування.

### Завдання 4. Завантажити файл

    wget -O example.html https://example.com

Перевір:

    ls -lh example.html
    file example.html
    less example.html

### Завдання 5. Перевірити локальний backend

Запусти власний Node.js, Express або NestJS backend, а потім виконай:

    curl -i http://localhost:3000

Якщо сервер використовує API-маршрут:

    curl -i http://localhost:3000/api

Заміни адресу й маршрут на ті, які реально визначені у твоєму проєкті.

### Завдання 6. Надіслати JSON до тестового endpoint

    curl -i http://localhost:3000/api/users \
      -H "Content-Type: application/json" \
      -d '{"name":"Test User"}'

Перевір:

- чи правильний метод;
- чи є потрібний маршрут;
- чи повертається очікуваний статус;
- чи відповідає тіло результату запиту.

### Завдання 7. Дослідити помилки

Порівняй:

    curl -v http://localhost:3000
    curl -v http://localhost:3999
    curl -i https://example.com/nonexistent-page

Поясни різницю між помилкою з'єднання, відсутнім маршрутом і HTTP-відповіддю з помилковим статусом.

## 22. Мінішпаргалка

    # Отримати HTML або тіло відповіді
    curl https://example.com

    # Отримати заголовки через HEAD
    curl -I https://example.com

    # Показати заголовки та тіло
    curl -i https://example.com

    # Докладна діагностика
    curl -v https://example.com

    # Пройти за перенаправленнями
    curl -L https://example.com

    # Зберегти відповідь у файл
    curl -o page.html https://example.com

    # Зберегти під назвою з URL
    curl -O https://example.com/file.zip

    # Вивести тільки HTTP-статус
    curl -sS -o /dev/null -w "%{http_code}\n" https://example.com

    # Обмежити загальний час запиту
    curl --max-time 10 https://example.com

    # Обмежити час установлення з'єднання
    curl --connect-timeout 5 https://example.com

    # Надіслати JSON
    curl https://api.example.com/users \
      -H "Content-Type: application/json" \
      -d '{"name":"Test"}'

    # Завантажити файл через wget
    wget https://example.com/file.zip

    # Вказати ім'я файлу
    wget -O archive.zip https://example.com/file.zip

    # Продовжити завантаження
    wget -c https://example.com/large-file.zip

    # Вибрати каталог
    wget -P ~/Downloads https://example.com/file.zip

    # Перевірити ресурс без звичайного завантаження
    wget -S --spider https://example.com

    # Перевірити DNS
    getent hosts example.com

## 23. Що потрібно пам'ятати

- `curl` — універсальний інструмент для HTTP-запитів, API та діагностики мережевих проблем.
- `wget` — зручний інструмент для завантаження файлів, повторних спроб і продовження перерваних завантажень.
- `curl -I` виконує HEAD-запит, а `curl -i` додає заголовки до виводу звичайної відповіді.
- `curl -v` допомагає побачити, що відбувається під час з'єднання.
- `curl -L` дозволяє переходити за перенаправленнями.
- HTTP-статус `404` або `500` — це відповідь сервера, а не обов'язково помилка мережевого з'єднання.
- `curl` за замовчуванням не вважає кожен HTTP-статус `4xx` або `5xx` помилкою завершення команди.
- Для API потрібно правильно вказувати метод, заголовки, тіло запиту й endpoint.
- `curl -k` вимикає перевірку сертифіката й не повинен бути звичайним рішенням проблеми HTTPS.
- Під час розробки backend перевіряй маршрути безпосередньо через `curl`, перш ніж шукати причину проблеми у frontend.
- У мережевій діагностиці розрізняй DNS, встановлення з'єднання, TLS і HTTP-відповідь.

**Головна ідея:** `ping` допомагає перевірити ICMP-зв'язок із вузлом, а `curl` і `wget` дають змогу перевіряти прикладні протоколи та отримувати реальні ресурси. Для Full Stack JavaScript-розробника `curl` — один із найкорисніших інструментів перевірки backend API без браузера.
