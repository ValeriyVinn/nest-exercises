# 05. ss and netstat

`ss` і `netstat` — командні інструменти Linux для перегляду мережевих з'єднань, сокетів, портів, статистики мережевих протоколів і таблиць маршрутизації.

`ss` — сучасний інструмент для аналізу сокетів у Linux. Він зазвичай доступний без додаткового встановлення та є основним вибором для діагностики мережевих з'єднань.

`netstat` — традиційна утиліта з пакета `net-tools`. У багатьох сучасних дистрибутивах вона не встановлена за замовчуванням, але досі зустрічається в документації та старих інструкціях.

Для Full Stack JavaScript-розробника ці команди корисні під час діагностики Node.js, Express, NestJS, PostgreSQL та інших мережевих сервісів.

## 1. Що потрібно знати

✔ `ss` — показує інформацію про мережеві сокети та з'єднання.

✔ `netstat` — стара утиліта для перегляду мережевої статистики, з'єднань, портів і маршрутів.

✔ **Socket** — програмний механізм для мережевої взаємодії.

✔ **Listening socket** — сокет, який очікує на вхідні TCP-з'єднання або приймає UDP-датаграми відповідно до своєї конфігурації.

✔ **TCP connection** — встановлене з'єднання між двома кінцевими точками.

✔ **Port** — числовий ідентифікатор транспортної кінцевої точки.

✔ **PID** — ідентифікатор процесу.

✔ **Process** — програма, що виконується в операційній системі.

✔ **Local Address** — локальна IP-адреса та порт сокета.

✔ **Peer Address** — адреса віддаленої сторони з'єднання.

✔ `LISTEN` — TCP-сокет очікує на вхідні з'єднання.

✔ `ESTAB` — TCP-з'єднання встановлено.

✔ `TIME-WAIT` — TCP-стан очікування після закриття з'єднання, потрібний для коректного завершення TCP-взаємодії.

✔ `CLOSE-WAIT` — віддалена сторона закрила з'єднання, а локальний процес ще не завершив його закриття.

✔ `-t` — фільтр TCP.

✔ `-u` — фільтр UDP.

✔ `-l` — listening sockets.

✔ `-a` — усі відповідні сокети, а не тільки ті, що слухають.

✔ `-n` — показувати числові адреси й порти.

✔ `-p` — показувати інформацію про процеси, якщо вона доступна.

## 2. Перевірка наявності команд

### 2.1. Перевірити ss

    ss --version

Також можна виконати:

    command -v ss

На Ubuntu `ss` зазвичай входить до набору інструментів `iproute2`.

### 2.2. Перевірити netstat

    netstat --version

Або:

    command -v netstat

Якщо команда відсутня, це не обов'язково означає проблему з мережею. Імовірно, пакет `net-tools` просто не встановлений.

### 2.3. Встановити netstat в Ubuntu

    sudo apt update
    sudo apt install net-tools

Після встановлення:

    netstat --version

**Запам'ятай:** для нових навчальних проєктів насамперед вивчай `ss`. `netstat` варто знати для сумісності зі старими інструкціями та системами.

## 3. Основи ss

### 3.1. Показати всі сокети

    ss -a

Команда показує сокети різних типів, які підтримуються відповідним режимом виводу.

Для окремих протоколів і типів сокетів зручніше використовувати конкретні параметри.

### 3.2. Показати TCP-сокети

    ss -t

Параметр `-t` обмежує вивід TCP-сокетами.

Без `-a` команда зазвичай зосереджується на встановлених або активних TCP-з'єднаннях, а не на всіх listening sockets.

### 3.3. Показати UDP-сокети

    ss -u

Параметр `-u` обмежує вивід UDP-сокетами.

UDP не має TCP-подібного процесу встановлення з'єднання та стану `LISTEN`. Проте UDP-сокет може бути прив'язаний до локальної адреси й порту та очікувати датаграми.

### 3.4. Показати TCP та UDP

    ss -tu

Команда показує TCP- та UDP-сокети, які відповідають вибраним умовам відображення.

### 3.5. Показати тільки listening sockets

    ss -l

Параметр `-l` обмежує вивід сокетами, що слухають або очікують на вхідні дані відповідно до типу сокета.

На практиці частіше використовують комбінації:

    ss -lt
    ss -lu

Перша команда показує TCP listening sockets, друга — UDP-сокети, прив'язані до локальних адрес і портів.

## 4. Найважливіші параметри ss

| Параметр | Значення |
|---|---|
| `-t` | TCP-сокети |
| `-u` | UDP-сокети |
| `-l` | Listening sockets |
| `-a` | Усі відповідні сокети |
| `-n` | Числові адреси та порти |
| `-p` | Інформація про процеси |
| `-r` | Спроба розв'язання адрес у зрозуміліші імена |
| `-e` | Розширена інформація про сокети |
| `-m` | Інформація про використання пам'яті сокетами |
| `-s` | Загальна статистика сокетів |
| `-4` | IPv4-сокети |
| `-6` | IPv6-сокети |
| `-i` | Внутрішня TCP-інформація |
| `-o` | Інформація про таймери сокетів |

Параметри можна комбінувати. Наприклад:

    ss -ltnp

Це одна з найкорисніших команд для щоденної діагностики.

## 5. Перегляд listening ports

### 5.1. Усі TCP-порти, що слухають

    ss -lt

Показує TCP listening sockets.

Приклад умовного виводу:

    State  Recv-Q Send-Q Local Address:Port Peer Address:Port
    LISTEN 0      511    0.0.0.0:3000       0.0.0.0:*

Це означає, що TCP-сокет слухає порт `3000` на всіх відповідних локальних IPv4-адресах.

`Recv-Q` і `Send-Q` мають різне значення залежно від стану сокета. Для listening TCP-сокета вони пов'язані з чергами приймання з'єднань; не слід трактувати їх так само, як для встановленого з'єднання.

### 5.2. TCP-порти з числовими адресами

    ss -ltn

Параметр `-n` не перетворює номери портів на назви сервісів.

Це корисно, коли потрібно побачити точні адреси та номери портів без додаткового розв'язання назв.

### 5.3. TCP-порти з інформацією про процеси

    sudo ss -ltnp

Команда показує listening TCP-сокети та, якщо доступно, процеси, пов'язані з ними.

Приклад:

    State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
    LISTEN 0      511    0.0.0.0:3000       0.0.0.0:*       users:(("node",pid=1234,fd=20))

Це умовний приклад. Реальні PID, назви процесів і адреси залежать від системи.

### 5.4. Усі TCP- та UDP-порти, що слухають

    sudo ss -tulpn

Пояснення:

- `-t` — TCP;
- `-u` — UDP;
- `-l` — listening sockets;
- `-p` — інформація про процеси;
- `-n` — числові адреси й порти.

Ця команда особливо корисна для перевірки, які сервіси доступні на локальних інтерфейсах.

### 5.5. Показати IPv4-сокети

    ss -4 -ltn

### 5.6. Показати IPv6-сокети

    ss -6 -ltn

Це допомагає з'ясувати, чи слухає сервіс IPv4, IPv6 або обидва протоколи. Поведінка dual-stack залежить від конфігурації системи та сокета.

## 6. Перегляд активних TCP-з'єднань

### 6.1. Показати встановлені TCP-з'єднання

    ss -t

Це короткий огляд TCP-з'єднань, які відповідають стандартним умовам виводу команди.

### 6.2. Показати всі TCP-стани

    ss -ta

Параметр `-a` дозволяє переглядати не лише встановлені з'єднання, а й інші відповідні TCP-сокети.

### 6.3. Залишити числові адреси

    ss -tan

Це зручний режим для аналізу адрес і портів.

### 6.4. Показати процеси активних TCP-з'єднань

    sudo ss -tanp

Зверни увагу на локальну адресу, віддалену адресу, порт і стан з'єднання.

### 6.5. Основні TCP-стани

| Стан | Значення |
|---|---|
| `LISTEN` | Сокет очікує на вхідні TCP-з'єднання |
| `ESTAB` | TCP-з'єднання встановлено |
| `SYN-SENT` | Надіслано запит на встановлення з'єднання |
| `SYN-RECV` | Отримано запит на встановлення з'єднання |
| `FIN-WAIT-1` | Почалося завершення локальної сторони з'єднання |
| `FIN-WAIT-2` | Локальна сторона очікує на завершення з боку партнера |
| `CLOSE-WAIT` | Віддалена сторона закрила з'єднання; локальна програма ще має його закрити |
| `LAST-ACK` | Сторона очікує підтвердження завершення |
| `TIME-WAIT` | Очікування після закриття TCP-з'єднання |
| `CLOSED` | З'єднання закрите |

Не всі стани будуть присутні у звичайному виводі. Частина з них виникає лише під час певних етапів життєвого циклу TCP.

## 7. Фільтрація за портом

Фільтри `ss` дають змогу переглядати тільки потрібні сокети.

### 7.1. Перевірити TCP-порт 3000, що слухає

    ss -ltn 'sport = :3000'

` sport ` означає локальний порт у фільтрі `ss`.

Команда шукає TCP listening sockets на локальному порту `3000`.

### 7.2. Перевірити TCP-з'єднання з локальним портом 3000

    ss -tan 'sport = :3000'

Це корисно, коли потрібно знайти TCP-сокети, пов'язані з локальним портом `3000`, незалежно від того, чи слухають вони, чи перебувають в іншому стані.

### 7.3. Знайти з'єднання з віддаленим портом 443

    ss -tn 'dport = :443'

`dport` — порт призначення.

Команда фільтрує TCP-сокети, для яких віддалений порт дорівнює `443`.

### 7.4. Фільтрація за IP-адресою

    ss -tn 'dst 192.168.1.10'

Фільтр `dst` шукає сокети за адресою призначення.

Для конкретного аналізу завжди звіряй результат із напрямком з'єднання та адресами виводу `ss`.

### 7.5. Поєднання умов

    ss -tn state established '( dport = :443 or sport = :443 )'

Команда шукає встановлені TCP-з'єднання, у яких локальний або віддалений порт дорівнює `443`.

Фільтри `ss` мають власний синтаксис. Якщо складний фільтр не працює, спочатку виконай простішу команду, наприклад `ss -tan`, і поступово додавай умови.

## 8. Перегляд UDP-сокетів

UDP не використовує TCP-стани `LISTEN` і `ESTAB` у тому самому значенні.

### 8.1. UDP-сокети

    ss -u

### 8.2. UDP-сокети, прив'язані до локальних портів

    ss -lu

### 8.3. UDP із числовими адресами

    ss -lun

### 8.4. UDP із процесами

    sudo ss -lunp

### 8.5. Перевірити UDP-порт 53

    ss -lun 'sport = :53'

Ця команда допомагає перевірити, чи є UDP-сокет, прив'язаний до локального порту `53`, наприклад для DNS-сервісу.

Відсутність такого сокета не означає, що DNS на комп'ютері взагалі не працює: система може використовувати віддалений DNS-сервер або інший локальний механізм.

## 9. Показати процес, який використовує порт

### 9.1. Через ss

    sudo ss -ltnp 'sport = :3000'

Знайди PID і назву процесу у виводі.

### 9.2. Через lsof

    sudo lsof -i :3000

`lsof` показує процеси, які мають відкриті мережеві сокети, пов'язані з портом `3000`.

### 9.3. Переглянути процес за PID

    ps -p 1234 -o pid,ppid,user,stat,cmd

Заміни `1234` на PID, отриманий із `ss` або `lsof`.

### 9.4. Переглянути процеси Node.js

    ps -ef | grep '[n]ode'

Це допомагає знайти процеси Node.js, але не доводить, що конкретний процес займає певний порт.

Для точного зіставлення процесу з портом використовуй `ss -p` або `lsof`.

## 10. netstat: основи

`netstat` — традиційна команда для перегляду мережевих з'єднань і статистики.

Її синтаксис відрізняється від `ss`, але багато параметрів схожі.

### 10.1. Показати активні з'єднання

    netstat

За замовчуванням команда виводить інформацію про мережеві з'єднання, залежно від параметрів і реалізації.

### 10.2. Показати TCP-з'єднання

    netstat -t

### 10.3. Показати UDP-сокети

    netstat -u

### 10.4. Показати listening sockets

    netstat -l

### 10.5. Показати числові адреси й порти

    netstat -n

Параметр `-n` вимикає перетворення числових адрес і портів на імена.

### 10.6. Показати процеси

    sudo netstat -p

Показує інформацію про процеси, якщо вона доступна.

### 10.7. Найкорисніша комбінація

    sudo netstat -tulpn

Параметри:

- `-t` — TCP;
- `-u` — UDP;
- `-l` — listening;
- `-p` — процеси;
- `-n` — числові адреси й порти.

Це один із найпоширеніших варіантів використання `netstat` у старих інструкціях.

## 11. Перегляд маршрутів через netstat

`netstat` може показувати таблицю маршрутизації.

    netstat -rn

Параметри:

- `-r` — таблиця маршрутів;
- `-n` — числові адреси.

На сучасному Linux для перегляду маршрутів зазвичай краще використовувати `ip route`:

    ip route
    ip route show default

Ці команди належать до теми мережевих інтерфейсів і маршрутизації, але корисні під час комплексної діагностики.

## 12. Статистика мережі через ss і netstat

### 12.1. Загальна статистика ss

    ss -s

Команда показує зведену інформацію про кількість сокетів та їхні категорії.

### 12.2. Статистика протоколів через netstat

    netstat -s

Команда показує статистику мережевих протоколів, зокрема TCP, UDP та IP.

Вивід залежить від версії ядра, утиліти та доступних даних.

### 12.3. Показати інтерфейси через netstat

    netstat -i

Показує мережеві інтерфейси та частину статистики їхньої роботи.

У сучасних системах для цього також зручно використовувати:

    ip -s link

Команда `ip -s link` показує статистику мережевих інтерфейсів, зокрема кількість переданих і прийнятих пакетів та помилки.

## 13. Порівняння ss і netstat

| Можливість | `ss` | `netstat` |
|---|---|---|
| Перегляд TCP-з'єднань | Так | Так |
| Перегляд UDP-сокетів | Так | Так |
| Listening ports | Так | Так |
| Інформація про процеси | `-p` | `-p` |
| Числові адреси й порти | `-n` | `-n` |
| Статистика сокетів | `-s` | `-s`, інший набір статистики |
| Таблиця маршрутів | Не основне призначення | `-r` |
| Статистика інтерфейсів | Не основне призначення | `-i` |
| Наявність в Ubuntu | Зазвичай є | Може потребувати встановлення |
| Рекомендація для нових Linux-проєктів | Основний інструмент | Для сумісності зі старими інструкціями |

**Запам'ятай:** `ss` не є повною копією всіх можливостей `netstat`. Для інтерфейсів і маршрутів у сучасному Linux часто зручніше використовувати `ip`.

## 14. Практичний сценарій: Node.js backend

Припустимо, твій Express або NestJS застосунок має слухати порт `3000`.

### Крок 1. Перевір listening socket

    ss -ltn 'sport = :3000'

Якщо команда нічого не виводить, відповідного TCP listening socket не знайдено.

### Крок 2. Знайди процес

    sudo ss -ltnp 'sport = :3000'

Перевір назву процесу та PID.

### Крок 3. Перевір HTTP-відповідь

    curl -i http://localhost:3000

Якщо сервер працює, ти маєш отримати HTTP-відповідь. Це може бути навіть `404`, якщо маршрут `/` не визначений.

### Крок 4. Перевір TCP-з'єднання

    nc -vz localhost 3000

Якщо TCP-підключення успішне, це ще не доводить, що потрібний HTTP-маршрут працює правильно.

### Крок 5. Якщо порт зайнятий

    sudo lsof -iTCP:3000 -sTCP:LISTEN

Визнач процес, перш ніж намагатися його зупинити.

### Крок 6. Перевір процес

    ps -p 1234 -o pid,ppid,user,stat,cmd

Заміни `1234` на справжній PID.

### Крок 7. Зупини власний процес коректно

Якщо сервер запущено в терміналі, зазвичай достатньо:

    Ctrl+C

Для процесу, який потрібно зупинити через PID, можна використати:

    kill 1234

Не завершуй невідомі системні процеси лише тому, що вони використовують порт.

## 15. Практичний сценарій: перевірка PostgreSQL

PostgreSQL зазвичай використовує TCP-порт `5432`.

### Крок 1. Перевір listening socket

    ss -ltn 'sport = :5432'

### Крок 2. Визнач процес

    sudo ss -ltnp 'sport = :5432'

### Крок 3. Перевір TCP-підключення

    nc -vz localhost 5432

### Крок 4. Перевір реальне підключення до бази

    psql -h localhost -p 5432 -U taubu -d educational

Заміни користувача, базу даних та порт на значення зі своєї конфігурації.

**Важливо:** listening socket і успішне TCP-підключення не гарантують успішної автентифікації PostgreSQL. Потрібно також перевірити користувача, пароль, назву бази, `pg_hba.conf` і налаштування сервера.

## 16. Діагностика мережевих проблем

### 16.1. Ситуація: порт не слухається

Виконай:

    ss -ltnp 'sport = :3000'

Перевір:

- чи запущений сервер;
- чи правильний порт;
- чи не використовує застосунок інший протокол;
- чи не завершується процес одразу після запуску.

### 16.2. Ситуація: порт слухається, але клієнт не підключається

Перевір:

    ss -ltnp 'sport = :3000'
    ip addr
    ip route

Можливі причини:

- сервер слухає лише loopback;
- використовується неправильна IP-адреса;
- firewall блокує з'єднання;
- відсутній мережевий маршрут;
- клієнт і сервер перебувають у різних мережевих просторах.

### 16.3. Ситуація: TCP-з'єднання працює, але API повертає помилку

Виконай:

    curl -i http://localhost:3000

Перевір:

- HTTP-статус;
- правильність маршруту;
- метод запиту;
- заголовки;
- тіло запиту;
- логи backend.

`ss` показує інформацію про сокети, але не аналізує логіку обробки HTTP-запитів.

### 16.4. Ситуація: з'єднання довго перебуває в CLOSE-WAIT

Перевір:

    ss -tan state close-wait

Окремі записи `CLOSE-WAIT` можуть бути нормальними на короткий час. Якщо їх накопичується багато, програма може не закривати сокети після закриття з'єднання віддаленою стороною.

Подальша діагностика потребує аналізу конкретного процесу та його коду.

### 16.5. Ситуація: багато TIME-WAIT

    ss -tan state time-wait

`TIME-WAIT` є нормальною частиною TCP. Велика кількість таких записів не означає автоматично проблему.

Потрібно враховувати інтенсивність з'єднань, тривалість їхнього життя та архітектуру застосунку.

## 17. Типові помилки початківців

### Помилка 1. Використовувати netstat, не знаючи про ss

У сучасному Linux `ss` зазвичай доступний відразу й часто є зручнішим вибором.

**Правильно:** вивчи `ss`, але розумій команди `netstat`, які можуть траплятися в старих інструкціях.

### Помилка 2. Виконувати ss -t і очікувати побачити всі listening ports

    ss -t

Для listening sockets краще використовувати:

    ss -lt

Для всіх відповідних TCP-сокетів:

    ss -ta

### Помилка 3. Плутати локальний порт і віддалений порт

У виводі `ss` є локальна й віддалена кінцеві точки.

Фільтр `sport` відповідає локальному порту, а `dport` — порту призначення у віддаленій кінцевій точці.

### Помилка 4. Вважати, що відкритий порт гарантує роботу застосунку

Listening socket означає, що є сокет у відповідному стані. Це не гарантує, що сервер правильно обробляє запити.

Перевіряй порт і прикладний протокол окремо.

### Помилка 5. Вважати, що відсутність результату доводить відсутність сервісу

Сервіс може використовувати іншу адресу, інший порт, UDP замість TCP або інший мережевий простір імен.

Перевіряй параметри запиту й конфігурацію застосунку.

### Помилка 6. Завершувати процес, не перевіривши PID

Перед `kill` перевір, який саме процес використовує порт:

    ps -p 1234 -o pid,ppid,user,stat,cmd

### Помилка 7. Ігнорувати IPv4 та IPv6

Сервер може слухати `127.0.0.1`, але не `::1`, або навпаки. Також він може слухати лише певну мережеву адресу.

Перевіряй:

    ss -4 -ltn
    ss -6 -ltn

### Помилка 8. Вважати TIME-WAIT помилкою

`TIME-WAIT` — нормальний TCP-стан. Його потрібно оцінювати в контексті, а не намагатися автоматично усунути.

## 21. Мінішпаргалка

    # TCP listening sockets
    ss -lt

    # UDP sockets
    ss -lu

    # TCP listening sockets із числовими адресами
    ss -ltn

    # Listening TCP/UDP sockets із процесами
    sudo ss -tulpn

    # Усі TCP-сокети
    ss -ta

    # TCP-сокети з числовими адресами
    ss -tan

    # Встановлені TCP-з'єднання
    ss -tan state established

    # TCP-з'єднання в CLOSE-WAIT
    ss -tan state close-wait

    # TCP-з'єднання в TIME-WAIT
    ss -tan state time-wait

    # Перевірити TCP-порт 3000
    ss -ltn 'sport = :3000'

    # Перевірити UDP-порт 53
    ss -lun 'sport = :53'

    # Знайти процес на TCP-порту 3000
    sudo lsof -iTCP:3000 -sTCP:LISTEN

    # Перевірити всі listening ports через netstat
    sudo netstat -tulpn

    # Переглянути таблицю маршрутів через netstat
    netstat -rn

    # Переглянути статистику протоколів
    netstat -s

    # Сучасний перегляд таблиці маршрутів
    ip route

    # Статистика мережевих інтерфейсів
    ip -s link

## 22. Що потрібно пам'ятати

- `ss` — основний сучасний інструмент Linux для аналізу сокетів і мережевих з'єднань.
- `netstat` — традиційна утиліта, яку корисно знати для роботи зі старими інструкціями.
- `ss -ltnp` показує TCP listening sockets із числовими адресами й інформацією про процеси.
- `ss -tulpn` — одна з найкорисніших команд для перевірки портів.
- `-t` означає TCP, `-u` — UDP, `-l` — listening, `-n` — числовий формат, `-p` — інформація про процеси.
- `LISTEN` означає очікування TCP-з'єднань, а `ESTAB` — встановлене TCP-з'єднання.
- `CLOSE-WAIT` може вказувати на те, що локальний процес ще не закрив сокет після завершення віддаленої сторони.
- `TIME-WAIT` — нормальний стан TCP, який сам по собі не є помилкою.
- Listening socket не гарантує, що API працює правильно. Перевіряй прикладний протокол через `curl`.
- Для пошуку власника порту використовуй `ss -p` або `lsof`.
- Для перегляду маршрутів у сучасному Linux використовуй `ip route`, а для статистики інтерфейсів — `ip -s link`.
- Перед завершенням процесу перевіряй його PID і призначення.

**Головна ідея:** `ss` допомагає зрозуміти, які мережеві сокети відкриті, які з'єднання встановлені та які процеси використовують порти. `netstat` дає схожу базову інформацію й залишається корисним для сумісності зі старими Linux-інструкціями.
