# 02. Ping and Connectivity

Ping and Connectivity (перевірка зв'язку та мережевої доступності) — це базова тема Linux Networking, яка допомагає перевірити, чи може комп'ютер обмінюватися мережевими пакетами з іншими пристроями.

У Linux для перевірки мережевого зв'язку найчастіше використовують команду `ping`.

Команда `ping` надсилає ICMP Echo Request і очікує на ICMP Echo Reply від цільового пристрою. За результатами можна оцінити доступність вузла, затримку передавання пакетів та втрату пакетів.

Ця тема використовується, коли потрібно:

- перевірити, чи працює локальний мережевий стек;
- перевірити доступність маршрутизатора;
- перевірити зв'язок з іншим комп'ютером у локальній мережі;
- перевірити доступність віддаленої IP-адреси;
- з'ясувати, чи є ознаки проблем із мережевим підключенням;
- виміряти приблизну затримку мережевого обміну;
- перевірити втрату пакетів;
- відрізнити проблему IP-з'єднання від проблеми DNS;
- виконати базову діагностику мережі перед використанням `curl`, `ssh` або інших мережевих інструментів.

Основні команди:

    ping
    ping -c
    ping -i
    ping -W
    ping -w
    ping -4
    ping -6
    ip addr
    ip route
    getent hosts
    tracepath
    traceroute
    mtr

Основна команда для початкової перевірки:

    ping -c 4 127.0.0.1

Для перевірки доступності зовнішньої IP-адреси:

    ping -c 4 1.1.1.1

Для перевірки доступності доменного імені:

    ping -c 4 example.com

Важливо: відсутність відповіді на `ping` не завжди означає, що пристрій недоступний. ICMP може блокуватися firewall, мережевими правилами або самим цільовим вузлом.

## Що потрібно пам'ятати

• `ping` — команда для перевірки мережевого зв'язку за допомогою ICMP Echo Request та Echo Reply.

• ICMP — протокол мережевого рівня, який використовується, зокрема, для діагностики та повідомлень про мережеві помилки.

• `ping -c 4` надсилає чотири запити та завершує роботу після їх обробки.

• `ping 127.0.0.1` перевіряє локальний IPv4-мережевий стек.

• `ping ::1` або `ping -6 ::1` перевіряє локальний IPv6-мережевий стек.

• `ping` без параметрів кількості запитів зазвичай продовжує працювати, доки його не зупинити через `Ctrl + C`.

• Час відповіді зазвичай показується в мілісекундах (`ms`).

• `time=20 ms` означає приблизно 20 мілісекунд на повний шлях запиту та відповіді, а не лише в один бік.

• `packet loss` — відсоток пакетів, на які не було отримано відповіді протягом перевірки.

• `100% packet loss` означає, що жоден із надісланих запитів не отримав відповіді. Це не обов'язково доводить, що цільовий пристрій вимкнений.

• Якщо `ping` за IP-адресою працює, а за доменним ім'ям — ні, варто перевірити DNS. Однак можуть існувати й інші причини.

• Якщо `ping` не працює, потрібно перевірити IP-адресу, маршрутизацію, шлюз, firewall і можливість блокування ICMP.

• Успішний `ping` не гарантує, що вебсайт, SSH-сервер або конкретний TCP-порт доступні.

• Невдалий `ping` не гарантує, що вебсайт або інший сервіс недоступний.

• `tracepath`, `traceroute` і `mtr` допомагають досліджувати маршрут до віддаленого вузла.

• Для початкової діагностики важливо перевіряти мережу послідовно: від локального комп'ютера до зовнішнього ресурсу.

# Network Connectivity

Network connectivity — це здатність пристроїв обмінюватися даними через мережу.

Наприклад, комп'ютер може мати:

    Network interface
    IP address
    Default gateway
    DNS configuration

Але це не означає, що всі мережеві з'єднання обов'язково працюватимуть.

Можливі проблеми:

    Interface is down
    Missing IP address
    Wrong subnet
    Missing default route
    Gateway is unreachable
    DNS resolution failure
    Firewall blocks traffic
    Remote server is unavailable
    ICMP packets are filtered

Тому діагностика повинна відбуватися поступово.

Приклад схеми:

    Linux Computer
          |
          v
    Local Network Stack
          |
          v
    Network Interface
          |
          v
    Local Network / Router
          |
          v
    Internet
          |
          v
    Remote Host

Команда `ping` допомагає перевірити окремі ділянки цього шляху, якщо відповідні вузли відповідають на ICMP-запити.

---

# ICMP

ICMP (Internet Control Message Protocol) — протокол, який використовується для передавання повідомлень про стан мережі та деякі помилки передавання IP-пакетів.

`ping` зазвичай використовує два типи ICMP-повідомлень:

    ICMP Echo Request
    ICMP Echo Reply

Спрощена схема:

    Client
       |
       | ICMP Echo Request
       v
    Remote Host
       |
       | ICMP Echo Reply
       v
    Client

Якщо клієнт отримав відповідь, це означає, що ICMP-обмін із цим вузлом спрацював.

Однак це не перевіряє всі інші мережеві протоколи.

Наприклад, сервер може відповідати на `ping`, але не приймати HTTP-запити на порті `80`.

Або сервер може обслуговувати HTTPS, але блокувати ICMP.

Тому `ping` — лише один із інструментів діагностики.

---

# Команда ping

`ping` — команда Linux для перевірки доступності мережевого вузла за допомогою ICMP.

Синтаксис:

    ping [OPTIONS] destination

Де:

    ping        → команда
    OPTIONS     → необов'язкові параметри
    destination → IP-адреса або hostname

Приклади:

    ping 127.0.0.1

    ping 192.168.1.1

    ping 1.1.1.1

    ping example.com

Поведінка команди залежить від параметрів, реалізації `ping` та системного оточення.

У більшості Linux-дистрибутивів команда `ping` за замовчуванням продовжує надсилати запити, доки її не зупинити вручну.

---

# Перевірка localhost

`localhost` — ім'я, яке зазвичай використовується для звернення до самого комп'ютера.

Типові loopback-адреси:

    127.0.0.1
    ::1

Перевірка IPv4:

    ping -c 4 127.0.0.1

Приклад результату:

    PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.
    64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.050 ms
    64 bytes from 127.0.0.1: icmp_seq=2 ttl=64 time=0.041 ms
    64 bytes from 127.0.0.1: icmp_seq=3 ttl=64 time=0.044 ms
    64 bytes from 127.0.0.1: icmp_seq=4 ttl=64 time=0.042 ms

    --- 127.0.0.1 ping statistics ---
    4 packets transmitted, 4 received, 0% packet loss

Це умовний приклад результату.

Успішна відповідь показує, що локальний IPv4-мережевий стек обробляє ці ICMP-запити.

Вона не доводить, що Wi-Fi, Ethernet, маршрутизатор або Інтернет працюють.

---

## Перевірка IPv6 loopback

Команда:

    ping -6 -c 4 ::1

Або в системах, де `ping` автоматично визначає сімейство адрес:

    ping -c 4 ::1

Приклад результату:

    64 bytes from ::1: icmp_seq=1 ttl=64 time=0.040 ms

`::1` — IPv6 loopback-адреса.

Якщо IPv6 вимкнений або налаштований інакше, результат може відрізнятися.

---

# Перевірка локального маршрутизатора

У домашній мережі маршрутизатор часто є шлюзом за замовчуванням.

Спочатку переглянь таблицю маршрутів:

    ip route

Приклад:

    default via 192.168.1.1 dev wlp2s0 proto dhcp metric 600
    192.168.1.0/24 dev wlp2s0 proto kernel scope link src 192.168.1.20

У цьому прикладі:

    192.168.1.1 → default gateway
    wlp2s0      → мережевий інтерфейс
    192.168.1.20 → локальна IPv4-адреса

Тепер перевір шлюз:

    ping -c 4 192.168.1.1

Використовуй реальну адресу зі своєї таблиці маршрутів, а не обов'язково `192.168.1.1`.

Якщо відповіді надходять, це свідчить про успішний ICMP-обмін зі шлюзом.

Якщо відповіді немає, можливі причини:

    Wrong gateway address
    Wi-Fi disconnected
    Ethernet connection problem
    Incorrect IP configuration
    Firewall filtering ICMP
    Router does not respond to ping

Відсутність відповіді сама по собі не доводить, що маршрутизатор несправний.

---

# Перевірка зовнішньої IP-адреси

Щоб перевірити зв'язок із зовнішнім вузлом без використання DNS, можна звернутися до IP-адреси.

Наприклад:

    ping -c 4 1.1.1.1

`1.1.1.1` — публічна IPv4-адреса DNS-резолвера Cloudflare. Вона використовується тут як приклад зовнішнього вузла для перевірки мережевого зв'язку, а не як гарантія доступності будь-якого сервісу.

Якщо відповіді надходять, це означає, що ICMP-обмін із цією адресою працює.

Якщо відповіді немає, можливі причини:

    Missing default route
    Gateway problem
    Internet connection failure
    Upstream network issue
    ICMP filtering
    Destination-specific filtering

Важливо: не роби висновок про стан DNS лише за результатом `ping 1.1.1.1`, оскільки тут використовується IP-адреса, а не доменне ім'я.

---

# Перевірка доменного імені

Команда `ping` може приймати hostname.

Наприклад:

    ping -c 4 example.com

Перед відправленням ICMP-запитів система зазвичай повинна визначити IP-адресу доменного імені.

Спрощена послідовність:

    example.com
         |
         v
    Name resolution
         |
         v
    IP address
         |
         v
    ICMP Echo Request
         |
         v
    Remote host

Якщо ім'я не вдалося розв'язати, команда може вивести повідомлення на кшталт:

    ping: example.com: Temporary failure in name resolution

Це вказує на проблему визначення імені, але конкретна причина потребує додаткової перевірки.

Можливі причини:

    DNS server unavailable
    Incorrect DNS configuration
    Network connectivity issue
    Temporary resolver failure
    Typo in hostname

Якщо доменне ім'я розв'язується, але відповіді на ICMP немає, це не обов'язково означає проблему DNS.

---

# Параметр -c

`-c` задає кількість запитів, які потрібно надіслати.

Синтаксис:

    ping -c COUNT destination

Приклад:

    ping -c 4 127.0.0.1

Команда надсилає чотири запити та завершується після їх обробки.

Ще приклад:

    ping -c 10 example.com

Надсилає до десяти запитів.

Це зручно для коротких тестів і скриптів.

Для початкової діагностики часто достатньо:

    ping -c 4 destination

---

# Зупинка ping через Ctrl + C

Якщо запустити:

    ping 127.0.0.1

команда зазвичай працюватиме без обмеження кількості запитів.

Щоб зупинити її:

    Ctrl + C

Після зупинки `ping` зазвичай показує статистику.

Приклад:

    ^C
    --- 127.0.0.1 ping statistics ---
    12 packets transmitted, 12 received, 0% packet loss

Це означає:

    12 transmitted → 12 запитів надіслано
    12 received    → 12 відповідей отримано
    0% packet loss → втрат відповідей не зафіксовано

`Ctrl + C` надсилає сигнал переривання поточному процесу у звичайному інтерактивному терміналі.

---

# Параметр -i

`-i` задає інтервал між запитами в секундах.

Приклад:

    ping -i 2 -c 5 1.1.1.1

Це запитує п'ять пакетів з інтервалом приблизно дві секунди.

Ще приклад:

    ping -i 0.5 -c 10 1.1.1.1

Інтервал приблизно пів секунди.

Можливість використання дуже малих інтервалів може залежати від прав користувача та реалізації `ping`.

Не надсилай надмірну кількість пакетів до сторонніх вузлів.

---

# Параметр -W

`-W` задає час очікування відповіді на окремий запит у секундах у типовій реалізації `iputils ping`.

Приклад:

    ping -W 2 -c 4 192.0.2.10

Команда очікує відповіді протягом обмеженого часу.

`192.0.2.10` — адреса з документаційного діапазону IPv4 `192.0.2.0/24`, тому вона використовується як приклад, а не як реальна ціль для перевірки Інтернету.

Важливо розрізняти:

    -W → timeout для очікування відповіді на запит
    -w → загальний deadline виконання ping

Точні деталі параметрів можуть відрізнятися в різних реалізаціях `ping`.

---

# Параметр -w

`-w` задає загальний час виконання команди в секундах у типовій реалізації `iputils ping`.

Приклад:

    ping -w 10 1.1.1.1

Команда завершується після досягнення загального deadline.

Якщо потрібно обмежити і час, і кількість пакетів, можна комбінувати параметри:

    ping -c 4 -w 10 1.1.1.1

Не плутай:

    -c → кількість запитів
    -W → час очікування відповіді
    -w → загальний deadline

---

# Параметри -4 та -6

Linux може використовувати IPv4 або IPv6 залежно від адреси та конфігурації.

## Примусове використання IPv4

    ping -4 -c 4 example.com

Команда використовує IPv4.

## Примусове використання IPv6

    ping -6 -c 4 example.com

Команда використовує IPv6.

Якщо домен має лише IPv4-записи або система не має IPv6-з'єднання, IPv6-перевірка може завершитися невдало.

Це не обов'язково означає, що IPv4-з'єднання також не працює.

## PING

Рядок:

    PING example.com (93.184.216.34)

Показує цільове ім'я та IP-адресу, яку було визначено для запиту.

Якщо використовується IPv6, адреса буде IPv6-формату.

---

## bytes

Приклад:

    64 bytes from 93.184.216.34

Показує розмір отриманої ICMP-відповіді.

Значення залежить від розміру пакета та реалізації команди.

---

## icmp_seq

Приклад:

    icmp_seq=1

Це порядковий номер ICMP-запиту.

Наступні відповіді можуть мати:

    icmp_seq=2
    icmp_seq=3
    icmp_seq=4

За номерами можна помітити, чи надходили відповіді на кожен запит.

---

## ttl

Приклад:

    ttl=54

TTL (Time To Live) — поле IP-пакета, яке обмежує кількість маршрутизаторів, через які пакет може пройти до того, як його буде відкинуто.

У IPv6 аналогічне за призначенням поле називається Hop Limit.

Значення TTL у відповіді не показує точну кількість маршрутизаторів до вузла, якщо невідоме початкове значення TTL та поведінка маршруту.

---

## time

Приклад:

    time=25.4 ms

Показує приблизний час між надсиланням запиту та отриманням відповіді.

Цей показник називають RTT (Round-Trip Time).

RTT включає шлях до вузла та назад.

Він не є прямим вимірюванням затримки передавання в один бік.

---

# RTT — Round-Trip Time

RTT — час, за який запит доходить до цільового вузла та відповідь повертається назад.

Приклад:

    time=10 ms
    time=25 ms
    time=80 ms

Загалом менше значення RTT означає меншу затримку повного циклу обміну.

Однак нормальні значення залежать від:

    Network distance
    Routing path
    Congestion
    Wi-Fi quality
    Router performance
    Server response behavior

Не варто оцінювати якість усієї мережі за одним вимірюванням.

---

# Packet Loss

Packet loss — втрата пакетів, тобто ситуація, коли частина надісланих пакетів не отримала відповідей у межах вимірювання.

Приклад:

    10 packets transmitted, 10 received, 0% packet loss

Втрати:

    0%

Інший приклад:

    10 packets transmitted, 8 received, 20% packet loss

Втрати:

    20%

Формула:

    Packet loss (%) =
        (Packets sent - Packets received)
        / Packets sent
        * 100

Наприклад:

    Sent = 10
    Received = 8

    (10 - 8) / 10 * 100 = 20%

Втрата відповідей може бути спричинена:

    Network congestion
    Wi-Fi interference
    Faulty network equipment
    Overloaded router
    Packet filtering
    Destination rate limiting

Важливо: відсутність ICMP-відповіді не завжди означає втрату звичайного користувацького трафіку. Деякі пристрої обмежують або блокують ICMP.

---

# Мінімальна, середня та максимальна затримка

Приклад статистики:

    rtt min/avg/max/mdev = 10.100/15.200/22.500/4.100 ms

Тут:

    min  → мінімальний RTT
    avg  → середній RTT
    max  → максимальний RTT
    mdev → середнє квадратичне відхилення RTT у реалізації iputils

Низьке середнє значення не гарантує відсутності проблем, якщо окремі вимірювання мають великі коливання.

Високі коливання можуть свідчити про нестабільність мережі, але потребують додаткової діагностики.

# DNS та ping

Коли запускається команда:

    ping example.com

система зазвичай спочатку визначає IP-адресу імені `example.com`.

Якщо визначення імені не працює, ICMP-запит може навіть не бути надісланий до цілі.

Щоб відокремити проблему DNS від проблеми ICMP, порівняй:

    ping -c 4 1.1.1.1

та:

    ping -c 4 example.com

Можливі ситуації:

| IP-адреса | Доменне ім'я | Можливе пояснення |
|---|---|---|
| Працює | Працює | IP-зв'язок та визначення імені працюють для цих перевірок |
| Працює | Не розв'язується | Можлива проблема DNS |
| Не працює | Не працює | Можлива проблема маршрутизації, доступу або блокування ICMP |
| Не працює | Працює | Домен може вести до іншого вузла; ICMP-політика або маршрут можуть відрізнятися |

Це лише орієнтир. Для повної діагностики потрібно перевіряти конкретні адреси, маршрути та сервіси.

# Чому ping може не працювати, навіть коли сайт відкривається

`ping` використовує ICMP.

Браузер зазвичай використовує HTTP або HTTPS поверх TCP чи QUIC/UDP.

Це різні механізми.

Наприклад:

    ping example.com
        ↓
    ICMP Echo Request / Echo Reply

    curl https://example.com
        ↓
    HTTPS request

Сервер або firewall може дозволяти HTTPS, але блокувати ICMP.

Тому:

    ping fails
    website works

— цілком можлива ситуація.

Так само успішний `ping` не гарантує, що вебсервер відповідає на порті `443`.

# Команда getent hosts

`getent hosts` дозволяє перевірити, як система розв'язує hostname у мережеву адресу через налаштований механізм визначення імен.

Приклад:

    getent hosts example.com

Можливий результат:

    2606:2800:220:1:248:1893:25c8:1946 example.com

Це лише приклад можливого результату. Фактичні адреси та їхній порядок можуть змінюватися.

Перевірити localhost:

    getent hosts localhost

Перевірка через `getent` корисна, оскільки враховує системний механізм розв'язання імен, який може включати DNS та локальні записи.

Важливо: `getent hosts` не є повною діагностикою DNS-сервера. Для глибшої перевірки використовують спеціалізовані DNS-інструменти.

# TTL

TTL (Time To Live) — поле IPv4-пакета, яке обмежує кількість переходів між маршрутизаторами.

Приклад відповіді:

    64 bytes from 1.1.1.1: icmp_seq=1 ttl=57 time=15.2 ms

Тут:

    ttl=57

Це TTL, який залишився у відповіді на момент її отримання.

Кожен маршрутизатор, який пересилає IPv4-пакет, зазвичай зменшує TTL щонайменше на одиницю.

Коли TTL досягає нуля, пакет відкидається, а маршрутизатор зазвичай надсилає ICMP Time Exceeded, якщо це не блокується.

TTL не слід плутати з часом у мілісекундах.

    ttl=57     → ліміт переходів у IPv4-пакеті на момент отримання
    time=15 ms → приблизний час повного циклу запиту та відповіді

В IPv6 аналогічне поле називається Hop Limit.

# Перевірка маршруту: tracepath

`tracepath` — інструмент для дослідження маршруту до мережевого вузла.

Команда:

    tracepath example.com

Вона намагається визначити проміжні маршрутизатори та інші параметри шляху.

Для IPv4-адреси:

    tracepath 1.1.1.1

Для IPv6:

    tracepath -6 example.com

Наявність параметрів залежить від версії `tracepath`.

У деяких системах команда може бути відсутня. В Ubuntu вона зазвичай надається пакетом `iputils-tracepath`.

`tracepath` може допомогти, якщо потрібно зрозуміти, на якому етапі маршруту виникають проблеми.

Але деякі маршрутизатори не відповідають на діагностичні запити, тому зірочки або неповні результати не завжди свідчать про несправність маршруту.

---

# Команда traceroute

`traceroute` — інструмент для визначення проміжних вузлів на шляху до цільової адреси.

Приклад:

    traceroute example.com

Для IPv4:

    traceroute -4 example.com

Для IPv6:

    traceroute -6 example.com

Залежно від реалізації та параметрів, `traceroute` може використовувати UDP, ICMP або TCP-проби.

Якщо команда відсутня, пакет потрібно встановлювати лише за потреби.

Наприклад, в Ubuntu:

    sudo apt install traceroute

Перед встановленням перевір, чи доступна команда:

    command -v traceroute

`traceroute` доповнює `ping`, але не замінює перевірку маршрутизації та конкретного сервісу.

---

# Команда mtr

`mtr` поєднує ідею `ping` та `traceroute`.

Він може багаторазово перевіряти проміжні вузли й показувати статистику затримок та втрат.

Запуск:

    mtr example.com

Текстовий звіт:

    mtr --report --report-cycles 10 example.com

Це приклад параметрів типової реалізації `mtr`.

Для IPv4:

    mtr -4 example.com

Для IPv6:

    mtr -6 example.com

Якщо команда відсутня в Ubuntu:

    sudo apt install mtr-tiny

Пакет `mtr-tiny` надає текстову версію інструмента в Ubuntu.

Увага: втрати на проміжному маршрутизаторі не обов'язково означають втрати транзитного трафіку. Маршрутизатор може обмежувати відповіді на діагностичні пакети, продовжуючи нормально пересилати звичайний трафік.

# ping та firewall

Firewall може блокувати ICMP Echo Request або Echo Reply.

У такому випадку:

    ping → no response

але інші протоколи можуть працювати.

Наприклад:

    HTTPS → works
    SSH   → works
    ICMP  → blocked

Це не обов'язково свідчить про помилку конфігурації Linux.

Якщо ти адмініструєш власний сервер, перевір правила firewall та мережеву політику.

Якщо це сторонній сервер, не намагайся змінювати його налаштування. Використовуй дозволені способи перевірки доступності сервісу.

# Втрата пакетів та нестабільність Wi-Fi

Wi-Fi може мати втрати пакетів через:

    Weak signal
    Radio interference
    Congestion
    Distance from router
    Wireless adapter issues
    Router overload

Для початкової перевірки:

    ping -c 20 <gateway-ip>

Заміни `<gateway-ip>` на адресу свого маршрутизатора.

Потім порівняй із зовнішньою адресою:

    ping -c 20 1.1.1.1

Якщо втрати спостерігаються вже на шлюзі, варто перевірити локальне з'єднання, Wi-Fi та маршрутизатор.

Якщо шлюз відповідає стабільно, а зовнішня адреса має втрати, проблема може бути далі в мережі або пов'язана з політикою відповіді цільового вузла.

Не роби остаточний висновок за одним коротким тестом.

# Типові помилки

❌ Вважати, що `ping` перевіряє абсолютно всі види мережевого з'єднання.

`ping` перевіряє ICMP-обмін. Він не перевіряє безпосередньо HTTP, HTTPS, SSH або доступність конкретного TCP-порту.

---

❌ Вважати, що `100% packet loss` завжди означає, що сервер вимкнений.

ICMP може блокуватися firewall або обмежуватися цільовим вузлом.

---

❌ Вважати, що успішний `ping` гарантує доступність сайту.

Сервер може відповідати на ICMP, але вебсервер може бути зупинений або потрібний порт може бути закритий.

---

❌ Вважати, що невдалий `ping` означає відсутність Інтернету.

Можливо, ICMP блокується, але HTTP(S) працює.

---

❌ Плутати `-c`, `-W` та `-w`.

    -c → кількість запитів
    -W → час очікування відповіді
    -w → загальний deadline виконання

---

❌ Запускати `ping` без обмеження кількості пакетів у скрипті.

Якщо не передбачено зупинки, команда може продовжувати працювати необмежено довго.

Для короткої перевірки часто краще:

    ping -c 4 destination

---

❌ Вважати, що TTL — це затримка в мілісекундах.

    ttl=57     → Time To Live у IPv4
    time=15 ms → Round-Trip Time

Це різні показники.

---

❌ Вважати, що `ping example.com` перевіряє тільки DNS.

Команда спочатку визначає адресу, а потім намагається виконати ICMP-обмін.

---

❌ Вважати, що відсутність відповіді на одному проміжному вузлі в `traceroute` або `mtr` означає втрату всього трафіку.

Маршрутизатор може не відповідати на діагностичні пакети, але продовжувати пересилати звичайний трафік.

# Міні-шпаргалка

## Перевірити локальний IPv4-стек

    ping -c 4 127.0.0.1

## Перевірити IPv6 loopback

    ping -6 -c 4 ::1

## Перевірити шлюз

    ip route
    ping -c 4 <gateway-ip>

## Перевірити зовнішню IP-адресу

    ping -c 4 1.1.1.1

## Перевірити доменне ім'я

    ping -c 4 example.com

## Перевірити DNS-розв'язання через системний resolver

    getent hosts example.com

## Обмежити кількість запитів

    ping -c 4 example.com

## Вказати інтервал між запитами

    ping -i 2 -c 5 example.com

## Задати час очікування відповіді

    ping -W 2 -c 4 example.com

## Задати загальний deadline

    ping -w 10 example.com

## Примусово використовувати IPv4

    ping -4 -c 4 example.com

## Примусово використовувати IPv6

    ping -6 -c 4 example.com

## Перевірити HTTPS

    curl -I --max-time 10 https://example.com

## Дослідити маршрут

    tracepath example.com

## Переглянути звіт про маршрут

    mtr --report --report-cycles 10 example.com

# Основні правила

    ping → перевірка ICMP connectivity

    ICMP Echo Request → запит
    ICMP Echo Reply   → відповідь

    127.0.0.1 → IPv4 loopback
    ::1       → IPv6 loopback

    -c → кількість запитів
    -i → інтервал між запитами
    -W → час очікування відповіді
    -w → загальний deadline
    -4 → IPv4
    -6 → IPv6

    RTT        → час повного циклу запиту та відповіді
    Packet loss → відсоток запитів без отриманої відповіді
    TTL        → ліміт переходів у IPv4-пакеті

    ip addr  → IP-адреси інтерфейсів
    ip route → таблиця маршрутизації
    getent hosts → системне визначення hostname

    tracepath  → дослідження мережевого маршруту
    traceroute → визначення проміжних вузлів
    mtr        → повторні вимірювання на маршруті

# Головне

• `ping` — базовий інструмент перевірки мережевого зв'язку через ICMP.

• Починай перевірку з локального IPv4 loopback:

    ping -c 4 127.0.0.1

• Потім перевір інтерфейс, IP-адресу та таблицю маршрутизації:

    ip link
    ip addr
    ip route

• Для перевірки локального з'єднання спробуй звернутися до шлюзу за замовчуванням.

• Для перевірки зовнішнього зв'язку можна використати:

    ping -c 4 1.1.1.1

• Для перевірки доменного імені:

    getent hosts example.com
    ping -c 4 example.com

• Якщо `ping` за IP працює, а ім'я не розв'язується, досліди DNS.

• Якщо `ping` не працює, не роби поспішного висновку: ICMP може бути заблокований.

• Успішний `ping` не гарантує доступності HTTP, HTTPS, SSH або інших сервісів.

• Для перевірки HTTPS використовуй інструмент відповідного рівня:

    curl -I --max-time 10 https://example.com

• Для дослідження маршруту використовуй:

    tracepath
    traceroute
    mtr

• Діагностуй мережу послідовно: локальний стек → інтерфейс → IP-адреса → маршрут → шлюз → зовнішня адреса → DNS → потрібний сервіс.

• Мета діагностики — не просто отримати відповідь на `ping`, а зрозуміти, на якому етапі виникає проблема.
