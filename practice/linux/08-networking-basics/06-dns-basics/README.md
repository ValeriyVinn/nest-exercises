# DNS Basics

DNS (Domain Name System) — система доменних імен, яка перетворює доменні імена на IP-адреси та допомагає комп'ютерам знаходити сервери в мережі.

Наприклад, коли ти відкриваєш `https://google.com`, комп'ютеру потрібно дізнатися IP-адресу сервера, до якого слід підключитися. Для цього використовується DNS.

DNS — одна з основ мережевої діагностики Linux. Вона особливо важлива під час роботи з HTTP-запитами, Node.js, NestJS, PostgreSQL, API та віддаленими серверами.

Мета цієї теми — навчитися перевіряти DNS, знаходити проблеми з розпізнаванням доменів і розуміти, як Linux визначає IP-адреси.

## 2. Що таке DNS

DNS розшифровується як Domain Name System.

Це розподілена система, яка дозволяє використовувати доменні імена замість запам'ятовування IP-адрес.

Наприклад:

    google.com → IP-адреса сервера

Доменне ім'я зручне для людини, а IP-адреса потрібна для мережевого з'єднання.

### 2.1. Як працює DNS

Спрощена послідовність:

1. Користувач вводить доменне ім'я в браузері.
2. Операційна система намагається знайти відповідну IP-адресу.
3. Система перевіряє доступні локальні джерела і кеш.
4. Якщо потрібної відповіді немає, запит передається DNS-резолверу.
5. Резолвер знаходить потрібну DNS-відповідь.
6. Комп'ютер отримує IP-адресу.
7. Браузер підключається до сервера за цією адресою.

На практиці частину цих операцій можуть виконувати кеші браузера, операційної системи, локальний DNS-сервіс або мережевий резолвер.

### 2.2. DNS і HTTP — це різні речі

DNS допомагає знайти IP-адресу сервера.

HTTP або HTTPS використовуються для обміну даними із сервером.

Наприклад:

    Доменне ім'я
        ↓
    DNS-запит
        ↓
    IP-адреса
        ↓
    TCP-з'єднання
        ↓
    TLS для HTTPS
        ↓
    HTTP-запит
        ↓
    Відповідь сервера

Якщо DNS не працює, браузер може не знати, до якої IP-адреси підключатися.

Але якщо DNS працює, це ще не гарантує, що вебсервер доступний.

## 3. Доменні імена та IP-адреси

Доменне ім'я може відповідати одній або кільком IP-адресам.

Приклади доменів:

    google.com
    github.com
    example.com
    api.example.com

Приклади IP-адрес:

    192.0.2.10
    2001:db8::10

У прикладах вище використовуються адреси з діапазонів, зарезервованих для документації. Вони не призначені для звичайного доступу до публічних серверів.

### 3.1. Домен і піддомен

Наприклад:

    example.com
    www.example.com
    api.example.com
    docs.example.com

`example.com` — домен.

`api.example.com` — піддомен, який може використовуватися для API.

`docs.example.com` — піддомен, який може використовуватися для документації.

Різні піддомени можуть вести на один сервер або на різні сервери.

### 3.2. Чому домен може мати декілька IP-адрес

Причини:

- розподіл навантаження між серверами;
- резервування;
- географічний розподіл серверів;
- використання IPv4 та IPv6;
- особливості інфраструктури хостингу.

Тому не варто очікувати, що один домен завжди матиме лише одну IP-адресу.

## 4. Основні DNS-записи

DNS зберігає інформацію у вигляді записів різних типів.

| Тип | Призначення |
|---|---|
| A | Пов'язує ім'я з IPv4-адресою |
| AAAA | Пов'язує ім'я з IPv6-адресою |
| CNAME | Створює псевдонім для іншого доменного імені |
| MX | Вказує поштові сервери домену |
| NS | Вказує авторитетні DNS-сервери домену |
| TXT | Зберігає текстові дані, зокрема SPF та інші перевірки |
| PTR | Використовується для зворотного пошуку імені за IP-адресою |
| SOA | Містить основну інформацію про DNS-зону |

### 4.1. Запис A

Запис A пов'язує домен з IPv4-адресою.

Приклад:

    example.com → 192.0.2.10

Перевірка:

    dig example.com A

### 4.2. Запис AAAA

Запис AAAA пов'язує домен з IPv6-адресою.

Приклад:

    example.com → 2001:db8::10

Перевірка:

    dig example.com AAAA

### 4.3. Запис CNAME

CNAME вказує, що одне доменне ім'я є псевдонімом іншого.

Приклад:

    www.example.com → example.com

Перевірка:

    dig www.example.com CNAME

Важливо: запит CNAME покаже цей тип запису, якщо він безпосередньо існує. Звичайний запит A може одразу повернути кінцеву IPv4-адресу після обробки псевдоніма.

### 4.4. Запис MX

MX визначає поштові сервери домену.

Перевірка:

    dig example.com MX

MX важливий для налаштування корпоративної або доменної електронної пошти.

### 4.5. Запис NS

NS визначає авторитетні DNS-сервери, які обслуговують DNS-зону.

Перевірка:

    dig example.com NS

### 4.6. Запис TXT

TXT використовується для зберігання текстової інформації.

Приклади застосування:

- SPF — правила, які визначають, яким серверам дозволено надсилати пошту від імені домену;
- перевірка права власності на домен;
- окремі механізми автентифікації та безпеки.

Перевірка:

    dig example.com TXT

### 4.7. Запис PTR

PTR застосовується для зворотного DNS-пошуку: IP-адреса → доменне ім'я.

Приклад:

    dig -x 192.0.2.10

Наявність PTR-запису не гарантує, що прямий запис домену веде назад на ту саму адресу.

## 5. TTL — час життя DNS-запису

TTL (Time To Live) визначає, скільки секунд DNS-відповідь може зберігатися в кеші.

Наприклад:

    example.com. 300 IN A 192.0.2.10

У цьому умовному записі TTL дорівнює 300 секунд.

Це означає, що кеш може зберігати отриману відповідь до 300 секунд, якщо інші правила кешування не впливають на її використання.

### Чому TTL важливий

Після зміни DNS-запису нова адреса може стати доступною не відразу для всіх користувачів.

Причини:

- кешування попередньої відповіді;
- різні DNS-резолвери;
- різний час оновлення кешів;
- помилки в налаштуваннях DNS-зони.

Зміна запису в панелі керування доменом не означає, що кожен DNS-резолвер одразу почне повертати нове значення.

Перевірити TTL:

    dig example.com A

Значення TTL зазвичай видно в колонці перед класом `IN` у секції відповіді.

## 6. Як перевірити DNS у Linux

Для базової діагностики корисні такі команди:

| Команда | Для чого |
|---|---|
| `getent hosts` | Перевіряє пошук імені через системний механізм NSS |
| `host` | Простий DNS-пошук |
| `nslookup` | Перевірка DNS-запитів |
| `dig` | Детальна діагностика DNS |
| `resolvectl` | Перегляд стану та параметрів DNS через systemd-resolved |
| `ping` | Перевірка доступності вузла разом із розпізнаванням імені |

Не всі утиліти обов'язково встановлені в системі.

### 6.1. Перевірка через getent

Команда:

    getent hosts example.com

Показує результат пошуку імені через системний механізм NSS (Name Service Switch).

Це корисно, тому що звичайні Linux-застосунки часто використовують саме системний механізм розпізнавання імен, а не виконують DNS-запити самостійно.

Приклад результату:

    192.0.2.10 example.com

Це лише приклад формату. Реальна адреса залежить від домену та поточної DNS-відповіді.

Перевірка конкретної IP-адреси:

    getent hosts 192.0.2.10

### 6.2. Перевірка через host

Команда:

    host example.com

Пошук IPv4-адрес:

    host -t A example.com

Пошук IPv6-адрес:

    host -t AAAA example.com

Пошук MX:

    host -t MX example.com

Пошук NS:

    host -t NS example.com

### 6.3. Перевірка через nslookup

Команда:

    nslookup example.com

У результаті можна побачити DNS-сервер, який відповів на запит, і отриману адресу.

Пошук конкретного типу запису:

    nslookup -type=A example.com
    nslookup -type=AAAA example.com
    nslookup -type=MX example.com
    nslookup -type=NS example.com

`nslookup` корисний для базової діагностики, але для детального аналізу зазвичай зручніше використовувати `dig`.

### 6.4. Перевірка через dig

`dig` — одна з найкорисніших утиліт для роботи з DNS.

Базовий запит:

    dig example.com

Коротка відповідь:

    dig +short example.com

Запит A:

    dig example.com A

Запит AAAA:

    dig example.com AAAA

Запит MX:

    dig example.com MX

Запит NS:

    dig example.com NS

Запит TXT:

    dig example.com TXT

Запит SOA:

    dig example.com SOA

Зворотний пошук:

    dig -x 192.0.2.10

### 6.5. Як читати результат dig

Типовий результат `dig` містить декілька секцій:

- `HEADER` — інформація про DNS-повідомлення та статус відповіді;
- `QUESTION SECTION` — запит, який було виконано;
- `ANSWER SECTION` — знайдені DNS-записи;
- `AUTHORITY SECTION` — інформація про авторитетні сервери або зону;
- `ADDITIONAL SECTION` — додаткова інформація, якщо вона надана;
- `Query time` — час виконання запиту;
- `SERVER` — DNS-сервер, до якого було надіслано запит;
- `WHEN` — час виконання запиту;
- `MSG SIZE` — розмір DNS-повідомлення.

Особливо важливо перевіряти:

    status: NOERROR

`NOERROR` означає, що DNS-сервер не повідомив про помилку протоколу під час обробки запиту. Але це не гарантує, що потрібний запис існує.

Наприклад, домен може існувати, але не мати запису AAAA. У такому разі відповідь може мати статус `NOERROR`, проте не містити потрібного запису.

## 7. DNS-коди відповіді

Під час діагностики можна зустріти такі статуси:

| Статус | Значення |
|---|---|
| `NOERROR` | Запит оброблено без помилки протоколу |
| `NXDOMAIN` | Запитане доменне ім'я не існує |
| `SERVFAIL` | DNS-сервер не зміг успішно обробити запит |
| `REFUSED` | DNS-сервер відмовив у виконанні запиту |
| `NOERROR` без потрібного запису | Ім'я може існувати, але потрібного типу запису немає |

### 7.1. NXDOMAIN

Приклад:

    dig nonexistent-domain.example

Якщо сервер повертає `NXDOMAIN`, це означає, що запитане доменне ім'я не існує в межах DNS-відповіді.

Причини можуть бути такими:

- помилка в написанні домену;
- домен не зареєстрований;
- домен ще не налаштований;
- DNS-зміни або делегування виконані неправильно.

Для внутрішнього домену також варто перевірити, чи доступний потрібний корпоративний DNS-сервер.

### 7.2. SERVFAIL

`SERVFAIL` означає, що DNS-сервер не зміг успішно обробити запит.

Можливі причини:

- проблеми з авторитетними DNS-серверами;
- помилки DNSSEC;
- проблеми з DNS-резолвером;
- тимчасові мережеві збої;
- неправильна конфігурація DNS-зони.

### 7.3. REFUSED

`REFUSED` означає, що сервер відмовив у виконанні запиту.

Наприклад, DNS-сервер може дозволяти запити лише від клієнтів певної мережі або не дозволяти рекурсивний пошук.

## 8. Які DNS-сервери використовує Linux

Linux може отримувати DNS-налаштування від:

- DHCP-сервера роутера;
- NetworkManager;
- systemd-networkd;
- VPN-з'єднання;
- локального DNS-резолвера;
- ручної конфігурації.

Тому не завжди достатньо подивитися лише на один конфігураційний файл.

### 8.1. Перевірка через resolvectl

На системах із `systemd-resolved`:

    resolvectl status

Команда показує загальний стан DNS та параметри мережевих інтерфейсів.

Інформація може містити:

- DNS-сервери;
- DNS-домени;
- параметри окремих мережевих інтерфейсів;
- поточну DNS-конфігурацію системи.

Перевірка конкретного домену:

    resolvectl query example.com

Якщо команда `resolvectl` відсутня або сервіс `systemd-resolved` не використовується, ці приклади можуть бути недоступними.

### 8.2. Перевірка /etc/resolv.conf

Команда:

    cat /etc/resolv.conf

Приклад вмісту:

    nameserver 192.0.2.53
    search example.internal

`nameserver` вказує DNS-сервер, який має використовуватися системою через цей конфігураційний механізм.

`search` задає домени пошуку для деяких запитів з неповним ім'ям.

Важливо: `/etc/resolv.conf` може бути символічним посиланням або файлом, який автоматично генерується іншою службою.

Перевірити:

    ls -l /etc/resolv.conf

Не варто без потреби вручну редагувати цей файл, якщо DNS-конфігурацією керують NetworkManager або systemd-resolved.

### 8.3. Перевірка DNS-конфігурації через NetworkManager

Якщо використовується NetworkManager:

    nmcli device show

Для перегляду параметрів DNS:

    nmcli device show | grep -E 'IP[46]\.DNS|IP[46]\.DOMAIN'

Це допомагає побачити DNS-сервери та домени, які NetworkManager отримав або налаштував для пристроїв.

### 8.4. Перевірка /etc/nsswitch.conf

Команда:

    cat /etc/nsswitch.conf

Знайди рядок, який починається з:

    hosts:

Наприклад:

    hosts: files dns

Це означає, що система використовує локальні файли, зокрема `/etc/hosts`, а потім DNS для пошуку імен.

Реальний рядок може містити додаткові модулі та правила, наприклад `resolve`, `myhostname` або інші елементи.

Порядок і правила в цьому рядку впливають на те, як системні програми знаходять IP-адреси.

## 9. Файл /etc/hosts

`/etc/hosts` — локальний файл відповідності імен та IP-адрес.

Переглянути його:

    cat /etc/hosts

Приклад:

    127.0.0.1 localhost
    127.0.1.1 my-computer
    192.0.2.10 internal.example

Формат запису:

    IP-адреса доменне-ім'я [додаткові-імена]

### 9.1. Як /etc/hosts впливає на DNS

Якщо ім'я знайдено в `/etc/hosts` і системні правила використовують цей файл перед DNS, система може повернути локальну відповідність, не звертаючись до зовнішнього DNS для цього пошуку.

Перевірка:

    getent hosts localhost

Перевірка іншого імені:

    getent hosts internal.example

### 9.2. Коли використовують /etc/hosts

- локальна розробка;
- тимчасова перевірка доступності сервера;
- внутрішні середовища без налаштованого DNS;
- тестування домену перед оновленням публічного DNS.

### 9.3. Обережно з ручними змінами

Неправильний запис у `/etc/hosts` може спричинити ситуацію, коли одні програми звертаються до неправильної IP-адреси, навіть якщо публічний DNS налаштований правильно.

Якщо домен не відкривається, перевір не лише DNS, а й `/etc/hosts`.

## 10. Як виконати DNS-запит до конкретного сервера

За допомогою `dig` можна явно вказати DNS-сервер.

Наприклад:

    dig @1.1.1.1 example.com
    dig @8.8.8.8 example.com

Це приклади публічних DNS-резолверів Cloudflare та Google. Їхня доступність залежить від мережі, політик провайдера та інших умов.

Запит конкретного типу запису:

    dig @1.1.1.1 example.com A

Коротка відповідь:

    dig @1.1.1.1 +short example.com A

### Навіщо це потрібно

Припустимо, звичайний запит не працює:

    dig example.com

А запит до конкретного сервера працює:

    dig @1.1.1.1 example.com

Це може вказувати на проблему з DNS-сервером, який система використовує за замовчуванням, або з локальними DNS-налаштуваннями.

Однак потрібно враховувати, що запити до різних резолверів можуть повертати різні відповіді через кешування, географічне розташування, політики мережі або різний стан DNS-даних.

Якщо мережа блокує зовнішні DNS-запити, запит до публічного сервера може не спрацювати навіть за справного локального DNS.

## 11. Як перевірити DNS через TCP

Звичайні DNS-запити часто використовують UDP на порті 53, але DNS також може використовувати TCP.

Перевірка через TCP за допомогою `dig`:

    dig +tcp @1.1.1.1 example.com

TCP може використовуватися, зокрема, коли потрібна більша відповідь або для певних операцій між DNS-серверами.

Не слід вважати, що DNS завжди працює лише через UDP.

### Перевірка доступності DNS-порту

Якщо встановлено `nc`:

    nc -vz 1.1.1.1 53

Ця команда перевіряє TCP-підключення до порту 53, а не повноцінну DNS-відповідь.

Тому успішне TCP-підключення не доводить, що DNS працює правильно, а невдале TCP-підключення не доводить, що DNS через UDP недоступний.

Для перевірки DNS-запиту краще використовувати `dig`.

## 12. DNS-кеш у Linux

DNS-кеш зберігає результати попередніх запитів, щоб не виконувати повторний пошук щоразу.

Кеш може бути на різних рівнях:

- у браузері;
- у системному DNS-сервісі;
- у локальному мережевому резолвері;
- у DNS-резолвері провайдера;
- у публічному DNS-резолвері.

Не кожна Linux-система має локальний DNS-кеш.

### 12.1. Перевірка systemd-resolved

Перевір стан служби:

    systemctl status systemd-resolved

Якщо служба використовується, можна очистити її кеш:

    sudo resolvectl flush-caches

Після цього повтори запит:

    resolvectl query example.com

Або:

    getent hosts example.com

Очищення локального кешу не очищає кеші браузера, роутера, провайдера чи зовнішніх DNS-резолверів.

### 12.2. Якщо systemd-resolved не використовується

Не потрібно запускати команди очищення кешу навмання.

Спочатку визнач, який DNS-сервіс використовується у твоїй системі.

Наприклад:

    systemctl --type=service --state=running | grep -E 'resolved|dnsmasq|named|unbound'

Ця команда може допомогти знайти деякі поширені DNS-сервіси, але не є універсальним способом виявлення всіх можливих реалізацій.

## 13. Встановлення DNS-утиліт в Ubuntu

У мінімальній інсталяції Linux деякі команди можуть бути відсутні.

В Ubuntu утиліти `dig`, `host` і `nslookup` зазвичай входять до пакета `dnsutils` або пакета, який його замінив у конкретному випуску.

Спробуй:

    sudo apt update
    sudo apt install dnsutils

Якщо пакет має іншу назву або більше не доступний у твоєму випуску, перевір пошук:

    apt search bind9-dnsutils
    apt search dnsutils

Пакет `bind9-dnsutils` у сучасних випусках Ubuntu може надавати DNS-утиліти, зокрема `dig` і `nslookup`.

Перевір, які команди доступні:

    command -v dig
    command -v host
    command -v nslookup
    command -v getent
    command -v resolvectl

`getent` зазвичай доступний у стандартному середовищі Linux, оскільки входить до базових системних компонентів.

## 14. Практичні сценарії діагностики

### Сценарій 1. Сайт не відкривається за доменним ім'ям

Перевір системне розпізнавання імені:

    getent hosts example.com

Потім перевір DNS:

    dig example.com

Перевір доступність вузла:

    ping -c 4 example.com

Перевір HTTPS:

    curl -I --connect-timeout 5 https://example.com

Як інтерпретувати результати:

- `getent` не повертає адресу — можлива проблема системного розпізнавання імені;
- `dig` повертає помилку — перевір DNS-відповідь і DNS-сервер;
- DNS працює, але `curl` не підключається — можлива проблема маршрутизації, TCP, TLS, проксі або самого вебсервера;
- `ping` не працює, але `curl` працює — це можливо, оскільки ICMP може блокуватися.

Жодна окрема команда не визначає всі причини збою. Порівнюй результати кількох перевірок.

### Сценарій 2. Домен не розпізнається

Виконай:

    getent hosts example.com
    dig example.com
    dig @1.1.1.1 example.com
    cat /etc/resolv.conf
    cat /etc/hosts

Порівняй результати.

Якщо запит до конкретного DNS-сервера успішний, а системний пошук — ні, перевір локальну конфігурацію, DNS-сервіс і порядок пошуку імен.

Якщо обидва запити не працюють, це ще не доводить, що домен не існує: можливо, немає доступу до DNS або є інша проблема в мережі.

### Сценарій 3. DNS повертає неправильну адресу

Перевір відповідь різних DNS-резолверів:

    dig example.com A
    dig @1.1.1.1 example.com A
    dig @8.8.8.8 example.com A

Перевір локальні записи:

    grep -n 'example.com' /etc/hosts

Перевір TTL:

    dig example.com A

Можливі причини:

- старий кешований запис;
- неправильний запис у DNS-панелі;
- помилка в `/etc/hosts`;
- різні відповіді DNS-резолверів;
- незавершене оновлення DNS.

Не змінюй DNS-налаштування системи, доки не визначиш, на якому рівні виникає проблема.

### Сценарій 4. Домен працює в браузері, але не в терміналі

Перевір:

    getent hosts example.com
    dig example.com
    curl -I https://example.com

Можливі причини:

- браузер використовує власний DNS-over-HTTPS;
- браузер має власний кеш;
- термінал і браузер використовують різні проксі;
- застосунок має власні мережеві налаштування;
- системний DNS налаштований неправильно.

Пам'ятай: браузер може використовувати DNS-механізм, відмінний від системного.

### Сценарій 5. Домен працює на одному комп'ютері, але не на іншому

На обох комп'ютерах виконай:

    getent hosts example.com
    dig example.com
    cat /etc/resolv.conf

Якщо результати відрізняються, порівняй:

- DNS-сервери;
- VPN;
- підключення до мережі;
- локальні файли `/etc/hosts`;
- кеш DNS;
- мережеві правила.

Це допомагає локалізувати проблему без випадкової зміни системних налаштувань.

## 15. DNS у веброзробці: Node.js і NestJS

Під час розробки застосунків DNS важливий для HTTP-запитів до сторонніх API, підключення до баз даних і роботи із зовнішніми сервісами.

### 15.1. Перевірка DNS перед HTTP-запитом

Припустимо, Node.js-застосунок звертається до:

    https://api.example.com

Якщо домен не розпізнається, HTTP-запит може завершитися помилкою до встановлення з'єднання з вебсервером.

Спочатку перевір у терміналі:

    getent hosts api.example.com
    dig api.example.com
    curl -I --connect-timeout 5 https://api.example.com

Після цього перевір поведінку самого Node.js-застосунку.

### 15.2. Перевірка DNS через Node.js

Node.js має вбудований модуль `node:dns`.

Приклад:

    import dns from "node:dns/promises";

    try {
      const addresses = await dns.lookup("example.com");

      console.log(addresses);
    } catch (error) {
      console.error("DNS lookup failed:", error);
    }

`dns.lookup()` використовує системний механізм розпізнавання імен. Тому його результат зазвичай ближчий до того, що бачить звичайний застосунок Linux, ніж результат прямого DNS-запиту до конкретного сервера.

Приклад із `resolve4()`:

    import dns from "node:dns/promises";

    try {
      const addresses = await dns.resolve4("example.com");

      console.log(addresses);
    } catch (error) {
      console.error("DNS query failed:", error);
    }

`dns.resolve4()` виконує DNS-запит для IPv4-записів, тоді як `dns.lookup()` використовує системний механізм пошуку імен.

Це важлива відмінність під час діагностики.

### 15.3. Типові помилки Node.js

Приклад повідомлення:

    getaddrinfo ENOTFOUND api.example.com

Це зазвичай означає, що Node.js не зміг знайти адресу для вказаного імені.

Можливі причини:

- неправильний домен;
- помилка в конфігурації;
- відсутній DNS-запис;
- проблема з DNS-сервером;
- проблема з доступом до DNS;
- домен доступний лише у внутрішній мережі.

Інше повідомлення:

    connect ECONNREFUSED 192.0.2.10:3000

Це вже інша ситуація: адреса відома, але підключення до вказаного порту відхилено.

Можливо, сервер не запущений, не слухає цей порт або з'єднання блокується.

### 15.4. DNS і PostgreSQL

Підключення до PostgreSQL може використовувати ім'я хоста замість IP-адреси.

Наприклад, у конфігурації:

    DB_HOST=db.example.com
    DB_PORT=5432

Перевір розпізнавання імені:

    getent hosts db.example.com

Якщо адреса не знаходиться, проблема може виникати ще до спроби автентифікації PostgreSQL.

Якщо адреса знаходиться, але підключення не працює, перевір порт, маршрутизацію, правила доступу, стан сервера та параметри підключення.

## 16. DNS і приватність

DNS-запити можуть розкривати інформацію про домени, до яких звертається пристрій.

Залежно від конфігурації, запити можуть передаватися локальному резолверу, DNS-серверу провайдера або іншому сервісу.

Існують зашифровані способи передавання DNS-запитів, зокрема:

- DNS over TLS (DoT);
- DNS over HTTPS (DoH).

Вони захищають DNS-трафік на певній ділянці між клієнтом і резолвером, але самі по собі не гарантують повної анонімності.

Для базового адміністрування Linux достатньо розуміти, що різні програми можуть використовувати різні DNS-механізми, а налаштування браузера не завжди збігаються із системними.

## 17. Типові помилки початківців

### Помилка 1. Вважати, що DNS і доступність сервера — одне й те саме

DNS може успішно повернути IP-адресу, але сервер може бути вимкнений або недоступний.

### Помилка 2. Вважати, що ping перевіряє лише DNS

`ping example.com` спочатку потребує розпізнавання імені, а потім намагається надсилати ICMP-пакети.

Якщо `ping` не працює, причина може бути в DNS, мережі або блокуванні ICMP.

### Помилка 3. Дивитися лише на /etc/resolv.conf

Цей файл не завжди відображає всю логіку DNS, особливо коли система використовує systemd-resolved або NetworkManager.

### Помилка 4. Вважати, що DNS-запит завжди використовує UDP

DNS може використовувати UDP і TCP, а також зашифровані механізми, наприклад DoT або DoH.

### Помилка 5. Плутати NXDOMAIN і SERVFAIL

- `NXDOMAIN` — ім'я не існує згідно з отриманою відповіддю.
- `SERVFAIL` — сервер не зміг успішно обробити запит.

### Помилка 6. Одразу змінювати DNS-сервер

Спочатку перевір, чи проблема справді пов'язана з DNS. Без діагностики зміна серверів може приховати причину або порушити доступ до внутрішніх ресурсів.

### Помилка 7. Вважати, що очищення локального кешу оновить DNS всюди

Кеші можуть існувати на декількох рівнях. Очищення кешу комп'ютера не змінює записи авторитетної DNS-зони та не очищає кеші інших резолверів.

## 20. Шлях вивчення теми

### Core — обов'язково знати

- Розуміти призначення DNS.
- Знати різницю між доменом та IP-адресою.
- Перевіряти домени через `getent hosts` і `dig`.
- Знати призначення A, AAAA, CNAME, MX і NS.
- Переглядати `/etc/hosts` та `/etc/resolv.conf`.
- Розуміти різницю між DNS-помилкою та недоступністю сервера.

### Junior — впевнено використовувати

- Виконувати DNS-запити через `dig`.
- Перевіряти різні типи записів.
- Порівнювати відповіді різних DNS-резолверів.
- Розуміти TTL і кешування.
- Перевіряти DNS перед HTTP-запитом.
- Розрізняти `NXDOMAIN`, `SERVFAIL` і `REFUSED`.
- Діагностувати `getaddrinfo ENOTFOUND` у Node.js.

### Middle — розуміти глибше

- Аналізувати делегування DNS-зон.
- Досліджувати NS і SOA.
- Розуміти рекурсивні та авторитетні DNS-сервери.
- Аналізувати проблеми DNSSEC.
- Розуміти вплив VPN, split DNS та DNS-over-HTTPS.
- Досліджувати відмінності між системним пошуком і прямими DNS-запитами.

### Senior — поглиблена діагностика

- Проєктувати DNS-інфраструктуру.
- Аналізувати складні проблеми делегування й кешування.
- Налаштовувати авторитетні та рекурсивні DNS-сервери.
- Досліджувати продуктивність і відмовостійкість DNS.
- Аналізувати безпеку DNS та DNSSEC.

Для початку достатньо рівня Core і більшої частини Junior.

## 22. Що потрібно пам'ятати

- DNS перетворює доменні імена на мережеві адреси та надає інші дані про домени.
- DNS не гарантує, що сервер доступний або що застосунок працює.
- `getent hosts` перевіряє системний механізм пошуку імен.
- `dig` — основний інструмент для детальної діагностики DNS.
- A відповідає за IPv4, AAAA — за IPv6.
- MX використовується для поштових серверів, NS — для авторитетних DNS-серверів.
- TTL визначає час кешування DNS-відповіді.
- `/etc/hosts` може впливати на результат системного пошуку імен.
- `/etc/resolv.conf` не завжди є єдиним джерелом DNS-налаштувань.
- DNS може працювати через UDP або TCP; існують також зашифровані DNS-протоколи.
- `NXDOMAIN` і `SERVFAIL` означають різні проблеми.
- Під час діагностики порівнюй `getent`, `dig` і `curl`, а не покладайся на одну команду.
- У Node.js DNS-помилки можуть виникати ще до встановлення HTTP-з'єднання.
- Спочатку визнач причину проблеми, а потім змінюй налаштування.

**Головне правило:** спочатку перевір, чи система може знайти IP-адресу домену; потім перевір мережеве з'єднання та доступність сервісу. Це допомагає відокремити проблеми DNS від проблем TCP, TLS, HTTP і самого сервера.
