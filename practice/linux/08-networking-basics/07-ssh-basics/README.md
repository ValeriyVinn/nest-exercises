# SSH Basics

SSH (Secure Shell) — мережевий протокол, який дозволяє безпечно підключатися до віддалених комп'ютерів, виконувати команди, передавати файли та керувати серверами через зашифроване з'єднання.

Наприклад, ти можеш зі свого Ubuntu-ноутбука підключитися до віддаленого Linux-сервера, запустити команди, перевірити журнали, оновити застосунок або керувати сервером, на якому працює NestJS API.

SSH особливо важливий для веброзробника, який працює з Linux-серверами, GitHub, VPS, хостингом і розгортанням застосунків.

Мета цієї теми — навчитися підключатися до віддалених серверів, працювати з SSH-ключами, копіювати файли та безпечно налаштовувати SSH-доступ.

## 2. Що таке SSH

SSH розшифровується як Secure Shell.

Це протокол для безпечного віддаленого доступу до комп'ютерів через мережу.

За допомогою SSH можна:

- входити на віддалений Linux-сервер;
- виконувати команди в терміналі сервера;
- передавати файли;
- копіювати каталоги;
- запускати команди на віддаленому комп'ютері;
- створювати захищені тунелі;
- працювати з Git-репозиторіями через SSH;
- адмініструвати сервери та застосунки.

Наприклад, твій локальний комп'ютер — Ubuntu, а віддалений сервер — VPS з Ubuntu Server.

    Локальний комп'ютер
        |
        | SSH-з'єднання
        |
        v
    Віддалений Linux-сервер
        |
        +-- Node.js
        +-- NestJS API
        +-- PostgreSQL
        +-- журнали застосунку

SSH дозволяє керувати віддаленим сервером так, ніби ти працюєш у його терміналі.

### 2.1. Чому SSH безпечний

SSH забезпечує:

- шифрування переданих даних;
- перевірку ідентичності сервера;
- автентифікацію користувача;
- захист передавання команд і результатів від простого перехоплення.

SSH не означає, що будь-який сервер автоматично безпечний. Важливо перевіряти ключ сервера, використовувати надійні способи автентифікації та обмежувати доступ.

### 2.2. SSH і Telnet

Telnet також дозволяє віддалено працювати з терміналом, але не забезпечує такого самого стандартного захисту переданих даних.

SSH шифрує з'єднання, тому його використовують для адміністрування Linux-серверів.

## 3. Основні компоненти SSH

SSH складається з клієнтської та серверної частин.

### 3.1. SSH-клієнт

Клієнт запускається на комп'ютері, з якого ти підключаєшся.

Основна команда:

    ssh

Перевірка наявності:

    ssh -V

Приклад результату:

    OpenSSH_...

Точна версія залежить від встановленого пакета.

### 3.2. SSH-сервер

SSH-сервер приймає вхідні підключення.

У Linux зазвичай використовується OpenSSH Server.

Основна служба в Ubuntu:

    ssh

Перевірити її стан:

    systemctl status ssh

Якщо служба не знайдена, це може означати, що SSH-сервер не встановлений або використовує іншу конфігурацію.

### 3.3. Порт SSH

Стандартний TCP-порт SSH:

    22

З'єднання за замовчуванням виглядає так:

    ssh username@server-ip

Якщо сервер використовує інший порт:

    ssh -p 2222 username@server-ip

Порт 2222 у прикладі умовний. Фактичний порт визначається конфігурацією сервера.

## 4. Базове підключення через SSH

Загальний синтаксис:

    ssh username@hostname

Або:

    ssh username@ip-address

Наприклад:

    ssh developer@192.0.2.10

`developer` — ім'я користувача на віддаленому сервері.

`192.0.2.10` — умовна IP-адреса сервера з діапазону для документації.

Для реального підключення потрібно використовувати справжню адресу сервера.

### 4.1. Підключення до домену

SSH підтримує підключення не лише за IP-адресою, а й за доменним ім'ям:

    ssh developer@server.example.com

У цьому випадку система повинна знайти IP-адресу домену за допомогою DNS або іншого системного механізму розпізнавання імен.

Якщо домен не розпізнається, перевір:

    getent hosts server.example.com

### 4.2. Підключення з іншим портом

Якщо SSH-сервер слухає порт 2222:

    ssh -p 2222 developer@192.0.2.10

Параметр `-p` указує порт SSH-сервера.

Не плутай його з `-P` у деяких інших мережевих утилітах: у команди `ssh` використовується саме маленька літера `-p`.

### 4.3. Перше підключення до сервера

Під час першого підключення SSH може показати повідомлення про те, що ідентичність сервера ще не підтверджена.

Клієнт пропонує перевірити відбиток ключа сервера.

Важливо:

- отримати fingerprint сервера з надійного джерела;
- порівняти його з показаним значенням;
- підтверджувати підключення лише тоді, коли ти довіряєш серверу.

Після підтвердження ключ сервера зазвичай зберігається у файлі:

    ~/.ssh/known_hosts

Це дозволяє SSH виявляти ситуації, коли ключ сервера несподівано змінився.

Не слід автоматично погоджуватися з будь-яким новим ключем сервера.

## 5. Парольна автентифікація та SSH-ключі

SSH підтримує різні способи автентифікації.

Найпоширеніші:

- пароль користувача;
- автентифікація за SSH-ключем;
- інші методи, якщо вони налаштовані на сервері.

### 5.1. Парольна автентифікація

Під час підключення:

    ssh developer@192.0.2.10

Сервер може запросити пароль користувача.

Перевага — простота.

Недоліки:

- пароль потрібно вводити;
- слабкі паролі легше підібрати;
- автоматизація стає незручною;
- сервер може зазнавати атак на парольну автентифікацію.

Парольна автентифікація може бути вимкнена адміністратором сервера.

### 5.2. Автентифікація за SSH-ключем

SSH-ключі зазвичай складаються з двох частин:

- приватного ключа;
- публічного ключа.

Приватний ключ залишається на твоєму комп'ютері.

Публічний ключ можна додати до облікового запису на сервері.

Під час підключення SSH використовує криптографічну перевірку, щоб підтвердити, що клієнт має відповідний приватний ключ.

Схема:

    Локальний комп'ютер
        |
        +-- Приватний ключ
        |
        | SSH-з'єднання
        |
        v
    Віддалений сервер
        |
        +-- Публічний ключ у ~/.ssh/authorized_keys

**Приватний ключ ніколи не потрібно передавати на сервер або публікувати.**

## 6. Створення SSH-ключа

Для створення ключа використовують команду `ssh-keygen`.

Рекомендований для більшості сучасних сценаріїв варіант:

    ssh-keygen -t ed25519 -C "your_email@example.com"

Тут:

- `-t ed25519` — тип ключа;
- `-C` — коментар, який допомагає ідентифікувати ключ.

Під час виконання команда запропонує вибрати шлях збереження та, за бажанням, установити парольну фразу (passphrase).

Типовий шлях:

    ~/.ssh/id_ed25519

Публічний ключ:

    ~/.ssh/id_ed25519.pub

### 6.1. Приватний і публічний ключі

| Файл | Призначення |
|---|---|
| `id_ed25519` | Приватний ключ |
| `id_ed25519.pub` | Публічний ключ |

Назви можуть відрізнятися, якщо ти задав власний шлях або ім'я файлу.

Перевірити файли:

    ls -la ~/.ssh

### 6.2. Навіщо потрібна passphrase

Passphrase — парольна фраза, якою захищається приватний ключ.

Якщо хтось отримає файл приватного ключа, passphrase може ускладнити його використання.

Використання passphrase особливо корисне для ключів, які мають доступ до серверів або GitHub.

### 6.3. Чи потрібно створювати новий ключ для кожного сервера

Не обов'язково.

Один ключ може використовуватися для декількох серверів, якщо це дозволено політикою безпеки.

Однак окремі ключі для різних середовищ або сервісів можуть спростити керування доступом і відкликання ключів.

Наприклад:

    ~/.ssh/id_ed25519
    ~/.ssh/id_github
    ~/.ssh/id_server

Назви довільні. Для нестандартного імені ключа потрібно вказати відповідний шлях під час підключення або налаштувати `~/.ssh/config`.

---

## 7. Як переглянути публічний ключ

Вивести публічний ключ у термінал:

    cat ~/.ssh/id_ed25519.pub

Результат буде одним довгим рядком, який починається приблизно так:

    ssh-ed25519 AAAA... your_email@example.com

Це приклад формату, а не справжній ключ.

Копіювати потрібно весь рядок публічного ключа.

Не виводь і не передавай іншим вміст приватного ключа:

    ~/.ssh/id_ed25519

### 7.1. Як скопіювати ключ в Ubuntu

Якщо встановлено `xclip` і працює графічне середовище:

    xclip -selection clipboard < ~/.ssh/id_ed25519.pub

Альтернативно можна використати `wl-copy`, якщо доступний відповідний Wayland-сеанс:

    wl-copy < ~/.ssh/id_ed25519.pub

Якщо ці утиліти відсутні, можна вивести ключ через `cat` і скопіювати його вручну.

## 8. Додавання публічного ключа на сервер

Публічний ключ додається до файлу:

    ~/.ssh/authorized_keys

Цей файл розташований у домашньому каталозі користувача на віддаленому сервері.

### 8.1. Якщо доступний пароль і команда ssh-copy-id

Найпростіший спосіб:

    ssh-copy-id developer@192.0.2.10

Якщо використовується нестандартний порт:

    ssh-copy-id -p 2222 developer@192.0.2.10

Команда додає публічний ключ до віддаленого облікового запису.

Вона зазвичай попросить пройти поточну автентифікацію, наприклад ввести пароль.

Після цього можна перевірити підключення:

    ssh developer@192.0.2.10

### 8.2. Якщо ssh-copy-id відсутня

Перевір наявність команди:

    command -v ssh-copy-id

Якщо її немає, можна вручну додати вміст публічного ключа до `~/.ssh/authorized_keys` на сервері.

Для цього потрібен доступ до сервера через пароль, іншу SSH-сесію або консоль хостинг-провайдера.

### 8.3. Права доступу на сервері

Для SSH важливі права доступу до домашнього каталогу, каталогу `.ssh` і файлу `authorized_keys`.

Типова конфігурація:

    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/authorized_keys

Ці команди потрібно виконувати у відповідному обліковому записі на сервері.

Власник каталогу та файлу також має бути правильним.

Перевірити:

    ls -ld ~/.ssh
    ls -l ~/.ssh/authorized_keys

Якщо права або власник неправильні, SSH-сервер може відмовитися використовувати ключ.

## 9. SSH-ключі та ssh-agent

Якщо приватний ключ захищений passphrase, її не завжди зручно вводити під час кожного підключення.

`ssh-agent` — агент, який може зберігати розблокований ключ у межах відповідного сеансу.

### 9.1. Додати ключ до агента

Спочатку перевір, чи працює агент:

    ssh-add -l

Якщо агент доступний і ключів ще немає, можна додати ключ:

    ssh-add ~/.ssh/id_ed25519

Команда може запросити passphrase.

Після цього перевір список:

    ssh-add -l

### 9.2. Якщо агент не працює

У графічному середовищі Ubuntu агент часто запускається автоматично або інтегрується з сеансом користувача.

Якщо `ssh-add` повідомляє, що не може підключитися до агента, перевір середовище запуску SSH і налаштування сесії.

У звичайному Bash-сеансі можна запустити агент так:

    eval "$(ssh-agent -s)"

Потім додати ключ:

    ssh-add ~/.ssh/id_ed25519

Це створює або підключає агент для поточного термінального сеансу. Не потрібно без потреби запускати новий агент при кожному відкритті термінала, якщо система вже керує ним.

## 10. Файл ~/.ssh/config

Файл `~/.ssh/config` дозволяє зберігати параметри SSH-підключень.

Замість довгої команди:

    ssh -p 2222 -i ~/.ssh/id_server developer@192.0.2.10

можна створити короткий псевдонім.

### 10.1. Створення конфігурації

Відкрий файл:

    nano ~/.ssh/config

Приклад конфігурації:

    Host my-server
        HostName 192.0.2.10
        User developer
        Port 2222
        IdentityFile ~/.ssh/id_server
        IdentitiesOnly yes

Збережи файл.

Після цього підключайся коротко:

    ssh my-server

Параметри:

| Параметр | Значення |
|---|---|
| `Host` | Псевдонім, який ти вводиш у команді |
| `HostName` | Справжнє ім'я або IP-адреса сервера |
| `User` | Користувач на сервері |
| `Port` | Порт SSH-сервера |
| `IdentityFile` | Шлях до приватного ключа |
| `IdentitiesOnly yes` | Обмежує використання ключів тими, що явно задані для цього з'єднання |

### 10.2. Декілька серверів

Можна описати декілька підключень:

    Host dev-server
        HostName dev.example.com
        User developer
        IdentityFile ~/.ssh/id_ed25519

    Host prod-server
        HostName prod.example.com
        User deploy
        IdentityFile ~/.ssh/id_prod

Підключення:

    ssh dev-server
    ssh prod-server

У цьому прикладі назви доменів умовні.

### 10.3. Права доступу до конфігурації

Рекомендовано обмежити доступ до SSH-конфігурації:

    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/config

SSH може приймати конфігурацію з ширшими правами, ніж у деяких інших чутливих файлів, але обмеження доступу — хороша практика.

## 11. Передавання файлів через scp

`scp` копіює файли між локальним комп'ютером і віддаленим сервером через SSH.

Загальний синтаксис:

    scp SOURCE DESTINATION

### 11.1. Копіювання локального файлу на сервер

    scp ./notes.txt developer@192.0.2.10:/home/developer/

Файл `notes.txt` буде скопійовано до домашнього каталогу користувача на сервері.

### 11.2. Завантаження файлу із сервера

    scp developer@192.0.2.10:/home/developer/notes.txt ./

Файл буде скопійовано до поточного локального каталогу.

### 11.3. Копіювання каталогу

Для копіювання каталогу використовують параметр `-r`:

    scp -r ./my-project developer@192.0.2.10:/home/developer/

### 11.4. Копіювання через нестандартний порт

Для `scp` параметр порту має велику літеру `-P`:

    scp -P 2222 ./notes.txt developer@192.0.2.10:/home/developer/

Це відрізняється від команди `ssh`, де порт задається через маленьку `-p`.

### 11.5. Коли використовувати scp

`scp` зручний для простого копіювання файлів.

Для великих проєктів або регулярного синхронізування каталогів можуть бути зручнішими `rsync` через SSH або системи розгортання.

## 12. Передавання файлів через sftp

SFTP — протокол передавання файлів, який працює через SSH.

Відкрити SFTP-сеанс:

    sftp developer@192.0.2.10

Усередині сеансу можна використовувати команди:

    pwd
    ls
    cd /home/developer
    lpwd
    lls
    lcd ~/projects
    put notes.txt
    get notes.txt
    exit

Призначення:

| Команда | Дія |
|---|---|
| `pwd` | Поточний віддалений каталог |
| `ls` | Перегляд віддалених файлів |
| `cd` | Перехід у віддалений каталог |
| `lpwd` | Поточний локальний каталог |
| `lls` | Перегляд локальних файлів |
| `lcd` | Перехід у локальний каталог |
| `put` | Завантаження локального файлу на сервер |
| `get` | Копіювання файлу із сервера |
| `exit` | Завершення сеансу |

SFTP — не те саме, що FTP із додаванням шифрування. Це окремий протокол, який працює через SSH.

## 13. Виконання віддалених команд

SSH дозволяє виконувати команди без відкриття інтерактивної оболонки.

Загальний синтаксис:

    ssh USER@HOST COMMAND

Наприклад:

    ssh developer@192.0.2.10 "whoami"

Команда виконається на віддаленому сервері.

Інші приклади:

    ssh developer@192.0.2.10 "hostname"
    ssh developer@192.0.2.10 "uptime"
    ssh developer@192.0.2.10 "df -h"
    ssh developer@192.0.2.10 "free -h"

Перевірка стану служби:

    ssh developer@192.0.2.10 "systemctl status ssh"

Для перегляду деяких системних ресурсів або керування службами можуть знадобитися додаткові права.

### 13.1. Віддалена перевірка застосунку

Наприклад, на сервері працює Node.js API.

Перевірити процеси:

    ssh developer@192.0.2.10 "ps aux | grep node"

Перевірити порти:

    ssh developer@192.0.2.10 "ss -lntp"

Перевірити журнали systemd-служби:

    ssh developer@192.0.2.10 "journalctl -u my-api.service -n 50 --no-pager"

`my-api.service` — умовна назва служби. Заміни її на реальну назву свого сервісу.

### 13.2. Використання sudo

Якщо користувач має відповідні права, можна виконувати адміністративні команди:

    ssh developer@192.0.2.10 "sudo systemctl status nginx"

Не варто без потреби надавати звичайному користувачу необмежені адміністративні права.

## 14. SSH до GitHub

SSH можна використовувати для роботи з GitHub без введення облікових даних під час кожного Git-запиту.

Для цього публічний ключ додається до налаштувань GitHub, а приватний ключ залишається на локальному комп'ютері.

### 14.1. Перевірка наявних ключів

    ls -la ~/.ssh

Якщо ключа ще немає, створи його:

    ssh-keygen -t ed25519 -C "your_email@example.com"

Якщо ключ уже використовується для іншої важливої системи, не перезаписуй його випадково. Можна створити окремий ключ з іншим ім'ям.

### 14.2. Додавання ключа до GitHub

Виведи публічний ключ:

    cat ~/.ssh/id_ed25519.pub

Далі:

1. Увійди у свій обліковий запис GitHub.
2. Відкрий Settings.
3. Перейди до SSH and GPG keys.
4. Обери New SSH key.
5. Додай публічний ключ.
6. Збережи налаштування.

Не завантажуй на GitHub приватний ключ без розширення `.pub`.

### 14.3. Перевірка підключення

Виконай:

    ssh -T git@github.com

Під час першого підключення перевір відбиток ключа сервера GitHub за офіційною документацією GitHub.

Якщо автентифікація успішна, GitHub зазвичай повідомить, що автентифікацію пройдено, але інтерактивний shell не надається.

Це нормальна поведінка.

### 14.4. Клонування репозиторію через SSH

Приклад:

    git clone git@github.com:USERNAME/REPOSITORY.git

Заміни `USERNAME` та `REPOSITORY` на свої значення.

Перевірити адресу віддаленого репозиторію:

    git remote -v

SSH-адреса зазвичай починається з:

    git@github.com:

Якщо репозиторій налаштований на HTTPS, Git використовуватиме HTTPS незалежно від того, чи маєш ти SSH-ключ.

## 15. Встановлення SSH-сервера в Ubuntu

Для вхідних SSH-підключень на комп'ютері має працювати SSH-сервер.

В Ubuntu пакет зазвичай називається `openssh-server`.

Встановлення:

    sudo apt update
    sudo apt install openssh-server

Перевірка служби:

    systemctl status ssh

Якщо потрібно запустити службу:

    sudo systemctl start ssh

Щоб вона запускалася автоматично під час завантаження:

    sudo systemctl enable ssh

Можна виконати обидві дії однією командою:

    sudo systemctl enable --now ssh

### 15.1. Перевірка SSH-порту

Виконай:

    sudo ss -lntp | grep ':22'

Команда перевіряє, чи є TCP-сокет, який слухає порт 22.

Якщо нічого не виведено, це не обов'язково означає, що SSH не встановлений. Служба може бути зупинена, слухати інший порт або бути налаштована на конкретну адресу.

### 15.2. Перевірка локального підключення

На тому самому комп'ютері можна перевірити:

    ssh localhost

Або:

    ssh username@127.0.0.1

Використовуй справжнє ім'я локального користувача.

Це перевіряє локальне SSH-підключення, але не доводить, що сервер доступний з інших пристроїв мережі.

### 15.3. Перевірка брандмауера

Якщо використовується UFW:

    sudo ufw status

Дозволити SSH можна командою:

    sudo ufw allow OpenSSH

Або, якщо SSH слухає інший порт, потрібно створити правило для фактичного порту.

Перед зміною правил переконайся, що дозволено потрібний порт і що ти не заблокуєш собі доступ до віддаленого сервера.

## 16. Основні файли та каталоги SSH

SSH використовує кілька важливих файлів.

### 16.1. Каталог ~/.ssh

Команда:

    ls -la ~/.ssh

Містить особисті SSH-налаштування користувача.

Типові файли:

| Файл | Призначення |
|---|---|
| `id_ed25519` | Приватний ключ |
| `id_ed25519.pub` | Публічний ключ |
| `authorized_keys` | Публічні ключі, яким дозволено вхід до цього облікового запису |
| `known_hosts` | Відомі ключі серверів |
| `config` | Налаштування клієнтських підключень |

Не всі файли обов'язково існують на кожному комп'ютері.

### 16.2. known_hosts

Файл:

    ~/.ssh/known_hosts

Зберігає ключі серверів, з якими клієнт уже встановлював довіру.

Якщо ключ сервера несподівано змінюється, SSH може попередити про можливу загрозу або зміну сервера.

Причини зміни ключа можуть бути законними:

- сервер перевстановили;
- ключ сервера було замінено;
- IP-адреса тепер указує на інший сервер.

Але також можлива атака посередника (Man-in-the-Middle).

Тому не видаляй попередження без перевірки нового fingerprint.

### 16.3. authorized_keys

Файл на віддаленому сервері:

    ~/.ssh/authorized_keys

Містить публічні ключі, яким дозволено автентифікуватися в цьому обліковому записі.

Кожен ключ зазвичай розміщується в окремому рядку.

Видалення ключа з цього файлу може відкликати доступ, який надавався відповідним ключем.

Перед видаленням перевір, чи не використовується ключ іншими системами або процесами розгортання.

### 16.4. Конфігурація SSH-сервера

Основний конфігураційний файл OpenSSH Server в Ubuntu:

    /etc/ssh/sshd_config

Перегляд:

    sudo less /etc/ssh/sshd_config

Після зміни конфігурації перевір синтаксис:

    sudo sshd -t

Якщо перевірка завершується без повідомлень, це зазвичай означає, що синтаксичних помилок не виявлено.

Потім можна перезавантажити конфігурацію служби:

    sudo systemctl reload ssh

Перед змінами конфігурації віддаленого сервера бажано зберегти відкриту SSH-сесію, щоб мати можливість виправити помилки, якщо нові підключення перестануть працювати.

## 17. Основи безпеки SSH

SSH надає віддалений доступ до системи, тому його потрібно налаштовувати обережно.

### 17.1. Використовуй SSH-ключі

Ключова автентифікація зазвичай зручніша та безпечніша за використання лише пароля, особливо якщо приватний ключ захищений passphrase.

Однак ключі потрібно зберігати та керувати ними відповідально.

### 17.2. Не передавай приватний ключ

Не надсилай приватний ключ:

- у повідомленнях;
- у публічних репозиторіях;
- у файлах проєкту;
- у CI/CD-логах;
- іншим людям без належної процедури керування доступом.

Якщо приватний ключ випадково опубліковано, вважай його скомпрометованим: відклич відповідний доступ і створи новий ключ.

### 17.3. Перевіряй ключ сервера

Під час першого підключення перевіряй fingerprint сервера.

Не ігноруй попередження про зміну ключа без з'ясування причини.

### 17.4. Обмежуй доступ користувачів

Створюй окремі облікові записи для людей і сервісів, яким потрібен доступ.

Надавай лише ті права, які необхідні для виконання завдань.

### 17.5. Обережно змінюй порт SSH

Зміна стандартного порту може зменшити кількість автоматичних сканувань, але не замінює належної автентифікації та інших заходів безпеки.

Якщо змінюєш порт, потрібно синхронно перевірити:

- конфігурацію SSH-сервера;
- брандмауер;
- правила хмарного провайдера;
- параметри SSH-клієнта;
- конфігурацію моніторингу.

### 17.6. Вимкнення парольної автентифікації

На сервері можна налаштувати автентифікацію лише за ключами, якщо це відповідає політиці безпеки.

Але перед вимкненням паролів переконайся, що ключова автентифікація працює для всіх потрібних облікових записів.

Зміна параметрів на кшталт `PasswordAuthentication` може призвести до втрати доступу, якщо ключі налаштовано неправильно.

Не змінюй ці параметри на віддаленому сервері без перевіреного альтернативного способу доступу.

## 18. Діагностика проблем SSH

Якщо SSH не працює, не варто відразу змінювати конфігурацію сервера.

Потрібно визначити, на якому етапі виникає помилка.

### 18.1. Помилка: Connection refused

Приклад:

    ssh: connect to host 192.0.2.10 port 22: Connection refused

Можливі причини:

- SSH-сервер не запущений;
- порт не слухається;
- підключення спрямоване на неправильний порт;
- з'єднання активно відхиляється мережевим пристроєм.

На сервері перевір:

    systemctl status ssh
    sudo ss -lntp | grep ':22'

### 18.2. Помилка: Connection timed out

Приклад:

    ssh: connect to host 192.0.2.10 port 22: Connection timed out

Можливі причини:

- сервер недоступний через мережу;
- порт блокується брандмауером;
- неправильна IP-адреса;
- неправильний порт;
- немає маршруту до мережі;
- сервер не відповідає.

Перевір:

    ping -c 4 192.0.2.10

Потім, якщо встановлено `nc`:

    nc -vz 192.0.2.10 22

Важливо: невдалий `ping` не доводить, що SSH недоступний, оскільки ICMP може блокуватися.

### 18.3. Помилка: Permission denied (publickey)

Приклад:

    Permission denied (publickey).

Можливі причини:

- неправильний користувач;
- неправильний приватний ключ;
- публічний ключ не додано до `authorized_keys`;
- неправильні права доступу;
- сервер не дозволяє відповідний тип ключа;
- потрібний ключ не використовується клієнтом.

Спробуй указати ключ явно:

    ssh -i ~/.ssh/id_ed25519 developer@192.0.2.10

Для діагностики використовуй докладний режим:

    ssh -v developer@192.0.2.10

Якщо потрібно більше інформації:

    ssh -vvv developer@192.0.2.10

Докладний режим показує етапи підключення, спроби використання ключів та причини відмови.

Перед публікацією логів перевір, чи не містять вони приватної інформації про сервери, користувачів або інфраструктуру.

### 18.4. Помилка: Could not resolve hostname

Приклад:

    ssh: Could not resolve hostname server.example.com

Можливі причини:

- неправильне доменне ім'я;
- проблема DNS;
- неправильний запис у `~/.ssh/config`;
- помилка в псевдонімі підключення.

Перевір:

    getent hosts server.example.com
    dig server.example.com

Якщо ти використовуєш псевдонім з `~/.ssh/config`, перевір конфігурацію:

    ssh -G my-server

Команда `ssh -G` показує підсумкові параметри, які клієнт використовуватиме для відповідного псевдоніма.

### 18.5. Попередження про зміну ключа сервера

Приклад повідомлення:

    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

Не ігноруй це попередження автоматично.

Спочатку перевір fingerprint сервера через адміністратора або офіційний канал хостинг-провайдера.

Якщо зміну підтверджено, старий запис можна видалити командою:

    ssh-keygen -R server.example.com

Для нестандартного порту:

    ssh-keygen -R '[server.example.com]:2222'

Після цього підключайся знову й перевір новий fingerprint перед підтвердженням.

Ці команди видаляють відповідні записи з локального `known_hosts`; вони не змінюють ключ сервера.

### 18.6. Діагностика на сервері

Якщо маєш локальний або альтернативний адміністративний доступ до сервера, перевір:

    systemctl status ssh
    sudo journalctl -u ssh -n 100 --no-pager
    sudo ss -lntp

Журнали можуть показати причини відмови в автентифікації або проблеми служби.

## 19. SSH і розробка на Linux

Для веброзробника SSH особливо важливий у декількох сценаріях.

### 19.1. Доступ до віддаленого сервера

Наприклад, застосунок розгорнуто на VPS.

Підключення:

    ssh deploy@server.example.com

Після входу можна перевірити:

    hostname
    uptime
    df -h
    free -h
    ss -lntp

Це базові команди для перевірки стану сервера.

### 19.2. Розгортання NestJS

Припустимо, на сервері розгорнуто NestJS API.

За допомогою SSH можна:

- перевірити код і файли застосунку;
- переглянути журнали;
- перевірити змінні середовища через належний механізм конфігурації;
- перевірити процес Node.js;
- перезапустити сервіс, якщо маєш відповідні права.

Наприклад:

    ssh deploy@server.example.com "systemctl status my-api.service"

Для перегляду журналів:

    ssh deploy@server.example.com "journalctl -u my-api.service -n 100 --no-pager"

Не виводь секрети або паролі в журнали та не передавай їх у командному рядку без потреби.

### 19.3. Git і GitHub

SSH-ключі дозволяють використовувати GitHub через SSH.

Типовий робочий процес:

    git status
    git add .
    git commit -m "Add networking notes"
    git push

Якщо віддалений репозиторій налаштований на SSH і ключ додано до GitHub, `git push` може працювати без повторного введення облікових даних.

Перевір адресу репозиторію:

    git remote -v

### 19.4. Передавання файлів на сервер

Наприклад, можна скопіювати конфігураційний файл:

    scp ./config.json deploy@server.example.com:/home/deploy/

Перед передаванням переконайся, що файл не містить секретів, токенів або паролів.

Для регулярного розгортання застосунків краще використовувати контрольований процес деплою, а не вручну копіювати весь проєкт щоразу.

## 20. Практична робота

Запитання:

### Завдання 8. Перевір помилки SSH

Не потрібно навмисно змінювати робочу конфігурацію сервера.

Замість цього проаналізуй типові повідомлення:

    Connection refused
    Connection timed out
    Permission denied (publickey)
    Could not resolve hostname

Для кожного повідомлення визнач:

- на якому етапі виникає проблема;
- які команди варто виконати;
- які причини потрібно перевірити першими.

## 21. Коротка таблиця команд

| Команда | Призначення |
|---|---|
| `ssh -V` | Перевірити версію SSH-клієнта |
| `ssh user@host` | Підключитися до сервера |
| `ssh -p 2222 user@host` | Підключитися через нестандартний порт |
| `ssh -i KEY user@host` | Використати конкретний приватний ключ |
| `ssh -v user@host` | Докладний режим діагностики |
| `ssh -vvv user@host` | Максимально докладний режим клієнта |
| `ssh -G host` | Показати підсумкові параметри клієнта |
| `ssh-keygen -t ed25519` | Створити SSH-ключ |
| `ssh-keygen -R host` | Видалити відповідний запис із `known_hosts` |
| `ssh-copy-id user@host` | Додати публічний ключ на сервер |
| `ssh-add KEY` | Додати ключ до агента |
| `ssh-add -l` | Переглянути ключі агента |
| `scp FILE user@host:/path/` | Копіювати файл на сервер |
| `scp user@host:/path/file ./` | Копіювати файл із сервера |
| `sftp user@host` | Відкрити SFTP-сеанс |
| `ssh user@host "COMMAND"` | Виконати команду на сервері |

| `sudo ss -lntp` | Переглянути TCP-порти, які слухаються |

| `sudo sshd -t` | Перевірити синтаксис конфігурації сервера |

## 22. Шлях вивчення теми

### Core — обов'язково знати

- Розуміти, що таке SSH.
- Уміти підключатися до сервера.
- Знати призначення SSH-порту.
- Розуміти різницю між приватним і публічним ключами.
- Знати призначення `~/.ssh/known_hosts` і `authorized_keys`.
- Розуміти, чому не можна передавати приватний ключ.
- Уміти перевіряти базові помилки підключення.

### Junior — впевнено використовувати

- Створювати ключі через `ssh-keygen`.
- Додавати публічні ключі на сервер.
- Використовувати `ssh-agent` і `ssh-add`.
- Налаштовувати `~/.ssh/config`.
- Передавати файли через `scp` і `sftp`.
- Виконувати віддалені команди.
- Налаштовувати SSH-доступ до GitHub.
- Діагностувати проблеми з портами, ключами та DNS.
- Розуміти базові права доступу SSH-файлів.

### Middle — розуміти глибше

- Аналізувати докладні журнали SSH.
- Налаштовувати обмеження доступу.
- Керувати ключами для різних середовищ.
- Розуміти SSH-тунелі та port forwarding.
- Безпечно налаштовувати серверну автентифікацію.
- Працювати з SSH у сценаріях автоматичного розгортання.

### Senior — поглиблена діагностика

- Проєктувати безпечний віддалений доступ до інфраструктури.
- Налаштовувати централізоване керування SSH-доступом.
- Використовувати bastion hosts і jump hosts.
- Аналізувати складні проблеми маршрутизації та автентифікації.
- Налаштовувати обмеження для автоматизованих облікових записів.
- Проєктувати ротацію та відкликання ключів.

Для початку достатньо Core і більшої частини Junior.

## 24. Що потрібно пам'ятати

- SSH забезпечує зашифроване віддалене підключення.
- Стандартний TCP-порт SSH — 22, але сервер може використовувати інший.
- `ssh` — основна команда для підключення.
- `ssh-keygen` створює SSH-ключі.
- Приватний ключ залишається на клієнті, публічний можна додавати на сервер.
- `authorized_keys` визначає, які публічні ключі дозволено використовувати для входу до облікового запису.
- `known_hosts` зберігає відомі ключі серверів.
- `ssh-agent` допомагає працювати з розблокованими ключами.
- `~/.ssh/config` дозволяє зберігати параметри підключень.
- `scp` і `sftp` використовуються для передавання файлів.
- SSH можна використовувати для віддаленого виконання команд і роботи з GitHub.
- `Connection refused` часто вказує на проблему з портом або службою.
- `Connection timed out` часто вказує на проблему доступності мережі або фільтрації трафіку.
- `Permission denied (publickey)` указує на проблему автентифікації ключем або пов'язаної конфігурації.
- Перед зміною ключів сервера потрібно перевірити їхню справжність.
- Перед зміною `sshd_config` перевіряй синтаксис і зберігай альтернативний доступ.
- Не передавай приватні ключі, паролі або інші секрети в репозиторії.

**Головне правило:** SSH — це не просто команда для входу на сервер, а основний інструмент безпечного адміністрування Linux, передавання файлів і роботи з віддаленою інфраструктурою. Для веброзробника впевнене володіння SSH необхідне під час роботи з GitHub, VPS, Node.js, NestJS та розгортанням застосунків.
