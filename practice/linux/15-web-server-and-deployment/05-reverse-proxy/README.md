# 05. Reverse Proxy

## 📌 Що таке Reverse Proxy

**Reverse proxy (зворотний проксі)** — це сервер, який приймає запити від клієнтів і передає їх до одного або кількох внутрішніх серверів, а потім повертає клієнту отриману відповідь.

Клієнт взаємодіє з reverse proxy, а не безпосередньо з внутрішнім сервером застосунку.

Наприклад, користувач відкриває сайт `https://example.com`. Запит надходить до Nginx, а Nginx передає його Node.js-застосунку, який працює на `localhost:3000`.

    Browser → Nginx → Node.js application
    Browser ← Nginx ← Node.js application

Reverse proxy часто використовують для вебзастосунків, створених на Node.js, Express, NestJS, Django, Flask та інших серверних технологіях.

У нашому випадку це особливо важливо для розуміння того, як розгорнути NestJS-застосунок на Linux-сервері.

---

## ✔ Основні поняття

- **Proxy** — посередник, який передає запити між клієнтом і сервером.
- **Forward proxy** — проксі, який зазвичай працює на боці клієнта та допомагає клієнтам виходити до зовнішніх ресурсів.
- **Reverse proxy** — проксі, який стоїть перед серверами застосунків і приймає запити від клієнтів.
- **Nginx** — вебсервер, який також може працювати як reverse proxy.
- **Upstream server** — внутрішній сервер, якому reverse proxy передає запит.
- **Backend** — серверна частина застосунку, яка обробляє бізнес-логіку та дані.
- **Proxy pass** — директива Nginx `proxy_pass`, яка визначає адресу сервера, куди передавати запит.
- **Upstream** — група серверів, визначена в конфігурації Nginx.
- **HTTP headers** — заголовки HTTP-запиту та відповіді.
- **Port** — мережевий порт, через який програма приймає з'єднання.
- **Load balancing** — розподіл запитів між кількома серверами.
- **TLS/HTTPS termination** — завершення HTTPS-з'єднання на reverse proxy, після чого запит може передаватися внутрішньому серверу через HTTP або HTTPS.
- **Forwarded headers** — заголовки, які передають початкову інформацію про клієнта та зовнішнє з'єднання.

## 1. Навіщо потрібен Reverse Proxy

Припустимо, у нас є NestJS-застосунок, який запускається командою:

    npm run start:prod

Застосунок слухає порт `3000`.

Без reverse proxy користувач міг би звертатися безпосередньо до:

    http://203.0.113.10:3000

Це може працювати для тестування, але для публічного вебсервера зазвичай краще використовувати Nginx перед застосунком.

Після налаштування reverse proxy схема виглядає так:

    User
      |
      | HTTP/HTTPS
      v
    Nginx :80 або :443
      |
      | HTTP
      v
    NestJS :3000
      |
      v
    Database

Користувач звертається до домену, а Nginx передає запит застосунку.

### Основні переваги

**1. Єдина публічна точка входу**

Користувачам не потрібно знати внутрішній порт застосунку.

**2. Приховування внутрішньої архітектури**

Клієнт не повинен напряму звертатися до внутрішніх серверів.

**3. HTTPS**

Nginx може приймати HTTPS-з'єднання та передавати запити застосунку.

**4. Кілька застосунків на одному сервері**

Nginx може спрямовувати запити до різних застосунків залежно від домену або URL.

**5. Балансування навантаження**

Nginx може розподіляти запити між кількома екземплярами застосунку.

**6. Централізовані журнали**

Можна переглядати HTTP-запити та помилки на рівні Nginx.

**7. Контроль доступу та обмеження**

Nginx може застосовувати правила доступу, обмеження частоти запитів та інші засоби захисту.

---

## 2. Reverse Proxy та Forward Proxy

Ці два поняття схожі, але працюють з різних боків.

### Forward Proxy

Forward proxy зазвичай розташований між клієнтом та інтернетом.

    Client → Forward Proxy → Internet

Наприклад, організація може налаштувати проксі, через який працівники виходять до зовнішніх сайтів.

### Reverse Proxy

Reverse proxy розташований перед серверами.

    Client → Reverse Proxy → Application Server

Наприклад, Nginx приймає запит користувача та передає його NestJS-застосунку.

### Порівняння

| Ознака | Forward Proxy | Reverse Proxy |
|---|---|---|
| Розташування | Перед клієнтами | Перед серверами |
| Основний напрямок | Від клієнта до зовнішніх ресурсів | Від клієнта до внутрішніх серверів |
| Кого представляє | Клієнта | Сервер або сервіс |
| Типове застосування | Контроль вихідного доступу | Публікація вебзастосунків |
| Приклад | Корпоративний проксі | Nginx перед NestJS |

**Запам'ятай:** forward proxy працює переважно на боці клієнта, reverse proxy — на боці сервера.

## 3. Як працює Nginx Reverse Proxy

Розглянемо повний шлях HTTP-запиту.

    1. Користувач відкриває https://example.com/api/users
    2. DNS визначає IP-адресу сервера.
    3. Браузер встановлює з'єднання з Nginx.
    4. Nginx приймає HTTP-запит.
    5. Nginx вибирає відповідний server block і location.
    6. Nginx передає запит до NestJS на localhost:3000.
    7. NestJS обробляє запит.
    8. NestJS повертає HTTP-відповідь.
    9. Nginx передає відповідь браузеру.

Приклад:

    Browser
       |
       | GET /api/users
       v
    Nginx :443
       |
       | proxy_pass
       v
    NestJS :3000
       |
       | HTTP response
       v
    Nginx
       |
       v
    Browser

У цій схемі Nginx і NestJS — окремі процеси. Вони можуть працювати на одній машині або на різних серверах.

### Що важливо розуміти

- Nginx приймає зовнішні запити.
- NestJS виконує серверну логіку.
- Nginx не замінює NestJS.
- NestJS не обов'язково має бути доступним безпосередньо з інтернету.
- Nginx може передавати запити через HTTP до локального порту застосунку.
- Якщо застосунок не працює або недоступний, Nginx не зможе отримати від нього звичайну відповідь.

## 4. Встановлення Nginx в Ubuntu

Перевірити, чи встановлений Nginx:

    nginx -v

Якщо команда не знайдена, можна встановити Nginx через пакетний менеджер.

Оновити список пакетів:

    sudo apt update

Встановити Nginx:

    sudo apt install nginx

Перевірити версію:

    nginx -v

Перевірити стан служби:

    systemctl status nginx

Запустити Nginx:

    sudo systemctl start nginx

Автоматично запускати після перезавантаження системи:

    sudo systemctl enable nginx

Запустити зараз і ввімкнути автозапуск:

    sudo systemctl enable --now nginx

Перевірити конфігурацію:

    sudo nginx -t

Перезавантажити конфігурацію без повного перезапуску служби:

    sudo systemctl reload nginx

Перезапустити службу:

    sudo systemctl restart nginx

Зупинити Nginx:

    sudo systemctl stop nginx

**Важливо:** перед застосуванням змін у конфігурації виконуй `sudo nginx -t`. Якщо перевірка не пройшла, не перезавантажуй конфігурацію, доки не виправиш помилку.

## 5. Основні файли та директорії Nginx

В Ubuntu та Debian зазвичай використовують таку структуру:

    /etc/nginx/
    ├── nginx.conf
    ├── mime.types
    ├── sites-available/
    ├── sites-enabled/
    └── conf.d/

Інші важливі шляхи:

    /var/www/html/
    /var/log/nginx/
    /run/nginx.pid

### `/etc/nginx/nginx.conf`

Головний конфігураційний файл Nginx.

У ньому можуть визначатися:

- глобальні налаштування;
- кількість worker-процесів;
- журналювання;
- HTTP-контекст;
- підключення інших конфігураційних файлів.

Переглянути файл:

    sudo less /etc/nginx/nginx.conf

### `/etc/nginx/sites-available/`

Містить конфігурації сайтів, які доступні для підключення.

Наприклад:

    /etc/nginx/sites-available/example.com

Сам факт створення файлу тут не завжди означає, що сайт активний.

### `/etc/nginx/sites-enabled/`

Містить конфігурації сайтів, які Nginx підключає до активної конфігурації.

В Ubuntu та Debian це часто символічні посилання на файли в `sites-available`.

### `/etc/nginx/conf.d/`

Може містити додаткові конфігураційні файли, які підключаються головною конфігурацією через директиву `include`.

Конкретна організація конфігурації залежить від дистрибутива та встановленого пакета Nginx.

### `/var/log/nginx/access.log`

Журнал HTTP-запитів.

### `/var/log/nginx/error.log`

Журнал помилок Nginx.

### Перевірити активну конфігурацію

    sudo nginx -T

Команда показує повну конфігурацію, яку Nginx завантажує, включно з підключеними файлами.

Увага: вивід може містити внутрішні адреси та інші конфігураційні дані. Не публікуй його без перевірки.

## 6. Основні директиви Reverse Proxy

Конфігурація Nginx складається з директив.

Директива — це інструкція, яка задає поведінку сервера.

Наприклад:

    listen 80;
    server_name example.com;
    proxy_pass http://127.0.0.1:3000;

Зазвичай директива завершується крапкою з комою.

### `server`

Описує конфігурацію окремого віртуального сервера.

    server {
        listen 80;
        server_name example.com;
    }

### `listen`

Визначає адресу та порт, на яких сервер приймає з'єднання.

    listen 80;

Порт `80` зазвичай використовують для HTTP.

Для HTTPS зазвичай використовують порт `443`, але для нього потрібна відповідна TLS-конфігурація.

### `server_name`

Визначає доменні імена, для яких призначена конфігурація.

    server_name example.com www.example.com;

Домен має бути спрямований на потрібний сервер через DNS або інший механізм адресації.

### `location`

Визначає, як обробляти запити з певним URI.

    location /api/ {
        proxy_pass http://127.0.0.1:3000;
    }

У цьому прикладі запити, які відповідають `location /api/`, передаються внутрішньому серверу.

### `proxy_pass`

Визначає адресу upstream-сервера, куди Nginx передає запит.

    proxy_pass http://127.0.0.1:3000;

Тут:

- `http://` — протокол між Nginx і застосунком;
- `127.0.0.1` — адреса локального інтерфейсу;
- `3000` — порт застосунку.

### `proxy_set_header`

Встановлює або змінює заголовки, які передаються внутрішньому серверу.

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

Ці заголовки допомагають застосунку отримувати інформацію про початковий запит.

### `proxy_http_version`

Дозволяє явно вказати версію HTTP між Nginx та upstream-сервером.

    proxy_http_version 1.1;

Це часто зустрічається в конфігураціях, де потрібна підтримка WebSocket або специфічна поведінка з'єднань.

## 7. Найпростіший Reverse Proxy для Node.js

Припустимо, Node.js-застосунок працює на:

    http://127.0.0.1:3000

Спочатку переконайся, що застосунок запущений і приймає запити на цьому порту.

Перевірити локальний доступ:

    curl -I http://127.0.0.1:3000

Якщо застосунок підтримує відповідний маршрут, можна перевірити його окремо:

    curl http://127.0.0.1:3000/

Тепер створимо конфігурацію Nginx.

Відкрий новий файл:

    sudo nano /etc/nginx/sites-available/my-app

Додай конфігурацію:

    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://127.0.0.1:3000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

Заміни `example.com` на власний домен. Якщо домену ще немає, для локального тестування можна тимчасово використати `server_name _;`, але це не замінює налаштування DNS для публічного домену.

### Активувати конфігурацію

Створи символічне посилання:

    sudo ln -s /etc/nginx/sites-available/my-app /etc/nginx/sites-enabled/my-app

Якщо посилання вже існує, не створюй його повторно.

Перевір конфігурацію:

    sudo nginx -t

Якщо перевірка пройшла успішно, застосуй зміни:

    sudo systemctl reload nginx

Перевір HTTP-відповідь:

    curl -I http://127.0.0.1/

Якщо тестуєш на іншому сервері, звернися до його IP-адреси або домену.

**Важливо:** якщо на порту `80` вже працює інший `server` block, результат залежатиме від того, як Nginx вибирає віртуальний сервер. Не додавай конфігурацію навмання, не перевіривши наявні сайти.

## 8. Що відбувається з URL у `proxy_pass`

Один із найважливіших нюансів Nginx — поведінка URI в директиві `proxy_pass`.

Розглянемо два приклади.

### Варіант A. Без URI в `proxy_pass`

    location /api/ {
        proxy_pass http://127.0.0.1:3000;
    }

Запит:

    /api/users

Зазвичай upstream отримає:

    /api/users

Префікс `/api/` зберігається.

### Варіант B. З URI в `proxy_pass`

    location /api/ {
        proxy_pass http://127.0.0.1:3000/;
    }

Запит:

    /api/users

У типовому випадку Nginx замінить відповідний префікс `/api/` на `/`, і upstream отримає:

    /users

Різниця — у кінцевому `/` після порту.

### Коли це важливо

Припустимо, у NestJS є маршрут:

    GET /api/users

Якщо Nginx передає `/users`, маршрут може не знайтися.

І навпаки, якщо застосунок очікує `/users`, а Nginx передає `/api/users`, сервер може відповісти `404 Not Found`.

**Запам'ятай:** перевіряй, який саме URI доходить до backend. Не вважай, що `proxy_pass` завжди зберігає або завжди видаляє префікс.

Правила обробки URI залежать від форми `proxy_pass`, типу `location` та способу обробки URI. Для складніших конфігурацій звертайся до офіційної документації Nginx.

## 9. Reverse Proxy для NestJS

NestJS — це Node.js-фреймворк для створення серверних застосунків.

У production середовище зазвичай має три окремі частини:

    Internet
       |
       v
    Nginx :80 / :443
       |
       v
    NestJS :3000
       |
       v
    PostgreSQL

### Запуск NestJS

У проєкті NestJS встанови залежності:

    npm install

Збери застосунок:

    npm run build

Запусти production-версію:

    npm run start:prod

Команди залежать від скриптів, визначених у `package.json`.

Перевір, чи працює сервер:

    curl http://127.0.0.1:3000/

Якщо в застосунку налаштований глобальний префікс, наприклад `api`, перевір відповідний маршрут:

    curl http://127.0.0.1:3000/api

### Приклад конфігурації Nginx

    server {
        listen 80;
        server_name api.example.com;

        location / {
            proxy_pass http://127.0.0.1:3000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

Тут:

- Nginx приймає запити до `api.example.com`;
- запити передаються до NestJS на порт `3000`;
- NestJS обробляє запити та звертається до бази даних, якщо це потрібно;
- Nginx повертає отриману відповідь клієнту.

### Чому backend часто слухає localhost

Якщо NestJS і Nginx працюють на одній машині, можна налаштувати NestJS на прослуховування:

    127.0.0.1:3000

Тоді застосунок доступний через локальний інтерфейс, а не напряму через зовнішній мережевий інтерфейс.

Це зменшує кількість точок публічного доступу.

Однак у Docker або при розміщенні Nginx і NestJS на різних машинах адреса upstream буде іншою. Наприклад, у Docker Compose це може бути ім'я сервісу в мережі контейнерів.

## 10. Заголовки Proxy

Коли Nginx передає запит до застосунку, backend може бачити адресу Nginx замість початкової адреси клієнта.

Щоб передати додаткову інформацію, використовують заголовки.

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

### `Host`

    proxy_set_header Host $host;

Передає ім'я хоста, до якого звертався клієнт.

Це може бути важливо для багатодоменних застосунків і формування URL.

### `X-Real-IP`

    proxy_set_header X-Real-IP $remote_addr;

Передає адресу клієнта, яку бачить Nginx на поточному з'єднанні.

Якщо перед Nginx стоїть ще один проксі, ця адреса може бути адресою попереднього проксі, а не кінцевого клієнта.

### `X-Forwarded-For`

    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

Додає адресу клієнта до ланцюжка адрес у заголовку `X-Forwarded-For`.

Якщо запит проходить через кілька проксі, цей заголовок може містити кілька адрес.

Не довіряй усім адресам із цього заголовка без налаштування довірених проксі: клієнт може спробувати підробити значення, якщо інфраструктура не очищає та не перевіряє його належним чином.

### `X-Forwarded-Proto`

    proxy_set_header X-Forwarded-Proto $scheme;

Передає протокол, який використовувався між клієнтом і Nginx.

Наприклад, `http` або `https`.

Це важливо, якщо Nginx приймає HTTPS, а до Node.js підключається через HTTP.

### Чому це важливо для застосунку

Коректно налаштовані заголовки допомагають backend:

- визначати зовнішній домен;
- розуміти початковий протокол;
- коректніше формувати посилання;
- журналювати мережеві запити;
- застосовувати правила, пов'язані з адресою клієнта.

Але заголовки самі по собі не роблять дані достовірними. Довіра до них має відповідати реальній мережевій схемі.

---

## 11. Reverse Proxy та HTTPS

Зазвичай публічний вебзастосунок має використовувати HTTPS.

Типова схема:

    Browser -- HTTPS --> Nginx -- HTTP --> NestJS

У цій схемі:

- браузер встановлює захищене HTTPS-з'єднання з Nginx;
- Nginx завершує TLS-з'єднання;
- Nginx передає запит локальному NestJS через HTTP;
- NestJS повертає відповідь Nginx;
- Nginx надсилає відповідь браузеру через HTTPS.

HTTP між Nginx і backend може бути прийнятним, якщо цей канал обмежений довіреною мережею, наприклад локальним інтерфейсом на одній машині.

Якщо backend розташований на іншому сервері або трафік проходить через недовірену мережу, варто розглянути HTTPS і між цими серверами.

### Що потрібно для HTTPS

Зазвичай потрібно:

- доменне ім'я;
- правильні DNS-записи;
- доступність сервера ззовні;
- TLS-сертифікат;
- конфігурація Nginx для порту `443`;
- поновлення сертифіката до завершення його строку дії.

Для автоматизованого керування сертифікатами часто використовують Let's Encrypt та Certbot.

### Важливо для Node.js

Якщо зовнішнє з'єднання HTTPS, а внутрішнє — HTTP, застосунок має коректно враховувати `X-Forwarded-Proto`.

Не налаштовуй безумовну довіру до довільних proxy-заголовків. Параметри довіри до проксі мають відповідати твоїй інфраструктурі.

---

## 12. Reverse Proxy для кількох застосунків

Nginx може передавати запити різним застосункам.

Наприклад:

    app.example.com     → React / Next.js
    api.example.com     → NestJS
    admin.example.com   → Admin application

Кожен домен може мати окремий `server` block.

### Приклад: API на NestJS

    server {
        listen 80;
        server_name api.example.com;

        location / {
            proxy_pass http://127.0.0.1:3000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

### Приклад: інший застосунок

    server {
        listen 80;
        server_name admin.example.com;

        location / {
            proxy_pass http://127.0.0.1:4000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

У цьому прикладі:

- `api.example.com` передає запити на порт `3000`;
- `admin.example.com` передає запити на порт `4000`.

Обидва застосунки можуть працювати на одному сервері, але слухати різні локальні порти.

**Важливо:** домени мають бути налаштовані через DNS, а відповідні порти застосунків повинні бути доступними для Nginx.

---

## 13. Reverse Proxy та Load Balancing

Reverse proxy може передавати запити не лише одному backend, а й групі серверів.

Це називається **load balancing** — балансування навантаження.

Наприклад:

    Nginx
      |
      ├── NestJS instance 1 :3001
      ├── NestJS instance 2 :3002
      └── NestJS instance 3 :3003

Nginx може розподіляти запити між доступними екземплярами.

### Приклад `upstream`

    upstream nest_backend {
        server 127.0.0.1:3001;
        server 127.0.0.1:3002;
        server 127.0.0.1:3003;
    }

    server {
        listen 80;
        server_name api.example.com;

        location / {
            proxy_pass http://nest_backend;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

У цьому прикладі група `nest_backend` містить три upstream-сервери.

Nginx використовує алгоритм розподілу запитів, який визначається його конфігурацією та доступними можливостями.

### Коли це потрібно

- коли один екземпляр застосунку не справляється з навантаженням;
- коли потрібно розподілити запити між кількома процесами;
- коли архітектура передбачає горизонтальне масштабування.

### Чого не слід плутати

Наявність кількох серверів в `upstream` сама по собі не гарантує високу доступність усієї системи.

Потрібно враховувати:

- стан backend;
- спільність або узгодженість даних;
- сесії користувачів;
- поведінку під час помилок;
- обмеження ресурсів;
- механізми перевірки доступності та відновлення.

На початковому етапі достатньо навчитися передавати запити одному локальному застосунку.

## 14. WebSocket через Nginx

WebSocket дозволяє встановлювати двостороннє з'єднання між клієнтом і сервером.

Його можуть використовувати:

- чати;
- системи сповіщень;
- інтерактивні панелі;
- застосунки реального часу.

Для WebSocket-з'єднання через Nginx зазвичай потрібні спеціальні заголовки.

    location /socket/ {
        proxy_pass http://127.0.0.1:3000;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

Тут:

- `Upgrade` використовується для переходу від HTTP до WebSocket;
- `Connection` передає інформацію про оновлення з'єднання;
- `proxy_http_version 1.1` вказує HTTP/1.1 для з'єднання з upstream.

Це приклад базової конфігурації. Для production можуть знадобитися додаткові налаштування тайм-аутів, доступу та роботи з конкретною WebSocket-бібліотекою.

## 15. Reverse Proxy та межі безпеки

Reverse proxy допомагає контролювати доступ до застосунку, але не замінює повноцінну безпеку.

### Основні правила

**1. Не відкривай backend-порт без потреби**

Якщо Nginx і NestJS працюють на одній машині, застосунок часто можна прив'язати до `127.0.0.1`.

**2. Відкривай лише необхідні порти**

Зазвичай для публічного вебсервера потрібні `80/tcp` і `443/tcp`.

Порт `3000` не потрібно відкривати в інтернет, якщо він використовується лише локальним Nginx.

**3. Не довіряй довільним proxy-заголовкам**

`X-Forwarded-For` та подібні заголовки мають значення лише за правильної конфігурації довірених проксі.

**4. Не вважай Nginx заміною автентифікації**

Якщо застосунок має приватні маршрути, він усе одно повинен перевіряти права користувачів.

**5. Використовуй HTTPS для публічного трафіку**

Особливо коли передаються паролі, сесійні cookie або інші чутливі дані.

**6. Перевіряй конфігурацію перед застосуванням**

    sudo nginx -t

**7. Контролюй журнали**

    sudo tail -f /var/log/nginx/error.log

    sudo tail -f /var/log/nginx/access.log

## 16. Налаштування Firewall

Якщо використовується UFW, перевір його стан:

    sudo ufw status

Дозволити HTTP:

    sudo ufw allow 80/tcp

Дозволити HTTPS:

    sudo ufw allow 443/tcp

Перевірити правила:

    sudo ufw status numbered

**Увага:** якщо ти працюєш на віддаленому сервері через SSH, перед зміною firewall переконайся, що SSH-доступ дозволений. Інакше можна втратити віддалене підключення.

Не потрібно відкривати порт `3000` для всього інтернету, якщо Nginx передає запити до застосунку через локальний інтерфейс.

## 17. Діагностика Reverse Proxy

Коли сайт не працює, важливо перевіряти систему послідовно.

### Крок 1. Чи працює Nginx?

    systemctl status nginx

Переглянути журнали служби:

    sudo journalctl -u nginx -n 50 --no-pager

### Крок 2. Чи правильна конфігурація?

    sudo nginx -t

Якщо перевірка не проходить, прочитай повідомлення про помилку. Зазвичай воно вказує файл і рядок.

### Крок 3. Чи слухає Nginx потрібний порт?

    sudo ss -tulpn

Або перевірити HTTP-порт:

    sudo ss -tulpn | grep ':80'

Для HTTPS:

    sudo ss -tulpn | grep ':443'

### Крок 4. Чи працює backend без Nginx?

    curl -I http://127.0.0.1:3000

Якщо цей запит не працює, проблема може бути в Node.js-застосунку, його порту або адресі.

### Крок 5. Чи відповідає Nginx?

    curl -I http://127.0.0.1/

Для домену:

    curl -I http://example.com/

Для діагностики конкретної IP-адреси з потрібним HTTP Host можна використати:

    curl -I -H 'Host: example.com' http://127.0.0.1/

Це допомагає перевірити вибір віртуального сервера без необхідності змінювати DNS.

### Крок 6. Перевір журнали

    sudo tail -f /var/log/nginx/access.log

    sudo tail -f /var/log/nginx/error.log

### Крок 7. Перевір стан застосунку

Якщо backend працює як systemd-служба:

    sudo systemctl status my-app

Назва `my-app` тут умовна. Використовуй справжню назву своєї служби.

Якщо застосунок запущений іншим способом, перевір відповідний процес або журнал менеджера процесів.

## 18. Типові помилки Reverse Proxy

### Помилка 502 Bad Gateway

Nginx не зміг отримати коректну відповідь від upstream-сервера.

Можливі причини:

- NestJS не запущений;
- неправильний порт;
- неправильна адреса upstream;
- застосунок завершився з помилкою;
- Nginx не може встановити з'єднання з backend.

Що перевірити:

    curl -I http://127.0.0.1:3000

    sudo tail -n 50 /var/log/nginx/error.log

### Помилка 504 Gateway Timeout

Nginx не дочекався відповіді від upstream у межах відповідного тайм-ауту.

Можливі причини:

- backend довго обробляє запит;
- база даних не відповідає;
- є мережеві затримки;
- застосунок завис або перевантажений;
- тайм-аути налаштовані невідповідно до реального часу обробки.

Не збільшуй тайм-аути автоматично, не з'ясувавши причину затримки.

### Помилка 404 Not Found

Можливі причини:

- маршрут не існує в NestJS;
- Nginx передає неправильний URI;
- вибрано не той `server` block;
- застосунок використовує глобальний префікс, наприклад `/api`.

Перевір URL безпосередньо на backend та через Nginx.

### Помилка 403 Forbidden

Можливі причини:

- правила доступу Nginx;
- права доступу до файлів або директорій;
- обмеження на рівні застосунку.

Для reverse proxy перевір також журнали backend.

### Помилка `connect() failed (111: Connection refused)`

Зазвичай це означає, що з'єднання з upstream було відхилене.

Перевір:

    sudo ss -tulpn

    curl -I http://127.0.0.1:3000

Переконайся, що застосунок працює саме на адресі та порту, вказаних у `proxy_pass`.

### Помилка `host not found in upstream`

Можливі причини:

- неправильно написано ім'я хоста;
- DNS або локальне розв'язання імен не працює;
- сервісне ім'я недоступне в поточній мережі;
- конфігурація не відповідає середовищу запуску.

Якщо використовуєш Docker, перевір мережу контейнерів і назви сервісів.

## 19. Різниця між `root`, `alias` і `proxy_pass`

Ці директиви виконують різні завдання.

### `root`

Вказує директорію, з якої Nginx віддає статичні файли.

    location / {
        root /var/www/html;
        index index.html;
    }

Наприклад, запит `/about.html` може відповідати файлу:

    /var/www/html/about.html

### `alias`

Зіставляє певний `location` з іншою директорією або шляхом.

    location /images/ {
        alias /var/www/site-images/;
    }

Наприклад, запит `/images/logo.png` відповідає файлу:

    /var/www/site-images/logo.png

Поведінка `alias` відрізняється від `root`, тому кінцеві слеші та відповідність `location` потрібно налаштовувати уважно.

### `proxy_pass`

Передає запит іншому серверу.

    location / {
        proxy_pass http://127.0.0.1:3000;
    }

У цьому випадку Nginx не шукає відповідний HTML-файл у локальній директорії, а передає запит застосунку.

### Порівняння

| Директива | Призначення |
|---|---|
| `root` | Віддавати статичні файли з директорії |
| `alias` | Зіставляти `location` з указаним файловим шляхом |
| `proxy_pass` | Передавати запити іншому серверу |

**Запам'ятай:** `root` і `alias` працюють із файлами, а `proxy_pass` — із запитами до upstream-сервера.

## 20. Reverse Proxy та CORS

CORS — це механізм браузера, який обмежує доступ JavaScript-коду до ресурсів іншого origin.

Origin визначається схемою, доменом і портом.

Наприклад:

    http://localhost:3000
    http://localhost:4000

Це різні origin, оскільки порти відрізняються.

Якщо frontend і API доступні через один домен, наприклад:

    https://example.com/
    https://example.com/api/

то браузер зазвичай розглядає ці адреси як один origin, оскільки схема, хост і порт однакові.

Nginx може спрямовувати `/api/` до backend, а інші маршрути — до frontend. Така схема часто спрощує CORS-конфігурацію.

Однак reverse proxy не скасовує CORS автоматично для будь-якої архітектури.

Якщо frontend і API залишаються на різних origin, можуть бути потрібні відповідні CORS-заголовки та налаштування застосунку.

**Запам'ятай:** спочатку перевір, чи справді frontend і API мають різні origin. Не додавай `Access-Control-Allow-Origin: *` без розуміння вимог до доступу та облікових даних.

## 21. Практична робота: Nginx перед локальним Node.js

Мета — навчитися перевіряти роботу backend окремо та через Nginx.

### Крок 1. Перевір Nginx

    nginx -v

    systemctl status nginx

### Крок 2. Запусти тестовий backend

Для цієї вправи можна використати вже наявний Node.js-застосунок, який слухає порт `3000`.

Перевір його напряму:

    curl -I http://127.0.0.1:3000

Якщо маршрут `/` не існує, перевір відомий маршрут свого застосунку.

### Крок 3. Створи конфігурацію

    sudo nano /etc/nginx/sites-available/practice-proxy

Приклад:

    server {
        listen 80;
        server_name _;

        location / {
            proxy_pass http://127.0.0.1:3000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

Це навчальна конфігурація для локального тестування. Для публічного production-сайту потрібно налаштувати домен, HTTPS та відповідні правила доступу.

### Крок 4. Активуй конфігурацію

    sudo ln -s /etc/nginx/sites-available/practice-proxy /etc/nginx/sites-enabled/practice-proxy

Якщо файл або посилання вже існують, спочатку перевір їхній вміст.

### Крок 5. Перевір конфігурацію

    sudo nginx -t

### Крок 6. Застосуй зміни

    sudo systemctl reload nginx

### Крок 7. Перевір результат

    curl -I http://127.0.0.1/

Порівняй відповідь з прямим запитом до backend:

    curl -I http://127.0.0.1:3000

### Крок 8. Переглянь журнал

    sudo tail -n 20 /var/log/nginx/access.log

    sudo tail -n 20 /var/log/nginx/error.log

### Крок 9. Зроби висновок

Переконайся, що ти можеш пояснити:

- який процес приймає зовнішній HTTP-запит;
- який процес обробляє бізнес-логіку;
- на який порт Nginx передає запит;
- як перевірити backend без Nginx;
- як перевірити конфігурацію;
- де шукати причину помилки `502`.

## 22. Практична робота: маршрутизація за URL

Мета — зрозуміти, як передавати різні запити різним застосункам.

Припустимо:

    Frontend: 127.0.0.1:3000
    Backend:  127.0.0.1:4000

Приклад конфігурації:

    server {
        listen 80;
        server_name _;

        location /api/ {
            proxy_pass http://127.0.0.1:4000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        location / {
            proxy_pass http://127.0.0.1:3000;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

У цій конфігурації:

- `/api/users` відповідає `location /api/` і передається backend;
- `/` та інші запити відповідають `location /` і передаються frontend.

Зверни увагу: `proxy_pass` у `location /api/` не має URI після порту, тому префікс `/api/` у типовому випадку зберігається.

Якщо backend очікує маршрути без `/api/`, конфігурацію потрібно адаптувати.

## 23. Корисні команди

### Інформація про Nginx

    nginx -v

    nginx -V

`nginx -V` показує версію, параметри складання та частину параметрів конфігурації.

### Перевірка конфігурації

    sudo nginx -t

    sudo nginx -T

### Керування службою

    systemctl status nginx

    sudo systemctl start nginx

    sudo systemctl stop nginx

    sudo systemctl restart nginx

    sudo systemctl reload nginx

    sudo systemctl enable nginx

### Перевірка портів

    sudo ss -tulpn

    sudo ss -tulpn | grep ':3000'

### HTTP-запити

    curl -I http://127.0.0.1/

    curl -v http://127.0.0.1/

    curl -I http://127.0.0.1:3000/

Прапорець `-I` надсилає запит HEAD. Не всі застосунки підтримують HEAD однаково, тому для повнішої перевірки можна використати звичайний GET із `curl -v`.

### Журнали

    sudo tail -f /var/log/nginx/access.log

    sudo tail -f /var/log/nginx/error.log

    sudo journalctl -u nginx -n 50 --no-pager

    sudo journalctl -u nginx -f

### Перевірка доступності сервера

    curl -I http://example.com/

Для діагностики DNS:

    getent hosts example.com

Для перегляду правил UFW:

    sudo ufw status

## 24. Що потрібно запам'ятати

✔ Reverse proxy приймає запити від клієнтів і передає їх внутрішнім серверам.

✔ Nginx може одночасно працювати як вебсервер і reverse proxy.

✔ `proxy_pass` визначає адресу upstream-сервера.

✔ `server` описує віртуальний сервер, а `location` — правила обробки URI.

✔ `proxy_set_header` дозволяє передавати backend інформацію про початковий запит.

✔ `127.0.0.1` — локальний IPv4-інтерфейс. Він підходить для зв'язку між Nginx і застосунком на тій самій машині, якщо застосунок слухає цей інтерфейс.

✔ Порт `80` зазвичай використовують для HTTP, а `443` — для HTTPS.

✔ Якщо frontend та backend працюють на різних портах, reverse proxy може надати їм спільний публічний origin.

✔ Кінцевий слеш у `proxy_pass` може змінювати URI, який отримує backend.

✔ `502 Bad Gateway` часто означає проблему з підключенням до upstream.

✔ `504 Gateway Timeout` часто означає, що upstream не відповів у межах налаштованого часу.

✔ `404 Not Found` може бути наслідком неправильного маршруту або зміни URI.

✔ Перед застосуванням змін перевіряй конфігурацію командою `sudo nginx -t`.

✔ Після успішної перевірки можна застосувати зміни через `sudo systemctl reload nginx`.

✔ Якщо Nginx і backend працюють на одній машині, немає потреби відкривати порт backend для всього інтернету.

✔ Reverse proxy не замінює автентифікацію, авторизацію, безпечне налаштування TLS та захист самого застосунку.

## 25. Типові запитання на співбесіді

### Core

**1. Що таке reverse proxy?**

Це сервер-посередник, який приймає запити клієнтів і передає їх одному або кільком внутрішнім серверам.

**2. Чим reverse proxy відрізняється від forward proxy?**

Forward proxy зазвичай працює на боці клієнта, а reverse proxy — перед серверами застосунків.

**3. Для чого використовують Nginx перед Node.js?**

Для приймання HTTP/HTTPS-запитів, маршрутизації, централізованого журналювання та передачі запитів Node.js-застосунку.

**4. Що робить `proxy_pass`?**

Вказує адресу upstream-сервера, якому Nginx передає запит.

**5. Що робить `proxy_set_header`?**

Встановлює заголовки, які передаються upstream-серверу.

**6. Для чого потрібна команда `nginx -t`?**

Для перевірки синтаксису конфігурації та можливості її завантаження.

### Junior

**7. Як перевірити, чи працює backend без Nginx?**

Надіслати запит безпосередньо на адресу та порт backend, наприклад `curl -I http://127.0.0.1:3000`.

**8. Що означає `502 Bad Gateway`?**

Nginx не зміг отримати коректну відповідь від upstream. Треба перевірити доступність backend, адресу, порт і журнали.

**9. Чому Node.js-застосунок можна прив'язати до `127.0.0.1`?**

Щоб приймати з'єднання лише через локальний інтерфейс, якщо застосунок має бути доступний тільки Nginx на цій машині.

**10. Чому важливий заголовок `X-Forwarded-Proto`?**

Він повідомляє backend про початкову схему запиту, наприклад HTTPS, якщо Nginx передає запит до backend через HTTP.

**11. Чим відрізняються `root` і `proxy_pass`?**

`root` використовують для віддавання локальних файлів, а `proxy_pass` — для передавання запитів іншому серверу.

**12. Чому маршрут може повертати `404` через Nginx, хоча backend працює?**

Можливо, Nginx змінює URI або передає запит не тому застосунку.

### Middle

**13. Для чого використовують `upstream`?**

Для визначення групи серверів, до яких можна передавати запити, зокрема для балансування навантаження.

**14. Як Nginx допомагає обслуговувати кілька застосунків на одному сервері?**

Використовують різні `server` blocks із різними доменами або різні `location` для маршрутизації за URI.

**15. Чому не можна безумовно довіряти `X-Forwarded-For`?**

Тому що клієнт може підробити заголовок, якщо довірені проксі не визначені та заголовок не обробляється належним чином.

**16. Чим відрізняються `reload` і `restart`?**

`reload` застосовує нову конфігурацію без повного зупинення служби, якщо конфігурація коректна. `restart` зупиняє та запускає службу знову.

**17. Що потрібно враховувати під час використання WebSocket?**

Потрібно коректно передавати заголовки `Upgrade` і `Connection`, а також перевірити HTTP-версію та тайм-аути.

### Senior

**18. Як спроєктувати reverse proxy для кількох сервісів?**

Потрібно визначити точки входу, правила маршрутизації, мережеву доступність upstream-серверів, TLS, журналювання, довіру до forwarded-заголовків і поведінку під час відмов.

**19. Чому балансування навантаження не гарантує повну відмовостійкість?**

Тому що можуть залишатися спільні точки відмови: база даних, мережа, сховище, конфігурація, інфраструктура або сам reverse proxy.

**20. Як діагностувати повільні відповіді через Nginx?**

Порівняти прямі запити до backend із запитами через Nginx, перевірити журнали, час обробки запитів, доступність залежностей і відповідність тайм-аутів реальній поведінці системи.

## 28. Підсумок

Reverse proxy — важливий елемент розгортання вебзастосунків на Linux.

У типовій схемі:

    Browser → Nginx → NestJS → PostgreSQL

Nginx приймає HTTP/HTTPS-запити, обирає відповідну конфігурацію та передає запити NestJS. Застосунок обробляє бізнес-логіку й за потреби працює з базою даних, а Nginx повертає відповідь клієнту.

Для початкового рівня найважливіше навчитися:

1. Встановлювати та запускати Nginx.
2. Розуміти структуру конфігураційних файлів.
3. Налаштовувати `server`, `location` і `proxy_pass`.
4. Передавати запити до локального Node.js/NestJS.
5. Перевіряти конфігурацію та журнали.
6. Діагностувати типові помилки.
7. Розуміти роль HTTPS, портів і мережевих меж.

**Головна ідея:** Nginx приймає зовнішній запит і передає його потрібному застосунку. Reverse proxy дає змогу керувати доступом до backend, маршрутизацією та поведінкою вебінфраструктури в одному місці.
