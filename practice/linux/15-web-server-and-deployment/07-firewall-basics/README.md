# 07. Firewall Basics

## 📌 Що таке Firewall

**Firewall (мережевий екран)** — це механізм безпеки, який контролює мережевий трафік відповідно до визначених правил.

Firewall допомагає визначити:

- які мережеві підключення дозволені;
- які порти доступні ззовні;
- які програми можуть приймати мережеві з'єднання;
- які вхідні або вихідні з'єднання потрібно блокувати;
- з яких IP-адрес дозволено підключатися до сервера.

Наприклад, на Linux-сервері працюють:

- Nginx — порт `80` для HTTP;
- Nginx — порт `443` для HTTPS;
- NestJS — порт `3000`;
- PostgreSQL — порт `5432`.

Для публічного вебсервера зазвичай потрібно дозволити HTTP і HTTPS, а порт NestJS залишити доступним лише локально або для довірених систем. PostgreSQL також не повинен бути відкритим для всього інтернету без конкретної потреби.

    Internet
       |
       v
    Firewall
       |
       +---- Port 80  ----> Nginx (HTTP)
       |
       +---- Port 443 ----> Nginx (HTTPS)
       |
       +---- Port 3000 ---> NestJS (краще лише локально)
       |
       +---- Port 5432 ---> PostgreSQL (обмежений доступ)

**Головна ідея:** firewall дозволяє контролювати мережевий доступ, але не замінює автентифікацію, оновлення системи, правильні права доступу та безпечну конфігурацію застосунків.

---

## ✔ Основні поняття

- **Firewall** — мережевий екран для контролю мережевих з'єднань.
- **Packet** — мережевий пакет, який передається мережею.
- **Rule** — правило, що визначає, як обробляти певний трафік.
- **Inbound traffic** — вхідний трафік до сервера.
- **Outbound traffic** — вихідний трафік із сервера.
- **Port** — числовий ідентифікатор мережевої кінцевої точки.
- **Protocol** — протокол передавання даних, наприклад TCP або UDP.
- **IP address** — адреса мережевого інтерфейсу.
- **Allow** — дозволити з'єднання або трафік відповідно до правила.
- **Deny** — відхилити або заблокувати трафік відповідно до правил firewall.
- **Drop** — відкинути пакет без обов'язкової відповіді від firewall.
- **Default policy** — політика, яка застосовується, якщо жодне відповідне правило не визначає іншу дію.
- **UFW** — простий інструмент керування firewall, поширений в Ubuntu.
- **iptables** — інструмент керування правилами фільтрації пакетів у Linux.
- **nftables** — сучасна система фільтрації пакетів Linux.
- **Listening port** — порт, на якому процес очікує мережеві з'єднання.
- **Loopback** — локальний мережевий інтерфейс, зазвичай із адресою `127.0.0.1`.
- **SSH** — протокол віддаленого керування сервером, зазвичай через TCP-порт `22`.
- **Least privilege** — принцип мінімально необхідних привілеїв і доступу.
- **Network troubleshooting** — діагностика проблем мережевого підключення.

## 1. Як працює firewall

Firewall перевіряє мережевий трафік і застосовує до нього правила.

Наприклад, можна налаштувати такі правила:

    TCP port 22  -> дозволити SSH лише з довіреної IP-адреси
    TCP port 80  -> дозволити HTTP
    TCP port 443 -> дозволити HTTPS
    TCP port 3000 -> не відкривати для всього інтернету
    TCP port 5432 -> не відкривати для всього інтернету

Тоді зовнішні клієнти зможуть відкривати сайт через Nginx, але не повинні мати прямого доступу до NestJS або PostgreSQL.

### Вхідний трафік

**Inbound traffic** — це трафік, який надходить до сервера.

Приклади:

- користувач відкриває сайт;
- адміністратор підключається через SSH;
- інша машина намагається підключитися до PostgreSQL.

### Вихідний трафік

**Outbound traffic** — це трафік, який сервер відправляє назовні.

Приклади:

- сервер завантажує пакети;
- NestJS звертається до зовнішнього API;
- система надсилає запит до іншого сервера.

У деяких конфігураціях вихідний трафік дозволений за замовчуванням, але це не універсальне правило.

### Firewall не запускає серверні програми

Firewall не запускає Nginx, Node.js або PostgreSQL.

Якщо порт дозволений, але жоден процес його не слухає, з'єднання все одно не працюватиме.

Перевірити активні порти:

    sudo ss -tulpn

Наприклад, якщо Nginx слухає порт `80`, а firewall блокує вхідні TCP-з'єднання до цього порту, зовнішній клієнт може не отримати доступ до сайту.

**Запам'ятай:** для успішного мережевого підключення потрібно, щоб сервіс працював, слухав правильну адресу й порт, а firewall та інші мережеві правила не блокували з'єднання.

## 2. TCP, UDP та мережеві порти

Firewall часто використовує протокол, порт і адресу як критерії для правил.

### TCP

TCP забезпечує встановлення з'єднання та надійне передавання даних.

Приклади використання:

- HTTP;
- HTTPS;
- SSH;
- PostgreSQL;
- типові HTTP-з'єднання між Nginx і NestJS.

### UDP

UDP передає датаграми без встановлення TCP-з'єднання.

Приклади використання:

- DNS-запити в типовій конфігурації;
- DHCP;
- деякі VPN;
- окремі мережеві та потокові протоколи.

### Типові порти

| Порт | Протокол | Призначення |
|---|---|---|
| `22` | TCP | SSH |
| `53` | TCP/UDP | DNS |
| `80` | TCP | HTTP |
| `123` | UDP | NTP |
| `443` | TCP | HTTPS; UDP також використовується для HTTP/3 |
| `3000` | Залежить від застосунку | Часто Node.js або NestJS |
| `5432` | TCP | PostgreSQL |
| `3306` | TCP | MySQL |

Порти `3000` і `5432` — поширені значення, але програми можуть використовувати інші порти.

### Перевірити, які порти слухають

    sudo ss -tulpn

Пояснення параметрів:

- `-t` — TCP;
- `-u` — UDP;
- `-l` — порти, які перебувають у стані очікування з'єднань;
- `-p` — показати процеси, якщо є достатньо прав;
- `-n` — не перетворювати адреси й порти на символьні назви.

Перевірити TCP-порт `3000`:

    sudo ss -tlnp | grep ':3000'

Перевірити TCP-порт `5432`:

    sudo ss -tlnp | grep ':5432'

**Запам'ятай:** відкритий порт у firewall і порт, який слухає процес, — це дві різні речі.

## 3. UFW — Uncomplicated Firewall

**UFW** — інструмент для спрощеного керування правилами firewall у Linux.

Він поширений в Ubuntu та використовує механізми фільтрації пакетів ядра Linux.

UFW дозволяє задавати правила простими командами замість ручного керування складними наборами мережевих правил.

### Перевірити, чи встановлено UFW

    ufw version

Якщо команда недоступна, перевір, чи встановлено пакет.

В Ubuntu або Debian:

    sudo apt update
    sudo apt install ufw

Не встановлюй і не перемикай firewall на сервері навмання, якщо доступ до нього здійснюється віддалено. Спочатку перевір наявні правила та спосіб керування мережею.

### Перевірити стан UFW

    sudo ufw status

Можливий результат:

    Status: inactive

Це означає, що UFW наразі не активний. Це не обов'язково означає, що на машині взагалі немає інших мережевих правил.

### Переглянути стан із деталями

    sudo ufw status verbose

### Переглянути правила з номерами

    sudo ufw status numbered

Нумерація зручна, коли потрібно видалити конкретне правило.

### Важливе зауваження

На сервері можуть одночасно діяти:
- UFW;
- правила `nftables` або `iptables`;
- firewall у хмарного провайдера;
- мережеві правила маршрутизатора;
- правила Docker або іншої системи контейнеризації.

Тому `ufw status` не завжди показує повну картину всіх мережевих обмежень.

## 4. Увімкнення UFW без втрати SSH-доступу

Це один із найважливіших практичних моментів.

Якщо ти працюєш через SSH і ввімкнеш firewall без дозволу SSH-підключення, можеш втратити віддалений доступ до сервера.

### Крок 1. Перевір поточні правила

    sudo ufw status verbose

### Крок 2. Дозволь SSH

Для стандартного SSH-порту `22`:

    sudo ufw allow OpenSSH

Альтернативний варіант:

    sudo ufw allow 22/tcp

Якщо SSH працює на іншому порту, потрібно дозволити саме цей порт.

Перевір налаштування SSH:

    sudo sshd -T | grep '^port '

Ця команда може показувати налаштовані порти, але остаточний результат залежить від конфігурації SSH і способу запуску служби.

### Крок 3. Дозволь HTTP і HTTPS, якщо сервер обслуговує вебсайт

    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

Ці правила потрібні, якщо відповідні сервіси мають бути доступні ззовні.

### Крок 4. Увімкни UFW

    sudo ufw enable

Під час виконання команди UFW може попередити про можливе порушення наявних SSH-з'єднань.

Перед підтвердженням переконайся, що SSH дозволений і використовується правильний порт.

### Крок 5. Перевір правила

    sudo ufw status verbose

### Крок 6. Перевір доступ

Якщо це віддалений сервер, відкрий нове SSH-з'єднання з іншого термінала, перш ніж закривати поточну сесію.

### Безпечний принцип

Порядок має бути таким:

    1. Перевірити поточну конфігурацію.
    2. Дозволити фактичний SSH-порт.
    3. Додати потрібні правила вебсервера.
    4. Увімкнути UFW.
    5. Перевірити стан і доступність.
    6. Переконатися, що нове SSH-з'єднання працює.

**Запам'ятай:** перед активацією firewall на віддаленому сервері завжди подбай про збереження адміністративного доступу.

## 5. Політика за замовчуванням

Firewall може мати політики за замовчуванням для вхідного, вихідного та транзитного трафіку.

Для типового вебсервера можна розглянути таку політику:

- вхідний трафік — блокувати за замовчуванням;
- вихідний трафік — дозволяти за замовчуванням;
- транзитний трафік — налаштовувати відповідно до ролі машини.

Транзитний трафік — це трафік, який проходить через машину між іншими вузлами. Звичайний вебсервер зазвичай не повинен працювати як маршрутизатор.

### Встановити політики UFW

    sudo ufw default deny incoming
    sudo ufw default allow outgoing

Перша команда блокує вхідний трафік за замовчуванням, якщо його не дозволено окремими правилами.

Друга команда дозволяє вихідний трафік за замовчуванням.

### Перевірити результат

    sudo ufw status verbose

### Чому це корисно

Якщо вхідний трафік за замовчуванням заблокований, випадково запущений сервіс не обов'язково стане доступним з інтернету через цей firewall.

Проте це не замінює перевірку мережевих інтерфейсів, правил інших firewall і доступу на рівні самого застосунку.

### Важливо

Не змінюй політики на робочому сервері, не перевіривши:
- доступ до SSH;
- потрібні відкриті порти;
- вихідні з'єднання, необхідні застосункам;
- правила VPN, маршрутизації та контейнерів.

## 6. Дозволити або заблокувати порт

UFW дозволяє створювати правила для конкретних портів і протоколів.

### Дозволити HTTP

    sudo ufw allow 80/tcp

### Дозволити HTTPS

    sudo ufw allow 443/tcp

### Дозволити SSH

    sudo ufw allow 22/tcp

### Дозволити порт Node.js

    sudo ufw allow 3000/tcp

Остання команда відкриває порт для вхідних з'єднань відповідно до правил UFW. Не виконуй її автоматично для production-застосунку: якщо NestJS доступний лише через локальний Nginx, порт `3000` зазвичай не потрібно відкривати для всього інтернету.

### Заблокувати конкретний порт

    sudo ufw deny 3000/tcp

Правило заборони може конфліктувати з іншими правилами доступу або змінити очікувану поведінку. Перевір результат через `ufw status numbered`.

### Дозволити порт із конкретного джерела

    sudo ufw allow from 203.0.113.10 to any port 5432 proto tcp

Це демонстраційний приклад. Адреса `203.0.113.10` належить до діапазону, зарезервованого для документації, і не є реальною адресою сервера.

Команда показує принцип: дозволити TCP-підключення до порту `5432` лише з певної IP-адреси.

### Дозволити SSH лише з певної IP-адреси

    sudo ufw allow from 203.0.113.10 to any port 22 proto tcp

Використовуй цей підхід лише тоді, коли достеменно знаєш адресу, з якої підключатимешся. Якщо твоя зовнішня IP-адреса змінюється, можна випадково втратити доступ.

### Перевірити правила

    sudo ufw status numbered

**Запам'ятай:** відкривай лише ті порти, які дійсно потрібні, і за можливості обмежуй доступ за джерелом.

## 7. Дозволити доступ за назвою профілю

UFW підтримує профілі застосунків. Наприклад, пакет Nginx може надавати профілі для HTTP і HTTPS.

### Переглянути доступні профілі

    sudo ufw app list

### Переглянути інформацію про профіль

    sudo ufw app info 'Nginx Full'

Якщо профіль існує, він зазвичай охоплює HTTP і HTTPS.

### Дозволити HTTP

    sudo ufw allow 'Nginx HTTP'

### Дозволити HTTP і HTTPS

    sudo ufw allow 'Nginx Full'

### Переглянути результат

    sudo ufw status

Назви профілів залежать від установлених пакетів і їхньої конфігурації.

Якщо профіль відсутній, можна використовувати явні правила портів:

    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

**Запам'ятай:** профілі зручні, але завжди перевіряй, які саме порти вони дозволяють.

## 8. Видалення та зміна правил

Під час навчання або обслуговування сервера може знадобитися прибрати зайве правило.

### Переглянути правила з номерами

    sudo ufw status numbered

Наприклад, результат може виглядати так:

    [ 1] 22/tcp                     ALLOW IN    Anywhere
    [ 2] 80/tcp                     ALLOW IN    Anywhere
    [ 3] 3000/tcp                   ALLOW IN    Anywhere

Це лише приклад. У твоїй системі номери та правила будуть іншими.

### Видалити правило за номером

    sudo ufw delete 3

Перед виконанням перевір, що номер відповідає потрібному правилу. Після видалення нумерація може змінитися.

### Видалити правило за його описом

    sudo ufw delete allow 3000/tcp

### Перевірити результат

    sudo ufw status numbered

### Чому краще не видаляти правила навмання

Можна випадково видалити правило, яке забезпечує SSH-доступ або роботу сайту.

Перед видаленням:
1. переглянь усі правила;
2. визнач, для чого потрібне конкретне правило;
3. видали лише те, яке більше не потрібне;
4. повторно перевір доступність сервісів.

## 9. UFW та SSH

SSH потрібен для віддаленого адміністрування Linux-сервера.

Типовий порт — `22/tcp`, але його можна змінити.

### Перевірити стан SSH-служби

В Ubuntu служба зазвичай називається `ssh`:

    systemctl status ssh

На інших системах назва може бути `sshd`.

### Перевірити порт, який слухає SSH

    sudo ss -tlnp | grep ssh

Або переглянути всі TCP-порти, які слухають:

    sudo ss -tlnp

### Дозволити стандартний SSH-порт

    sudo ufw allow OpenSSH

Якщо профіль `OpenSSH` недоступний:

    sudo ufw allow 22/tcp

### Якщо SSH використовує інший порт

Наприклад, якщо SSH налаштований на TCP-порт `2222`:

    sudo ufw allow 2222/tcp

Використовуй фактичний порт своєї конфігурації, а не прикладове значення.

### Перевірити доступ

    sudo ufw status verbose

Після зміни правил перевір нове підключення з іншого термінала.

**Запам'ятай:** не вмикай суворі правила вхідного трафіку, доки не переконаєшся, що потрібний SSH-порт дозволений.

## 10. Firewall для Nginx, NestJS і PostgreSQL

Для навчального серверного проєкту важливо правильно розділити публічні та внутрішні сервіси.

Припустимо, архітектура така:

    Internet
       |
       v
    Nginx :80 / :443
       |
       v
    NestJS :3000
       |
       v
    PostgreSQL :5432

### Nginx

Nginx приймає зовнішні HTTP-запити.

Якщо сайт повинен бути доступний з інтернету, зазвичай дозволяють:

    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

### NestJS

Якщо Nginx і NestJS працюють на одному сервері, NestJS може слухати:

    127.0.0.1:3000

У такому разі Nginx може звертатися до NestJS через loopback-адресу.

Зазвичай не потрібно створювати публічне правило:

    sudo ufw allow 3000/tcp

Натомість потрібно переконатися, що NestJS не слухає публічний інтерфейс без потреби.

### PostgreSQL

Якщо PostgreSQL працює на тій самій машині, застосунок може підключатися до нього локально.

Зазвичай не потрібно відкривати порт `5432` для всього інтернету:

    sudo ufw allow 5432/tcp

Не додавай це правило без чіткої вимоги.

### Якщо база даних на окремому сервері

У такій архітектурі потрібно дозволити підключення до PostgreSQL лише від серверів, яким воно необхідне.

Наприклад:

    sudo ufw allow from 10.0.0.20 to any port 5432 proto tcp

Адреса `10.0.0.20` тут умовна. Використовуй реальну внутрішню IP-адресу застосунку.

Також перевір налаштування PostgreSQL, правила автентифікації та мережеві правила обох серверів.

### Приклад мінімального набору правил вебсервера

Для сервера, який обслуговує сайт і доступний через SSH:

    sudo ufw allow OpenSSH
    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp
    sudo ufw status verbose

Перш ніж активувати UFW, переконайся, що SSH дозволено. Також врахуй, що назва профілю `OpenSSH` має існувати в системі.

**Запам'ятай:** публічним зазвичай має бути вебсервер, а не кожен процес, який працює на машині.

## 11. Діагностика проблем із firewall

Якщо сайт або застосунок не працює, не варто одразу змінювати правила.

Потрібно визначити, де саме виникає проблема.

### Крок 1. Перевір стан firewall

    sudo ufw status verbose

Якщо UFW неактивний, причина може бути в іншому firewall, мережевій конфігурації або самому сервісі.

### Крок 2. Перевір, чи працює служба

Для Nginx:

    systemctl status nginx

Для PostgreSQL:

    systemctl status postgresql

Для власної служби:

    systemctl status my-app

Назви служб залежать від конфігурації.

### Крок 3. Перевір, чи слухає порт

    sudo ss -tulpn

Якщо потрібного порту немає у списку, firewall може бути ні до чого: сервіс може бути зупинений або налаштований на іншу адресу.

### Крок 4. Перевір локальне підключення

Для Nginx:

    curl -v http://127.0.0.1/

Для NestJS:

    curl -v http://127.0.0.1:3000/

Якщо локальний запит працює, а зовнішній — ні, потрібно дослідити firewall, мережевий інтерфейс, маршрутизацію, DNS та правила зовнішньої мережі.

### Крок 5. Перевір журнали

    sudo journalctl -u nginx -n 50 --no-pager

    sudo tail -n 50 /var/log/nginx/error.log

### Крок 6. Перевір зовнішні правила

У хмарному середовищі можуть діяти додаткові правила:
- security groups;
- network ACL;
- firewall провайдера;
- правила маршрутизатора.

Навіть якщо UFW дозволяє порт, зовнішній firewall може його блокувати.

### Крок 7. Перевір з іншої машини

Для HTTP:

    curl -v http://SERVER_IP/

Заміни `SERVER_IP` на IP-адресу сервера.

Для HTTPS:

    curl -v https://example.com/

Використовуй справжній домен і відповідну конфігурацію HTTPS.

### Важливо

Не діагностуй усі проблеми як помилки firewall. Причиною можуть бути:
- неправильний DNS;
- неправильний порт;
- непрацюючий процес;
- неправильна адреса прив'язки;
- проблеми маршрутизації;
- неправильні права;
- помилка застосунку.

## 12. Типові повідомлення про проблеми з мережею

### `Connection refused`

З'єднання було відхилене.

Можливі причини:
- на цій адресі та порту немає процесу, який приймає з'єднання;
- сервіс слухає іншу адресу;
- з'єднання активно відхиляється мережевим пристроєм або правилом.

Перевір:

    sudo ss -tulpn

    curl -v http://127.0.0.1:3000/

### `Connection timed out`

З'єднання не завершилося в межах очікуваного часу.

Можливі причини:
- firewall відкидає пакети;
- сервер недоступний;
- мережевий маршрут несправний;
- зовнішній firewall блокує трафік.

Перевір:

    ip route

    sudo ufw status verbose

    curl -v http://SERVER_IP/

### `No route to host`

Система не може знайти придатний мережевий шлях до призначення або отримує відповідну мережеву помилку.

Перевір:

    ip addr

    ip route

### Порт не слухає

Перевір:

    sudo ss -tulpn | grep ':3000'

Якщо результат порожній, перевір стан застосунку та його налаштування.

### Сайт відкривається локально, але не з інтернету

Перевір:
1. адресу, на якій слухає Nginx;
2. правила UFW;
3. правила зовнішнього firewall;
4. маршрутизатор або мережеві ACL;
5. публічну IP-адресу;
6. DNS-записи;
7. доступність порту з іншої мережі.

## 13. UFW, iptables і nftables

У Linux є кілька інструментів та механізмів роботи з firewall.

### UFW

Простий інструмент керування правилами.

Приклад:

    sudo ufw allow 80/tcp

Зручний для базового налаштування сервера Ubuntu.

### iptables

Інструмент для перегляду та керування правилами фільтрації пакетів.

Переглянути правила:

    sudo iptables -L -n -v

Переглянути правила з номерами:

    sudo iptables -L -n -v --line-numbers

Важливо: на системах із сучасним `iptables`, який працює через backend `nf_tables`, вивід `iptables` може відображати правила, реалізовані через nftables.

### nftables

Сучасна система фільтрації пакетів у Linux.

Переглянути наявні правила:

    sudo nft list ruleset

Ця команда показує правила nftables, доступні в системі.

### Чому не потрібно змішувати інструменти навмання

Якщо одночасно змінювати UFW, iptables і nftables без розуміння взаємодії між ними, можна:
- створити конфлікт правил;
- заблокувати потрібний трафік;
- ускладнити діагностику;
- отримати різну поведінку після перезавантаження.

Для початкового адміністрування Ubuntu краще навчитися керувати типовими правилами через UFW, а потім розібратися, як вони пов'язані з нижчими рівнями фільтрації пакетів.

**Запам'ятай:** UFW — це інтерфейс керування, а не окремий механізм фільтрації, незалежний від ядра Linux.

## 14. Firewall і Docker

Docker може змінювати мережеві правила, щоб забезпечити роботу контейнерів і перенаправлення портів.

Наприклад, контейнер може бути запущений із публічним відображенням порту:

    docker run -p 3000:3000 my-app

Це означає, що порт контейнера `3000` публікується через порт `3000` хоста. Фактична доступність залежить від адреси прив'язки, конфігурації Docker і мережевих правил.

### Перевірити опубліковані порти

    docker ps

### Важливе застереження

Не припускай, що звичайне правило UFW автоматично контролює всі шляхи доступу до опублікованих Docker-портів.

Docker може створювати правила фільтрації та перенаправлення, які впливають на обробку трафіку.

### Рекомендації

- не публікуй порти бази даних без потреби;
- використовуй внутрішні Docker-мережі для взаємодії сервісів;
- публікуй лише ті порти, які мають бути доступними через хост;
- перевіряй правила Docker і firewall разом;
- не покладайся лише на `ufw status`, щоб оцінити всі шляхи доступу до контейнерів.

### Приклад обмеження доступу до локального сервісу

Якщо потрібно опублікувати сервіс лише для локального доступу хоста, можна використовувати прив'язку до loopback:

    docker run -p 127.0.0.1:3000:3000 my-app

У такій конфігурації порт публікується на локальній адресі хоста, а не на всіх його IPv4-інтерфейсах.

Це не замінює правильну конфігурацію мережі та безпеки Docker.

**Запам'ятай:** якщо застосунок працює в контейнері, перевір не лише firewall, а й параметри публікації портів Docker.

## 15. Firewall у хмарному середовищі

На віддаленому сервері мережевий доступ може контролюватися на декількох рівнях.

Наприклад:

    Internet
       |
       v
    Cloud Firewall / Security Group
       |
       v
    Server Network
       |
       v
    Linux Firewall (UFW)
       |
       v
    Listening Service

Щоб з'єднання працювало, усі потрібні рівні мають дозволяти трафік.

### Приклад

Якщо UFW дозволяє порт `443`, але security group блокує його, сайт не буде доступний з інтернету.

Якщо зовнішній firewall дозволяє порт, але UFW блокує його, результат також може бути негативним.

Якщо обидва дозволяють порт, але Nginx не працює, з'єднання все одно не буде успішним.

### Що перевіряти

- правила хмарного firewall;
- security groups;
- мережеві ACL;
- публічну IP-адресу;
- маршрути;
- локальні правила UFW;
- порти, які слухають процеси;
- DNS;
- журнали служб.

**Запам'ятай:** доступність сервера визначається не одним правилом, а всім мережевим шляхом від клієнта до сервісу.

## 16. Принцип найменших привілеїв

**Principle of Least Privilege** — принцип, за яким кожному сервісу надають лише той доступ, який необхідний для його роботи.

Для мережевого firewall це означає:

- не відкривати всі порти без потреби;
- обмежувати адміністративний доступ;
- не публікувати базу даних без конкретної вимоги;
- не відкривати порт backend, якщо він доступний через Nginx;
- дозволяти доступ лише з потрібних мереж;
- регулярно переглядати старі правила.

### Поганий підхід

    sudo ufw allow 1:65535/tcp

Це дозволяє широкий діапазон TCP-портів і суттєво збільшує поверхню атаки.

### Кращий підхід

    sudo ufw allow OpenSSH
    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

Цей приклад підходить лише для сервера, якому потрібні SSH, HTTP та HTTPS. Він не є універсальною конфігурацією для всіх серверів.

### Для PostgreSQL

Не відкривай порт `5432` для всіх IP-адрес, якщо база даних не повинна бути публічно доступною.

Якщо потрібен віддалений доступ, обмеж його до необхідних IP-адрес або приватної мережі та налаштуй автентифікацію PostgreSQL.

### Для SSH

Якщо можливо, обмеж доступ довіреними IP-адресами, використовуй ключі SSH і вимкни непотрібні способи автентифікації відповідно до вимог сервера.

**Запам'ятай:** безпечний firewall не просто дозволяє потрібні з'єднання — він також обмежує непотрібні.

## 17. Практична робота: налаштувати UFW в Ubuntu

Мета — створити базову конфігурацію firewall для вебсервера.

Виконуй ці дії на навчальній машині або сервері, до якого маєш надійний доступ.

### Крок 1. Перевір систему

    cat /etc/os-release

### Крок 2. Перевір UFW

    sudo ufw status verbose

### Крок 3. Переглянь порти

    sudo ss -tulpn

### Крок 4. Перевір SSH

    systemctl status ssh

Якщо служба має іншу назву, перевір її у своїй системі.

### Крок 5. Дозволь SSH

    sudo ufw allow OpenSSH

Якщо профілю немає, а SSH працює на стандартному порту:

    sudo ufw allow 22/tcp

Якщо SSH використовує інший порт, дозволь фактичний порт.

### Крок 6. Дозволь HTTP та HTTPS

    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

Це потрібно, якщо сервер має приймати відповідний вебтрафік.

### Крок 7. Встанови політики за замовчуванням

    sudo ufw default deny incoming
    sudo ufw default allow outgoing

Не застосовуй ці зміни без перевірки спеціальних вимог до мережі, VPN, маршрутизації та віддаленого доступу.

### Крок 8. Увімкни UFW

    sudo ufw enable

Перевір попередження перед підтвердженням.

### Крок 9. Перевір результат

    sudo ufw status verbose

### Крок 10. Перевір сайт локально

    curl -I http://127.0.0.1/

Якщо HTTPS налаштований:

    curl -I https://example.com/

Заміни `example.com` на свій домен.

### Крок 11. Перевір доступ ззовні

З іншої машини перевір доступність сайту та SSH.

Не закривай поточну SSH-сесію, доки не переконаєшся, що нове підключення працює.

### Крок 12. Запиши результат

Зафіксуй:
- які правила додані;
- які порти доступні;
- які служби слухають ці порти;
- чи працює сайт;
- чи зберігається SSH-доступ.

## 18. Практична робота: обмежити доступ до PostgreSQL

Мета — не допустити непотрібного зовнішнього доступу до бази даних.

### Крок 1. Перевір порт PostgreSQL

    sudo ss -tlnp | grep ':5432'

### Крок 2. Перевір поточні правила

    sudo ufw status numbered

### Крок 3. Переконайся, що немає непотрібного правила

Якщо існує правило, яке відкриває `5432/tcp` для всіх, з'ясуй, чи справді воно необхідне.

### Крок 4. Видали зайве правило, якщо воно більше не потрібне

    sudo ufw delete allow 5432/tcp

Виконуй це лише після перевірки чинної конфігурації. Якщо правило було створене в іншій формі, команда може не відповідати потрібному запису.

### Крок 5. Перевір локальне підключення

    psql -h 127.0.0.1 -U taubu -d educational

Заміни користувача й назву бази на свої значення.

### Крок 6. Перевір налаштування PostgreSQL

Firewall не є єдиним механізмом контролю доступу. Також перевір:
- адресу, на якій слухає PostgreSQL;
- правила автентифікації;
- користувачів і права бази даних;
- необхідність віддалених з'єднань.

### Крок 7. Запиши висновок

Поясни, чому доступ до бази даних має бути обмежений і чому локальне підключення не вимагає публічного відкриття порту `5432`.

## 19. Практична робота: діагностика недоступного сайту

Припустимо, сайт не відкривається з іншої машини.

### Крок 1. Перевір Nginx

    systemctl status nginx

### Крок 2. Перевір порт

    sudo ss -tlnp | grep -E ':(80|443)\b'

### Крок 3. Перевір UFW

    sudo ufw status verbose

### Крок 4. Перевір HTTP локально

    curl -v http://127.0.0.1/

### Крок 5. Перевір HTTPS локально, якщо він налаштований

    curl -vk https://127.0.0.1/

Параметр `-k` вимикає перевірку сертифіката. Використовуй його лише як діагностичний інструмент, щоб відокремити проблему з'єднання від проблеми перевірки сертифіката. Він не повинен використовуватися як звичайний спосіб безпечного доступу.

### Крок 6. Перевір зовнішню адресу

    curl -v http://SERVER_IP/

Заміни `SERVER_IP` на адресу свого сервера.

### Крок 7. Перевір зовнішні правила

Якщо локально сайт працює, але ззовні ні, перевір firewall провайдера, маршрутизатор, DNS і мережеву конфігурацію.

### Крок 8. Визнач місце проблеми

    Nginx не працює
        -> перевір службу та журнали

    Nginx працює, порт не слухає
        -> перевір конфігурацію та адресу прив'язки

    Порт слухає, UFW блокує
        -> перевір і виправ правила

    UFW дозволяє, але сайт недоступний
        -> перевір зовнішній firewall, DNS, маршрутизацію

    Сайт доступний, але API повертає помилку
        -> перевір NestJS і його залежності

**Запам'ятай:** перевіряй мережевий шлях послідовно, а не змінюй усі правила одночасно.

## 20. Типові помилки початківців

### 1. Увімкнути UFW без дозволу SSH

Наслідок: можна втратити віддалений доступ.

Правильний підхід: спочатку дозволити фактичний SSH-порт, потім активувати firewall і перевірити нове з'єднання.

### 2. Відкрити всі порти

Наслідок: зайві сервіси стають доступнішими для атак.

Правильний підхід: дозволяти лише необхідні порти.

### 3. Вважати, що UFW — єдиний firewall

Наслідок: можна не помітити правила Docker, хмарного провайдера або nftables.

Правильний підхід: досліджувати всі рівні мережевого доступу.

### 4. Вважати, що дозволений порт означає працюючий сервіс

Наслідок: порт дозволений, але програма не запущена.

Правильний підхід: перевіряти і firewall, і стан процесу через `ss`.

### 5. Відкривати PostgreSQL для всього інтернету

Наслідок: база даних стає доступною з непотрібних джерел.

Правильний підхід: використовувати локальну або приватну мережу й обмежувати джерела підключень.

### 6. Використовувати `ufw disable` для діагностики на production

Наслідок: сервер може втратити важливий рівень мережевого захисту.

Правильний підхід: перевірити конкретне правило, журнал, порт і маршрут.

### 7. Не перевіряти правила після змін

Наслідок: помилкове правило може залишитися непоміченим.

Правильний підхід:

    sudo ufw status verbose

### 8. Змінювати правила відразу на кількох рівнях

Наслідок: важко визначити, яка зміна вплинула на результат.

Правильний підхід: змінювати одну річ за раз і перевіряти результат.

## 21. Корисні команди

### UFW

    sudo ufw status
    sudo ufw status verbose
    sudo ufw status numbered
    sudo ufw app list
    sudo ufw app info 'Nginx Full'

### Дозвіл доступу

    sudo ufw allow OpenSSH
    sudo ufw allow 22/tcp
    sudo ufw allow 80/tcp
    sudo ufw allow 443/tcp

### Дозвіл доступу з певної адреси

    sudo ufw allow from 203.0.113.10 to any port 5432 proto tcp

Адреса в цьому прикладі призначена для документації, а не для реального підключення.

### Видалення правил

    sudo ufw status numbered
    sudo ufw delete 3
    sudo ufw delete allow 3000/tcp

Перед видаленням перевір, що правило відповідає потрібному запису.

### Перевірка портів

    sudo ss -tulpn
    sudo ss -tlnp
    sudo ss -tlnp | grep ':80'

### Перевірка мережі

    ip addr
    ip route
    getent hosts example.com
    curl -v http://127.0.0.1/

### Перевірка служб

    systemctl status nginx
    systemctl status ssh
    sudo journalctl -u nginx -n 50 --no-pager

### Інші інструменти

    sudo iptables -L -n -v
    sudo nft list ruleset

## 22. Що потрібно запам'ятати

✔ Firewall контролює мережевий трафік відповідно до правил.

✔ Вхідний трафік надходить до сервера, а вихідний — відправляється сервером.

✔ TCP і UDP — різні транспортні протоколи.

✔ UFW — простий інструмент керування firewall, поширений в Ubuntu.

✔ `sudo ufw status verbose` показує стан і основні політики UFW.

✔ Перед активацією firewall на віддаленому сервері потрібно дозволити фактичний SSH-порт.

✔ `sudo ufw allow 80/tcp` дозволяє вхідний TCP-трафік до порту `80` відповідно до правил UFW.

✔ `sudo ufw allow 443/tcp` дозволяє вхідний TCP-трафік до порту `443`.

✔ Дозволений порт не гарантує, що сервіс працює.

✔ `sudo ss -tulpn` допомагає побачити порти, які слухають процеси.

✔ `Connection refused` і `Connection timed out` можуть мати різні причини.

✔ Для типового вебсервера зазвичай відкривають лише потрібні порти SSH, HTTP і HTTPS.

✔ Порт NestJS не потрібно відкривати для інтернету, якщо він доступний лише через локальний Nginx.

✔ PostgreSQL не слід відкривати для всіх адрес без конкретної потреби.

✔ UFW не обов'язково показує всі мережеві правила, які діють у системі.

✔ Docker і хмарні firewall можуть додатково впливати на мережевий доступ.

✔ Не варто вимикати firewall лише для того, щоб перевірити, чи він спричиняє проблему.

✔ Після зміни правил потрібно перевіряти їхній стан і фактичну доступність сервісів.

✔ Найкраща базова стратегія — дозволяти лише необхідний трафік.

## 23. Типові запитання на співбесіді

### Core

**1. Що таке firewall?**

Це механізм контролю мережевого трафіку, який застосовує правила дозволу або блокування з'єднань.

**2. Що таке UFW?**

Це інструмент спрощеного керування firewall у Linux, який часто використовують в Ubuntu.

**3. Що таке inbound traffic?**

Це трафік, який надходить до сервера.

**4. Що таке порт?**

Це числовий ідентифікатор мережевої кінцевої точки, через яку програма може приймати або обмінюватися даними.

**5. Для чого потрібен порт 443?**

Він зазвичай використовується для HTTPS через TCP. HTTP/3 використовує QUIC поверх UDP, зазвичай також із номером порту `443`.

### Junior

**6. Як перевірити стан UFW?**

Використати `sudo ufw status verbose`.

**7. Як дозволити HTTP?**

Використати `sudo ufw allow 80/tcp`.

**8. Як дозволити HTTPS?**

Використати `sudo ufw allow 443/tcp`.

**9. Чому потрібно дозволити SSH перед активацією firewall?**

Щоб не заблокувати віддалений адміністративний доступ до сервера.

**10. Як перевірити, чи слухає порт 3000?**

Використати `sudo ss -tlnp | grep ':3000'`.

**11. Чи означає відкритий порт, що застосунок працює?**

Ні. Firewall і процес, який слухає порт, — різні компоненти.

### Middle

**12. Чому сайт не відкривається, хоча UFW дозволяє порт 80?**

Можливі причини: Nginx не працює, слухає іншу адресу, порт блокується зовнішнім firewall або є проблеми DNS чи маршрутизації.

**13. Чому не варто відкривати порт PostgreSQL для всього інтернету?**

Це збільшує поверхню атаки та наражає базу даних на непотрібні спроби підключення.

**14. Чим відрізняються `Connection refused` і `Connection timed out`?**

Перша помилка зазвичай означає відхилення з'єднання, а друга — відсутність відповіді в межах очікуваного часу. Причини потрібно перевіряти за конкретним мережевим шляхом.

**15. Чому UFW може не показувати всі правила, які впливають на Docker?**

Docker може створювати власні правила перенаправлення та фільтрації пакетів.

### Senior

**16. Як організувати firewall для production-сервера?**

Потрібно визначити необхідні порти, обмежити джерела доступу, зберегти адміністративний доступ, перевірити зовнішні мережеві правила та документувати зміни.

**17. Як діагностувати недоступність сервісу з інтернету?**

Перевірити процес, порт, локальний запит, локальний firewall, зовнішні правила, IP-адресу, DNS і маршрутизацію.

**18. Чому важливо розділяти вебсервер і backend?**

Nginx може приймати зовнішній трафік, тоді як backend залишається доступним лише локально або через приватну мережу.

**19. Що означає принцип найменших привілеїв у firewall?**

Дозволяти лише ті мережеві підключення, які необхідні для роботи системи.

## 26. Підсумок

Firewall — один із базових механізмів безпеки Linux-сервера. Він контролює мережевий доступ і допомагає обмежити кількість сервісів, доступних із зовнішніх мереж.

Для повсякденної роботи важливо вміти:

1. Перевіряти стан firewall через `ufw status`.
2. Дозволяти лише необхідні порти.
3. Зберігати SSH-доступ під час зміни правил.
4. Перевіряти, які процеси слухають мережеві порти.
5. Розділяти публічний доступ до Nginx і внутрішній доступ до NestJS та PostgreSQL.
6. Діагностувати проблеми послідовно — від процесу до мережі.
7. Враховувати Docker, зовнішні firewall та правила хмарного провайдера.

**Головна ідея:** відкривай лише необхідні порти, обмежуй доступ настільки, наскільки це практично можливо, і перевіряй фактичну мережеву доступність після кожної важливої зміни.
