# 06. Logs and Troubleshooting

## 📌 Що таке Logs and Troubleshooting

**Logs (журнали)** — це записи про події, які відбуваються в операційній системі, службах, вебсервері та застосунках.

**Troubleshooting (діагностика та усунення несправностей)** — це послідовний процес пошуку причини проблеми, перевірки гіпотез і виправлення помилки.

У Linux журнали допомагають зрозуміти:

- чому не запускається служба;
- чому сервер повертає помилку;
- чому Nginx не може підключитися до Node.js;
- чому застосунок не може підключитися до PostgreSQL;
- чи виникають проблеми з диском, пам'яттю або мережею;
- що відбувалося на сервері перед збоєм.

Наприклад, якщо NestJS-застосунок перестав відповідати, не варто відразу перезапускати всі служби. Спочатку потрібно перевірити його стан, журнали, доступність порту та залежності.

    User
      |
      v
    Nginx
      |
      v
    NestJS
      |
      v
    PostgreSQL

Якщо користувач отримує помилку, причина може бути на будь-якому з цих рівнів.

---

## ✔ Основні поняття

- **Log** — запис про подію.
- **Log file** — файл, у якому зберігаються журнальні записи.
- **System log** — журнал подій операційної системи.
- **Application log** — журнал подій застосунку.
- **Error log** — журнал помилок.
- **Access log** — журнал HTTP-запитів до вебсервера.
- **systemd** — система керування службами та їхнім життєвим циклом у багатьох сучасних дистрибутивах Linux.
- **journalctl** — команда для перегляду журналів systemd-journald.
- **rsyslog** — служба, яка може збирати, обробляти та записувати системні повідомлення.
- **Troubleshooting** — систематичний пошук причини несправності.
- **Root cause** — першопричина проблеми.
- **Exit code** — код завершення команди або процесу.
- **Permission denied** — помилка доступу через права або обмеження безпеки.
- **Connection refused** — з'єднання відхилено, часто тому, що на потрібній адресі та порту немає процесу, який приймає з'єднання.
- **Timeout** — операція не завершилася в межах очікуваного часу.
- **Disk space** — доступне місце на диску.
- **Log rotation** — ротація журналів: перейменування, архівування та видалення старих журналів за правилами.
- **Monitoring** — постійне спостереження за станом системи.
- **Incident** — подія, що порушує нормальну роботу системи.

## 1. Як організовані журнали в Linux

У Linux журнали можуть зберігатися у файлах, у системному журналі systemd або в інших системах журналювання.

Найважливіші місця:

    /var/log/
    /var/log/syslog
    /var/log/messages
    /var/log/auth.log
    /var/log/secure
    /var/log/kern.log
    /var/log/nginx/
    /var/log/postgresql/

Не всі ці файли обов'язково існують у кожному дистрибутиві.

### `/var/log/`

Основна директорія, у якій багато служб зберігають журнали.

Переглянути вміст:

    ls -lah /var/log/

Знайти файли та піддиректорії:

    find /var/log -maxdepth 2 -type f

Переглянути розміри файлів:

    sudo du -ah /var/log | sort -h | tail -n 20

### `/var/log/syslog`

У багатьох системах Ubuntu та Debian цей файл містить різноманітні системні повідомлення.

Переглянути останні записи:

    sudo tail -n 50 /var/log/syslog

Файл може бути відсутній, якщо система використовує іншу конфігурацію журналювання.

### `/var/log/messages`

У деяких дистрибутивах, зокрема в конфігураціях на основі RHEL, цей файл може містити загальні системні повідомлення.

    sudo tail -n 50 /var/log/messages

### `/var/log/auth.log`

В Ubuntu та Debian часто використовується для повідомлень, пов'язаних з автентифікацією.

    sudo tail -n 50 /var/log/auth.log

У системах на основі RHEL аналогічну роль часто виконує:

    sudo tail -n 50 /var/log/secure

### `/var/log/kern.log`

У деяких системах містить повідомлення ядра Linux.

    sudo tail -n 50 /var/log/kern.log

Повідомлення ядра також можна переглядати командою:

    sudo dmesg

### Журнали конкретних служб

Наприклад, Nginx:

    /var/log/nginx/access.log
    /var/log/nginx/error.log

PostgreSQL може використовувати окрему директорію для журналів, але фактичне розташування залежить від конфігурації.

**Запам'ятай:** не припускай, що кожен файл журналу існує. Спочатку перевір структуру своєї системи.

## 2. systemd та journalctl

У сучасних Linux-системах, які використовують systemd, багато служб передають повідомлення до системи журналювання `systemd-journald`.

Перегляд цих повідомлень виконується командою `journalctl`.

### Переглянути журнал

    journalctl

Команда показує доступні записи системного журналу, до яких користувач має доступ.

### Переглянути останні записи

    journalctl -n 50

Показати останні 50 записів.

### Переглядати нові записи в реальному часі

    journalctl -f

Команда продовжує показувати нові записи в міру їх надходження.

Для виходу натисни `Ctrl + C`.

### Переглянути журнал поточного завантаження

    journalctl -b

Показує записи поточного завантаження системи.

### Переглянути журнал попереднього завантаження

    journalctl -b -1

Працює, якщо журнали попереднього завантаження збережені.

Це корисно, коли потрібно дослідити проблему після перезавантаження комп'ютера або сервера.

### Показати лише помилки

    journalctl -p err

Показує записи рівня `error` і серйозніші рівні.

### Показати помилки поточного завантаження

    journalctl -b -p err

### Показати повідомлення ядра

    journalctl -k

### Показати повідомлення ядра поточного завантаження

    journalctl -k -b

### Обмежити кількість записів

    journalctl -n 100 --no-pager

Параметр `--no-pager` виводить результат без інтерактивного переглядача.

### Важливі рівні журналювання

| Рівень | Значення |
|---|---|
| `emerg` | Система непридатна до роботи |
| `alert` | Потрібна негайна дія |
| `crit` | Критична помилка |
| `err` | Помилка |
| `warning` | Попередження |
| `notice` | Важлива нормальна подія |
| `info` | Інформаційне повідомлення |
| `debug` | Детальна діагностична інформація |

Для параметра `-p` можна вказувати назву рівня, наприклад:

    journalctl -p warning

**Запам'ятай:** `journalctl -p err` показує не лише повідомлення з рівнем `err`, а й повідомлення серйозніших рівнів.

## 3. Журнали конкретної служби

Під час діагностики часто потрібно дивитися не весь системний журнал, а повідомлення конкретної служби.

Для цього використовується `journalctl -u`.

### Перевірити стан Nginx

    systemctl status nginx

Команда показує стан служби та може містити останні журнальні повідомлення.

### Переглянути журнал Nginx

    sudo journalctl -u nginx

### Останні 50 записів Nginx

    sudo journalctl -u nginx -n 50 --no-pager

### Стежити за журналом Nginx у реальному часі

    sudo journalctl -u nginx -f

### Переглянути журнал PostgreSQL

Назва служби залежить від дистрибутива, версії та способу встановлення.

    systemctl list-units --type=service | grep -i postgres

Якщо відома назва служби:

    sudo journalctl -u postgresql -n 50 --no-pager

### Переглянути журнал власної служби

Припустимо, NestJS-застосунок працює як systemd-служба `my-app`.

    sudo journalctl -u my-app -n 100 --no-pager

Для перегляду нових повідомлень:

    sudo journalctl -u my-app -f

Назва `my-app` умовна. Заміни її на назву своєї служби.

### Чому це зручно

Якщо сервер має багато служб, системний журнал може містити тисячі записів.

Фільтрація за назвою служби дозволяє зосередитися на конкретному процесі.

**Запам'ятай:** якщо служба не запускається, починай із `systemctl status`, а потім переходь до `journalctl -u назва-служби`.

## 4. Перегляд файлів журналів

Не всі журнали переглядають через `journalctl`. Багато програм записують їх безпосередньо у файли.

Для цього потрібні стандартні команди роботи з текстом.

### `cat`

Показує весь вміст файлу.

    cat file.log

Для великих журналів це не завжди зручно.

### `less`

Дозволяє переглядати файл посторінково.

    less file.log

Основні клавіші:

- `Space` — наступна сторінка;
- `b` — попередня сторінка;
- `/error` — пошук слова `error`;
- `n` — наступний результат пошуку;
- `N` — попередній результат пошуку;
- `q` — вихід.

Для системного журналу:

    sudo less /var/log/syslog

### `head`

Показує початок файлу.

    head file.log

Показати перші 20 рядків:

    head -n 20 file.log

### `tail`

Показує кінець файлу.

    tail file.log

Показати останні 50 рядків:

    tail -n 50 file.log

### `tail -f`

Стежить за новими записами у файлі.

    sudo tail -f /var/log/nginx/error.log

Це одна з найкорисніших команд під час діагностики вебсервера.

### `tail -F`

    sudo tail -F /var/log/nginx/error.log

Відрізняється від `-f` тим, що може продовжувати стеження після ротації журналу або створення нового файлу з тією самою назвою.

### Переглянути кілька останніх журналів

    sudo tail -n 30 /var/log/syslog
    sudo tail -n 30 /var/log/nginx/error.log

Кожна команда читає окремий файл.

**Запам'ятай:**
- `less` — зручно досліджувати старі записи;
- `tail -n` — швидко переглянути останні записи;
- `tail -f` — спостерігати за новими записами.

## 5. Пошук помилок у журналах

Часто журнал великий, тому потрібно знайти конкретні повідомлення.

### `grep`

Знайти слово `error`:

    grep 'error' file.log

Ігнорувати регістр:

    grep -i 'error' file.log

Показати номери рядків:

    grep -in 'error' file.log

Знайти кілька можливих ознак проблеми:

    grep -Ei 'error|failed|denied|timeout' file.log

### Пошук у журналах Nginx

    sudo grep -i 'error' /var/log/nginx/error.log

Знайти помилки доступу:

    sudo grep -Ei 'denied|permission|forbidden' /var/log/nginx/error.log

Знайти проблеми з підключенням до backend:

    sudo grep -Ei 'upstream|connect\(\) failed|timed out' /var/log/nginx/error.log

### Пошук у системному журналі

    sudo grep -i 'failed' /var/log/syslog

Цей приклад працює, якщо файл `/var/log/syslog` існує.

### Пошук із контекстом

Показати три рядки перед і після збігу:

    grep -C 3 'error' file.log

Показати три рядки після збігу:

    grep -A 3 'error' file.log

Показати три рядки перед збігом:

    grep -B 3 'error' file.log

### Підрахувати кількість збігів

    grep -ic 'error' file.log

### Рекурсивний пошук у директорії

    sudo grep -Rni 'error' /var/log/nginx/

### Поєднання `tail` та `grep`

Стежити за журналом і показувати рядки, які містять `error`:

    sudo tail -F /var/log/nginx/error.log | grep --line-buffered -i 'error'

Параметр `--line-buffered` допомагає показувати результати без зайвої затримки через буферизацію.

**Запам'ятай:** не шукай лише слово `error`. Причина може бути описана як `failed`, `denied`, `refused`, `timeout`, `unavailable` або іншим повідомленням.

## 6. Часові мітки та пошук за часом

Під час діагностики важливо знати, коли саме виникла проблема.

Наприклад, якщо застосунок перестав працювати о 14:30, потрібно дослідити записи навколо цього часу.

### Переглянути журнал за останню годину

    journalctl --since "1 hour ago"

### Переглянути записи за останні 30 хвилин

    journalctl --since "30 minutes ago"

### Переглянути журнал за конкретний проміжок

    journalctl --since "2026-10-19 14:00:00" --until "2026-10-19 15:00:00"

Використовуй дату й час, які відповідають потрібному періоду. Приклади вище — демонстраційні.

### Переглянути записи служби за останню годину

    sudo journalctl -u nginx --since "1 hour ago"

### Переглянути помилки за певний період

    sudo journalctl -p err --since "today"

### Перевірити поточний час системи

    date

### Перевірити часовий пояс

    timedatectl

### Чому час важливий

Різниця між часовими поясами може ускладнити пошук причини помилки.

Наприклад:
- журнал записаний в UTC;
- користувач повідомив час за місцевим часовим поясом;
- застосунок і база даних мають різні налаштування часу.

Під час розслідування помилки зіставляй часові мітки Nginx, застосунку та бази даних.

**Запам'ятай:** спочатку визнач точний або приблизний час інциденту, а потім звужуй пошук до цього проміжку.

## 7. Exit Code — код завершення команди

Код завершення показує, чи завершилася команда успішно з погляду її власної логіки.

У Bash код попередньої команди доступний через `$?`.

Приклад:

    ls
    echo $?

Якщо команда `ls` завершилася успішно, зазвичай отримаємо:

    0

Якщо команда завершилася помилкою, зазвичай буде ненульовий код.

### Основне правило

- `0` — успішне завершення;
- ненульове значення — помилка або інший результат, визначений програмою.

Не кожен ненульовий код означає системний збій. Конкретне значення залежить від програми.

### Приклад із неіснуючим файлом

    cat missing.txt
    echo $?

Команда `cat` повідомить, що файл не існує, та поверне ненульовий код.

### Перевірити код команди відразу

    nginx -t
    echo $?

Якщо `nginx -t` успішний, код завершення зазвичай буде `0`.

Важливо виконувати `echo $?` відразу після команди, яку перевіряєш. Якщо між ними виконати іншу команду, `$?` покаже результат останньої команди.

### Умовна конструкція Bash

    if sudo nginx -t; then
        echo "Конфігурація коректна"
    else
        echo "Знайдено помилку в конфігурації"
    fi

Тут не потрібно вручну перевіряти `$?`: `if` використовує код завершення команди.

### `&&` та `||`

Виконати другу команду лише після успішного завершення першої:

    sudo nginx -t && echo "Configuration is valid"

Виконати другу команду, якщо перша завершилася помилкою:

    sudo nginx -t || echo "Configuration test failed"

**Запам'ятай:** код завершення — один зі способів перевірити результат команди, але він не замінює аналіз її виводу та журналів.

## 8. Troubleshooting: правильний порядок дій

**Troubleshooting** — це не випадкове виконання команд, а послідовна перевірка можливих причин проблеми.

Зручний алгоритм:

    1. Визначити симптом.
    2. Визначити, який компонент не працює.
    3. Перевірити стан служби.
    4. Переглянути журнали.
    5. Перевірити конфігурацію.
    6. Перевірити мережу та порти.
    7. Перевірити доступність залежностей.
    8. Знайти першопричину.
    9. Внести мінімальну зміну.
    10. Повторно перевірити роботу.
    11. Зафіксувати результат.

### Крок 1. Сформулюй проблему

Не просто:

    "Сайт не працює"

Краще:

    "Nginx працює, але запит до /api/users повертає 502."

Чим точніше описано симптом, тим легше вибрати правильні команди.

### Крок 2. Перевір стан компонента

Для Nginx:

    systemctl status nginx

Для PostgreSQL:

    systemctl status postgresql

Для власної systemd-служби:

    systemctl status my-app

Назви служб залежать від системи та конфігурації.

### Крок 3. Переглянь журнали

    sudo journalctl -u nginx -n 50 --no-pager

    sudo tail -n 50 /var/log/nginx/error.log

Для власної служби:

    sudo journalctl -u my-app -n 100 --no-pager

### Крок 4. Перевір конфігурацію

Для Nginx:

    sudo nginx -t

Для PostgreSQL перевіряй конфігурацію відповідно до встановленої версії та її розташування.

### Крок 5. Перевір порти

    sudo ss -tulpn

Переконайся, що потрібна програма слухає правильний порт.

### Крок 6. Перевір мережеве з'єднання

    curl -v http://127.0.0.1:3000/

Для бази даних можна перевірити з'єднання через відповідний клієнт, наприклад `psql`.

### Крок 7. Перевір залежності

Наприклад, NestJS може не працювати через недоступність PostgreSQL.

У такому випадку проблема може бути не в самому Nginx і навіть не в маршрутах NestJS.

### Крок 8. Виправ причину

Якщо проблема спричинена неправильною адресою backend, виправ конфігурацію.

Якщо проблема в доступі до бази даних, перевір її стан і параметри підключення.

### Крок 9. Перевір результат

Повтори саме той запит, який раніше не працював.

### Крок 10. Зафіксуй висновок

Запиши:
- симптом;
- першопричину;
- використані команди;
- внесені зміни;
- результат перевірки.

**Запам'ятай:** перезапуск може тимчасово приховати проблему, але не обов'язково усуває її першопричину.

## 9. Діагностика Nginx

Для вебсерверів важливо розрізняти системний журнал служби та журнали HTTP-запитів.

### Перевірити стан

    systemctl status nginx

### Перевірити конфігурацію

    sudo nginx -t

### Переглянути системний журнал

    sudo journalctl -u nginx -n 50 --no-pager

### Переглянути журнал помилок

    sudo tail -n 50 /var/log/nginx/error.log

### Переглянути журнал запитів

    sudo tail -n 50 /var/log/nginx/access.log

### Перевірити порт 80

    sudo ss -tulpn | grep ':80'

### Перевірити HTTP-відповідь

    curl -I http://127.0.0.1/

### Типові проблеми Nginx

**1. Nginx не запускається**

Можливі причини:
- синтаксична помилка;
- порт уже зайнятий;
- помилка доступу до файлу;
- неправильний шлях у конфігурації.

Перевір:

    sudo nginx -t

    sudo journalctl -u nginx -n 100 --no-pager

**2. Nginx повертає 502**

Можливі причини:
- backend не запущений;
- неправильний порт;
- неправильна адреса upstream;
- з'єднання з backend відхилене.

Перевір:

    curl -I http://127.0.0.1:3000/

    sudo tail -n 50 /var/log/nginx/error.log

**3. Nginx повертає 404**

Можливі причини:
- неправильний URL;
- невідповідний `location`;
- неправильний URI після `proxy_pass`;
- запит потрапив до іншого `server` block;
- маршрут не існує в backend.

**4. Nginx повертає 403**

Можливі причини:
- правила доступу;
- права доступу до статичних файлів;
- обмеження на рівні застосунку.

**5. Сайт не відкривається ззовні**

Перевір:
- чи працює Nginx;
- чи слухає він потрібний порт;
- чи правильні DNS-записи;
- чи дозволений порт у firewall;
- чи доступний сервер із мережі.

## 10. Діагностика Node.js та NestJS

### Варіант C. Застосунок працює через менеджер процесів

Якщо використовується PM2, переглянь список процесів:

    pm2 list

Переглянь журнали:

Переглянь журнали конкретного процесу:

    pm2 logs my-app

Ці команди доступні лише тоді, коли PM2 встановлений і використовується для запуску застосунку.

### Перевірити доступність Node.js

### Перевірити порт

### Перевірити HTTP-відповідь

### Типові проблеми Node.js

- помилка в коді;
- відсутні залежності;
- неправильні змінні середовища;
- неправильний порт;
- недоступна база даних;
- відсутні права на потрібні файли;
- недостатньо пам'яті;
- конфлікт портів.

**Запам'ятай:** спочатку з'ясуй, як запущено застосунок. Від цього залежить, де шукати його журнали.

## 11. Діагностика PostgreSQL

Якщо NestJS не може отримати дані з PostgreSQL, потрібно перевірити базу даних окремо.

### Перевірити стан служби

    systemctl status postgresql

На деяких системах PostgreSQL може працювати через окрему службу конкретного кластера. Назву потрібно перевірити у своїй системі.

### Переглянути журнали

    sudo journalctl -u postgresql -n 100 --no-pager

### Перевірити, чи слухає PostgreSQL порт 5432

    sudo ss -tulpn | grep ':5432'

Стандартний порт PostgreSQL — `5432`, але його можна змінити в конфігурації.

### Перевірити підключення через `psql`

Наприклад, якщо відомі користувач і база даних:

    psql -h 127.0.0.1 -U taubu -d educational

Заміни значення на ті, які використовуються у твоєму середовищі.

### Перевірити базу даних

Після підключення:

    \conninfo

Показати таблиці:

    \dt

Вийти:

    \q

### Типові проблеми PostgreSQL

**1. Connection refused**

Можливі причини:
- сервер не запущений;
- неправильний порт;
- сервер не слухає вказаний інтерфейс.

**2. Password authentication failed**

Можливі причини:
- неправильний пароль;
- неправильний користувач;
- невідповідні правила автентифікації.

**3. Database does not exist**

Можливо, вказано неправильну назву бази даних.

**4. Connection timed out**

Можливі причини:
- мережевий доступ заблокований;
- сервер недоступний;
- неправильна адреса;
- мережеві проблеми.

**5. NestJS не може підключитися до PostgreSQL**

Перевір:
- адресу;
- порт;
- назву бази;
- ім'я користувача;
- пароль;
- доступність PostgreSQL;
- налаштування мережі;
- журнали NestJS та PostgreSQL.

Не змінюй правила автентифікації бази даних навмання. Спочатку з'ясуй, чому підключення не працює.

## 12. Діагностика мережі та портів

Проблема може бути не в програмі, а в мережі або конфігурації портів.

### Переглянути мережеві інтерфейси

    ip addr

### Переглянути маршрути

    ip route

### Перевірити DNS

    getent hosts example.com

### Перевірити доступність HTTP-сервера

    curl -I http://127.0.0.1/

### Переглянути порти, які слухають програми

    sudo ss -tulpn

### Перевірити конкретний порт

    sudo ss -tulpn | grep ':3000'

### Перевірити правила UFW

    sudo ufw status

### Типові проблеми

- застосунок слухає лише `127.0.0.1`, але запит надходить з іншої машини;
- застосунок слухає неправильний порт;
- firewall блокує підключення;
- Nginx передає запит не на ту адресу;
- DNS вказує на неправильну IP-адресу;
- порт уже зайнятий іншим процесом.

### Важливе розрізнення

`127.0.0.1` — це loopback-адреса конкретної машини.

Якщо NestJS слухає `127.0.0.1:3000`, Nginx на цій самій машині може підключатися до нього.

Але інша машина не може звернутися до цього сервісу через власну адресу `127.0.0.1`.

**Запам'ятай:** завжди визначай, з якої машини виконується запит і до якої адреси він спрямований.

## 13. Діагностика диска та пам'яті

Не всі проблеми застосунків спричинені конфігурацією. Іноді серверу не вистачає ресурсів.

### Перевірити вільне місце на диску

    df -h

Команда показує файлові системи та використання дискового простору.

### Перевірити розмір директорій

    sudo du -sh /var/log

Перевірити розмір піддиректорій:

    sudo du -h --max-depth=1 /var/log

### Перевірити пам'ять

    free -h

### Перевірити процеси

    top

Якщо встановлений `htop`:

    htop

### Перевірити повідомлення ядра

    sudo dmesg -T | tail -n 50

Звертай увагу на повідомлення про:
- нестачу пам'яті;
- завершення процесів через OOM killer;
- проблеми диска;
- помилки файлової системи;
- проблеми драйверів або пристроїв.

Параметр `-T` намагається показувати часові мітки в читабельному форматі, але їхня точність і відповідність системному часу можуть мати обмеження.

### Чому це важливо

Якщо диск заповнений, система може не мати змоги записувати нові журнали, створювати тимчасові файли або коректно працювати з базою даних.

Якщо бракує пам'яті, Linux може завершувати процеси, щоб звільнити ресурси.

**Запам'ятай:** якщо служби раптово перестали працювати, перевір не лише їхні конфігурації, а й ресурси системи.

## 14. Log Rotation — ротація журналів

Журнали можуть постійно збільшуватися. Якщо не контролювати їхній розмір, вони здатні зайняти значну частину диска.

**Log rotation** — це механізм, який дозволяє:

- архівувати старі журнали;
- створювати нові файли;
- обмежувати кількість збережених копій;
- стискати старі журнали;
- видаляти записи, які вже не потрібно зберігати.

У багатьох Linux-дистрибутивах для цього використовується `logrotate`.

### Перевірити наявність

    logrotate --version

### Основний конфігураційний файл

    /etc/logrotate.conf

### Конфігурації окремих служб

    /etc/logrotate.d/

Переглянути конфігурацію Nginx, якщо вона існує:

    cat /etc/logrotate.d/nginx

### Приклад конфігурації

Нижче наведено навчальний приклад, а не готову конфігурацію для встановлення без перевірки.

    /var/log/my-app/*.log {
        daily
        rotate 7
        compress
        missingok
        notifempty
    }

Що означають директиви:

- `daily` — виконувати ротацію щодня;
- `rotate 7` — зберігати до семи старих копій;
- `compress` — стискати старі файли;
- `missingok` — не вважати відсутність файлу помилкою;
- `notifempty` — не ротувати порожній файл.

Реальна поведінка залежить від решти конфігурації та способу, яким застосунок відкриває журнальні файли.

### Перевірити конфігурацію без внесення змін

    sudo logrotate -d /etc/logrotate.conf

Режим `-d` призначений для діагностики та не виконує звичайну ротацію.

### Важливо

Не видаляй великі журнали без з'ясування причини їхнього зростання.

Якщо журнал швидко збільшується, спочатку перевір:
- чи немає циклічної помилки;
- чи не повторюється повідомлення тисячі разів;
- чи налаштована ротація;
- чи потрібно зберігати ці записи відповідно до вимог проєкту.

## 15. systemd-journald та розмір журналів

Система `systemd-journald` може зберігати журнали в оперативній пам'яті або на диску — залежно від конфігурації.

### Переглянути використання диска журналами

    journalctl --disk-usage

### Видалити старі журнали за часовим обмеженням

    sudo journalctl --vacuum-time=7d

Команда видаляє архівні журнали, старші за вказаний період. Вона не гарантує, що будуть видалені всі записи поточного активного журналу.

### Обмежити розмір журналів

    sudo journalctl --vacuum-size=500M

Це видаляє старі архівні файли журналу, щоб зменшити загальний розмір до приблизно вказаного обсягу.

### Важливе застереження

Не очищай журнали без потреби під час розслідування інциденту.

Перед видаленням старих записів переконайся, що:
- важливі дані вже збережені;
- записи не потрібні для подальшої діагностики;
- дотримано вимог щодо зберігання журналів.

**Запам'ятай:** керування журналами має допомагати контролювати диск, але не повинно знищувати потрібні для діагностики дані.

## 16. Як читати повідомлення про помилки

Журнальний запис може містити кілька важливих частин:

    timestamp hostname process[pid]: message

Наприклад:

    Oct 19 14:30:12 server nginx[1234]: connect() failed (111: Connection refused)

Умовно це можна розділити так:

- `Oct 19 14:30:12` — час події;
- `server` — ім'я хоста;
- `nginx[1234]` — процес і його ідентифікатор;
- `connect() failed` — опис помилки;
- `Connection refused` — пояснення причини на рівні мережевого з'єднання.

Формат залежить від джерела журналу.

### На що звертати увагу

**1. Час**

Коли саме виникла помилка?

**2. Назва процесу**

Яка служба повідомила про проблему?

**3. Код або тип помилки**

Чи це помилка доступу, мережі, конфігурації або ресурсу?

**4. Адреса чи файл**

Який ресурс не вдалося відкрити або до якого сервера не вдалося підключитися?

**5. Повторюваність**

Це одинична помилка чи повідомлення повторюється постійно?

**6. Попередні записи**

Іноді справжня причина з'являється за кілька секунд до основної помилки.

### Приклад аналізу

Повідомлення:

    connect() failed (111: Connection refused) while connecting to upstream

Перший висновок:

    Nginx не зміг встановити з'єднання з upstream.

Наступні перевірки:

    sudo ss -tulpn

    curl -I http://127.0.0.1:3000/

    sudo journalctl -u my-app -n 50 --no-pager

Мета — не просто знайти повідомлення, а перевірити гіпотезу про причину.

## 17. Типові помилки та їхні причини

| Симптом | Можливі причини | Що перевірити |
|---|---|---|
| Служба не запускається | Помилка конфігурації, зайнятий порт, неправильні права | `systemctl status`, `journalctl -u` |
| `Permission denied` | Права файлів, каталогів або обмеження безпеки | `ls -l`, `namei -l`, журнали |
| `Connection refused` | Немає процесу, який слухає порт, або адреса неправильна | `ss -tulpn`, `curl` |
| `Connection timed out` | Мережеві затримки, firewall, недоступний сервер | `curl -v`, `ip route`, firewall |
| `502 Bad Gateway` | Nginx не може отримати коректну відповідь від backend | Nginx error log, backend logs |
| `504 Gateway Timeout` | Backend не відповів вчасно | Журнали, час відповіді, залежності |
| `404 Not Found` | Неправильний URL або відсутній маршрут | URL, конфігурація Nginx, маршрути застосунку |
| `No space left on device` | Заповнений диск або вичерпаний відповідний ресурс | `df -h`, `df -i`, `du -sh` |
| `Out of memory` | Нестача оперативної пам'яті | `free -h`, `top`, `dmesg` |
| `Address already in use` | Порт уже зайнятий іншим процесом | `ss -tulpn` |
| `Authentication failed` | Неправильні облікові дані або правила доступу | Конфігурація, журнали, клієнт підключення |
| `No such file or directory` | Файл відсутній або шлях неправильний | `ls`, `find`, перевірка конфігурації |

**Важливо:** це можливі причини, а не гарантований діагноз. Одне повідомлення може мати кілька пояснень.

## 18. Приклад: сайт повертає 502 Bad Gateway

Припустимо, браузер показує `502 Bad Gateway`.

Схема:

    Browser → Nginx → NestJS :3000

### Крок 1. Перевір Nginx

    systemctl status nginx

Якщо Nginx не працює, досліди причину.

Якщо працює, продовжуй.

### Крок 2. Переглянь журнал помилок

    sudo tail -n 50 /var/log/nginx/error.log

Припустимо, є запис:

    connect() failed (111: Connection refused) while connecting to upstream

Це вказує на проблему зі з'єднанням до upstream.

### Крок 3. Перевір порт

    sudo ss -tulpn | grep ':3000'

Якщо нічого не знайдено, можливо, застосунок не слухає порт `3000`.

### Крок 4. Перевір backend

    curl -v http://127.0.0.1:3000/

Якщо з'єднання не встановлюється, проблема може бути в самому застосунку або його адресі.

### Крок 5. Перевір службу NestJS

    sudo journalctl -u my-app -n 100 --no-pager

Назва служби умовна.

Можливо, застосунок завершився через помилку конфігурації або недоступність PostgreSQL.

### Крок 6. Виправ першопричину

Наприклад:
- запусти застосунок;
- виправ порт у конфігурації Nginx;
- виправ адресу upstream;
- усунь помилку, через яку NestJS завершується.

### Крок 7. Перевір результат

    curl -I http://127.0.0.1/

Повтори запит через браузер або HTTP-клієнт.

### Крок 8. Зафіксуй висновок

Наприклад:

    Симптом:
    Nginx повертав 502.

    Причина:
    NestJS не працював на порту 3000.

    Перевірка:
    curl не міг підключитися до 127.0.0.1:3000.

    Виправлення:
    Відновлено запуск NestJS.

    Результат:
    Запит через Nginx повертає очікувану відповідь.

## 19. Приклад: диск заповнений журналами

Припустимо, служби почали працювати нестабільно.

### Крок 1. Перевір диск

    df -h

Якщо файловій системі не вистачає вільного місця, визнач, що саме займає простір.

### Крок 2. Перевір журнали

    sudo du -sh /var/log

Переглянь найбільші файли:

    sudo du -ah /var/log | sort -h | tail -n 20

### Крок 3. Знайди джерело зростання

    sudo tail -n 100 /var/log/nginx/error.log

Перевір, чи не повторюється одна й та сама помилка.

### Крок 4. Перевір ротацію

    cat /etc/logrotate.conf

    ls -lah /etc/logrotate.d/

### Крок 5. Виправ причину

Можливі дії:
- усунути помилку, яка генерує надмірну кількість записів;
- перевірити налаштування ротації;
- скоригувати політику зберігання;
- звільнити місце відповідно до правил системи.

### Чого не потрібно робити

Не видаляй усі журнали навмання:

    sudo rm -rf /var/log/*

Це небезпечно й може пошкодити очікувану структуру журналювання, знищити важливі записи та ускладнити діагностику.

**Запам'ятай:** спочатку знайди джерело зростання журналів, потім обирай безпечний спосіб звільнення місця.

## 20. Приклад: `Permission denied`

Припустимо, Nginx не може прочитати файл або застосунок не може записати файл.

### Крок 1. Подивись на помилку

    sudo tail -n 50 /var/log/nginx/error.log

### Крок 2. Перевір права файлу

    ls -l /path/to/file

Заміни шлях на реальний.

### Крок 3. Перевір права всіх директорій у шляху

    namei -l /path/to/file

Для доступу до файлу процесу потрібні відповідні права на сам файл і можливість проходити через директорії шляху.

### Крок 4. Перевір користувача процесу

Для Nginx:

    ps -eo user,pid,comm | grep nginx

Для конкретної systemd-служби:

    systemctl show my-app -p User -p Group

### Крок 5. Виправ лише потрібні права

Не використовуй `chmod -R 777` як універсальне рішення.

Натомість з'ясуй:
- який процес повинен мати доступ;
- чи потрібне читання, запис або виконання;
- хто є власником файлу;
- які права повинні мати інші користувачі.

**Запам'ятай:** правильне виправлення — надати мінімально необхідні права потрібному процесу, а не відкрити доступ усім.

## 21. Практична робота: аналіз системного журналу

Мета — навчитися знаходити системні повідомлення за службою, часом і рівнем серйозності.

### Крок 1. Переглянь останні повідомлення

    journalctl -n 50 --no-pager

### Крок 2. Переглянь помилки поточного завантаження

    journalctl -b -p err --no-pager

### Крок 3. Переглянь повідомлення за останню годину

    journalctl --since "1 hour ago" --no-pager

### Крок 4. Переглянь журнал Nginx

    sudo journalctl -u nginx -n 50 --no-pager

### Крок 5. Переглянь помилки в реальному часі

    sudo journalctl -u nginx -f

### Крок 6. Знайди закономірність

Відповідай на запитання:
- яка служба створила повідомлення;
- коли воно з'явилося;
- чи повторюється помилка;
- чи є записи безпосередньо перед нею;
- чи збігається час із моментом виникнення проблеми.

### Крок 7. Запиши висновок

Навіть якщо проблема не виникла, зафіксуй команди та поясни, які дані вони показують.

## 22. Практична робота: діагностика Nginx і NestJS

Мета — перевірити весь ланцюжок від вебсервера до backend.

### Крок 1. Перевір Nginx

    systemctl status nginx

### Крок 2. Перевір конфігурацію

    sudo nginx -t

### Крок 3. Перевір порт backend

    sudo ss -tulpn | grep ':3000'

### Крок 4. Перевір backend напряму

    curl -v http://127.0.0.1:3000/

### Крок 5. Перевір Nginx

    curl -v http://127.0.0.1/

### Крок 6. Переглянь журнал помилок

    sudo tail -n 50 /var/log/nginx/error.log

### Крок 7. Переглянь журнал NestJS

    sudo journalctl -u my-app -n 100 --no-pager

### Крок 8. Порівняй результати

Можливі сценарії:

- backend не відповідає напряму — досліджуй Node.js;
- backend відповідає, але Nginx повертає 502 — перевір upstream-конфігурацію та доступність;
- Nginx повертає 404 — перевір URL і маршрутизацію;
- обидва відповідають, але API працює неправильно — перевір логіку NestJS і залежності.

## 23. Безпека журналів

Журнали можуть містити важливу або чутливу інформацію.

Наприклад:
- IP-адреси;
- імена користувачів;
- шляхи до файлів;
- URL із параметрами;
- діагностичні повідомлення;
- випадково записані токени або інші секрети.

### Основні правила

✔ Обмежуй доступ до журналів.

✔ Не публікуй повні журнали без перевірки вмісту.

✔ Не записуй паролі та секретні токени в журнали.

✔ Не передавай публічно конфігурації, що містять секрети.

✔ Налаштовуй ротацію та строки зберігання.

✔ Перевіряй журнали перед видаленням під час інциденту.

✔ Дотримуйся правил зберігання даних і вимог проєкту.

### Перевірити права на файл

    ls -l /var/log/nginx/error.log

### Перевірити власника та групу

    stat /var/log/nginx/error.log

Не змінюй права системних журналів без розуміння того, як служба ними керує.

**Запам'ятай:** журнали допомагають діагностувати проблеми, але самі журнали теж потребують захисту.

## 25. Що потрібно запам'ятати

✔ `/var/log/` — важлива директорія для файлових журналів Linux.

✔ `journalctl` — основна команда для перегляду журналів systemd-journald.

✔ `journalctl -u nginx` дозволяє переглядати журнал конкретної служби.

✔ `journalctl -b` показує записи поточного завантаження системи.

✔ `journalctl -p err` показує помилки та серйозніші повідомлення.

✔ `tail -n 50` дозволяє швидко переглянути останні 50 рядків файлу.

✔ `tail -f` показує нові записи в реальному часі.

✔ `grep` допомагає знаходити повідомлення за ключовими словами.

✔ `$?` містить код завершення останньої команди.

✔ Код завершення `0` зазвичай означає успіх, а ненульовий код — помилку або інший визначений програмою результат.

✔ `systemctl status` показує стан служби та може містити останні повідомлення.

✔ `sudo nginx -t` перевіряє конфігурацію Nginx.

✔ `sudo ss -tulpn` допомагає перевірити, які порти слухають процеси.

✔ `curl -v` показує деталі HTTP-запиту та з'єднання.

✔ `df -h` показує використання дискового простору.

✔ `free -h` показує використання пам'яті.

✔ `logrotate` допомагає керувати розміром файлових журналів.

✔ `journalctl --disk-usage` показує, скільки дискового простору займають журнали systemd-journald.

✔ `502 Bad Gateway` часто вказує на проблему між Nginx і backend.

✔ `Permission denied` вимагає перевірки прав доступу та користувача процесу.

✔ `Connection refused` часто означає, що з'єднання до вказаної адреси та порту не приймається.

✔ Перш ніж змінювати конфігурацію, потрібно зібрати достатньо даних про причину проблеми.

✔ Перезапуск служби не завжди усуває першопричину несправності.

## 26. Типові запитання на співбесіді

### Core

**1. Що таке журнал у Linux?**

Це запис про події системи, служби або застосунку, який допомагає аналізувати роботу та діагностувати проблеми.

**2. Де зберігаються журнали Linux?**

Багато файлових журналів розташовані в `/var/log/`, а повідомлення служб systemd можна переглядати через `journalctl`.

**3. Що робить `journalctl`?**

Дозволяє переглядати й фільтрувати записи системного журналу systemd-journald.

**4. Для чого потрібна команда `tail -f`?**

Для спостереження за новими записами у файлі журналу в реальному часі.

**5. Як знайти слово `error` у файлі?**

Використати `grep -i 'error' file.log`.

**6. Що таке troubleshooting?**

Це систематичний процес пошуку причини несправності та її усунення.

### Junior

**7. Як переглянути журнали Nginx?**

Можна використати `journalctl -u nginx`, а також файлові журнали `/var/log/nginx/access.log` і `/var/log/nginx/error.log`, якщо вони налаштовані.

**8. Як переглянути останні 100 записів служби?**

Використати `sudo journalctl -u назва-служби -n 100 --no-pager`.

**9. Що означає код завершення `0`?**

Зазвичай це означає, що команда завершилася успішно.

**10. Як перевірити, чи слухає застосунок порт 3000?**

Використати `sudo ss -tulpn | grep ':3000'`.

**11. Як діагностувати `502 Bad Gateway`?**

Перевірити журнали Nginx, доступність backend, правильність адреси та порту upstream.

**12. Як перевірити, чи вистачає місця на диску?**

Використати `df -h`, а для пошуку великих директорій — `du`.

### Middle

**13. Чим відрізняються `journalctl` і `tail`?**

`journalctl` переглядає записи системного журналу systemd-journald, а `tail` читає останні рядки звичайного файлу.

**14. Що таке log rotation?**

Це механізм архівування, перейменування, стискання та видалення старих журналів за визначеними правилами.

**15. Як визначити першопричину проблеми?**

Зіставити симптоми, журнали, час виникнення, стан служб, конфігурацію та мережеві перевірки.

**16. Чому не варто одразу перезапускати службу?**

Перезапуск може приховати симптом або тимчасово відновити роботу, не усунувши першопричину.

**17. Як дослідити помилку, яка виникла до перезавантаження?**

Використати `journalctl -b -1`, якщо журнали попереднього завантаження збережені.

### Senior

**18. Як організувати журналювання production-застосунку?**

Потрібно визначити рівні журналювання, формат записів, доступ, строки зберігання, ротацію, моніторинг і правила захисту чутливих даних.

**19. Як пов'язати помилки Nginx, Node.js і PostgreSQL?**

Зіставити часові мітки, ідентифікатори запитів, журнали кожного компонента та результати незалежних перевірок.

**20. Чому очищення журналів може ускладнити діагностику?**

Тому що воно знищує докази, необхідні для визначення першопричини інциденту.

## 29. Підсумок

Журнали — один із головних інструментів адміністрування Linux і підтримки серверних застосунків.

Вони допомагають визначити, що сталося, коли виникла проблема, який компонент повідомив про неї та які дії варто виконати для перевірки.

Для повсякденної роботи особливо важливі:

1. `journalctl` — перегляд системних журналів.
2. `systemctl status` — перевірка стану служби.
3. `tail` і `less` — читання файлових журналів.
4. `grep` — пошук повідомлень.
5. `curl` і `ss` — перевірка HTTP-запитів та портів.
6. `df`, `du` і `free` — перевірка ресурсів системи.
7. `logrotate` — керування файловими журналами.
8. Послідовний troubleshooting — пошук першопричини проблеми.

**Головна ідея:** не вгадуй причину несправності. Збери дані, перевір стан компонентів, зістав журнали й лише після цього змінюй конфігурацію або перезапускай службу.
