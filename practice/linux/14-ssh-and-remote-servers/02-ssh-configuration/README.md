# 02. SSH Configuration

SSH Configuration (налаштування SSH) — це конфігурація SSH-клієнта та SSH-сервера, яка визначає, як встановлюється SSH-з'єднання, які ключі використовуються для автентифікації, як вибираються користувачі й порти та які параметри безпеки застосовуються.

SSH-конфігурація дозволяє спростити підключення до віддалених Linux-серверів, уникнути повторного введення довгих команд і керувати кількома серверами з одного комп'ютера.

SSH configuration використовується для:

- налаштування коротких імен серверів замість IP-адрес;
- автоматичного вибору користувача та порту;
- вибору приватного SSH-ключа для конкретного сервера;
- керування перевіркою host keys;
- налаштування тайм-аутів і повторного використання з'єднань;
- роботи з кількома серверами та SSH-ключами;
- налаштування доступу до GitHub через SSH;
- організації віддаленої розробки та deployment;
- централізованого керування параметрами SSH-клієнта;
- налаштування SSH-сервера, якщо є відповідні адміністративні права.

Основні файли:

    ~/.ssh/config
        → персональна конфігурація SSH-клієнта

    /etc/ssh/ssh_config
        → системна конфігурація SSH-клієнта

    /etc/ssh/sshd_config
        → конфігурація SSH-сервера

    ~/.ssh/known_hosts
        → відомі host keys серверів

    ~/.ssh/authorized_keys
        → публічні ключі, дозволені для входу
          до конкретного облікового запису на сервері

Основні команди:

    ssh
        → підключення до сервера

    ssh -G
        → перегляд обчисленої конфігурації клієнта

    ssh -F
        → використання альтернативного файла конфігурації

    ssh -v
        → діагностика SSH-підключення

    ssh-keygen
        → створення та керування SSH-ключами

    ssh-add
        → керування ключами через ssh-agent

    sshd -t
        → перевірка синтаксису конфігурації SSH-сервера

    systemctl
        → керування службою SSH-сервера в systemd

### Що потрібно пам'ятати

• `~/.ssh/config` — персональний конфігураційний файл SSH-клієнта.

• `/etc/ssh/ssh_config` — системна конфігурація SSH-клієнта.

• `/etc/ssh/sshd_config` — конфігурація SSH-сервера.

• `ssh_config` і `sshd_config` — різні файли для різних компонентів SSH.

• `Host` задає шаблон імені, яке ти вказуєш у команді `ssh`.

• `HostName` визначає справжню адресу сервера.

• `User` визначає користувача, від імені якого виконується підключення.

• `Port` визначає порт SSH-сервера. Стандартний порт — `22`.

• `IdentityFile` задає шлях до приватного ключа.

• `IdentitiesOnly yes` допомагає обмежити використання ключів тими, які явно задані конфігурацією або відповідними параметрами.

• `ssh deploy-server` може використовувати налаштування з `~/.ssh/config`, замість того щоб щоразу вказувати адресу, користувача, порт і ключ.

• Конфігурація клієнта не створює SSH-ключі та не надає доступ автоматично. Сервер усе одно повинен дозволяти автентифікацію.

• Налаштування `~/.ssh/config` не замінюють перевірку ідентичності сервера через host keys.

• `StrictHostKeyChecking` впливає на перевірку host keys. Не вимикай цю перевірку без обґрунтованої причини.

• `ForwardAgent yes` передає доступ до локального SSH-agent через з'єднання. Використовуй його лише тоді, коли це справді потрібно.

• `ssh -G alias` дозволяє переглянути обчислені параметри конфігурації для певного підключення.

• `ssh -v alias` допомагає з'ясувати, який конфігураційний файл, ключ і спосіб автентифікації використовує клієнт.

• Зміни в `~/.ssh/config` зазвичай застосовуються до наступних SSH-підключень без перезапуску служби.

• Зміни в `sshd_config` стосуються SSH-сервера. Перед застосуванням їх потрібно перевірити та обережно перезавантажити службу.

• Перед зміною конфігурації SSH-сервера варто залишити відкритою поточну робочу сесію та переконатися, що є спосіб відновити доступ.

# SSH Client Configuration

SSH client configuration — налаштування SSH-клієнта, який запускається на твоєму комп'ютері.

Наприклад, на Ubuntu можна підключитися так:

    ssh deploy@192.168.1.100

Або, якщо сервер використовує порт `2222`:

    ssh -p 2222 deploy@192.168.1.100

Якщо для підключення потрібен окремий приватний ключ:

    ssh -i ~/.ssh/deploy_server deploy@192.168.1.100

Ці команди працюють, але їх доводиться повторювати.

За допомогою SSH-конфігурації можна описати сервер один раз і надалі використовувати коротке ім'я.

Наприклад:

    ssh deploy-server

SSH-клієнт прочитає відповідний блок у `~/.ssh/config` і застосує налаштовані параметри.

Схема:

    ~/.ssh/config
          |
          v
    SSH client
          |
          | HostName
          | User
          | Port
          | IdentityFile
          |
          v
    Remote SSH server

# ~/.ssh/config

`~/.ssh/config` — персональний конфігураційний файл SSH-клієнта.

Типовий шлях:

    /home/username/.ssh/config

Символ `~` означає домашній каталог поточного користувача.

Перевірити, чи існує файл:

    ls -l ~/.ssh/config

Якщо файла немає, його можна створити:

    mkdir -p ~/.ssh
    touch ~/.ssh/config
    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/config

Права:

    ~/.ssh/
        → 700

    ~/.ssh/config
        → 600

Відкрити файл у редакторі:

    nano ~/.ssh/config

Або у VS Code, якщо команда `code` доступна:

    code ~/.ssh/config

Приклад простої конфігурації:

    Host my-server
        HostName 192.168.1.100
        User deploy
        Port 22

Тепер замість:

    ssh deploy@192.168.1.100

можна виконати:

    ssh my-server

SSH-клієнт підставить адресу, користувача та порт із конфігурації.

Важливо:

• `my-server` — довільний псевдонім, який ти сам обираєш.

• `HostName` — справжня адреса сервера або його DNS-ім'я.

• `User` — ім'я користувача на віддаленому сервері.

• `Port` — порт SSH-сервера.

• Відступи в прикладах роблять конфігурацію читабельнішою. Зазвичай для параметрів усередині блоку використовують пробіли або табуляцію.

• Сам файл конфігурації не повинен містити приватні ключі як текст. У ньому вказують шлях до файла ключа.

---

# Host

`Host` задає шаблон псевдоніма, який використовується під час виклику SSH-клієнта.

Наприклад:

    Host my-server
        HostName 192.168.1.100
        User deploy

Підключення:

    ssh my-server

Тут:

    Host my-server
        → псевдонім для підключення

    HostName 192.168.1.100
        → адреса сервера

    User deploy
        → користувач на сервері

Псевдонім може бути будь-яким зручним іменем:

    Host development
        HostName dev.example.com
        User developer

    Host production
        HostName prod.example.com
        User deploy

Підключення:

    ssh development
    ssh production

Назви `development` і `production` не мають спеціального значення для SSH. Це лише імена, які допомагають організувати конфігурацію.

---

# HostName

`HostName` задає адресу, до якої SSH-клієнт повинен підключитися.

Це може бути:

    IP address
        → 192.168.1.100

    Domain name
        → server.example.com

Приклад:

    Host development
        HostName dev.example.com
        User developer

Команда:

    ssh development

SSH-клієнт підключатиметься до `dev.example.com`.

Якщо `HostName` не задано, SSH зазвичай використовує ім'я, передане команді `ssh`, як ім'я хоста для з'єднання.

Приклад без псевдоніма:

    ssh developer@dev.example.com

Приклад із псевдонімом:

    Host development
        HostName dev.example.com
        User developer

    ssh development

---

# User

`User` визначає ім'я користувача на віддаленому сервері.

Приклад:

    Host my-server
        HostName 192.168.1.100
        User deploy

Підключення:

    ssh my-server

SSH використовуватиме користувача `deploy`.

Без параметра `User` клієнт зазвичай використовує ім'я поточного локального користувача.

Наприклад:

    ssh 192.168.1.100

Якщо на локальному комп'ютері ти працюєш як `valer`, SSH може спробувати підключитися як `valer`.

Якщо на сервері потрібен користувач `deploy`, вкажи його явно:

    ssh deploy@192.168.1.100

Або налаштуй `User` у `~/.ssh/config`.

Важливо: локальний користувач і віддалений користувач можуть мати різні імена.

---

# Port

`Port` задає порт SSH-сервера.

Стандартний порт:

    22

Приклад конфігурації:

    Host my-server
        HostName 192.168.1.100
        User deploy
        Port 2222

Підключення:

    ssh my-server

SSH-клієнт використовуватиме порт `2222`.

Без конфігурації нестандартний порт можна вказати через `-p`:

    ssh -p 2222 deploy@192.168.1.100

Важливо:

• Зміна порту на клієнті не змінює порт самого сервера.

• Сервер повинен реально слухати вказаний порт.

• Мережеві правила та firewall мають дозволяти з'єднання.

• Порт `2222` у прикладі є умовним. Не вважай його портом свого сервера, доки це не підтверджено його налаштуваннями.

---

# IdentityFile

`IdentityFile` задає шлях до приватного ключа, який SSH-клієнт може використовувати для автентифікації.

Приклад:

    Host my-server
        HostName 192.168.1.100
        User deploy
        IdentityFile ~/.ssh/deploy_server

Підключення:

    ssh my-server

SSH-клієнт використовуватиме вказаний файл ключа відповідно до конфігурації та доступних методів автентифікації.

Інший приклад:

    Host github-work
        HostName github.com
        User git
        IdentityFile ~/.ssh/github_work

Тепер можна використовувати псевдонім `github-work` у Git SSH URL.

Наприклад:

    git clone git@github-work:username/repository.git

Тут `github-work` — псевдонім із SSH-конфігурації, а `username/repository.git` — шлях до репозиторію.

Важливо:

• `IdentityFile` указує на приватний ключ, а не на `.pub` файл.

• Відповідний public key має бути зареєстрований на сервері або в сервісі.

• Якщо файл ключа відсутній або недоступний, автентифікація може не відбутися.

• Використовуй повний або коректно розгорнутий шлях до ключа.

---

# IdentitiesOnly

`IdentitiesOnly yes` допомагає обмежити використання ключів, які SSH-клієнт пропонує для певного підключення, ключами, заданими явно в конфігурації або команді.

Це особливо корисно, якщо в `ssh-agent` завантажено багато ключів.

Приклад:

    Host github-work
        HostName github.com
        User git
        IdentityFile ~/.ssh/github_work
        IdentitiesOnly yes

Для підключення:

    ssh -T github-work

Цей параметр допомагає уникнути ситуації, коли клієнт пропонує багато інших ключів, перш ніж дійде до потрібного.

Важливо:

• `IdentitiesOnly yes` не створює ключ.

• Він не додає public key до GitHub.

• Він не гарантує успішної автентифікації, якщо ключ не зареєстрований у відповідному акаунті.

---

# PreferredAuthentications

`PreferredAuthentications` задає порядок бажаних методів автентифікації, які пропонує клієнт.

Приклад:

    Host my-server
        HostName 192.168.1.100
        User deploy
        PreferredAuthentications publickey

Це вказує клієнту віддавати перевагу методу `publickey`.

Однак цей параметр не вмикає public-key authentication на сервері та не гарантує, що сервер її дозволяє.

Для звичайного використання часто не потрібно встановлювати цей параметр вручну.

Він може бути корисним під час діагностики або в спеціальних середовищах.

---

# Host *

`Host *` — шаблон, який відповідає всім псевдонімам підключення.

Наприклад:

    Host *
        ServerAliveInterval 60
        ServerAliveCountMax 3

Ці параметри застосовуватимуться до всіх відповідних підключень, якщо їх не змінюють інші правила конфігурації.

`Host *` часто використовують для загальних налаштувань клієнта.

Наприклад:

    Host *
        ServerAliveInterval 60
        ServerAliveCountMax 3
        ConnectTimeout 10

Важливо розуміти порядок конфігурації.

OpenSSH зазвичай використовує перше отримане значення для більшості параметрів. Значення, задані в командному рядку, мають вищий пріоритет.

Тому загальні правила часто розміщують після специфічних блоків `Host`, щоб специфічні налаштування могли спрацювати раніше.

# SSH Configuration Precedence

SSH-клієнт може отримувати параметри з кількох джерел.

Типові джерела:

    1. Параметри командного рядка
    2. Персональна конфігурація ~/.ssh/config
    3. Системна конфігурація /etc/ssh/ssh_config
    4. Вбудовані значення за замовчуванням

Для багатьох параметрів OpenSSH використовує перше отримане значення. Точна поведінка залежить від параметра та способу його застосування.

Приклад:

    Host my-server
        User deploy
        Port 2222

У команді можна передати додаткові параметри:

    ssh -p 2200 my-server

Параметр `-p 2200` у командному рядку має пріоритет над `Port 2222` у конфігурації.

Для діагностики обчисленої конфігурації:

    ssh -G my-server

Команда виведе багато параметрів, зокрема:

    hostname
    user
    port
    identityfile
    serveraliveinterval

Щоб знайти окремі значення:

    ssh -G my-server | grep -E '^(hostname|user|port|identityfile) '

Це корисно, коли SSH підключається не до тієї адреси, використовує неправильного користувача або вибирає неочікуваний ключ.

# Кілька серверів в одному config

У файлі `~/.ssh/config` можна описати багато серверів.

Приклад:

    Host development
        HostName dev.example.com
        User developer
        IdentityFile ~/.ssh/id_ed25519

    Host staging
        HostName staging.example.com
        User deploy
        Port 2222
        IdentityFile ~/.ssh/staging_key

    Host production
        HostName prod.example.com
        User deploy
        IdentityFile ~/.ssh/production_key
        IdentitiesOnly yes

Підключення:

    ssh development
    ssh staging
    ssh production

Переваги:

• Не потрібно щоразу вводити довгі адреси.

• Легше розрізняти середовища.

• Для кожного сервера можна використовувати окремий ключ.

• Менше шансів випадково підключитися не до того середовища.

• Налаштування простіше підтримувати.

Для реального production-сервера варто використовувати захищені ключі, перевірені host keys та доступ лише з потрібними правами.

# GitHub SSH Configuration

SSH-конфігурація може допомогти використовувати різні ключі для GitHub.

Наприклад, є два ключі:

    ~/.ssh/github_personal
    ~/.ssh/github_work

У `~/.ssh/config` можна додати:

    Host github-personal
        HostName github.com
        User git
        IdentityFile ~/.ssh/github_personal
        IdentitiesOnly yes

    Host github-work
        HostName github.com
        User git
        IdentityFile ~/.ssh/github_work
        IdentitiesOnly yes

Для перевірки персонального підключення:

    ssh -T git@github-personal

Для робочого:

    ssh -T git@github-work

Для використання конкретного псевдоніма в Git потрібно використовувати його в SSH URL репозиторію.

Наприклад:

    git clone git@github-personal:username/personal-repo.git

Або:

    git clone git@github-work:organization/work-repo.git

У цих прикладах `username`, `organization` і назви репозиторіїв потрібно замінити на реальні.

Важливо:

• Відповідний public key має бути доданий до потрібного акаунта GitHub.

• SSH-псевдонім у конфігурації — це локальне налаштування клієнта.

• `User git` — типовий користувач для SSH-підключень до GitHub, а не ім'я твого акаунта.

• SSH-аутентифікація не замінює права доступу до конкретного репозиторію.

# ConnectTimeout

`ConnectTimeout` визначає максимальний час очікування під час встановлення з'єднання та початкового рукостискання SSH.

Приклад:

    Host slow-server
        HostName server.example.com
        User deploy
        ConnectTimeout 10

Тут `10` означає десять секунд.

Якщо з'єднання не встановлюється вчасно, клієнт може завершити спробу з помилкою.

Цей параметр корисний для:

    - автоматизованих скриптів;
    - серверів, доступність яких нестабільна;
    - скорочення очікування на недоступному хості.

Важливо: `ConnectTimeout` не є загальним обмеженням тривалості всієї віддаленої команди.

---

# ServerAliveInterval

`ServerAliveInterval` задає інтервал, через який клієнт надсилає запити для перевірки активності SSH-з'єднання, якщо від сервера не надходять дані.

Приклад:

    Host my-server
        ServerAliveInterval 60

Клієнт використовуватиме інтервал у 60 секунд.

Це може допомогти виявляти завислі або неактивні мережеві з'єднання.

---

# ServerAliveCountMax

`ServerAliveCountMax` визначає, скільки запитів перевірки активності можуть залишатися без відповіді, перш ніж клієнт визнає з'єднання недоступним.

Приклад:

    Host my-server
        ServerAliveInterval 60
        ServerAliveCountMax 3

Умовно:

    ServerAliveInterval 60
        → перевірка приблизно кожні 60 секунд

    ServerAliveCountMax 3
        → після кількох невдалих перевірок
          з'єднання буде визнано недоступним

Фактичний час завершення залежить від стану з'єднання та реалізації SSH.

Ці параметри корисні під час роботи через нестабільну мережу.

Важливо: keepalive-параметри не гарантують, що мережеві проблеми зникнуть. Вони допомагають виявляти ситуації, коли з'єднання перестало відповідати.

---

# StrictHostKeyChecking

`StrictHostKeyChecking` керує поведінкою SSH-клієнта під час перевірки host keys.

Приклад:

    Host my-server
        StrictHostKeyChecking yes

Цей параметр вимагає суворої перевірки відомого host key. Якщо ключ відсутній або не відповідає очікуваному, підключення може бути відхилене.

Основні значення:

    yes
        → суворо перевіряти host key

    ask
        → запитувати підтвердження в ситуаціях,
          які допускають інтерактивну перевірку

    accept-new
        → автоматично приймати нові ключі,
          але відхиляти змінені вже відомі ключі

Підтримка та точна поведінка значень залежать від версії OpenSSH.

Не рекомендується без потреби використовувати:

    StrictHostKeyChecking no

Це послаблює захист від підключення до сервера з неочікуваним ключем.

Найкраща практика — перевіряти host key сервера через довірений канал, особливо під час першого підключення або після зміни інфраструктури.

---

# UserKnownHostsFile

`UserKnownHostsFile` визначає файл або файли, які SSH-клієнт використовує для збереження host keys користувача.

Типове розташування:

    ~/.ssh/known_hosts

Приклад:

    Host my-server
        UserKnownHostsFile ~/.ssh/known_hosts

У більшості випадків не потрібно змінювати цей параметр.

Він може бути корисним для:

    - ізольованих тестових середовищ;
    - спеціальних автоматизованих процесів;
    - окремого керування довірою до певних серверів.

Не використовуй порожній або тимчасовий файл known_hosts лише для приховування попереджень про зміну host key.

---

# ForwardAgent

`ForwardAgent` керує передаванням доступу до локального SSH-agent на віддалену машину.

Приклад:

    Host jump-server
        HostName jump.example.com
        User deploy
        ForwardAgent no

За замовчуванням forwarding зазвичай вимкнений.

Чому це важливо:

Якщо forwarding увімкнено, процеси на віддаленому сервері можуть отримати можливість звертатися до переадресованого агента, поки доступ активний.

Це не означає, що приватний ключ копіюється на сервер, але зловмисний процес на сервері потенційно може зловживати доступом до агента для підписування запитів.

Тому:

• Не вмикай `ForwardAgent yes` без потреби.

• Використовуй його лише на серверах, яким довіряєш.

• Для типового входу на віддалений сервер forwarding не потрібний.

• Якщо потрібне багатоступеневе підключення, спочатку розглянь `ProxyJump`, який часто дозволяє обійтися без agent forwarding.

---

# ProxyJump

`ProxyJump` дозволяє підключатися до цільового сервера через проміжний SSH-сервер.

Такий проміжний сервер часто називають jump host або bastion host.

Схема:

    Local computer
          |
          v
    Jump server
          |
          v
    Internal server

Приклад:

    Host jump-server
        HostName bastion.example.com
        User deploy

    Host internal-server
        HostName 10.0.0.25
        User admin
        ProxyJump jump-server

Підключення:

    ssh internal-server

SSH-клієнт спочатку використовуватиме `jump-server` як проміжний вузол, щоб дістатися до `internal-server`.

Без конфігурації подібний підхід можна записати командою:

    ssh -J deploy@bastion.example.com admin@10.0.0.25

Важливо:

• Jump server повинен мати мережевий доступ до цільового сервера.

• Обидва підключення повинні мати належні налаштування автентифікації.

• Перевірка host keys цільового сервера все одно важлива.

• `ProxyJump` не надає автоматичних прав доступу до внутрішньої мережі.

---

# ControlMaster

`ControlMaster` дозволяє кільком SSH-з'єднанням використовувати спільне основне з'єднання.

Це може зменшувати затримки, коли часто запускаються нові SSH-команди до того самого сервера.

Приклад конфігурації:

    Host development
        HostName dev.example.com
        User developer
        ControlMaster auto
        ControlPath ~/.ssh/cm-%C
        ControlPersist 10m

Параметри:

    ControlMaster auto
        → використовувати спільне з'єднання,
          якщо це можливо

    ControlPath ~/.ssh/cm-%C
        → шлях до Unix socket для керування з'єднанням

    ControlPersist 10m
        → залишати основне з'єднання доступним
          до 10 хвилин після завершення сесії

`%C` — спеціальний токен OpenSSH, який допомагає сформувати унікальне ім'я socket на основі параметрів підключення.

Важливо:

• Каталог для `ControlPath` має існувати.

• Socket-файли потрібно захищати від доступу сторонніх користувачів.

• Необережне спільне використання контрольних сокетів може створити ризики безпеки.

• Для початкового рівня ці параметри достатньо розуміти концептуально. Вони не обов'язкові для звичайного SSH-підключення.

---

# Include

`Include` дозволяє включати інші конфігураційні файли.

Це зручно, якщо налаштувань багато.

Приклад:

    Include ~/.ssh/config.d/*

Можна організувати файли так:

    ~/.ssh/
    ├── config
    └── config.d/
        ├── github
        ├── development
        └── production

Основний файл:

    Include ~/.ssh/config.d/*

Окремий файл `~/.ssh/config.d/development`:

    Host development
        HostName dev.example.com
        User developer
        IdentityFile ~/.ssh/id_ed25519

Переваги:

• Легше підтримувати велику конфігурацію.

• Можна логічно розділяти сервери.

• Простіше оновлювати окремі групи налаштувань.

Важливо: файли, що підключаються через `Include`, є частиною конфігурації та повинні бути захищені відповідно до політик доступу.

---

# Match

`Match` дозволяє застосовувати окремі параметри за певних умов.

Наприклад, можна створити умовні правила для конкретного користувача або хоста.

Однак `Match` у конфігурації SSH-клієнта має обмежений набір умов і не призначений для довільної логіки.

На початковому рівні достатньо знати:

    Host
        → налаштування за шаблоном імені хоста

    Match
        → налаштування за підтримуваними умовами

Не плутай:

    Match у ~/.ssh/config
        → умовні правила SSH-клієнта

    Match у /etc/ssh/sshd_config
        → умовні правила SSH-сервера

Доступні умови та правила їх застосування залежать від конкретного файла конфігурації й версії OpenSSH.

---

# SSH Client vs SSH Server Configuration

Це одна з найважливіших відмінностей.

## SSH Client

Клієнт запускається на твоєму комп'ютері.

Основні файли:

    ~/.ssh/config
        → персональні налаштування клієнта

    /etc/ssh/ssh_config
        → системні налаштування клієнта

Основна команда:

    ssh

Приклад:

    ssh development

## SSH Server

SSH-сервер приймає підключення від клієнтів.

Основний конфігураційний файл:

    /etc/ssh/sshd_config

Основна програма:

    sshd

У Linux із systemd служба зазвичай називається `ssh` або `sshd`, залежно від дистрибутива.

Наприклад, в Ubuntu часто використовується:

    ssh.service

Перевірити стан:

    systemctl status ssh

У системах, де служба має іншу назву:

    systemctl status sshd

Не кожна Linux-система використовує systemd або однакові назви служб.

Порівняння:

    ~/.ssh/config
        → як мій комп'ютер підключається до серверів

    /etc/ssh/ssh_config
        → системні правила SSH-клієнта

    /etc/ssh/sshd_config
        → як мій сервер приймає SSH-підключення

---

# /etc/ssh/sshd_config

`/etc/ssh/sshd_config` — основний конфігураційний файл демона SSH-сервера OpenSSH.

Цей файл може керувати:

    - портом SSH-сервера;
    - дозволеними способами автентифікації;
    - доступом користувачів;
    - root login;
    - правилами переадресації;
    - іншими параметрами безпеки сервера.

Переглянути основний файл:

    sudo less /etc/ssh/sshd_config

Редагувати його потрібно обережно:

    sudo nano /etc/ssh/sshd_config

Зміни в цьому файлі впливають на SSH-сервер, а не на клієнтські підключення, які ти ініціюєш зі свого комп'ютера.

Перед змінами:

    1. Зроби резервну копію конфігурації.
    2. Переконайся, що маєш адміністративний доступ.
    3. Перевір синтаксис.
    4. Застосуй зміни обережно.
    5. Перевір нове підключення, не закриваючи стару сесію.

Створення резервної копії:

    sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

Важливо: перед зміною параметрів автентифікації, root login або порту необхідно розуміти, як повернути попередні налаштування, якщо нова конфігурація заблокує доступ.

---

# PasswordAuthentication

`PasswordAuthentication` у `sshd_config` керує тим, чи дозволена парольна автентифікація користувачів через SSH.

Приклад:

    PasswordAuthentication no

Це вимикає звичайну парольну автентифікацію SSH, якщо ефективна конфігурація та інші механізми не змінюють результат.

Приклад протилежного значення:

    PasswordAuthentication yes

Важливо:

• Це параметр сервера, а не клієнтський параметр.

• Не вимикай парольну автентифікацію, доки не перевіриш, що ключовий доступ працює.

• Інші методи, зокрема keyboard-interactive, мають окремі параметри й можуть поводитися по-різному.

• У деяких дистрибутивах додаткові файли з `Include` можуть змінювати ефективні значення.

---

# PubkeyAuthentication

`PubkeyAuthentication` у конфігурації SSH-сервера керує автентифікацією за публічними ключами.

Приклад:

    PubkeyAuthentication yes

Це дозволяє використовувати public-key authentication, якщо її не обмежують інші правила.

Публічні ключі користувачів зазвичай зберігаються в:

    ~/.ssh/authorized_keys

Важливо: цей параметр не додає ключі автоматично. Public key має бути встановлений для потрібного користувача, а права доступу та інші параметри сервера мають бути коректними.

---

# PermitRootLogin

`PermitRootLogin` керує можливістю входу безпосередньо під обліковим записом `root`.

Приклад:

    PermitRootLogin no

Це забороняє прямий SSH-вхід під `root`.

Для звичайного адміністративного сценарію часто краще:

    SSH login as regular user
          |
          v
    sudo for administrative tasks

Наприклад:

    ssh deploy@server-address

Після входу користувач із відповідними правами може виконувати адміністративні команди через `sudo`.

Важливо:

• Не вимикай root login, доки не переконаєшся, що маєш робочий доступ під іншим користувачем.

• Не дозволяй root login лише для зручності без оцінки ризиків.

• Фактичні правила доступу залежать також від інших параметрів і політик сервера.

---

# Перевірка SSH-серверної конфігурації

Перед застосуванням змін до `sshd_config` перевір синтаксис:

    sudo sshd -t

Якщо команда завершується без повідомлень про помилки, це зазвичай означає, що синтаксична перевірка пройшла успішно.

Це не гарантує, що нові налаштування не заблокують доступ або що сервер працюватиме так, як ти очікуєш.

Переглянути ефективну конфігурацію сервера можна командою:

    sudo sshd -T

Команда виводить обчислені параметри конфігурації сервера.

Для перевірки окремих значень:

    sudo sshd -T | grep -E '^(port|permitrootlogin|pubkeyauthentication|passwordauthentication) '

Якщо використовуються правила `Match`, для перевірки конфігурації конкретного з'єднання може знадобитися параметр `-C` з відповідними даними.

Приклад:

    sudo sshd -T -C user=deploy,host=server.example.com,addr=192.168.1.50

Значення `host` і `addr` тут умовні. Для точної перевірки потрібно використовувати дані, що відповідають потрібному з'єднанню.

---

# Застосування змін SSH-сервера

Після зміни `sshd_config` потрібно застосувати нові налаштування.

Спочатку перевір:

    sudo sshd -t

Потім, якщо система використовує systemd і службу `ssh`:

    sudo systemctl reload ssh

На деяких дистрибутивах служба називається `sshd`:

    sudo systemctl reload sshd

Якщо reload не підтримується або не підходить для конкретної системи, спосіб застосування залежить від дистрибутива та менеджера служб.

Перевірити стан:

    systemctl status ssh

Або:

    systemctl status sshd

Важливо:

• Не перезапускай SSH-сервер навмання на віддаленій машині.

• Залиш поточне робоче SSH-з'єднання відкритим.

• Після застосування змін відкрий нове з'єднання в окремому терміналі.

• Переконайся, що нові налаштування працюють.

• Лише після успішної перевірки закривай стару сесію.

---

# SSH Configuration Debugging

Якщо підключення не працює, почни з простих перевірок.

## 1. Перевір обчислену конфігурацію

    ssh -G my-server

Знайди параметри:

    hostname
    user
    port
    identityfile

Це допоможе з'ясувати, які налаштування фактично застосовуються.

## 2. Перевір підключення з докладним виводом

    ssh -v my-server

Якщо інформації недостатньо:

    ssh -vvv my-server

## 3. Явно вкажи ключ

    ssh -i ~/.ssh/deploy_server deploy@192.168.1.100

Якщо це працює, а псевдонім — ні, перевір `IdentityFile`, `Host` і порядок конфігурації.

## 4. Перевір права

    ls -ld ~/.ssh
    ls -l ~/.ssh/config
    ls -l ~/.ssh/deploy_server

## 5. Перевір доступність мережі

Переконайся, що адреса правильна, сервер доступний, а порт відкритий.

Наприклад, якщо встановлено `nc`:

    nc -vz server.example.com 22

Ця команда перевіряє можливість встановити TCP-з'єднання з указаним портом, але не перевіряє успішність SSH-автентифікації.

## 6. Перевір серверну конфігурацію

Якщо маєш адміністративний доступ до сервера:

    sudo sshd -t
    sudo sshd -T

## 7. Перевір журнали сервера

На Ubuntu із systemd:

    sudo journalctl -u ssh -n 50 --no-pager

На системах зі службою `sshd`:

    sudo journalctl -u sshd -n 50 --no-pager

Назва служби залежить від дистрибутива.

# Типові помилки

## 1. Неправильний псевдонім Host

Конфігурація:

    Host development
        HostName dev.example.com
        User developer

А команда:

    ssh dev

У цьому випадку блок `Host development` не обов'язково відповідатиме імені `dev`.

Виправлення:

    ssh development

Або зміни псевдонім у конфігурації.

---

## 2. Неправильний HostName

Конфігурація:

    Host production
        HostName 192.168.1.100
        User deploy

Якщо адреса застаріла або неправильна, SSH не підключиться до потрібного сервера.

Перевір:

    ssh -G production

---

## 3. Неправильний шлях до ключа

Конфігурація:

    Host my-server
        IdentityFile ~/.ssh/wrong_key

Перевір:

    ls -l ~/.ssh/wrong_key

Виправ `IdentityFile`, якщо шлях неправильний.

---

## 4. Неправильний порт

Конфігурація:

    Host my-server
        Port 2222

Якщо сервер слухає порт `22`, підключення до `2222` може завершитися помилкою.

Перевір правильний порт за документацією сервера або через адміністратора.

---

## 5. Конфігурація перекривається іншим правилом

Приклад:

    Host *
        User default-user

    Host production
        User deploy

Оскільки OpenSSH зазвичай використовує перше отримане значення для більшості параметрів, порядок блоків може впливати на результат.

Розміщуй специфічні блоки перед загальними, а результат перевіряй:

    ssh -G production

---

## 6. SSH-клієнт використовує не той ключ

Перевір:

    ssh -vvv my-server

За потреби додай:

    IdentitiesOnly yes

та правильний:

    IdentityFile ~/.ssh/deploy_server

Переконайся, що відповідний public key дозволений на сервері.

---

## 7. Змінено host key

Якщо SSH повідомляє про зміну host key, спочатку перевір fingerprint сервера через довірений канал.

Не вимикай перевірку host key лише для того, щоб прибрати попередження.

---

## 8. Помилка в sshd_config

Перед застосуванням серверної конфігурації виконай:

    sudo sshd -t

Якщо є синтаксична помилка, виправ її перед reload або restart.

---

## 9. Втрата доступу після зміни конфігурації

Причиною можуть бути:

    - неправильний порт;
    - заборона потрібного способу автентифікації;
    - неправильні права;
    - заборона потрібного користувача;
    - некоректні правила Match.

Завжди зберігай робочу сесію відкритою до перевірки нового підключення.

# Практика

## Завдання 1 — створити SSH config

Перевір, чи існує файл:

    ls -la ~/.ssh/

Якщо файла немає, створи:

    touch ~/.ssh/config
    chmod 600 ~/.ssh/config

Додай умовну конфігурацію:

    Host practice-server
        HostName 192.168.1.100
        User deploy
        Port 22

Поки що не підключайся, якщо ця адреса не відповідає твоєму реальному тестовому серверу.

---

## Завдання 2 — переглянути конфігурацію

Виконай:

    ssh -G practice-server

Знайди:

    hostname
    user
    port
    identityfile

Поясни, які значення SSH-клієнт отримав із конфігурації.

---

## Завдання 3 — додати окремий ключ

Якщо маєш окремий навчальний ключ, додай його до блоку:

    Host practice-server
        HostName 192.168.1.100
        User deploy
        IdentityFile ~/.ssh/linux_practice
        IdentitiesOnly yes

Переконайся, що шлях до ключа існує.

Перевір:

    ssh -G practice-server

---

## Завдання 4 — створити кілька псевдонімів

Створи блоки:

    Host development
        HostName dev.example.com
        User developer

    Host staging
        HostName staging.example.com
        User deploy
        Port 2222

Поясни, чим відрізняються параметри цих підключень.

Ці адреси наведені для навчання. Для реального з'єднання заміни їх на адреси доступних тобі серверів.

---

## Завдання 5 — перевірити пріоритет параметрів

Нехай конфігурація містить:

    Host practice-server
        HostName 192.168.1.100
        User deploy
        Port 2222

Виконай:

    ssh -G practice-server

Потім:

    ssh -G -p 2200 practice-server

Порівняй значення `port`.

Не потрібно встановлювати з'єднання для цього завдання: достатньо переглянути обчислену конфігурацію.

---

## Завдання 6 — діагностувати SSH

Виконай:

    ssh -v practice-server

Зверни увагу на:

    - читання конфігураційних файлів;
    - застосування правил Host;
    - вибір ключів;
    - встановлення з'єднання;
    - етап автентифікації.

---

## Завдання 7 — перевірити конфігурацію сервера

Якщо маєш власний Linux-сервер і адміністративні права, виконай:

    sudo sshd -t
    sudo sshd -T

Поясни різницю між цими командами.

Не редагуй `sshd_config` на віддаленому сервері без плану відновлення доступу.

---

## Завдання 8 — GitHub із псевдонімом

Якщо маєш відповідні ключі, створи конфігурацію:

    Host github-practice
        HostName github.com
        User git
        IdentityFile ~/.ssh/github_work
        IdentitiesOnly yes

Перевір:

    ssh -T git@github-practice

Це спрацює лише тоді, коли вказаний приватний ключ відповідає public key, доданому до GitHub, і належним чином налаштовані інші параметри підключення.

# Головне

• SSH configuration спрощує та стандартизує підключення до серверів.

• `~/.ssh/config` — основний файл персональних налаштувань SSH-клієнта.

• `Host` створює псевдонім для підключення.

• `HostName`, `User` та `Port` визначають адресу, користувача й порт.

• `IdentityFile` указує, який приватний ключ використовувати.

• `IdentitiesOnly yes` допомагає уникати пропонування зайвих ключів.

• `Host *` задає загальні правила для багатьох підключень.

• `ssh -G` показує обчислену конфігурацію клієнта.

• `ssh -v` допомагає діагностувати проблеми.

• `ProxyJump` дозволяє проходити через проміжний сервер.

• `ServerAliveInterval` та `ServerAliveCountMax` допомагають виявляти неактивні з'єднання.

• `StrictHostKeyChecking` керує перевіркою host keys, яку не слід без потреби вимикати.

• `/etc/ssh/sshd_config` визначає налаштування SSH-сервера.

• `sudo sshd -t` перевіряє синтаксис серверної конфігурації.

• `sudo sshd -T` показує ефективні параметри сервера.

• Перед застосуванням змін на сервері потрібно перевірити конфігурацію та зберегти можливість відновлення доступу.

• Основна модель SSH configuration:

    ~/.ssh/config
          |
          v
    SSH client
          |
          | Host
          | HostName
          | User
          | Port
          | IdentityFile
          |
          v
    Remote SSH server

• Для Junior Linux Developer важливо вміти створити `~/.ssh/config`, налаштувати кілька серверів, вибрати потрібний ключ, перевірити ефективні параметри й безпечно діагностувати помилки SSH.
