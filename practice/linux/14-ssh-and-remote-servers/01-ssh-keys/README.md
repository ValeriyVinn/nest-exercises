# 01. SSH Keys

SSH Keys (SSH-ключі) — це криптографічні ключі, які використовуються для безпечної автентифікації під час підключення до віддалених серверів через протокол SSH (Secure Shell).

SSH дозволяє безпечно працювати з віддаленим комп'ютером, виконувати команди, передавати файли та адмініструвати сервер через мережу.

SSH keys використовуються для:

- безпечного підключення до віддалених Linux-серверів;
- входу на сервер без введення пароля облікового запису під час кожного підключення;
- автентифікації на GitHub та інших Git-сервісах;
- автоматизації розгортання застосунків;
- виконання команд на віддаленому сервері;
- передавання файлів через `scp` та `rsync`;
- налаштування CI/CD;
- обмеження доступу до серверів за допомогою криптографічної автентифікації.

Основні інструменти та файли:

    ssh          → підключення до віддаленого сервера
    ssh-keygen   → створення SSH-ключів
    ssh-agent    → керування завантаженими приватними ключами
    ssh-add      → додавання ключів до ssh-agent
    ssh-copy-id  → копіювання публічного ключа на сервер
    ~/.ssh/      → каталог SSH-конфігурації та ключів
    authorized_keys → список дозволених публічних ключів
    known_hosts  → список відомих SSH-серверів

### Що потрібно пам'ятати

• SSH — протокол для безпечного віддаленого доступу до комп'ютерів.

• SSH-ключі — це пара криптографічно пов'язаних ключів: public key та private key.

• Public key можна передавати серверу або сервісу, який має перевіряти автентичність користувача.

• Private key потрібно зберігати в таємниці. Його не можна передавати на сервер, публікувати в GitHub або надсилати іншим людям.

• Public key зазвичай має розширення `.pub`, наприклад `id_ed25519.pub`.

• Private key зазвичай зберігається без розширення, наприклад `id_ed25519`.

• `ssh-keygen` створює пару SSH-ключів.

• Ed25519 — сучасний алгоритм, який зазвичай є хорошим вибором для створення нових SSH-ключів.

• Passphrase захищає приватний ключ додатковим секретом.

• Passphrase не є паролем облікового запису на віддаленому сервері.

• `ssh-agent` може зберігати розблокований ключ у пам'яті, щоб не вводити passphrase під час кожного використання ключа.

• `ssh-add` додає приватний ключ до `ssh-agent`.

• `ssh-copy-id` копіює публічний ключ на сервер, зазвичай у файл `~/.ssh/authorized_keys`.

• Файл `authorized_keys` містить публічні ключі, яким дозволено автентифікуватися для відповідного облікового запису.

• Файл `known_hosts` зберігає ідентифікатори серверів, з якими клієнт уже встановлював довірений зв'язок.

• `known_hosts` і `authorized_keys` виконують різні функції.

• Права доступу до приватного ключа мають бути обмеженими.

• Для приватного ключа зазвичай використовують права `600`, а для каталогу `~/.ssh/` — `700`.

• Наявність ключа на клієнті ще не гарантує успішного входу. Сервер повинен приймати відповідний public key для потрібного користувача.

• SSH-ключ для GitHub не надає автоматичного доступу до будь-якого Linux-сервера.

• Для безпечної роботи важливо перевіряти fingerprint сервера під час першого підключення.

# SSH

SSH (Secure Shell) — мережевий протокол, який забезпечує зашифрований зв'язок між клієнтом і віддаленим сервером.

Наприклад, ти працюєш на своєму Ubuntu-ноутбуці та хочеш керувати іншим Linux-комп'ютером через мережу.

Схема:

    Local computer
          |
          | SSH connection
          |
          v
    Remote Linux server

Для підключення використовується команда:

    ssh username@server-address

Наприклад:

    ssh deploy@192.168.1.100

Тут:

    ssh                  → SSH-клієнт
    deploy               → ім'я користувача на сервері
    192.168.1.100        → адреса сервера

SSH може використовувати різні методи автентифікації:

    password authentication
        → автентифікація паролем

    public-key authentication
        → автентифікація за допомогою SSH-ключів

У цьому розділі основна увага приділяється public-key authentication.

# SSH Key Pair

SSH key pair — це пара ключів:

    Public key
        → публічний ключ

    Private key
        → приватний ключ

Ключі криптографічно пов'язані між собою, але приватний ключ не потрібно передавати для перевірки автентичності.

Схема:

    Local computer
    ┌──────────────────────────────┐
    │                              │
    │  Private key                 │
    │  id_ed25519                  │
    │                              │
    │  Public key                  │
    │  id_ed25519.pub              │
    │                              │
    └──────────────────────────────┘
                  |
                  | Public key is installed
                  | on the remote server
                  v
    Remote Linux server
    ┌──────────────────────────────┐
    │                              │
    │  ~/.ssh/authorized_keys      │
    │                              │
    │  Contains allowed            │
    │  public keys                 │
    │                              │
    └──────────────────────────────┘

Принцип роботи:

    1. Клієнт ініціює SSH-підключення.
    2. Сервер перевіряє доступні методи автентифікації.
    3. Клієнт доводить, що має відповідний приватний ключ.
    4. Сервер перевіряє, чи дозволений відповідний public key.
    5. Якщо перевірка успішна та інші умови доступу виконані,
       автентифікація може завершитися успішно.

Приватний ключ не передається серверу як секрет під час звичайної public-key authentication.

Важливо розрізняти:

    User authentication
        → перевірка особи користувача

    Server authentication
        → перевірка ідентичності віддаленого сервера

SSH-ключі користувача зазвичай беруть участь у user authentication. Перевірка сервера використовує host key та механізми довіри до сервера.

---

# Public Key

Public key — публічний ключ, який можна передавати системам, що мають перевіряти автентичність користувача.

Наприклад:

    id_ed25519.pub

Типовий вміст такого файла для Ed25519:

    ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... user@computer

Це лише ілюстрація формату, а не справжній ключ для використання.

Публічний ключ зазвичай містить:

    key type
        → тип ключа

    key data
        → закодовані дані ключа

    comment
        → необов'язковий коментар

Коментар часто містить ім'я користувача або пристрою.

Наприклад:

    user@ubuntu-laptop

Коментар допомагає розрізняти ключі, але сам по собі не забезпечує безпеку.

Public key можна встановити:

    на Linux-сервері
        → ~/.ssh/authorized_keys

    у налаштуваннях GitHub
        → SSH keys

    у налаштуваннях іншого сервісу
        → відповідно до його документації

Пам'ятай:

    public key  → можна передавати
    private key → потрібно захищати

---

# Private Key

Private key — приватний ключ, який доводить, що клієнт має право використовувати відповідну пару SSH-ключів.

Типовий файл:

    ~/.ssh/id_ed25519

Він зберігається на локальному комп'ютері.

Перевірити наявні файли можна командою:

    ls -la ~/.ssh/

Приклад:

    drwx------ 2 user user 4096 Oct 19 15:00 .
    -rw------- 1 user user  464 Oct 19 15:00 id_ed25519
    -rw-r--r-- 1 user user  104 Oct 19 15:00 id_ed25519.pub

Це ілюстрація можливого виводу. Реальні розміри та дати можуть відрізнятися.

Приватний ключ не повинен бути доступним для читання іншим звичайним користувачам системи.

Встановити типові права:

    chmod 600 ~/.ssh/id_ed25519

Перевірити:

    ls -l ~/.ssh/id_ed25519

Очікуваний формат прав:

    -rw-------

Тут:

    r → read
    w → write
    - → permission відсутній

Важливо:

• Не копіюй приватний ключ у репозиторій.

• Не додавай приватний ключ до Git-коміту.

• Не надсилай приватний ключ через електронну пошту або месенджери.

• Не вставляй приватний ключ у публічні чати.

• Не зберігай приватний ключ на віддаленому сервері без обґрунтованої потреби.

• Якщо приватний ключ скомпрометований, потрібно припинити його використання та відкликати відповідний доступ на всіх системах, де цей public key був дозволений.

# ~/.ssh/

`~/.ssh/` — каталог користувача для SSH-ключів і SSH-конфігурації.

Символ `~` означає домашній каталог поточного користувача.

Наприклад:

    /home/valer/.ssh/

Переглянути каталог:

    ls -la ~/.ssh/

Типова структура:

    ~/.ssh/
    ├── id_ed25519
    ├── id_ed25519.pub
    ├── known_hosts
    └── config

Також можуть бути інші файли:

    id_rsa
    id_rsa.pub
    authorized_keys
    known_hosts.old
    інші ключі та конфігураційні файли

Призначення:

    id_ed25519
        → приватний ключ

    id_ed25519.pub
        → публічний ключ

    config
        → налаштування SSH-клієнта

    known_hosts
        → відомі ідентифікатори серверів

    authorized_keys
        → публічні ключі, дозволені для входу
          до конкретного облікового запису

Важливо: `authorized_keys` зазвичай розташовується в `~/.ssh/` на сервері для конкретного користувача. Його відсутність на локальному клієнті є нормальною.

# Створення SSH-ключа

Для створення SSH-ключів використовується команда:

    ssh-keygen

Рекомендований варіант для нового ключа на сучасній Linux-системі:

    ssh-keygen -t ed25519 -C "user@ubuntu-laptop"

Тут:

    ssh-keygen
        → програма створення ключів

    -t ed25519
        → тип ключа

    -C "user@ubuntu-laptop"
        → коментар до ключа

Після запуску програма запитає, куди зберегти ключ.

Приклад:

    Enter file in which to save the key
    (/home/user/.ssh/id_ed25519):

Якщо запропонований шлях підходить, натисни Enter.

Далі програма запитає passphrase.

Приклад:

    Enter passphrase (empty for no passphrase):

Можна встановити passphrase для додаткового захисту приватного ключа.

Після створення ключів з'являться файли:

    ~/.ssh/id_ed25519
    ~/.ssh/id_ed25519.pub

---

### Покрокове створення ключа

Крок 1. Перевір каталог SSH.

    ls -la ~/.ssh/

Якщо каталогу ще немає, це нормально.

Крок 2. Створи ключ.

    ssh-keygen -t ed25519 -C "user@ubuntu-laptop"

Крок 3. Вкажи шлях.

Для першого стандартного ключа зазвичай достатньо натиснути Enter, прийнявши:

    ~/.ssh/id_ed25519

Якщо файл уже існує, не перезаписуй його автоматично. Спочатку з'ясуй, для чого він використовується.

Крок 4. Встанови passphrase.

За можливості використовуй надійну passphrase.

Крок 5. Перевір створені файли.

    ls -l ~/.ssh/id_ed25519*

Крок 6. Перевір fingerprint публічного ключа.

    ssh-keygen -lf ~/.ssh/id_ed25519.pub

Команда покаже fingerprint ключа.

Приклад формату:

    256 SHA256:... user@ubuntu-laptop (ED25519)

Це ілюстрація, а не реальний fingerprint.

# Ed25519

Ed25519 — алгоритм цифрового підпису на основі еліптичних кривих, який широко використовується для SSH-автентифікації.

Створення ключа:

    ssh-keygen -t ed25519

Переваги Ed25519:

• Компактний розмір ключів і підписів.

• Висока продуктивність.

• Простий вибір параметрів порівняно з багатьма конфігураціями RSA.

• Підтримка сучасними версіями OpenSSH.

Для більшості нових SSH-ключів Ed25519 є хорошим стандартним вибором.

Однак сумісність залежить від клієнта, сервера та їхніх версій. Для старих систем може знадобитися інший алгоритм.

---

# RSA

RSA — криптографічний алгоритм, який також може використовуватися для SSH-ключів.

Створення RSA-ключа:

    ssh-keygen -t rsa -b 4096 -C "user@ubuntu-laptop"

Тут:

    -t rsa
        → алгоритм RSA

    -b 4096
        → розмір ключа в бітах

RSA може бути потрібний для сумісності зі старими системами або спеціальними середовищами.

Проте для нового звичайного SSH-підключення на сучасних системах зазвичай можна почати з Ed25519.

Не плутай:

    RSA 4096
        → розмір RSA-ключа 4096 біт

    Ed25519
        → інший алгоритм із власними параметрами

Не потрібно створювати RSA-ключ лише тому, що його розмір у бітах більший.

# Passphrase

Passphrase — секретна фраза, яка захищає приватний ключ.

Вона використовується для розблокування приватного ключа перед його застосуванням.

Схема:

    Private key
          |
          v
    Passphrase protection
          |
          v
    Unlocked key
          |
          v
    SSH authentication

Passphrase не замінює приватний ключ і не є паролем користувача на сервері.

Порівняння:

    Account password
        → пароль облікового запису на сервері

    Private key
        → криптографічний ключ користувача

    Passphrase
        → секрет для захисту приватного ключа

Для приватного ключа з passphrase під час використання може знадобитися її введення.

Для зручності можна використовувати `ssh-agent`.

---

# ssh-agent

`ssh-agent` — програма, яка допомагає керувати приватними ключами, що використовуються для SSH-автентифікації.

Вона дозволяє зберігати розблоковані ключі в пам'яті протягом часу роботи агента.

Завдяки цьому не потрібно вводити passphrase щоразу, коли використовується відповідний ключ.

Перевірити змінну середовища агента:

    echo "$SSH_AUTH_SOCK"

Якщо команда нічого не виводить, це може означати, що змінна не встановлена в поточному середовищі. Це не завжди означає, що SSH взагалі не працює.

Перевірити наявність доступного агента:

    ssh-add -l

Якщо агент доступний, команда покаже завантажені ключі.

Якщо ключів немає, можна отримати повідомлення:

    The agent has no identities.

Якщо агент недоступний, можлива помилка підключення до агента.

Запуск агента в типовому Linux-середовищі:

    eval "$(ssh-agent -s)"

Після запуску команда зазвичай виводить PID агента.

Додай приватний ключ:

    ssh-add ~/.ssh/id_ed25519

Після введення passphrase ключ буде доступний через агент.

Перевір завантажені ключі:

    ssh-add -l

Важливо:

• У багатьох графічних середовищах агент уже запускається автоматично.

• Не завжди потрібно запускати `ssh-agent` вручну.

• У різних середовищах, зокрема WSL, контейнерах і віддалених сесіях, налаштування можуть відрізнятися.

• Агент forwarding має окремі ризики безпеки. Не вмикай його без потреби.

---

# ssh-add

`ssh-add` — команда для додавання та керування ключами в `ssh-agent`.

Основні команди:

    ssh-add ~/.ssh/id_ed25519
        → додати приватний ключ до агента

    ssh-add -l
        → показати fingerprints завантажених ключів

    ssh-add -L
        → показати публічні ключі, завантажені в агент

    ssh-add -d ~/.ssh/id_ed25519
        → видалити конкретний ключ з агента

    ssh-add -D
        → видалити всі ключі з агента

Зверни увагу:

    ssh-add -D
        → прибирає ключі з агента

Ця команда не видаляє самі файли приватних ключів із диска.

Перевіряти стан агента потрібно до того, як робити висновок, що ключ відсутній або несправний.

# ssh-copy-id

`ssh-copy-id` — утиліта для встановлення публічного ключа на віддаленому сервері.

Приклад:

    ssh-copy-id -i ~/.ssh/id_ed25519.pub user@192.168.1.100

Тут:

    -i ~/.ssh/id_ed25519.pub
        → файл публічного ключа

    user@192.168.1.100
        → користувач та адреса сервера

Зазвичай утиліта підключається до сервера, часто використовуючи пароль або інший уже доступний метод автентифікації, і додає ключ до `authorized_keys` відповідного користувача.

Після успішного встановлення можна перевірити підключення:

    ssh user@192.168.1.100

Якщо сервер і клієнт налаштовані правильно, вхід може виконуватися без введення пароля облікового запису сервера.

Якщо приватний ключ захищений passphrase, її введення все ще може знадобитися, якщо ключ не розблоковано через агент.

Важливо:

• `ssh-copy-id` копіює public key, а не private key.

• Команда не обходить серверні політики доступу.

• Для встановлення ключа зазвичай потрібен попередній доступ до облікового запису на сервері.

• На сервері можуть бути вимкнені певні методи автентифікації або встановлені додаткові обмеження.

---

# authorized_keys

`authorized_keys` — файл на сервері, який містить публічні ключі, дозволені для автентифікації конкретного користувача.

Типовий шлях:

    ~/.ssh/authorized_keys

Наприклад, для користувача `deploy`:

    /home/deploy/.ssh/authorized_keys

Кожен запис зазвичай містить один публічний ключ.

Умовна структура:

    ssh-ed25519 AAAAC3... user@laptop
    ssh-ed25519 AAAAC3... admin-workstation

Це лише приклад формату.

Якщо публічний ключ клієнта присутній у відповідному `authorized_keys`, це може дозволити автентифікацію, якщо інші налаштування сервера також її дозволяють.

Перевірити права на сервері:

    ls -ld ~/.ssh
    ls -l ~/.ssh/authorized_keys

Типові права:

    ~/.ssh/
        700

    ~/.ssh/authorized_keys
        600

Виправлення прав:

    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/authorized_keys

Ці команди потрібно виконувати для відповідного облікового запису на сервері. Не змінюй права системних або чужих файлів без розуміння наслідків.

---

# known_hosts

`known_hosts` — файл SSH-клієнта, який зберігає ідентифікатори серверів, з якими клієнт установлював довірений зв'язок.

Типовий шлях:

    ~/.ssh/known_hosts

Цей файл допомагає клієнту перевіряти, чи відповідає ключ сервера очікуваній ідентичності.

Важливо розрізняти:

    authorized_keys
        → які користувацькі ключі дозволені на сервері

    known_hosts
        → яким ключам серверів довіряє клієнт

Коли ти вперше підключаєшся до сервера, SSH-клієнт може показати fingerprint host key та запитати підтвердження довіри.

Не підтверджуй його автоматично, якщо не маєш можливості перевірити ідентичність сервера.

Якщо host key змінився, причиною може бути:

    - перевстановлення сервера;
    - законна ротація host key;
    - зміна адреси або інфраструктури;
    - підключення до іншого сервера;
    - потенційна атака посередника (MITM).

Зміна ключа не завжди означає атаку, але її потрібно перевірити.

---

# Key Fingerprint

Key fingerprint — короткий криптографічний відбиток ключа, який використовується для його ідентифікації.

Для публічного ключа:

    ssh-keygen -lf ~/.ssh/id_ed25519.pub

Приклад формату:

    256 SHA256:AbCdEf... user@ubuntu-laptop (ED25519)

Fingerprint зручно використовувати, щоб перевірити, чи йдеться про той самий ключ.

Він може бути корисним для:

    - ідентифікації SSH-ключа;
    - перевірки публічного ключа;
    - підтвердження host key сервера;
    - порівняння ключа з довіреним джерелом.

Важливо:

• Fingerprint не є приватним ключем.

• Сам факт знання fingerprint не дозволяє автентифікуватися як власник ключа.

• Fingerprint сервера потрібно порівнювати з відомим надійним джерелом, наприклад даними адміністратора через незалежний канал.

---

# Перевірка SSH-ключів

Переглянути вміст каталогу:

    ls -la ~/.ssh/

Перевірити наявність стандартного приватного ключа:

    test -f ~/.ssh/id_ed25519 && echo "Private key exists"

Перевірити наявність публічного ключа:

    test -f ~/.ssh/id_ed25519.pub && echo "Public key exists"

Вивести публічний ключ:

    cat ~/.ssh/id_ed25519.pub

Це безпечно за умови, що ти копіюєш саме `.pub` файл і передаєш його у відповідне поле налаштувань.

Не використовуй `cat` для демонстрації приватного ключа:

    ~/.ssh/id_ed25519

Приватний ключ не потрібно показувати або надсилати іншим людям.

Перевірити тип і fingerprint:

    ssh-keygen -lf ~/.ssh/id_ed25519.pub

Перевірити права:

    stat -c '%A %a %n' ~/.ssh/id_ed25519
    stat -c '%A %a %n' ~/.ssh/id_ed25519.pub

Приклад очікуваних прав:

    -rw------- 600 /home/user/.ssh/id_ed25519
    -rw-r--r-- 644 /home/user/.ssh/id_ed25519.pub

Конкретні права можуть відрізнятися залежно від системи та налаштувань. Найважливіше — щоб приватний ключ не був доступний для читання стороннім користувачам.

---

# Права доступу SSH

Linux використовує права доступу для захисту SSH-файлів.

Типова рекомендована конфігурація:

    ~/.ssh/
        chmod 700

    ~/.ssh/id_ed25519
        chmod 600

    ~/.ssh/id_ed25519.pub
        chmod 644

    ~/.ssh/config
        chmod 600

    ~/.ssh/authorized_keys
        chmod 600

`known_hosts` також має бути захищений від небажаного запису іншими користувачами.

Встановлення прав на локальному комп'ютері:

    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/id_ed25519
    chmod 644 ~/.ssh/id_ed25519.pub

Якщо існує файл конфігурації:

    chmod 600 ~/.ssh/config

Пам'ятай:

    7 = read + write + execute
    6 = read + write
    4 = read
    0 = no permissions

Для каталогу право `execute` означає можливість проходити до файлів усередині нього.

Права доступу можуть бути причиною відмови SSH-клієнта використовувати приватний ключ або причиною проблем на сервері.

Не виправляй усі SSH-файли однаковою командою без перевірки їхнього призначення.

---

# Підключення з використанням ключа

Після встановлення public key на сервер можна виконати:

    ssh user@192.168.1.100

Якщо ключ має стандартне ім'я та розташований у `~/.ssh/`, SSH зазвичай може знайти його автоматично.

Якщо використовується нестандартний шлях:

    ssh -i ~/.ssh/deploy_key user@192.168.1.100

Тут:

    -i ~/.ssh/deploy_key
        → явно вказаний приватний ключ

Важливо:

• Параметр `-i` вказує шлях до приватного ключа на клієнті.

• На сервері має бути дозволений відповідний публічний ключ.

• Користувач, адреса, порт і серверні налаштування мають бути правильними.

• Якщо використовуєш нестандартний порт, можна додати `-p`.

Наприклад:

    ssh -i ~/.ssh/deploy_key -p 2222 user@192.168.1.100

Тут:

    -p 2222
        → порт SSH-сервера

---

# SSH-ключі та GitHub

SSH-ключі можна використовувати для автентифікації на GitHub під час роботи з Git.

Наприклад, якщо репозиторій використовує SSH URL:

    git@github.com:username/repository.git

Git використовує SSH-клієнт для встановлення з'єднання з GitHub.

Типовий процес:

    1. Створити SSH-ключ на локальному комп'ютері.
    2. Скопіювати вміст public key.
    3. Додати public key у налаштування GitHub.
    4. Перевірити SSH-з'єднання.
    5. Використовувати SSH URL репозиторію.

Показати публічний ключ:

    cat ~/.ssh/id_ed25519.pub

Перевірити з'єднання з GitHub:

    ssh -T git@github.com

Під час першого підключення перевіряй host key GitHub за офіційними інструкціями сервісу.

У разі успішної автентифікації GitHub може вивести повідомлення з іменем користувача та поясненням, що shell-доступ не надається.

Це нормально: GitHub підтримує SSH для операцій Git, але не є звичайним Linux-сервером, на якому можна відкрити інтерактивний shell.

Важливо:

    GitHub SSH key
        → автентифікація для підтримуваних операцій Git

    Linux server SSH key
        → автентифікація на відповідному Linux-сервері

Один і той самий public key технічно можна зареєструвати в кількох системах, але для кращого розмежування доступу часто зручно використовувати окремі ключі для різних пристроїв, сервісів або ролей.

---

# Кілька SSH-ключів

Можна мати кілька SSH-ключів для різних задач.

Наприклад:

    ~/.ssh/
    ├── id_ed25519
    ├── id_ed25519.pub
    ├── github_work
    ├── github_work.pub
    ├── deploy_server
    └── deploy_server.pub

Призначення:

    id_ed25519
        → основний особистий ключ

    github_work
        → ключ для робочого GitHub-акаунта

    deploy_server
        → ключ для підключення до сервера

Створити окремий ключ:

    ssh-keygen -t ed25519 -f ~/.ssh/deploy_server -C "deploy-server"

Важливо: параметр `-f` задає шлях збереження ключа.

Перед створенням переконайся, що файл із таким ім'ям не існує або що ти свідомо хочеш його замінити.

Використати конкретний ключ:

    ssh -i ~/.ssh/deploy_server deploy@192.168.1.100

Для регулярного використання кількох ключів зручніше налаштувати файл `~/.ssh/config`. Це розглядається в наступному розділі:

    02-ssh-configuration

# Копіювання публічного ключа

На Linux можна скопіювати public key у буфер обміну за допомогою доступної в системі утиліти, наприклад `xclip` або `wl-copy`.

Спочатку можна просто вивести ключ:

    cat ~/.ssh/id_ed25519.pub

Потім скопіювати весь рядок, який починається приблизно так:

    ssh-ed25519 AAAAC3...

Для копіювання через `xclip`, якщо він установлений:

    xclip -selection clipboard < ~/.ssh/id_ed25519.pub

Для середовища Wayland, якщо доступний `wl-copy`:

    wl-copy < ~/.ssh/id_ed25519.pub

Якщо утиліти відсутні, їх можна встановити через пакетний менеджер відповідно до своєї системи.

Перед вставленням у вебформу переконайся, що скопійовано саме публічний ключ із розширенням `.pub`.

---

# Резервне копіювання SSH-ключів

Приватні ключі потрібно захищати від втрати та несанкціонованого доступу.

Втрата приватного ключа може означати, що доведеться створити нову пару ключів і повторно налаштувати доступ до всіх серверів та сервісів.

Варіанти захисту:

    - зберігати приватний ключ у захищеному місці;
    - використовувати надійну passphrase;
    - мати контрольований план відновлення доступу;
    - не зберігати незахищені копії ключа в публічних репозиторіях;
    - періодично переглядати, де зареєстрований public key;
    - відкликати ключі, які більше не використовуються.

Не варто копіювати приватний ключ у звичайний репозиторій, навіть якщо репозиторій приватний.

Для робочого середовища потрібно враховувати політики безпеки організації та використовувати дозволені засоби керування секретами.

---

# Втрата або компрометація ключа

Якщо приватний ключ втрачено, але немає ознак компрометації, можна створити новий ключ і налаштувати доступ заново.

Якщо є підозра, що приватний ключ став відомий стороннім особам, потрібно діяти швидше.

Рекомендований порядок:

    1. Створити нову пару ключів на довіреному пристрої.
    2. Додати новий public key до потрібних серверів і сервісів.
    3. Перевірити, що новий ключ працює.
    4. Видалити старий public key з authorized_keys.
    5. Видалити старий ключ із GitHub та інших сервісів,
       де він був зареєстрований.
    6. Перевірити інші місця, де цей ключ міг надавати доступ.
    7. За потреби перевірити журнали входів і виконати
       додаткові заходи реагування на інцидент.

Видалення локального файла приватного ключа не відкликає доступ автоматично.

Доступ потрібно відкликати на кожному сервері або сервісі, який довіряє відповідному public key.

Якщо ключ зберігався в Git-репозиторії, видалення файла з останнього коміту не гарантує усунення секрету з історії. У такому разі ключ слід вважати скомпрометованим і відкликати.

---

# SSH Key Rotation

SSH key rotation — планова заміна SSH-ключів.

Причини:

    - зміна політики безпеки;
    - періодична ротація;
    - зміна пристрою;
    - зміна ролі користувача;
    - підозра на компрометацію;
    - завершення співпраці з працівником.

Загальна схема:

    Old key
        |
        v
    Generate new key
        |
        v
    Install new public key
        |
        v
    Test new connection
        |
        v
    Remove old public key

Не видаляй старий ключ до перевірки нового доступу, якщо це може заблокувати тобі доступ до сервера.

Для критичних серверів ротацію краще виконувати з можливістю альтернативного входу або за затвердженим планом відновлення.

---

# Типові помилки

## 1. Public key не встановлений на сервері

Помилка:

    Permission denied (publickey).

Можлива причина:

    Публічний ключ відсутній у authorized_keys
    відповідного користувача.

Що перевірити:

    - чи правильний користувач;
    - чи скопійовано потрібний public key;
    - чи правильний шлях до authorized_keys;
    - чи дозволена public-key authentication на сервері.

---

## 2. Використовується неправильний приватний ключ

Наприклад:

    ssh -i ~/.ssh/another_key user@192.168.1.100

Але на сервері дозволений інший ключ.

Перевір:

    ssh -v -i ~/.ssh/another_key user@192.168.1.100

Опція `-v` виводить діагностичну інформацію.

---

## 3. Неправильні права приватного ключа

SSH-клієнт може відмовитися використовувати приватний ключ, якщо права доступу надто відкриті.

Перевір:

    ls -l ~/.ssh/id_ed25519

Виправ:

    chmod 600 ~/.ssh/id_ed25519

---

## 4. Приватний ключ захищений passphrase

Якщо приватний ключ зашифрований passphrase, SSH може запросити її під час використання.

Це не обов'язково означає помилку.

Для зручності можна завантажити ключ до агента:

    ssh-add ~/.ssh/id_ed25519

---

## 5. ssh-agent не працює або не доступний

Перевір:

    ssh-add -l

Якщо агент недоступний, перевір налаштування поточного середовища.

За потреби в типовому Linux-сеансі можна запустити:

    eval "$(ssh-agent -s)"

Після цього:

    ssh-add ~/.ssh/id_ed25519

Не запускай додаткові агенти без потреби, якщо система вже керує ними автоматично.

---

## 6. Змінено host key сервера

Повідомлення може містити:

    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

Не ігноруй попередження автоматично.

Спочатку перевір fingerprint сервера через довірений канал.

Якщо зміна підтверджена, можна оновити відповідний запис `known_hosts`.

Для сервера на стандартному SSH-порті:

    ssh-keygen -R 192.168.1.100

Для сервера на нестандартному порту, наприклад `2222`:

    ssh-keygen -R "[192.168.1.100]:2222"

Ці команди видаляють відповідний запис із локального `known_hosts`. Вони не перевіряють, чи новий ключ є справжнім.

Після цього повторно підключайся лише після перевірки нового fingerprint.

---

## 7. Використовується неправильний користувач

Команда:

    ssh root@192.168.1.100

може не працювати, навіть якщо ключ налаштований правильно.

Можливі причини:

    - root login заборонений;
    - ключ дозволений іншому користувачу;
    - користувач не існує;
    - політика сервера обмежує доступ.

Спробуй правильний обліковий запис, якщо він тобі відомий:

    ssh deploy@192.168.1.100

Не вмикай root login лише для того, щоб обійти проблему.

---

## 8. Public key скопійовано неправильно

Публічний ключ зазвичай має бути записаний повністю, в одному рядку.

Перевір локальний файл:

    cat ~/.ssh/id_ed25519.pub

Порівняй його з записом, установленим на сервері або в сервісі.

Не копіюй приватний ключ замість публічного.

---

# SSH Authentication Debugging

Для діагностики проблем автентифікації використовують параметри `-v`, `-vv` та `-vvv`.

Звичайний докладний режим:

    ssh -v user@192.168.1.100

Докладніший режим:

    ssh -vv user@192.168.1.100

Максимальний рівень діагностики:

    ssh -vvv user@192.168.1.100

Ці команди показують інформацію про:

    - завантаження конфігурації;
    - вибір ключів;
    - звернення до ssh-agent;
    - спроби автентифікації;
    - перевірку host key;
    - причини відмови.

Якщо потрібно явно вказати ключ:

    ssh -vvv -i ~/.ssh/id_ed25519 user@192.168.1.100

У виводі шукай рядки на кшталт:

    Offering public key
        → клієнт пропонує public key

    Server accepts key
        → сервер приймає ключ для подальшої автентифікації

    Authenticated to ...
        → автентифікація успішна

Точний текст повідомлень залежить від версії OpenSSH.

Увага: перед публікацією діагностичного виводу переглянь його та прибери адреси, імена користувачів та інші дані, які не потрібно розголошувати.

# SSH Key Security

Основні правила безпеки:

• Використовуй сучасний алгоритм, наприклад Ed25519, якщо його підтримує середовище.

• Захищай приватний ключ passphrase.

• Зберігай приватний ключ із обмеженими правами доступу.

• Не копіюй приватний ключ на сервер для звичайної автентифікації.

• Не передавай приватний ключ іншим користувачам.

• Не зберігай приватний ключ у Git-репозиторії.

• Не вимикай перевірку host key без вагомої причини.

• Не підтверджуй змінений host key без перевірки.

• Використовуй окремі ключі для різних пристроїв або ролей, якщо це спрощує керування доступом.

• Видаляй застарілі public keys із серверів і сервісів.

• Не залишай непотрібні ключі в ssh-agent.

• Не використовуй agent forwarding без розуміння ризиків.

• Дотримуйся принципу least privilege: ключ повинен надавати лише необхідний доступ.

# Практика

## Завдання 1 — перевірити SSH-каталог

Виконай:

    ls -la ~/.ssh/

З'ясуй:

    - чи існує каталог;
    - які файли в ньому є;
    - чи є приватний ключ;
    - чи є відповідний public key;
    - чи існує config;
    - чи існує known_hosts.

Не створюй нову пару ключів, якщо вже є ключ, який використовується для робочого доступу, доки не з'ясуєш його призначення.

---

## Завдання 2 — створити навчальний ключ

Створи окремий ключ для практики:

    ssh-keygen -t ed25519 -f ~/.ssh/linux_practice -C "linux-practice"

Очікувані файли:

    ~/.ssh/linux_practice
    ~/.ssh/linux_practice.pub

Встанови passphrase, якщо це доречно для твого навчального середовища.

---

## Завдання 3 — перевірити fingerprint

Виконай:

    ssh-keygen -lf ~/.ssh/linux_practice.pub

Визнач:

    - алгоритм ключа;
    - fingerprint;
    - коментар.

---

## Завдання 4 — перевірити права

Виконай:

    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/linux_practice
    chmod 644 ~/.ssh/linux_practice.pub

Перевір:

    ls -l ~/.ssh/linux_practice*

Поясни, чому приватний ключ і публічний ключ мають різні вимоги до захисту.

---

## Завдання 5 — додати ключ до ssh-agent

Перевір агент:

    ssh-add -l

Якщо агент доступний, додай ключ:

    ssh-add ~/.ssh/linux_practice

Перевір:

    ssh-add -l

Після завершення практики можна прибрати ключ з агента:

    ssh-add -d ~/.ssh/linux_practice

Якщо агент не запущений, спочатку розберися з його налаштуванням у своєму середовищі.

---

## Завдання 6 — установити public key на тестовий сервер

Якщо маєш доступ до навчального Linux-сервера, виконай:

    ssh-copy-id -i ~/.ssh/linux_practice.pub user@server-address

Заміни `user@server-address` на реальні дані свого тестового сервера.

Після цього перевір:

    ssh -i ~/.ssh/linux_practice user@server-address

Не виконуй ці команди з вигаданою адресою або на чужому сервері без дозволу.

---

## Завдання 7 — перевірити SSH для GitHub

Якщо твій public key уже доданий до GitHub, виконай:

    ssh -T git@github.com

Порівняй результат з очікуваною поведінкою GitHub SSH.

Якщо з'єднання не працює, перевір:

    - чи доданий public key до правильного акаунта;
    - чи використовується потрібний приватний ключ;
    - чи доступний ssh-agent;
    - чи правильно перевірено host key;
    - чи немає проблем із мережею.

---

## Завдання 8 — діагностувати невдале підключення

Виконай для свого тестового сервера:

    ssh -vvv -i ~/.ssh/linux_practice user@server-address

Визнач:

    - який ключ пропонує клієнт;
    - чи приймає сервер ключ;
    - на якому етапі виникає помилка;
    - чи проблема пов'язана з автентифікацією або мережею.

Не намагайся виправляти проблему вимкненням перевірок безпеки.

---

# Типові помилки початківців

❌ Плутати public key і private key.

    id_ed25519
        → private key

    id_ed25519.pub
        → public key

---

❌ Копіювати приватний ключ на сервер.

Для звичайного входу за SSH на сервер потрібно встановити public key, а приватний ключ зберігати на клієнті.

---

❌ Вважати, що passphrase — це пароль серверного користувача.

Passphrase захищає приватний ключ, а пароль облікового запису використовується для іншого способу автентифікації.

---

❌ Думати, що ssh-agent створює ключі.

    ssh-keygen
        → створює ключі

    ssh-agent
        → керує доступом до розблокованих ключів

    ssh-add
        → додає ключі до агента

---

❌ Вважати, що ssh-copy-id створює нову пару ключів.

`ssh-copy-id` зазвичай установлює на сервері вже створений public key.

---

❌ Видаляти приватний ключ, не перевіривши, де він використовується.

Це може призвести до втрати доступу до серверів або сервісів.

---

❌ Ігнорувати повідомлення про зміну host key.

Спочатку потрібно перевірити, чи зміна очікувана.

---

❌ Використовувати надто відкриті права на приватний ключ.

Для звичайного приватного ключа зазвичай підходить:

    chmod 600 ~/.ssh/id_ed25519

---

❌ Вважати, що наявність public key автоматично гарантує доступ.

Доступ також залежить від користувача, налаштувань сервера, прав файлів, мережі та політик автентифікації.

# Головне

• SSH забезпечує зашифроване віддалене з'єднання.

• SSH key pair складається з public key та private key.

• Public key можна встановлювати на сервери й реєструвати в сервісах.

• Private key повинен залишатися під контролем власника.

• `ssh-keygen` створює пару ключів.

• Ed25519 — хороший стандартний вибір для нових ключів на сучасних системах.

• Passphrase додає захист приватному ключу.

• `ssh-agent` допомагає працювати з розблокованими ключами.

• `ssh-add` додає ключі до агента.

• `ssh-copy-id` установлює public key на сервері.

• `authorized_keys` містить дозволені публічні ключі для облікового запису сервера.

• `known_hosts` допомагає перевіряти ідентичність віддалених серверів.

• Для приватного ключа зазвичай використовують права `600`, а для каталогу `~/.ssh/` — `700`.

• SSH-ключ для GitHub і ключ для Linux-сервера можуть бути різними.

• Якщо SSH не працює, перевір ключ, користувача, права доступу, конфігурацію та журнали діагностики.

• Зміну host key потрібно перевіряти, а не ігнорувати.

• Видалення локального приватного ключа не відкликає його public key на серверах.

• У разі компрометації потрібно відкликати старий ключ у всіх системах, які йому довіряють.

• Найважливіша модель SSH-автентифікації:

    Local computer
          |
          | Private key proves possession
          |
          v
    SSH server
          |
          | Checks authorized public key
          |
          v
    Authentication succeeds
    if all required checks pass

• Для практичного Linux-адміністрування потрібно вміти створити SSH-ключ, захистити його, установити public key на тестовий сервер, перевірити підключення та безпечно діагностувати помилки.
