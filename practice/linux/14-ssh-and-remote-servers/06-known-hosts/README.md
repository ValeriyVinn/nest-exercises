# 06. Known Hosts — відомі SSH-сервери

`known_hosts` — це файл, у якому SSH зберігає ідентифікатори (host keys) серверів, до яких користувач підключався раніше.

Його головне призначення — допомогти переконатися, що під час повторного підключення ти звертаєшся до того самого SSH-сервера, а не до іншого сервера, який видає себе за нього.

## 1. Основні поняття

✔ **SSH host key** — криптографічний ключ, який ідентифікує SSH-сервер.

✔ **`known_hosts`** — файл зі збереженими ключами SSH-серверів.

✔ **Fingerprint** — коротке контрольне представлення ключа, яке зручно порівнювати.

✔ **Host verification** — перевірка ідентичності сервера під час SSH-підключення.

✔ **Host key mismatch** — ситуація, коли отриманий ключ сервера відрізняється від раніше збереженого.

✔ **MITM (Man-in-the-Middle)** — атака, за якої зловмисник намагається перехопити з'єднання між клієнтом і сервером.

✔ **`ssh-keygen -F`** — пошук запису про сервер у `known_hosts`.

✔ **`ssh-keygen -R`** — видалення записів сервера з `known_hosts`.

✔ **`StrictHostKeyChecking`** — параметр SSH-клієнта, який визначає, як перевіряти ключі серверів.

## 2. Де зберігаються відомі SSH-сервери

За замовчуванням SSH-клієнт зберігає ключі серверів у файлі:

    ~/.ssh/known_hosts

Наприклад, для користувача `valer` у Linux шлях може виглядати так:

    /home/valer/.ssh/known_hosts

Перевірити наявність файлу:

    ls -l ~/.ssh/known_hosts

Переглянути його вміст:

    cat ~/.ssh/known_hosts

Якщо файл не існує, це не обов'язково означає проблему. Можливо, ти ще не підключався до SSH-серверів із цього облікового запису.

Переглянути вміст каталогу `.ssh`:

    ls -la ~/.ssh

Типові файли в каталозі:

    ~/.ssh/
    ├── id_ed25519          # приватний ключ
    ├── id_ed25519.pub      # відкритий ключ користувача
    ├── known_hosts         # ключі відомих серверів
    └── config              # налаштування SSH-клієнта

Важливо: `known_hosts` — це не файл із паролями та не файл із приватними ключами користувача. Він зберігає дані, потрібні для перевірки серверів.

## 3. Як працює known_hosts

Під час першого підключення до нового SSH-сервера клієнт зазвичай показує повідомлення приблизно такого вигляду:

    The authenticity of host 'example.com (203.0.113.10)' can't be established.
    ED25519 key fingerprint is SHA256:...
    Are you sure you want to continue connecting (yes/no/[fingerprint])?

SSH повідомляє, що ще не має збереженого ключа для цього сервера.

Послідовність роботи:

1. SSH-клієнт встановлює з'єднання із сервером.
2. Сервер надає свій host key.
3. Клієнт перевіряє, чи є відповідний ключ у `known_hosts`.
4. Якщо ключ уже відомий і збігається, перевірка проходить.
5. Якщо ключ невідомий, клієнт залежно від налаштувань може попросити підтвердження.
6. Після підтвердження ключ зазвичай записується в `known_hosts`.
7. Під час наступних підключень SSH порівнює отриманий ключ зі збереженим.

**Важливо:** під час першого підключення не варто автоматично відповідати `yes`, не перевіривши, що fingerprint належить потрібному серверу. Якщо є можливість, звір його з офіційним джерелом або отримай через довірений канал.

Сам факт появи запиту SSH не доводить, що сервер безпечний.

## 4. Перегляд відомих серверів

### 4.1. Прочитати файл

    cat ~/.ssh/known_hosts

Для довгого файлу зручніше:

    less ~/.ssh/known_hosts

У `less`:

- `Space` — наступна сторінка.
- `b` — попередня сторінка.
- `/текст` — пошук.
- `q` — вихід.

### 4.2. Порахувати записи

    wc -l ~/.ssh/known_hosts

Це підраховує рядки, а не обов'язково кількість різних серверів. Один сервер може мати декілька записів — наприклад, для різних портів або типів ключів.

### 4.3. Переглянути перші рядки

    head ~/.ssh/known_hosts

Останні рядки:

    tail ~/.ssh/known_hosts

### 4.4. Чому записи можуть бути незрозумілими

Запис у `known_hosts` може виглядати приблизно так:

    github.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...

У ньому є:

- ім'я хоста або його представлення;
- тип ключа;
- закодований відкритий host key.

SSH може зберігати назви хостів у хешованому вигляді. Тому замість читабельного `github.com` ти можеш побачити рядок, що починається з `|1|`.

Хешування імен хостів у `known_hosts` ускладнює простий перегляд списку серверів, але не замінює перевірку їхніх ключів.

## 5. Пошук конкретного сервера

Для пошуку сервера використовуй `ssh-keygen -F`.

Знайти записи для GitHub:

    ssh-keygen -F github.com

Знайти записи для іншого сервера:

    ssh-keygen -F example.com

Команда шукає ім'я хоста навіть тоді, коли його запис у файлі хешований.

Якщо SSH використовує нестандартний порт, хост зазвичай записується у форматі `[hostname]:port`.

Наприклад:

    ssh-keygen -F '[example.com]:2222'

Для нестандартного порту запис може мати такий вигляд:

    [example.com]:2222 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...

Зверни увагу: квадратні дужки тут є частиною формату імені хоста в `known_hosts`.

## 6. Fingerprint — відбиток ключа сервера

Fingerprint — це коротке криптографічне представлення ключа. Його використовують, щоб перевірити, чи відповідає ключ очікуваному.

Під час першого підключення SSH може показати:

    ED25519 key fingerprint is SHA256:...

Перш ніж довіряти серверу, бажано порівняти fingerprint із даними, отриманими з надійного джерела.

### 6.1. Отримати host key сервера

Команда для отримання публічних ключів сервера:

    ssh-keyscan example.com

Для нестандартного порту:

    ssh-keyscan -p 2222 example.com

`ssh-keyscan` допомагає отримати ключі, які сервер показує під час встановлення SSH-з'єднання.

**Критично важливо:** результат `ssh-keyscan` сам по собі не підтверджує справжність сервера. Якщо зловмисник може перехоплювати з'єднання, він потенційно може підставити інший ключ. Отриманий ключ потрібно перевірити через незалежне довірене джерело.

### 6.2. Обчислити fingerprint отриманого ключа

Зберегти ключі в тимчасовий файл:

    ssh-keyscan example.com > /tmp/example-host-keys

Показати fingerprint ключів:

    ssh-keygen -lf /tmp/example-host-keys

Після перевірки тимчасовий файл можна видалити:

    rm /tmp/example-host-keys

Не використовуй результат `ssh-keyscan` як єдине підтвердження довіри до сервера.

### 6.3. Перевірити ключі, збережені у файлі

    ssh-keygen -lf ~/.ssh/known_hosts

Команда показує fingerprints ключів, які є у файлі.

Для пошуку конкретного сервера спочатку можна виконати:

    ssh-keygen -F github.com

Але для перевірки fingerprint зручніше використовувати `ssh-keygen -lf` із відповідним файлом або попередньо отриманим записом.

## 7. Що означає WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED

Під час підключення може з'явитися повідомлення:

    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

Це означає, що ключ сервера відрізняється від ключа, який SSH зберіг раніше.

Можливі причини:

1. Адміністратор законно замінив host key.
2. Сервер перевстановили або відновили з іншої конфігурації.
3. DNS-ім'я тепер указує на інший сервер.
4. Ти підключаєшся до іншого сервера з тим самим ім'ям.
5. Хтось намагається перехопити з'єднання.

**Не ігноруй це попередження автоматично.** Воно може вказувати на проблему безпеки.

### Правильний алгоритм перевірки

1. Зупинися та не вводь пароль або інші секретні дані.
2. Перевір, чи повідомляв адміністратор про заміну ключів.
3. Звір новий fingerprint із надійним джерелом.
4. Переконайся, що підключаєшся до правильного хоста та порту.
5. Лише після підтвердження причини онови запис у `known_hosts`.

Не видаляй запис лише для того, щоб прибрати попередження, не з'ясувавши причину зміни ключа.

## 8. Видалення запису про сервер

Після підтвердженої заміни ключа можна видалити старий запис за допомогою `ssh-keygen -R`.

Для звичайного хоста:

    ssh-keygen -R example.com

Для сервера на нестандартному порту:

    ssh-keygen -R '[example.com]:2222'

Команда видаляє відповідні записи з `known_hosts`. Залежно від ситуації вона також може створити резервну копію файлу з розширенням `.old`.

Після цього під час наступного підключення SSH сприйматиме сервер як невідомий і знову запропонує перевірити його ключ.

Перед підтвердженням нового ключа обов'язково звір його fingerprint.

### 8.1. Перевірити результат

    ssh-keygen -F example.com

Якщо відповідного запису більше немає, команда не знайде його.

### 8.2. Чого не варто робити

Не видаляй увесь `known_hosts` лише через проблему з одним сервером:

    rm ~/.ssh/known_hosts

Це прибере збережені перевірки для всіх серверів у цьому файлі. Наступні підключення можуть вимагати повторної перевірки, а користувачеві буде складніше помітити несподівану зміну ключа.

Краще видаляти лише конкретний підтверджений застарілий запис:

    ssh-keygen -R example.com

## 9. Налаштування StrictHostKeyChecking

Параметр `StrictHostKeyChecking` визначає, як SSH поводиться з невідомими або зміненими ключами серверів.

Типові значення:

- `yes` — відхиляти невідомі ключі та ключі, що не збігаються зі збереженими.
- `ask` — запитувати підтвердження для невідомих ключів; це типовий режим у багатьох конфігураціях OpenSSH.
- `accept-new` — автоматично приймати нові ключі, але відхиляти змінені ключі.
- `no` — послаблює перевірку нових ключів; конкретна поведінка залежить від версії OpenSSH та інших параметрів.

### 9.1. Задати параметр для одного підключення

Строга перевірка:

    ssh -o StrictHostKeyChecking=yes user@example.com

Режим автоматичного прийняття нових ключів, якщо це усвідомлений вибір:

    ssh -o StrictHostKeyChecking=accept-new user@example.com

Для звичайної роботи та навчання не варто вимикати перевірку host key без чіткої причини.

### 9.2. Налаштувати параметр у конфігурації

Відкрий файл:

    nano ~/.ssh/config

Наприклад:

    Host *
        StrictHostKeyChecking ask

Це задає режим запиту для всіх хостів, якщо його не перевизначає інше правило конфігурації.

Параметр `Host *` застосовується широко. Якщо потрібно налаштувати поведінку лише для одного сервера, краще створити окремий блок `Host`.

Наприклад:

    Host myserver
        HostName example.com
        User deploy
        StrictHostKeyChecking yes

Тоді підключення виконується командою:

    ssh myserver

У цьому прикладі `myserver` — псевдонім, визначений у `~/.ssh/config`.

## 10. Перевірка конфігурації SSH

Щоб побачити ефективні параметри для конкретного хоста:

    ssh -G example.com

Щоб відфільтрувати налаштування, пов'язані з host key:

    ssh -G example.com | grep -i 'stricthostkeychecking\|userknownhostsfile\|globalknownhostsfile'

Це допомагає з'ясувати, який режим перевірки та які файли `known_hosts` використовуються.

У SSH можуть бути як користувацькі, так і системні файли відомих хостів. Їхні шляхи та налаштування можуть залежати від дистрибутива й конфігурації OpenSSH.

## 11. Кілька важливих особливостей

### 11.1. Один сервер може мати кілька ключів

SSH-сервер може підтримувати кілька алгоритмів host key, наприклад:

- Ed25519;
- ECDSA;
- RSA.

Тому в `known_hosts` можуть бути декілька записів для одного хоста.

### 11.2. Один хост може мати різні записи для різних портів

Наприклад:

    example.com

і

    [example.com]:2222

Це можуть бути різні SSH-служби або різні сервери. Перевіряй ключ для того порту, до якого підключаєшся.

### 11.3. Можуть використовуватися хешовані імена

Якщо `HashKnownHosts` увімкнено, назви серверів можуть зберігатися у хешованому вигляді.

Це не означає, що ключ зашифрований або що перевірка не працює. SSH усе одно може знаходити відповідні записи за допомогою:

    ssh-keygen -F example.com

### 11.4. `known_hosts` і `authorized_keys` — різні файли

`known_hosts` зберігає ключі серверів, яким клієнт уже довіряє.

`authorized_keys` на сервері містить відкриті ключі клієнтів, яким дозволено автентифікуватися відповідним обліковим записом.

Не плутай їх:

    ~/.ssh/known_hosts

    ~/.ssh/authorized_keys

Зазвичай перший файл розташований на клієнті, а другий — на сервері, в домашньому каталозі користувача, якому дозволено вхід за ключем.

## 12. Практика на Ubuntu

### Вправа 1. Перевірити наявність файлу

    ls -la ~/.ssh
    test -f ~/.ssh/known_hosts && echo "known_hosts exists" || echo "known_hosts does not exist"

Мета: зрозуміти, чи є файл із відомими серверами.

### Вправа 2. Переглянути збережені ключі

    cat ~/.ssh/known_hosts

Якщо файл містить багато записів, використовуй:

    less ~/.ssh/known_hosts

Мета: побачити структуру записів і зрозуміти, що в них зберігається.

### Вправа 3. Знайти запис GitHub

    ssh-keygen -F github.com

Якщо ти раніше підключався до GitHub через SSH, запис може бути вже збережений.

Якщо запису немає, це не обов'язково проблема: можливо, ти ще не підключався до нього з цього облікового запису або використовуєш інший файл конфігурації.

### Вправа 4. Перевірити fingerprint

    ssh-keygen -lf ~/.ssh/known_hosts

Мета: побачити fingerprints збережених ключів.

Для точного порівняння fingerprint конкретного сервера потрібно визначити відповідний запис і порівняти його з fingerprint, отриманим через довірене джерело.

### Вправа 5. Перевірити конфігурацію

    ssh -G github.com | grep -i 'stricthostkeychecking\|userknownhostsfile'

Мета: з'ясувати, який режим перевірки й який файл відомих хостів використовуються для цього підключення.

### Вправа 6. Безпечно дослідити `ssh-keyscan`

    ssh-keyscan github.com

Мета: побачити, як SSH-сервер передає свої відкриті host keys.

Не додавай результат до `known_hosts` і не довіряй йому автоматично. Для довіри fingerprint потрібно перевірити незалежно.

### Вправа 7. Навчитися знаходити застарілі записи

Використовуй команду пошуку, не видаляючи нічого:

    ssh-keygen -F example.com

Для нестандартного порту:

    ssh-keygen -F '[example.com]:2222'

Мета: навчитися знаходити записи перед тим, як виконувати будь-які зміни.

## 13. Типові помилки

### Помилка 1. Бездумно підтверджувати новий сервер

Причина: користувач не перевіряє, кому належить fingerprint.

Правильно: звірити fingerprint через надійне джерело перед підтвердженням.

### Помилка 2. Видаляти запис після будь-якого попередження

Причина: бажання швидко усунути повідомлення про зміну ключа.

Правильно: спочатку з'ясувати, чому ключ змінився, і лише потім видаляти застарілий запис.

### Помилка 3. Плутати ключ користувача з ключем сервера

Причина: плутанина між `id_ed25519`, `id_ed25519.pub` та `known_hosts`.

Правильно:

- `id_ed25519` — приватний ключ користувача;
- `id_ed25519.pub` — відкритий ключ користувача;
- `known_hosts` — збережені ключі SSH-серверів.

### Помилка 4. Вважати `ssh-keyscan` перевіркою справжності сервера

Причина: команда успішно отримує ключ, і користувач припускає, що він справжній.

Правильно: `ssh-keyscan` лише отримує ключ. Його fingerprint потрібно звірити незалежно.

### Помилка 5. Видаляти весь `known_hosts`

Причина: спроба виправити помилку для одного сервера.

Правильно: після перевірки причини використовувати точкове видалення:

    ssh-keygen -R example.com

### Помилка 6. Вимикати перевірку host key для зручності

Причина: бажання позбутися попереджень.

Правильно: залишати перевірку ввімкненою та розбиратися з невідомими або зміненими ключами.

## 14. Що потрібно запам'ятати

- `~/.ssh/known_hosts` зберігає ключі SSH-серверів, які клієнт уже бачив.
- Host key допомагає перевірити ідентичність сервера.
- Fingerprint — коротке представлення ключа, яке можна порівняти з довіреним значенням.
- Під час першого підключення потрібно перевірити fingerprint, якщо є можливість.
- `ssh-keygen -F hostname` шукає запис сервера.
- `ssh-keygen -R hostname` видаляє запис сервера з `known_hosts`.
- `ssh-keyscan` отримує ключі, але не підтверджує їхню справжність.
- `StrictHostKeyChecking` керує поведінкою перевірки ключів.
- Попередження `REMOTE HOST IDENTIFICATION HAS CHANGED` не можна ігнорувати без перевірки.
- `known_hosts` не є аналогом `authorized_keys`.
- Не видаляй усі записи лише для того, щоб прибрати одне попередження.

## 15. Рівні володіння

### Core

- Знаю призначення `known_hosts`.
- Можу знайти файл у `~/.ssh`.
- Розумію, що таке host key і fingerprint.
- Розумію, чому не можна бездумно підтверджувати невідомий ключ.

### Junior

- Умію шукати записи через `ssh-keygen -F`.
- Умію переглядати fingerprints через `ssh-keygen -lf`.
- Розумію різницю між `known_hosts` і `authorized_keys`.
- Умію перевірити ефективні параметри SSH за допомогою `ssh -G`.
- Знаю, як видалити конкретний запис після перевірки причини зміни ключа.

### Middle

- Умію аналізувати повідомлення про зміну host key.
- Розумію ризики атаки Man-in-the-Middle.
- Можу пояснити, чому `ssh-keyscan` не є самостійним доказом справжності сервера.
- Умію працювати з кількома портами та хешованими записами.
- Розумію вплив `StrictHostKeyChecking` на безпеку підключення.

### Senior

- Можу спланувати безпечну ротацію host keys.
- Умію організувати перевірку fingerprints через довірений канал.
- Розумію особливості керування host keys у великих інфраструктурах.
- Можу налаштувати політику перевірки ключів відповідно до вимог безпеки.

## 16. Мінішпаргалка

    # Переглянути файл
    cat ~/.ssh/known_hosts

    # Переглянути fingerprints усіх ключів у файлі
    ssh-keygen -lf ~/.ssh/known_hosts

    # Знайти запис сервера
    ssh-keygen -F github.com

    # Знайти запис сервера на нестандартному порту
    ssh-keygen -F '[example.com]:2222'

    # Отримати відкриті host keys сервера
    ssh-keyscan example.com

    # Обчислити fingerprints ключів із файлу
    ssh-keygen -lf /tmp/example-host-keys

    # Видалити запис після перевірки причини зміни ключа
    ssh-keygen -R example.com

    # Переглянути ефективні налаштування SSH
    ssh -G example.com

    # Підключитися зі строгою перевіркою ключа
    ssh -o StrictHostKeyChecking=yes user@example.com

## 17. Головне правило безпеки

**`known_hosts` допомагає SSH виявляти зміну ідентичності сервера, але сам по собі не гарантує, що перший отриманий ключ справжній.**

Під час першого підключення перевіряй fingerprint через довірене джерело. Якщо ключ раптово змінився, спочатку з'ясуй причину, а вже потім оновлюй `known_hosts`.
