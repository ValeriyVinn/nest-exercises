# 03. Remote Login — віддалений вхід через SSH

## 1. Що таке Remote Login

**Remote Login** — це підключення до іншого комп'ютера через мережу для роботи з його терміналом, файлами та програмами.

У Linux для цього найчастіше використовують **SSH (Secure Shell)** — протокол, який забезпечує зашифроване з'єднання між клієнтом і сервером.

Наприклад, ти працюєш на своєму ноутбуці з Ubuntu, але хочеш увійти на віддалений Linux-сервер, щоб переглянути файли, запустити програму або керувати вебсервером.

Замість фізичного доступу до сервера ти виконуєш команду:

    ssh valeriy@server.example.com

Після успішної автентифікації отримуєш віддалений термінал.

### Основні поняття

✔ **Local machine** — твій комп'ютер, з якого виконується підключення.

✔ **Remote host** — віддалений комп'ютер або сервер.

✔ **SSH client** — програма на твоєму комп'ютері, яка встановлює SSH-з'єднання.

✔ **SSH server** — служба на віддаленому комп'ютері, яка приймає SSH-з'єднання.

✔ **Remote login** — вхід у систему віддаленого комп'ютера під певним користувачем.

✔ **Authentication** — перевірка того, чи маєш ти право підключитися.

✔ **Hostname** — доменне ім'я або адреса сервера.

✔ **IP address** — мережева адреса комп'ютера.

✔ **Port** — мережевий порт, на якому SSH-сервер приймає з'єднання. Типовий порт SSH — `22`.

✔ **Remote shell** — командна оболонка, яка запускається на віддаленому комп'ютері.

✔ **Session** — активне SSH-з'єднання, протягом якого ти працюєш із віддаленою системою.

### Що потрібно запам'ятати

SSH дозволяє працювати з віддаленим Linux-комп'ютером так, ніби ти відкрив його термінал локально.

Однак команди після підключення зазвичай виконуються **на віддаленому комп'ютері**, а не на твоєму локальному.

## 2. Як працює SSH-підключення

Типовий процес підключення складається з кількох етапів:

1. SSH-клієнт знаходить сервер за доменом або IP-адресою.
2. Клієнт встановлює TCP-з'єднання з SSH-портом сервера.
3. Клієнт і сервер узгоджують параметри захищеного з'єднання.
4. Клієнт перевіряє ключ хоста сервера.
5. Сервер перевіряє особу користувача.
6. Після успішної автентифікації відкривається віддалена сесія.

Схематично:

    Твій комп'ютер
        |
        | ssh user@server.example.com
        |
        v
    SSH-сервер на віддаленому комп'ютері
        |
        | перевірка автентифікації
        |
        v
    Віддалений термінал

### Що захищає SSH

SSH шифрує передавання даних між клієнтом і сервером.

Це допомагає захистити від перехоплення:

- команди, які ти вводиш;
- текст, який повертає сервер;
- дані автентифікації;
- файли, що передаються через SSH-протоколи.

Проте SSH не гарантує безпеку, якщо ти підключаєшся до підробленого сервера, використовуєш скомпрометований ключ або працюєш на зараженому комп'ютері.

### SSH і Telnet

| Характеристика | SSH | Telnet |
|---|---|---|
| Шифрування | Так | Ні, зазвичай відкритий текст |
| Безпечний віддалений вхід | Так, за правильного налаштування | Ні для звичайного використання через недовірену мережу |
| Типовий порт | `22` | `23` |
| Сучасне використання | Адміністрування серверів | Переважно спеціальні діагностичні випадки |

**Для звичайного віддаленого адміністрування Linux використовуй SSH, а не Telnet.**

## 3. SSH-клієнт і SSH-сервер

SSH складається з двох основних частин.

### SSH-клієнт

Клієнт запускається на твоєму комп'ютері.

Основна команда:

    ssh

Перевірити наявність SSH-клієнта:

    ssh -V

Приклад результату:

    OpenSSH_10.x, OpenSSL ...

Точна версія залежить від установленої системи.

Якщо команда `ssh` не знайдена, в Ubuntu можна встановити клієнт:

    sudo apt update
    sudo apt install openssh-client

### SSH-сервер

SSH-сервер приймає вхідні підключення. У Linux його зазвичай реалізує пакет `openssh-server`, а службу називають `ssh` або `sshd`, залежно від дистрибутива та способу запуску.

На Ubuntu перевірити статус служби:

    systemctl status ssh

Якщо потрібно встановити сервер:

    sudo apt update
    sudo apt install openssh-server

Запустити службу:

    sudo systemctl start ssh

Увімкнути автоматичний запуск після перезавантаження:

    sudo systemctl enable ssh

Перевірити, чи служба слухає порт:

    sudo ss -tlnp | grep ssh

**Важливо:** для підключення до чужого сервера не потрібно встановлювати SSH-сервер на власному комп'ютері. SSH-клієнта достатньо.

## 4. Перше SSH-підключення

Загальний синтаксис:

    ssh USER@HOST

Де:

- `USER` — ім'я користувача на віддаленому комп'ютері;
- `HOST` — доменне ім'я або IP-адреса віддаленого комп'ютера.

Наприклад:

    ssh valeriy@server.example.com

Або через IP-адресу:

    ssh valeriy@192.0.2.10

Адреси `192.0.2.10` та домени `example.com` у прикладах використовуються як документаційні. Для реального підключення потрібна адреса твого сервера.

### Підключення без зазначення користувача

    ssh server.example.com

У цьому випадку SSH зазвичай використовує ім'я поточного локального користувача як ім'я віддаленого користувача.

Наприклад, якщо локально ти увійшов як `valeriy`, команда спробує підключитися як `valeriy` на віддаленому сервері.

### Підключення через нестандартний порт

Якщо SSH-сервер використовує порт, відмінний від `22`:

    ssh -p 2222 valeriy@server.example.com

Параметр `-p` задає порт віддаленого SSH-сервера.

Не плутай його з параметром `-P` у деяких інших мережевих утилітах: для команди `ssh` потрібен саме малий `-p`.

## 5. Перше підключення та ключ хоста

Під час першого підключення до сервера SSH може показати повідомлення приблизно такого вигляду:

    The authenticity of host 'server.example.com' can't be established.
    Are you sure you want to continue connecting (yes/no/[fingerprint])?

Це означає, що SSH ще не має збереженого ключа хоста для цієї адреси.

### Що таке host key

**Host key** — криптографічний ключ, за допомогою якого сервер підтверджує свою ідентичність.

Це не те саме, що твій приватний ключ користувача.

SSH-клієнт зберігає відомості про перевірені сервери у файлі:

    ~/.ssh/known_hosts

Після першого успішного підтвердження SSH може порівнювати ключ під час наступних підключень.

### Як правильно діяти

1. Перевір адресу сервера.
2. Якщо сервер важливий, отримай його fingerprint через надійний незалежний канал — наприклад, від адміністратора або з офіційної панелі керування.
3. Порівняй fingerprint із тим, який показує SSH.
4. Підтверджуй з'єднання лише тоді, коли впевнений, що це правильний сервер.

Не підтверджуй ключ автоматично для незнайомих серверів.

### Що означає попередження про зміну ключа

Приклад:

    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

Це може означати:

- сервер перевстановили;
- його SSH host key законно змінився;
- IP-адреса тепер належить іншому серверу;
- хтось намагається перехопити з'єднання.

Не ігноруй попередження. Спочатку перевір причину зміни ключа через довірений канал.

Після підтвердження законної зміни старий запис можна видалити:

    ssh-keygen -R server.example.com

Якщо сервер використовував нестандартний порт:

    ssh-keygen -R '[server.example.com]:2222'

Після цього підключись повторно та перевір новий fingerprint перед підтвердженням.

## 6. Автентифікація: пароль і SSH-ключі

SSH підтримує різні методи автентифікації.

### Автентифікація паролем

Якщо сервер дозволяє парольну автентифікацію, SSH може попросити пароль віддаленого користувача.

Наприклад:

    ssh valeriy@server.example.com

Після запиту пароля введи пароль облікового запису на віддаленому сервері.

Під час введення пароль зазвичай не відображається в терміналі. Це нормально.

**Пароль віддаленого користувача не обов'язково збігається з паролем твого локального Linux-користувача.**

### Автентифікація за ключем

Для SSH можна використовувати пару криптографічних ключів:

- **Private key** — приватний ключ, який потрібно зберігати в безпеці.
- **Public key** — відкритий ключ, який можна розмістити на сервері.

Типові файли:

    ~/.ssh/id_ed25519
    ~/.ssh/id_ed25519.pub

Приватний ключ не можна передавати іншим людям або копіювати на сервер без особливої потреби.

Відкритий ключ зазвичай додають до файлу на сервері:

    ~/.ssh/authorized_keys

Докладніше створення ключів розглядається в темі про SSH-ключі.

### Чим відрізняються `known_hosts` і `authorized_keys`

| Файл | Де зазвичай розташований | Призначення |
|---|---|---|
| `known_hosts` | На клієнті | Зберігає відомості про сервери, до яких підключався клієнт |
| `authorized_keys` | На сервері | Містить відкриті ключі, яким дозволено входити під відповідним користувачем |
| `id_ed25519` | На клієнті | Приватний ключ користувача |
| `id_ed25519.pub` | На клієнті | Відповідний відкритий ключ |

Ці файли виконують різні функції — не плутай їх.

## 7. Робота у віддаленій сесії

Після успішного підключення ти працюєш у терміналі віддаленого комп'ютера.

Наприклад:

    ssh valeriy@server.example.com

На віддаленому сервері можна виконувати звичайні Linux-команди:

    whoami
    hostname
    pwd
    ls -la
    df -h
    free -h

Пояснення:

- `whoami` — показує поточного користувача;
- `hostname` — показує ім'я комп'ютера;
- `pwd` — показує поточний каталог;
- `ls -la` — показує файли, зокрема приховані;
- `df -h` — показує використання файлових систем;
- `free -h` — показує використання пам'яті.

Щоб зрозуміти, на якому комп'ютері виконується команда, використовуй:

    hostname

Порівняй результат локально та у віддаленій сесії.

### Як завершити віддалену сесію

Введи:

    exit

Або натисни `Ctrl + D`, якщо це підтримує поточна оболонка.

Після завершення з'єднання ти повернешся до локального термінала.

### Чи працює віддалена сесія після закриття термінала

Звичайна інтерактивна SSH-сесія завершується при закритті з'єднання.

Проте окремі процеси можуть продовжувати працювати, якщо їх запущено з відповідним керуванням сесіями або фоновим виконанням, наприклад через `tmux`, `screen` чи службу `systemd`.

Не припускай, що будь-яка програма автоматично продовжить роботу після розриву SSH.

## 8. Виконання окремої команди на сервері

Не обов'язково відкривати інтерактивний термінал. SSH може виконати одну команду на віддаленому комп'ютері.

Синтаксис:

    ssh USER@HOST COMMAND

Приклад:

    ssh valeriy@server.example.com hostname

Виконай команду:

    ssh valeriy@server.example.com 'ls -la'

Перевір користувача:

    ssh valeriy@server.example.com whoami

Переглянь вільне місце:

    ssh valeriy@server.example.com 'df -h'

У цих прикладах команда виконується на віддаленому сервері, а її результат повертається до локального термінала.

### Для чого це потрібно

- швидко перевірити стан сервера;
- автоматизувати адміністративні операції;
- запускати команди в Bash-скриптах;
- отримувати інформацію без відкриття інтерактивної сесії.

### Увага до лапок

Команди з лапками потребують уважності. Зазвичай локальна оболонка спочатку обробляє введений рядок, а потім команда передається на віддалену сторону.

Наприклад:

    ssh valeriy@server.example.com 'echo "$HOME"'

У типовому випадку `$HOME` усередині одинарних лапок не розгортається локально, а розгортається на віддаленому сервері.

Це корисно, але складні команди з лапками варто тестувати окремо.

## 9. Інтерактивний і неінтерактивний SSH

### Інтерактивне підключення

    ssh valeriy@server.example.com

Ти отримуєш віддалений термінал і можеш вводити команди вручну.

### Неінтерактивне підключення

    ssh valeriy@server.example.com 'uptime'

SSH виконує одну команду та зазвичай завершує з'єднання після її виконання.

### Пакетний режим

Параметр `-T` вимикає виділення псевдотермінала:

    ssh -T valeriy@server.example.com

Це не те саме, що вимкнення самого SSH-з'єднання. Такий режим корисний для автоматизації, передачі даних і деяких операцій Git.

Для сценаріїв автоматизації існує також:

    ssh -o BatchMode=yes valeriy@server.example.com 'uptime'

`BatchMode=yes` вимикає інтерактивні запити на кшталт запиту пароля користувача або підтвердження passphrase. Якщо потрібна автентифікація не може пройти без введення даних, команда завершиться помилкою, а не чекатиме на введення.

## 10. Підключення під іншим користувачем

Загальний формат:

    ssh USER@HOST

Наприклад:

    ssh deploy@server.example.com

Тут `deploy` — користувач на віддаленому сервері.

На одному сервері можуть існувати різні облікові записи:

    ssh admin@server.example.com
    ssh deploy@server.example.com
    ssh student@server.example.com

Кожен користувач має власні права доступу та домашній каталог.

**Не використовуй `root` для звичайної щоденної роботи без потреби.** Краще підключатися під окремим користувачем з обмеженими правами, а адміністративні команди виконувати через `sudo`, якщо це дозволено.

Наприклад:

    ssh deploy@server.example.com
    sudo systemctl status nginx

Можливість використовувати `sudo` залежить від налаштувань облікового запису на сервері.

## 11. SSH-підключення за IP-адресою

Якщо відоме IP сервера, можна підключатися без доменного імені:

    ssh valeriy@192.0.2.10

IP-адреси бувають IPv4 та IPv6.

Приклад IPv6:

    ssh valeriy@2001:db8::10

IPv6-адреса в цьому прикладі документаційна. У деяких командах, де потрібно розділити адресу та порт, синтаксис IPv6 має додаткові нюанси, але в стандартній команді `ssh USER@IPv6_ADDRESS` окреме зазначення порту через `-p` залишається найпростішим способом.

### Що перевірити, якщо підключення не працює

- чи правильна адреса;
- чи доступний сервер через мережу;
- чи запущений SSH-сервер;
- чи правильний порт;
- чи дозволяє firewall вхідні з'єднання;
- чи існує вказаний користувач;
- чи дозволений обраний метод автентифікації.

Перевірка мережевої доступності не завжди гарантує, що SSH-порт доступний: сервер може відповідати на ICMP, але блокувати TCP-порт `22`, або навпаки.

## 12. Корисні параметри команди `ssh`

### Підключення на певний порт

    ssh -p 2222 valeriy@server.example.com

### Використання конкретного приватного ключа

    ssh -i ~/.ssh/id_ed25519 valeriy@server.example.com

### Детальна діагностика

    ssh -v valeriy@server.example.com

Більш докладний рівень:

    ssh -vvv valeriy@server.example.com

### Використання іншого конфігураційного файлу

    ssh -F ~/.ssh/config valeriy@server.example.com

### Задання параметра лише для однієї команди

    ssh -o ConnectTimeout=10 valeriy@server.example.com

Це обмежує час очікування встановлення з'єднання значенням у секундах.

### Виконання команди без інтерактивного термінала

    ssh -T valeriy@server.example.com

### Коротка таблиця

| Параметр | Призначення |
|---|---|
| `-p PORT` | Задати порт сервера |
| `-i FILE` | Використати конкретний приватний ключ |
| `-v` | Показати діагностичну інформацію |
| `-vvv` | Увімкнути докладну діагностику |
| `-F FILE` | Використати інший конфігураційний файл |
| `-o OPTION=VALUE` | Задати параметр SSH для одного запуску |
| `-T` | Не виділяти псевдотермінал |
| `-t` | Примусово запросити псевдотермінал |
| `-N` | Не запускати віддалену команду; корисно для тунелювання |
| `-J HOST` | Підключитися через проміжний SSH-хост |

Не потрібно запам'ятовувати всі параметри відразу. На початку достатньо впевнено користуватися `ssh`, `-p`, `-i` та `-v`.

## 13. SSH і передавання файлів

SSH використовується не тільки для віддаленого термінала. На його основі працюють інструменти передавання файлів.

### SCP

Скопіювати локальний файл на сервер:

    scp ./notes.txt valeriy@server.example.com:/home/valeriy/

Скопіювати файл із сервера на локальний комп'ютер:

    scp valeriy@server.example.com:/home/valeriy/notes.txt ./

Скопіювати каталог рекурсивно:

    scp -r ./project valeriy@server.example.com:/home/valeriy/

### SFTP

Запустити інтерактивний клієнт передавання файлів:

    sftp valeriy@server.example.com

Усередині SFTP можна використовувати команди на кшталт:

    pwd
    ls
    lpwd
    lls
    get notes.txt
    put notes.txt
    exit

У SFTP `pwd` та `ls` стосуються віддаленої сторони, а `lpwd` та `lls` — локальної.

### RSYNC

Для синхронізації каталогів часто використовують `rsync` через SSH:

    rsync -av ./project/ valeriy@server.example.com:/home/valeriy/project/

Зворотна синхронізація:

    rsync -av valeriy@server.example.com:/home/valeriy/project/ ./project/

Увага: напрямок копіювання та кінцевий `/` у шляхах `rsync` мають значення. Перед синхронізацією важливих даних можна перевірити заплановані зміни через `--dry-run`.

    rsync -av --dry-run ./project/ valeriy@server.example.com:/home/valeriy/project/

## 14. Віддалений доступ до Linux із Windows

SSH-клієнт доступний і у Windows, тому не обов'язково відкривати Linux-термінал, щоб підключитися до сервера.

У Windows Terminal або PowerShell можна виконати:

    ssh valeriy@server.example.com

У Git Bash також можна використовувати SSH, якщо клієнт доступний у середовищі.

Приклад підключення до нестандартного порту:

    ssh -p 2222 valeriy@server.example.com

Приклад використання ключа:

    ssh -i ~/.ssh/id_ed25519 valeriy@server.example.com

Шлях до ключа залежить від середовища. У Windows PowerShell типовий каталог користувача має вигляд:

    C:\Users\USERNAME\.ssh\

У Git Bash шлях до того самого каталогу зазвичай можна записати як:

    ~/.ssh/

Не плутай локальне середовище, у якому запускається SSH-клієнт, із віддаленою операційною системою. Твій клієнт може працювати у Windows, а сервер — в Ubuntu або іншому Linux-дистрибутиві.

## 15. Типові помилки під час Remote Login

### `Could not resolve hostname`

Приклад:

    ssh: Could not resolve hostname server.example.com

Можливі причини:

- помилка в доменному імені;
- неправильний псевдонім SSH;
- проблема з DNS;
- неправильний запис у конфігурації.

Перевір адресу та конфігурацію.

### `Connection refused`

Приклад:

    ssh: connect to host server.example.com port 22: Connection refused

Можливі причини:

- SSH-сервер не запущений;
- сервер не слухає вказаний порт;
- підключення відхиляється на рівні сервера або мережевого обладнання.

Якщо маєш доступ до сервера іншим способом, перевір службу:

    sudo systemctl status ssh

### `Connection timed out`

Можливі причини:

- сервер недоступний через мережу;
- неправильна адреса;
- firewall блокує з'єднання;
- використовується неправильний порт;
- мережевий маршрут не працює.

### `Permission denied (publickey)`

Можливі причини:

- використано не той приватний ключ;
- відповідний відкритий ключ не додано на сервер;
- неправильне ім'я віддаленого користувача;
- сервер не дозволяє обраний метод автентифікації;
- неправильні права доступу до ключів або каталогів.

Перевір конкретний ключ:

    ssh -i ~/.ssh/id_ed25519 -v valeriy@server.example.com

Не надсилай приватний ключ іншим людям під час діагностики.

### `REMOTE HOST IDENTIFICATION HAS CHANGED`

Можлива зміна ключа сервера або ризик підміни хоста.

Не вимикай перевірку ключа лише для того, щоб прибрати повідомлення. Спочатку перевір fingerprint сервера.

### `No route to host`

Можливі причини:

- відсутній мережевий маршрут;
- сервер або мережевий сегмент недоступний;
- мережеве обладнання блокує трафік.

### Як діагностувати послідовно

    ssh -v valeriy@server.example.com
    ssh -vvv valeriy@server.example.com

Докладний журнал допомагає з'ясувати, на якому етапі зупиняється підключення.

Пам'ятай: помилка підключення не завжди означає проблему з паролем. Спочатку потрібно зрозуміти, чи взагалі вдалося встановити мережеве з'єднання.

## 16. Безпека віддаленого входу

Remote Login надає доступ до іншої системи, тому важливо дотримуватися базових правил безпеки.

### Основні правила

✔ Використовуй SSH замість незашифрованих протоколів віддаленого входу.

✔ Перевіряй ключ хоста під час першого підключення.

✔ Не ігноруй попередження про зміну ключа хоста.

✔ Не передавай приватні SSH-ключі іншим людям.

✔ Використовуй окремі облікові записи з необхідними правами.

✔ Не підключайся під `root` без реальної потреби.

✔ Використовуй парольну фразу для захисту приватного ключа, якщо це відповідає твоєму сценарію.

✔ На серверах із зовнішнім доступом налаштовуй firewall та автентифікацію відповідно до потреб.

✔ Не вимикай перевірку host key заради швидкого усунення помилки.

✔ Не вводь паролі або ключі в команди так, щоб вони могли потрапити до історії оболонки чи журналів.

### Чому небезпечно ігнорувати перевірку ключа

Якщо клієнт не перевіряє ідентичність сервера, він може встановити зашифроване з'єднання не з тим комп'ютером, до якого ти хотів підключитися.

Саме тому не варто глобально встановлювати небезпечні параметри на кшталт `StrictHostKeyChecking no` без обґрунтованої потреби.

### Що варто вивчати далі

- створення SSH-ключів;
- використання `ssh-agent`;
- файл `~/.ssh/config`;
- обмеження доступу до SSH-сервера;
- firewall;
- журнали автентифікації;
- тунелювання та проміжні сервери.

## 17. Практика: підключення до власного сервера

Виконуй цю практику, коли маєш власний Linux-сервер або тестову віртуальну машину з увімкненим SSH.

### Крок 1. Перевір SSH-клієнт

    ssh -V

### Крок 2. Дізнайся ім'я локального комп'ютера

    hostname

### Крок 3. Підключись до сервера

    ssh USER@SERVER

Заміни `USER` та `SERVER` на справжні дані свого тестового сервера.

### Крок 4. Перевір віддалену систему

    whoami
    hostname
    pwd
    uname -a

### Крок 5. Виконай окрему команду

    ssh USER@SERVER 'uptime'

### Крок 6. Скопіюй тестовий файл

Створи локальний файл:

    echo "SSH practice" > ssh-test.txt

Передай його на сервер:

    scp ssh-test.txt USER@SERVER:/tmp/

Перевір файл на сервері:

    ssh USER@SERVER 'cat /tmp/ssh-test.txt'

### Крок 7. Заверши сесію

    exit

### Крок 8. Перевір діагностику

    ssh -v USER@SERVER

Знайди в журналі інформацію про встановлення з'єднання, перевірку ключа хоста та автентифікацію.

## 20. Мінішпаргалка

    # Перевірити SSH-клієнт
    ssh -V

    # Підключитися до сервера
    ssh USER@HOST

    # Підключитися через нестандартний порт
    ssh -p 2222 USER@HOST

    # Використати конкретний приватний ключ
    ssh -i ~/.ssh/id_ed25519 USER@HOST

    # Увімкнути діагностику
    ssh -v USER@HOST

    # Виконати одну команду на сервері
    ssh USER@HOST 'hostname'

    # Скопіювати файл на сервер
    scp ./file.txt USER@HOST:/tmp/

    # Скопіювати файл із сервера
    scp USER@HOST:/tmp/file.txt ./

    # Відкрити SFTP-сесію
    sftp USER@HOST

    # Видалити застарілий запис host key
    # Використовувати лише після перевірки зміни ключа
    ssh-keygen -R HOST

    # Завершити сесію
    exit

## 21. Головні правила

1. SSH забезпечує зашифроване віддалене підключення до іншої системи.
2. `ssh USER@HOST` — базова команда віддаленого входу.
3. `-p` задає порт, а `-i` — приватний ключ для автентифікації.
4. Команди всередині віддаленої сесії виконуються на сервері.
5. Окрему команду можна виконати через SSH без інтерактивного термінала.
6. `known_hosts` зберігає відомості про сервери, а `authorized_keys` — дозволені відкриті ключі користувачів.
7. Попередження про зміну ключа сервера потрібно перевіряти, а не просто вимикати.
8. `scp`, `sftp` та `rsync` допомагають передавати файли через SSH.
9. `ssh -v` — перший інструмент для діагностики проблем із підключенням.
10. Для безпечної роботи використовуй окремі облікові записи, мінімально необхідні права та надійне керування ключами.

**Основна ідея:** SSH дозволяє безпечно входити на віддалені Linux-системи, виконувати команди та передавати файли. Це одна з базових навичок для роботи з Linux-серверами, Node.js-застосунками, Git, PostgreSQL та розгортанням вебпроєктів.
