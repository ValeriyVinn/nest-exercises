# 06. Environment Variables — змінні середовища в Bash

Змінні середовища (*environment variables*) — це змінні, які передають інформацію про середовище виконання програм і можуть бути успадковані дочірніми процесами.

У Linux змінні середовища використовують для зберігання налаштувань системи, шляхів до програм, параметрів користувача, конфігурації застосунків та іншої інформації.

Вони особливо важливі під час написання Bash-скриптів, роботи з Node.js, налаштування серверів і запуску застосунків.

## 1. Основні поняття

✔ **Shell variable** — звичайна змінна поточної оболонки Bash.

✔ **Environment variable** — змінна, яку Bash експортує в середовище дочірніх процесів.

✔ **`export`** — команда, яка позначає змінну для передавання дочірнім процесам.

✔ **`$NAME`** — спосіб отримати значення змінної.

✔ **`printenv`** — команда для перегляду змінних середовища.

✔ **`env`** — команда для перегляду середовища або запуску програми з додатковими змінними.

✔ **`unset`** — команда для видалення змінної з поточної оболонки.

✔ **`$PATH`** — змінна середовища, яка містить каталоги для пошуку виконуваних команд.

✔ **`$HOME`** — домашній каталог поточного користувача.

✔ **`$USER`** — ім'я користувача, яке зазвичай встановлюється під час входу в систему.

✔ **`$SHELL`** — шлях до оболонки, визначеної для користувача; це не обов'язково оболонка, яка зараз виконується.

## 2. Що потрібно пам'ятати

- Змінні Bash зазвичай доступні лише в поточній оболонці, якщо їх не експортувати.
- Команда `export NAME=value` створює або оновлює змінну та експортує її в дочірні процеси.
- Змінні середовища передаються дочірнім процесам, але не передаються автоматично батьківському процесу.
- Ім'я змінної чутливе до регістру: `PATH`, `Path` і `path` — різні імена.
- Для присвоєння значення не можна ставити пробіли навколо `=`.
- Під час звернення до змінної використовують `$NAME` або `${NAME}`.
- Змінні середовища не є автоматично постійними: зміни в поточному терміналі зазвичай не зберігаються після завершення оболонки.
- Значення змінних середовища можуть містити секрети, тому не слід без потреби виводити їх у термінал, логи або коміти Git.

## 3. Звичайні змінні Bash

### 3.1. Створення змінної

У Bash змінну можна створити простим присвоєнням.

    name="Valeriy"
    project="nest-exercises"
    count=10

Для присвоєння значення пробіли навколо `=` не допускаються.

Правильно:

    name="Valeriy"

Неправильно:

    name = "Valeriy"

У неправильному прикладі Bash сприйматиме `name` як назву команди, а `=` та `"Valeriy"` — як її аргументи.

### 3.2. Отримання значення змінної

Для виведення значення використовують `$` перед ім'ям змінної.

    name="Valeriy"

    echo "$name"

Результат:

    Valeriy

Для більш надійного форматування в скриптах часто використовують `printf`.

    name="Valeriy"

    printf 'Користувач: %s\n' "$name"

Результат:

    Користувач: Valeriy

### 3.3. Фігурні дужки `${NAME}`

Фігурні дужки явно визначають межі імені змінної.

    name="Valeriy"

    echo "$name"
    echo "${name}"

Обидва варіанти виведуть:

    Valeriy
    Valeriy

Дужки особливо корисні, коли після змінної потрібно додати текст.

    prefix="linux"

    echo "${prefix}-course"

Результат:

    linux-course

Без дужок Bash намагатиметься знайти змінну з назвою `prefixcourse`, якщо написати `$prefixcourse`.

### 3.4. Змінна та дочірній процес

Звичайна змінна доступна в поточному Bash, але не передається автоматично зовнішнім командам.

    project="nest-exercises"

    bash -c 'printf "project=%s\n" "${project-unset}"'

Результат:

    project=unset

Тут запускається дочірній Bash. Він не отримує звичайну змінну `project` із батьківської оболонки.

Це можна виправити за допомогою `export`.

    project="nest-exercises"
    export project

    bash -c 'printf "project=%s\n" "$project"'

Результат:

    project=nest-exercises

**Важливо:** дочірній процес отримує копію середовища. Якщо він змінить змінну, це не змінить відповідну змінну в батьківському Bash.

## 4. Змінні середовища та команда `export`

### 4.1. Експортування змінної

Команда `export` позначає змінну для передавання в середовище дочірніх процесів.

    APP_NAME="my-app"
    export APP_NAME

Або створення змінної та її експортування одразу:

    export APP_NAME="my-app"

Перевірка:

    printenv APP_NAME

Результат:

    my-app

### 4.2. Звичайна змінна проти змінної середовища

    APP_NAME="my-app"

    # Змінна доступна в поточному Bash.
    echo "$APP_NAME"

    # Змінна експортується в дочірні процеси.
    export APP_NAME

    # Дочірній процес може отримати її значення.
    bash -c 'echo "$APP_NAME"'

Перед експортуванням:

- змінна доступна поточній оболонці;
- зовнішні команди не отримують її автоматично через середовище.

Після експортування:

- змінна залишається доступною поточній оболонці;
- дочірні процеси можуть отримати її через середовище.

### 4.3. Перегляд експортованих змінних

Команда `export -p` показує змінні, які експортуються.

    export -p

Щоб переглянути одну конкретну змінну:

    export -p | grep 'APP_NAME'

Зверни увагу: результат може містити формат, придатний для відтворення налаштувань Bash, а не просто значення змінної.

### 4.4. Експорт змінної не означає постійне збереження

Якщо виконати:

    export APP_MODE="development"

Змінна буде доступна в поточній оболонці та її дочірніх процесах.

Але після закриття термінала ця зміна зазвичай зникне.

Для автоматичного встановлення змінних під час наступних сеансів використовують файли конфігурації оболонки або окремі файли налаштувань.

## 5. Команди `printenv` та `env`

### 5.1. Команда `printenv`

`printenv` виводить значення змінних середовища.

Перегляд усіх змінних середовища:

    printenv

Перегляд однієї змінної:

    printenv HOME

Перегляд декількох змінних:

    printenv HOME USER SHELL PATH

Якщо змінна не існує в середовищі, `printenv` не виведе її значення та завершиться з ненульовим кодом.

Перевірка коду завершення:

    printenv APP_NAME
    echo "$?"

Важливо: команда `printenv` перевіряє саме середовище. Звичайна неекспортована змінна Bash може існувати, але `printenv` її не покаже.

### 5.2. Команда `env`

Без аргументів `env` показує середовище поточного процесу:

    env

Команда `env` також може запускати іншу програму з певними змінними середовища.

    env APP_MODE=development bash -c 'echo "$APP_MODE"'

Результат:

    development

У цьому прикладі `APP_MODE` передається запущеному Bash, але не встановлюється автоматично в поточній оболонці.

Перевірка:

    echo "${APP_MODE-unset}"

Якщо раніше змінну не було задано, результат буде:

    unset

### 5.3. Тимчасова змінна для однієї команди

Можна задати змінну безпосередньо перед запуском команди:

    APP_MODE=production node app.js

Значення `APP_MODE` буде передано запущеному процесу `node`.

Цей спосіб зручний для запуску застосунків із різними налаштуваннями.

Наприклад:

    APP_MODE=development node app.js

    APP_MODE=production node app.js

Для звичайної зовнішньої команди таке присвоєння діє на її середовище, а не встановлює змінну назавжди в поточній оболонці.

Особливості присвоєння перед командами Bash можуть відрізнятися для спеціальних вбудованих команд оболонки, тому для початкової практики найкраще використовувати зовнішні програми.

## 6. Видалення змінних: `unset`

Команда `unset` видаляє змінну з поточної оболонки.

    APP_NAME="my-app"

    echo "$APP_NAME"

    unset APP_NAME

    echo "${APP_NAME-unset}"

Результат:

    my-app
    unset

Якщо змінна була експортована, `unset` також видалить її з поточного середовища оболонки.

    export APP_MODE="development"

    unset APP_MODE

    printenv APP_MODE

Після видалення `printenv` не знайде змінну.

Видалення змінної в батьківському Bash не змінює середовище вже запущених дочірніх процесів.

**Застереження:** `unset` змінює стан лише поточної оболонки та не видаляє значення з конфігураційних файлів, де його могли встановити.

## 7. Поширені змінні середовища Linux

### 7.1. `HOME`

Містить шлях до домашнього каталогу користувача.

    echo "$HOME"

Приклад результату:

    /home/taubu

Фактичне значення залежить від системи та користувача.

### 7.2. `USER`

Зазвичай містить ім'я поточного користувача.

    echo "$USER"

Це поширена змінна середовища, але її значення не слід вважати універсальним або використовувати як єдину перевірку особи користувача.

### 7.3. `SHELL`

Містить шлях до оболонки, визначеної для користувача.

    echo "$SHELL"

Наприклад:

    /bin/bash

`$SHELL` не обов'язково показує поточну оболонку. Якщо користувач запустив Bash із іншої оболонки, значення `$SHELL` може залишитися тим самим.

Щоб перевірити поточну оболонку Bash, можна використати:

    ps -p "$$" -o comm=

### 7.4. `PATH`

`PATH` містить список каталогів, у яких оболонка шукає виконувані команди.

    echo "$PATH"

Приклад:

    /usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin:/sbin

Каталоги розділяються двокрапками `:`.

Перегляд кожного каталогу окремо:

    printf '%s\n' "$PATH" | tr ':' '\n'

Наприклад:

    /usr/local/bin
    /usr/bin
    /bin

Коли ти вводиш:

    node --version

Bash шукає виконувану програму `node` у каталогах, перелічених у `PATH`.

Перевірити, яку команду буде знайдено, можна так:

    command -v node

Якщо програма не знайдена, причина може полягати в тому, що її немає в системі або її каталог не входить до `PATH`.

### 7.5. `PWD`

Містить шлях до поточного робочого каталогу.

    echo "$PWD"

Перевірити поточний каталог також можна командою:

    pwd

Для більшості практичних задач `pwd` є простим і надійним способом дізнатися, де саме ти перебуваєш.

### 7.6. `OLDPWD`

Містить попередній робочий каталог після відповідного переходу між каталогами.

    cd /tmp
    cd /etc

    echo "$OLDPWD"

Команда:

    cd -

повертає до попереднього робочого каталогу.

### 7.7. `LANG` та `LC_*`

Ці змінні впливають на локалізацію програм, мову повідомлень, сортування та інші локальні правила.

    echo "$LANG"
    locale

Приклад значення `LANG`:

    uk_UA.UTF-8

Окремі змінні `LC_*` можуть перевизначати певні аспекти локалі, навіть якщо встановлено `LANG`.

### 7.8. `EDITOR`

Може містити назву або шлях до редактора, який деякі програми використовують за замовчуванням.

    export EDITOR="nano"

Наприклад, окремі інструменти можуть використовувати `$EDITOR` для відкриття тексту на редагування.

Не кожна програма зобов'язана враховувати цю змінну.

### 7.9. `TERM`

Містить тип термінала, який використовується програмами для визначення можливостей відображення.

    echo "$TERM"

Приклад:

    xterm-256color

Ця змінна не визначає саму оболонку. Вона допомагає програмам зрозуміти можливості термінального середовища.

### 7.10. `SHLVL`

Показує рівень вкладеності оболонок Bash у типовій ситуації.

    echo "$SHLVL"

Наприклад, запуск дочірнього Bash може збільшити значення `SHLVL`.

Не слід використовувати цю змінну як точний лічильник усіх процесів або всіх оболонок у системі.

## 8. Різниця між змінними та змінними середовища

Розглянемо приклад:

    PROJECT="nest-exercises"
    export APP_MODE="development"

Тут `PROJECT` — звичайна змінна, а `APP_MODE` — змінна середовища.

Перевіримо їх у поточному Bash:

    echo "$PROJECT"
    echo "$APP_MODE"

Обидві змінні доступні.

Перевіримо їх через `printenv`:

    printenv PROJECT
    printenv APP_MODE

За умови, що `PROJECT` не експортували раніше, `printenv PROJECT` не покаже його значення. Натомість `printenv APP_MODE` виведе `development`.

Перевіримо дочірній Bash:

    bash -c 'echo "PROJECT=${PROJECT-unset}"'
    bash -c 'echo "APP_MODE=${APP_MODE-unset}"'

Результат:

    PROJECT=unset
    APP_MODE=development

### Коротке порівняння

| Характеристика | Звичайна змінна Bash | Змінна середовища |
|---|---|---|
| Доступна поточній оболонці | Так | Так |
| Видима через `printenv` | Ні, якщо не експортована | Так |
| Передається дочірнім процесам | Ні, якщо не експортована | Так |
| Зберігається після закриття оболонки автоматично | Ні | Ні |
| Створюється присвоєнням `NAME=value` | Так | Так, якщо вже експортована або використано `export` |

Важливо: змінна, яку вже експортували, зберігає цей статус під час подальших присвоєнь у тій самій оболонці.

## 9. Змінні середовища у Bash-скриптах

### 9.1. Використання змінної середовища

Створимо файл `app-info.sh`:

    #!/usr/bin/env bash

    printf 'Application: %s\n' "${APP_NAME:-unknown}"
    printf 'Mode: %s\n' "${APP_MODE:-development}"

Запуск:

    APP_NAME="my-app" APP_MODE="production" bash app-info.sh

Результат:

    Application: my-app
    Mode: production

Тут скрипт отримує значення змінних середовища під час запуску.

### 9.2. Значення за замовчуванням: `${VAR:-default}`

У Bash можна задати значення за замовчуванням, якщо змінна не встановлена або має порожнє значення.

    echo "${APP_MODE:-development}"

Якщо `APP_MODE` не встановлена або порожня, результат:

    development

Якщо змінна має значення:

    APP_MODE="production"

    echo "${APP_MODE:-development}"

Результат:

    production

Оператор `:-` перевіряє і наявність значення, і те, чи воно непорожнє.

### 9.3. Значення за замовчуванням: `${VAR-default}`

Цей варіант використовує значення за замовчуванням лише тоді, коли змінна не встановлена.

    APP_MODE=""

    echo "${APP_MODE-default}"

Результат буде порожнім рядком, тому що змінна існує.

А ось:

    echo "${APP_MODE:-development}"

виведе:

    development

Різниця:

- `${VAR-default}` — підставляє `default`, якщо змінна не встановлена.
- `${VAR:-default}` — підставляє `default`, якщо змінна не встановлена або порожня.

### 9.4. Обов'язкова змінна: `${VAR:?message}`

Якщо змінна повинна бути задана, можна використати перевірку:

    : "${DATABASE_URL:?Не задано DATABASE_URL}"

Якщо `DATABASE_URL` не встановлена або порожня, Bash виведе повідомлення про помилку та припинить виконання поточного shell-контексту.

Приклад скрипту:

    #!/usr/bin/env bash

    set -u

    : "${DATABASE_URL:?Не задано DATABASE_URL}"

    printf 'DATABASE_URL задано.\n'

Використовуй цей підхід для обов'язкових налаштувань застосунку.

**Безпека:** не виводь повний рядок підключення до бази даних, якщо він містить пароль.

### 9.5. Чому важливо використовувати лапки

Правильно:

    printf 'Application: %s\n' "$APP_NAME"

Також правильно:

    node "$SCRIPT_PATH"

Небажано:

    node $SCRIPT_PATH

Без лапок значення може розділятися на декілька аргументів за пробілами, а також зазнавати підстановки шаблонів імен файлів.

Для змінних, значення яких може містити пробіли або спеціальні символи, використовуй подвійні лапки.

## 10. Постійне налаштування змінних середовища

Змінна, яку ти задав командою `export`, зазвичай існує лише в поточній оболонці та її дочірніх процесах.

Щоб встановлювати змінні автоматично, використовують файли конфігурації.

### 10.1. Файл `~/.bashrc`

`~/.bashrc` зазвичай виконується під час запуску інтерактивного Bash.

Відкриття файлу:

    nano ~/.bashrc

Наприкінці файлу можна додати:

    export EDITOR="nano"
    export PROJECTS_DIR="$HOME/projects"

Збережи файл і перезавантаж його в поточній оболонці:

    source ~/.bashrc

Або:

    . ~/.bashrc

Перевірка:

    echo "$EDITOR"
    echo "$PROJECTS_DIR"

Важливо: `source ~/.bashrc` виконує команди файлу в поточній оболонці. Якщо файл містить помилки або небажані команди, вони можуть вплинути на поточний сеанс.

### 10.2. Файл `~/.profile`

`~/.profile` часто використовується для налаштувань середовища під час входу користувача в систему.

Приклад:

    export PROJECTS_DIR="$HOME/projects"

Точний спосіб завантаження цього файлу залежить від способу входу в систему та конфігурації оболонки.

Не потрібно бездумно дублювати однакові налаштування одночасно в `~/.profile` і `~/.bashrc`.

### 10.3. Який файл вибрати?

| Файл | Типове призначення |
|---|---|
| `~/.bashrc` | Налаштування інтерактивного Bash |
| `~/.profile` | Налаштування середовища під час входу |
| `/etc/environment` | Системні змінні середовища в системах, що використовують цей механізм |
| `/etc/profile` | Загальносистемні налаштування для оболонок входу, залежно від конфігурації |

Для початкового навчання Bash зазвичай достатньо знати `~/.bashrc` і розуміти, що постійні налаштування відрізняються від тимчасових змінних поточного термінала.

**Застереження:** `/etc/environment` не є звичайним Bash-скриптом. Не використовуй у ньому конструкції на кшталт `export NAME=value` або очікування, що `$HOME` обов'язково буде розгорнуто як у Bash.

## 11. Змінні середовища та `sudo`

Команда `sudo` запускає програму з підвищеними привілеями відповідно до налаштувань системи.

З міркувань безпеки `sudo` може очищати або обмежувати середовище змінних.

Наприклад:

    export APP_MODE="development"

    sudo printenv APP_MODE

Значення не обов'язково буде доступне команді, запущеній через `sudo`.

Якщо потрібно передати конкретну змінну, спочатку перевір політику `sudo` у своїй системі. У деяких випадках може працювати:

    sudo --preserve-env=APP_MODE printenv APP_MODE

Але це залежить від конфігурації `sudo` і дозволів адміністратора.

Для навчальних скриптів не варто запускати все через `sudo` без необхідності.

## 12. Змінні середовища та безпека

Змінні середовища зручні для передавання конфігурації, але вони не є повноцінним сховищем секретів.

### 12.1. Не записуй секрети безпосередньо в код

Небажано:

    DATABASE_URL="postgres://user:password@example/db"

    # Інший код програми...

Якщо цей файл потрапить у Git, пароль може стати доступним іншим людям.

Краще передавати конфігурацію через змінні середовища:

    node app.js

А значення встановлювати окремо відповідно до середовища запуску.

### 12.2. Не виводь секрети в термінал без потреби

Команди:

    printenv
    env

можуть показати секрети, якщо вони присутні в середовищі.

У логах, звітах про помилки або записах термінала такі значення також можуть залишитися.

Для перевірки наявності змінної без виведення її значення можна використати:

    if [[ -n "${DATABASE_URL:-}" ]]; then
        printf 'DATABASE_URL задано.\n'
    else
        printf 'DATABASE_URL не задано.\n'
    fi

Цей приклад перевіряє, чи змінна непорожня, але не перевіряє правильність рядка підключення.

### 12.3. Файл `.env`

У багатьох JavaScript-проєктах використовують файл `.env` для локальної конфігурації.

Приклад вмісту:

    APP_MODE=development
    PORT=3000

Сам по собі файл `.env` не стає автоматично набором змінних середовища лише тому, що він лежить поруч із програмою.

Його потрібно завантажити відповідним механізмом, наприклад засобами Node.js або бібліотекою конфігурації, або використати інструмент, який уміє читати цей формат.

Для локальних секретів:

- додай `.env` до `.gitignore`;
- не коміть паролі та токени;
- за потреби створи `.env.example` з назвами змінних і без реальних секретів;
- перевір, які змінні потрібні застосунку, перш ніж запускати його.

Приклад `.env.example`:

    APP_MODE=development
    PORT=3000
    DATABASE_URL=

Не всі застосунки використовують однаковий формат `.env`, тому завжди перевіряй документацію конкретного інструмента.

## 13. Перевірка наявності змінної

### 13.1. Перевірка, чи змінна встановлена

У Bash:

    if [[ -v APP_NAME ]]; then
        printf 'APP_NAME встановлена.\n'
    else
        printf 'APP_NAME не встановлена.\n'
    fi

`[[ -v APP_NAME ]]` перевіряє, чи змінна встановлена, навіть якщо її значення порожнє.

### 13.2. Перевірка, чи змінна непорожня

    if [[ -n "${APP_NAME:-}" ]]; then
        printf 'APP_NAME має значення.\n'
    else
        printf 'APP_NAME порожня або не встановлена.\n'
    fi

Це корисно для перевірки налаштувань перед запуском застосунку.

### 13.3. Перевірка через `printenv`

    if printenv APP_NAME >/dev/null; then
        printf 'APP_NAME є у середовищі.\n'
    else
        printf 'APP_NAME відсутня в середовищі.\n'
    fi

Тут перевіряється саме наявність змінної в середовищі, а не лише існування звичайної змінної Bash.

## 14. Змінні середовища та `PATH`

Оскільки `PATH` впливає на пошук команд, змінювати його потрібно обережно.

### 14.1. Додавання каталогу на початок `PATH`

Приклад для каталогу `~/bin`:

    export PATH="$HOME/bin:$PATH"

Це додає каталог на початок списку. Якщо в ньому є виконуваний файл з тією самою назвою, що й системна команда, він може бути знайдений першим.

### 14.2. Додавання каталогу в кінець `PATH`

    export PATH="$PATH:$HOME/bin"

Тепер каталог буде перевірятися після вже наявних каталогів.

### 14.3. Чому не варто перезаписувати `PATH` без потреби

Небажано:

    export PATH="$HOME/bin"

Такий запис може прибрати каталоги, потрібні для пошуку стандартних команд, наприклад `/usr/bin`.

У результаті команди можуть перестати знаходитися.

Зазвичай потрібно саме доповнювати наявний `PATH`, а не замінювати його повністю.

### 14.4. Перевірка після зміни

    printf '%s\n' "$PATH" | tr ':' '\n'

Перевірка команди:

    command -v node
    command -v git
    command -v bash

Якщо щойно змінений `PATH` не дає очікуваного результату, перевір, чи існує каталог і чи містить він потрібний виконуваний файл.

## 15. Типові помилки

### Помилка 1. Пробіли навколо `=`

Неправильно:

    APP_MODE = "development"

Правильно:

    APP_MODE="development"

### Помилка 2. Очікування, що звичайна змінна доступна дочірньому процесу

    APP_MODE="development"

    bash -c 'echo "$APP_MODE"'

Якщо змінну не експортували раніше, дочірній Bash зазвичай не отримає її.

Правильно:

    export APP_MODE="development"

    bash -c 'echo "$APP_MODE"'

### Помилка 3. Очікування, що `printenv` показує всі змінні Bash

`printenv` показує змінні середовища, а не всі звичайні змінні поточної оболонки.

Для перегляду змінних і функцій Bash використовують:

    declare -p

Для перегляду експортованих змінних:

    export -p

### Помилка 4. Забуті лапки

Небажано:

    printf '%s\n' $PROJECTS_DIR

Краще:

    printf '%s\n' "$PROJECTS_DIR"

Лапки допомагають уникнути небажаного розбиття значення на аргументи.

### Помилка 5. Очікування постійності після `export`

    export APP_MODE="production"

Це не означає, що змінна автоматично збережеться після закриття термінала.

Для постійного налаштування використовують відповідні файли конфігурації або механізми запуску застосунків.

### Помилка 6. Неправильне очікування щодо `.env`

Наявність файлу `.env` сама по собі не гарантує, що змінні будуть доступні програмі.

Переконайся, що застосунок або інструмент завантажує цей файл.

### Помилка 7. Перезапис `PATH`

    export PATH="/home/taubu/bin"

Такий запис може прибрати системні каталоги зі шляху пошуку команд.

Частіше потрібно:

    export PATH="$HOME/bin:$PATH"

### Помилка 8. Виведення секретів

    printenv

Ця команда може показати паролі, токени та інші конфіденційні значення.

Не використовуй її бездумно на системах, де середовище містить секрети.

### Помилка 9. Очікування, що дочірній процес змінить батьківську оболонку

Якщо скрипт виконує:

    export APP_MODE="production"

це не змінює автоматично `APP_MODE` у терміналі, з якого запущено скрипт.

Щоб виконати команди скрипту в поточній оболонці, використовують `source` або `.`. Робити це слід лише для довірених скриптів.

## 17. Рівні знань

### Core — базовий рівень

Потрібно вміти:

- створювати змінні Bash;
- читати значення через `$NAME` і `${NAME}`;
- розуміти різницю між звичайною змінною та змінною середовища;
- використовувати `export`;
- переглядати значення через `printenv`;
- видаляти змінні через `unset`;
- розуміти призначення `HOME`, `USER`, `PATH` і `PWD`.

### Junior — практичний рівень

Потрібно вміти:

- передавати конфігурацію в Bash-скрипти через середовище;
- задавати змінну для однієї команди;
- перевіряти обов'язкові змінні перед запуском застосунку;
- використовувати значення за замовчуванням;
- розуміти роль `~/.bashrc`;
- додавати каталоги до `PATH`, не перезаписуючи його випадково;
- пояснювати, чому `.env` потрібно окремо завантажувати.

### Middle — поглиблений рівень

Потрібно розуміти:

- успадкування середовища процесами;
- різницю між середовищем поточної оболонки та дочірнього процесу;
- вплив `sudo` на середовище;
- поведінку змінних у різних сценаріях запуску Bash;
- відмінності між інтерактивною оболонкою та оболонкою входу;
- ризики витоку секретів через середовище, логи та діагностичні команди;
- правила налаштування конфігурації для локального та production-середовища.

### Senior — системне розуміння

Потрібно розуміти:

- як середовище передається між процесами на рівні операційної системи;
- чому дочірній процес не може змінити середовище батьківського процесу;
- як середовище впливає на відтворюваність запуску застосунків;
- як керувати конфігурацією та секретами в production;
- як уникати небезпечних змін `PATH`;
- як системні служби та менеджери процесів задають середовище програм;
- чому змінні середовища можуть бути доступні іншим компонентам, які мають відповідний доступ до процесу або його діагностики.

## 18. Мінішпаргалка

    # Створення звичайної змінної
    APP_NAME="my-app"

    # Читання змінної
    echo "$APP_NAME"

    # Читання з явними межами імені
    echo "${APP_NAME}"

    # Експортування змінної
    export APP_NAME

    # Створення та експортування
    export APP_MODE="development"

    # Перегляд усіх змінних середовища
    printenv

    # Перегляд однієї змінної середовища
    printenv HOME

    # Перегляд експортованих змінних Bash
    export -p

    # Перегляд змінних Bash
    declare -p

    # Запуск дочірнього Bash із доступом до експортованої змінної
    bash -c 'echo "$APP_MODE"'

    # Змінна лише для запуску команди
    APP_MODE=production bash -c 'echo "$APP_MODE"'

    # Значення за замовчуванням, якщо змінна відсутня або порожня
    echo "${APP_MODE:-development}"

    # Значення за замовчуванням, якщо змінна не встановлена
    echo "${APP_MODE-development}"

    # Перевірка наявності змінної
    [[ -v APP_NAME ]]

    # Перевірка непорожнього значення
    [[ -n "${APP_NAME:-}" ]]

    # Видалення змінної
    unset APP_NAME

    # Перегляд PATH
    echo "$PATH"

    # Перегляд каталогів PATH окремими рядками
    printf '%s\n' "$PATH" | tr ':' '\n'

    # Додавання каталогу до PATH
    export PATH="$HOME/bin:$PATH"

    # Перезавантаження налаштувань Bash
    source ~/.bashrc

## 19. Практичні завдання

### Завдання 1. Створення звичайної змінної

1. Створи змінну `COURSE_NAME` зі значенням `Linux`.
2. Виведи її значення.
3. Зміни значення на `Bash`.
4. Виведи нове значення.

Очікуваний результат:

    Linux
    Bash

### Завдання 2. Порівняння звичайної змінної та змінної середовища

1. Створи змінну `PROJECT_NAME="nest-exercises"`.
2. Створи змінну `APP_MODE="development"` та експортуй її.
3. Перевір обидві через `echo`.
4. Перевір обидві через `printenv`.
5. Запусти дочірній Bash і виведи обидві змінні.

Поясни, чому результати відрізняються.

### Завдання 3. Тимчасова змінна

Запусти команду, яка передає `APP_MODE=production` лише дочірньому процесу Bash.

Переконайся, що дочірній процес бачить `production`, а поточна оболонка не отримала цю змінну автоматично.

### Завдання 4. Значення за замовчуванням

Виконай перевірки для змінної `APP_MODE`, коли вона:

1. Не встановлена.
2. Має порожнє значення.
3. Має значення `production`.

Порівняй:

    echo "${APP_MODE-default}"

    echo "${APP_MODE:-default}"

### Завдання 5. Інформація про середовище

Виведи значення змінних:

    HOME
    USER
    SHELL
    PWD
    PATH
    LANG

Для `PATH` покажи кожен каталог окремим рядком.

### Завдання 6. Налаштування Bash

1. Відкрий `~/.bashrc`.
2. Додай змінну `PROJECTS_DIR="$HOME/projects"` через `export`.
3. Перезавантаж конфігурацію за допомогою `source ~/.bashrc`.
4. Перевір значення змінної.
5. Відкрий новий термінал і перевір її знову.

Перед редагуванням перевір, чи не існує такого налаштування вже.

### Завдання 7. Bash-скрипт із конфігурацією

Створи файл `app-info.sh` із таким вмістом:

    #!/usr/bin/env bash

    APP_NAME="${APP_NAME:-my-app}"
    APP_MODE="${APP_MODE:-development}"

    printf 'Application: %s\n' "$APP_NAME"
    printf 'Mode: %s\n' "$APP_MODE"

Запусти скрипт без додаткових змінних, а потім передай `APP_NAME` і `APP_MODE` під час запуску.

Порівняй результати.

### Завдання 8. Перевірка обов'язкової змінної

Створи скрипт, який вимагає змінну `DATABASE_URL`.

Використай конструкцію:

    : "${DATABASE_URL:?Не задано DATABASE_URL}"

Перевір поведінку скрипту, коли змінна відсутня та коли вона задана. Не використовуй реальні паролі або секрети в тестових значеннях.

### Завдання 9. Робота з `PATH`

1. Виведи поточний `PATH`.
2. Розділи його на окремі рядки.
3. Додай `$HOME/bin` на початок `PATH`.
4. Перевір результат.
5. Поясни, чому не варто повністю замінювати `PATH` одним каталогом.

### Завдання 10. Безпечна перевірка конфігурації

Створи скрипт, який перевіряє наявність `DATABASE_URL`, але не виводить її значення.

Він повинен виводити лише одне з повідомлень:

    DATABASE_URL задано.

або

    DATABASE_URL не задано.

Перевір обидва сценарії.

## 20. Підсумок

Змінні середовища — один із базових механізмів передавання конфігурації в Linux. Вони допомагають налаштовувати Bash-скрипти, сервери та застосунки без необхідності записувати кожен параметр безпосередньо в код.

Найважливіше запам'ятати:

- `NAME=value` створює або змінює змінну в поточній оболонці.
- `export NAME` робить змінну доступною через середовище дочірніх процесів.
- `printenv NAME` показує значення змінної середовища.
- `env NAME=value command` запускає команду з указаною змінною.
- `unset NAME` видаляє змінну з поточної оболонки.
- `${NAME:-default}` дозволяє задати значення за замовчуванням.
- `PATH` визначає, де оболонка шукає виконувані команди.
- `~/.bashrc` допомагає налаштовувати інтерактивний Bash.
- `.env` — це формат файлу конфігурації, який потрібно завантажити відповідним механізмом.
- Секрети потрібно захищати від випадкового виведення в термінал, потрапляння в логи та коміти Git.

**Головний принцип:** звичайна змінна належить поточній оболонці, а змінна середовища передає значення дочірнім процесам. Постійність налаштувань залежить від того, де і як вони встановлюються.
