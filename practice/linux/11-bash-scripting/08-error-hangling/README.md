# Bash Scripting — 08. Error Handling

Обробка помилок (`error handling`) у Bash — це набір прийомів, які допомагають скрипту правильно реагувати на невдалі команди, неправильні аргументи, відсутні файли, проблеми з доступом і помилки зовнішніх програм.

Надійний скрипт повинен не лише виконувати потрібні команди, а й перевіряти їхні результати, повідомляти про проблеми та завершуватися з відповідним кодом.

Наприклад, якщо скрипт повинен прочитати конфігураційний файл, він має повідомити про помилку, якщо файл відсутній:

    #!/usr/bin/env bash

    config="config.txt"

    if [[ ! -f "$config" ]]; then
        echo "Помилка: конфігураційний файл не знайдено" >&2
        exit 1
    fi

    echo "Конфігураційний файл знайдено"

## 1. Основи обробки помилок

### 1.1. Що таке помилка в Bash

Помилка — це ситуація, коли команда або скрипт не може виконати заплановану операцію.

Типові приклади:

- файл не існує;
- каталог неможливо створити;
- користувач не має необхідних прав;
- команда не встановлена;
- аргумент має неправильний формат;
- зовнішня програма завершилася невдало;
- команда отримала неправильні дані;
- скрипт не зміг записати результат.

Приклад:

    cp "source.txt" "backup/"

Якщо файл `source.txt` відсутній або каталог `backup` недоступний для запису, команда `cp` може завершитися з помилкою.

Надійний скрипт повинен уміти виявити таку ситуацію.

### 1.2. Основні інструменти error handling

| Інструмент | Призначення |
|---|---|
| `$?` | Код завершення попередньої команди |
| `if` | Перевірка успіху або невдачі команди |
| `exit` | Завершення скрипту з кодом |
| `return` | Завершення функції з кодом |
| `||` | Виконання альтернативної команди, якщо попередня завершилася невдало |
| `&&` | Виконання наступної команди лише за успіху попередньої |
| `trap` | Реакція на сигнали та певні події Bash |
| `set -e` | Намагання завершувати скрипт при певних невдалих командах |
| `set -u` | Помилка при використанні незаданих змінних |
| `set -o pipefail` | Виявлення помилки в конвеєрі, якщо будь-яка його команда завершилася невдало |
| `printf` | Формування зрозумілих повідомлень |
| `>&2` | Перенаправлення повідомлення до стандартного потоку помилок |

Важливо: жоден окремий механізм не замінює розуміння логіки скрипту. Наприклад, `set -e` не гарантує автоматичного виявлення всіх можливих помилок.

## 2. Коди завершення

### 2.1. Що таке exit status

Кожна команда в Bash завершується з певним кодом.

За загальним правилом:

- `0` — успішне виконання;
- ненульове значення — помилка або інший результат, який команда вважає неуспішним.

Приклад:

    true

    echo "$?"

Результат:

    0

Команда `true` завершується успішно.

Інший приклад:

    false

    echo "$?"

Результат:

    1

Команда `false` навмисно завершується з кодом `1`.

### 2.2. Змінна `$?`

`$?` містить код завершення останньої виконаної команди.

    ls

    echo "$?"

Якщо команда `ls` виконалася успішно, буде виведено `0`.

Якщо вона завершилася помилкою, код буде ненульовим.

Важливо: значення `$?` потрібно зберегти або перевірити одразу, якщо воно потрібне.

Неправильно:

    cp source.txt backup/
    echo "Копіювання завершено"
    echo "$?"

Останній `echo` успішно завершується, тому `$?` зазвичай міститиме код `0`, а не результат `cp`.

Правильно:

    cp source.txt backup/
    status=$?

    echo "Код завершення cp: $status"

А ще краще, якщо потрібно лише перевірити результат, використати `if`.

### 2.3. Перевірка коду завершення через `if`

    if cp source.txt backup/; then
        echo "Копіювання завершено успішно"
    else
        echo "Помилка копіювання" >&2
        exit 1
    fi

Цей підхід зрозумілий і часто є найкращим вибором для початкових скриптів.

Команда після `if` виконується як умова. Якщо вона повертає `0`, виконується гілка `then`; інакше — `else`.

### 2.4. Власні коди завершення скрипту

Для завершення скрипту використовують `exit`.

    exit 0

Успішне завершення.

    exit 1

Завершення з помилкою.

Можна використовувати й інші ненульові коди, якщо це допомагає розрізняти причини невдачі.

Наприклад:

    #!/usr/bin/env bash

    if [[ $# -eq 0 ]]; then
        echo "Помилка: передай шлях до файлу" >&2
        exit 2
    fi

    if [[ ! -f "$1" ]]; then
        echo "Помилка: файл не знайдено" >&2
        exit 1
    fi

    echo "Файл знайдено"
    exit 0

У цьому прикладі:

- `0` — успіх;
- `1` — файл не знайдено;
- `2` — неправильне використання скрипту.

Коди `1` і `2` тут обрані як домовленість самого скрипту. Не всі програми використовують однакові значення для конкретних помилок.

## 3. Стандартний потік помилок — stderr

### 3.1. stdout і stderr

У Linux процеси зазвичай мають три стандартні потоки:

| Потік | Номер | Призначення |
|---|---:|---|
| stdin | `0` | Вхідні дані |
| stdout | `1` | Звичайний вивід |
| stderr | `2` | Повідомлення про помилки |

Звичайне повідомлення:

    echo "Операцію завершено"

Повідомлення про помилку:

    echo "Помилка: файл не знайдено" >&2

Або:

    printf 'Помилка: файл не знайдено\n' >&2

`>&2` перенаправляє вивід у стандартний потік помилок.

### 3.2. Чому помилки краще виводити в stderr

Припустимо, скрипт виводить список файлів, який інша команда повинна обробити.

Якщо помилки виводити в stdout, вони можуть потрапити до цього списку й завадити обробці даних.

Приклад:

    #!/usr/bin/env bash

    if [[ ! -f "data.txt" ]]; then
        printf 'Помилка: data.txt не знайдено\n' >&2
        exit 1
    fi

    cat -- "data.txt"

Тепер звичайні дані залишаються у stdout, а повідомлення про помилку надходить у stderr.

### 3.3. Перенаправлення stderr у файл

    ./script.sh 2> errors.log

Стандартний вивід залишається в терміналі, а повідомлення stderr записуються до `errors.log`.

Щоб записувати повідомлення про помилки в кінець файлу:

    ./script.sh 2>> errors.log

### 3.4. Приховування повідомлень про помилки

    command_name 2>/dev/null

`/dev/null` відкидає передані йому дані.

Наприклад:

    if command -v node >/dev/null 2>&1; then
        echo "Node.js доступний"
    else
        echo "Node.js не знайдено"
    fi

Тут вивід `command -v` приховується, а результат використовується в умові.

Не приховуй помилки без потреби: під час налагодження вони часто містять важливу інформацію.

## 4. Обробка помилок за допомогою `if`

### 4.1. Перевірка зовнішньої команди

    if mkdir -p "reports"; then
        echo "Каталог готовий"
    else
        echo "Не вдалося створити каталог" >&2
        exit 1
    fi

Цей варіант перевіряє фактичний результат `mkdir`, а не лише попередню умову.

### 4.2. Перевірка читання файлу

    file="data.txt"

    if [[ ! -f "$file" ]]; then
        echo "Помилка: файл не існує" >&2
        exit 1
    fi

    if [[ ! -r "$file" ]]; then
        echo "Помилка: файл недоступний для читання" >&2
        exit 1
    fi

    if ! cat -- "$file"; then
        echo "Помилка під час читання файлу" >&2
        exit 1
    fi

Тут перевіряються три окремі ситуації:

1. Файл відсутній.
2. Файл недоступний для читання.
3. Спроба читання завершилася невдало.

Перевірка перед операцією корисна для зрозумілих повідомлень, але саме читання все одно потрібно перевіряти.

### 4.3. Перевірка введених аргументів

    #!/usr/bin/env bash

    if [[ $# -ne 1 ]]; then
        echo "Використання: $0 <файл>" >&2
        exit 2
    fi

    file="$1"

    if [[ ! -f "$file" ]]; then
        printf 'Помилка: звичайний файл не знайдено: %s\n' "$file" >&2
        exit 1
    fi

    printf 'Файл знайдено: %s\n' "$file"

`$#` містить кількість позиційних параметрів скрипту.

`-ne` означає «не дорівнює» в арифметичному порівнянні.

### 4.4. Перевірка числового аргументу

Перед арифметичними операціями корисно перевіряти формат введення.

    #!/usr/bin/env bash

    value="${1:-}"

    if [[ ! "$value" =~ ^[0-9]+$ ]]; then
        echo "Помилка: потрібно передати невід'ємне ціле число" >&2
        exit 2
    fi

    printf 'Отримано число: %s\n' "$value"

Регулярний вираз `^[0-9]+$` перевіряє, що весь рядок складається з однієї або більше цифр.

Цей приклад не приймає від'ємні числа, десяткові дроби або порожній рядок.

## 5. Оператори `&&` та `||`

### 5.1. Оператор `&&`

`&&` виконує наступну команду лише тоді, коли попередня завершилася з кодом `0`.

    mkdir -p "logs" && echo "Каталог готовий"

Якщо `mkdir` завершиться невдало, `echo` не виконається.

### 5.2. Оператор `||`

`||` виконує наступну команду, якщо попередня завершилася з ненульовим кодом.

    cp source.txt backup/ || echo "Помилка копіювання" >&2

Якщо `cp` завершиться невдало, буде виведено повідомлення.

Але цей рядок сам по собі не завершує скрипт.

### 5.3. Комбінація `&&` та `||`

    mkdir -p "logs" &&
        echo "Каталог створено" ||
        echo "Помилка створення каталогу" >&2

Цей запис виглядає коротким, але може бути неоднозначним для читання, оскільки `&&` та `||` виконують керування потоком команд, а не працюють як звичайні логічні оператори в будь-якому контексті.

Для критичної логіки краще використовувати `if`:

    if mkdir -p "logs"; then
        echo "Каталог готовий"
    else
        echo "Помилка створення каталогу" >&2
        exit 1
    fi

### 5.4. Не використовуй `|| true` без розуміння наслідків

    some_command || true

Цей запис перетворює невдале виконання `some_command` на успішний результат у контексті цього списку команд.

Іноді це потрібно, наприклад, коли певна невдача очікувана. Але так можна приховати справжню помилку.

Використовуй його лише тоді, коли невдача справді допустима і ти розумієш, чому її можна ігнорувати.

## 6. Функції та обробка помилок

### 6.1. Код завершення функції

Функція Bash може завершитися з кодом через `return`.

    check_file() {
        local file="$1"

        if [[ -f "$file" ]]; then
            return 0
        fi

        return 1
    }

    if check_file "config.txt"; then
        echo "Файл знайдено"
    else
        echo "Файл не знайдено" >&2
    fi

`return` завершує функцію, а `exit` — весь скрипт або поточну оболонку.

### 6.2. Перевірка аргументів функції

    copy_file() {
        if [[ $# -ne 2 ]]; then
            printf 'Помилка: потрібно передати джерело та призначення\n' >&2
            return 2
        fi

        local source="$1"
        local destination="$2"

        if [[ ! -f "$source" ]]; then
            printf 'Помилка: файл не знайдено: %s\n' "$source" >&2
            return 1
        fi

        if cp -- "$source" "$destination"; then
            return 0
        else
            printf 'Помилка копіювання: %s\n' "$source" >&2
            return 1
        fi
    }

    if copy_file "source.txt" "backup.txt"; then
        echo "Копіювання завершено"
    else
        echo "Функція завершилася з помилкою" >&2
    fi

Функція повертає код завершення, який викликаючий код може перевірити.

### 6.3. Різниця між `return` і `exit`

| Команда | Дія |
|---|---|
| `return 0` | Завершує функцію успішно |
| `return 1` | Завершує функцію з помилкою |
| `exit 0` | Завершує скрипт успішно |
| `exit 1` | Завершує скрипт із помилкою |

У функціях, які можуть використовуватися повторно, часто краще повертати код помилки, а рішення про завершення всього скрипту залишати викликаючому коду.

## 7. Команди `set -e`, `set -u` та `pipefail`

Ці параметри часто називають строгим режимом Bash:

    set -euo pipefail

Вони можуть допомогти виявляти помилки, але кожен має свої особливості.

### 7.1. `set -e`

`set -e` просить Bash завершувати виконання в багатьох ситуаціях, коли проста команда повертає ненульовий код.

    #!/usr/bin/env bash

    set -e

    echo "Початок"
    cp missing.txt backup/
    echo "Цей рядок може не виконатися"

Якщо `cp` завершиться невдало в цьому контексті, скрипт зазвичай завершиться до останнього `echo`.

Однак `set -e` має винятки та залежить від контексту виконання. Наприклад, невдалу команду в умові `if` Bash не трактує так само, як невдалу просту команду в основному потоці виконання.

Тому не слід покладатися лише на `set -e` для всієї логіки обробки помилок.

### 7.2. `set -u`

`set -u` змушує Bash повідомляти про використання незаданих змінних у багатьох звичайних контекстах.

    #!/usr/bin/env bash

    set -u

    echo "$username"

Якщо `username` не задана, скрипт зазвичай завершиться з помилкою.

Безпечніший варіант для необов'язкової змінної:

    echo "${username:-Guest}"

Якщо `username` не задана або порожня, буде використано `Guest`.

Для необов'язкового позиційного параметра:

    file="${1:-}"

Це дозволяє перевірити аргумент без помилки через відсутність `$1`.

### 7.3. `set -o pipefail`

За замовчуванням код завершення конвеєра зазвичай дорівнює коду завершення останньої команди.

Наприклад:

    false | true

Без `pipefail` код завершення такого конвеєра зазвичай буде `0`, оскільки остання команда `true` успішна.

З `pipefail`:

    set -o pipefail

    false | true

Тепер конвеєр завершується з ненульовим кодом, оскільки одна з команд завершилася невдало.

Це особливо корисно для конвеєрів, де результат попередніх команд важливий.

### 7.4. Комбінування параметрів

    #!/usr/bin/env bash

    set -euo pipefail

    file="${1:-}"

    if [[ -z "$file" ]]; then
        echo "Використання: $0 <файл>" >&2
        exit 2
    fi

    if [[ ! -f "$file" ]]; then
        echo "Помилка: файл не знайдено" >&2
        exit 1
    fi

    cat -- "$file"

Тут:

- `-e` допомагає виявляти певні невдалі команди;
- `-u` допомагає виявляти використання незаданих змінних;
- `pipefail` допомагає виявляти помилки конвеєрів.

Навіть із цими параметрами потрібно перевіряти критичні операції та не покладатися на неявну поведінку Bash.

## 8. Обробка помилок у конвеєрах

### 8.1. Що таке pipeline

Конвеєр передає stdout однієї команди на stdin іншої.

    cat data.txt | grep "error" | sort

Тут:

1. `cat` читає файл.
2. `grep` вибирає рядки, що містять `error`.
3. `sort` сортує результат.

### 8.2. Проблема стандартного коду завершення pipeline

    false | true

Без `pipefail` результат конвеєра зазвичай буде успішним, оскільки остання команда `true` повертає `0`.

Це може приховати помилку попередньої команди.

### 8.3. Використання `pipefail`

    #!/usr/bin/env bash

    set -o pipefail

    if cat -- "data.txt" | grep "error" | sort; then
        echo "Конвеєр завершився успішно"
    else
        echo "Помилка в конвеєрі або немає збігів grep" >&2
    fi

Важливо: `grep` повертає ненульовий код, якщо збігів не знайдено. Це не завжди помилка обробки даних — усе залежить від логіки програми.

Тому в реальних скриптах потрібно розрізняти очікувану відсутність збігів і справжню помилку, якщо це важливо для завдання.

### 8.4. Обережно з `grep`

    if grep -q "error" "app.log"; then
        echo "Знайдено помилки"
    else
        echo "Збігів немає або сталася помилка" >&2
    fi

Код `1` у `grep` зазвичай означає, що збігів не знайдено, а інші ненульові коди можуть свідчити про помилку.

Якщо важливо розрізняти ці ситуації, перевіряй код завершення окремо.

    grep -q "error" "app.log"
    status=$?

    if [[ "$status" -eq 0 ]]; then
        echo "Знайдено помилки"
    elif [[ "$status" -eq 1 ]]; then
        echo "Збігів немає"
    else
        echo "Помилка під час пошуку" >&2
        exit "$status"
    fi

## 9. Обробка помилок за допомогою `trap`

### 9.1. Що таке `trap`

`trap` дозволяє виконувати певні дії, коли Bash отримує сигнал або виникає спеціальна подія.

Наприклад:

    trap 'echo "Скрипт завершується"' EXIT

    echo "Робота скрипту"

Обробник `EXIT` виконується під час завершення поточної оболонки або скрипту.

### 9.2. Обробник EXIT

    #!/usr/bin/env bash

    cleanup() {
        echo "Виконується завершення скрипту"
    }

    trap cleanup EXIT

    echo "Основна робота"

Функція `cleanup` буде викликана під час завершення скрипту.

Це зручно для очищення тимчасових файлів або інших ресурсів.

### 9.3. Обробник помилок із `ERR`

У Bash можна використовувати псевдосигнал `ERR`, який спрацьовує для багатьох невдалих команд відповідно до правил Bash.

    #!/usr/bin/env bash

    set -E
    set -o errtrace

    trap 'printf "Помилка: код %s, команда: %s\n" "$?" "$BASH_COMMAND" >&2' ERR

    false

Тут:

- `$?` у повідомленні містить код завершення команди, що викликала обробник;
- `$BASH_COMMAND` містить команду, яку Bash виконував або збирався виконати в цьому контексті;
- `set -E` допомагає поширювати успадкування `ERR`-trap у функції та деякі інші контексти;
- `errtrace` є довгою формою `-E`.

`ERR` має винятки, подібні до особливостей `set -e`. Він не є універсальним перехоплювачем усіх помилок.

### 9.4. Обробка сигналу INT

Сигнал `INT` зазвичай виникає, коли користувач натискає `Ctrl+C` у терміналі.

    #!/usr/bin/env bash

    trap 'echo "Скрипт перервано користувачем" >&2; exit 130' INT

    while true; do
        sleep 1
        echo "Робота триває"
    done

Код `130` часто використовують для позначення завершення через `SIGINT`.

Обробники сигналів потрібно проєктувати обережно, особливо якщо скрипт працює з тимчасовими файлами або фоновими процесами.

### 9.5. Видалення тимчасових файлів

    #!/usr/bin/env bash

    set -u

    temp_file="$(mktemp)" || {
        echo "Не вдалося створити тимчасовий файл" >&2
        exit 1
    }

    cleanup() {
        rm -f -- "$temp_file"
    }

    trap cleanup EXIT

    printf 'Тимчасові дані\n' > "$temp_file"

    cat -- "$temp_file"

`mktemp` створює тимчасовий файл із безпечно згенерованим ім'ям.

`trap cleanup EXIT` забезпечує спробу видалення файлу під час завершення скрипту, зокрема після багатьох звичайних помилок.

Це не гарантує очищення після аварійного вимкнення системи або ситуацій, коли обробник не може виконатися.

### 9.6. Збереження коду помилки під час очищення

Якщо скрипт завершується з помилкою, функція очищення не повинна випадково приховати початковий код завершення.

    #!/usr/bin/env bash

    cleanup() {
        local status=$?

        rm -f -- "${temp_file:-}"

        return "$status"
    }

    temp_file="$(mktemp)" || exit 1

    trap cleanup EXIT

    false

У цьому прикладі функція `cleanup` зберігає код, з яким почала виконання, перед запуском `rm`.

Однак код завершення самого обробника `EXIT` не слід використовувати як універсальний механізм зміни кінцевого статусу скрипту. Якщо потрібна складніша логіка завершення, зберігай початковий статус явно та організовуй завершення в одному контрольованому місці.

## 10. Функція для повідомлень про помилки

### 10.1. Створення функції `error`

    error() {
        printf 'Помилка: %s\n' "$*" >&2
    }

    error "Файл не знайдено"

Результат:

    Помилка: Файл не знайдено

`$*` об'єднує аргументи функції в рядок, що зручно для простих повідомлень.

### 10.2. Функція `die`

Функція `die` може вивести повідомлення й завершити скрипт.

    die() {
        printf 'Помилка: %s\n' "$*" >&2
        exit 1
    }

    [[ -f "config.txt" ]] || die "Конфігурацію не знайдено"

Такий підхід дозволяє уникнути повторення однакових конструкцій.

Використовуй `die` для помилок, після яких продовжувати виконання скрипту немає сенсу.

### 10.3. Функція `die` з кодом завершення

    die() {
        local status="$1"
        shift

        printf 'Помилка: %s\n' "$*" >&2
        exit "$status"
    }

    [[ $# -eq 1 ]] || die 2 "Використання: $0 <файл>"

    [[ -f "$1" ]] || die 1 "Файл не знайдено: $1"

Тут перший аргумент функції визначає код завершення, а решта аргументів утворюють повідомлення.

### 10.4. Різниця між `error` і `die`

| Функція | Призначення |
|---|---|
| `error` | Виводить повідомлення, але не завершує скрипт |
| `die` | Виводить повідомлення й завершує скрипт |
| `return` | Дозволяє функції повідомити про невдачу викликаючому коду |
| `exit` | Завершує весь скрипт |

Не кожна помилка повинна завершувати програму. Наприклад, якщо скрипт перевіряє десятки файлів, він може повідомити про відсутні файли й продовжити перевірку решти.

## 11. Повідомлення про помилки та логування

### 11.1. Функції для логування

    log_info() {
        printf '[INFO] %s\n' "$*"
    }

    log_warn() {
        printf '[WARN] %s\n' "$*" >&2
    }

    log_error() {
        printf '[ERROR] %s\n' "$*" >&2
    }

    log_info "Скрипт запущено"
    log_warn "Файл конфігурації не задано"
    log_error "Не вдалося створити каталог"

Розділення рівнів повідомлень полегшує читання виводу скрипту.

### 11.2. Запис логів у файл

    log_file="app.log"

    printf '[INFO] Запуск скрипту\n' >> "$log_file"

Оператор `>>` додає повідомлення до кінця файлу, не перезаписуючи його попередній вміст.

Перевіряй результат запису, якщо він важливий:

    if ! printf '[INFO] Запуск скрипту\n' >> "$log_file"; then
        printf 'Не вдалося записати лог\n' >&2
        exit 1
    fi

### 11.3. Дата й час у логах

    log_info() {
        printf '[%s] [INFO] %s\n' \
            "$(date '+%Y-%m-%d %H:%M:%S')" "$*"
    }

    log_error() {
        printf '[%s] [ERROR] %s\n' \
            "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2
    }

    log_info "Запуск"
    log_error "Не вдалося прочитати файл"

Для системної автоматизації часові мітки допомагають з'ясувати, коли саме виникла помилка.

## 12. Практичний приклад: надійний Bash-скрипт

Створимо скрипт, який перевіряє вхідний файл і записує його вміст у вихідний файл.

### 12.1. Вимоги

Скрипт повинен:

- приймати два аргументи: вхідний і вихідний файли;
- перевіряти кількість аргументів;
- перевіряти вхідний файл;
- створювати каталог вихідного файлу, якщо це можливо;
- перевіряти результат копіювання;
- повідомляти про помилки в stderr;
- завершуватися з відповідним кодом.

### 12.2. Код скрипту

    #!/usr/bin/env bash

    set -u
    set -o pipefail

    error() {
        printf 'Помилка: %s\n' "$*" >&2
    }

    if [[ $# -ne 2 ]]; then
        error "Використання: $0 <вхідний-файл> <вихідний-файл>"
        exit 2
    fi

    source_file="$1"
    destination_file="$2"

    if [[ ! -f "$source_file" ]]; then
        error "Вхідний файл не знайдено: $source_file"
        exit 1
    fi

    if [[ ! -r "$source_file" ]]; then
        error "Вхідний файл недоступний для читання: $source_file"
        exit 1
    fi

    destination_dir="$(dirname -- "$destination_file")"

    if ! mkdir -p -- "$destination_dir"; then
        error "Не вдалося створити каталог: $destination_dir"
        exit 1
    fi

    if cp -- "$source_file" "$destination_file"; then
        printf 'Файл успішно скопійовано: %s\n' "$destination_file"
    else
        error "Не вдалося скопіювати файл"
        exit 1
    fi

### 12.3. Пояснення

- `set -u` допомагає виявляти використання незаданих змінних.
- `set -o pipefail` визначає поведінку кодів завершення конвеєрів, хоча в цьому прикладі конвеєрів немає.
- `error` виводить повідомлення до stderr.
- `$#` перевіряє кількість аргументів.
- `dirname` визначає каталог вихідного шляху.
- `mkdir -p` створює потрібний каталог.
- `cp` копіює файл.
- `if` перевіряє результат критичних операцій.

У цьому прикладі вихідний файл може бути перезаписаний, якщо вже існує. Для сценаріїв, де перезапис заборонений, потрібна додаткова перевірка або інший механізм створення файлу.

## 13. Типові помилки в обробці помилок

### Помилка 1. Перевіряють `$?` занадто пізно

Неправильно:

    cp source.txt backup/
    echo "Копіювання"
    echo "$?"

Проблема: `$?` містить результат `echo`, а не `cp`.

Правильно:

    cp source.txt backup/
    status=$?

    if [[ "$status" -eq 0 ]]; then
        echo "Копіювання успішне"
    else
        echo "Помилка копіювання" >&2
        exit "$status"
    fi

Або:

    if cp source.txt backup/; then
        echo "Копіювання успішне"
    else
        echo "Помилка копіювання" >&2
        exit 1
    fi

### Помилка 2. Повідомлення про помилку виводять у stdout

Небажано:

    echo "Помилка: файл не знайдено"

Рекомендовано:

    echo "Помилка: файл не знайдено" >&2

Це дозволяє відокремити звичайні дані від діагностичних повідомлень.

### Помилка 3. Вважають, що `set -e` ловить усі помилки

    set -e

    false
    echo "Продовження"

У цьому простому випадку `echo` зазвичай не виконається. Проте в складніших умовах, функціях, конвеєрах і логічних списках `set -e` має винятки.

Для важливих команд явно перевіряй результат:

    if some_command; then
        echo "Успіх"
    else
        echo "Помилка" >&2
        exit 1
    fi

### Помилка 4. Використовують `exit` усередині функції без потреби

Небажано для функції, яку планують повторно використовувати:

    check_file() {
        if [[ ! -f "$1" ]]; then
            echo "Файл не знайдено" >&2
            exit 1
        fi
    }

Ця функція завершує весь скрипт.

Гнучкіший варіант:

    check_file() {
        if [[ ! -f "$1" ]]; then
            echo "Файл не знайдено" >&2
            return 1
        fi
    }

    if ! check_file "config.txt"; then
        exit 1
    fi

### Помилка 5. Ігнорують код завершення зовнішньої команди

Небажано:

    mkdir -p "reports"
    echo "Готово"

Краще:

    if mkdir -p "reports"; then
        echo "Каталог готовий"
    else
        echo "Помилка створення каталогу" >&2
        exit 1
    fi

### Помилка 6. Приховують усі помилки через `/dev/null`

    some_command >/dev/null 2>&1

Це приховує і звичайний вивід, і повідомлення про помилки.

Використовуй такий підхід лише тоді, коли обидва потоки справді не потрібні. Інакше приховані повідомлення можуть ускладнити діагностику.

### Помилка 7. Не враховують помилки всередині конвеєра

    cat data.txt | grep "error" | sort

Якщо `cat` завершиться невдало, а остання команда успішно виконається, звичайний код завершення конвеєра може приховати проблему.

Використовуй `set -o pipefail`, коли важливо враховувати помилки попередніх команд конвеєра.

### Помилка 8. Вважають, що будь-який ненульовий код означає аварію

Наприклад, `grep` повертає `1`, коли збігів не знайдено. Це може бути нормальним результатом пошуку.

Потрібно розрізняти:

- успішне знаходження;
- відсутність збігів;
- справжню помилку виконання.

### Помилка 9. Використовують `trap ERR` як універсальний обробник

`ERR` не спрацьовує в усіх ситуаціях, де команда повертає ненульовий код. Його поведінка залежить від контексту Bash.

Використовуй `trap ERR` як допоміжний механізм діагностики, а критичні операції перевіряй явно.

## 14. Налагодження скриптів

### 14.1. Перевірка синтаксису

    bash -n script.sh

Перевіряє синтаксис без виконання команд скрипту.

### 14.2. Трасування команд

    bash -x script.sh

Виводить команди під час виконання та допомагає з'ясувати, де виникає проблема.

### 14.3. Перевірка коду завершення

    ./script.sh
    status=$?

    printf 'Код завершення: %s\n' "$status"

Зберігай `$?` одразу після команди, результат якої потрібно перевірити.

### 14.4. Перевірка через ShellCheck

    shellcheck script.sh

ShellCheck може знайти типові помилки Bash, зокрема неправильне використання змінних, лапок, умов та деяких конструкцій обробки помилок.

## 15. Практичні завдання

### Завдання 1. Перевірка аргументів

Створи скрипт, який вимагає рівно один аргумент.

Якщо аргумент відсутній або їх більше одного, виведи повідомлення в stderr і заверши скрипт із кодом `2`.

### Завдання 2. Перевірка файлу

Створи скрипт, який перевіряє існування звичайного файлу.

Якщо файл відсутній, виведи повідомлення й заверши скрипт із кодом `1`.

### Завдання 3. Копіювання з перевіркою

Створи скрипт, який копіює файл до іншого каталогу.

Перевір результат `cp` і виведи повідомлення про успіх або помилку.

### Завдання 4. Функція `die`

Створи функцію `die`, яка:

- приймає код завершення;
- приймає повідомлення;
- виводить повідомлення в stderr;
- завершує скрипт із заданим кодом.

### Завдання 5. Логування

Створи функції `log_info`, `log_warn` і `log_error`.

Інформаційні повідомлення виводь у stdout, а попередження та помилки — у stderr.

### Завдання 6. Робота з `set -u`

Створи скрипт із `set -u`.

Спробуй прочитати незадану змінну, а потім виправ код за допомогою `${variable:-}`.

### Завдання 7. Перевірка pipeline

Створи конвеєр, у якому перша команда завершується невдало, а остання — успішно.

Перевір різницю між поведінкою без `pipefail` і з `set -o pipefail`.

### Завдання 8. Обробник EXIT

Створи тимчасовий файл через `mktemp`.

Встанови `trap`, який видаляє його під час завершення скрипту.

Перевір, що файл видаляється після звичайного завершення.

### Завдання 9. Перевірка результату `grep`

Напиши скрипт, який розрізняє три ситуації:

- знайдено збіг;
- збігів немає;
- команда завершилася через помилку.

### Завдання 10. Повний скрипт

Створи `safe-copy.sh`, який:

- перевіряє аргументи;
- перевіряє вхідний файл;
- створює вихідний каталог;
- копіює файл;
- обробляє помилки;
- повертає правильні коди завершення;
- виводить помилки у stderr.

## 17. Що потрібно запам'ятати

✔ Код завершення `0` зазвичай означає успіх.

✔ Ненульовий код зазвичай означає невдачу або інший неуспішний результат.

✔ `$?` зберігає код завершення останньої виконаної команди.

✔ Перевіряй критичні команди через `if`.

✔ `exit` завершує скрипт, а `return` — функцію.

✔ Повідомлення про помилки зазвичай потрібно виводити в stderr через `>&2`.

✔ `&&` виконує наступну команду лише за успіху попередньої.

✔ `||` виконує наступну команду за невдачі попередньої.

✔ `set -e` допомагає виявляти певні помилки, але має винятки.

✔ `set -u` допомагає виявляти використання незаданих змінних.

✔ `set -o pipefail` дозволяє враховувати невдалі команди всередині конвеєрів.

✔ `trap EXIT` корисний для очищення тимчасових ресурсів під час завершення скрипту.

✔ `trap ERR` не є універсальним механізмом перехоплення всіх помилок.

✔ Не кожен ненульовий код є аварією: наприклад, `grep` повертає `1`, якщо збігів немає.

✔ Для налагодження використовуй `bash -n`, `bash -x` і `shellcheck`.

## 18. Мінішпаргалка

| Завдання | Синтаксис |
|---|---|
| Перевірити код завершення | `echo "$?"` |
| Завершити успішно | `exit 0` |
| Завершити з помилкою | `exit 1` |
| Завершити функцію з помилкою | `return 1` |
| Перевірити команду | `if command; then ...; else ...; fi` |
| Вивести помилку в stderr | `printf 'Помилка\n' >&2` |
| Виконати за успіху | `command1 && command2` |
| Виконати за невдачі | `command1 || command2` |
| Увімкнути `errexit` | `set -e` |
| Увімкнути `nounset` | `set -u` |
| Увімкнути `pipefail` | `set -o pipefail` |
| Увімкнути строгі параметри | `set -euo pipefail` |
| Обробити завершення | `trap cleanup EXIT` |
| Обробити багато невдалих команд | `trap '...' ERR` |
| Перевірити синтаксис | `bash -n script.sh` |
| Трасувати виконання | `bash -x script.sh` |
| Перевірити стиль | `shellcheck script.sh` |
| Перенаправити stderr у файл | `command 2> errors.log` |
| Додати stderr у файл | `command 2>> errors.log` |
| Приховати stderr | `command 2>/dev/null` |

## 19. Підсумок

Обробка помилок — основа надійної автоматизації в Bash. Вона дозволяє скриптам правильно реагувати на невдалі команди, відсутні файли, неправильні аргументи та проблеми з доступом.

Для впевненої роботи потрібно вміти:

- перевіряти коди завершення;
- розрізняти stdout і stderr;
- використовувати `if`, `&&` та `||`;
- повертати відповідні коди через `return` і `exit`;
- розуміти особливості `set -e`, `set -u` та `pipefail`;
- застосовувати `trap` для очищення ресурсів і обробки певних подій;
- створювати зрозумілі повідомлення про помилки;
- налагоджувати скрипти за допомогою Bash і ShellCheck.

Головне правило: **не припускай, що команда завершилася успішно, — перевіряй результат критичних операцій і повертай зрозумілий код завершення.**
