# Jobs and Processes

Завдання оболонки (jobs), системні процеси (processes), їхні PID і PPID, дерево процесів, групи процесів, керування дочірніми процесами та взаємодія між Bash і операційною системою Linux.

## 1. Що таке Jobs and Processes?

У Linux поняття **process (процес)** і **job (завдання оболонки)** пов'язані, але не тотожні.

**Процес (process)** — це екземпляр програми, який виконується або очікує на виконання операційною системою. Кожен процес має ідентифікатор PID, стан, власника та інші характеристики.

**Завдання оболонки (job)** — це одиниця роботи, яку оболонка, наприклад Bash, відстежує за допомогою механізму керування завданнями (job control). Одне завдання може містити один або декілька процесів.

Наприклад:

    sleep 60

Ця команда запускає процес `sleep` на передньому плані.

А команда:

    sleep 60 &

запускає його у фоновому режимі. Bash зазвичай реєструє цей запуск як завдання оболонки.

Якщо виконати конвеєр:

    cat file.txt | grep "Linux" | sort

оболонка може створити кілька процесів, які працюють разом як одне завдання.

Отже:

- процес — це об'єкт, яким керує ядро Linux;
- завдання — це об'єкт керування оболонки;
- одне завдання може складатися з кількох процесів;
- не кожен процес системи є завданням поточної оболонки.

## 2. Коли це потрібно?

✔ Розуміти, як Bash запускає та відстежує команди.

✔ Розрізняти PID, PPID і Job ID.

✔ Переглядати процеси за допомогою `ps`, `top` і `pstree`.

✔ Керувати фоновими та призупиненими завданнями.

✔ Розуміти, як працюють конвеєри команд.

✔ З'ясовувати, які процеси належать одному завданню.

✔ Визначати батьківські та дочірні процеси.

✔ Розуміти, чому процес може залишатися після завершення оболонки.

✔ Знати різницю між процесом, потоком, завданням оболонки та системною службою.

✔ Правильно завершувати процеси й не зупиняти випадково інші програми.

## 3. Основні команди

| Команда | Призначення |
|---|---|
| `ps` | Перегляд процесів |
| `ps aux` | Перегляд процесів системи у форматі BSD |
| `ps -ef` | Перегляд процесів у форматі System V |
| `jobs` | Перегляд завдань поточної оболонки |
| `jobs -l` | Перегляд завдань із PID |
| `pgrep` | Пошук процесів за назвою або критеріями |
| `pstree` | Відображення дерева процесів |
| `top` | Моніторинг процесів у реальному часі |
| `htop` | Інтерактивний монітор процесів, якщо встановлений |
| `fg` | Переміщення завдання на передній план |
| `bg` | Продовження призупиненого завдання у фоні |
| `wait` | Очікування завершення дочірніх процесів |
| `kill` | Надсилання сигналу процесу або завданню |
| `nice` | Запуск процесу з певним значенням nice |
| `renice` | Зміна значення nice запущеного процесу |

## 4. Що потрібно пам'ятати

- PID — ідентифікатор процесу.
- PPID — ідентифікатор батьківського процесу.
- Job ID — номер завдання в поточній оболонці, наприклад `%1`.
- Job ID і PID — різні ідентифікатори.
- `jobs` показує завдання поточної оболонки, а не всі процеси системи.
- `ps` показує процеси, а не лише завдання оболонки.
- Конвеєр може містити кілька процесів, об'єднаних в одне завдання.
- Батьківський процес може створювати дочірні процеси.
- Дочірній процес не обов'язково завершується одночасно з батьківським.
- `&` запускає команду у фоновому режимі, але не гарантує її незалежність від термінала.
- `Ctrl + Z` зазвичай призупиняє foreground-завдання, а `Ctrl + C` зазвичай надсилає `SIGINT`.
- Процес, завдання оболонки та системна служба — не одне й те саме.

# 5. Що таке процес?

Процес — це запущений екземпляр програми, яким керує ядро операційної системи.

Наприклад, коли ти виконуєш:

    node server.js

оболонка запускає Node.js, який виконує файл `server.js`.

У системі з'являється процес або група пов'язаних процесів, залежно від способу запуску та роботи програми.

Процес має певні характеристики:

- PID — ідентифікатор;
- PPID — ідентифікатор батьківського процесу;
- UID і користувач-власник;
- стан виконання;
- пріоритет планування;
- використання пам'яті та процесорного часу;
- відкриті файлові дескриптори;
- змінні середовища та аргументи запуску;
- зв'язки з іншими процесами.

Не всі ці характеристики видно в одному виводі `ps`. Для різних завдань використовують різні параметри.

## 5.1. Переглянути процеси

    ps

Ця команда показує процеси, пов'язані з поточним терміналом відповідно до стандартного режиму `ps`.

Щоб переглянути ширший список процесів:

    ps aux

Або:

    ps -ef

Обидва варіанти використовуються для перегляду великої кількості процесів, але формат їхнього виводу відрізняється.

## 5.2. Переглянути конкретний процес

    ps -p 1234 -f

Заміни `1234` на реальний PID.

Щоб побачити PID, PPID, стан і команду:

    ps -p 1234 -o pid,ppid,stat,comm,args

Це допомагає зрозуміти, який саме процес ти досліджуєш.

# 6. Що таке завдання оболонки (job)?

Завдання оболонки — це команда або конвеєр команд, якими оболонка керує за допомогою job control.

Наприклад:

    sleep 60 &

Bash запускає команду у фоновому режимі й зазвичай призначає їй Job ID.

Приклад умовного повідомлення:

    [1] 2468

Тут:

- `[1]` — номер завдання;
- `2468` — PID процесу, який запускається.

Для цього простого прикладу завдання містить один процес. Для конвеєра воно може містити декілька процесів.

## 6.1. Переглянути завдання

    jobs

Приклад:

    [1]+  Running    sleep 60 &

## 6.2. Переглянути завдання з PID

    jobs -l

Приклад:

    [1]+ 2468 Running    sleep 60 &

## 6.3. Чому jobs показує не все?

Команда:

    jobs

показує завдання, які відстежує поточна оболонка.

Якщо ти відкриєш інший термінал, він матиме інший контекст керування завданнями. Його `jobs` не обов'язково покаже процеси, запущені в першому терміналі.

Для перегляду процесів системи використовуй:

    ps aux

Для пошуку конкретного процесу:

    pgrep -a node

## 6.4. Чи може одне завдання мати кілька процесів?

Так.

Приклад:

    sleep 100 | cat &

Це конвеєр із двох команд. Bash зазвичай запускає кожну команду конвеєра в окремому процесі та керує конвеєром як одним завданням.

Точні деталі залежать від оболонки й особливостей виконання команд, але головний принцип такий: **одне завдання може включати кілька процесів**.

# 7. PID, PPID і Job ID

Ці три поняття потрібно чітко розрізняти.

## 7.1. PID

PID (Process ID) — унікальний у певний момент часу ідентифікатор процесу.

Переглянути PID:

    pgrep -a sleep

Або:

    ps -eo pid,comm,args

Приклад умовного результату:

    2468 sleep 60

Тут `2468` — PID.

PID може бути повторно використаний системою після завершення процесу, тому не слід вважати, що конкретне число назавжди відповідає певній програмі.

## 7.2. PPID

PPID (Parent Process ID) — ідентифікатор батьківського процесу.

Переглянути PID і PPID:

    ps -eo pid,ppid,comm,args

Приклад умовного виводу:

    PID   PPID  COMMAND
    1000  950   bash
    2468  1000  sleep

У цьому прикладі процес `sleep` має PPID `1000`, тобто його батьківським процесом є процес із PID `1000`.

Це лише спрощена ілюстрація. Реальні PID та зв'язки залежать від системи.

## 7.3. Job ID

Job ID — номер завдання в поточній оболонці.

Приклад:

    sleep 60 &

Оболонка може вивести:

    [1] 2468

У цьому випадку:

- Job ID — `1`;
- PID — `2468`.

Для керування завданням оболонки:

    fg %1

Для надсилання сигналу процесу:

    kill -TERM 2468

У Bash можна також надсилати сигнал завданню через його специфікацію:

    kill -TERM %1

## 7.4. Порівняння

| Поняття | Значення | Приклад |
|---|---|---|
| PID | Ідентифікатор процесу | `2468` |
| PPID | Ідентифікатор батьківського процесу | `1000` |
| Job ID | Номер завдання оболонки | `%1` |

# 8. Батьківські та дочірні процеси

Процеси в Linux можуть створювати інші процеси.

- **Батьківський процес (parent)** — процес, який створив інший процес.
- **Дочірній процес (child)** — процес, створений іншим процесом.

Наприклад, коли Bash запускає зовнішню команду, він може створити дочірній процес для її виконання.

Спрощена схема:

    bash
    └── sleep

Якщо запустити конвеєр, структура може бути складнішою:

    bash
    ├── cat
    ├── grep
    └── sort

Це схематичні приклади, а не гарантоване дерево для кожного способу запуску.

## 8.1. Подивитися на батьківський процес

    ps -p 2468 -o pid,ppid,comm,args

Якщо PID процесу — `2468`, поле `PPID` покаже PID його батьківського процесу.

## 8.2. Переглянути дерево процесів

    pstree

Якщо команда не встановлена, в Ubuntu її зазвичай можна отримати через пакет `psmisc`:

    sudo apt update
    sudo apt install psmisc

Переглянути дерево з PID:

    pstree -p

Переглянути дерево конкретного процесу:

    pstree -p 2468

Це допомагає побачити, як процеси пов'язані між собою.

## 8.3. Чому дерево процесів корисне?

Дерево процесів допомагає:

- знайти батьківський процес;
- зрозуміти, хто запустив певну програму;
- дослідити дочірні процеси;
- розібратися, чому після завершення одного процесу інші продовжують працювати;
- визначити, які процеси належать до однієї програми або служби.

# 9. Як Bash керує завданнями?

Bash має механізм керування завданнями (job control), який дає змогу працювати з foreground і background-завданнями.

Основні команди:

    jobs
    fg
    bg
    wait

## 9.1. Запустити фонове завдання

    sleep 300 &

## 9.2. Переглянути список

    jobs -l

## 9.3. Повернути на передній план

    fg %1

## 9.4. Призупинити

Під час виконання foreground-завдання натисни:

    Ctrl + Z

## 9.5. Продовжити у фоні

    bg %1

## 9.6. Дочекатися завершення

    wait %1

Команда `wait` може чекати завершення відповідного дочірнього процесу або завдання, відомого оболонці. Її точна поведінка залежить від аргументів і стану завдання.

Важливо: `fg` і `bg` керують завданнями оболонки, а не будь-якими довільними процесами системи.

---

# 10. Що таке група процесів?

Група процесів (process group) — це набір процесів, об'єднаних спільним ідентифікатором PGID (Process Group ID).

Групи процесів важливі для керування завданнями та сигналами.

Наприклад, конвеєр:

    cat file.txt | grep Linux | sort

може працювати як одне завдання оболонки, що складається з кількох процесів в одній групі процесів.

Це дає змогу оболонці керувати пов'язаними процесами разом, зокрема передавати керування терміналом foreground-завданню.

## 10.1. Переглянути PGID

    ps -eo pid,ppid,pgid,sid,stat,comm,args

Основні поля:

- `PID` — ідентифікатор процесу;
- `PPID` — ідентифікатор батьківського процесу;
- `PGID` — ідентифікатор групи процесів;
- `SID` — ідентифікатор сесії;
- `STAT` — стан процесу.

## 10.2. Чому це важливо?

Коли ти натискаєш `Ctrl + C`, сигнал зазвичай надсилається foreground-групі процесів керівного термінала.

Це дозволяє перервати не лише одну команду, а й пов'язаний конвеєр.

Наприклад:

    sleep 300 | cat

Якщо конвеєр виконується на передньому плані, натискання `Ctrl + C` зазвичай перериває відповідну foreground-групу процесів.

## 10.3. Не плутай групу процесів із завданням

Зазвичай одне завдання оболонки відповідає одній групі процесів, але ці поняття описують різні рівні керування:

- job — поняття оболонки;
- process group — поняття операційної системи;
- process — окремий процес.

# 11. Що таке сесія процесів?

Сесія (session) — це група груп процесів, які пов'язані між собою на рівні керування процесами.

У Linux сесії важливі для:

- керівних терміналів;
- груп процесів;
- керування завданнями;
- від'єднання процесів від термінала;
- роботи оболонок та інтерактивних сеансів.

Переглянути ідентифікатор сесії:

    ps -eo pid,ppid,pgid,sid,tty,stat,comm,args

Поле `SID` показує ідентифікатор сесії процесу.

## 11.1. Як це пов'язано з терміналом?

Інтерактивна оболонка зазвичай працює в сесії, пов'язаній із терміналом.

Коли запускається foreground-завдання, оболонка передає йому керування терміналом.

Після завершення або призупинення завдання оболонка зазвичай повертає керування собі.

Цей механізм пояснює, чому `Ctrl + C` і `Ctrl + Z` впливають на активне foreground-завдання, а не довільно на всі процеси системи.

# 12. Конвеєри та завдання

Конвеєр (pipeline) з'єднує стандартне виведення однієї команди зі стандартним введенням іншої.

Приклад:

    ps aux | grep node

Команда `ps aux` формує список процесів, а `grep node` відбирає рядки, що містять `node`.

У звичайному випадку оболонка створює окремі процеси для зовнішніх команд конвеєра.

## 12.1. Запустити конвеєр у фоні

    sleep 100 | cat &

Оболонка зазвичай реєструє цей конвеєр як одне фонове завдання.

Переглянути:

    jobs -l

## 12.2. Чому один job може мати кілька PID?

Тому що конвеєр складається з кількох команд, які можуть виконуватися в різних процесах.

Наприклад:

    cat file.txt | grep Linux | sort

У спрощеній моделі це три процеси:

- `cat`;
- `grep`;
- `sort`.

Але оболонка керує їхньою роботою як одним завданням.

## 12.3. Переглянути процеси конвеєра

Якщо конвеєр ще працює, спробуй:

    ps -eo pid,ppid,pgid,stat,comm,args

У деяких випадках процеси завершуються настільки швидко, що їх важко побачити. Для навчального експерименту можна використати `sleep`:

    sleep 100 | cat &

Потім:

    jobs -l
    ps -eo pid,ppid,pgid,stat,comm,args

# 13. Фонові процеси та завершення оболонки

Фоновий процес не обов'язково припиняється разом із завершенням оболонки, але й не гарантовано продовжить роботу.

Наприклад:

    sleep 300 &

Це створює фонове завдання. Якщо оболонка завершиться, поведінка процесу залежатиме від сигналів, налаштувань оболонки та способу запуску.

У багатьох сценаріях процес може отримати `SIGHUP`.

## 13.1. Перевірити, чи процес працює

    pgrep -a sleep

Або:

    ps -eo pid,ppid,stat,comm,args

## 13.2. Що робить nohup?

Команда `nohup` запускає програму з ігноруванням `SIGHUP`.

Приклад:

    nohup sleep 300 >sleep.log 2>&1 &

Однак `nohup` не є менеджером служб і не гарантує автоматичного перезапуску процесу після аварійного завершення.

## 13.3. Що робить disown?

У Bash команда `disown` вилучає завдання зі списку завдань оболонки.

Приклад:

    sleep 300 &
    disown %1

Це змінює спосіб, у який Bash відстежує завдання, але не є універсальною заміною `systemd` або `tmux`.

## 13.4. Коли використовувати tmux?

`tmux` дозволяє створити сесію термінала, від'єднатися від неї та пізніше повернутися.

    tmux new -s dev

Щоб від'єднатися від сесії:

    Ctrl + B
    D

Щоб повернутися:

    tmux attach -t dev

Це зручно для тривалих задач, особливо через SSH.

# 14. Процеси та системні служби

Процес і системна служба — не тотожні поняття.

**Процес** — це екземпляр програми, який виконується в системі.

**Служба (service)** — програмний компонент, який виконує певну функцію системи або застосунку. У Linux служба часто керується менеджером служб, наприклад `systemd`.

Наприклад, вебсервер може працювати як процес і водночас бути частиною служби `nginx.service`.

## 14.1. Переглянути службу

    systemctl status nginx

Це приклад для системи, де встановлено `nginx.service`. Якщо такої служби немає, команда повідомить про помилку.

## 14.2. Чому не завжди варто використовувати kill?

Якщо процес належить системній службі, його примусове завершення через `kill` може призвести до того, що:

- менеджер служб перезапустить його;
- служба тимчасово перестане працювати;
- буде втрачено незавершені операції;
- журнали покажуть помилку або аварійне завершення.

Для служб зазвичай краще використовувати відповідний менеджер:

    sudo systemctl stop nginx

Ця команда зупиняє службу `nginx`, якщо вона існує і користувач має необхідні права.

Для власного тестового процесу `sleep` команда `kill` доречна. Для керованих системних служб зазвичай варто починати з `systemctl`.

# 15. Процеси та потоки

Процес і потік (thread) — це різні поняття.

**Процес** має власний адресний простір і системні ресурси.

**Потік** — це одиниця виконання всередині процесу. Потоки одного процесу зазвичай спільно використовують його адресний простір та багато ресурсів.

Одна програма може створювати кілька потоків, які працюють паралельно або конкурують за процесорний час.

## 15.1. Переглянути потоки через ps

    ps -eLf

Ця команда показує процеси та їхні потоки у форматі, який містить додаткові поля для потоків.

## 15.2. Переглянути потоки через top

Запусти:

    top

У багатьох версіях `top` клавіша `H` перемикає показ потоків. Точна поведінка може залежати від версії та конфігурації.

## 15.3. Що потрібно запам'ятати?

- процес — не те саме, що потік;
- один процес може мати багато потоків;
- потоки одного процесу зазвичай спільно використовують пам'ять процесу;
- `jobs` не є інструментом для повного перегляду потоків;
- для перегляду потоків використовуй `ps -eLf` або відповідні можливості `top`.

# 16. Стани процесів

Процес не завжди виконується безперервно. Він може працювати, чекати на подію або бути призупиненим.

Переглянути стани:

    ps -eo pid,ppid,stat,comm,args

Основні позначення:

| Символ | Значення |
|---|---|
| `R` | Процес виконується або готовий до виконання |
| `S` | Переривний сон, очікування події |
| `D` | Непереривний сон, часто очікування операції введення-виведення |
| `T` | Процес зупинено або призупинено |
| `Z` | Процес-зомбі |

У полі `STAT` можуть бути додаткові символи, що описують властивості процесу.

## 16.1. Running

Процес у стані `R` виконується або готовий до виконання, очікуючи процесорного часу.

## 16.2. Sleeping

Процес у стані `S` чекає на подію. Наприклад, `sleep 60` проводить більшу частину часу в очікуванні.

## 16.3. Stopped

Процес у стані `T` призупинений, наприклад, через `Ctrl + Z` або сигнал `SIGSTOP`.

## 16.4. Zombie

Зомбі — це процес, який уже завершив виконання, але його батьківський процес ще не забрав код завершення.

Надсилання `SIGKILL` зомбі зазвичай не допомагає, оскільки він уже завершив роботу. Потрібно дослідити батьківський процес.

# 19. Типові помилки

## Помилка 1. Плутати процес і завдання

Процесом керує ядро Linux, а завданням оболонки — механізм job control.

Одне завдання може містити кілька процесів.

## Помилка 2. Вважати, що jobs показує всі процеси

    jobs

Показує завдання поточної оболонки. Для системних процесів використовуй `ps` або `top`.

## Помилка 3. Плутати PID і Job ID

    fg %1

Тут `%1` — номер завдання, а не PID.

## Помилка 4. Вважати, що PPID не змінюється

Якщо батьківський процес завершується, дочірній процес може бути перепризначений іншому процесу, наприклад відповідному системному процесу. Тому PPID може змінитися протягом життя процесу.

## Помилка 5. Вважати, що кожна команда створює лише один процес

Конвеєри, оболонки та складні програми можуть створювати кілька процесів.

## Помилка 6. Вважати, що всі процеси Node.js належать одному серверу

Можуть одночасно працювати кілька незалежних Node.js-застосунків. Перед завершенням процесу перевіряй його аргументи.

## Помилка 7. Завершувати системні процеси без перевірки

Не надсилай сигнали процесам навмання. Спочатку з'ясуй їхнє призначення та зв'язки з іншими процесами.

## Помилка 8. Вважати, що фоновий процес обов'язково переживе закриття термінала

Звичайний запуск через `&` цього не гарантує.

## Помилка 9. Плутати процес і службу

Процес — це екземпляр програми. Служба — керований системою компонент, який може включати один або кілька процесів.

# 23. Головне

У Linux потрібно розрізняти три основні поняття:

- **Process** — процес, яким керує ядро операційної системи.
- **Job** — завдання, яким керує поточна оболонка.
- **Process group** — група процесів, яка використовується, зокрема, для керування завданнями та сигналами.

Запам'ятай базову послідовність:

    jobs -l
    ps -eo pid,ppid,pgid,sid,stat,comm,args
    pgrep -af "node server.js"
    pstree -p

Ці команди допомагають побачити завдання оболонки, знайти процес, дослідити його батьківський процес і зрозуміти структуру системи.

**Основна ідея:** `jobs` пояснює, якими завданнями керує твоя оболонка, а `ps`, `pgrep` і `pstree` допомагають досліджувати процеси та їхні зв'язки в Linux.
