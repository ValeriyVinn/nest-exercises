# 01. ps

`ps` (process status) — це команда Linux, яка дозволяє переглядати інформацію про процеси, що виконуються в системі.

Команда використовується, коли потрібно:

- переглянути запущені процеси;
- знайти процес за назвою або PID;
- побачити, який користувач запустив процес;
- перевірити використання CPU та пам'яті;
- переглянути стан процесу;
- визначити батьківський процес;
- перевірити процеси термінала;
- знайти процеси Node.js, PostgreSQL або інших програм;
- діагностувати проблеми із завислими програмами;
- підготуватися до завершення процесу через `kill`.

Основні команди для роботи з процесами:

    ps
    ps aux
    ps -ef
    ps -u
    ps -p
    ps -C
    ps --forest
    pgrep
    pstree

Команда `ps` показує знімок стану процесів на момент виконання команди. Для постійного оновлення інформації використовують `top` або `htop`.

## Що потрібно пам'ятати

• Процес — це екземпляр програми, яка виконується в системі.

• Кожен процес має власний PID — ідентифікатор процесу.

• PPID — ідентифікатор батьківського процесу.

• `ps` показує інформацію про процеси у вигляді знімка на момент виконання команди.

• `ps` без параметрів зазвичай показує процеси, пов'язані з поточним терміналом.

• `ps aux` показує широкий перелік процесів системи в поширеному BSD-форматі.

• `ps -ef` показує процеси системи у форматі System V.

• `ps -u username` дозволяє переглянути процеси певного користувача.

• `ps -p PID` показує інформацію про процес із конкретним PID.

• `ps -C name` дозволяє знайти процеси за назвою виконуваного файлу.

• `ps --forest` допомагає побачити ієрархію процесів.

• `pgrep` дозволяє знаходити PID за назвою процесу або іншими критеріями.

• `pstree` показує процеси у вигляді дерева, якщо команда встановлена.

• `STAT` показує стан процесу, а не просто факт його існування.

• `ps` не є інструментом безперервного моніторингу. Для цього використовують `top` або `htop`.

• Для завершення процесу можна використати `kill PID`, але спочатку потрібно правильно визначити потрібний процес.

• Не слід завершувати процес лише через незнайому назву. Спочатку перевіряй PID, користувача та команду.

# Process

Process (процес) — це екземпляр програми, що виконується операційною системою.

Наприклад, коли ти запускаєш Node.js:

    node server.js

Linux створює процес, який виконує програму Node.js.

Переглянути процеси поточного термінала:

    ps

Приклад результату:

    PID TTY          TIME CMD
    2140 pts/0    00:00:00 bash
    2195 pts/0    00:00:00 ps

Тут:

    PID   → ідентифікатор процесу
    TTY   → пов'язаний термінал
    TIME  → накопичений CPU time
    CMD   → команда

Зверни увагу: числа PID у прикладі умовні. На твоєму комп'ютері вони будуть іншими.

Команда `ps` сама також створює процес на короткий час, тому її можна побачити у власному результаті.

---

# PID

PID (Process ID) — унікальний ідентифікатор процесу серед процесів, що одночасно існують у системі.

Наприклад:

    PID TTY          TIME CMD
    2140 pts/0    00:00:00 bash
    2250 pts/0    00:00:01 node

У цьому прикладі:

    2140 → PID процесу bash
    2250 → PID процесу node

PID потрібен, щоб:

    знайти конкретний процес
        ↓
    перевірити його стан
        ↓
    переглянути його характеристики
        ↓
    за потреби надіслати сигнал процесу

---

## Перегляд процесу за PID

Синтаксис:

    ps -p PID

Наприклад:

    ps -p 2250

Щоб побачити більше інформації:

    ps -fp 2250

Або вибрати конкретні поля:

    ps -p 2250 -o pid,ppid,user,stat,%cpu,%mem,cmd

Приклад результату:

    PID    PPID USER     STAT %CPU %MEM CMD
    2250   2100 valer    Sl    0.2  1.4 node server.js

Пояснення:

    PID   → ідентифікатор процесу
    PPID  → батьківський процес
    USER  → власник процесу
    STAT  → стан процесу
    %CPU  → використання CPU
    %MEM  → використання RAM
    CMD   → команда запуску

Якщо процес уже завершився, команда може не вивести жодного рядка з інформацією про нього.

---

# PPID

PPID (Parent Process ID) — PID батьківського процесу.

Процеси Linux часто утворюють ієрархію.

Наприклад:

    systemd
        └── terminal
              └── bash
                    └── node server.js

Це умовна схема для пояснення. Реальна ієрархія залежить від способу запуску програм.

У такій структурі:

    bash → parent process для node
    node → child process для bash

Переглянути PID і PPID:

    ps -o pid,ppid,cmd

Переглянути інформацію про конкретний процес:

    ps -p 2250 -o pid,ppid,cmd

PPID допомагає зрозуміти:

- який процес створив інший процес;
- як програми пов'язані між собою;
- звідки походить певний процес;
- чому процеси завершуються або продовжують працювати після закриття термінала.

---

# ps

`ps` без параметрів показує процеси, пов'язані з поточним терміналом.

Синтаксис:

    ps

Приклад:

    PID TTY          TIME CMD
    2140 pts/0    00:00:00 bash
    2310 pts/0    00:00:00 ps

Це корисно для швидкої перевірки процесів, запущених у поточному сеансі.

Але команда не показує повний перелік усіх процесів системи.

Для ширшого перегляду використовують:

    ps aux

або:

    ps -ef

---

# ps aux

`ps aux` — одна з найпоширеніших команд для перегляду процесів Linux.

    ps aux

Вона показує процеси різних користувачів, а не лише процеси поточного термінала.

Приклад результату:

    USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
    root         1  0.0  0.1 168000 12000 ?        Ss   10:00   0:02 /sbin/init
    valer     2140  0.0  0.1  12000  6000 pts/0    Ss   20:00   0:00 bash
    valer     2250  0.2  1.4 900000 70000 pts/0    Sl   20:01   0:01 node server.js

Це умовні дані для прикладу.

---

## Що означають колонки ps aux

### USER

Користувач, від імені якого виконується процес.

    USER
    root
    valer

`root` — суперкористувач Linux.

Інші процеси можуть працювати від імені звичайних користувачів або системних облікових записів.

### PID

Ідентифікатор процесу.

    PID
    1
    2140
    2250

### %CPU

Оцінка частки використання CPU процесом.

    %CPU
    0.0
    0.2
    15.4

Це значення залежить від системи та часу спостереження. Не слід трактувати його як точний миттєвий вимір.

### %MEM

Оцінка частки фізичної пам'яті, яку використовує процес.

    %MEM
    0.1
    1.4
    5.8

### VSZ

Virtual Memory Size — розмір віртуального адресного простору процесу, зазвичай у KiB у виводі procps-ng.

VSZ не дорівнює фактично зайнятій фізичній RAM.

### RSS

Resident Set Size — обсяг фізичної пам'яті, яка наразі перебуває в RAM і пов'язана з процесом.

RSS не слід просто підсумовувати між усіма процесами як точне споживання системної пам'яті: деякі сторінки пам'яті можуть бути спільними.

### TTY

Термінал, пов'язаний із процесом.

Наприклад:

    pts/0

Якщо процес не пов'язаний із терміналом, часто відображається:

    ?

### STAT

Стан процесу та додаткові ознаки.

Наприклад:

    R
    S
    D
    T
    Z

Ці значення розглянемо окремо.

### START

Час або дата запуску процесу — формат залежить від віку процесу та налаштувань виводу.

### TIME

Накопичений CPU time, витрачений процесом.

Це не час, який минув від запуску програми.

### COMMAND

Команда, пов'язана з процесом.

Наприклад:

    node server.js
    bash
    /usr/lib/systemd/systemd

---

# Що означають параметри aux

У команді:

    ps aux

параметри належать до традиційного BSD-синтаксису `ps`.

    a → показувати процеси, пов'язані з терміналами різних користувачів
    u → використовувати орієнтований на користувача формат виводу
    x → включати процеси без керуючого термінала

Разом вони дають зручний широкий перелік процесів.

Важливо: `aux` тут записується без дефіса, оскільки це BSD-стиль параметрів.

---

# ps -ef

`ps -ef` — інший поширений спосіб переглянути процеси системи.

    ps -ef

Приклад результату:

    UID          PID    PPID  C STIME TTY          TIME CMD
    root           1       0  0 10:00 ?        00:00:02 /sbin/init
    valer       2140    2000  0 20:00 pts/0    00:00:00 bash
    valer       2250    2140  0 20:01 pts/0    00:00:01 node server.js

Це умовні дані.

Основні колонки:

    UID   → користувач
    PID   → ідентифікатор процесу
    PPID  → ідентифікатор батьківського процесу
    C     → показник використання CPU у форматі цього виводу
    STIME → час запуску
    TTY   → термінал
    TIME  → накопичений CPU time
    CMD   → команда

---

## ps aux vs ps -ef

Обидві команди широко використовуються для перегляду процесів, але формат їхнього виводу відрізняється.

    ps aux
        → USER, PID, %CPU, %MEM, VSZ, RSS, STAT...

    ps -ef
        → UID, PID, PPID, C, STIME, TTY, TIME, CMD

Коли потрібно швидко оцінити пам'ять і CPU:

    ps aux

Коли потрібно побачити PPID та ієрархію запуску:

    ps -ef

Обидві команди корисні. Вибирай ту, яка краще відповідає задачі.

---

# ps -u

Параметр `-u` дозволяє вибрати процеси певного користувача.

Синтаксис:

    ps -u username

Наприклад:

    ps -u valer

У деяких системах команда показує орієнтований на користувача формат процесів вибраного користувача.

Щоб явно побачити процеси, що належать певному користувачу, можна використати:

    ps -u valer -o pid,ppid,stat,%cpu,%mem,cmd

Також поширений варіант:

    ps -U valer -u valer -o pid,ppid,user,stat,cmd

Різниця між параметрами:

    -u → вибір за ефективним UID у відповідних режимах ps
    -U → вибір за реальним UID

Для звичайних навчальних задач часто достатньо:

    ps -u valer

Заміни `valer` на ім'я свого користувача.

---

# ps -p

`ps -p` дозволяє переглянути один або кілька процесів за PID.

Синтаксис:

    ps -p PID

Приклад:

    ps -p 2250

Кілька PID:

    ps -p 2250,2300,2400

Вибрані колонки:

    ps -p 2250 -o pid,ppid,user,stat,etime,cmd

Тут:

    etime → час, що минув від запуску процесу

Це корисно, коли потрібно перевірити конкретний сервер, скрипт або іншу програму.

---

# ps -C

`ps -C` дозволяє вибирати процеси за назвою виконуваного файлу.

Синтаксис:

    ps -C process_name

Наприклад:

    ps -C node

Або:

    ps -C bash

З додатковою інформацією:

    ps -C node -o pid,ppid,user,stat,%cpu,%mem,cmd

Важливо: `ps -C node` шукає за назвою виконуваного файлу, а не за довільним текстом у повному командному рядку.

Якщо потрібно знайти процеси за фрагментом командного рядка, можна використати:

    pgrep -af 'node server.js'

Будь уважний: різні способи пошуку можуть повертати різні результати.

---

# Пошук процесів через ps і grep

Один зі звичних підходів:

    ps aux | grep node

Команда:

    ps aux
        ↓
    усі процеси у вибраному форматі
        ↓
    grep node
        ↓
    рядки, що містять node

Наприклад:

    ps aux | grep node

Можна побачити:

    valer     2250  0.2  1.4 ... node server.js
    valer     2410  0.0  0.0 ... grep --color=auto node

Другий рядок може належати самій команді `grep`.

Це нормальна поведінка: `grep` теж є процесом.

---

## Як уникнути рядка grep

Можна використати:

    ps aux | grep '[n]ode'

Або, що часто зручніше:

    pgrep -af node

Пояснення:

    pgrep → пошук процесів
    -a    → показувати командний рядок
    -f    → шукати за повним командним рядком

Використовуй `pgrep`, коли головне завдання — знайти відповідні процеси.

# STAT — стан процесу

Колонка `STAT` показує основний стан процесу та додаткові ознаки.

Найважливіші стани:

    R → Running або Runnable
    S → Interruptible sleep
    D → Uninterruptible sleep
    T → Stopped або traced
    Z → Zombie

---

## R — Running / Runnable

`R` означає, що процес виконується або готовий до виконання й очікує CPU.

Наприклад:

    PID STAT CMD
    2250 R    node server.js

Процес може перебувати в стані `R` навіть тоді, коли в конкретну мить він ще чекає своєї черги на процесор.

---

## S — Interruptible sleep

`S` означає, що процес очікує на певну подію, але може бути перерваний сигналом.

Наприклад, сервер може чекати на:

- мережеве з'єднання;
- введення;
- завершення операції;
- дані від іншого процесу.

Багато звичайних процесів тривалий час перебувають у стані `S`. Це не обов'язково означає проблему.

---

## D — Uninterruptible sleep

`D` означає, що процес перебуває в непереривному очікуванні, зазвичай пов'язаному з операціями ядра, часто введенням-виведенням.

Наприклад, процес може чекати на завершення операції з пристроєм або файловою системою.

Якщо процес довго перебуває в стані `D`, варто дослідити причину очікування.

Звичайний сигнал завершення може не подіяти, доки процес перебуває в цьому стані. Це не означає, що потрібно відразу застосовувати `kill -9`.

---

## T — Stopped / Traced

`T` означає, що процес зупинений або перебуває під трасуванням.

Процес може бути зупинений сигналом:

    SIGSTOP
    SIGTSTP

Наприклад, натискання `Ctrl+Z` у терміналі зазвичай призупиняє foreground job і переводить її процес у зупинений стан.

---

## Z — Zombie

Zombie — це завершений процес, для якого батьківський процес ще не забрав код завершення.

Такий процес уже не виконує звичайну роботу, але запис про нього тимчасово залишається в таблиці процесів.

Зомбі може відображатися приблизно так:

    PID  PPID STAT COMMAND
    2800 2140 Z    [worker] <defunct>

Що важливо:

- Zombie не є звичайним активним процесом.
- Він зазвичай не споживає помітного обсягу RAM як повноцінний процес.
- Надсилання `SIGKILL` самому зомбі не розв'язує проблему.
- Потрібно з'ясувати, чому батьківський процес не забирає статус завершення.
- Якщо батьківський процес завершиться, процес-сирота може бути перепризначений системному процесу, який згодом забере його статус.

---

## Додаткові символи STAT

Окрім основного стану, `STAT` може містити додаткові символи.

Наприклад:

    Ss
    Sl
    S+
    R+
    Z

У поширеному виводі procps-ng:

    s → лідер сеансу
    l → багатопотоковий процес
    + → процес належить до foreground process group термінала

Конкретний набір додаткових символів залежить від реалізації `ps`.

Не потрібно намагатися вивчити всі комбінації відразу. На початковому рівні достатньо впевнено розпізнавати `R`, `S`, `D`, `T` і `Z`.

# Показати стан процесів

Вивести PID, PPID, стан і команду:

    ps -eo pid,ppid,stat,cmd

Відсортувати або відфільтрувати результати можна додатковими інструментами.

Наприклад, знайти рядки зі станом, який містить `Z`:

    ps -eo pid,ppid,stat,cmd | grep ' Z'

Це навчальний приклад, а не ідеальний універсальний фільтр: текстовий `grep` може давати зайві збіги.

Для пошуку зомбі зручніше спочатку вивести всі процеси зі станом:

    ps -eo pid,ppid,stat,comm

Потім перевірити відповідні рядки.

---

# ps -o

Параметр `-o` дозволяє самостійно вибирати колонки, які потрібно показати.

Синтаксис:

    ps -o field1,field2,field3

Наприклад:

    ps -eo pid,ppid,user,stat,cmd

Тут:

    -e → вибрати всі процеси
    -o → задати формат виводу

Інший приклад:

    ps -eo pid,comm,%cpu,%mem

Ця команда показує:

    PID
    назву команди
    використання CPU
    використання пам'яті

Для перевірки конкретного процесу:

    ps -p 2250 -o pid,ppid,user,stat,etime,%cpu,%mem,cmd

---

## Корисні поля ps -o

    pid     → PID процесу
    ppid    → PPID
    user    → користувач
    uid     → числовий ідентифікатор користувача
    stat    → стан процесу
    comm    → назва виконуваного файлу
    cmd     → командний рядок
    etime   → час від запуску
    time    → накопичений CPU time
    %cpu    → оцінка використання CPU
    %mem    → оцінка використання RAM
    rss     → resident memory
    vsz     → virtual memory size
    tty     → термінал

Не всі формати та поля однаково підтримуються кожною реалізацією `ps`. Наведені приклади орієнтовані на типовий Linux із procps-ng.

# ps -e

Параметр `-e` вибирає всі процеси.

    ps -e

Зручніший формат:

    ps -ef

З вибраними колонками:

    ps -eo pid,ppid,stat,cmd

Різниця між командами:

    ps
        → зазвичай процеси поточного термінала

    ps -e
        → усі процеси

    ps -ef
        → усі процеси у форматі, що включає PPID

# ps --forest

`ps --forest` дозволяє показувати ієрархію процесів у вигляді дерева.

Наприклад:

    ps -ef --forest

Умовний результат:

    UID       PID  PPID CMD
    root        1     0 /sbin/init
    root      800     1  \_ /usr/lib/systemd/systemd --user
    valer    2100   800      \_ bash
    valer    2250  2100          \_ node server.js

Тут можна побачити приблизний зв'язок між батьківськими та дочірніми процесами.

Дерево корисне для розуміння:

- хто запустив процес;
- які дочірні процеси створює програма;
- як організовані системні служби;
- які процеси належать до одного ланцюжка запуску.

Фактичний вигляд дерева залежить від системи та доступного набору процесів.

# pgrep

`pgrep` — команда для пошуку процесів за назвою та іншими критеріями.

Знайти PID процесів за назвою:

    pgrep node

Показати PID процесів `bash`:

    pgrep bash

Показати PID і назви процесів:

    pgrep -l node

Показати PID та повний командний рядок:

    pgrep -af node

Основні параметри:

    -l → показувати назви процесів
    -a → показувати командний рядок
    -f → шукати за повним командним рядком

Точна поведінка пошуку залежить від параметрів. Якщо потрібно знайти конкретний сервер, перевіряй повний результат, щоб не переплутати схожі процеси.

# pstree

`pstree` — команда для відображення процесів у вигляді дерева.

Приклад:

    pstree

З PID:

    pstree -p

З інформацією про користувачів:

    pstree -u

Дерево може виглядати приблизно так:

    systemd(1)─┬─NetworkManager(...)
               ├─sshd(...)
               ├─systemd(...)
               └─bash(2100)───node(2250)

Це умовний приклад.

Команда `pstree` може бути відсутня в системі за замовчуванням.

На Ubuntu її зазвичай надає пакет:

    psmisc

За потреби встановити пакет можна так:

    sudo apt update
    sudo apt install psmisc

Встановлення пакетів потребує відповідних прав і доступу до репозиторіїв.

# Сортування процесів

Команда `ps` дозволяє сортувати процеси за певними полями.

Наприклад, за використанням CPU:

    ps -eo pid,ppid,%cpu,%mem,cmd --sort=-%cpu

Зверни увагу на:

    --sort=-%cpu

Мінус означає сортування за спаданням.

Процеси з більшим значенням `%CPU` опиняться вище.

За використанням пам'яті:

    ps -eo pid,ppid,%cpu,%mem,rss,cmd --sort=-%mem

За часом CPU:

    ps -eo pid,time,cmd --sort=-time

Так можна швидко побачити процеси з найбільшими значеннями відповідного показника.

Важливо: це знімок інформації, а не безперервний моніторинг.

# Пошук процесів Node.js

Під час розробки Node.js корисно перевіряти, чи працює сервер.

Наприклад:

    pgrep -af node

Або:

    ps aux | grep '[n]ode'

Якщо сервер запущений командою:

    node server.js

можна перевірити його PID і стан:

    ps -C node -o pid,ppid,user,stat,%cpu,%mem,etime,cmd

Якщо є декілька процесів Node.js, не припускай, що кожен із них — потрібний сервер.

Перевіряй:

    PID
    USER
    STAT
    COMMAND

Це особливо важливо, якщо паралельно працюють:

- Next.js;
- NestJS;
- Express;
- інші Node.js-скрипти;
- інструменти розробки.

# Пошук процесів PostgreSQL

Якщо PostgreSQL працює як системна служба, його процеси можуть бути запущені від імені системного користувача `postgres`.

Переглянути відповідні процеси:

    ps -u postgres -o pid,ppid,stat,cmd

Або:

    ps aux | grep '[p]ostgres'

У PostgreSQL може працювати декілька процесів, пов'язаних з одним екземпляром сервера.

Тому не слід вважати кожен рядок `postgres` окремим сервером або помилкою.

Для перевірки стану системної служби в Ubuntu використовують окремі команди, наприклад:

    systemctl status postgresql

`ps` показує процеси, а `systemctl` допомагає перевірити стан системної служби.

# Пошук процесів поточного користувача

Дізнатися ім'я поточного користувача:

    whoami

Переглянути процеси користувача:

    ps -u "$(whoami)" -o pid,ppid,stat,%cpu,%mem,cmd

Тут:

    whoami
        ↓
    повертає ім'я поточного користувача
        ↓
    "$(whoami)"
        ↓
    підставляє результат у команду ps

Це зручний шаблон для командного рядка.

# Час життя процесу

`ps` може показати, скільки часу минуло від запуску процесу.

Наприклад:

    ps -eo pid,etime,time,cmd

Тут:

    etime → elapsed time
    time  → накопичений CPU time

Це різні поняття.

Припустимо, Node.js-сервер працює вже 2 години, але більшу частину часу очікує запити.

Тоді:

    etime → приблизно 2 години
    time  → може становити лише кілька секунд або хвилин CPU time

Процес може довго існувати, майже не використовуючи CPU.

---

# ps і потоки

Linux-процес може містити декілька потоків виконання.

Щоб переглянути потоки:

    ps -eLf

Або для конкретного процесу:

    ps -T -p 2250

Параметр `-L` у поширеній реалізації procps-ng показує потоки у форматі списку процесів.

Зверни увагу: потоки — не те саме, що незалежні процеси.

Потоки одного процесу зазвичай спільно використовують його адресний простір і багато інших ресурсів.

Для початкового рівня достатньо знати, що:

    process → контейнер виконання програми
    thread  → окремий потік виконання всередині процесу

---

# ps і foreground / background

Процеси можуть запускатися у foreground або background відносно оболонки.

Наприклад, звичайний запуск:

    node server.js

Команда працює у foreground, а термінал очікує завершення команди.

Запуск у background:

    node server.js &

Символ `&` просить оболонку запустити команду у фоновому режимі.

Перевірити процес:

    ps -C node -o pid,ppid,stat,cmd

Але background process не обов'язково є daemon або системною службою.

Це різні поняття:

    foreground → команда працює у передньому плані оболонки
    background  → команда працює у фоновому режимі оболонки
    daemon      → процес, призначений для роботи у фоні без звичайної взаємодії з терміналом
    service     → служба, якою часто керує systemd або інша система ініціалізації

Детальніше background jobs розглядаються в темах:

    04-background-and-foreground
    05-jobs-and-processes

# ps і kill

`ps` допомагає знайти процес, а `kill` надсилає йому сигнал.

Спочатку знайди процес:

    ps -C node -o pid,ppid,user,stat,cmd

Припустимо, PID потрібного процесу — `2250`.

Надіслати сигнал завершення:

    kill 2250

За замовчуванням `kill PID` надсилає `SIGTERM`.

Цей сигнал дає процесу можливість коректно завершити роботу.

Якщо процес не реагує, існує примусовий варіант:

    kill -KILL 2250

Або:

    kill -9 2250

Але `SIGKILL` слід використовувати лише тоді, коли звичайне завершення не допомагає і ти впевнений, що вибрав правильний PID.

Не потрібно виконувати `kill` для невідомого процесу лише тому, що він споживає ресурси.

Детальніше сигнали розглядаються в темі:

    03-kill-and-signals

# Практичний сценарій: пошук процесу Node.js

Уявімо, що ти працюєш над NestJS або Express-проєктом і хочеш перевірити, чи залишився запущений сервер.

Крок 1. Знайди процеси Node.js.

    pgrep -af node

Крок 2. Визнач, який процес відповідає потрібному проєкту.

    PID
    USER
    COMMAND

Крок 3. Перевір його стан.

    ps -p PID -o pid,ppid,stat,%cpu,%mem,etime,cmd

Заміни `PID` на числовий ідентифікатор процесу.

Крок 4. Якщо сервер працює нормально, нічого не потрібно робити.

Крок 5. Якщо сервер завис або його потрібно зупинити, спочатку спробуй коректне завершення через термінал, у якому його запущено, або надішли `SIGTERM` конкретному процесу.

    kill PID

Крок 6. Перевір, чи завершився процес.

    ps -p PID

Якщо результат не містить рядка процесу, він, імовірно, вже завершився. Якщо процес зник і відразу з'явився новий PID, його міг автоматично перезапустити менеджер процесів або системна служба.

Не завершуй усі процеси Node.js без розбору: інші проєкти можуть використовувати їх одночасно.

# Типові помилки

## ❌ Вважати, що ps показує всі процеси

    ps

Без параметрів команда зазвичай показує лише процеси, пов'язані з поточним терміналом.

Щоб побачити широкий перелік:

    ps aux

Або:

    ps -ef

---

## ❌ Плутати PID і PPID

    PID  → ідентифікатор самого процесу
    PPID → ідентифікатор батьківського процесу

Це різні значення.

---

## ❌ Плутати CPU time та elapsed time

    TIME  → накопичений CPU time
    ETIME → час, що минув від запуску

Процес може існувати годинами, але використовувати CPU лише короткий час.

---

## ❌ Вважати стан S ознакою зависання

    S → Interruptible sleep

Процес може нормально очікувати на мережеві дані, введення або іншу подію.

Це не обов'язково помилка.

---

## ❌ Вважати, що будь-який процес у стані D можна завершити через kill -9

    D → Uninterruptible sleep

Процес може чекати на завершення операції ядра. Сигнал завершення може бути оброблений лише після виходу зі стану непереривного очікування.

Потрібно з'ясувати причину очікування.

---

## ❌ Надсилати SIGKILL зомбі

    Z → Zombie

Зомбі вже завершив виконання. `SIGKILL` не вирішує проблему незабраного статусу завершення.

Потрібно перевірити батьківський процес.

---

## ❌ Вважати ps aux і ps -ef абсолютно однаковими

Обидві команди показують багато процесів, але використовують різні стилі форматування.

    ps aux → формат із %CPU, %MEM, VSZ, RSS
    ps -ef → формат із PPID, STIME та іншими полями

---

## ❌ Завершувати процес лише за назвою

Наприклад:

    pkill node

Це може вплинути на декілька процесів Node.js одночасно.

Спочатку краще знайти потрібний процес:

    pgrep -af node

Потім перевірити його PID і командний рядок.

Для навчання безпечніше працювати з конкретним PID, який ти перевірив.

---

## ❌ Вважати %CPU точним миттєвим показником

`ps` показує оцінку використання CPU відповідно до своєї методики обчислення.

Для спостереження за змінами в часі краще використовувати:

    top

або:

    htop

---

## ❌ Вважати VSZ фактично зайнятою RAM

    VSZ → віртуальний адресний простір
    RSS → фізична пам'ять, що перебуває в RAM

Ці показники описують різні характеристики процесу.

---

## ❌ Забувати, що PID може повторно використовуватися

Після завершення процесу його PID згодом може бути призначений іншому процесу.

Тому не варто зберігати PID надовго й припускати, що він завжди належить тій самій програмі.

Перед важливою дією перевіряй процес повторно.

## Показати процеси

    ps

## Показати широкий перелік процесів

    ps aux

## Альтернативний формат

    ps -ef

## Показати PID та PPID

    ps -eo pid,ppid,cmd

## Знайти процес за PID

    ps -p 2250

## Показати детальну інформацію про PID

    ps -p 2250 -o pid,ppid,user,stat,%cpu,%mem,etime,cmd

## Знайти процес за назвою виконуваного файлу

    ps -C node -o pid,ppid,stat,cmd

## Знайти процеси за командним рядком

    pgrep -af node

## Показати процеси користувача

    ps -u "$(whoami)" -o pid,ppid,stat,cmd

## Показати дерево процесів

    ps -ef --forest

## Відсортувати за CPU

    ps -eo pid,%cpu,%mem,cmd --sort=-%cpu

## Відсортувати за пам'яттю

    ps -eo pid,%mem,rss,cmd --sort=-%mem

## Переглянути потоки

    ps -T -p 2250

    Z → zombie

    TIME → накопичений CPU time

# Головне

• `ps` — основна команда для отримання інформації про процеси Linux.

• `ps` показує знімок процесів на момент виконання команди.

• `ps aux` — зручний спосіб переглянути широкий перелік процесів, їхні CPU та memory показники.

• `ps -ef` — альтернативний формат із PID, PPID, часом запуску та іншими полями.

• PID ідентифікує процес, а PPID вказує на його батьківський процес.

• Колонка `STAT` допомагає визначити стан процесу.

• `R` означає виконання або готовність до виконання, `S` — переривне очікування, `D` — непереривне очікування, `T` — зупинку або трасування, `Z` — zombie.

• Zombie — це вже завершений процес, статус якого ще не забрав батьківський процес.

• VSZ описує віртуальний адресний простір, а RSS — фізичну пам'ять процесу в RAM.

• `TIME` — накопичений CPU time, а `ETIME` — час, що минув від запуску.

• `ps -p` дозволяє переглянути процес за PID.

• `ps -C` допомагає знайти процеси за назвою виконуваного файлу.

• `ps -o` дозволяє вибрати потрібні колонки.

• `ps --forest` показує ієрархію процесів.

• `pgrep` зручний для пошуку процесів за назвою або командним рядком.

• `pstree` допомагає зрозуміти взаємозв'язки між процесами.

• Для спостереження за змінами в часі використовують `top` або `htop`, а не лише `ps`.

• Перед завершенням процесу необхідно перевірити його PID, користувача та команду.

• Основна модель роботи:

    запустити ps
        ↓
    переглянути список процесів
        ↓
    знайти потрібний процес
        ↓
    перевірити PID, PPID і STAT
        ↓
    за потреби дослідити ресурси
        ↓
    виконати дію лише після перевірки

• Для повсякденної роботи розробника важливо вміти знайти власний процес Node.js, перевірити його стан, побачити батьківський процес і безпечно завершити потрібний сервер.
