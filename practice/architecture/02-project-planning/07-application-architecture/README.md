# Application Architecture

## 1. Що таке Application Architecture

**Application Architecture (архітектура застосунку)** — це спосіб організації програмного забезпечення, який визначає його основні компоненти, їхні обов'язки, взаємозв'язки та правила взаємодії.

Архітектура відповідає на запитання:

- З яких основних частин складається застосунок?
- За що відповідає кожна частина?
- Як компоненти обмінюються даними?
- Де розташована бізнес-логіка?
- Як організовано роботу з базою даних?
- Як перевіряються права доступу?
- Як змінювати та розширювати систему без зайвих ризиків?

Наприклад, у застосунку Worship Schedule можуть бути:

    Frontend
        інтерфейс користувача
        форми створення розкладів
        відображення подій

    Backend
        обробка HTTP-запитів
        перевірка даних
        бізнес-логіка
        авторизація

    Database
        користувачі
        розклади
        події

Архітектура визначає не тільки наявність цих частин, а й те, **як вони розділяють відповідальність та взаємодіють між собою**.

Головна ідея: хороша архітектура допомагає зробити застосунок зрозумілим, змінюваним, тестованим і достатньо надійним для його потреб.

---

## 2. Навіщо потрібна архітектура

Невеликий застосунок можна створити в одному файлі. Але зі збільшенням функціональності код стає складнішим.

Наприклад, один файл може одночасно:

- Приймати HTTP-запити.
- Перевіряти введені користувачем дані.
- Виконувати SQL-запити.
- Перевіряти права доступу.
- Формувати відповіді API.
- Обробляти помилки.

Такий підхід швидко ускладнює підтримку.

Архітектура допомагає розділити ці завдання.

### Основні переваги

✔ Розділення відповідальності між компонентами.

✔ Зрозуміла структура проєкту.

✔ Повторне використання коду.

✔ Простіше тестування окремих частин.

✔ Менше небажаних залежностей.

✔ Легше змінювати базу даних або зовнішні сервіси.

✔ Зручніше працювати над проєктом командою.

✔ Легше знаходити помилки та додавати нові функції.

Важливо: архітектура не повинна бути складнішою за саму проблему. Для невеликого навчального проєкту достатньо простого розділення на frontend, backend і database з кількома зрозумілими шарами всередині backend.

## 3. Основні поняття Application Architecture

### 3.1. Component — компонент

**Component** — частина системи, яка виконує певну роль і взаємодіє з іншими частинами.

Приклади:

    Authentication Module
        реєстрація
        вхід
        перевірка автентифікації

    Schedule Module
        створення розкладів
        перегляд розкладів
        редагування розкладів

    Event Module
        створення подій
        редагування подій
        видалення подій

Компонент може бути модулем, пакетом, сервісом або більшою підсистемою — залежно від рівня архітектури.

Не кожен компонент обов'язково повинен бути окремим сервером.

### 3.2. Responsibility — відповідальність

**Responsibility** — завдання, за яке відповідає конкретний компонент.

Наприклад:

    ScheduleController
        приймає HTTP-запит
        читає параметри
        повертає HTTP-відповідь

    ScheduleService
        виконує сценарій створення розкладу
        перевіряє бізнес-правила
        координує необхідні операції

    ScheduleRepository
        читає та зберігає дані розкладів

Це приклад поширеного розділення відповідальності, а не обов'язкова структура для кожного проєкту.

### 3.3. Dependency — залежність

**Dependency** — ситуація, коли один компонент використовує інший.

Наприклад:

    ScheduleService → ScheduleRepository

Сервіс залежить від компонента, який забезпечує доступ до даних.

Залежності необхідні, але важливо контролювати їхню кількість, напрямок і силу зв'язку.

### 3.4. Interface — інтерфейс взаємодії

**Interface** визначає, як один компонент може взаємодіяти з іншим.

У TypeScript це може бути тип або контракт:

    type Schedule = {
        id: number;
        title: string;
        ownerId: number;
    };

    interface ScheduleRepository {
        findById(id: number): Promise<Schedule | null>;
        create(
            data: Omit<Schedule, "id">
        ): Promise<Schedule>;
    }

Інтерфейс описує очікувані операції, не прив'язуючи код до конкретного способу їх реалізації.

Важливо: у TypeScript `interface` — це конструкція мови програмування. Архітектурний контракт може також реалізовуватися функціями, типами, API-схемами або іншими засобами.

### 3.5. Boundary — межа компонента

**Boundary** — межа, яка визначає, що належить певному компоненту, а що перебуває за його межами.

Наприклад:

    Schedule Module
        ScheduleController
        ScheduleService
        ScheduleRepository

Модуль розкладів відповідає за роботу з розкладами, а не за всі операції застосунку.

Чіткі межі допомагають не змішувати різні частини системи.

## 4. Основні архітектурні принципи

### 4.1. Separation of Concerns

**Separation of Concerns (SoC)** — розділення різних завдань між окремими частинами програми.

Наприклад, інтерфейс не повинен самостійно реалізовувати всі правила збереження даних у базі.

    Frontend
        відображає дані
        збирає введення користувача

    Backend
        перевіряє запит
        виконує бізнес-логіку

    Database
        зберігає дані
        забезпечує цілісність

Кожна частина має свою основну відповідальність.

### 4.2. Single Responsibility Principle

**Single Responsibility Principle (SRP)** — принцип єдиної відповідальності: модуль або клас повинен мати одну основну причину для зміни.

Наприклад, сервіс розкладів не повинен одночасно відповідати за:

- Створення розкладів.
- Відправлення всіх видів email.
- Форматування HTML-сторінок.
- Генерацію PDF.
- Роботу з усіма таблицями застосунку.

Частину функціональності варто винести в окремі компоненти, коли для цього є реальна потреба.

Водночас SRP не означає, що кожна функція повинна бути в окремому файлі.

### 4.3. High Cohesion

**High Cohesion (висока зв'язність усередині компонента)** означає, що функціональність компонента об'єднана спільною метою.

Наприклад, модуль `Schedule` містить операції, пов'язані з розкладами.

    schedules/
        schedule.controller.ts
        schedule.service.ts
        schedule.repository.ts
        schedule.types.ts

Усі ці файли допомагають реалізувати одну функціональну область.

### 4.4. Low Coupling

**Low Coupling (низька залежність між компонентами)** означає, що зміна одного компонента не повинна без потреби змушувати змінювати багато інших.

Наприклад, якщо бізнес-логіка напряму залежить від конкретної бібліотеки PostgreSQL, заміна способу доступу до даних може вимагати значних змін.

Якщо доступ до даних ізольований за чітким контрактом, заміна реалізації може бути простішою.

Низька зв'язаність не означає повну відсутність залежностей. Вона означає, що залежності контрольовані й виправдані.

### 4.5. Don't Repeat Yourself

**DRY (Don't Repeat Yourself)** — принцип уникнення дублювання знань і правил.

Якщо однакове бізнес-правило повторюється в багатьох місцях, зміни можуть призвести до суперечностей.

Наприклад, правило допустимості назви розкладу краще визначити в одному відповідному місці backend-логіки, а не копіювати в кожному контролері.

Однак не будь-яке повторення коду є поганим. Передчасне створення абстракцій також може ускладнювати програму.

### 4.6. KISS

**KISS (Keep It Simple, Stupid)** — прагнення до простих рішень, які задовольняють реальні вимоги.

Для застосунку з кількома CRUD-операціями не обов'язково відразу створювати:

- Мікросервісну систему.
- Окрему інфраструктуру повідомлень.
- Складну систему подій.
- Десятки абстрактних базових класів.

Краще починати з простого рішення та ускладнювати його за наявності конкретних причин.

## 5. Типи архітектурних рішень

Архітектура охоплює кілька рівнів рішень.

### 5.1. System Architecture

Описує систему на найвищому рівні:

- Які застосунки та зовнішні системи існують?
- Де розташований frontend?
- Де працює backend?
- Яка база даних використовується?
- Які зовнішні API потрібні?

Приклад:

    Browser
        ↓ HTTPS
    Next.js Application
        ↓ database connection
    PostgreSQL

Це спрощена схема. Реальний спосіб підключення до бази залежить від розгортання та обраної платформи.

### 5.2. Application Architecture

Описує внутрішню організацію застосунку:

    Application
        Presentation Layer
        Application Layer
        Domain Layer
        Infrastructure Layer

Ці шари не обов'язково мають бути реалізовані як окремі сервери. Часто це логічні частини одного застосунку.

### 5.3. Module Architecture

Описує функціональні модулі:

    Application
        Auth Module
        Users Module
        Schedules Module
        Events Module

Модулі можуть мати власні контролери, сервіси, типи та компоненти доступу до даних.

### 5.4. Code-Level Design

Описує структуру класів, функцій, типів та їхні взаємодії.

Наприклад:

    ScheduleService
        createSchedule()
        getScheduleById()
        updateSchedule()
        deleteSchedule()

Це вже ближче до проєктування конкретного коду.

**Висновок:** архітектура не обмежується структурою папок. Вона також визначає межі, контракти та правила взаємодії компонентів.

## 6. Layered Architecture — багатошарова архітектура

**Layered Architecture** — підхід, за якого застосунок поділяють на логічні шари, кожен із яких виконує певну роль.

Поширений приклад для backend:

    HTTP Request
        ↓
    Controller
        ↓
    Service
        ↓
    Repository
        ↓
    Database

### 6.1. Presentation Layer

**Presentation Layer** відповідає за взаємодію із зовнішнім світом.

Для HTTP backend це зазвичай контролери та компоненти, що обробляють запити.

Обов'язки:

- Приймати HTTP-запити.
- Читати параметри маршруту та тіла запиту.
- Виконувати базову перевірку формату.
- Викликати потрібний сценарій.
- Формувати HTTP-відповідь.

### 6.2. Application Layer

**Application Layer** координує виконання сценаріїв використання.

Наприклад:

    CreateSchedule
        отримати користувача
        перевірити вхідні дані
        створити розклад
        повернути результат

У невеликому NestJS-застосунку цю роль часто виконують сервіси.

Application Layer не обов'язково повинен бути окремою папкою. Важливо розуміти його відповідальність.

### 6.3. Domain Layer

**Domain Layer** містить ключові поняття та бізнес-правила предметної області.

Наприклад:

- Правила допустимості розкладу.
- Правила зміни статусу.
- Перевірки, що визначають коректність доменних даних.

У простому CRUD-проєкті окремий складний доменний шар може бути зайвим. Частина бізнес-правил може знаходитися у звичайних сервісах.

### 6.4. Infrastructure Layer

**Infrastructure Layer** містить технічні реалізації, необхідні для роботи застосунку.

Приклади:

- Підключення до PostgreSQL.
- Реалізація репозиторіїв.
- Робота з файловим сховищем.
- Відправлення email.
- Інтеграція із зовнішнім API.

### 6.5. Приклад структури

    src/
    ├── schedules/
    │   ├── schedule.controller.ts
    │   ├── schedule.service.ts
    │   ├── schedule.repository.ts
    │   └── schedule.types.ts
    │
    ├── database/
    │   └── database.service.ts
    │
    └── main.ts

Це спрощена структура. Для невеликого NestJS-проєкту вона може бути достатньою.

Не потрібно створювати окремі папки `domain`, `application`, `infrastructure` лише заради відповідності шаблону. Розділяй шари тоді, коли вони справді допомагають контролювати відповідальність і залежності.

## 7. Monolithic Architecture — монолітна архітектура

**Monolithic Architecture** — архітектура, у якій основна функціональність застосунку розгортається як один застосунок або один основний deployment unit.

Моноліт може мати добре розділені внутрішні модулі.

    Application
        ├── Auth Module
        ├── Users Module
        ├── Schedules Module
        └── Events Module

Це не означає, що весь код повинен бути в одному файлі.

### Переваги

✔ Простішим може бути локальний запуск.

✔ Легше налагоджувати взаємодію між модулями.

✔ Менше інфраструктурних компонентів.

✔ Зазвичай простіше почати розробку.

✔ Можна використовувати спільні транзакції бази даних.

### Недоліки

- За відсутності модульних меж код може перетворитися на заплутану систему залежностей.
- Розгортання окремих функціональних частин незалежно одне від одного зазвичай складніше.
- Зростання застосунку може збільшити вимоги до процесу тестування та релізів.

### Коли обирати

Моноліт часто є хорошим вибором для:

- Навчальних проєктів.
- MVP.
- Невеликих комерційних застосунків.
- Систем із помірною складністю.
- Команд, які хочуть швидко розробляти та підтримувати один застосунок.

Для Worship Schedule або Lyceum логічно почати з модульного моноліту.

## 8. Modular Monolith — модульний моноліт

**Modular Monolith** — моноліт, внутрішня структура якого організована в окремі модулі з чіткими відповідальностями та контрольованими залежностями.

Приклад:

    src/
    ├── auth/
    │   ├── auth.controller.ts
    │   ├── auth.service.ts
    │   └── auth.module.ts
    │
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.module.ts
    │
    ├── schedules/
    │   ├── schedules.controller.ts
    │   ├── schedules.service.ts
    │   └── schedules.module.ts
    │
    ├── events/
    │   ├── events.controller.ts
    │   ├── events.service.ts
    │   └── events.module.ts
    │
    └── app.module.ts

Кожен модуль відповідає за власну функціональність.

Наприклад:

    Auth Module
        реєстрація
        вхід
        перевірка автентифікації

    Schedules Module
        створення розкладів
        редагування розкладів
        перевірка доступу до розкладів

    Events Module
        створення подій
        редагування подій
        видалення подій

### Переваги

- Код простіше знаходити.
- Відповідальність модулів зрозуміліша.
- Залежності легше контролювати.
- Можна тестувати окремі функціональні частини.
- У майбутньому простіше визначити, чи варто виділяти компонент в окремий сервіс.

### Важливий принцип

**Модульність не визначається кількістю папок.**

Якщо `SchedulesService` напряму змінює внутрішні дані `UsersService`, `EventsService` та ще п'яти модулів, формальний поділ на папки не робить архітектуру модульною.

Потрібно визначити:

- Які дані належать модулю.
- Які операції він надає іншим модулям.
- Які залежності дозволені.
- Які внутрішні деталі не повинні бути доступні зовні.

## 9. Microservices Architecture — мікросервісна архітектура

**Microservices Architecture** — підхід, у якому система складається з окремих сервісів, що можуть розроблятися, розгортатися та масштабуватися незалежно.

Наприклад:

    Web Application
        ↓
    API Gateway
        ├── Auth Service
        ├── Schedule Service
        ├── Notification Service
        └── Reporting Service

Це лише ілюстрація: API Gateway не є обов'язковим у кожній мікросервісній системі.

### Переваги

- Незалежне розгортання сервісів.
- Можливість окремо масштабувати навантажені компоненти.
- Можливість використовувати різні технології там, де це виправдано.
- Краща ізоляція деяких технічних або організаційних проблем.

### Недоліки

- Мережеві виклики складніші за виклики функцій усередині процесу.
- Потрібно обробляти тайм-аути, повторні запити та часткові відмови.
- Складніше забезпечувати узгодженість даних між сервісами.
- З'являються додаткові витрати на моніторинг, логування, безпеку та розгортання.
- Тестування взаємодії сервісів стає складнішим.

### Коли обирати

Мікросервіси можуть бути доречними, коли:

- Команди мають потребу незалежно розробляти та розгортати різні частини системи.
- Компоненти мають суттєво різні вимоги до масштабування.
- Межі предметної області достатньо добре зрозумілі.
- Організація готова підтримувати розподілену інфраструктуру.

**Для початкового MVP зазвичай не потрібно починати з мікросервісів.** Спочатку варто створити добре організований моноліт і перевірити реальні потреби системи.

## 10. Client-Server Architecture

**Client-Server Architecture** розділяє клієнтську частину, яка ініціює запити, та серверну частину, яка їх обробляє.

Для вебзастосунку:

    Browser
        ↓ HTTP Request
    Backend API
        ↓
    Database
        ↑
    Backend API
        ↓ HTTP Response
    Browser

### Client

Клієнт може:

- Відображати інтерфейс.
- Збирати введені дані.
- Викликати API.
- Відображати результати.
- Виконувати базову перевірку введення.

### Server

Сервер може:

- Приймати запити.
- Перевіряти дані.
- Перевіряти автентифікацію та права доступу.
- Виконувати бізнес-логіку.
- Читати та змінювати дані в базі.
- Повертати результати клієнту.

### Database

База даних відповідає за зберігання даних та їхню цілісність.

Клієнт не повинен отримувати прямий доступ до приватних даних бази через відкриті облікові дані PostgreSQL.

Якщо використовується платформа, яка дозволяє безпосередньо звертатися до бази через захищений API, наприклад Supabase, необхідно правильно налаштувати політики доступу та обмеження на рівні платформи.

## 11. Архітектура Next.js-застосунку

Next.js поєднує можливості React із серверними функціями, тому архітектура може відрізнятися від класичної схеми з окремим frontend і backend.

### 11.1. Варіант з одним Next.js-застосунком

    Browser
        ↓
    Next.js
        ├── React UI
        ├── Server Components
        ├── Server Actions / Route Handlers
        └── Data Access
                ↓
            PostgreSQL

Це спрощена схема. Конкретний потік залежить від того, як організовано маршрути, серверні функції та доступ до даних.

Для невеликого проєкту не завжди потрібен окремий Express або NestJS backend.

### 11.2. Варіант з окремим backend

    Browser
        ↓
    Next.js Frontend
        ↓ HTTP API
    NestJS Backend
        ↓
    PostgreSQL

Цей варіант може бути корисним, якщо:

- Backend має окрему бізнес-логіку.
- API використовують кілька клієнтів.
- Потрібно незалежно розгортати frontend і backend.
- Є достатньо складні серверні модулі.

### 11.3. Як обрати

| Ситуація | Можливий вибір |
|---|---|
| Невеликий застосунок з простими CRUD-операціями | Next.js із серверними можливостями |
| Окремий API для кількох клієнтів | Next.js + NestJS |
| Складна backend-логіка | Next.js + NestJS або інший окремий backend |
| MVP з обмеженим часом | Найпростіша архітектура, що задовольняє вимоги |

Це не жорсткі правила. Обирай структуру відповідно до функціональності, складності та вимог до розгортання.

## 12. Dependency Direction — напрямок залежностей

Архітектура визначає не лише те, які компоненти існують, а й те, у якому напрямку вони можуть залежати один від одного.

У простій шаровій архітектурі:

    Controller
        ↓
    Service
        ↓
    Repository
        ↓
    Database

Це зрозуміла схема для багатьох CRUD-застосунків.

Однак у складніших архітектурах важливо не дозволяти бізнес-правилам залежати від деталей інфраструктури.

Наприклад, якщо сервіс безпосередньо використовує специфічні методи конкретної ORM, заміна ORM може зачепити бізнес-логіку.

Можна визначити контракт:

    interface ScheduleRepository {
        findById(id: number): Promise<Schedule | null>;
        save(schedule: Schedule): Promise<Schedule>;
    }

А потім реалізувати його для PostgreSQL:

    class PostgresScheduleRepository
        implements ScheduleRepository {
        // Реалізація доступу до PostgreSQL
    }

Це ілюстративний приклад. У реальному коді необхідно реалізувати методи повністю та визначити типи відповідно до обраної моделі.

Такий підхід може полегшити тестування та заміну інфраструктури, але створює додатковий рівень абстракції.

**Не створюй інтерфейс для кожного класу автоматично.** Він потрібен тоді, коли дає реальну користь: визначає важливий контракт, ізолює зовнішню залежність або спрощує тестування.

## 13. API Contracts — контракти API

**API Contract** визначає, як клієнт і сервер взаємодіють між собою.

Контракт може описувати:

- HTTP-методи.
- URL.
- Формат запиту.
- Формат відповіді.
- Коди помилок.
- Правила автентифікації.
- Обмеження введених даних.

Наприклад:

    GET /api/schedules

    Response:
        [
            {
                "id": 1,
                "title": "Недільний розклад"
            }
        ]

Створення розкладу:

    POST /api/schedules

    Request:
        {
            "title": "Недільний розклад"
        }

    Response:
        {
            "id": 1,
            "title": "Недільний розклад"
        }

Це лише приклад формату, а не повна специфікація API.

Контракт повинен бути узгодженим між frontend і backend. Якщо backend змінює структуру відповіді, frontend має бути відповідно оновлений або зміна повинна залишатися сумісною.

### Чому це архітектурне питання

Якщо компоненти взаємодіють через чіткі контракти, їх можна змінювати незалежніше.

Наприклад, frontend не повинен залежати від внутрішньої назви таблиці PostgreSQL або структури ORM-моделі.

## 14. Архітектура обробки помилок

Обробка помилок також повинна мати зрозумілу структуру.

Наприклад:

    Frontend
        показує повідомлення користувачеві

    Controller / Exception Handler
        перетворює помилку на HTTP-відповідь

    Service
        виявляє порушення бізнес-правил

    Database
        повертає помилки обмежень або з'єднання

Приклади типових ситуацій:

- `400 Bad Request` — некоректний запит.
- `401 Unauthorized` — користувач не автентифікований.
- `403 Forbidden` — доступ заборонено.
- `404 Not Found` — ресурс не знайдено.
- `409 Conflict` — конфлікт із поточним станом даних.
- `500 Internal Server Error` — неочікувана помилка сервера.

Конкретний статус залежить від обставин та контракту API.

Наприклад, запит на редагування чужого розкладу може повертати `403` або `404` залежно від політики безпеки застосунку.

Не варто повертати користувачу деталі SQL-помилок, секрети або внутрішні stack traces у production-відповідях.

## 15. Архітектура автентифікації та авторизації

Ці поняття потрібно розрізняти.

**Authentication (автентифікація)** відповідає на запитання:

> Хто цей користувач?

**Authorization (авторизація)** відповідає на запитання:

> Що цей користувач має право робити?

Приклад:

    Request
        ↓
    Authentication
        перевірка сесії або токена
        ↓
    Authorization
        перевірка прав доступу
        ↓
    Business Logic
        виконання операції

Для Worship Schedule:

    User A
        створив Schedule A

    User B
        намагається редагувати Schedule A

Backend повинен перевірити власника або відповідні права доступу.

Сам факт того, що користувач знає `scheduleId`, не означає, що він має право редагувати розклад.

Приклад логіки:

    async function updateSchedule(
        scheduleId: number,
        userId: number,
        input: UpdateScheduleInput
    ) {
        const schedule = await repository.findById(scheduleId);

        if (!schedule) {
            throw new NotFoundError();
        }

        if (schedule.ownerId !== userId) {
            throw new ForbiddenError();
        }

        return repository.update(scheduleId, input);
    }

Це псевдоприклад: назви типів і реалізація репозиторію залежать від проєкту. Також для конкурентних змін і критичних операцій може знадобитися додатковий захист.

Архітектурний висновок: перевірка доступу повинна бути в довіреній серверній частині або в надійно налаштованому механізмі доступу платформи, а не лише у frontend.

## 16. Архітектурні рішення та компроміси

Архітектурні рішення майже завжди мають переваги й недоліки.

Наприклад, окремий NestJS backend може краще організувати складну бізнес-логіку, але водночас:

- Збільшує кількість частин системи.
- Вимагає окремого розгортання або додаткової конфігурації.
- Створює необхідність підтримувати API-контракт між frontend і backend.

А використання Next.js як єдиного застосунку може спростити розробку, але не завжди буде найзручнішим рішенням для складного API, який використовують різні клієнти.

### Приклади компромісів

| Рішення | Перевага | Компроміс |
|---|---|---|
| Моноліт | Простота розробки та розгортання | Спільний процес розгортання |
| Мікросервіси | Незалежність сервісів | Мережева та операційна складність |
| Один модуль | Менше абстракцій | Може зростати відповідальність |
| Багато модулів | Чіткіші межі | Більше структурного коду |
| ORM | Зручність типових операцій | Додатковий рівень абстракції |
| Прямий SQL | Контроль над запитами | Більше ручної роботи |
| Суворі контракти | Краща передбачуваність | Потрібно підтримувати узгодженість |

Правильне рішення — не те, що вважається найсучаснішим, а те, що найкраще відповідає вимогам і обмеженням конкретного проєкту.

## 19. Як обрати архітектуру для нового проєкту

Перед вибором архітектури дай відповідь на кілька запитань.

### Запитання 1. Яка складність предметної області?

Якщо це простий CRUD-застосунок, достатньо кількох модулів і шарів.

Якщо застосунок має багато складних бізнес-правил, потрібні чіткіші доменні межі.

### Запитання 2. Скільки клієнтів використовуватимуть backend?

Якщо є один вебінтерфейс, серверні можливості Next.js можуть бути достатніми.

Якщо потрібні вебклієнт, мобільний застосунок і сторонні інтеграції, окремий API може бути зручнішим.

### Запитання 3. Наскільки незалежно повинні розвиватися компоненти?

Якщо всі частини змінюються разом, моноліт часто простіший.

Якщо певні частини потрібно незалежно розгортати та масштабувати, можна розглянути окремі сервіси.

### Запитання 4. Які вимоги до команди та підтримки?

Складніша архітектура потребує більше часу на тестування, розгортання, моніторинг і документацію.

### Запитання 5. Які обмеження MVP?

Потрібно враховувати:

- Час розробки.
- Доступні ресурси.
- Вимоги до безпеки.
- Складність підтримки.
- Можливості хостингу.

**Практичне правило:** обирай найпростішу архітектуру, яка задовольняє поточні вимоги та залишає розумний шлях для розвитку.

## 20. Типові архітектурні помилки

### Помилка 1. Архітектура заради архітектури

Створення великої кількості шарів, інтерфейсів і абстракцій без реальної потреби.

**Краще:** вводити додаткову структуру тоді, коли вона допомагає розв'язати конкретну проблему.

### Помилка 2. Один великий сервіс

Усі операції розташовані в одному сервісі, який відповідає за всю систему.

**Краще:** розділяти функціональність за відповідальністю та предметною областю.

### Помилка 3. Контролери з бізнес-логікою

Контролер містить складні перевірки, SQL-запити й правила предметної області.

**Краще:** залишати контролер тонким, а основну логіку розміщувати у відповідному сервісному або доменному компоненті.

### Помилка 4. Модулі залежать від внутрішніх деталей один одного

Один модуль напряму змінює таблиці та внутрішні об'єкти іншого модуля.

**Краще:** визначати межі, контракти та дозволені способи взаємодії.

### Помилка 5. Передчасний перехід до мікросервісів

Застосунок має кілька простих функцій, але вже складається з багатьох незалежних сервісів.

**Краще:** почати з модульного моноліту, якщо немає обґрунтованої потреби в іншій архітектурі.

### Помилка 6. Змішування frontend і backend-відповідальності

Frontend вважається єдиним місцем перевірки доступу.

**Краще:** виконувати критичні перевірки на довіреній серверній стороні або в захищених механізмах платформи.

### Помилка 7. Ігнорування залежностей

Компоненти можуть викликати один одного в довільному напрямку, створюючи циклічні залежності.

**Краще:** визначити допустимі напрямки залежностей і контролювати їх.

### Помилка 8. Немає документації рішень

Через кілька місяців незрозуміло, чому обрали конкретну технологію або структуру.

**Краще:** документувати важливі рішення та їхні наслідки.

### Помилка 9. Передчасне узагальнення

Створюються універсальні системи для функцій, які ще не потрібні.

**Краще:** спочатку реалізувати кілька реальних сценаріїв, а потім визначити, які абстракції справді корисні.

### Помилка 10. Архітектура не відповідає вимогам

Наприклад, система має підтримувати кілька клієнтів, але бізнес-логіка повністю прив'язана до компонентів одного інтерфейсу.

**Краще:** враховувати реальні сценарії використання, вимоги до API та можливий розвиток проєкту.

## 21. Як архітектура пов'язана з іншими темами

Application Architecture використовує результати попередніх етапів планування та впливає на подальшу реалізацію.

    Requirements and MVP
        ↓
    User Stories and Use Cases
        ↓
    User Flows
        ↓
    Wireframes and Screen Planning
        ↓
    Domain and Data Modeling
        ↓
    Application Architecture
        ↓
    Implementation
        ↓
    Testing and Deployment

Це умовна схема. На практиці розробка і планування відбуваються ітеративно.

### Зв'язок із Requirements

Вимоги визначають, які функції повинна підтримувати система.

Архітектура визначає, як організувати компоненти, щоб реалізувати ці функції.

### Зв'язок із Domain Modeling

Domain Model визначає сутності та правила предметної області.

Application Architecture визначає, де розташувати ці правила та які компоненти відповідають за їх виконання.

### Зв'язок із Data Modeling

Data Model визначає структуру даних.

Архітектура визначає, як компоненти працюють із цими даними та як доступ до них ізольовано від решти коду.

### Зв'язок із Testing

Чіткі межі компонентів допомагають тестувати їх окремо.

Наприклад:

    ScheduleService
        unit tests

    SchedulesController
        integration tests

    Application + PostgreSQL
        end-to-end tests

Конкретна стратегія тестування залежить від ризиків і складності застосунку.

### Зв'язок із Deployment

Архітектура впливає на:

- Кількість застосунків, які потрібно розгортати.
- Налаштування середовища.
- Зберігання секретів.
- Підключення до бази даних.
- Моніторинг.
- Процес оновлення версій.

Тому розгортання потрібно враховувати під час проєктування, а не лише наприкінці розробки.

## 24. Що потрібно знати на різних рівнях

### Core — основа

✔ Розуміти, що таке Application Architecture.

✔ Знати основні компоненти вебзастосунку.

✔ Розуміти розділення відповідальності.

✔ Знати принципи Separation of Concerns, SRP, KISS і DRY.

✔ Розуміти, навіщо розділяти frontend, backend і database.

### Junior — практична розробка

✔ Уміти створювати просту шарову структуру backend.

✔ Розділяти контролери, сервіси та доступ до даних.

✔ Організовувати код за функціональними модулями.

✔ Розуміти різницю між монолітом і модульним монолітом.

✔ Проєктувати API-контракти.

✔ Розуміти межі відповідальності frontend і backend.

✔ Забезпечувати серверну перевірку прав доступу.

✔ Документувати основні архітектурні рішення.

### Middle — поглиблене розуміння

✔ Контролювати залежності між модулями.

✔ Визначати межі модулів за предметною областю.

✔ Розуміти Dependency Inversion та інші принципи керування залежностями.

✔ Обґрунтовувати використання абстракцій.

✔ Оцінювати компроміси між монолітом і мікросервісами.

✔ Враховувати безпеку, спостережуваність і розгортання.

### Senior — системне проєктування

✔ Проєктувати архітектуру з урахуванням функціональних і нефункціональних вимог.

✔ Визначати межі великих підсистем.

✔ Оцінювати ризики та довгострокову вартість архітектурних рішень.

✔ Планувати еволюцію архітектури без непотрібної складності.

✔ Враховувати відмовостійкість, масштабування та експлуатацію.

✔ Узгоджувати архітектурні рішення між командами.

## 25. Головне, що потрібно запам'ятати

**Application Architecture — це не просто вибір технологій або створення папок. Це система рішень про відповідальність компонентів, їхні межі, залежності та взаємодію.**

Під час проєктування нового застосунку:

    1. Зрозумій вимоги.
    2. Визнач основні сценарії використання.
    3. Побудуй Domain Model.
    4. Спроєктуй Data Model.
    5. Визнач компоненти та їхню відповідальність.
    6. Встанови правила взаємодії між компонентами.
    7. Обери найпростішу відповідну архітектуру.
    8. Реалізуй і протестуй основні сценарії.
    9. Документуй важливі рішення.
    10. Переглядай архітектуру, коли змінюються вимоги.

Для Junior Full Stack Developer найважливіше — навчитися організовувати код так, щоб кожна частина мала зрозумілу роль, бізнес-правила не губилися між компонентами, а зміни в одній частині не ламали весь застосунок.

Починай із простого модульного моноліту, чітких меж і зрозумілих контрактів. Складніші архітектурні рішення додавай тоді, коли з'являється реальна потреба.
