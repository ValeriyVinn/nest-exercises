# Domain and Data Modeling

## 1. Що таке Domain and Data Modeling

**Domain Modeling (моделювання предметної області)** — це процес опису понять реального світу, правил і взаємозв'язків, які існують у певній сфері бізнесу або діяльності.

**Data Modeling (моделювання даних)** — це процес визначення того, які дані потрібно зберігати, як вони структуровані та як пов'язані між собою.

Ці поняття тісно пов'язані, але не тотожні:

- **Domain Model** описує предметну область: сутності, поняття, правила та їхню поведінку.
- **Data Model** описує структуру даних: поля, типи, зв'язки, обмеження та способи зберігання.
- **Database Schema** — конкретна структура бази даних, реалізована в обраній СУБД.

Наприклад, для застосунку розкладів богослужінь потрібно розуміти, що таке користувач, розклад, подія та місце проведення. Після цього можна спроєктувати таблиці PostgreSQL, які зберігатимуть відповідні дані.

    Domain Model
        User
        Schedule
        Event

            ↓

    Data Model
        User має багато Schedule
        Schedule має багато Event

            ↓

    Database Schema
        users
        schedules
        events

Головна ідея: **спочатку зрозуміти предметну область, потім визначити модель даних і лише після цього реалізовувати структуру бази даних.**

---

## 2. Навіщо потрібне моделювання

Моделювання допомагає перетворити нечіткий опис майбутнього застосунку на зрозумілу структуру.

Наприклад, вимога:

> Користувач повинен мати можливість створювати власні розклади та додавати до них події.

Породжує запитання:

- Що таке користувач?
- Що таке розклад?
- Чи може користувач мати декілька розкладів?
- Чи може один розклад містити багато подій?
- Чи може подія належати декільком розкладам?
- Чи може користувач редагувати чужий розклад?
- Що відбувається з подіями, якщо розклад видаляють?
- Які дані необхідно зберігати для кожної сутності?

Без відповідей на ці запитання легко створити базу даних, яку доведеться переробляти під час розробки.

### Основні переваги

✔ Допомагає зрозуміти вимоги до застосунку.

✔ Визначає основні сутності та їхні зв'язки.

✔ Допомагає уникнути дублювання даних.

✔ Робить структуру бази даних зрозумілішою.

✔ Виявляє суперечності в бізнес-правилах до написання коду.

✔ Допомагає визначити відповідальність backend-модулів.

✔ Спрощує тестування, підтримку та подальше розширення проєкту.

## 3. Основні поняття Domain Modeling

### 3.1. Domain — предметна область

**Domain** — сфера діяльності, яку обслуговує застосунок.

Приклади:

- LMS — навчання, курси, уроки, учні та викладачі.
- Інтернет-магазин — товари, кошики, замовлення та платежі.
- Застосунок розкладів — користувачі, розклади, події та місця проведення.
- Медичний застосунок — пацієнти, лікарі, прийоми та медичні записи.

Предметна область визначає, які поняття мають значення для системи.

Наприклад, у застосунку розкладів немає потреби моделювати всі можливі властивості церковної будівлі. Потрібно зберігати лише те, що необхідне для функціональності застосунку.

### 3.2. Entity — сутність

**Entity** — об'єкт предметної області, який має власну ідентичність.

Приклади:

- User
- Schedule
- Event
- Course
- Student
- Order

Сутність зазвичай має унікальний ідентифікатор.

    User
        id
        email
        name

    Schedule
        id
        title
        ownerId

Два користувачі можуть мати однакові імена, але це різні користувачі, оскільки вони мають різні ідентифікатори.

    User 1:
        id = 1
        name = "Олександр"

    User 2:
        id = 2
        name = "Олександр"

Ідентичність сутності не визначається лише її назвою або іншими змінюваними властивостями.

### 3.3. Attribute — атрибут

**Attribute** — властивість сутності або іншого об'єкта моделі.

Наприклад, сутність `Schedule` може мати такі атрибути:

    Schedule
        id
        title
        description
        createdAt
        updatedAt

Для кожного атрибута необхідно визначити:

- Назву.
- Тип даних.
- Чи є значення обов'язковим.
- Чи має воно значення за замовчуванням.
- Які обмеження до нього застосовуються.

Наприклад:

    title:
        type: string
        required: true
        maxLength: 100

    description:
        type: string
        required: false
        maxLength: 2000

Конкретні обмеження потрібно узгоджувати з вимогами проєкту.

### 3.4. Relationship — зв'язок

**Relationship** — відношення між сутностями.

Наприклад:

    User → Schedule
        один користувач має багато розкладів

    Schedule → Event
        один розклад має багато подій

Зв'язки допомагають зрозуміти структуру системи та визначити, як сутності взаємодіють між собою.

### 3.5. Business Rules — бізнес-правила

**Business Rules** — правила предметної області, які визначають, що дозволено, а що заборонено.

Приклади:

- Кожен приватний розклад має власника.
- Користувач може редагувати лише власний розклад.
- Подія повинна належати певному розкладу.
- Назва розкладу не може бути порожньою.
- Час завершення події не повинен передувати часу її початку.

Бізнес-правила потрібно визначати до реалізації, адже вони впливають на модель даних, backend-логіку та перевірки.

## 4. Основні поняття Data Modeling

### 4.1. Data Model — модель даних

Модель даних описує, які дані зберігаються в системі та як вони організовані.

Наприклад:

    User
        id: integer
        email: string
        name: string

    Schedule
        id: integer
        title: string
        ownerId: integer

    Event
        id: integer
        title: string
        startsAt: datetime
        scheduleId: integer

Це логічний опис структури, а не обов'язково готова схема конкретної бази даних.

### 4.2. Primary Key — первинний ключ

**Primary Key (PK)** — поле або набір полів, які однозначно ідентифікують запис у таблиці.

Приклад:

    users
        id: PRIMARY KEY
        email
        name

У PostgreSQL можна використати автоінкрементний ідентифікатор:

    CREATE TABLE users (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        email TEXT NOT NULL,
        name TEXT NOT NULL
    );

Первинний ключ:

- Має унікальне значення.
- Не може бути `NULL`.
- Дає змогу однозначно посилатися на запис.
- Не повинен залежати від властивості, яка може змінитися.

Для email зазвичай застосовують окреме обмеження унікальності, якщо за правилами системи він має бути унікальним.

### 4.3. Foreign Key — зовнішній ключ

**Foreign Key (FK)** — поле або набір полів, які посилаються на запис в іншій таблиці або, за потреби, у тій самій таблиці.

Наприклад, кожен розклад належить певному користувачеві.

    users
        id
        email

    schedules
        id
        title
        owner_id → users.id

У PostgreSQL:

    CREATE TABLE schedules (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title TEXT NOT NULL,
        owner_id INTEGER NOT NULL REFERENCES users(id)
    );

Зовнішній ключ забезпечує посилальну цілісність: не можна створити розклад із `owner_id`, який не відповідає наявному користувачеві.

Важливо: Foreign Key сам по собі **не перевіряє права доступу**. Перевірка того, чи може конкретний користувач редагувати розклад, належить до логіки авторизації.

### 4.4. Constraints — обмеження

Обмеження визначають правила, яким мають відповідати дані.

Основні типи:

- `PRIMARY KEY` — первинний ключ.
- `FOREIGN KEY` — зовнішній ключ.
- `NOT NULL` — значення обов'язкове.
- `UNIQUE` — значення або комбінація значень унікальні.
- `CHECK` — значення повинно відповідати умові.
- `DEFAULT` — значення за замовчуванням.

Приклад:

    CREATE TABLE events (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title TEXT NOT NULL,
        starts_at TIMESTAMPTZ NOT NULL,
        ends_at TIMESTAMPTZ,
        CONSTRAINT valid_event_time
            CHECK (
                ends_at IS NULL
                OR ends_at >= starts_at
            )
    );

Тут `CHECK` не дозволяє зберегти подію, у якої час завершення передує часу початку.

Обмеження на рівні бази даних важливі, тому що дані можуть надходити не лише через один конкретний інтерфейс.

## 5. Cardinality — кратність зв'язків

**Cardinality** визначає, скільки екземплярів однієї сутності можуть бути пов'язані з екземпляром іншої сутності.

### 5.1. One-to-One (1:1)

Один запис пов'язаний максимум з одним записом іншої сутності, і навпаки.

Приклад:

    User 1 ─── 0..1 UserProfile

Один користувач має максимум один додатковий профіль, а кожен профіль належить одному користувачеві.

Реалізація в PostgreSQL:

    CREATE TABLE user_profiles (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        user_id INTEGER NOT NULL UNIQUE REFERENCES users(id),
        bio TEXT
    );

`UNIQUE` на `user_id` не дозволяє створити кілька профілів для одного користувача.

Не кожен зв'язок потрібно реалізовувати окремою таблицею. Іноді достатньо додати поля до наявної таблиці. Окрема сутність корисна, коли має власні властивості, життєвий цикл або окремі правила доступу.

### 5.2. One-to-Many (1:N)

Один запис пов'язаний із багатьма записами іншої сутності.

Приклад:

    User 1 ─── N Schedule

Один користувач може мати багато розкладів, але кожен розклад має одного власника.

Реалізація:

    CREATE TABLE schedules (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title TEXT NOT NULL,
        owner_id INTEGER NOT NULL REFERENCES users(id)
    );

Зовнішній ключ розташовується на стороні `many`, тобто в таблиці `schedules`.

### 5.3. Many-to-Many (M:N)

Багато записів однієї сутності можуть бути пов'язані з багатьма записами іншої сутності.

Приклад:

    Student N ─── M Course

Один студент може відвідувати багато курсів, а один курс може мати багато студентів.

У реляційній базі даних такий зв'язок зазвичай реалізують через проміжну таблицю.

    students
        id
        name

    courses
        id
        title

    enrollments
        student_id
        course_id
        enrolled_at

Реалізація:

    CREATE TABLE enrollments (
        student_id INTEGER NOT NULL REFERENCES students(id),
        course_id INTEGER NOT NULL REFERENCES courses(id),
        enrolled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
        PRIMARY KEY (student_id, course_id)
    );

Складений первинний ключ не дозволяє двічі додати того самого студента до того самого курсу.

Якщо зв'язок має власні атрибути, наприклад дату запису, статус або оцінку, проміжна таблиця стає особливо важливою.

---

## 6. Optionality — обов'язковість зв'язку

Cardinality відповідає на запитання «скільки?», а optionality — «чи обов'язково?».

Наприклад:

    User 1 ─── 0..N Schedule

Користувач може не мати жодного розкладу або мати багато розкладів.

    Schedule N ─── 1 User

Кожен розклад повинен мати рівно одного власника.

У таблиці `schedules`:

    owner_id INTEGER NOT NULL REFERENCES users(id)

`NOT NULL` означає, що власник обов'язковий.

Якщо за вимогами власник може бути відсутнім, наприклад у системі є спільні шаблони, які не належать конкретному користувачеві, модель потрібно спроєктувати інакше.

**Висновок:** під час моделювання потрібно визначити не лише кількість можливих зв'язків, а й те, чи може зв'язок бути відсутнім.

## 7. Як побудувати Domain Model

Практичний алгоритм моделювання предметної області:

### Крок 1. Зрозуміти вимоги

Почни з опису функціональності звичайною мовою.

Наприклад:

> Користувач реєструється, створює приватні розклади, додає до них події та редагує власні дані.

### Крок 2. Визначити іменники

З опису можна виділити:

- Користувач.
- Розклад.
- Подія.
- Дані користувача.

Це кандидати на сутності, але не кожен іменник повинен ставати таблицею.

Наприклад, «дані користувача» — не обов'язково окрема сутність. Це може бути частиною `User`.

### Крок 3. Визначити сутності

Для початкової версії застосунку можна вибрати:

    User
    Schedule
    Event

Пізніше можуть з'явитися:

    ScheduleTemplate
    Location
    Category
    SharedAccess

Не потрібно створювати всі можливі сутності заздалегідь. Додавай їх тоді, коли цього вимагають функціональність і правила предметної області.

### Крок 4. Визначити атрибути

Наприклад:

    User
        id
        email
        name

    Schedule
        id
        title
        ownerId
        createdAt
        updatedAt

    Event
        id
        scheduleId
        title
        startsAt
        endsAt

На цьому етапі визнач, які поля обов'язкові, які необов'язкові та які мають обмеження.

### Крок 5. Визначити зв'язки

    User 1 ─── N Schedule
    Schedule 1 ─── N Event

Пояснення:

- Один користувач може створити багато розкладів.
- Кожен розклад має одного власника.
- Один розклад може містити багато подій.
- Кожна подія належить одному розкладу.

### Крок 6. Визначити бізнес-правила

Наприклад:

    Rule 1:
        Розклад повинен мати назву.

    Rule 2:
        Кожен приватний розклад має власника.

    Rule 3:
        Користувач може редагувати тільки власні розклади.

    Rule 4:
        Подія належить конкретному розкладу.

    Rule 5:
        Якщо задано час завершення,
        він не може передувати часу початку.

### Крок 7. Перевірити модель на сценаріях

Спробуй відповісти на запитання:

- Що відбувається, якщо користувач не створив жодного розкладу?
- Чи можна створити порожній розклад?
- Чи може подія існувати без розкладу?
- Що відбувається з подіями після видалення розкладу?
- Що відбувається з розкладами після видалення користувача?
- Як система перевіряє, що користувач редагує власні дані?

Якщо на ці запитання немає чітких відповідей, модель ще потребує уточнення.

## 8. ER Diagram — діаграма сутність-зв'язок

**ER Diagram (Entity-Relationship Diagram)** — схема, яка показує сутності, їхні атрибути та зв'язки.

Вона допомагає побачити структуру даних до написання SQL-коду.

Для навчальних проєктів достатньо простого текстового опису:

    User
        id (PK)
        email
        name

          1
          |
          | owns
          |
          N

    Schedule
        id (PK)
        owner_id (FK)
        title

          1
          |
          | contains
          |
          N

    Event
        id (PK)
        schedule_id (FK)
        title
        starts_at
        ends_at

Ця схема показує два зв'язки типу One-to-Many.

Для складніших моделей зручно використовувати графічні інструменти, наприклад diagrams.net або dbdiagram.io.

Важливо: діаграма не замінює опис бізнес-правил. Вона показує структуру, але не завжди пояснює поведінку системи.

## 9. Рівні моделювання даних

Зазвичай виділяють три рівні: концептуальний, логічний і фізичний.

### 9.1. Conceptual Data Model

**Концептуальна модель** показує головні поняття предметної області та зв'язки між ними.

Приклад:

    User → Schedule → Event

На цьому рівні не потрібно визначати точні SQL-типи, індекси чи синтаксис конкретної СУБД.

Мета — узгодити загальне розуміння системи.

### 9.2. Logical Data Model

**Логічна модель** уточнює сутності, атрибути, ключі та зв'язки.

    User
        id
        email
        name

    Schedule
        id
        title
        ownerId

    Event
        id
        title
        startsAt
        scheduleId

На цьому рівні вже визначаються ключі, обов'язкові поля та правила зв'язків, але модель ще не прив'язана до всіх особливостей конкретної СУБД.

### 9.3. Physical Data Model

**Фізична модель** описує конкретну реалізацію в обраній базі даних.

Наприклад, PostgreSQL:

    CREATE TABLE schedules (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title VARCHAR(100) NOT NULL,
        owner_id INTEGER NOT NULL REFERENCES users(id),
        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    );

Тут уже визначено:

- Типи стовпців.
- Обмеження.
- Значення за замовчуванням.
- Спосіб генерації ідентифікатора.
- Зовнішні ключі.

### Порівняння

| Рівень | Головне запитання | Приклад |
|---|---|---|
| Conceptual | Які поняття існують? | User, Schedule, Event |
| Logical | Які атрибути та зв'язки мають ці поняття? | Schedule має ownerId |
| Physical | Як це реалізувати в БД? | PostgreSQL, INTEGER, FK |

Для невеликого навчального застосунку ці рівні не обов'язково оформлювати як три окремі документи. Головне — розуміти різницю між ними.

---

## 10. Normalization — нормалізація даних

**Normalization (нормалізація)** — організація реляційних даних так, щоб зменшити надлишковість і уникнути проблем під час вставлення, оновлення та видалення записів.

### 10.1. Проблема дублювання

Уявімо таблицю, у якій зберігаються розклади:

    schedules
        id
        title
        owner_name
        owner_email

    1 | Розклад на будні | Олександр | alex@example.com
    2 | Святковий       | Олександр | alex@example.com
    3 | Недільний       | Олександр | alex@example.com

Ім'я та email користувача повторюються в кожному розкладі.

Якщо email зміниться, доведеться оновлювати кілька рядків. Якщо один рядок залишиться без змін, дані стануть суперечливими.

### 10.2. Розділення таблиць

Краще зберігати користувачів окремо:

    users
        id
        name
        email

    schedules
        id
        title
        owner_id

Тепер ім'я та email зберігаються в одному місці, а `owner_id` вказує на власника.

### 10.3. Перша нормальна форма (1NF)

Спрощене практичне правило: кожен стовпець повинен містити одне значення відповідного типу, а не список значень, упакований в одне поле.

Невдалий варіант:

    schedules
        id
        title
        event_titles

    1 | Розклад | Літургія, Вечірня, Утреня

Краще:

    schedules
        id
        title

    events
        id
        schedule_id
        title

Тепер кожна подія є окремим записом.

### 10.4. Друга нормальна форма (2NF)

Таблиця повинна відповідати 1NF, а кожен неключовий атрибут має залежати від усього складеного ключа, а не лише від його частини.

Наприклад:

    enrollments
        student_id
        course_id
        student_name
        enrolled_at

    PRIMARY KEY (student_id, course_id)

`student_name` залежить від `student_id`, а не від усієї комбінації `student_id + course_id`.

Тому ім'я студента краще зберігати в таблиці `students`.

### 10.5. Третя нормальна форма (3NF)

Таблиця повинна відповідати 2NF і не містити небажаних транзитивних залежностей неключових атрибутів.

Спрощений приклад:

    users
        id
        city_id
        city_name

Якщо `city_name` визначається через `city_id`, назву міста не потрібно дублювати в кожному користувачі.

Можна створити:

    cities
        id
        name

    users
        id
        city_id

Однак окрема таблиця міст потрібна не завжди. Рішення залежить від вимог, повторного використання даних і правил предметної області.

**Для початку достатньо навчитися помічати дублювання, правильно розділяти сутності та визначати ключі.** Глибше вивчення нормальних форм можна проводити поступово.

---

## 11. Data Integrity — цілісність даних

**Data Integrity** — властивість даних залишатися правильними, узгодженими та відповідати встановленим правилам.

Основні види:

### Entity Integrity

Кожен запис має однозначний ідентифікатор.

    PRIMARY KEY (id)

### Referential Integrity

Зовнішній ключ посилається на наявний запис.

    owner_id INTEGER REFERENCES users(id)

### Domain Integrity

Значення відповідає очікуваному типу та допустимим обмеженням.

    title TEXT NOT NULL

    age INTEGER CHECK (age >= 0)

### Business Integrity

Дані відповідають правилам предметної області.

Наприклад, подія не може завершуватися раніше, ніж починається.

    CHECK (
        ends_at IS NULL
        OR ends_at >= starts_at
    )

Важливо розділяти перевірки:

- **Frontend** — допомагає користувачеві вводити коректні дані.
- **Backend** — перевіряє вхідні дані та права доступу.
- **Database** — гарантує цілісність на рівні збережених даних.

Ці рівні доповнюють один одного, а не замінюють.

---

## 12. Типи даних і вибір полів

Під час фізичного моделювання потрібно вибирати типи даних відповідно до змісту поля.

Приклади для PostgreSQL:

| Дані | Тип | Приклад |
|---|---|---|
| Ідентифікатор | `INTEGER` або `BIGINT` | `id` |
| Короткий текст | `VARCHAR(n)` або `TEXT` | `title` |
| Ціле число | `INTEGER` | `sort_order` |
| Грошова сума | `NUMERIC(p, s)` | `price` |
| Дата | `DATE` | `event_date` |
| Дата й час із часовим поясом | `TIMESTAMPTZ` | `starts_at` |
| Логічне значення | `BOOLEAN` | `is_active` |
| Структуровані JSON-дані | `JSONB` | `settings` |

Приклади:

    CREATE TABLE events (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title TEXT NOT NULL,
        event_date DATE,
        starts_at TIMESTAMPTZ,
        is_published BOOLEAN NOT NULL DEFAULT FALSE
    );

Кілька практичних правил:

- Не зберігай дату як довільний текст, якщо з нею потрібно працювати як із датою.
- Не зберігай гроші у `REAL` або `DOUBLE PRECISION`, якщо потрібна точна десяткова арифметика; зазвичай краще використовувати `NUMERIC`.
- Не роби кожне поле `TEXT` лише заради простоти.
- Не використовуй `JSONB` замість нормалізованих таблиць без конкретної причини.
- Не додавай поля «про всяк випадок», якщо вони не потрібні вимогам.

## 13. Назви сутностей, таблиць і полів

Послідовна система назв полегшує читання коду.

Приклад моделі:

    Domain entity:
        Schedule

    Database table:
        schedules

    Database column:
        owner_id

    TypeScript property:
        ownerId

Зазвичай у PostgreSQL зручно використовувати `snake_case` для назв таблиць і стовпців.

    users
    schedules
    schedule_events

    created_at
    updated_at
    owner_id
    schedule_id

У JavaScript і TypeScript поширений `camelCase`:

    createdAt
    updatedAt
    ownerId
    scheduleId

Не потрібно намагатися зробити всі назви однаковими в усіх шарах. Важливо, щоб перетворення між назвами було зрозумілим і послідовним.

## 14. Domain Model не дорівнює Database Model

Це важлива архітектурна відмінність.

Сутність предметної області не завжди повинна повністю збігатися з таблицею бази даних або об'єктом, який повертається клієнту.

Наприклад, у базі даних:

    users
        id
        email
        password_hash
        name

А публічний профіль може містити лише:

    UserProfile
        id
        name

`password_hash` потрібен для роботи системи автентифікації, але його не можна передавати у звичайну відповідь API.

У TypeScript можна описати різні типи:

    type UserRecord = {
        id: number;
        email: string;
        passwordHash: string;
        name: string;
    };

    type PublicUser = {
        id: number;
        name: string;
    };

Тут:

- `UserRecord` описує дані, з якими працює backend.
- `PublicUser` описує безпечне представлення користувача для клієнта.

Це навчальний приклад. У реальному проєкті типи варто розміщувати відповідно до архітектури та призначення модулів.

**Правило:** не повертай клієнту весь запис бази даних автоматично, якщо він містить приватні або внутрішні поля.

---

## 15. Domain Model і бізнес-логіка

Domain Model може бути не просто набором даних. Вона також може описувати правила, що визначають допустиму поведінку.

Наприклад, розклад має статус публікації.

    Schedule
        id
        title
        status

    Possible statuses:
        draft
        published
        archived

Необхідно визначити допустимі переходи:

    draft → published
    published → archived

А також з'ясувати:

- Чи можна редагувати опублікований розклад?
- Чи можна повернути архівний розклад до стану `published`?
- Хто має право змінювати статус?
- Чи потрібна дата публікації?

Якщо ці правила важливі, їх потрібно явно описати.

Для простого застосунку достатньо функцій і перевірок у сервісному шарі. У складніших системах правила можуть бути частиною окремих доменних об'єктів або модулів.

Не потрібно автоматично впроваджувати складні патерни на зразок Domain-Driven Design у кожному навчальному проєкті.

## 16. Практичний приклад: Worship Schedule

Розглянемо початкову модель застосунку, у якому користувачі створюють власні розклади богослужінь.

### 16.1. Вимоги

- Користувач має обліковий запис.
- Користувач може створювати кілька приватних розкладів.
- Кожен розклад має назву.
- Розклад може містити багато подій.
- Користувач може редагувати власні розклади.
- Подія має назву та час.
- Розклад і події зберігаються в PostgreSQL.

### 16.2. Domain Model

    User
        id
        email
        name

    Schedule
        id
        title
        ownerId
        createdAt
        updatedAt

    Event
        id
        scheduleId
        title
        startsAt
        endsAt

### 16.3. Зв'язки

    User 1 ─── N Schedule

    Schedule 1 ─── N Event

### 16.4. Бізнес-правила

    1. Email користувача має бути унікальним.
    2. Кожен розклад має власника.
    3. Назва розкладу обов'язкова.
    4. Подія повинна належати розкладу.
    5. Користувач редагує тільки власні розклади.
    6. Час завершення не передує часу початку.

### 16.5. Логічна модель таблиць

    users
        id
        email
        name

    schedules
        id
        title
        owner_id
        created_at
        updated_at

    events
        id
        schedule_id
        title
        starts_at
        ends_at

### 16.6. SQL-реалізація

Припустімо, що таблиця `users` уже створена.

    CREATE TABLE schedules (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        title VARCHAR(100) NOT NULL,
        owner_id INTEGER NOT NULL REFERENCES users(id)
            ON DELETE CASCADE,
        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
        updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    );

    CREATE TABLE events (
        id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        schedule_id INTEGER NOT NULL REFERENCES schedules(id)
            ON DELETE CASCADE,
        title VARCHAR(200) NOT NULL,
        starts_at TIMESTAMPTZ NOT NULL,
        ends_at TIMESTAMPTZ,
        CONSTRAINT valid_event_time
            CHECK (
                ends_at IS NULL
                OR ends_at >= starts_at
            )
    );

Тут `ON DELETE CASCADE` означає:

- Видалення користувача видаляє його розклади.
- Видалення розкладу видаляє пов'язані події.

Таке рішення є прикладом, а не універсальним правилом. Перед використанням каскадного видалення потрібно переконатися, що воно відповідає вимогам. Якщо дані необхідно зберігати для історії, аудиту або відновлення, модель може бути іншою.

Також `updated_at` не змінюється автоматично лише тому, що поле має значення за замовчуванням. Оновлення цього поля потрібно реалізувати окремо — наприклад, у backend або за допомогою тригера бази даних.

### 16.7. Перевірка моделі

Перед написанням API перевір:

- Чи може користувач створити два розклади з однаковою назвою?
- Чи потрібна унікальність назви в межах одного користувача?
- Чи можна зберегти подію без часу завершення?
- Чи потрібно зберігати історію видалених розкладів?
- Чи можуть розклади бути спільними?
- Чи потрібно додавати категорії подій?
- Чи є події повторюваними?

Ці запитання не обов'язково означають, що потрібно додати всі відповідні поля та таблиці. Вони допомагають з'ясувати межі першої версії застосунку.

## 17. Моделювання повторюваних подій

У розкладах може виникнути потреба зберігати події, що повторюються щотижня або щороку.

На перший погляд можна додати поле:

    events
        id
        title
        starts_at
        recurrence

Але `recurrence` може означати багато різних речей:

- Повторюється щотижня.
- Повторюється в певні дні тижня.
- Повторюється щороку.
- Має дату завершення повторень.
- Має винятки з правила повторення.

Якщо потрібна складна логіка повторень, варто відокремити правило повторення від конкретних екземплярів подій.

Спрощена модель:

    events
        id
        title
        starts_at
        recurrence_rule_id

    recurrence_rules
        id
        frequency
        interval
        ends_at

Це лише ілюстрація. Конкретна структура залежить від вимог і формату правил повторення.

Для першої версії застосунку не потрібно створювати складну систему повторюваних подій, якщо достатньо звичайних подій із конкретними датами.

## 18. Типові помилки під час моделювання

### Помилка 1. Створення таблиць без аналізу вимог

Починати відразу з SQL небезпечно: можна не врахувати важливі сценарії.

**Краще:** спочатку описати сутності, зв'язки та бізнес-правила.

### Помилка 2. Одна таблиця для всіх даних

Наприклад, зберігати користувача, розклад і всі події в одному записі.

Це ускладнює пошук, оновлення, видалення та контроль цілісності.

**Краще:** розділяти сутності за змістом і правилами предметної області.

### Помилка 3. Дублювання даних

Зберігати email користувача в кожному його розкладі.

**Краще:** зберігати email у `users`, а в `schedules` — посилання на власника.

### Помилка 4. Відсутність Foreign Key

Поле `owner_id` існує, але не має зовнішнього ключа.

У такому разі база даних може прийняти посилання на неіснуючого користувача.

**Краще:** застосовувати Foreign Key там, де він відображає справжній зв'язок.

### Помилка 5. Плутанина між зв'язком і правами доступу

Наявність `owner_id` ще не означає, що backend автоматично перевіряє власника.

**Краще:** перевіряти авторизацію під час кожної операції, яка вимагає обмеження доступу.

### Помилка 6. Занадто багато таблиць

Створення окремої таблиці для кожного простого атрибута може ускладнити модель без реальної користі.

**Краще:** створювати окрему сутність, коли вона має самостійний зміст, зв'язки, правила або потребує окремого життєвого циклу.

### Помилка 7. Передчасна оптимізація

Додавання багатьох індексів, кешів і складних структур до появи реальних вимог.

**Краще:** спочатку створити правильну модель, а потім оптимізувати за результатами вимірювань.

### Помилка 8. Зберігання списків у звичайному текстовому полі

Наприклад:

    event_titles = "Літургія, Вечірня, Утреня"

**Краще:** якщо елементи є самостійними записами зі своїми властивостями, зберігати їх окремо.

### Помилка 9. Ігнорування правил видалення

Видалення користувача може залишити записи без власника або випадково знищити потрібну історію.

**Краще:** заздалегідь визначити `CASCADE`, `RESTRICT`, `SET NULL` або іншу відповідну поведінку.

### Помилка 10. Змішування внутрішніх даних і публічного API

Повернення всього рядка користувача разом із `password_hash`.

**Краще:** визначати окремі DTO або типи відповіді API.

## 19. Як Domain and Data Modeling пов'язане з іншими етапами архітектури

Моделювання предметної області та даних не існує окремо від інших архітектурних рішень.

    Requirements
        ↓
    Domain Model
        ↓
    Data Model
        ↓
    Database Schema
        ↓
    Backend Services
        ↓
    API
        ↓
    Frontend UI

Це спрощена послідовність, а не обов'язково суворий односпрямований процес. Під час реалізації нові вимоги можуть змусити переглянути модель.

Наприклад:

- **Requirements and MVP** визначає, які функції потрібні першій версії.
- **User Stories and Use Cases** описує, як користувач взаємодіє із системою.
- **User Flows** показує послідовність дій.
- **Wireframes and Screen Planning** допомагає зрозуміти, які дані потрібні інтерфейсу.
- **Domain and Data Modeling** визначає сутності, їхні властивості, зв'язки та правила.
- **Software Architecture** визначає, де розташувати логіку й як організувати компоненти.

Наприклад, якщо інтерфейс дозволяє створювати кілька приватних розкладів, це впливає на модель `User → Schedule`. Якщо пізніше з'явиться спільний доступ, доведеться додати правила авторизації, а можливо, і нову сутність для спільного доступу.

## 20. Domain Modeling і Domain-Driven Design

**Domain-Driven Design (DDD)** — підхід до розробки складних систем, який ставить у центр уваги предметну область, її мову та бізнес-правила.

Domain Modeling є одним з інструментів DDD, але ці поняття не тотожні.

У DDD зустрічаються такі поняття:

- **Ubiquitous Language** — спільна мова, якою користуються розробники та фахівці предметної області.
- **Entity** — об'єкт з ідентичністю.
- **Value Object** — об'єкт, який визначається своїми значеннями, а не окремою ідентичністю.
- **Aggregate** — група пов'язаних доменних об'єктів із визначеною межею узгодженості.
- **Repository** — абстракція для доступу до доменних об'єктів.
- **Bounded Context** — межа, у якій модель і терміни мають конкретне значення.

Наприклад, `Event` може бути доменною сутністю, а проміжок часу — Value Object.

Однак для простого CRUD-застосунку не потрібно відразу реалізовувати повний DDD. Спочатку важливо впевнено володіти базовими поняттями: сутності, атрибути, зв'язки, обмеження та бізнес-правила.

## 21. Практичний алгоритм для власних проєктів

Перед створенням таблиць PostgreSQL використовуй такий порядок.

### Етап 1. Опис предметної області

    Назва проєкту:
        Worship Schedule

    Основні користувачі:
        зареєстровані користувачі

    Основні можливості:
        створення розкладів
        редагування розкладів
        додавання подій

### Етап 2. Список сутностей

    User
    Schedule
    Event

### Етап 3. Атрибути сутностей

    User:
        id
        email
        name

    Schedule:
        id
        title
        ownerId

    Event:
        id
        scheduleId
        title
        startsAt
        endsAt

### Етап 4. Зв'язки

    User 1:N Schedule
    Schedule 1:N Event

### Етап 5. Бізнес-правила

    User:
        email унікальний

    Schedule:
        має власника
        має непорожню назву

    Event:
        має розклад
        має назву
        час завершення не передує часу початку

### Етап 6. Перевірка сценаріїв

    Create:
        Чи можна створити запис із неповними даними?

    Read:
        Які записи може переглядати користувач?

    Update:
        Чи можна редагувати чужі записи?

    Delete:
        Що відбувається з пов'язаними записами?

### Етап 7. SQL-реалізація

Створи таблиці, ключі, обмеження та індекси відповідно до моделі.

### Етап 8. Перевірка

Переконайся, що база даних не приймає очевидно некоректні дані та що зв'язки працюють так, як було задумано.

## 22. Що потрібно знати на різних рівнях

### Core — основа

✔ Розуміти, що таке Domain Model і Data Model.

✔ Вміти визначати сутності та їхні атрибути.

✔ Розуміти Primary Key і Foreign Key.

✔ Розрізняти зв'язки 1:1, 1:N і M:N.

✔ Розуміти `NOT NULL`, `UNIQUE`, `CHECK` і `DEFAULT`.

✔ Уміти намалювати просту ER-діаграму.

### Junior — практична розробка

✔ Перетворювати вимоги на модель даних.

✔ Проєктувати таблиці PostgreSQL.

✔ Визначати обов'язкові та необов'язкові поля.

✔ Використовувати зовнішні ключі й обмеження цілісності.

✔ Розуміти базові принципи нормалізації.

✔ Продумувати поведінку під час видалення пов'язаних записів.

✔ Відокремлювати дані бази від DTO, які повертаються через API.

✔ Перевіряти права доступу окремо від цілісності зв'язків.

### Middle — поглиблене розуміння

✔ Моделювати складніші бізнес-правила.

✔ Розуміти компроміси між нормалізацією та денормалізацією.

✔ Проєктувати індекси відповідно до запитів.

✔ Визначати межі доменних модулів.

✔ Аналізувати транзакції та конкурентні зміни.

✔ Проєктувати міграції без втрати даних.

✔ Визначати, коли виправдані Value Objects, Aggregates та інші концепції DDD.

### Senior — системне проєктування

✔ Моделювати великі предметні області.

✔ Узгоджувати модель даних між незалежними модулями.

✔ Враховувати історичність, аудит, версіонування та життєвий цикл даних.

✔ Оцінювати наслідки зміни моделі для API, міграцій і сумісності.

✔ Приймати обґрунтовані рішення щодо розподілу даних між сервісами.

✔ Визначати компроміси між узгодженістю, масштабованістю та складністю системи.

## 24. Мінішпаргалка

    Domain
        предметна область

    Entity
        сутність з ідентичністю

    Attribute
        властивість сутності

    Relationship
        зв'язок між сутностями

    Business Rule
        правило предметної області

    Primary Key
        унікальний ідентифікатор запису

    Foreign Key
        посилання на запис іншої таблиці

    Cardinality
        кількість пов'язаних записів

    Optionality
        обов'язковість зв'язку

    ER Diagram
        діаграма сутностей і зв'язків

    Conceptual Model
        основні поняття предметної області

    Logical Model
        сутності, атрибути, ключі та зв'язки

    Physical Model
        реалізація моделі в конкретній СУБД

    Normalization
        зменшення надлишковості та аномалій даних

    Data Integrity
        правильність і узгодженість даних

    Constraint
        обмеження допустимих даних

    DTO
        об'єкт передачі даних між шарами або через API

    DDD
        підхід до розробки з фокусом на предметній області

## 25. Головне, що потрібно запам'ятати

**Domain Modeling відповідає на запитання: «Які поняття, правила та взаємозв'язки існують у предметній області?»**

**Data Modeling відповідає на запитання: «Як структурувати дані, щоб правильно їх зберігати та пов'язувати?»**

**Database Schema відповідає на запитання: «Як саме ця структура реалізована в конкретній базі даних?»**

Практичний порядок роботи:

    Requirements
        ↓
    Identify Entities
        ↓
    Define Attributes
        ↓
    Define Relationships
        ↓
    Define Business Rules
        ↓
    Create ER Diagram
        ↓
    Design Database Schema
        ↓
    Implement Constraints
        ↓
    Test Data Integrity

Для Junior Full Stack Developer найважливіше — навчитися перетворювати вимоги на просту, зрозумілу модель, правильно визначати зв'язки та забезпечувати цілісність даних.

Не потрібно відразу будувати складну архітектуру. Почни з невеликої моделі, перевір її на реальних сценаріях і розширюй лише тоді, коли цього вимагають потреби застосунку.
