# Deployment Planning — Планування розгортання

> **Deployment Planning** — це процес планування того, як програмне забезпечення буде підготовлено до запуску, розгорнуто в цільовому середовищі, налаштовано, перевірено та оновлюватиметься після випуску.

Deployment Planning допомагає відповісти на запитання:

- Де буде працювати застосунок?
- Як frontend, backend і database взаємодіятимуть між собою?
- Як підготувати production-середовище?
- Як зберігати та передавати змінні середовища й секрети?
- Як налаштувати домен, HTTPS і доступ до сервера?
- Як виконувати міграції бази даних?
- Як перевірити застосунок після розгортання?
- Як безпечно випускати нові версії?
- Як повернутися до попередньої версії, якщо оновлення зламало застосунок?
- Як контролювати помилки, доступність і продуктивність після запуску?

Головна мета — **заздалегідь визначити надійний і повторюваний спосіб доставки застосунку від розробки до production**.

---

## 1. Навіщо потрібне планування розгортання

Під час розробки застосунок зазвичай запускається локально.

    Developer's computer
        ↓
    npm run dev
        ↓
    Browser
        ↓
    Local application

Але локальна робота ще не означає, що застосунок готовий до використання іншими людьми.

У production можуть виникнути проблеми:

- сервер не має потрібної версії Node.js;
- відсутні змінні середовища;
- frontend звертається до неправильного API URL;
- production-база даних не налаштована;
- міграції не виконані;
- HTTPS або домен працюють неправильно;
- сервер не має доступу до бази даних;
- секрети випадково потрапили до Git;
- нова версія несумісна з поточною структурою бази;
- після оновлення застосунок перестає запускатися;
- немає резервної копії даних;
- помилки виникають, але ніхто їх не помічає.

Deployment Planning допомагає передбачити ці проблеми до випуску.

### Основні переваги

- ✔ Передбачуваний процес розгортання.
- ✔ Менше помилок конфігурації.
- ✔ Розділення development і production.
- ✔ Безпечніше керування секретами.
- ✔ Контроль змін бази даних.
- ✔ Швидше виявлення проблем після випуску.
- ✔ Можливість відновити роботу після невдалого оновлення.
- ✔ Зрозумілий процес подальшого супроводу застосунку.

---

## 2. Місце Deployment Planning в архітектурі проєкту

Планування розгортання спирається на вимоги, архітектуру застосунку, API-контракти та стратегію тестування.

    Requirements
        ↓
    Domain and Data Modeling
        ↓
    Application Architecture
        ↓
    API Contracts
        ↓
    Implementation Planning
        ↓
    Testing Strategy
        ↓
    Deployment Planning
        ↓
    Implementation and Configuration
        ↓
    Build and Test
        ↓
    Deployment
        ↓
    Verification and Monitoring

Це спрощена послідовність. Насправді планування розгортання починається ще під час проєктування архітектури.

Наприклад, якщо застосунок використовує PostgreSQL, потрібно заздалегідь вирішити:

    - де розміщуватиметься база даних;
    - як backend підключатиметься до неї;
    - як зберігатимуться облікові дані;
    - як виконуватимуться міграції;
    - як створюватимуться резервні копії;
    - як перевірятиметься доступність бази.

Ці рішення впливають на структуру застосунку, безпеку, вартість і подальший супровід.

## 3. Основні поняття

### 3.1. Deployment — розгортання

Deployment — процес розміщення та запуску програмного забезпечення в певному середовищі.

Він може включати:

- отримання вихідного коду;
- встановлення залежностей;
- перевірку коду;
- збирання застосунку;
- виконання міграцій;
- налаштування конфігурації;
- запуск або перезапуск сервісів;
- перевірку працездатності.

Розгортання може виконуватися вручну або автоматично.

### 3.2. Build — збирання

Build — процес підготовки застосунку до запуску або публікації.

Для frontend це може бути перетворення вихідного коду на оптимізовані HTML, CSS і JavaScript.

Для Next.js production build також може містити серверні компоненти застосунку та інші артефакти, необхідні для production-запуску.

Приклад:

    npm run build

Конкретний результат залежить від фреймворку та конфігурації.

### 3.3. Release — випуск версії

Release — підготовлена версія програмного забезпечення, яку планують зробити доступною користувачам.

Release може містити:

    - конкретну версію коду;
    - номер версії або Git commit;
    - зміни API;
    - зміни бази даних;
    - нотатки про випуск;
    - інструкції з розгортання.

### 3.4. Rollback — відкат

Rollback — повернення до попереднього робочого стану або версії після невдалого оновлення.

Наприклад:

    Version 1 → Version 2

    Version 2 має критичну помилку.

    Повертаємо застосунок до Version 1.

Важливо: відкат коду не завжди автоматично відновлює попередній стан бази даних. Міграції потрібно планувати окремо.

### 3.5. Infrastructure — інфраструктура

Інфраструктура — середовище та ресурси, необхідні для роботи застосунку.

Наприклад:

- сервер або хмарна платформа;
- база даних;
- мережа;
- DNS;
- HTTPS-сертифікати;
- файлове сховище;
- система логування;
- моніторинг;
- резервне копіювання.

### 3.6. Configuration — конфігурація

Configuration — параметри, які визначають поведінку застосунку в конкретному середовищі.

Наприклад:

    NODE_ENV=production
    DATABASE_URL=...
    API_BASE_URL=...

Конфігурація повинна відповідати середовищу, у якому запускається застосунок.

### 3.7. Artifact — артефакт збірки

Artifact — результат підготовки програмного забезпечення, який можна використати для розгортання.

Це може бути:

- зібраний frontend;
- production build Next.js;
- архів із застосунком;
- Docker image;
- пакет певної версії.

Артефакт допомагає відокремити підготовку програми від її запуску.

## 4. Deployment Environments — середовища розгортання

Застосунок може існувати в кількох середовищах.

Найпоширеніші:

- Development.
- Test.
- Staging.
- Production.

### 4.1. Development

Development — середовище, у якому розробник створює та змінює код.

    Typical characteristics:
    - локальний запуск;
    - швидке оновлення коду;
    - тестові дані;
    - debugging;
    - development-сервер.

Приклад:

    npm run dev

Development може використовувати локальну PostgreSQL або іншу окрему базу даних.

### 4.2. Test

Test environment — середовище для автоматизованих або ручних перевірок.

    Typical characteristics:
    - тестова база даних;
    - контрольовані тестові дані;
    - автоматичний запуск тестів;
    - ізоляція від production.

Не слід використовувати production-базу для тестів, які можуть змінювати або видаляти дані.

### 4.3. Staging

Staging — середовище, яке максимально наближене до production і використовується для перевірки майбутнього випуску.

Тут можна перевірити:

- production-збірку;
- змінні середовища;
- міграції;
- інтеграцію сервісів;
- поведінку перед випуском;
- основні сценарії користувачів.

Для маленького навчального проєкту окремий staging може бути необов'язковим.

### 4.4. Production

Production — середовище, у якому застосунком користуються реальні користувачі.

Production потребує особливої уваги до:

- безпеки;
- доступності;
- конфігурації;
- приватності даних;
- резервного копіювання;
- логування;
- контролю помилок;
- процесу оновлення.

### Порівняння середовищ

| Середовище | Основне призначення | Типові дані |
|---|---|---|
| Development | Розробка | Локальні тестові дані |
| Test | Автоматизовані перевірки | Ізольовані тестові дані |
| Staging | Перевірка перед випуском | Тестові або підготовлені дані |
| Production | Робота для користувачів | Реальні дані |

### Основний принцип

Середовища можуть мати різну конфігурацію, але поведінка застосунку має залишатися передбачуваною.

## 5. Вибір способу розгортання

Спосіб розгортання залежить від архітектури застосунку, бюджету, досвіду розробника та вимог до обслуговування.

### 5.1. Static Hosting

Static hosting — розміщення статичних файлів, наприклад HTML, CSS, JavaScript і зображень.

Підходить для:

- простих сайтів;
- документації;
- портфоліо;
- frontend-застосунків, які не потребують власного серверного виконання.

Переваги:

- просте налаштування;
- часто невисока вартість;
- зручне розповсюдження статичних файлів;
- зазвичай не потрібно адмініструвати сервер.

Обмеження:

- серверна логіка не виконується без окремого backend або serverless-функцій;
- доступ до бази даних не можна безпечно організувати безпосередньо з браузера.

### 5.2. Frontend Hosting

Frontend hosting може підтримувати статичні застосунки та фреймворки із серверними можливостями.

Наприклад, Next.js може потребувати:

- статичного хостингу для повністю статичного результату;
- платформи, яка підтримує серверні можливості Next.js;
- власного сервера або контейнера.

Перед вибором платформи потрібно перевірити, чи підтримує вона саме ті функції фреймворку, які використовує проєкт.

### 5.3. Backend Hosting

Backend можна розмістити на:

- керованій платформі застосунків;
- віртуальному сервері;
- контейнерній платформі;
- serverless-платформі, якщо архітектура сумісна.

Потрібно врахувати:

    - запуск Node.js;
    - встановлення залежностей;
    - змінні середовища;
    - мережевий доступ до бази;
    - логи;
    - перезапуск після помилок;
    - підтримку потрібної версії Node.js.

### 5.4. Managed Database

Managed database — база даних, адмініструванням якої частково займається провайдер.

Для PostgreSQL провайдер може забезпечувати:

- створення інстансу;
- мережеве підключення;
- оновлення;
- резервне копіювання;
- контроль ресурсів;
- інструменти відновлення.

Конкретний набір можливостей залежить від тарифу та провайдера.

### 5.5. VPS — Virtual Private Server

VPS — віртуальний сервер, на якому розробник або адміністратор самостійно керує значною частиною середовища.

Можна встановити:

- Linux;
- Node.js;
- PostgreSQL;
- Nginx;
- системні служби;
- firewall;
- інструменти моніторингу.

Переваги:

- гнучкість;
- контроль над конфігурацією;
- можливість розміщувати кілька сервісів.

Недоліки:

- більше адміністративної роботи;
- необхідність оновлювати систему;
- налаштування безпеки;
- відповідальність за резервні копії та відновлення.

Для першого full-stack проєкту керовані сервіси часто дозволяють швидше зосередитися на розробці. VPS корисний для вивчення Linux, мереж і серверного адміністрування.

## 6. Deployment Architecture — архітектура розгортання

Deployment architecture описує, де саме розміщені компоненти системи та як вони взаємодіють у production.

Наприклад, вебзастосунок може мати таку структуру:

    User
      ↓
    Browser
      ↓ HTTPS
    Frontend Hosting
      ↓ HTTPS
    Backend API
      ↓
    PostgreSQL

Це лише одна з можливих схем. Frontend і backend можуть бути на одній платформі або на різних сервісах.

### Що потрібно визначити

- де розміщуватиметься frontend;
- де працюватиме backend;
- де буде база даних;
- як компоненти взаємодіятимуть;
- як обмежити доступ до бази;
- як передаватимуться секрети;
- які домени використовуватимуться;
- як організувати HTTPS;
- як перевіряти доступність компонентів.

### Приклад для Next.js + NestJS + PostgreSQL

    Browser
       |
       | HTTPS
       v
    Next.js Application
       |
       | HTTPS / API
       v
    NestJS Backend
       |
       | PostgreSQL connection
       v
    PostgreSQL Database

У такій архітектурі браузер не повинен отримувати пароль PostgreSQL або безпосередньо підключатися до бази даних.

Backend виконує перевірки доступу та взаємодіє з PostgreSQL.

Якщо Next.js сам виконує серверну бізнес-логіку, окремий NestJS може бути не потрібний. Архітектуру не слід ускладнювати без конкретної потреби.

## 7. Build Process — процес збирання

Перед розгортанням потрібно визначити, як застосунок готується до production.

Типовий процес:

    Source Code
        ↓
    Install Dependencies
        ↓
    Static Checks
        ↓
    Tests
        ↓
    Build
        ↓
    Deployment Artifact
        ↓
    Deployment

### Що потрібно перевірити

- чи існує команда встановлення залежностей;
- чи можна виконати перевірку типів;
- чи проходять тести;
- чи успішно виконується build;
- чи не використовуються локальні файли, відсутні в production;
- чи не потрібні додаткові ресурси;
- чи відповідає Node.js версія вимогам проєкту.

### Приклад команд

    npm ci
    npm run lint
    npm run typecheck
    npm test
    npm run build

Це приклад можливої послідовності. Скрипти `lint`, `typecheck` і `test` мають бути визначені в `package.json`.

`npm ci` зазвичай використовують у CI для встановлення залежностей за lock-файлом. Для цього потрібен актуальний `package-lock.json`.

### Чому build потрібно перевіряти до розгортання

Застосунок може працювати в development, але не збиратися для production через:

- помилки TypeScript;
- неправильні імпорти;
- відсутні залежності;
- використання браузерних API в серверному коді;
- помилки конфігурації;
- неправильні змінні середовища.

Успішний development-запуск не замінює перевірку production-збірки.

## 8. Environment Variables — змінні середовища

Environment variables — параметри, які передаються застосунку через його середовище запуску.

Вони допомагають відокремити конфігурацію від вихідного коду.

### Приклад

    NODE_ENV=production
    DATABASE_URL=...
    SESSION_SECRET=...
    API_BASE_URL=...

Це умовний приклад. Реальні значення потрібно задавати в налаштуваннях конкретного середовища.

### Що зберігають у змінних середовища

- адресу бази даних;
- секрети сесій;
- ключі зовнішніх API;
- налаштування режиму роботи;
- адреси внутрішніх сервісів;
- параметри інтеграцій.

### Чого не слід робити

Не потрібно зберігати production-секрети безпосередньо у вихідному коді.

Небажаний приклад:

    const databaseUrl =
        "postgres://admin:real-password@example.com/app";

Краще:

    const databaseUrl = process.env.DATABASE_URL;

У реальному застосунку потрібно також перевірити, що обов'язкова змінна визначена, і коректно завершити запуск, якщо її немає.

### Приклад перевірки конфігурації в Node.js

    const databaseUrl = process.env.DATABASE_URL;

    if (!databaseUrl) {
        throw new Error("DATABASE_URL is required");
    }

Для складніших застосунків зручно централізовано перевіряти всі змінні середовища під час запуску.

### Frontend і секрети

Важливо розрізняти серверні та клієнтські змінні.

У Next.js змінні з префіксом `NEXT_PUBLIC_` призначені для значень, які можуть потрапити до клієнтського коду.

Наприклад:

    NEXT_PUBLIC_API_URL=https://api.example.com

Не можна використовувати цей префікс для паролів, приватних API-ключів або секретів сесії.

Значення, які потрапляють до браузера, потрібно вважати публічними.

## 9. Database Deployment — розгортання бази даних

База даних є критичною частиною deployment planning.

Потрібно визначити:

- де розміщуватиметься база;
- хто матиме до неї доступ;
- як backend підключатиметься;
- як застосовуватимуться зміни схеми;
- як зберігатимуться резервні копії;
- як відновлюватимуться дані;
- як контролюватимуться витрати та ресурси.

### 9.1. Development Database

Локальна база для розробки.

    Developer
        ↓
    Local PostgreSQL
        ↓
    Development Data

Вона може містити тестові користувацькі записи та демонстраційні дані.

### 9.2. Production Database

Production-база з даними реальних користувачів.

    Backend
        ↓
    Protected Connection
        ↓
    Production PostgreSQL

До production-бази не повинні підключатися випадкові клієнти або сторонні процеси без належної авторизації.

### 9.3. Database Migrations

Міграції — контрольовані зміни структури бази даних.

Наприклад:

    Migration 001:
    Створити таблицю users.

    Migration 002:
    Створити таблицю schedules.

    Migration 003:
    Додати поле updated_at.

Міграції мають бути версіонованими та зберігатися разом із кодом.

### Чому не варто змінювати production-схему вручну без контролю

Якщо зміни бази не задокументовані, різні середовища можуть мати різну структуру.

У результаті:

    Development:
    Нове поле існує.

    Production:
    Нового поля немає.

    Результат:
    Застосунок працює локально,
    але падає після розгортання.

Міграції допомагають зробити зміни повторюваними та контрольованими.

### 9.4. Порядок застосування міграцій

Для простого застосунку типовий процес може бути таким:

    1. Створити резервну копію, якщо це необхідно.
    2. Перевірити міграцію на тестовому середовищі.
    3. Перевірити сумісність із поточним кодом.
    4. Застосувати міграцію.
    5. Розгорнути сумісну версію застосунку.
    6. Перевірити основні сценарії.

Точний порядок залежить від типу змін. Для несумісних змін потрібно планувати окрему процедуру.

### 9.5. Backward-compatible Migrations

Backward-compatible migration — зміна, яка дозволяє старій і новій версіям застосунку певний час працювати з тією самою схемою бази.

Наприклад, якщо потрібно перейменувати поле `name` на `title`, безпечніший підхід може передбачати кілька етапів:

    1. Додати нове поле title.
    2. Навчити застосунок працювати з обома полями.
    3. Перенести наявні значення.
    4. Переконатися, що нова версія працює.
    5. Прибрати старе поле в окремому випуску.

Це лише загальна схема. Конкретні кроки залежать від моделі даних і сумісності застосунку.

## 10. Domain, DNS і HTTPS

Для публічного вебзастосунку зазвичай потрібні домен і захищене з'єднання.

### 10.1. Domain

Домен — зрозуміла адреса, за якою користувачі знаходять застосунок.

Наприклад:

    example.com
    app.example.com
    api.example.com

Назви наведені як приклади.

### 10.2. DNS

DNS допомагає спрямувати домен на відповідний сервіс або інфраструктуру.

Під час налаштування потрібно:

- перевірити вимоги хостинг-платформи;
- створити потрібні DNS-записи;
- уникати конфліктних записів;
- перевірити поширення змін;
- переконатися, що домен веде до правильного середовища.

### 10.3. HTTPS

HTTPS захищає передавання даних між клієнтом і сервером за допомогою TLS.

Для production важливо:

- використовувати коректний сертифікат;
- перевірити автоматичне поновлення сертифіката;
- не передавати облікові дані через незахищене з'єднання;
- правильно налаштувати cookie та session security;
- уникати змішаного вмісту HTTP/HTTPS.

Багато керованих платформ автоматично налаштовують сертифікати для підключених доменів, але це потрібно перевірити для конкретного провайдера.

## 11. CORS і мережеві підключення

Якщо frontend і backend працюють на різних доменах, потрібно правильно налаштувати доступ браузера до API.

Наприклад:

    Frontend:
    https://app.example.com

    Backend:
    https://api.example.com

CORS — механізм браузера, який визначає, чи дозволено сторінці з одного origin робити певні запити до іншого origin.

### Що потрібно перевірити

- дозволені origin;
- потрібні HTTP-методи;
- необхідні заголовки;
- правила передачі credentials;
- cookie та їхні атрибути;
- поведінку preflight-запитів.

У production не варто без потреби дозволяти будь-який origin.

CORS також не замінює автентифікацію та авторизацію. Він не є повноцінним механізмом захисту API від усіх небажаних запитів.

### Backend і база даних

Для з'єднання backend із PostgreSQL потрібно перевірити:

- правильну адресу сервера;
- порт;
- ім'я бази;
- користувача та пароль;
- SSL-вимоги провайдера;
- мережеві правила;
- дозволені IP-адреси, якщо вони використовуються.

Секрети підключення не повинні передаватися frontend-клієнту.

## 12. CI/CD — автоматизація доставки

CI/CD — набір практик, що допомагають автоматизувати перевірку, підготовку та доставку програмного забезпечення.

### CI — Continuous Integration

Continuous Integration — регулярне інтегрування змін із автоматичними перевірками.

Наприклад:

    Git Push
        ↓
    Install Dependencies
        ↓
    Lint and Type Check
        ↓
    Tests
        ↓
    Build

### Continuous Delivery

Continuous Delivery — підхід, за якого зміни автоматично готуються до випуску, але production-розгортання може вимагати окремого підтвердження.

### Continuous Deployment

Continuous Deployment — підхід, за якого зміни, що проходять усі визначені перевірки, автоматично розгортаються в production.

Не слід плутати Continuous Delivery і Continuous Deployment: останній передбачає автоматичне розгортання змін у production.

### Приклад pipeline

    Developer
        ↓
    Git Commit
        ↓
    Pull Request
        ↓
    CI Checks
        ↓
    Merge
        ↓
    Build Artifact
        ↓
    Deployment
        ↓
    Smoke Tests
        ↓
    Monitoring

Конкретна схема залежить від команди та платформи.

### Чому CI/CD корисний

- зменшує кількість ручних операцій;
- робить процес повторюваним;
- допомагає виявляти помилки до випуску;
- зменшує ризик неправильного розгортання;
- полегшує роботу з кількома середовищами.

Для першого проєкту достатньо автоматизувати перевірки та підключити розгортання після успішної збірки.

## 13. Deployment Strategies — стратегії розгортання

Існує кілька підходів до випуску нових версій.

### 13.1. Recreate Deployment

Стару версію зупиняють, після чого запускають нову.

    Stop Version 1
        ↓
    Deploy Version 2
        ↓
    Start Version 2

Переваги:

- проста реалізація;
- мало інфраструктурних вимог.

Недоліки:

- можливий короткий простій;
- невдалий запуск може залишити застосунок недоступним.

Для невеликих проєктів такий підхід може бути цілком прийнятним.

### 13.2. Rolling Deployment

Нова версія поступово замінює стару на кількох екземплярах застосунку.

    Instance 1: Version 1 → Version 2
    Instance 2: Version 1
    Instance 3: Version 1

Потім оновлюються інші екземпляри.

Переваги:

- можна зменшити простій;
- є можливість контролювати процес поступового оновлення.

Недоліки:

- потрібно підтримувати сумісність версій;
- складніше керувати станом системи.

### 13.3. Blue-Green Deployment

Два середовища підготовлені окремо:

    Blue:
    Поточна production-версія.

    Green:
    Нова версія.

Після перевірки трафік перемикається на нове середовище.

Переваги:

- швидке перемикання;
- можливість повернути трафік на попередню версію.

Недоліки:

- вища вартість інфраструктури;
- складніше керування базою даних;
- не всі зміни можна безпечно відкотити простим перемиканням.

### 13.4. Canary Deployment

Нова версія спочатку отримує лише невелику частину трафіку.

    5% traffic → Version 2
    95% traffic → Version 1

Якщо перевірки проходять успішно, частка трафіку для нової версії поступово збільшується.

Цей підхід корисний для складних систем із достатньою інфраструктурою та моніторингом.

### Яку стратегію обрати?

Для навчального застосунку зазвичай достатньо простого deployment із можливістю повернути попередню версію.

Blue-Green, Canary та Rolling Deployment варто вивчати глибше, коли з'являються вимоги до високої доступності, кілька екземплярів застосунку або значний трафік.

---

## 14. Zero-downtime Deployment

Zero-downtime deployment — розгортання, під час якого користувачі не повинні помічати перерви в роботі сервісу.

Це складніше, ніж просто запустити нову версію.

Потрібно враховувати:

- кількість екземплярів застосунку;
- балансування трафіку;
- readiness та health checks;
- сумісність старого і нового коду;
- сумісність схеми бази даних;
- довготривалі запити;
- активні сесії;
- механізм перемикання версій.

Наприклад, якщо новий backend очікує поле `title`, якого ще немає в базі, deployment може завершитися помилкою.

Тому zero-downtime deployment часто потребує поетапних змін коду та бази даних.

Для невеликого MVP не обов'язково забезпечувати повну відсутність простою. Важливо розуміти компроміс між простотою та доступністю.

---

## 15. Health Checks — перевірка стану сервісу

Health check — механізм перевірки, чи може застосунок нормально працювати.

Можуть існувати різні типи перевірок.

### Liveness Check

Перевіряє, чи процес застосунку працює та не перебуває в безнадійному стані.

### Readiness Check

Перевіряє, чи готовий застосунок приймати запити.

### Dependency Check

Перевіряє доступність критичних залежностей, наприклад бази даних.

Для backend можна створити endpoint:

    GET /health

У найпростішому випадку він повертає успішну відповідь, якщо процес працює.

Але проста відповідь не гарантує, що база даних доступна або що застосунок може виконувати всі операції.

Для більш інформативної перевірки можна передбачити окремий readiness endpoint, який перевіряє необхідні залежності.

Водночас не слід без потреби розкривати через публічний endpoint деталі внутрішньої інфраструктури.

---

## 16. Rollback Planning — план відновлення після невдалого випуску

Планування розгортання має включати сценарій невдалого оновлення.

### Що може піти не так

- застосунок не запускається;
- з'являються помилки API;
- frontend не працює з новим backend;
- міграція пошкодила дані;
- нова версія має критичну помилку;
- сервіс не може підключитися до бази;
- збільшується кількість помилок після випуску.

### Що потрібно підготувати

- знати попередню робочу версію;
- зберігати ідентифікатори Git commit або release;
- мати спосіб повторного розгортання;
- перевірити, чи сумісна попередня версія з новою схемою бази;
- визначити, коли потрібно виконувати rollback;
- знати, як відновлювати дані з резервної копії;
- мати доступ до логів для визначення причини проблеми.

### Приклад простого плану

    1. Виявити критичну помилку.
    2. Зупинити подальше розгортання.
    3. Визначити, чи можна повернути попередню версію коду.
    4. Перевірити сумісність бази даних.
    5. Відновити попередню версію, якщо це безпечно.
    6. Перевірити health checks та основні сценарії.
    7. Проаналізувати причину помилки.
    8. Виправити проблему перед повторним випуском.

Важливо: не слід автоматично відновлювати стару базу даних лише тому, що відкотили код. Відновлення бази може втратити нові дані, записані після випуску.

Rollback коду та відновлення бази даних — різні операції.

---

## 17. Backup and Recovery — резервне копіювання та відновлення

Backup — резервна копія даних.

Recovery — процес відновлення даних або сервісу після втрати чи пошкодження.

Для застосунку з обліковими записами та приватними розкладами це особливо важливо.

### Що потрібно визначити

- які дані резервуються;
- як часто створюються копії;
- де вони зберігаються;
- хто має до них доступ;
- як довго вони зберігаються;
- як відновити базу;
- як часто перевіряється процедура відновлення.

### RPO — Recovery Point Objective

RPO — максимально допустима втрата даних, виражена як проміжок часу.

Наприклад:

    RPO = 24 години

Це означає, що за визначеного сценарію відновлення організація готова допустити втрату приблизно до 24 годин змін.

Це не означає, що відновлення завжди гарантовано відбудеться саме так: результат залежить від механізму резервного копіювання.

### RTO — Recovery Time Objective

RTO — цільовий максимальний час відновлення сервісу після інциденту.

Наприклад:

    RTO = 4 години

Це означає, що бажано відновити роботу в межах чотирьох годин.

RPO і RTO допомагають визначити, які механізми резервування та відновлення потрібні проєкту.

### Для невеликого застосунку

Мінімальний план може передбачати:

    - регулярні резервні копії PostgreSQL;
    - захищене місце зберігання копій;
    - обмеження доступу;
    - документацію відновлення;
    - періодичну перевірку відновлення на окремому середовищі.

Резервна копія має цінність лише тоді, коли її можна відновити.

---

## 18. Logging and Monitoring — логування та моніторинг

Після розгортання потрібно розуміти, що відбувається із застосунком.

### Logging

Logging — запис подій, помилок і важливої технічної інформації.

Наприклад:

    - запуск сервера;
    - помилка підключення до бази;
    - невдалий запит;
    - помилка зовнішнього сервісу;
    - результат критичної операції.

Логи допомагають розслідувати проблеми.

Не слід записувати до логів паролі, токени, секрети сесій або непотрібні приватні дані користувачів.

### Monitoring

Monitoring — спостереження за станом і поведінкою системи.

Можна контролювати:

- доступність сервісу;
- частоту помилок;
- час відповіді;
- використання ресурсів;
- кількість запитів;
- доступність бази даних.

### Alerting

Alerting — сповіщення про ситуації, які потребують уваги.

Наприклад:

    - сервіс недоступний;
    - кількість помилок різко зросла;
    - база даних недоступна;
    - використання ресурсів перевищило встановлену межу.

Для невеликого проєкту не потрібно одразу впроваджувати складну observability-платформу. Почни з доступних логів хостингу, базових health checks і перевірки помилок після випуску.

---

## 19. Security Planning — безпека під час розгортання

Production-середовище має бути захищеним не лише на рівні коду, а й на рівні інфраструктури.

### Основні перевірки

    [ ] Production-секрети не зберігаються у Git.
    [ ] Паролі не потрапляють до frontend.
    [ ] База даних не відкрита для необмеженого доступу.
    [ ] HTTPS налаштований.
    [ ] Backend перевіряє авторизацію.
    [ ] Доступ до ресурсів перевіряється на сервері.
    [ ] Залежності регулярно оновлюються.
    [ ] Production-конфігурація перевірена.
    [ ] Логи не містять зайвих секретів.
    [ ] Адміністративний доступ обмежений.
    [ ] Резервні копії захищені.

### Принцип найменших привілеїв

Least Privilege — кожен компонент повинен мати лише ті права, які потрібні для його роботи.

Наприклад, застосунку зазвичай не потрібен суперкористувач PostgreSQL для звичайних операцій.

Краще використовувати окремого користувача бази даних із потрібними дозволами.

### Development і Production

Не слід автоматично переносити локальну конфігурацію до production.

Production має використовувати окремі:

- секрети;
- базу даних;
- домени;
- облікові записи;
- дозволи;
- інтеграції.

Це зменшує ризик випадкового доступу до реальних даних із локального середовища.

## 20. Deployment Planning для Worship Schedule

Розглянемо вебзастосунок, у якому користувачі створюють, переглядають і редагують власні приватні розклади.

Припустимо, технологічний стек:

    Frontend:
    Next.js

    Backend:
    NestJS або серверна логіка Next.js

    Database:
    PostgreSQL

    Source Control:
    Git + GitHub

Конкретні платформи розгортання можна обрати пізніше.

### 20.1. Цільова архітектура

    User
      ↓
    HTTPS
      ↓
    Next.js Application
      ↓
    Backend API
      ↓
    PostgreSQL

Якщо NestJS використовується окремо, він буде самостійним backend-сервісом. Якщо серверної логіки Next.js достатньо, окремий backend може не знадобитися.

### 20.2. Development

    Local Computer
        ├── Next.js
        ├── NestJS, якщо потрібен
        └── PostgreSQL або тестова база

Тут розробляються функції, запускаються тести та перевіряється інтеграція.

### 20.3. Production

    Browser
        ↓
    HTTPS Domain
        ↓
    Frontend / Web Application
        ↓
    Backend API
        ↓
    Managed PostgreSQL

Production-компоненти повинні мати правильну конфігурацію, а доступ до бази має бути обмежений.

### 20.4. Що потрібно спланувати

    Source Code:
    - репозиторій GitHub;
    - зрозумілі release-коміти;
    - lock-файли залежностей.

    Build:
    - команда production-збірки;
    - перевірка TypeScript;
    - автоматизовані тести.

    Hosting:
    - платформа для frontend;
    - платформа для backend;
    - підтримка потрібної версії Node.js.

    Database:
    - production PostgreSQL;
    - окремі облікові дані;
    - міграції;
    - резервне копіювання.

    Configuration:
    - DATABASE_URL;
    - секрети авторизації;
    - URL API;
    - production-режим.

    Security:
    - HTTPS;
    - обмежений доступ до бази;
    - серверна перевірка прав власника.

    Monitoring:
    - логи;
    - health checks;
    - перевірка помилок після розгортання.

### 20.5. Критична перевірка приватності

Для кожного розкладу потрібно перевіряти, що він належить правильному користувачу.

    User A:
    Створює Schedule A.

    User B:
    Намагається отримати Schedule A.

    Expected:
    Сервер не надає доступ до чужого розкладу.

Це потрібно перевіряти не лише локально, а й перед запуском production-версії.

## 21. Приклад Deployment Checklist

Перед першим production-випуском можна використати такий список.

### Source Code

    [ ] Код збережений у Git.
    [ ] Залежності зафіксовані lock-файлом.
    [ ] Production-збірка проходить локально.
    [ ] Тести проходять.
    [ ] Немає випадково доданих секретів.

### Configuration

    [ ] Налаштовані production-змінні середовища.
    [ ] DATABASE_URL вказує на правильну базу.
    [ ] Секрети зберігаються безпечно.
    [ ] Frontend використовує правильний API URL.
    [ ] Немає залежності від локальних шляхів.

### Database

    [ ] Production-база створена.
    [ ] Міграції підготовлені.
    [ ] Міграції перевірені.
    [ ] Права доступу налаштовані.
    [ ] Резервне копіювання передбачене.
    [ ] Є план відновлення.

### Hosting and Network

    [ ] Застосунок успішно розгортається.
    [ ] Домен налаштований.
    [ ] HTTPS працює.
    [ ] API доступний.
    [ ] CORS налаштований, якщо потрібний.
    [ ] Backend має доступ до бази.

### Security

    [ ] Авторизація працює.
    [ ] Права власника перевіряються на сервері.
    [ ] Production-секрети не передаються клієнту.
    [ ] Приватні дані не доступні іншим користувачам.
    [ ] Немає зайвого публічного доступу до бази.

### Verification

    [ ] Головна сторінка відкривається.
    [ ] Основні API endpoints працюють.
    [ ] Користувач може увійти.
    [ ] Користувач може створити розклад.
    [ ] Користувач може відредагувати розклад.
    [ ] Зміни зберігаються.
    [ ] Користувач не може редагувати чужий розклад.
    [ ] Логи доступні для перевірки.
    [ ] Є спосіб повернути попередню версію коду.

## 22. Deployment Runbook — інструкція розгортання

Deployment runbook — документ із конкретними кроками, за якими можна розгорнути або перевірити застосунок.

Для невеликого проєкту він може бути частиною README або окремим документом.

Приклад:

    # Deployment Runbook

    ## 1. Prepare
    - Перевірити останній Git commit.
    - Переконатися, що зміни готові до випуску.
    - Запустити тести.

    ## 2. Build
    - Встановити залежності.
    - Виконати production build.
    - Перевірити результат.

    ## 3. Configure
    - Перевірити змінні середовища.
    - Переконатися, що підключено правильну базу.
    - Перевірити конфігурацію домену.

    ## 4. Database
    - Перевірити нові міграції.
    - Переконатися в їхній сумісності.
    - Виконати міграції у визначеному порядку.

    ## 5. Deploy
    - Запустити deployment.
    - Дочекатися завершення процесу.
    - Перевірити статус сервісу.

    ## 6. Verify
    - Відкрити застосунок.
    - Перевірити health endpoint.
    - Виконати основний користувацький сценарій.
    - Переглянути логи.

    ## 7. If Deployment Fails
    - Зупинити подальші зміни.
    - Визначити причину помилки.
    - За потреби повернути попередню версію.
    - Перевірити базу та основні сценарії.

Цей документ повинен відповідати реальним командам і платформі проєкту. Не слід копіювати приклад без адаптації.

## 24. Infrastructure as Code — інфраструктура як код

Infrastructure as Code (IaC) — підхід, за якого інфраструктура описується у файлах конфігурації, а не створюється лише вручну через графічні інтерфейси.

За допомогою IaC можна описувати:

- сервери;
- мережі;
- правила доступу;
- ресурси хмарних платформ;
- бази даних;
- балансувальники навантаження;
- інші компоненти інфраструктури.

Інструменти можуть включати Terraform, OpenTofu, Ansible та інші рішення залежно від задачі.

### Переваги

- повторюване створення середовищ;
- документована інфраструктура;
- контроль змін через Git;
- менше ручних помилок;
- простіше відновлення середовища.

### Чи потрібен IaC для першого проєкту?

Не обов'язково.

Для невеликого застосунку на керованій платформі достатньо почати з налаштування через інтерфейс провайдера та задокументованих кроків.

IaC стає кориснішим, коли інфраструктура ускладнюється або її потрібно регулярно відтворювати.

## 25. Docker і Deployment Planning

Docker дозволяє пакувати застосунок та його залежності в контейнер.

Контейнер допомагає зробити середовище запуску більш передбачуваним.

### Основні поняття

    Dockerfile:
    Інструкції для створення image.

    Image:
    Пакет із застосунком і необхідними компонентами.

    Container:
    Запущений екземпляр image.

    Docker Compose:
    Інструмент для опису та запуску кількох сервісів.

### Приклад архітектури

    Docker Compose
        ├── frontend
        ├── backend
        └── database

Це концептуальна схема. Не обов'язково запускати всі компоненти в контейнерах, особливо якщо production-базу надає керований сервіс.

### Переваги Docker

- однаковіший процес запуску;
- простіше відтворити середовище;
- зручно запускати кілька сервісів;
- легше підготувати застосунок до контейнерного хостингу.

### Чи потрібно починати з Docker?

Не обов'язково.

Спочатку корисно зрозуміти:

- як запускається Node.js;
- як працюють змінні середовища;
- як застосунок підключається до PostgreSQL;
- як виконується production build;
- як працює deployment.

Після цього Docker буде легше зрозуміти як спосіб пакування та запуску вже знайомої системи.

## 26. Cost Planning — планування вартості розгортання

Deployment Planning включає не лише технічні рішення, а й оцінку витрат.

Потенційні витрати:

- frontend hosting;
- backend hosting;
- PostgreSQL;
- домен;
- резервне копіювання;
- зберігання файлів;
- зовнішні API;
- моніторинг;
- трафік;
- додаткові обчислювальні ресурси.

### Що потрібно оцінити

    - скільки користувачів очікується;
    - який обсяг даних зберігатиметься;
    - скільки запитів буде виконуватися;
    - чи потрібна постійно запущена серверна логіка;
    - які обмеження має тариф;
    - чи є платні резервні копії;
    - чи передбачені додаткові витрати за трафік.

### Для MVP

Для першої версії краще уникати непотрібної складності:

    - не створювати кілька backend-сервісів без потреби;
    - не запускати окремий сервер для кожної маленької функції;
    - не використовувати дорогі ресурси без вимірюваної причини;
    - перевіряти обмеження безкоштовних і недорогих тарифів;
    - заздалегідь розуміти, що відбудеться після перевищення лімітів.

Ціни, квоти та умови хостингу змінюються, тому перед вибором конкретної платформи потрібно перевіряти її актуальні умови.

## 27. Як планувати deployment перед реалізацією

Deployment не потрібно повністю налаштовувати до написання першого рядка коду, але основні рішення бажано прийняти заздалегідь.

### Крок 1. Визначити архітектуру

    - frontend;
    - backend;
    - database;
    - зовнішні сервіси;
    - спосіб авторизації.

### Крок 2. Визначити production-середовище

    - де працюватиме frontend;
    - де працюватиме backend;
    - де розміщуватиметься база;
    - як компоненти спілкуватимуться.

### Крок 3. Визначити конфігурацію

    - обов'язкові змінні середовища;
    - секрети;
    - адреси API;
    - налаштування бази;
    - режими роботи.

### Крок 4. Визначити процес збирання

    - встановлення залежностей;
    - перевірка типів;
    - тести;
    - production build.

### Крок 5. Визначити процес роботи з базою

    - міграції;
    - резервні копії;
    - права доступу;
    - відновлення.

### Крок 6. Визначити спосіб випуску

    - ручний deployment;
    - автоматичний deployment;
    - порядок перевірок;
    - спосіб повернення попередньої версії.

### Крок 7. Визначити перевірки після розгортання

    - доступність застосунку;
    - робота API;
    - підключення до бази;
    - авторизація;
    - основні користувацькі сценарії.

### Крок 8. Документувати рішення

Рішення мають бути зрозумілими та доступними для повторного використання.

## 28. Часті помилки під час планування розгортання

### Помилка 1. Вважати, що локальний запуск гарантує production-готовність

Локальне середовище відрізняється від production за конфігурацією, доступами, мережею та ресурсами.

Потрібно перевіряти production build і реальне середовище запуску.

### Помилка 2. Зберігати секрети у вихідному коді

Секрети можуть потрапити до Git або frontend bundle.

Використовуй змінні середовища та механізми зберігання секретів, які надає платформа.

### Помилка 3. Не розділяти development і production

Локальні та production-дані повинні бути відокремлені.

Це зменшує ризик пошкодження реальних даних.

### Помилка 4. Забути про міграції

Новий код може очікувати поля, якого ще немає в production-базі.

Міграції потрібно планувати разом зі змінами моделі даних.

### Помилка 5. Не перевіряти результат deployment

Успішне повідомлення платформи не гарантує, що всі функції працюють.

Після випуску потрібно перевірити health checks, логи та основні сценарії.

### Помилка 6. Не мати плану rollback

Якщо нова версія зламалася, потрібно розуміти, як відновити роботу.

Відкат коду не завжди означає відновлення бази даних.

### Помилка 7. Не налаштувати резервне копіювання

Помилка застосунку, пошкодження даних або випадкове видалення можуть призвести до втрати інформації.

Потрібно передбачити резервування та перевірку відновлення.

### Помилка 8. Відкрити базу даних для всіх

База має бути доступна лише тим компонентам і користувачам, яким це необхідно.

### Помилка 9. Використовувати надто складну інфраструктуру

Мікросервіси, Kubernetes, складні deployment pipelines та кілька середовищ не потрібні автоматично кожному проєкту.

Обирай рішення відповідно до реальних вимог.

### Помилка 10. Не документувати процес

Якщо deployment залежить лише від пам'яті розробника, повторний запуск або передавання проєкту іншій людині стає складнішим.

Зберігай інструкції та важливі архітектурні рішення в документації.

## 29. Мінімальна стратегія розгортання для Junior Full Stack Developer

Для першого full-stack застосунку можна використати просту послідовність.

### Етап 1. Підготовка коду

    - Git-репозиторій;
    - lock-файл залежностей;
    - коректні команди запуску;
    - перевірка TypeScript;
    - тести;
    - production build.

### Етап 2. Підготовка середовища

    - frontend hosting;
    - backend hosting, якщо потрібен окремий сервер;
    - production PostgreSQL;
    - змінні середовища;
    - домен і HTTPS.

### Етап 3. Перший deployment

    - розгорнути застосунок;
    - перевірити запуск;
    - перевірити підключення до бази;
    - застосувати міграції;
    - перевірити API.

### Етап 4. Перевірка функцій

    - вхід;
    - створення розкладу;
    - перегляд;
    - редагування;
    - видалення;
    - ізоляція даних користувачів.

### Етап 5. Супровід

    - перевіряти логи;
    - відстежувати помилки;
    - зберігати резервні копії;
    - контролювати витрати;
    - документувати оновлення;
    - мати спосіб повернути попередню версію.

Цього достатньо, щоб навчитися основного deployment workflow без передчасного ускладнення інфраструктури.

## 31. Мінішпаргалка

    Deployment Planning
        Планування процесу запуску, випуску та супроводу застосунку.

    Deployment
        Розгортання застосунку в цільовому середовищі.

    Build
        Підготовка застосунку до запуску або публікації.

    Release
        Версія програмного забезпечення, підготовлена до випуску.

    Artifact
        Результат збирання, який використовується для розгортання.

    Development
        Середовище розробки.

    Test
        Середовище перевірок.

    Staging
        Середовище перевірки перед production.

    Production
        Середовище для реальних користувачів.

    Environment Variables
        Конфігурація, передана через середовище запуску.

    Database Migration
        Контрольована зміна схеми бази даних.

    CI
        Автоматичні перевірки під час інтеграції змін.

    CD
        Автоматизація підготовки та/або розгортання випусків.

    Health Check
        Перевірка стану або готовності сервісу.

    Rollback
        Повернення до попередньої робочої версії.

    Backup
        Резервна копія даних.

    Recovery
        Відновлення після збою або втрати даних.

    RPO
        Допустима втрата даних у часовому вимірі.

    RTO
        Цільовий час відновлення сервісу.

    Monitoring
        Спостереження за станом і поведінкою системи.

    Основний принцип
        Плануй не лише запуск нової версії,
        а й перевірку, супровід та відновлення після помилки.

## 32. Що потрібно запам'ятати

- Deployment Planning визначає, як застосунок потрапить із розробки в production.
- Середовища development, test, staging і production мають різні призначення.
- Архітектура розгортання визначає розташування компонентів та їхню взаємодію.
- Production build потрібно перевіряти до розгортання.
- Конфігурацію потрібно відокремлювати від вихідного коду.
- Production-секрети не повинні потрапляти до frontend або Git.
- Міграції бази даних потрібно планувати разом зі змінами коду.
- Домен, HTTPS, мережевий доступ і CORS потрібно налаштовувати відповідно до архітектури.
- CI/CD допомагає автоматизувати перевірки та випуск.
- Стратегія розгортання залежить від вимог до доступності й складності інфраструктури.
- Rollback коду не завжди відновлює попередній стан бази.
- Резервні копії потрібно не лише створювати, а й перевіряти на можливість відновлення.
- Після розгортання необхідно перевіряти основні сценарії та логи.
- Не варто використовувати складні інфраструктурні рішення без конкретної потреби.
- Документація deployment допомагає повторювати процес і передавати проєкт іншим розробникам.

**Головна думка:** успішне розгортання — це не просто завантажити код на сервер. Це підготувати середовище, безпечно налаштувати компоненти, перевірити роботу застосунку та мати зрозумілий план дій у разі збою.
