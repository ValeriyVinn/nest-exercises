# API Contracts

## 1. Що таке API Contracts

**API Contract (контракт API)** — це формальний або чітко визначений опис правил взаємодії між двома програмними компонентами через API.

Контракт визначає, як один компонент може звертатися до іншого, які дані потрібно передавати, яку відповідь очікувати та як обробляти помилки.

Для вебзастосунку найчастіше йдеться про взаємодію між frontend і backend через HTTP API.

Наприклад, у застосунку Worship Schedule frontend повинен мати можливість отримати список розкладів користувача.

    Request:
        GET /api/schedules

    Response:
        [
            {
                "id": 1,
                "title": "Недільний розклад"
            },
            {
                "id": 2,
                "title": "Святковий розклад"
            }
        ]

Цей приклад показує не лише URL, а й очікувану структуру відповіді.

Якщо frontend очікує поле `title`, а backend повертає `name`, взаємодія може зламатися. Контракт допомагає уникнути таких ситуацій.

### Основна ідея

**API Contract — це домовленість між компонентами про те, як вони взаємодіють.**

Контракт визначає:

- Які операції доступні.
- За якими адресами вони виконуються.
- Які HTTP-методи використовуються.
- Які параметри потрібні.
- Яку структуру мають запити й відповіді.
- Які правила валідації застосовуються.
- Які помилки можуть виникнути.
- Які вимоги до автентифікації та авторизації.

## 2. Навіщо потрібні API Contracts

У застосунку frontend і backend можуть розроблятися окремо. Навіть якщо над ними працює одна людина, компоненти повинні узгоджено обмінюватися даними.

Без контракту розробник може не знати:

- Чи потрібно передавати `scheduleId` у URL або в тілі запиту.
- Чи повертає сервер об'єкт або масив.
- Чи може поле бути `null`.
- Який формат має дата.
- Що повертає сервер, якщо ресурс не знайдено.
- Який статус отримує клієнт, якщо користувач не має доступу.

### Основні переваги

✔ Frontend і backend можуть розроблятися незалежніше.

✔ Зменшується кількість помилок через невідповідність форматів.

✔ Легше тестувати API.

✔ Простіше документувати функціональність.

✔ Легше інтегрувати сторонні сервіси.

✔ Зміни API можна перевіряти на сумісність.

✔ Нові розробники швидше розуміють правила взаємодії.

✔ Контракт можна використовувати для автоматичної генерації документації та типів.

### Приклад проблеми без контракту

Frontend надсилає:

    {
        "title": "Недільний розклад"
    }

Backend очікує:

    {
        "name": "Недільний розклад"
    }

Запит не працює, хоча обидві частини окремо можуть бути реалізовані правильно.

Контракт заздалегідь визначає єдину назву поля.

## 3. Основні поняття API Contract

### 3.1. API — Application Programming Interface

**API** — інтерфейс, через який одна програмна частина може використовувати функціональність іншої.

Наприклад, frontend викликає backend API, щоб отримати розклади.

    Frontend
        ↓ HTTP Request
    Backend API
        ↓
    Database
        ↑
    Backend API
        ↓ HTTP Response
    Frontend

API може бути HTTP API, бібліотечним інтерфейсом, API операційної системи або іншим способом взаємодії.

У цій шпаргалці основна увага приділяється HTTP API вебзастосунків.

### 3.2. Endpoint

**Endpoint** — конкретна точка доступу до API, яка зазвичай визначається HTTP-методом і URL-шляхом.

Наприклад:

    GET    /api/schedules
    POST   /api/schedules
    GET    /api/schedules/42
    PATCH  /api/schedules/42
    DELETE /api/schedules/42

Ці endpoints можуть відповідати за:

- Отримання списку розкладів.
- Створення розкладу.
- Отримання одного розкладу.
- Часткове оновлення розкладу.
- Видалення розкладу.

Однаковий URL із різними HTTP-методами може виконувати різні операції.

### 3.3. Request

**Request** — запит клієнта до сервера.

Він може містити:

- HTTP-метод.
- URL.
- Path parameters.
- Query parameters.
- Headers.
- Request body.

Наприклад:

    PATCH /api/schedules/42
    Content-Type: application/json

    {
        "title": "Оновлений розклад"
    }

### 3.4. Response

**Response** — відповідь сервера на запит.

Вона містить:

- HTTP status code.
- Headers.
- За потреби — response body.

Наприклад:

    HTTP/1.1 200 OK
    Content-Type: application/json

    {
        "id": 42,
        "title": "Оновлений розклад"
    }

Формат наведено для пояснення. Реальна відповідь залежить від реалізації API.

### 3.5. Schema

**Schema** — опис структури даних і правил, яким ці дані повинні відповідати.

Наприклад:

    Schedule:
        id: integer
        title: string
        createdAt: date-time string

Схема може також визначати обов'язкові поля, допустимі значення, мінімальну довжину та інші обмеження.

### 3.6. Contract

Контракт об'єднує правила взаємодії:

    Endpoint:
        PATCH /api/schedules/{id}

    Authentication:
        required

    Request:
        title: optional string, max 100 characters

    Success Response:
        200 OK
        Schedule object

    Errors:
        400 Bad Request
        401 Unauthorized
        403 Forbidden
        404 Not Found

Це короткий приклад контракту. У реальному проєкті потрібно також визначити точну структуру помилок та інші важливі деталі.

## 4. HTTP Methods

HTTP-метод визначає тип операції, яку клієнт просить виконати.

### 4.1. GET — отримання даних

Використовується для читання ресурсу.

    GET /api/schedules

Отримати список розкладів.

    GET /api/schedules/42

Отримати розклад з ідентифікатором `42`.

Зазвичай `GET` не повинен змінювати стан ресурсу на сервері.

### 4.2. POST — створення або виконання операції

Використовується для створення ресурсу або виконання операції, визначеної API.

    POST /api/schedules

    {
        "title": "Недільний розклад"
    }

Сервер створює новий розклад.

Типова успішна відповідь для створення ресурсу:

    201 Created

### 4.3. PUT — повне оновлення або заміна

`PUT` зазвичай використовується для повного оновлення або заміни представлення ресурсу.

    PUT /api/schedules/42

    {
        "title": "Святковий розклад"
    }

Точна семантика залежить від контракту API. Якщо ресурс має багато обов'язкових полів, `PUT` може вимагати їх усі.

### 4.4. PATCH — часткове оновлення

`PATCH` використовується для часткової зміни ресурсу.

    PATCH /api/schedules/42

    {
        "title": "Новий заголовок"
    }

У цьому випадку змінюється лише назва, якщо саме так визначено контракт.

### 4.5. DELETE — видалення

    DELETE /api/schedules/42

Сервер видаляє ресурс, якщо запит коректний і користувач має відповідні права.

Можлива відповідь:

    204 No Content

Це означає, що операція успішна, але тіло відповіді відсутнє.

### 4.6. Коротка таблиця

| Метод | Типове призначення |
|---|---|
| `GET` | Отримання даних |
| `POST` | Створення ресурсу або виконання операції |
| `PUT` | Повне оновлення або заміна |
| `PATCH` | Часткове оновлення |
| `DELETE` | Видалення ресурсу |

Важливо: семантика методу має відповідати поведінці endpoint. Не варто використовувати `GET` для видалення чи зміни даних.

## 5. URL та структура endpoint

Контракт повинен чітко визначати адресу кожної операції.

Поширений стиль REST API використовує назви ресурсів у множині.

    /api/users
    /api/schedules
    /api/events

### 5.1. Collection endpoint

Collection endpoint працює з колекцією ресурсів.

    GET /api/schedules

Отримати доступні користувачеві розклади.

    POST /api/schedules

Створити розклад.

### 5.2. Resource endpoint

Resource endpoint працює з конкретним ресурсом.

    GET /api/schedules/42
    PATCH /api/schedules/42
    DELETE /api/schedules/42

Число `42` — ідентифікатор ресурсу в цьому прикладі.

### 5.3. Вкладені ресурси

Якщо подія належить певному розкладу, можна використовувати:

    GET  /api/schedules/42/events
    POST /api/schedules/42/events

Це підкреслює зв'язок подій із розкладом.

Однак вкладені маршрути не завжди потрібні. Якщо події мають власні ідентифікатори й незалежні операції, також може бути доречним:

    GET /api/events/15
    PATCH /api/events/15
    DELETE /api/events/15

Вибір залежить від моделі ресурсів та вимог API.

### 5.4. Уникай назв дій у URL без потреби

Менш типовий REST-стиль:

    /api/createSchedule
    /api/deleteSchedule/42

Зазвичай краще:

    POST   /api/schedules
    DELETE /api/schedules/42

Проте для спеціальних операцій, які не є звичайним CRUD, окремий маршрут дії може бути виправданим.

## 6. Path Parameters, Query Parameters і Request Body

Ці три способи передавання даних мають різне призначення.

### 6.1. Path Parameters

Path parameters визначають ресурс або його частину в URL.

    GET /api/schedules/42

Тут `42` — ідентифікатор розкладу.

У NestJS:

    @Get(":id")
    findOne(@Param("id") id: string) {
        return this.schedulesService.findOne(Number(id));
    }

Це навчальний приклад. У production-коді потрібно також перевіряти формат і допустимість `id`, наприклад через відповідний pipe.

### 6.2. Query Parameters

Query parameters зазвичай використовуються для фільтрації, сортування, пошуку та пагінації.

    GET /api/schedules?limit=10&page=2

Або:

    GET /api/events?date=2026-10-20

Можливі параметри:

    page
    limit
    sort
    order
    search
    date
    status

Контракт повинен визначати:

- Тип параметра.
- Чи є він обов'язковим.
- Значення за замовчуванням.
- Допустимий діапазон.
- Поведінку для некоректних значень.

### 6.3. Request Body

Request body передає дані, необхідні для створення або оновлення ресурсу.

    POST /api/schedules
    Content-Type: application/json

    {
        "title": "Недільний розклад"
    }

Контракт визначає структуру body та правила перевірки.

### 6.4. Як обрати

| Місце | Типове призначення | Приклад |
|---|---|---|
| Path | Ідентифікація ресурсу | `/schedules/42` |
| Query | Фільтрація та налаштування запиту | `?page=2` |
| Body | Дані для створення або зміни | `{"title":"..."}` |

Не передавай пароль, токен або інші чутливі дані в URL. URL може потрапляти в журнали, історію браузера та інші системи спостереження.

## 7. Headers

**HTTP Headers** — метадані запиту або відповіді.

Вони допомагають визначити формат даних, правила кешування, автентифікацію та інші параметри.

### 7.1. Content-Type

Визначає формат тіла запиту або відповіді.

    Content-Type: application/json

Для JSON API це поширений варіант.

### 7.2. Accept

Клієнт повідомляє, які формати відповіді він може прийняти.

    Accept: application/json

### 7.3. Authorization

Може містити дані для автентифікації, наприклад Bearer token.

    Authorization: Bearer <token>

Це лише приклад формату. Конкретний механізм залежить від способу автентифікації.

Не записуй справжні токени в документацію, репозиторій або публічні приклади.

### 7.4. Headers у контракті

Для кожного endpoint варто визначити, які headers є необхідними.

Наприклад:

    Endpoint:
        POST /api/schedules

    Required Headers:
        Content-Type: application/json
        Authorization: Bearer token

Якщо автентифікація використовує cookies і сесії, правила будуть іншими.

## 8. Request Schema — схема запиту

Контракт повинен визначати точну структуру вхідних даних.

Наприклад, створення розкладу:

    CreateScheduleRequest:
        title: string
        description: optional string

Правила:

- `title` обов'язковий.
- `title` не повинен бути порожнім.
- Максимальна довжина `title` — 100 символів.
- `description` необов'язковий.
- Максимальна довжина `description` — 2000 символів.

Це приклад обмежень, які потрібно узгодити з реальними вимогами.

### TypeScript-тип

    type CreateScheduleRequest = {
        title: string;
        description?: string;
    };

Такий тип допомагає під час розробки, але сам по собі не перевіряє дані, які приходять із мережі.

JavaScript-клієнт або зловмисник може надіслати будь-який JSON, тому backend повинен виконувати runtime-валідацію.

### Приклад валідації в NestJS

    import { IsNotEmpty, IsOptional, IsString, MaxLength } from "class-validator";

    export class CreateScheduleDto {
        @IsString()
        @IsNotEmpty()
        @MaxLength(100)
        title!: string;

        @IsOptional()
        @IsString()
        @MaxLength(2000)
        description?: string;
    }

Щоб така валідація працювала в NestJS, потрібно правильно налаштувати `ValidationPipe` та відповідні залежності.

Наприклад, глобально в `main.ts`:

    app.useGlobalPipes(
        new ValidationPipe({
            whitelist: true,
            forbidNonWhitelisted: true,
            transform: true,
        }),
    );

Це поширена конфігурація. Параметри потрібно обирати відповідно до вимог API.

## 9. Response Schema — схема відповіді

Контракт повинен визначати, що саме сервер повертає клієнту.

Наприклад:

    ScheduleResponse:
        id: integer
        title: string
        description: string | null
        createdAt: date-time string

Приклад JSON:

    {
        "id": 42,
        "title": "Недільний розклад",
        "description": null,
        "createdAt": "2026-10-20T09:30:00.000Z"
    }

### Чому важливо визначати response schema

Frontend повинен знати:

- Які поля гарантовано присутні.
- Які поля можуть бути відсутні.
- Які поля можуть мати значення `null`.
- Які типи даних використовуються.
- Як представляються дата й час.
- Чи повертає сервер один об'єкт або масив.

### Optional і Nullable — не одне й те саме

У TypeScript:

    type Example = {
        description?: string;
        subtitle: string | null;
    };

Тут:

- `description?` означає, що властивість може бути відсутня.
- `subtitle: string | null` означає, що властивість повинна існувати, але її значення може бути `null`.

Контракт повинен чітко визначати, який варіант використовується.

### Не повертай внутрішню модель автоматично

Якщо база даних містить:

    UserRecord:
        id
        email
        passwordHash
        name

Публічна відповідь може бути:

    UserResponse:
        id
        name

Не можна автоматично повертати приватні поля лише тому, що вони є в об'єкті бази даних.

## 10. HTTP Status Codes

HTTP status code показує загальний результат виконання запиту.

### Основні коди успіху

| Код | Значення | Типове використання |
|---|---|---|
| `200 OK` | Успішно | Отримання або оновлення ресурсу |
| `201 Created` | Створено | Створення ресурсу |
| `202 Accepted` | Прийнято | Асинхронна операція прийнята до виконання |
| `204 No Content` | Успішно без тіла | Видалення або операція без відповіді |

### Основні коди помилок клієнта

| Код | Значення | Типове використання |
|---|---|---|
| `400 Bad Request` | Некоректний запит | Некоректні параметри або body |
| `401 Unauthorized` | Не автентифіковано | Відсутні або недійсні облікові дані |
| `403 Forbidden` | Доступ заборонено | Недостатньо прав |
| `404 Not Found` | Не знайдено | Ресурс відсутній або недоступний за обраною політикою |
| `409 Conflict` | Конфлікт | Порушення унікальності або конфлікт стану |
| `422 Unprocessable Content` | Дані не можуть бути оброблені | Семантично некоректні дані, якщо API використовує цей код |
| `429 Too Many Requests` | Забагато запитів | Перевищено ліміт запитів |

### Основний код помилки сервера

| Код | Значення |
|---|---|
| `500 Internal Server Error` | Неочікувана помилка сервера |
| `502 Bad Gateway` | Некоректна відповідь від upstream-сервера |
| `503 Service Unavailable` | Сервіс тимчасово недоступний |
| `504 Gateway Timeout` | Upstream-сервіс не відповів вчасно |

Не потрібно використовувати всі ці коди в кожному API. Визначай лише ті, які мають сенс для конкретних операцій.

### Приклад контракту

    POST /api/schedules

    Success:
        201 Created

    Errors:
        400 Bad Request
        401 Unauthorized
        500 Internal Server Error

Клієнт може використовувати статус, щоб визначити, чи потрібно показати помилку, попросити користувача ввійти або перейти до іншого сценарію.

---

## 11. Error Response — формат помилок

Окрім статусу, корисно визначити єдиний формат тіла помилки.

Наприклад:

    {
        "statusCode": 400,
        "code": "VALIDATION_ERROR",
        "message": "Request validation failed",
        "details": [
            {
                "field": "title",
                "message": "Title must not be empty"
            }
        ]
    }

Це приклад власного формату, а не універсальний стандарт.

### Що варто передбачити

- HTTP status code.
- Стабільний код помилки.
- Зрозуміле повідомлення.
- Деталі валідації, якщо вони потрібні клієнту.
- Ідентифікатор запиту для пошуку помилки в логах, якщо це доречно.

### Чому стабільний код корисний

Frontend може орієнтуватися на:

    VALIDATION_ERROR
    UNAUTHENTICATED
    FORBIDDEN
    RESOURCE_NOT_FOUND
    RESOURCE_CONFLICT

Це надійніше, ніж аналізувати текст повідомлення, який може змінюватися або перекладатися.

### Безпека

Не повертай клієнту:

- SQL-запити з чутливими параметрами.
- Паролі або токени.
- Внутрішні stack traces у production.
- Секрети конфігурації.
- Надмірні технічні подробиці про інфраструктуру.

Повні технічні деталі варто записувати в захищені серверні логи.

## 12. Authentication та Authorization у контракті

Контракт API повинен описувати, чи потребує endpoint автентифікації та які права необхідні для операції.

### Authentication

**Authentication** — перевірка особи користувача.

Приклади:

- Cookie-based session.
- Bearer token.
- OAuth 2.0 / OpenID Connect через відповідного провайдера.

### Authorization

**Authorization** — перевірка того, чи має користувач право виконувати конкретну дію.

Наприклад:

    PATCH /api/schedules/42

Можливі вимоги:

    Authentication:
        required

    Authorization:
        user must own the schedule
        or have explicit edit permission

Це важливо, тому що сам факт успішного входу не надає права редагувати всі розклади.

### Перевірка на backend

    Request
        ↓
    Authenticate user
        ↓
    Validate request
        ↓
    Check resource access
        ↓
    Execute operation
        ↓
    Return response

Конкретна послідовність може відрізнятися, але перевірка прав повинна відбуватися до виконання захищеної операції.

### Що задокументувати

Для кожного endpoint визнач:

- Чи потрібна автентифікація.
- Які ролі або дозволи необхідні.
- Чи перевіряється власник ресурсу.
- Яка відповідь повертається за відсутності доступу.

Не покладайся лише на приховування кнопок у frontend.

## 13. Pagination, Filtering і Sorting

Якщо ресурсів багато, API не завжди повинен повертати всі записи одним запитом.

Контракт може визначати параметри пагінації.

### 13.1. Pagination

Наприклад:

    GET /api/schedules?page=2&limit=10

Можлива відповідь:

    {
        "items": [
            {
                "id": 11,
                "title": "Розклад 11"
            }
        ],
        "page": 2,
        "limit": 10,
        "totalItems": 35,
        "totalPages": 4
    }

Це приклад структури. У реальному API `items` міститиме всі записи поточної сторінки.

Контракт повинен визначати:

- Значення `page` за замовчуванням.
- Максимальне значення `limit`.
- Поведінку для некоректних параметрів.
- Структуру метаданих.

Для великих наборів даних може бути доречна cursor-based pagination замість нумерації сторінок.

### 13.2. Filtering

Наприклад:

    GET /api/events?date=2026-10-20

Або:

    GET /api/schedules?search=недільний

Контракт повинен визначати допустимі параметри фільтрації та правила їх обробки.

### 13.3. Sorting

Наприклад:

    GET /api/schedules?sort=createdAt&order=desc

Контракт повинен визначати дозволені поля сортування.

Не можна безпечно вставляти довільне значення `sort` у SQL-запит. Потрібно використовувати перевірений список допустимих полів.

## 14. Date, Time та формати даних

Контракт повинен визначати, як передаються дати й час.

Поширений формат для дати й часу — ISO 8601.

Наприклад:

    {
        "startsAt": "2026-10-20T09:30:00.000Z"
    }

Символ `Z` позначає UTC.

### Дата без часу

    {
        "eventDate": "2026-10-20"
    }

### Дата й час із часовою зоною

    {
        "startsAt": "2026-10-20T12:30:00+03:00"
    }

Це інший запис того самого моменту часу, що й `2026-10-20T09:30:00Z`.

### Що потрібно визначити

- Чи передається лише дата, чи дата з часом.
- Чи містить значення часову зону.
- Як сервер інтерпретує час.
- Як форматуються значення у відповіді.
- Як поводитися з некоректними датами.

Для розкладів богослужінь це особливо важливо, оскільки події мають відображатися в правильний місцевий час.

Не варто передавати дати в неоднозначних форматах на кшталт `10/11/2026`, оскільки різні системи можуть трактувати їх по-різному.

## 15. API Versioning — версіонування API

**API Versioning** — спосіб керувати змінами API, особливо коли зміни можуть порушити сумісність із наявними клієнтами.

Наприклад:

    /api/v1/schedules
    /api/v2/schedules

### Коли потрібне версіонування

Версіонування може бути потрібним, якщо:

- Змінюється структура відповіді.
- Видаляються поля.
- Змінюється семантика операцій.
- Змінюються правила авторизації.
- Старі клієнти повинні продовжувати працювати.

### Сумісна зміна

Додавання необов'язкового поля часто є сумісною зміною:

    {
        "id": 42,
        "title": "Недільний розклад",
        "description": null
    }

Але навіть додавання поля може порушити роботу клієнта, якщо той очікує точну схему без додаткових властивостей.

### Потенційно несумісна зміна

Було:

    {
        "title": "Недільний розклад"
    }

Стало:

    {
        "name": "Недільний розклад"
    }

Якщо клієнт очікує `title`, така зміна порушує контракт.

### Практичне правило

Не потрібно створювати версії API для кожної невеликої зміни. Спочатку визначай, чи справді зміна порушує сумісність і чи існують клієнти, які потрібно підтримувати.

## 16. OpenAPI — стандарт опису HTTP API

**OpenAPI Specification** — стандарт для опису HTTP API у машинозчитуваному форматі.

OpenAPI дає змогу документувати:

- Endpoints.
- HTTP-методи.
- Path і query parameters.
- Request bodies.
- Response schemas.
- HTTP status codes.
- Схеми автентифікації.

На основі специфікації можна створювати документацію, перевірки та клієнтський код за допомогою відповідних інструментів.

### Приклад OpenAPI

    openapi: 3.1.0

    info:
      title: Worship Schedule API
      version: 1.0.0

    paths:
      /api/schedules:
        get:
          summary: Get schedules
          responses:
            "200":
              description: List of schedules

Це скорочений фрагмент для демонстрації структури. Повна специфікація повинна містити точні схеми запитів і відповідей, параметри та інші потрібні деталі.

### Переваги OpenAPI

✔ Документація має узгоджену структуру.

✔ API можна описати незалежно від реалізації.

✔ Розробники можуть переглядати контракт до запуску backend.

✔ Інструменти можуть генерувати клієнти та перевіряти схеми.

✔ Зміни контракту простіше аналізувати.

### OpenAPI у NestJS

NestJS підтримує інтеграцію з OpenAPI через пакет `@nestjs/swagger`.

Він дає змогу створювати документацію на основі контролерів, DTO та додаткових декораторів.

Однак документація не завжди автоматично відображає всі бізнес-правила. Її потрібно перевіряти й доповнювати.

## 17. TypeScript Types і Runtime Validation

TypeScript допомагає описувати контракти на рівні коду, але типи TypeScript самі по собі не перевіряють дані під час виконання.

Наприклад:

    type CreateScheduleRequest = {
        title: string;
    };

Цей тип допомагає розробнику, але сервер усе одно може отримати:

    {
        "title": 123
    }

Або:

    {
        "unexpectedField": true
    }

Тому потрібно розрізняти два завдання.

### Compile-time Type Checking

Перевірка типів під час розробки та компіляції.

    const input: CreateScheduleRequest = {
        title: "Недільний розклад",
    };

TypeScript допомагає виявляти помилки в коді, який перевіряється компілятором.

### Runtime Validation

Перевірка реальних даних, які надходять через HTTP.

Для цього можна використовувати:

- DTO та `class-validator`.
- Zod.
- Valibot.
- Інші схеми валідації.

Приклад із Zod:

    import { z } from "zod";

    const createScheduleSchema = z.object({
        title: z.string().trim().min(1).max(100),
        description: z.string().max(2000).optional(),
    });

    type CreateScheduleRequest = z.infer<
        typeof createScheduleSchema
    >;

Перевірка:

    const result = createScheduleSchema.safeParse(input);

    if (!result.success) {
        // Обробити помилку валідації
    } else {
        // Використати result.data
    }

Це приклад для Zod. Конкретний спосіб інтеграції залежить від архітектури застосунку.

**Правило:** типи допомагають під час розробки, а runtime validation перевіряє фактичні дані.

## 18. Shared Types між Frontend і Backend

Якщо frontend і backend написані на TypeScript, виникає спокуса зберігати всі типи в одному спільному файлі.

Наприклад:

    export type Schedule = {
        id: number;
        title: string;
        ownerId: number;
    };

Для невеликого монорепозиторію спільні типи можуть бути корисними.

Однак потрібно розрізняти:

- Типи доменної моделі.
- Типи бази даних.
- Request DTO.
- Response DTO.
- Типи внутрішніх сервісів.

Вони можуть не збігатися.

Наприклад, backend може зберігати `ownerId`, але не повертати його у звичайній відповіді клієнту.

    type ScheduleResponse = {
        id: number;
        title: string;
    };

А запит на створення може містити тільки:

    type CreateScheduleRequest = {
        title: string;
    };

Не слід використовувати один універсальний тип для всіх шарів лише заради зменшення кількості файлів.

### Практична рекомендація

Для невеликого застосунку:

    shared/
        api-types.ts

Для більшого монорепозиторію можна створити окремий пакет контрактів.

Але спільні TypeScript-типи не замінюють runtime validation і не повинні відкривати приватні поля.

## 19. Contract Testing — тестування контрактів

**Contract Testing** — перевірка того, що взаємодія між компонентами відповідає узгодженому контракту.

Мета — виявляти невідповідності між тим, що клієнт очікує, і тим, що сервер фактично надає.

### Приклад

Контракт визначає:

    GET /api/schedules/42

    Success:
        200 OK

    Response:
        {
            "id": 42,
            "title": "Недільний розклад"
        }

А сервер повертає:

    {
        "id": "42",
        "name": "Недільний розклад"
    }

Є дві невідповідності:

- `id` має тип `string`, а контракт очікує `number`.
- `title` замінено на `name`.

Contract Testing допомагає виявити такі проблеми автоматично, якщо відповідні перевірки налаштовані.

### Рівні тестування API

**Unit Tests**

Перевіряють окремі функції та компоненти.

**Integration Tests**

Перевіряють взаємодію кількох компонентів, наприклад сервісу та бази даних.

**API Tests**

Перевіряють HTTP-запити, статуси та структуру відповідей.

**Contract Tests**

Перевіряють відповідність реалізації узгодженому контракту.

Ці категорії можуть перетинатися залежно від інструментів і способу організації тестів.

Для початку достатньо тестувати основні сценарії API: успішні запити, некоректні дані, відсутність авторизації та заборонений доступ.

## 20. Практичний приклад: API Contracts для Worship Schedule

Розглянемо невеликий API для керування приватними розкладами.

### 20.1. Вимоги

- Користувач повинен бути автентифікований.
- Користувач може отримувати власні розклади.
- Користувач може створювати розклади.
- Користувач може редагувати власні розклади.
- Користувач може видаляти власні розклади.
- Назва розкладу обов'язкова.

### 20.2. Endpoint 1 — отримання розкладів

    GET /api/schedules

    Authentication:
        required

    Query Parameters:
        page: optional integer
        limit: optional integer

    Success:
        200 OK

    Response:
        {
            "items": [
                {
                    "id": 42,
                    "title": "Недільний розклад"
                }
            ],
            "page": 1,
            "limit": 10,
            "totalItems": 1,
            "totalPages": 1
        }

    Errors:
        401 Unauthorized

Контракт має уточнювати, що повертаються тільки розклади, доступні поточному користувачеві.

### 20.3. Endpoint 2 — створення розкладу

    POST /api/schedules

    Authentication:
        required

    Request:
        {
            "title": "Недільний розклад"
        }

    Validation:
        title is required
        title must not be empty
        title max length is 100

    Success:
        201 Created

    Response:
        {
            "id": 42,
            "title": "Недільний розклад"
        }

    Errors:
        400 Bad Request
        401 Unauthorized

Власника зазвичай визначають на сервері з автентифікованої сесії або іншого довіреного контексту, а не приймають безумовно з body.

### 20.4. Endpoint 3 — отримання одного розкладу

    GET /api/schedules/42

    Authentication:
        required

    Success:
        200 OK

    Errors:
        401 Unauthorized
        403 Forbidden
        404 Not Found

Потрібно визначити, чи може користувач переглядати тільки власні розклади, чи також розклади, якими з ним поділилися.

### 20.5. Endpoint 4 — оновлення розкладу

    PATCH /api/schedules/42

    Authentication:
        required

    Request:
        {
            "title": "Оновлений розклад"
        }

    Success:
        200 OK

    Errors:
        400 Bad Request
        401 Unauthorized
        403 Forbidden
        404 Not Found

Контракт повинен визначати, чи дозволено надсилати порожній об'єкт, як обробляються невідомі поля та які властивості можна редагувати.

### 20.6. Endpoint 5 — видалення розкладу

    DELETE /api/schedules/42

    Authentication:
        required

    Success:
        204 No Content

    Errors:
        401 Unauthorized
        403 Forbidden
        404 Not Found

Потрібно також визначити поведінку пов'язаних подій та інших даних після видалення розкладу.

### 20.7. Зведена таблиця

| Метод | Endpoint | Призначення |
|---|---|---|
| `GET` | `/api/schedules` | Отримати список |
| `POST` | `/api/schedules` | Створити розклад |
| `GET` | `/api/schedules/{id}` | Отримати один розклад |

Ця таблиця — основа контракту. Для повноцінної специфікації потрібно доповнити її схемами, параметрами, статусами та правилами авторизації.

Цей формат легко читати та перевіряти під час розробки.

## 23. Типові помилки під час проєктування API Contracts

### Помилка 1. Невизначена структура відповіді

Frontend не знає, чи сервер повертає масив, об'єкт або `null`.

**Краще:** явно описувати response schema.

### Помилка 2. Невідповідність назв полів

Frontend очікує `createdAt`, а backend повертає `created_at`.

**Краще:** визначити єдиний формат API та послідовно його дотримуватися.

### Помилка 3. TypeScript використовується замість валідації

Розробник створив тип, але сервер приймає довільний JSON.

**Краще:** перевіряти вхідні дані під час виконання.

### Помилка 4. Немає правил авторизації

Контракт описує успішний запит, але не визначає, хто може виконувати операцію.

**Краще:** документувати вимоги до автентифікації та прав доступу.

### Помилка 5. Усі помилки повертаються як 500

Некоректний запит, відсутність доступу й внутрішня помилка сервера мають різну семантику.

**Краще:** використовувати відповідні статуси та узгоджений формат помилок.

### Помилка 6. Непослідовні формати дат

Один endpoint повертає UTC, інший — локальний час без часової зони.

**Краще:** визначити формат дат і часових значень на рівні контракту.

### Помилка 7. Надмірна кількість полів

API повертає весь об'єкт бази даних, включно з внутрішніми полями.

**Краще:** визначати окремі response DTO та повертати лише потрібні дані.

### Помилка 8. Непродумані зміни контракту

Поле перейменовується без перевірки клієнтів, які його використовують.

**Краще:** оцінювати сумісність і планувати міграцію.

### Помилка 9. Документація застаріла

OpenAPI або Markdown описує попередню версію API.

**Краще:** перевіряти контракт разом із тестами та змінами коду.

### Помилка 10. Зайве ускладнення

Для маленького приватного API створюється складна система версій, генерації клієнтів і контрактного тестування без реальної потреби.

**Краще:** почати з мінімального достатнього набору інструментів.

## 24. Як API Contracts пов'язані з іншими етапами архітектури

Контракт API поєднує потреби користувача, модель даних та реалізацію frontend і backend.

    Requirements
        ↓
    User Stories and Use Cases
        ↓
    Domain and Data Modeling
        ↓
    Application Architecture
        ↓
    API Contracts
        ↓
    Frontend and Backend Implementation
        ↓
    API Testing
        ↓
    Deployment

Це спрощена схема: контракт можна створювати паралельно з архітектурою та уточнювати в процесі розробки.

### Зв'язок із Requirements

Вимоги визначають, що користувач повинен мати змогу робити.

API Contract визначає, як клієнт може попросити сервер виконати ці операції.

### Зв'язок із Domain and Data Modeling

Модель визначає сутності, атрибути та зв'язки.

API не обов'язково повинен копіювати структуру бази даних. Він надає клієнту представлення, яке відповідає потребам конкретного сценарію.

### Зв'язок із Application Architecture

Архітектура визначає, який компонент обробляє запит, де розташована бізнес-логіка та як виконуються операції з даними.

Контракт визначає зовнішню поведінку API незалежно від багатьох внутрішніх деталей реалізації.

### Зв'язок із Frontend

Frontend використовує контракт, щоб знати:

- Який endpoint викликати.
- Які дані передати.
- Яку структуру відповіді очікувати.
- Як обробляти помилки.

### Зв'язок із Backend

Backend реалізує контракт:

- Валідує запит.
- Перевіряє права доступу.
- Виконує бізнес-логіку.
- Повертає відповідь відповідної структури.

## 28. Головне, що потрібно запам'ятати

**API Contract — це чітка домовленість про те, як клієнт і сервер обмінюються даними.**

Хороший контракт визначає:

- Які операції доступні.
- Які запити потрібно надсилати.
- Які дані є обов'язковими.
- Які відповіді повертаються.
- Які помилки можуть виникнути.
- Які правила безпеки застосовуються.
- Як змінювати API без непотрібного порушення сумісності.

Практичний порядок роботи:

    1. Визнач сценарій використання.
    2. Визнач ресурс і endpoint.
    3. Обери HTTP-метод.
    4. Опиши параметри та request body.
    5. Визнач правила валідації.
    6. Опиши response schema.
    7. Визнач статуси та формат помилок.
    8. Опиши автентифікацію й авторизацію.
    9. Реалізуй endpoint.
    10. Перевір його тестами та документацією.

Для Junior Full Stack Developer найважливіше — навчитися проєктувати передбачувані endpoints, узгоджувати TypeScript-типи з реальною структурою JSON, перевіряти дані на сервері та документувати поведінку API.

**Контракт повинен описувати реальну поведінку системи, а реалізація повинна відповідати контракту.**
