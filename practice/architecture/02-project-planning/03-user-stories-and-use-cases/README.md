# User Stories and Use Cases

## 1. Що таке User Stories and Use Cases

**User Stories** (історії користувача) та **Use Cases** (сценарії використання) — це способи описати, що користувач хоче зробити в системі, навіщо йому це потрібно та як система повинна реагувати на його дії.

Вони допомагають перетворити загальну вимогу на зрозумілу поведінку застосунку, яку можна спроєктувати, реалізувати й перевірити.

Наприклад, загальна вимога:

    Користувач повинен мати можливість керувати розкладом богослужінь.

Це ще не пояснює, що саме означає «керувати». Потрібно уточнити:

- Хто може створювати розклад?
- Чи може користувач редагувати власний розклад?
- Чи може він видаляти розклад?
- Чи може інший користувач змінювати чужий розклад?
- Що відбувається, якщо введено неправильні дані?

User Stories та Use Cases допомагають дати відповіді на ці запитання.

### Для чого це потрібно

- Зрозуміти потреби користувачів до початку програмування.
- Визначити функції, які має виконувати застосунок.
- Розмежувати можливості різних ролей.
- Продумати основні та альтернативні сценарії.
- Визначити умови, за яких функцію можна вважати завершеною.
- Перетворити вимоги на задачі для розробки.
- Зменшити ризик реалізації непотрібних функцій.

### Основна ідея

    User Story → що потрібно користувачу і навіщо.
    Use Case → як користувач взаємодіє із системою.
    Acceptance Criteria → як перевірити, що результат правильний.

Ці три поняття доповнюють одне одного, але не є взаємозамінними.

## 2. Основні поняття

### ✔ User Story

Короткий опис потреби користувача з погляду його ролі та мети.

    Як [роль],
    я хочу [дія або можливість],
    щоб [користь або результат].

### ✔ Use Case

Опис сценарію взаємодії користувача із системою для досягнення конкретної мети.

Зазвичай включає:

- актора;
- передумови;
- основний сценарій;
- альтернативні сценарії;
- помилки та виняткові ситуації;
- очікуваний результат.

### ✔ Actor

Актор — людина, зовнішня система або інший учасник, який взаємодіє із застосунком.

Приклади:

- гість;
- зареєстрований користувач;
- адміністратор;
- викладач;
- платіжний сервіс;
- зовнішній API.

Актор — це не обов'язково людина. Наприклад, зовнішній сервіс може надсилати дані до нашого backend.

### ✔ User Role

Роль користувача визначає його можливості та дозволені дії.

Наприклад:

    Guest:
        переглядати публічні сторінки.

    User:
        створювати власні розклади;
        редагувати власні розклади;
        видаляти власні розклади.

    Admin:
        керувати користувачами;
        виконувати адміністративні дії.

Роль описує набір дозволів, а User Story — конкретну потребу представника цієї ролі.

### ✔ Main Flow

Основний сценарій — послідовність кроків, коли все відбувається успішно.

### ✔ Alternative Flow

Альтернативний сценарій — інший допустимий шлях до результату.

Наприклад, користувач зберігає розклад без необов'язкового опису.

### ✔ Exception Flow

Сценарій помилки або ситуації, яка перешкоджає виконанню операції.

Наприклад:

- користувач не авторизований;
- дані не пройшли валідацію;
- розклад не знайдено;
- користувач не має дозволу на редагування;
- база даних тимчасово недоступна.

### ✔ Acceptance Criteria

Критерії приймання — конкретні умови, які повинні виконуватися, щоб функцію можна було вважати реалізованою.

### ✔ User Journey

Шлях користувача — послідовність взаємодій із продуктом для досягнення більшої мети.

Наприклад:

    Відкрити сайт
        ↓
    Зареєструватися
        ↓
    Увійти
        ↓
    Створити розклад
        ↓
    Відредагувати розклад
        ↓
    Переглянути збережений результат

User Journey охоплює загальний досвід користувача, тоді як User Story та Use Case описують окремі потреби й сценарії.

## 3. User Story: структура

### 3.1. Стандартний шаблон

Найпоширеніший формат:

    Як [тип користувача],
    я хочу [виконати дію],
    щоб [отримати користь].

Англійський варіант:

    As a [type of user],
    I want [some capability],
    so that [some benefit].

Приклад для застосунку Worship Schedule:

    Як зареєстрований користувач,
    я хочу створити власний розклад богослужінь,
    щоб зберігати й редагувати його в одному місці.

У цьому прикладі:

- Роль: зареєстрований користувач.
- Потреба: створити власний розклад.
- Користь: зручно зберігати та редагувати інформацію.

### 3.2. Чому важливо вказувати користь

Порівняймо два варіанти.

Погано:

    Як користувач, я хочу натиснути кнопку «Зберегти»,
    щоб натиснути кнопку «Зберегти».

Цей опис зосереджений на інтерфейсі, а не на потребі.

Краще:

    Як користувач,
    я хочу зберегти зміни до розкладу,
    щоб мати змогу повернутися до оновленої версії пізніше.

Кнопка — лише один із можливих способів реалізації. Сама потреба полягає в збереженні змін.

### 3.3. User Story має описувати цінність

Невдало сформульована історія:

    Як користувач,
    я хочу таблицю з десятьма колонками,
    щоб бачити таблицю з десятьма колонками.

Кращий варіант:

    Як користувач,
    я хочу бачити дату, час і назву богослужіння,
    щоб швидко знаходити потрібну інформацію.

Перша історія передчасно визначає реалізацію. Друга описує потрібний результат і залишає простір для архітектурних та UI-рішень.

### 3.4. Одна історія — одна зрозуміла потреба

Занадто велика історія:

    Як користувач,
    я хочу зареєструватися, створювати розклади,
    редагувати їх, завантажувати зображення,
    експортувати PDF і керувати налаштуваннями,
    щоб повністю керувати своїм акаунтом.

Це набір різних потреб.

Краще розділити його:

    US-01: Користувач хоче створити обліковий запис.
    US-02: Користувач хоче увійти до системи.
    US-03: Користувач хоче створити розклад.
    US-04: Користувач хоче редагувати власний розклад.
    US-05: Користувач хоче видалити власний розклад.
    US-06: Користувач хоче експортувати розклад у PDF.

Це полегшує оцінювання, реалізацію та тестування.

Водночас історія не повинна бути настільки дрібною, щоб описувати кожне натискання кнопки окремо.

## 4. Acceptance Criteria: критерії приймання

User Story описує потребу, але не завжди пояснює всі деталі поведінки системи.

Для цього використовують Acceptance Criteria.

### 4.1. Приклад

User Story:

    Як зареєстрований користувач,
    я хочу створити власний розклад,
    щоб зберігати інформацію про богослужіння.

Критерії приймання:

    1. Авторизований користувач може відкрити форму створення розкладу.
    2. Користувач повинен вказати обов'язкову назву розкладу.
    3. Якщо назву не вказано, система показує повідомлення про помилку.
    4. Після успішного збереження розклад з'являється у списку користувача.
    5. Неавторизований користувач не може створити розклад.
    6. Користувач не може отримати право редагування чужого розкладу лише через зміну ID у запиті.

Останній критерій важливий для безпеки. Приховати кнопку редагування в інтерфейсі недостатньо — backend також повинен перевіряти права доступу.

### 4.2. Given / When / Then

Для формалізації критеріїв можна використовувати формат Given / When / Then.

- **Given** — початкові умови.
- **When** — дія користувача або системи.
- **Then** — очікуваний результат.

Приклад успішного створення:

    Given:
        користувач авторизований;
        користувач відкрив форму створення розкладу.

    When:
        користувач вводить коректну назву;
        користувач натискає «Зберегти».

    Then:
        система створює розклад;
        система зберігає його в базі даних;
        розклад з'являється у списку користувача.

Приклад помилки валідації:

    Given:
        користувач авторизований;
        форма створення розкладу відкрита.

    When:
        користувач залишає обов'язкову назву порожньою;
        користувач надсилає форму.

    Then:
        система не створює розклад;
        користувач отримує зрозуміле повідомлення про помилку.

### 4.3. Навіщо потрібні критерії приймання

Вони допомагають:

- уникнути неоднозначних вимог;
- визначити межі функціональності;
- спланувати тестування;
- перевірити, чи відповідає реалізація очікуванням;
- зрозуміти, коли задачу можна завершити.

### 4.4. Acceptance Criteria та технічна реалізація

Критерії приймання переважно описують спостережувану поведінку, а не конкретний код.

Необов'язково писати:

    Система повинна використовувати NestJS Guard,
    сервіс ScheduleService і метод repository.save().

Це вже рішення щодо реалізації.

Краще:

    Система повинна перевіряти, чи має користувач
    право редагувати вибраний розклад.

Після цього розробник обирає відповідний механізм реалізації.

## 5. Use Case: структура сценарію використання

Use Case докладніше описує взаємодію між актором і системою.

Для складніших операцій він може бути кориснішим за одну коротку User Story.

### 5.1. Типова структура

    Use Case ID:
        UC-03

    Назва:
        Створення розкладу

    Основний актор:
        Зареєстрований користувач

    Мета:
        Створити та зберегти власний розклад.

    Передумови:
        Користувач має обліковий запис.
        Користувач авторизований.

    Тригер:
        Користувач обирає дію «Створити розклад».

    Основний сценарій:
        1. Система відкриває форму.
        2. Користувач вводить назву розкладу.
        3. Користувач заповнює інші необхідні поля.
        4. Користувач надсилає форму.
        5. Система перевіряє дані.
        6. Система зберігає розклад.
        7. Система повідомляє про успішне створення.

    Альтернативні сценарії:
        A1. Користувач не заповнив необов'язкові поля.
        A2. Користувач скасував створення.

    Виняткові сценарії:
        E1. Назва не пройшла валідацію.
        E2. Сесія користувача завершилася.
        E3. База даних недоступна.

    Постумови:
        Розклад збережено та пов'язано з власником.

### 5.2. Передумови та постумови

**Передумови** — умови, які мають виконуватися до початку сценарію.

Приклади:

- користувач авторизований;
- потрібний запис існує;
- користувач має необхідні права.

**Постумови** — стан системи після завершення сценарію.

Наприклад:

- новий розклад збережено;
- зміни запису збережено;
- запис видалено;
- дані залишилися незмінними через помилку.

Важливо не плутати успішний результат із будь-яким завершенням сценарію. Якщо операція не вдалася, постумова може передбачати, що дані не змінилися.

### 5.3. Основний, альтернативний та винятковий потоки

Основний потік:

    Користувач → вводить дані → система перевіряє →
    система зберігає → користувач бачить результат.

Альтернативний потік:

    Користувач → вводить дані →
    залишає необов'язкове поле порожнім →
    система успішно зберігає запис.

Винятковий потік:

    Користувач → надсилає некоректні дані →
    система відхиляє запит →
    користувач отримує повідомлення про помилку.

Альтернативний сценарій не обов'язково є помилкою. Це може бути цілком допустимий спосіб використання функції.

## 6. User Stories та Use Cases: у чому різниця

| Критерій | User Story | Use Case |
|---|---|---|
| Основна мета | Описати потребу користувача | Описати взаємодію із системою |
| Типовий розмір | Короткий | Докладніший |
| Фокус | Роль, потреба, користь | Кроки, умови, результати |
| Альтернативні сценарії | Можуть бути в критеріях | Зазвичай описуються окремо |
| Типове використання | Backlog, планування спринту | Аналіз поведінки та складних сценаріїв |
| Формат | «Як ..., я хочу ..., щоб ...» | Актор, передумови, потоки, постумови |

Приклад:

    User Story:
        Як користувач, я хочу редагувати власний розклад,
        щоб виправляти або оновлювати інформацію.

    Use Case:
        UC-04 — Редагування розкладу.

        1. Користувач відкриває список своїх розкладів.
        2. Система показує доступні записи.
        3. Користувач відкриває потрібний запис.
        4. Система перевіряє право доступу.
        5. Система показує форму редагування.
        6. Користувач змінює дані.
        7. Система перевіряє дані та зберігає зміни.

        Якщо запис не належить користувачу,
        система відхиляє операцію.

**Що запам'ятати:** User Story не замінює Use Case, а Use Case не обов'язково потрібен для кожної дрібної функції.

Для простих функцій достатньо User Story та критеріїв приймання. Для складних операцій, особливо з правами доступу та альтернативними сценаріями, корисно створити докладний Use Case.

## 7. Як визначати акторів і ролі

Перш ніж описувати історії, потрібно зрозуміти, хто взаємодіє із системою.

### 7.1. Приклад ролей

Для Worship Schedule:

    Guest:
        переглядає публічні сторінки.

    Registered User:
        створює власні розклади;
        переглядає власні розклади;
        редагує власні розклади;
        видаляє власні розклади.

    Administrator:
        виконує адміністративні операції,
        визначені вимогами проєкту.

Це лише приклад. Реальні ролі потрібно визначати відповідно до потреб конкретного продукту.

### 7.2. Роль — не те саме, що актор

Актор — учасник взаємодії, а роль — набір повноважень або характеристика цього учасника в контексті системи.

Наприклад, одна людина може бути користувачем на одному сайті та адміністратором на іншому.

Для невеликого застосунку достатньо простого переліку ролей. Не потрібно одразу будувати складну систему дозволів, якщо вона не потрібна.

### 7.3. Зв'язок із backend

Описана User Story повинна враховувати не лише інтерфейс.

Наприклад:

    User Story:
        Як користувач, я хочу редагувати власний розклад.

    Frontend:
        показує кнопку редагування для доступних записів.

    Backend:
        отримує запит на зміну;
        визначає користувача;
        перевіряє право редагування;
        перевіряє дані;
        зберігає зміни.

    Database:
        зберігає дані розкладу та його власника.

Навіть якщо frontend приховав кнопку, backend не повинен дозволяти редагування чужого запису.

## 8. Як розбивати великі потреби на User Stories

Великі потреби зазвичай потрібно розділяти на менші історії, які можна окремо реалізувати та перевірити.

### 8.1. Приклад: керування розкладами

Загальна потреба:

    Користувач повинен мати можливість керувати розкладами.

Розбиваємо її:

    US-01: Створення розкладу.
    US-02: Перегляд власних розкладів.
    US-03: Перегляд одного розкладу.
    US-04: Редагування розкладу.
    US-05: Видалення розкладу.
    US-06: Перевірка доступу до розкладу.
    US-07: Відображення помилок валідації.

Але US-06 та US-07 можуть бути не окремими користувацькими функціями, а наскрізними вимогами або критеріями приймання інших історій.

Тому розбивати потрібно не механічно, а відповідно до структури потреб.

### 8.2. Epic, Feature та User Story

Ці терміни часто використовують для організації backlog.

**Epic** — велика область функціональності або значна потреба.

**Feature** — конкретна можливість продукту.

**User Story** — менша історія, що описує потребу, яку можна реалізувати та перевірити.

Приклад:

    Epic:
        Керування розкладами.

        Feature:
            Створення розкладів.

            User Story:
                Як користувач, я хочу створити розклад,
                щоб зберегти його для подальшого використання.

        Feature:
            Редагування розкладів.

            User Story:
                Як користувач, я хочу змінити дані розкладу,
                щоб підтримувати інформацію актуальною.

        Feature:
            Видалення розкладів.

            User Story:
                Як користувач, я хочу видалити непотрібний
                розклад, щоб прибрати застарілі дані.

Ієрархія може відрізнятися залежно від команди та інструмента. Важливо, щоб вона допомагала керувати роботою, а не створювала зайву документацію.

### 8.3. Як зрозуміти, що історія завелика

Історію варто розглянути для поділу, якщо:

- вона містить багато незалежних функцій;
- її важко оцінити;
- її неможливо завершити за розумний робочий інтервал;
- критерії приймання охоплюють різні потреби;
- різні частини можна реалізувати та перевірити окремо.

Не існує універсального правила, за яким кожна User Story повинна мати певну кількість рядків або кроків.

## 9. INVEST: ознаки хорошої User Story

INVEST — поширена пам'ятка для оцінювання якості історій користувача.

### I — Independent

**Незалежна.**

Історія має бути якомога менш залежною від інших історій.

Наприклад, створення розкладу може залежати від реалізованої авторизації. Такі залежності потрібно розуміти й враховувати під час планування.

Повної незалежності досягти не завжди можливо.

### N — Negotiable

**Відкрита до обговорення.**

Історія описує потребу, а не диктує всі деталі реалізації.

    Погано:
        Обов'язково використати три конкретні React-компоненти.

    Краще:
        Користувач повинен бачити список власних розкладів
        і мати можливість відкрити потрібний.

### V — Valuable

**Має цінність.**

Результат повинен бути корисним для користувача або іншого визначеного зацікавленого учасника.

    Як користувач,
    я хочу зберегти розклад,
    щоб мати доступ до нього пізніше.

### E — Estimable

**Піддається оцінюванню.**

Команда повинна розуміти обсяг роботи настільки, щоб приблизно оцінити складність.

Якщо історія незрозуміла, спочатку потрібно уточнити вимоги.

### S — Small

**Достатньо мала.**

Історія має бути достатньо компактною для планування та перевірки.

Велике керування акаунтом можна розділити на реєстрацію, вхід, зміну профілю та інші незалежні можливості.

### T — Testable

**Перевіряється.**

Повинні існувати зрозумілі критерії, за якими можна визначити, чи реалізована потреба.

    Нечітко:
        Розклад повинен зручно відображатися.

    Краще:
        Користувач бачить назву, дату та час кожної події.
        Якщо подій немає, система показує повідомлення
        про порожній список.

INVEST — це орієнтир, а не формальний закон. Історії можуть мати залежності або потребувати уточнення до того, як стануть готовими до реалізації.

## 10. Пріоритизація User Stories

Не всі історії потрібно реалізовувати одночасно.

Для планування можна використовувати простий підхід MoSCoW.

### Must Have

Критично необхідні можливості.

Приклад:

    Користувач може створити обліковий запис.
    Користувач може увійти.
    Користувач може створити та зберегти розклад.
    Користувач може переглянути власні розклади.
    Система перевіряє права доступу.

### Should Have

Важливі можливості, які можна відкласти, якщо є вагома причина.

Приклад:

    Користувач може редагувати власний розклад.
    Користувач може видаляти власний розклад.

У конкретному продукті редагування може бути критичною вимогою. Пріоритет визначається потребами продукту, а не самою назвою категорії.

### Could Have

Корисні додаткові можливості.

Приклад:

    Користувач може змінювати колір заголовка.
    Користувач може вибирати розмір шрифту.
    Користувач може змінювати вирівнювання тексту.

### Won't Have for Now

Можливості, які свідомо не входять до поточного обсягу робіт.

Приклад:

    Спільне редагування в реальному часі.
    Складна система шаблонів.
    Інтеграція з кількома зовнішніми календарями.

Це не обов'язково означає, що функцію ніколи не буде реалізовано. Її просто не планують на поточному етапі.

### Практичне правило

Для першої версії потрібно визначити мінімальний набір функцій, який дозволяє користувачу отримати основну цінність продукту.

Не слід додавати функцію лише тому, що її легко запрограмувати.

## 11. User Stories у процесі розробки

User Story — це не просто текстовий опис. Вона може бути частиною всього процесу роботи над функцією.

Типовий процес:

    1. Визначити потребу користувача.
    2. Сформулювати User Story.
    3. Уточнити критерії приймання.
    4. Виявити залежності та обмеження.
    5. Оцінити складність.
    6. Визначити пріоритет.
    7. Розділити на технічні задачі.
    8. Реалізувати функцію.
    9. Перевірити критерії приймання.
    10. Прийняти або повернути задачу на доопрацювання.

### 11.1. User Story та технічні задачі

Приклад історії:

    US-04:
        Як користувач,
        я хочу редагувати власний розклад,
        щоб оновлювати інформацію.

Можливі технічні задачі:

    Frontend:
        створити форму редагування;
        заповнювати форму поточними даними;
        показувати повідомлення про помилки.

    Backend:
        створити endpoint для оновлення;
        перевіряти автентифікацію;
        перевіряти право редагування;
        перевіряти вхідні дані;
        повертати зрозумілі HTTP-статуси.

    Database:
        зберігати оновлені поля;
        не змінювати дані, які користувач не має права змінювати.

    Testing:
        перевірити успішне редагування;
        перевірити неправильні дані;
        перевірити спробу редагування чужого запису;
        перевірити ситуацію, коли запис не існує.

User Story описує результат для користувача. Технічні задачі описують роботу, необхідну для досягнення цього результату.

### 11.2. Definition of Done

**Definition of Done (DoD)** — спільне визначення того, що означає завершена робота.

Приклад для невеликого навчального проєкту:

    ✔ Функціональність реалізована.
    ✔ Критерії приймання перевірені.
    ✔ Backend перевіряє права доступу.
    ✔ Помилки обробляються належним чином.
    ✔ Код не містить відомих критичних проблем.
    ✔ Зміни перевірені локально.
    ✔ Документацію оновлено, якщо потрібно.

DoD відрізняється від Acceptance Criteria.

- **Acceptance Criteria** описують вимоги до конкретної історії.
- **Definition of Done** описує загальні вимоги до завершення роботи.

## 12. Від User Story до архітектури застосунку

Вимоги користувача впливають на структуру frontend, backend і бази даних.

Розглянемо приклад:

    User Story:
        Як зареєстрований користувач,
        я хочу переглядати власні розклади,
        щоб швидко знаходити потрібний.

З неї випливають питання до архітектури.

### Frontend

- Як відображати список?
- Як показувати стан завантаження?
- Як показувати порожній список?
- Як повідомляти про помилки?

### Backend

- Який endpoint повертає список розкладів?
- Як backend визначає поточного користувача?
- Як він перевіряє, які записи дозволено повертати?
- Які HTTP-статуси використовувати?

### Database

- Як зберігати розклади?
- Як пов'язати розклад із власником?
- Які поля потрібні?
- Як отримувати записи конкретного користувача?

### Приклад API

    GET /api/schedules

Запит має повертати лише розклади, доступні поточному користувачу, відповідно до правил доступу застосунку.

У спрощеній моделі база даних може містити:

    users
        id
        email

    schedules
        id
        user_id
        title
        created_at
        updated_at

Зв'язок:

    users.id → schedules.user_id

Це лише приклад можливої структури. Реальна модель залежить від вимог: чи існують публічні розклади, спільний доступ, організації або різні ролі.

### Важливий принцип

    Потреба користувача
        ↓
    User Story
        ↓
    Acceptance Criteria
        ↓
    Use Case для складних сценаріїв
        ↓
    Архітектурні рішення
        ↓
    Технічні задачі
        ↓
    Реалізація та перевірка

Не потрібно проєктувати складну архітектуру, доки незрозуміло, яку проблему вона повинна розв'язувати.

## 13. Типові помилки

### Помилка 1. Описувати лише технічну задачу

Погано:

    Як розробник, я хочу створити таблицю schedules.

Це може бути корисною технічною задачею, але не обов'язково є User Story.

Краще:

    Як користувач,
    я хочу зберігати власні розклади,
    щоб переглядати їх пізніше.

Технічна задача створення таблиці може бути частиною реалізації цієї історії.

### Помилка 2. Описувати реалізацію замість потреби

Погано:

    Як користувач, я хочу бачити компонент ScheduleCard.

Краще:

    Як користувач,
    я хочу бачити основну інформацію про кожен розклад,
    щоб швидко знаходити потрібний запис.

Назва React-компонента належить до деталей реалізації.

### Помилка 3. Занадто загальна User Story

Погано:

    Як користувач, я хочу керувати всім застосунком.

Потрібно уточнити конкретні можливості та розділити їх на історії.

### Помилка 4. Нечіткі критерії приймання

Погано:

    Система повинна працювати швидко та зручно.

Краще визначити перевірювані умови, які мають значення для продукту.

Наприклад, якщо швидкість є вимогою, можна встановити вимірюваний час відповіді для конкретного сценарію та умов навантаження.

### Помилка 5. Ігнорувати негативні сценарії

Недостатньо перевірити лише успішний шлях.

Потрібно розглянути:

- неправильні дані;
- відсутній запис;
- відсутню авторизацію;
- недостатні права;
- повторне надсилання запиту;
- недоступність залежного сервісу, якщо це актуально.

### Помилка 6. Вважати приховану кнопку захистом

Frontend може приховати дію, але це не замінює перевірку прав на backend.

Користувач може надіслати HTTP-запит самостійно.

### Помилка 7. Створювати Use Case для кожної дрібниці

Не потрібно документувати складний сценарій для кожної незначної дії.

Для простої функції можуть бути достатні User Story та Acceptance Criteria.

### Помилка 8. Намагатися одразу описати все

Документація повинна допомагати розробці.

Для навчального або невеликого проєкту краще почати з головних сценаріїв, а деталі уточнювати в міру потреби.

## 14. Практичний приклад: Worship Schedule

Припустимо, ми створюємо застосунок, у якому зареєстровані користувачі можуть створювати й редагувати власні розклади богослужінь.

### 14.1. Список основних User Stories

    US-01 — Реєстрація:
        Як новий користувач,
        я хочу створити обліковий запис,
        щоб користуватися персональними функціями.

    US-02 — Вхід:
        Як зареєстрований користувач,
        я хочу увійти до системи,
        щоб отримати доступ до своїх розкладів.

    US-03 — Створення:
        Як користувач,
        я хочу створити розклад,
        щоб зберегти інформацію про богослужіння.

    US-04 — Перегляд:
        Як користувач,
        я хочу бачити список власних розкладів,
        щоб знаходити потрібний.

    US-05 — Редагування:
        Як користувач,
        я хочу змінювати власний розклад,
        щоб оновлювати інформацію.

    US-06 — Видалення:
        Як користувач,
        я хочу видалити власний розклад,
        щоб прибрати непотрібні записи.

    US-07 — Форматування:
        Як користувач,
        я хочу змінювати оформлення тексту розкладу,
        щоб зробити його зручнішим для читання.

    US-08 — Друк:
        Як користувач,
        я хочу підготувати розклад до друку,
        щоб використовувати його в паперовому вигляді.

Це початковий backlog, а не остаточний перелік обов'язкових функцій. Пріоритети потрібно визначити окремо.

### 14.2. Деталізація US-05 — Редагування

User Story:

    Як користувач,
    я хочу змінювати власний розклад,
    щоб оновлювати інформацію.

Acceptance Criteria:

    1. Користувач може відкрити форму редагування власного розкладу.
    2. Форма показує поточні значення полів.
    3. Користувач може змінити дозволені поля.
    4. Після успішного збереження зміни зберігаються в базі даних.
    5. Якщо дані некоректні, система повідомляє про помилку.
    6. Якщо розклад не існує, система повідомляє, що запис не знайдено.
    7. Якщо розклад належить іншому користувачу, система не дозволяє його змінити.
    8. Якщо збереження не вдалося, система не показує операцію як успішну.

### 14.3. Use Case UC-05 — Редагування розкладу

    Актор:
        Зареєстрований користувач.

    Передумови:
        Користувач авторизований.
        Розклад існує.
        Користувач має право його редагувати.

    Основний сценарій:
        1. Користувач відкриває список розкладів.
        2. Користувач обирає потрібний розклад.
        3. Система перевіряє право доступу.
        4. Система показує форму з поточними даними.
        5. Користувач змінює потрібні поля.
        6. Користувач надсилає форму.
        7. Система перевіряє вхідні дані.
        8. Система зберігає зміни.
        9. Система показує оновлений розклад.

    Альтернативний сценарій:
        Користувач скасовує редагування.
        Зміни не зберігаються.

    Винятковий сценарій:
        Дані не проходять валідацію.
        Система показує помилки.
        Збереження не виконується.

    Винятковий сценарій:
        Користувач не має права редагувати запис.
        Система відхиляє запит.
        Дані не змінюються.

    Постумова успішного сценарію:
        Зміни збережено.

    Постумова невдалого сценарію:
        Початкові дані залишилися незмінними.

### 14.4. Що з цього випливає для реалізації

    Frontend:
        форма редагування;
        перевірка введення для зручності користувача;
        повідомлення про результат.

    Backend:
        endpoint оновлення;
        автентифікація;
        авторизація;
        серверна валідація;
        обробка помилок.

    Database:
        збереження змінених полів;
        зв'язок запису з власником.

    Tests:
        успішне редагування;
        некоректні дані;
        відсутній запис;
        редагування чужого запису;
        помилка збереження.

Одна User Story може вимагати змін у кількох частинах застосунку. Це нормально: історія описує користувацький результат, а не окремий шар системи.

## 15. Як документувати User Stories у проєкті

Для невеликого проєкту достатньо Markdown-файлу. Не потрібно одразу використовувати спеціальну систему управління вимогами.

Наприклад, можна створити структуру:

    project/
    ├── README.md
    └── docs/
        ├── requirements.md
        ├── user-stories.md
        └── use-cases.md

Або зберігати все в одному файлі, якщо історій поки небагато.

### Приклад user-stories.md

    # User Stories

    ## Epic: Керування розкладами

    ### US-01 — Створення розкладу

    Як зареєстрований користувач,
    я хочу створити власний розклад,
    щоб зберігати інформацію про богослужіння.

    Acceptance Criteria:

    - Користувач авторизований.
    - Назва розкладу є обов'язковою.
    - Дані проходять перевірку.
    - Після успішного збереження запис доступний власнику.
    - Неавторизований користувач не може створити запис.

    Priority: Must Have

    Status: Planned

    ---

    ### US-02 — Редагування розкладу

    Як користувач,
    я хочу редагувати власний розклад,
    щоб підтримувати інформацію актуальною.

    Acceptance Criteria:

    - Користувач може відкрити власний запис.
    - Форма показує поточні дані.
    - Система перевіряє дані перед збереженням.
    - Backend перевіряє право редагування.
    - Після успішного збереження показуються оновлені дані.

    Priority: Must Have

    Status: Planned

Це лише один із можливих форматів. Для навчального репозиторію важливо, щоб документ залишався зрозумілим і відповідав поточній версії функціональності.

## 16. Як змінювати User Stories у процесі розробки

Під час реалізації можуть з'являтися нові вимоги або уточнення.

Наприклад, спочатку планувалося, що користувач створює лише звичайний текстовий розклад. Пізніше з'являється бажання змінювати розмір шрифту, колір і вирівнювання.

Не варто автоматично додавати всі ці можливості до поточної задачі.

Потрібно з'ясувати:

- Чи справді це важливо для першої версії?
- Чи змінює це основну потребу?
- Чи впливає на модель даних?
- Чи потрібні нові критерії приймання?
- Чи впливає це на безпеку або збереження даних?
- Чи потрібно розділити історію на кілька менших?

Наприклад:

    Початкова історія:
        Користувач може створити та зберегти розклад.

    Додаткова історія:
        Користувач може змінювати оформлення тексту.

    Можлива наступна історія:
        Користувач може зберігати власні шаблони оформлення.

Це дозволяє розвивати продукт поступово, не перетворюючи першу версію на надто великий проєкт.

## 17. Зв'язок із тестуванням

User Stories та Use Cases допомагають визначити, що саме потрібно перевіряти.

Наприклад:

    User Story:
        Як користувач,
        я хочу редагувати власний розклад.

    Acceptance Criteria:
        Backend не дозволяє редагувати чужий розклад.

З цього критерію можна сформувати тест:

    1. Створити двох користувачів.
    2. Створити розклад для першого користувача.
    3. Авторизуватися від імені другого користувача.
    4. Спробувати надіслати запит на редагування
       розкладу першого користувача.
    5. Переконатися, що запит відхилено.
    6. Переконатися, що дані розкладу не змінилися.

Так вимога перетворюється на перевірювану поведінку системи.

### Важливо розрізняти

- **Acceptance Criteria** — умови приймання функції.
- **Test Case** — конкретні кроки, тестові дані та очікуваний результат перевірки.
- **Automated Test** — програмний тест, який виконує перевірку автоматично.

Не кожен критерій обов'язково має бути окремим автоматизованим тестом, але критичні сценарії варто автоматизувати, коли це доцільно.

## 18. Що варто знати Junior-розробнику

На початковому рівні потрібно навчитися читати вимоги та перетворювати їх на зрозумілі технічні задачі.

### Core

    ✔ Розуміти, що таке User Story.
    ✔ Знати шаблон «Як ..., я хочу ..., щоб ...».
    ✔ Відрізняти потребу користувача від технічної задачі.
    ✔ Розуміти Acceptance Criteria.
    ✔ Знати формат Given / When / Then.
    ✔ Відрізняти основний сценарій від сценарію помилки.
    ✔ Розуміти ролі користувачів.
    ✔ Перевіряти, чи можна протестувати вимогу.

### Junior

    ✔ Розбивати велику потребу на невеликі історії.
    ✔ Визначати залежності між історіями.
    ✔ Створювати прості Use Cases.
    ✔ Описувати позитивні та негативні сценарії.
    ✔ Перетворювати критерії приймання на тестові сценарії.
    ✔ Пов'язувати вимоги з frontend, backend і database.
    ✔ Враховувати автентифікацію та авторизацію.
    ✔ Визначати, що входить до поточної версії продукту.

### Middle

    ✔ Виявляти неоднозначні вимоги.
    ✔ Проводити декомпозицію великих функціональних областей.
    ✔ Аналізувати альтернативні та виняткові сценарії.
    ✔ Виявляти ризики й залежності.
    ✔ Допомагати визначати пріоритети.
    ✔ Узгоджувати вимоги з архітектурними рішеннями.
    ✔ Враховувати нефункціональні вимоги.
    ✔ Підтримувати відповідність між вимогами, реалізацією та тестами.

### Senior / Architecture

    ✔ Аналізувати потреби різних зацікавлених сторін.
    ✔ Виявляти суперечливі вимоги.
    ✔ Визначати системні обмеження та ризики.
    ✔ Оцінювати вплив вимог на архітектуру.
    ✔ Враховувати масштабування, безпеку та підтримуваність.
    ✔ Організовувати керування змінами вимог.
    ✔ Допомагати команді обирати правильний рівень деталізації.
    ✔ Не допускати надмірного ускладнення рішення.

Ці рівні — орієнтир для навчання, а не формальна сертифікація компетентності.

### Приклад хорошої відповіді

**Запитання:** Чим User Story відрізняється від Use Case?

    User Story коротко описує потребу користувача
    та цінність, яку він хоче отримати.

    Use Case докладніше описує взаємодію актора
    із системою: передумови, основний потік,
    альтернативні сценарії та очікувані результати.

    Для простої функції можуть бути достатні User Story
    та Acceptance Criteria. Для складної взаємодії
    корисно додатково описати Use Case.

## 20. Мінішпаргалка

### User Story

    Як [роль],
    я хочу [можливість],
    щоб [користь].

### Acceptance Criteria

    Які конкретні умови повинні виконуватися,
    щоб функцію можна було прийняти?

### Given / When / Then

    Given — початкові умови.
    When — дія.
    Then — очікуваний результат.

### Use Case

    Назва
    Актор
    Мета
    Передумови
    Тригер
    Основний сценарій
    Альтернативні сценарії
    Виняткові сценарії
    Постумови

### INVEST

    I — Independent
    N — Negotiable
    V — Valuable
    E — Estimable
    S — Small
    T — Testable

### MoSCoW

    Must Have — критично необхідне.
    Should Have — важливе.
    Could Have — бажане.
    Won't Have for Now — поза поточним обсягом.

### Основний ланцюжок

    Потреба
        ↓
    User Story
        ↓
    Acceptance Criteria
        ↓
    Use Case за потреби
        ↓
    Технічні задачі
        ↓
    Реалізація
        ↓
    Тестування

## 21. Головне, що потрібно запам'ятати

User Stories та Use Cases допомагають розробнику зрозуміти не лише те, що потрібно реалізувати, а й те, **для кого, навіщо та за яких умов система повинна це робити**.

Під час планування проєкту:

1. Спочатку визначай потребу користувача.
2. Формулюй User Story простою та зрозумілою мовою.
3. Додавай конкретні критерії приймання.
4. Для складних сценаріїв описуй Use Case.
5. Враховуй альтернативні ситуації, помилки та права доступу.
6. Розбивай великі потреби на менші історії.
7. Визначай пріоритети та межі поточної версії.
8. Перетворюй історії на технічні задачі лише після розуміння очікуваного результату.
9. Перевіряй реалізацію за критеріями приймання.
10. Уточнюй документацію, коли змінюються вимоги.

**Ключова думка:** хороша User Story описує цінність для користувача, хороший Use Case пояснює взаємодію із системою, а хороші Acceptance Criteria дозволяють перевірити, чи отримано очікуваний результат.
