# User Flows

## 1. Що таке User Flows

**User Flow** (потік користувача) — це послідовність кроків, які користувач проходить у застосунку, щоб досягти певної мети.

User Flow показує, як користувач переходить від початкової точки до очікуваного результату, які дії виконує та як система реагує на них.

Наприклад, у застосунку Worship Schedule користувач хоче створити власний розклад богослужінь.

    Відкрити застосунок
        ↓
    Увійти до облікового запису
        ↓
    Відкрити розділ розкладів
        ↓
    Натиснути «Створити розклад»
        ↓
    Заповнити форму
        ↓
    Зберегти розклад
        ↓
    Побачити створений розклад

Це простий User Flow, який показує основний шлях до досягнення мети.

### Для чого потрібні User Flows

- Зрозуміти, як користувач взаємодіє із застосунком.
- Спланувати навігацію між сторінками.
- Виявити зайві кроки та складні місця.
- Продумати поведінку інтерфейсу.
- Визначити, де потрібні перевірки та повідомлення про помилки.
- Зрозуміти, які функції мають бути реалізовані на frontend і backend.
- Підготувати основу для UI-дизайну та тестування.
- Виявити відсутні сценарії ще до написання коду.

### Основна ідея

    User Story:
        Яку потребу має користувач?

    User Flow:
        Якими кроками користувач досягає мети?

    Use Case:
        Як саме відбувається взаємодія із системою?

    Acceptance Criteria:
        Як перевірити, що результат відповідає вимогам?

Ці поняття пов'язані, але виконують різні завдання.

## 2. Основні поняття

### ✔ User Flow

Послідовність дій користувача та реакцій системи, яка веде до певного результату.

### ✔ User Journey

Ширший шлях користувача під час взаємодії з продуктом, який може охоплювати кілька User Flows, різні канали взаємодії та емоційний досвід.

### ✔ Entry Point

Початкова точка потоку користувача.

Приклади:

- головна сторінка;
- сторінка входу;
- посилання на конкретний розклад;
- повідомлення електронної пошти;
- сторінка, відкрита через закладку браузера.

### ✔ Action

Дія користувача або системи.

Приклади:

- натиснути кнопку;
- ввести текст;
- обрати пункт меню;
- надіслати форму;
- перевірити права доступу;
- отримати дані з API.

### ✔ Decision Point

Точка прийняття рішення, у якій потік розгалужується залежно від умови.

Наприклад:

    Користувач авторизований?
        ├── Так → відкрити список розкладів
        └── Ні → відкрити сторінку входу

### ✔ Branch

Окрема гілка потоку, яка виникає після перевірки умови або вибору користувача.

### ✔ Success Path

Основний шлях, яким користувач успішно досягає мети.

### ✔ Error Path

Шлях, яким користувач проходить у разі помилки або невдалої операції.

### ✔ Exit Point

Точка завершення потоку.

Приклади:

- розклад успішно створено;
- користувач вийшов з облікового запису;
- користувач скасував операцію;
- система повідомила про помилку, і користувач повернувся до форми.

### ✔ Screen Flow

Потік переходів між екранами або сторінками застосунку.

### ✔ Task Flow

Послідовність кроків для виконання конкретного завдання, наприклад створення розкладу або зміна пароля.

## 3. User Flow та суміжні поняття

### 3.1. User Flow vs User Journey

**User Flow** зосереджується на конкретному шляху виконання завдання.

**User Journey** охоплює ширший досвід взаємодії з продуктом.

Приклад User Flow:

    Увійти
        ↓
    Відкрити розклади
        ↓
    Створити розклад
        ↓
    Зберегти результат

Приклад User Journey:

    Дізнатися про застосунок
        ↓
    Відвідати сайт
        ↓
    Зареєструватися
        ↓
    Навчитися створювати розклади
        ↓
    Регулярно користуватися застосунком
        ↓
    Поділитися результатом або повернутися пізніше

User Journey може включати не лише дії в інтерфейсі, а й пошук інформації, спілкування з підтримкою та інші етапи.

### 3.2. User Flow vs Use Case

User Flow зручно показує послідовність дій та розгалуження.

Use Case докладніше описує взаємодію актора із системою, включаючи передумови, основний сценарій, альтернативні потоки та постумови.

Приклад User Flow:

    Відкрити форму
        ↓
    Ввести назву
        ↓
    Натиснути «Зберегти»
        ↓
    Дані коректні?
        ├── Так → зберегти розклад
        └── Ні → показати помилку

Приклад Use Case:

    UC-03 — Створення розкладу.

    Актор:
        Авторизований користувач.

    Передумови:
        Користувач має право створювати розклади.

    Основний сценарій:
        1. Користувач відкриває форму.
        2. Вводить дані.
        3. Надсилає форму.
        4. Система перевіряє дані.
        5. Система зберігає розклад.
        6. Система показує результат.

    Альтернативний сценарій:
        Якщо дані некоректні, система показує помилки.

### 3.3. User Flow vs Wireframe

**Wireframe** — спрощене схематичне зображення структури екрана.

**User Flow** — схема послідовності кроків і переходів.

Наприклад, wireframe може показувати розташування кнопки «Створити розклад», поля назви та кнопки «Зберегти».

User Flow показує, звідки користувач переходить до форми, що робить після її заповнення та куди потрапляє після збереження.

Ці інструменти доповнюють один одного.

## 4. Як побудувати User Flow

Для початку достатньо семи кроків.

### Крок 1. Визначити мету користувача

Не починай зі сторінок або компонентів. Спочатку сформулюй, чого хоче досягти користувач.

Наприклад:

    Мета:
        Створити та зберегти власний розклад богослужінь.

### Крок 2. Визначити початкову точку

Звідки користувач починає?

    Entry Point:
        Сторінка списку розкладів.

Або:

    Entry Point:
        Головна сторінка застосунку.

Початкова точка залежить від того, звідки користувач зазвичай виконує завдання.

### Крок 3. Визначити необхідні дії

Запиши основні кроки без зайвих деталей інтерфейсу.

    1. Відкрити розділ розкладів.
    2. Обрати створення розкладу.
    3. Заповнити форму.
    4. Надіслати дані.
    5. Отримати результат.

### Крок 4. Визначити точки прийняття рішень

Подумай, де система або користувач повинні зробити вибір.

    Користувач авторизований?
        ├── Так → продовжити
        └── Ні → перейти до входу

    Дані коректні?
        ├── Так → зберегти
        └── Ні → показати помилки

### Крок 5. Продумати альтернативні сценарії

Основний шлях не охоплює всі можливі ситуації.

Потрібно розглянути:

- користувач скасував дію;
- користувач ввів неправильні дані;
- запис не знайдено;
- доступ заборонено;
- сервер не відповідає;
- користувач повторно надсилає форму.

Не кожна ситуація обов'язково має бути окремою великою гілкою на схемі. Для простого потоку достатньо показати найважливіші розгалуження, а деталі описати окремо.

### Крок 6. Визначити кінцеві результати

Наприклад:

    Успіх:
        Розклад створено і показано користувачу.

    Помилка:
        Розклад не створено.
        Користувач бачить пояснення та може виправити дані.

    Скасування:
        Користувач повертається до списку.
        Новий запис не створюється.

### Крок 7. Перевірити потік

Постав собі запитання:

- Чи може користувач зрозуміти, що робити далі?
- Чи є непотрібні переходи?
- Чи зрозуміло, як повернутися назад?
- Чи враховані помилки?
- Чи не губляться введені дані?
- Чи перевіряються права доступу?
- Чи існує чіткий результат завершення?

## 5. Типи User Flows

### 5.1. Happy Path

**Happy Path** — основний успішний сценарій без помилок і несподіваних перешкод.

Приклад:

    Відкрити застосунок
        ↓
    Увійти
        ↓
    Відкрити розклади
        ↓
    Створити розклад
        ↓
    Заповнити правильні дані
        ↓
    Зберегти
        ↓
    Побачити успішний результат

Це перший потік, який зазвичай варто спроєктувати.

Але не можна обмежуватися лише ним.

### 5.2. Error Flow

Error Flow описує поведінку системи, коли щось іде не так.

Приклад:

    Відкрити форму
        ↓
    Ввести неправильні дані
        ↓
    Натиснути «Зберегти»
        ↓
    Система перевіряє дані
        ↓
    Виявлено помилку
        ↓
    Показати повідомлення
        ↓
    Користувач виправляє дані

Хороший Error Flow не просто повідомляє про помилку, а допомагає користувачу продовжити роботу.

### 5.3. Authentication Flow

Потік автентифікації показує, як користувач входить до системи.

    Відкрити захищений розділ
        ↓
    Перевірити стан авторизації
        ├── Авторизований
        │       ↓
        │   Відкрити розділ
        │
        └── Не авторизований
                ↓
            Показати сторінку входу
                ↓
            Ввести облікові дані
                ↓
            Перевірити дані
                ├── Правильні → відкрити розділ
                └── Неправильні → показати помилку

Після успішного входу користувачеві бажано повернутися до потрібної сторінки, якщо це безпечно й відповідає логіці застосунку.

### 5.4. CRUD Flow

CRUD — чотири базові операції з даними:

    Create — створення.
    Read   — читання.
    Update — оновлення.
    Delete — видалення.

Приклад керування розкладами:

    Список розкладів
        ├── Створити → форма → зберегти
        ├── Відкрити → перегляд розкладу
        ├── Редагувати → форма → зберегти зміни
        └── Видалити → підтвердити → видалити запис

Для багатьох навчальних застосунків CRUD-потоки є гарною відправною точкою.

### 5.5. Onboarding Flow

Onboarding Flow допомагає новому користувачу почати роботу із застосунком.

    Відкрити сайт
        ↓
    Ознайомитися з можливостями
        ↓
    Створити обліковий запис
        ↓
    Увійти
        ↓
    Створити перший розклад
        ↓
    Побачити результат

Не кожному застосунку потрібен окремий майстер знайомства. Іноді достатньо зрозумілої головної сторінки та простих підказок.

### 5.6. Search Flow

Потік пошуку показує, як користувач знаходить потрібну інформацію.

    Відкрити список
        ↓
    Ввести пошуковий запит
        ↓
    Система обробляє запит
        ↓
    Є результати?
        ├── Так → показати список
        └── Ні → показати повідомлення
                  про відсутність результатів

Важливо продумати порожній результат, неправильний запит і можливість швидко очистити пошук.

### 5.7. Form Submission Flow

Потік надсилання форми описує введення, перевірку та збереження даних.

    Заповнити форму
        ↓
    Надіслати
        ↓
    Перевірити дані
        ├── Помилка → показати повідомлення
        │              ↓
        │          Виправити дані
        │
        └── Успіх → надіслати запит
                    ↓
                 Backend перевіряє дані
                    ├── Успіх → зберегти
                    └── Помилка → повернути помилку
                    ↓
                 Показати результат

Перевірки на frontend покращують зручність, але backend повинен самостійно перевіряти вхідні дані.

## 6. Як позначати User Flow на схемі

Для простих схем можна використовувати кілька базових елементів.

### Основні елементи

    Овал:
        початок або завершення потоку.

    Прямокутник:
        дія або крок.

    Ромб:
        рішення або перевірка умови.

    Стрілка:
        напрямок переходу.

    Паралелограм:
        введення або виведення даних
        у традиційній блок-схемі.

У реальних діаграмах оформлення може відрізнятися. Головне — послідовно використовувати символи та пояснювати незвичні позначення.

### Приклад текстової схеми

    (Початок)
         |
         v
    [Відкрити форму]
         |
         v
    [Ввести дані]
         |
         v
    <Дані коректні?>
       /       \
     Так       Ні
      |         |
      v         v
    [Зберегти] [Показати помилку]
      |         |
      v         |
    [Результат] |
      |         |
      v         |
    (Кінець) <--+

Ця схема демонструє розгалуження та повернення до виправлення помилки.

### Mermaid для документації

Mermaid дозволяє описувати діаграми текстом у Markdown-файлах. Це зручно для навчального репозиторію та документації поруч із кодом.

Приклад:

    flowchart TD
        A([Початок]) --> B[Відкрити форму]
        B --> C[Ввести дані]
        C --> D{Дані коректні?}
        D -- Так --> E[Зберегти розклад]
        E --> F([Успіх])
        D -- Ні --> G[Показати помилки]
        G --> C

Де:

- `flowchart TD` — напрямок згори вниз;
- `A`, `B`, `C` — ідентифікатори вузлів;
- `[]` — дія;
- `{}` — рішення;
- `-->` — стрілка;
- `-- Так -->` — підпис переходу;
- `([Текст])` — вузол початку або завершення.

Інші напрямки:

    flowchart TD
        Напрямок згори вниз.

    flowchart LR
        Напрямок зліва направо.

    flowchart RL
        Напрямок справа наліво.

    flowchart BT
        Напрямок знизу вгору.

У цьому README приклади коду оформлено відступами, щоб весь документ можна було скопіювати як один Markdown-файл.

## 7. User Flow та навігація

User Flow допомагає спланувати, як користувач переходить між сторінками.

Приклад:

    Головна сторінка
        ├── Вхід
        │    └── Особистий кабінет
        │         └── Мої розклади
        │              ├── Створення
        │              └── Перегляд розкладу
        │                   └── Редагування
        │
        └── Публічна інформація

Але не слід плутати User Flow з повною картою сайту.

**Sitemap** показує структуру сторінок і розділів.

**User Flow** показує шлях до конкретної мети.

Наприклад, сторінка редагування може бути доступна зі списку розкладів і зі сторінки перегляду окремого розкладу. Sitemap покаже наявність сторінки, а User Flow — можливі переходи до неї.

### 7.1. Переходи вперед і назад

Потрібно продумати, що відбувається, якщо користувач:

- натискає кнопку «Назад»;
- переходить на іншу сторінку;
- оновлює сторінку;
- відкриває пряме посилання;
- закриває форму;
- повертається після успішного збереження.

Для багатокрокових форм варто визначити, чи зберігаються введені дані при поверненні до попереднього кроку.

### 7.2. Не створюй тупики

Тупик — ситуація, коли користувач не розуміє, що робити далі, або не має очевидного способу продовжити роботу.

Поганий приклад:

    Користувач надсилає форму
        ↓
    Виникає помилка
        ↓
    Показується повідомлення «Щось пішло не так»

Краще:

    Користувач надсилає форму
        ↓
    Виникає помилка
        ↓
    Показується зрозуміле повідомлення
        ↓
    Дані форми зберігаються, якщо це можливо
        ↓
    Користувач може повторити спробу

Повідомлення має пояснювати проблему настільки, наскільки це безпечно, і давати користувачу зрозумілий наступний крок.

## 8. User Flow і стани інтерфейсу

Потік користувача повинен враховувати не лише переходи між сторінками, а й стани інтерфейсу під час виконання операцій.

### 8.1. Основні UI-стани

    Initial:
        початковий стан.

    Loading:
        дані завантажуються.

    Success:
        операція успішна.

    Empty:
        даних немає.

    Error:
        сталася помилка.

    Disabled:
        дія тимчасово недоступна.

Наприклад, після відкриття списку розкладів:

    Відкрити список
        ↓
    Завантажити дані
        ├── Завантаження успішне
        │       ├── Є розклади → показати список
        │       └── Немає розкладів → показати порожній стан
        │
        └── Помилка → показати повідомлення
                      та можливість повторити запит

Це важливо для застосунків, які отримують дані з API.

### 8.2. Чому Loading — це частина потоку

Запит до backend може тривати певний час.

Якщо користувач натискає «Зберегти», але не бачить жодної реакції, він може повторно натиснути кнопку й надіслати кілька запитів.

Тому потік може включати:

    Натиснути «Зберегти»
        ↓
    Заблокувати повторне надсилання
        ↓
    Показати індикатор завантаження
        ↓
    Дочекатися відповіді
        ├── Успіх → показати результат
        └── Помилка → показати повідомлення
                       та дозволити повторну спробу

У backend також потрібно продумати поведінку операцій, які можуть бути повторно надіслані. Самого блокування кнопки недостатньо для всіх сценаріїв.

## 9. User Flow та frontend, backend і database

User Flow може стати основою для планування технічної реалізації.

Розглянемо створення розкладу.

### 9.1. Frontend

Frontend відповідає за взаємодію з користувачем:

- показує форму;
- приймає введені дані;
- виконує базову перевірку введення;
- надсилає HTTP-запит;
- показує стан завантаження;
- відображає результат або помилку.

### 9.2. Backend

Backend виконує серверну логіку:

- перевіряє автентифікацію;
- перевіряє права доступу;
- перевіряє вхідні дані;
- виконує бізнес-правила;
- взаємодіє з базою даних;
- повертає результат або помилку.

### 9.3. Database

База даних зберігає інформацію, необхідну для виконання сценарію.

Наприклад:

    users
        id
        email

    schedules
        id
        user_id
        title
        content
        created_at
        updated_at

Зв'язок:

    users.id → schedules.user_id

Це спрощений приклад. Реальна структура залежить від того, чи містить розклад окремі події, форматування, шаблони або спільний доступ.

### 9.4. Приклад HTTP-запиту

Створення розкладу може використовувати endpoint:

    POST /api/schedules

Приклад JSON:

    {
        "title": "Розклад богослужінь",
        "content": "Недільне богослужіння — 09:00"
    }

Це лише приклад форми запиту. У реальному застосунку потрібно визначити схему даних, автентифікацію та правила доступу.

Потік на рівні системи:

    Користувач заповнює форму
        ↓
    Frontend надсилає POST-запит
        ↓
    Backend перевіряє користувача
        ↓
    Backend перевіряє дані
        ↓
    Backend зберігає запис у database
        ↓
    Backend повертає результат
        ↓
    Frontend показує створений розклад

Ця схема допомагає побачити, що відбувається між дією користувача та результатом на екрані.

## 10. Важливі питання безпеки в User Flows

Не кожен потік є лише навігаційним. Деякі сценарії включають перевірки доступу та захист даних.

### 10.1. Авторизація

Потрібно перевірити, чи має користувач право виконати конкретну дію.

Приклад:

    Користувач відкриває розклад
        ↓
    Backend перевіряє доступ
        ├── Доступ дозволено → повернути дані
        └── Доступ заборонено → відхилити запит

Приховування сторінки або кнопки на frontend не замінює перевірку на сервері.

### 10.2. Власник запису

Якщо кожен користувач має власні приватні розклади, потік повинен враховувати власника запису.

    Користувач надсилає запит на редагування
        ↓
    Backend визначає поточного користувача
        ↓
    Backend знаходить запис
        ↓
    Backend перевіряє право редагування
        ├── Власник має право → продовжити
        └── Немає права → відхилити запит

Не можна довіряти лише ID користувача або запису, які передає frontend.

### 10.3. Пряме відкриття URL

Користувач може відкрити адресу сторінки без попереднього проходження звичайного потоку.

Наприклад:

    /schedules/123/edit

Тому потрібно визначити поведінку, коли:

- користувач не авторизований;
- запис не існує;
- запис належить іншому користувачу;
- користувач не має дозволу редагувати його.

User Flow повинен враховувати такі випадки, а не припускати, що користувач завжди переходить між сторінками в очікуваному порядку.

## 11. Як знаходити проблеми в User Flow

Після створення схеми потрібно перевірити, наскільки легко користувачу досягти мети.

### 11.1. Зайві кроки

Приклад:

    Відкрити розклади
        ↓
    Відкрити окрему сторінку меню
        ↓
    Відкрити налаштування
        ↓
    Повернутися до розкладів
        ↓
    Створити розклад

Якщо проміжні переходи не мають сенсу, їх варто прибрати.

Однак менша кількість кроків не завжди означає кращий досвід. Додаткове підтвердження може бути виправданим для небезпечної або незворотної операції.

### 11.2. Незрозумілі дії

Якщо користувач не розуміє призначення кнопки, проблема може бути в тексті, розташуванні або контексті.

Замість загального напису «Далі» іноді краще використовувати конкретніший:

    «Перейти до оформлення»
    «Зберегти розклад»
    «Підтвердити видалення»

Текст повинен відповідати реальній дії.

### 11.3. Відсутність зворотного зв'язку

Після дії користувач має розуміти, що сталося.

Приклади:

    Після збереження:
        «Розклад успішно збережено».

    Якщо список порожній:
        «У вас ще немає розкладів».
        «Створити перший розклад».

    Якщо сталася помилка:
        зрозуміле повідомлення та доступна наступна дія.

### 11.4. Відсутність альтернативного шляху

Якщо користувач не може виконати дію, потрібно подумати, чи можна допомогти йому продовжити.

Наприклад:

    Користувач забув пароль
        ↓
    Не може увійти
        ↓
    Обрати відновлення пароля
        ↓
    Пройти перевірку
        ↓
    Встановити новий пароль
        ↓
    Увійти до системи

Для реального відновлення пароля необхідно окремо продумати безпеку, строк дії токенів та інші вимоги.

Не потрібно автоматично вважати один варіант правильним. Вибір залежить від того, що користувачеві логічніше робити далі.

## 14. Як пов'язати User Flows із вимогами

User Flow не повинен існувати окремо від інших проєктних документів.

Наприклад:

    User Story:
        US-04 — Редагування власного розкладу.

    Acceptance Criteria:
        AC-04-01 — Форма показує поточні дані.
        AC-04-02 — Некоректні дані не зберігаються.
        AC-04-03 — Чужий запис не можна редагувати.

    User Flow:
        UF-04 — Редагування розкладу.

    Use Case:
        UC-04 — Редагування розкладу.

    Технічні задачі:
        FE-04 — Створити форму редагування.
        BE-04 — Реалізувати endpoint оновлення.
        BE-05 — Перевіряти право редагування.
        TEST-04 — Перевірити успішний сценарій.
        TEST-05 — Перевірити заборонений доступ.

Така структура допомагає зрозуміти, чому існує кожна технічна задача і які вимоги вона реалізує.

Для невеликого проєкту не обов'язково створювати окремий файл для кожного ідентифікатора. Достатньо зберігати зв'язки у зрозумілій документації або в системі управління задачами.

## 15. Як зберігати User Flows у проєкті

Для навчального репозиторію можна створити окрему теку документації.

    project/
    ├── README.md
    └── docs/
        ├── requirements.md
        ├── user-stories.md
        ├── use-cases.md
        └── user-flows.md

У файлі `user-flows.md` можна зберігати схеми Mermaid і короткі пояснення.

Якщо потоків багато, їх можна розділити:

    docs/
    └── user-flows/
        ├── authentication.md
        ├── schedule-creation.md
        ├── schedule-editing.md
        ├── schedule-deletion.md
        └── password-recovery.md

Не потрібно створювати всі ці файли одразу. Починай із потоків, які описують основні можливості першої версії застосунку.

### Приклад документації одного потоку

    # UF-03 — Створення розкладу

    ## Мета

    Користувач хоче створити власний розклад.

    ## Актор

    Авторизований користувач.

    ## Початкова точка

    Список розкладів.

    ## Основний потік

    1. Користувач натискає «Створити».
    2. Система відкриває форму.
    3. Користувач вводить дані.
    4. Користувач надсилає форму.
    5. Система перевіряє дані.
    6. Система зберігає розклад.
    7. Система показує результат.

    ## Альтернативні сценарії

    - Користувач скасовує створення.
    - Дані не проходять валідацію.
    - Backend не може зберегти запис.

    ## Пов'язані вимоги

    - US-03 — Створення розкладу.
    - AC-03-01 — Назва є обов'язковою.
    - AC-03-02 — Неавторизований користувач
      не може створювати приватні розклади.

## 16. Типові помилки під час проєктування User Flows

### Помилка 1. Починати з UI-компонентів

Погано:

    Створити кнопку.
        ↓
    Створити модальне вікно.
        ↓
    Створити форму.

Це перелік елементів інтерфейсу, а не повний User Flow.

Краще починати з мети користувача, а потім визначати, які екрани та дії потрібні.

### Помилка 2. Описувати лише Happy Path

Якщо схема показує лише успішний сценарій, вона може приховувати важливі проблеми.

Потрібно врахувати хоча б основні помилки, скасування та відсутність доступу.

### Помилка 3. Змішувати всі потоки в одну величезну схему

Якщо одна діаграма одночасно описує реєстрацію, створення розкладу, редагування, видалення, налаштування та відновлення пароля, її буде важко читати.

Краще розділяти потоки за користувацькими цілями.

### Помилка 4. Показувати лише сторінки

Схема виду:

    Головна → Кабінет → Розклади → Редагування

показує переходи між сторінками, але не пояснює, що відбувається під час збереження, перевірки даних або виникнення помилки.

Для складних сценаріїв потрібно показувати також дії та точки прийняття рішень.

### Помилка 5. Ігнорувати стан системи

Потрібно визначити, що бачить користувач під час завантаження, після успіху, у разі помилки або за відсутності даних.

### Помилка 6. Не враховувати прямі посилання

Користувач може відкрити захищену сторінку напряму, а не через головну сторінку.

Потрібно продумати поведінку для неавторизованих користувачів і користувачів без необхідних прав.

### Помилка 7. Ускладнювати потік без потреби

Не потрібно моделювати кожен рух миші або кожне натискання клавіші.

Показуй кроки, які впливають на досягнення мети, переходи, рішення та важливі стани системи.

### Помилка 8. Вважати User Flow архітектурою

User Flow допомагає визначати поведінку системи, але сам по собі не описує повну архітектуру.

Він не замінює моделювання даних, проєктування API, визначення модулів або опис інфраструктури.

    ✔ Продумано поведінку для неавторизованого користувача.
    ✔ Враховано права доступу.
    ✔ Продумано Loading, Empty, Success та Error.
    ✔ Зрозуміло, куди користувач може перейти далі.
    ✔ Потік відповідає User Story та критеріям приймання.
    ✔ Схему можна прочитати без додаткових пояснень автора.

Цей список — практичний орієнтир. Не кожен пункт однаково важливий для кожного потоку.

### Приклад хорошої відповіді

**Запитання:** Навіщо розробнику User Flow?

    User Flow показує послідовність дій користувача
    та реакцій системи під час виконання конкретного завдання.

    Він допомагає спланувати навігацію, виявити зайві кроки,

    На його основі можна уточнити вимоги, розділити роботу
    між frontend і backend та підготувати тестові сценарії.

## 20. Мінішпаргалка

### User Flow

    Послідовність кроків, яка допомагає користувачу
    досягти конкретної мети.

### Основна структура

    Entry Point
        ↓
    Action
        ↓
    Decision Point
        ↓
    Branch
        ↓
    Result / Exit Point

### Типи потоків

    Happy Path — успішний сценарій.
    Error Flow — сценарій помилки.
    Authentication Flow — вхід до системи.
    CRUD Flow — створення, читання, оновлення, видалення.
    Onboarding Flow — початок роботи з продуктом.
    Search Flow — пошук інформації.

### Основні стани інтерфейсу

    Initial
    Loading
    Success
    Empty
    Error
    Disabled

### Суміжні поняття

    User Story:
        що потрібно користувачу і навіщо.

    User Flow:
        якими кроками користувач досягає мети.

    Use Case:
        як відбувається взаємодія із системою.

    Acceptance Criteria:
        як перевірити правильність результату.

    Sitemap:
        як організовані сторінки сайту.

    Wireframe:
        як структурований окремий екран.

### Практичний порядок роботи

    1. Визначити мету.
    2. Визначити початкову точку.
    3. Записати основні дії.
    4. Додати точки прийняття рішень.
    5. Продумати помилки та альтернативи.
    6. Визначити результат.
    7. Перевірити зручність і безпеку.
    8. Пов'язати потік із вимогами та тестами.

## 21. Головне, що потрібно запам'ятати

User Flow — це інструмент планування поведінки застосунку з погляду користувача.

Він допомагає відповісти на запитання:

- Звідки користувач починає?
- Що він робить далі?
- Як система реагує?
- Де можуть виникнути проблеми?
- Які альтернативні шляхи доступні?
- Як користувач розуміє, що завдання завершено?

Під час планування проєкту:

1. Починай із мети користувача, а не з компонентів інтерфейсу.
2. Спочатку опиши основний успішний сценарій.
3. Додай важливі альтернативи та помилки.
4. Враховуй стани інтерфейсу й поведінку backend.
5. Перевіряй права доступу для захищених операцій.
6. Не змішуй User Flow, User Journey, Use Case та Sitemap.
7. Пов'язуй потоки з вимогами та тестуванням.
8. Створюй окремі діаграми для складних незалежних сценаріїв.
9. Не деталізуй схему більше, ніж потрібно для розуміння поведінки.
10. Оновлюй документацію, коли змінюється функціональність.

**Ключова думка:** хороший User Flow допомагає спроєктувати шлях до результату ще до написання коду — разом з основними діями, альтернативами, помилками та зрозумілим завершенням.
