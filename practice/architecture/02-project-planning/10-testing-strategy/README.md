# Testing Strategy — Стратегія тестування

> **Testing Strategy** — це загальний план перевірки програмного забезпечення, який визначає, що потрібно тестувати, на яких рівнях, якими методами, у якій послідовності та за якими критеріями оцінювати якість результату.

Стратегія тестування допомагає відповісти на запитання:

- Що саме потрібно перевірити?
- Які типи тестів потрібні для проєкту?
- Що перевіряти автоматично, а що вручну?
- Де розміщувати тести?
- Як перевіряти взаємодію frontend, backend і database?
- Як переконатися, що користувач не може отримати доступ до чужих даних?
- Коли можна вважати функцію достатньо перевіреною?
- Як уникнути повторної появи вже виправлених помилок?

Головна мета — не написати якомога більше тестів, а **створити надійний спосіб перевіряти правильність роботи застосунку та зменшувати ризик помилок**.

---

## 1. Навіщо потрібна стратегія тестування

У невеликому навчальному проєкті може здаватися, що достатньо запустити застосунок і перевірити його в браузері.

Такий підхід допомагає на початку, але зі зростанням проєкту виникають проблеми:

- після зміни однієї функції перестає працювати інша;
- помилки з'являються лише за певних вхідних даних;
- frontend неправильно обробляє відповіді API;
- backend повертає неочікувані помилки;
- база даних отримує некоректні дані;
- неавторизований користувач може виконати заборонену операцію;
- виправлення однієї помилки випадково створює іншу.

Стратегія тестування допомагає визначити, як виявляти такі проблеми систематично.

### Основні переваги

- ✔ Раніше виявлення помилок.
- ✔ Менший ризик регресій після змін.
- ✔ Більша впевненість під час рефакторингу.
- ✔ Перевірка бізнес-правил незалежно від інтерфейсу.
- ✔ Контроль взаємодії компонентів.
- ✔ Перевірка безпеки та доступу до даних.
- ✔ Зрозумілі критерії готовності функцій.
- ✔ Можливість автоматично повторювати перевірки.

Важливо: **тести не доводять, що програма абсолютно позбавлена помилок**. Вони перевіряють конкретні властивості та сценарії, які ми визначили.

## 2. Місце Testing Strategy в архітектурі проєкту

Стратегія тестування пов'язана з вимогами, архітектурою та плануванням реалізації.

    Requirements
        ↓
    User Stories and Use Cases
        ↓
    Application Architecture
        ↓
    API Contracts
        ↓
    Implementation Planning
        ↓
    Testing Strategy
        ↓
    Implementation + Tests
        ↓
    Integration and Regression Testing
        ↓
    Deployment
        ↓
    Monitoring and Feedback

Це спрощена схема. У реальному проєкті тестування починається вже під час аналізу вимог і продовжується протягом усього життєвого циклу застосунку.

Наприклад, якщо вимога звучить так:

    Кожен користувач має доступ лише до власних розкладів.

Під час планування тестування потрібно одразу передбачити:

    - перевірку отримання власних розкладів;
    - перевірку доступу до чужого розкладу;
    - перевірку редагування чужого розкладу;
    - перевірку видалення чужого розкладу;
    - перевірку запитів без авторизації.

Такі сценарії краще визначити до завершення реалізації, а не після виявлення проблеми.

## 3. Основні поняття тестування

### 3.1. Test Strategy — стратегія тестування

Визначає загальний підхід до перевірки застосунку.

Наприклад:

    - критична бізнес-логіка покривається unit-тестами;
    - API перевіряється інтеграційними тестами;
    - основні користувацькі сценарії перевіряються E2E-тестами;
    - критичні функції додатково перевіряються вручну;
    - усі важливі зміни проходять перевірку перед розгортанням.

Стратегія описує принципи, а не кожен конкретний тест.

### 3.2. Test Plan — план тестування

Документ або список конкретних перевірок для певного етапу чи функції.

Наприклад:

    Feature: Створення розкладу

    Перевірити:
    - створення з валідними даними;
    - відхилення порожньої назви;
    - відхилення запиту без авторизації;
    - збереження правильного власника;
    - обробку помилки бази даних.

Стратегія відповідає на запитання «Як загалом ми тестуємо застосунок?», а план тестування — «Що конкретно перевіряємо для цієї функції?».

### 3.3. Test Case — тестовий випадок

Описує конкретну перевірку, її умови та очікуваний результат.

    Test Case: Створення розкладу

    Передумова:
    Користувач авторизований.

    Вхідні дані:
    title = "Недільний розклад"

    Дія:
    Надіслати запит на створення розкладу.

    Очікуваний результат:
    - сервер повертає успішну відповідь;
    - розклад зберігається в базі;
    - запис має правильного власника.

### 3.4. Test Suite — набір тестів

Група пов'язаних тестів.

Наприклад:

    Authentication Test Suite:
    - успішна реєстрація;
    - реєстрація з некоректними даними;
    - успішний вхід;
    - неправильний пароль;
    - вихід;
    - доступ до захищеного ресурсу.

### 3.5. Test Data — тестові дані

Дані, які використовуються під час перевірок.

Наприклад:

    User A:
    id = 1

    User B:
    id = 2

    Schedule A:
    user_id = 1

    Schedule B:
    user_id = 2

Ці дані дозволяють перевірити, чи правильно система розділяє ресурси різних користувачів.

### 3.6. Test Environment — тестове середовище

Середовище, у якому виконуються тести.

Це може бути:

- локальний комп'ютер;
- окрема тестова база даних;
- тимчасова тестова інфраструктура;
- CI-середовище;
- окреме staging-середовище.

Тестове середовище має бути достатньо схожим на реальне, щоб перевірки давали корисні результати.

## 4. Основні рівні тестування

Для вебзастосунків часто використовують чотири основні рівні:

1. Unit tests.
2. Integration tests.
3. End-to-end tests.
4. Manual testing.

Вони доповнюють одне одного та мають різні цілі.

---

## 5. Unit Testing — модульне тестування

**Unit test** перевіряє окрему невелику одиницю логіки ізольовано від більшості зовнішніх залежностей.

Це може бути:

- функція;
- метод класу;
- модуль бізнес-логіки;
- валідатор;
- перетворення даних;
- обчислення.

### Приклад

Припустимо, є функція перевірки назви розкладу.

    export function isValidScheduleTitle(title: string): boolean {
        return title.trim().length > 0;
    }

Для неї можна написати тести:

    import { describe, expect, it } from "vitest";
    import { isValidScheduleTitle } from "./schedule-validation";

    describe("isValidScheduleTitle", () => {
        it("accepts a non-empty title", () => {
            expect(isValidScheduleTitle("Sunday Schedule")).toBe(true);
        });

        it("rejects an empty title", () => {
            expect(isValidScheduleTitle("")).toBe(false);
        });

        it("rejects whitespace-only title", () => {
            expect(isValidScheduleTitle("   ")).toBe(false);
        });
    });

Приклад використовує TypeScript і Vitest. Для запуску потрібні відповідні залежності та налаштування проєкту.

### Що перевіряє unit-тест

    Вхідні дані → Функція → Очікуваний результат

Наприклад:

    ""       → isValidScheduleTitle → false
    "   "    → isValidScheduleTitle → false
    "Sunday" → isValidScheduleTitle → true

### Переваги

- швидке виконання;
- точне визначення місця помилки;
- просте тестування граничних випадків;
- зручність під час рефакторингу;
- можливість перевіряти бізнес-правила без браузера та сервера.

### Що не варто перевіряти unit-тестом

Не потрібно в кожному unit-тесті запускати справжню базу даних або відкривати браузер.

Якщо перевіряється SQL-запит, взаємодія з базою даних або повний HTTP-запит, імовірно, йдеться вже про інший рівень тестування.

### Коли unit-тести особливо корисні

- складна бізнес-логіка;
- валідація;
- форматування даних;
- обчислення;
- перетворення об'єктів;
- логіка дозволів;
- обробка граничних випадків.

## 6. Integration Testing — інтеграційне тестування

**Integration test** перевіряє, чи правильно взаємодіють кілька компонентів.

Наприклад:

    API endpoint
        ↓
    Service
        ↓
    PostgreSQL

Або:

    React Component
        ↓
    API Client
        ↓
    HTTP Response

Інтеграційні тести перевіряють не лише логіку окремої функції, а й взаємодію частин системи.

### Приклад для backend

Припустимо, endpoint створює розклад у PostgreSQL.

Інтеграційний тест може перевіряти:

    1. Надіслати HTTP-запит.
    2. Передати валідні дані.
    3. Дочекатися відповіді сервера.
    4. Перевірити HTTP-статус.
    5. Перевірити тіло відповіді.
    6. Переконатися, що запис з'явився в тестовій базі.
    7. Очистити тестові дані.

Для такого тесту можна використати Node.js test runner або Vitest разом із HTTP-тестовим інструментом, наприклад Supertest.

### Що перевіряють інтеграційні тести

- чи правильно endpoint викликає сервіс;
- чи правильно сервіс працює з базою даних;
- чи відповідає результат API-контракту;
- чи працює валідація на межі API;
- чи правильно обробляються помилки бази даних;
- чи застосовується авторизація;
- чи коректно працює транзакційна логіка, якщо вона використовується.

### Unit vs Integration

    Unit:
    Перевіряємо функцію окремо.

    Integration:
    Перевіряємо взаємодію кількох компонентів.

Наприклад, unit-тест може перевірити, що функція правильно визначає допустимість назви. Інтеграційний тест перевірить, що HTTP-запит із порожньою назвою отримує очікувану помилку та не створює запис у базі.

## 7. End-to-End Testing — наскрізне тестування

**E2E test** перевіряє повний сценарій роботи системи з погляду користувача.

Для вебзастосунку такий тест може включати браузер, frontend, backend і базу даних.

    Користувач
        ↓
    Browser
        ↓
    Frontend
        ↓
    API
        ↓
    Backend
        ↓
    Database

### Приклад сценарію

    1. Відкрити сторінку входу.
    2. Увійти до облікового запису.
    3. Відкрити список розкладів.
    4. Створити новий розклад.
    5. Переконатися, що він відображається.
    6. Відкрити його редагування.
    7. Змінити назву.
    8. Переконатися, що зміна збережена.

E2E-тести можуть виконуватися за допомогою Playwright або Cypress.

### Переваги

- перевіряють реальний користувацький сценарій;
- виявляють помилки інтеграції;
- перевіряють взаємодію інтерфейсу із сервером;
- допомагають перевірити критичні сценарії перед випуском.

### Недоліки

- зазвичай повільніші за unit-тести;
- потребують більшого налаштування;
- можуть бути нестабільними через таймінги або стан середовища;
- складніше визначити точне місце помилки.

Тому E2E-тести варто використовувати для найважливіших сценаріїв, а не обов'язково для кожної дрібної умови.

---

## 8. Manual Testing — ручне тестування

**Manual testing** — перевірка поведінки застосунку людиною без обов'язкового автоматизованого тестового сценарію.

Наприклад:

    - відкрити сайт у браузері;
    - пройти сценарій реєстрації;
    - перевірити вигляд форми;
    - змінити розмір вікна;
    - перевірити повідомлення про помилки;
    - оцінити зрозумілість інтерфейсу;
    - перевірити поведінку з клавіатури.

Ручне тестування корисне для оцінки:

- зручності інтерфейсу;
- візуального вигляду;
- зрозумілості повідомлень;
- доступності;
- поведінки на різних пристроях;
- сценаріїв, які ще не автоматизовані.

Однак ручні перевірки складно повторювати абсолютно однаково після кожної зміни. Тому стабільні та важливі сценарії поступово варто автоматизувати.

## 9. Test Pyramid — піраміда тестування

Піраміда тестування — це модель, яка показує приблизний розподіл тестів за рівнями.

    /\
    /  \       E2E
    /----\      Невелика кількість
    /      \
    /--------\  Integration
    /          \ Помірна кількість
    /------------\
    /              \ Unit
    /________________\ Багато швидких тестів

Це концептуальна модель, а не обов'язкова пропорція для кожного проєкту.

### Unit tests

Зазвичай їх багато, тому що вони швидкі та перевіряють окремі правила.

### Integration tests

Перевіряють взаємодію компонентів, API та бази даних.

### E2E tests

Зазвичай їх менше, але вони охоплюють критичні сценарії користувача.

### Чому не варто покладатися лише на E2E

Якщо єдиний тест перевіряє повний сценарій, а він падає, може бути важко визначити причину:

- неправильна валідація;
- помилка backend;
- проблема бази даних;
- неправильна відповідь API;
- проблема frontend.

Unit- та інтеграційні тести допомагають локалізувати помилку.

### Чи потрібно суворо дотримуватися піраміди?

Ні. Конкретний розподіл залежить від архітектури та ризиків.

Для простого сайту з невеликою кількістю бізнес-логіки можна мати відносно мало unit-тестів і більше перевірок на рівні компонентів. Для складної серверної логіки кількість unit- та інтеграційних тестів може бути значно більшою.

## 10. Functional Testing — функціональне тестування

**Functional testing** перевіряє, чи виконує система вимоги та очікувану поведінку.

Приклади для Worship Schedule:

    - користувач може створити розклад;
    - користувач може переглянути список;
    - користувач може змінити назву;
    - користувач може видалити розклад;
    - некоректні дані відхиляються;
    - після збереження зміни не зникають.

Функціональне тестування описує, що саме перевіряється, а не обов'язково яким технічним способом.

Його можна виконувати через unit-тести, інтеграційні тести, E2E-тести або вручну.

---

## 11. Non-functional Testing — нефункціональне тестування

Нефункціональне тестування перевіряє не лише правильність функцій, а й інші характеристики системи.

Основні напрями:

### Performance Testing

Перевіряє швидкість і продуктивність.

    Приклади:
    - час відповіді API;
    - швидкість завантаження сторінки;
    - поведінка при великій кількості записів.

### Security Testing

Перевіряє захищеність системи.

    Приклади:
    - доступ до чужих розкладів;
    - обхід авторизації;
    - некоректна обробка введених даних;
    - розкриття секретів;
    - небезпечне відображення користувацького вмісту.

### Accessibility Testing

Перевіряє доступність інтерфейсу.

    Приклади:
    - керування клавіатурою;
    - видимість фокуса;
    - доступні назви полів;
    - контрастність;
    - зрозумілі повідомлення про помилки.

### Compatibility Testing

Перевіряє роботу в різних середовищах.

    Приклади:
    - різні браузери;
    - мобільні та настільні екрани;
    - різні розміри вікна.

### Reliability Testing

Перевіряє здатність системи стабільно працювати.

    Приклади:
    - обробка тимчасових помилок;
    - відновлення після перезапуску;
    - коректна поведінка, коли база недоступна.

Для навчального MVP не обов'язково виконувати повномасштабні навантажувальні перевірки, але критичні питання безпеки, доступності та надійності потрібно враховувати.

---

## 12. Regression Testing — регресійне тестування

**Regression testing** — перевірка того, що нові зміни не зламали функціональність, яка раніше працювала.

Наприклад:

    Було:
    - створення розкладу працює;
    - редагування працює.

    Змінили:
    - структуру таблиці schedules;
    - формат API-відповіді.

    Потрібно повторно перевірити:
    - створення;
    - перегляд;
    - редагування;
    - видалення;
    - відображення даних у frontend.

Регресійні перевірки можуть бути ручними або автоматизованими.

### Чому автоматизація важлива

Без автоматизованих тестів після кожної зміни доводиться повторювати багато однакових дій вручну.

Автоматизований набір тестів дозволяє швидко перевірити критичні функції після:

- зміни моделі даних;
- рефакторингу;
- оновлення залежностей;
- зміни API;
- додавання нових функцій.

---

## 13. Smoke Testing і Sanity Testing

Ці поняття часто використовують під час перевірки нових збірок або змін.

### Smoke Testing

**Smoke testing** — коротка перевірка, що основні частини системи запускаються та працюють на базовому рівні.

Наприклад:

    - застосунок запускається;
    - головна сторінка відкривається;
    - сервер відповідає;
    - база даних доступна;
    - користувач може увійти.

Мета — швидко виявити критичну проблему, яка робить подальше тестування недоцільним.

### Sanity Testing

**Sanity testing** — вузька перевірка, що конкретна зміна або виправлення працює так, як очікується.

Наприклад:

    Виправлено помилку редагування розкладу.

    Перевірити:
    - редагування працює;
    - змінені дані зберігаються;
    - оновлені дані показуються після повторного відкриття.

У різних командах ці терміни можуть використовуватися дещо по-різному.

---

## 14. Positive Testing і Negative Testing

### Positive Testing

Перевіряє поведінку системи з коректними вхідними даними.

    Приклад:
    title = "Недільний розклад"

    Очікування:
    Розклад успішно створюється.

### Negative Testing

Перевіряє поведінку системи з некоректними даними або забороненими діями.

    Приклади:
    - порожня назва;
    - відсутній обов'язковий параметр;
    - неправильний формат даних;
    - запит без авторизації;
    - доступ до чужого запису;
    - неіснуючий ідентифікатор.

Очікування — система безпечно та передбачувано обробляє ситуацію.

Negative testing особливо важливе для API та функцій, що працюють із приватними даними.

---

## 15. Boundary Testing — тестування граничних значень

Багато помилок виникають на межах допустимих значень.

Припустимо, назва розкладу має бути від 1 до 200 символів після обрізання пробілів.

Тоді потрібно перевірити:

    0 символів:
    "" → відхилити.

    1 символ:
    "A" → прийняти.

    200 символів:
    довжина 200 → прийняти.

    201 символ:
    довжина 201 → відхилити.

Якщо правило визначає довжину після обрізання пробілів, це потрібно перевірити окремо.

### Що варто тестувати на межах

- мінімальну та максимальну довжину;
- нульові значення;
- порожні рядки;
- порожні масиви;
- відсутні поля;
- дуже великі значення;
- мінімальні та максимальні числові межі;
- граничні дати;
- кількість елементів на сторінці.

Для більшості валідацій достатньо перевірити значення нижче межі, на межі та вище межі.

---

## 16. API Testing — тестування API

API-тестування перевіряє, чи правильно сервер приймає запити та повертає відповіді.

Для endpoint потрібно перевірити:

- HTTP-метод;
- URL;
- заголовки;
- формат запиту;
- валідацію;
- статус відповіді;
- формат тіла відповіді;
- обробку помилок;
- автентифікацію;
- авторизацію;
- побічні ефекти в базі даних.

### Приклад контракту

    POST /api/schedules

    Request:
    {
        "title": "Недільний розклад",
        "content": "08:00 — Літургія"
    }

    Успішний результат:
    201 Created

    {
        "id": 42,
        "title": "Недільний розклад",
        "content": "08:00 — Літургія"
    }

Це умовний приклад. Фактичний формат залежить від API-контракту проєкту.

### Перелік перевірок

    1. Валідний запит.
    2. Відсутня назва.
    3. Назва неправильного типу.
    4. Назва перевищує дозволену довжину.
    5. Відсутня авторизація.
    6. Некоректний формат JSON.
    7. Помилка бази даних.
    8. Перевірка власника створеного запису.

API-тести можна виконувати через тестовий код, HTTP-клієнт або спеціалізовані інструменти.

---

## 17. Database Testing — тестування бази даних

База даних є частиною поведінки застосунку, тому її потрібно перевіряти окремо.

### Що перевіряти

- правильність SQL-запитів;
- відповідність типів даних;
- обов'язкові поля;
- унікальні обмеження;
- зовнішні ключі;
- каскадні операції, якщо вони використовуються;
- транзакції;
- коректне збереження й читання;
- ізоляцію даних користувачів.

### Приклад перевірки приватності

    User A:
    id = 1

    User B:
    id = 2

    Schedule:
    id = 10
    user_id = 1

    Очікування:
    User A може отримати доступ до schedule 10.
    User B не може отримати доступ до schedule 10.

Перевірка лише в frontend недостатня. Backend повинен перевіряти права доступу незалежно від того, як працює інтерфейс.

### Чому потрібна окрема тестова база

Не варто запускати тести, які створюють, змінюють або видаляють записи, на базі з реальними даними.

Краще використовувати окрему тестову базу, яку можна безпечно очищати та заповнювати тестовими даними.

---

## 18. Frontend Testing — тестування інтерфейсу

Frontend-тестування перевіряє поведінку компонентів та інтерфейсу.

### Що перевіряти

- правильне відображення даних;
- реакцію на натискання кнопок;
- введення та валідацію форм;
- стани завантаження;
- відображення помилок;
- порожні стани;
- навігацію;
- доступність елементів;
- обробку відповідей API.

### Приклад сценарію форми

    1. Відкрити форму створення розкладу.
    2. Залишити назву порожньою.
    3. Натиснути «Зберегти».
    4. Переконатися, що показано повідомлення про помилку.

Важливо також перевірити backend-валідацію. Перевірка у frontend потрібна для зручності користувача, але її можна обійти прямим HTTP-запитом.

### Інструменти для React

Для тестування React-компонентів часто використовують:

- Vitest або Jest — тестовий runner;
- React Testing Library — перевірка поведінки компонентів;
- Playwright або Cypress — наскрізні браузерні сценарії.

Не потрібно встановлювати всі інструменти одразу. Починай із того набору, який відповідає поточній архітектурі та навчальним цілям.

---

## 19. Contract Testing — перевірка контрактів

Contract testing перевіряє, чи відповідає взаємодія між компонентами погодженому контракту.

Наприклад, frontend очікує:

    {
        "id": 42,
        "title": "Недільний розклад",
        "content": "08:00 — Літургія"
    }

А backend випадково починає повертати:

    {
        "scheduleId": 42,
        "name": "Недільний розклад",
        "content": "08:00 — Літургія"
    }

Навіть якщо сервер працює без помилок, frontend може перестати відображати назву.

Contract testing допомагає виявляти такі несумісності.

### Що можна перевіряти

- обов'язкові поля;
- типи даних;
- структуру відповіді;
- формати помилок;
- HTTP-статуси;
- сумісність frontend із backend;
- відповідність документації реальній поведінці.

Для невеликого застосунку достатньо почати з тестів API-контрактів та перевірки схем запитів і відповідей. Складніші consumer-driven contract testing інструменти потрібні не кожному проєкту.

---

## 20. Security Testing — перевірка безпеки

Для застосунку з приватними розкладами перевірка безпеки є обов'язковою частиною стратегії.

### Основні сценарії

    Authentication:
    - користувач не авторизований;
    - користувач передає неправильні облікові дані;
    - користувач намагається отримати захищений ресурс.

    Authorization:
    - користувач A читає власний розклад;
    - користувач B намагається прочитати розклад A;
    - користувач B намагається змінити розклад A;
    - користувач B намагається видалити розклад A.

    Input validation:
    - неправильний тип даних;
    - надто довгі значення;
    - відсутні поля;
    - небезпечний вміст.

    Error handling:
    - сервер не розкриває секрети;
    - відповіді не містять зайвих внутрішніх деталей;
    - помилки не призводять до витоку приватних даних.

### Особливо важливо: IDOR

**IDOR (Insecure Direct Object Reference)** — клас помилок контролю доступу, коли користувач може отримати доступ до чужого об'єкта, підставивши інший ідентифікатор.

Наприклад:

    GET /api/schedules/10

Якщо розклад із ID 10 належить іншому користувачу, сервер не повинен повертати його лише тому, що запит містить правильний ID.

Перевірка власника має виконуватися на сервері.

### Принцип тестування приватності

Перевіряй не лише успішні сценарії, а й заборонені дії.

Для системи приватних розкладів тестування доступу до чужих даних не є необов'язковим покращенням — це одна з ключових перевірок правильності реалізації.

## 21. Test Coverage — покриття тестами

**Test coverage** — показник того, яка частина коду або поведінки була виконана під час тестів.

Поширені види покриття:

### Line Coverage

Які рядки коду були виконані.

### Statement Coverage

Які інструкції були виконані.

### Branch Coverage

Які гілки умовної логіки були пройдені.

### Function Coverage

Які функції були викликані.

### Приклад

    function getAccessMessage(isOwner: boolean): string {
        if (isOwner) {
            return "Allowed";
        }

        return "Forbidden";
    }

Якщо тест перевіряє лише `isOwner = true`, одна гілка буде виконана, але друга залишиться неперевіреною.

Потрібно перевірити обидва варіанти:

    getAccessMessage(true)  → "Allowed"
    getAccessMessage(false) → "Forbidden"

### Чи потрібно прагнути до 100% coverage?

Не обов'язково.

Високий відсоток покриття не гарантує, що тести перевіряють правильні результати.

Наприклад, тест може викликати функцію, але не перевіряти її результат.

Корисніше запитати:

- Чи перевірено критичну бізнес-логіку?
- Чи перевірено граничні значення?
- Чи перевірено негативні сценарії?
- Чи перевірено права доступу?
- Чи перевірено основні інтеграції?

Покриття — це індикатор, а не самостійна мета якості.

---

## 22. Flaky Tests — нестабільні тести

**Flaky test** — тест, який за однакових умов іноді проходить, а іноді падає.

Причини можуть бути такими:

- залежність від часу;
- випадкові дані;
- неконтрольований порядок виконання;
- паралельні тести, що змінюють одні дані;
- очікування фіксованої затримки;
- зовнішній сервіс;
- залишкові дані від попередніх тестів.

### Приклад проблемного підходу

    await new Promise((resolve) => setTimeout(resolve, 1000));

    // Припускаємо, що операція вже завершилася.

Такий підхід ненадійний: операція може тривати довше або завершитися раніше.

Краще очікувати конкретний результат операції або використовувати механізми очікування, які надає тестовий інструмент.

### Як зменшити нестабільність

- ізолювати тестові дані;
- очищати стан після тестів;
- не залежати від порядку виконання;
- контролювати час і випадковість;
- не використовувати реальні зовнішні сервіси без потреби;
- очікувати конкретні події або стани;
- усувати причину нестабільності, а не просто багаторазово перезапускати тест.

---

## 23. Test Doubles: mocks, stubs і fakes

Під час unit-тестування іноді потрібно замінити реальну залежність контрольованим об'єктом.

Для цього використовують test doubles — замінники реальних компонентів.

### Stub

Повертає заздалегідь визначений результат.

    Приклад:
    Сервіс замість реального API повертає
    заздалегідь підготовлений список розкладів.

### Mock

Дозволяє перевірити взаємодію з залежністю, наприклад чи був виклик із потрібними аргументами.

    Приклад:
    Перевірити, що сервіс викликав метод
    з ідентифікатором поточного користувача.

### Fake

Спрощена робоча реалізація, яка замінює справжню залежність.

    Приклад:
    Тимчасове сховище в пам'яті замість бази даних
    у простому unit-тесті.

Ці терміни можуть мати різні нюанси залежно від тестового фреймворку.

### Коли використовувати

Замінники корисні, коли потрібно ізолювати логіку від зовнішньої системи.

Але не варто замінювати абсолютно все. Якщо тест перевіряє взаємодію з PostgreSQL, використання лише mock-об'єкта не підтвердить, що реальний SQL-запит працює правильно.

---

## 24. Test Environment і тестові дані

Надійні тести залежать від передбачуваного середовища.

### Рекомендації

- використовуй окрему тестову базу даних;
- не підключай автоматичні тести до production-бази;
- не зберігай реальні паролі та секрети в тестових файлах;
- створюй потрібні дані перед тестом;
- очищай або ізолюй дані після тесту;
- не покладайся на порядок виконання тестів;
- фіксуй необхідні версії середовища;
- перевіряй, що тести можна запускати повторно.

### Приклад змінних середовища

    # .env.test
    NODE_ENV=test
    DATABASE_URL=postgres://test_user:test_password@localhost:5432/worship_schedule_test

Це лише приклад. Не потрібно використовувати ці вигадані облікові дані як реальні секрети.

Файл із секретами зазвичай не додають до Git. Для CI змінні налаштовують у конфігурації середовища, а локальні значення зберігають відповідно до правил проєкту.

## 25. Continuous Integration — автоматичний запуск тестів

**Continuous Integration (CI)** — практика регулярного інтегрування змін із автоматичними перевірками.

Наприклад, після створення pull request або надсилання змін до репозиторію CI може виконати:

    1. Встановлення залежностей.
    2. Перевірку форматування.
    3. Статичний аналіз коду.
    4. Перевірку TypeScript.
    5. Unit-тести.
    6. Інтеграційні тести.
    7. Збірку застосунку.

Якщо критична перевірка не проходить, проблему можна виявити до розгортання.

### Приклад локальних команд

Конкретні команди залежать від налаштувань `package.json`.

    npm run lint
    npm run typecheck
    npm test
    npm run build

Не кожен проєкт має всі ці скрипти. Їх потрібно додати та налаштувати відповідно до вибраних інструментів.

### Чому CI корисний навіть для одного розробника

- перевірки виконуються однаково;
- легше помітити помилку після змін;
- зменшується залежність від пам'яті;
- зручніше працювати з кількох комп'ютерів;
- можна перевірити, що проєкт збирається в чистому середовищі.

## 26. Testing Strategy для Worship Schedule

Розглянемо практичну стратегію для застосунку, у якому користувачі створюють і редагують приватні розклади.

### 26.1. Основні ризики

    1. Користувач не може увійти.
    2. Дані не зберігаються.
    3. Після редагування показується стара версія.
    4. Користувач може прочитати чужий розклад.
    5. Користувач може змінити чужий розклад.
    6. Некоректні дані спричиняють помилки.
    7. Frontend не обробляє помилку сервера.
    8. Після розгортання відсутні потрібні змінні середовища.

### 26.2. Unit-тести

    - правила валідації назви;
    - перевірка допустимого вмісту;
    - перетворення даних;
    - формування повідомлень;
    - правила бізнес-логіки.

### 26.3. Інтеграційні тести

    - створення розкладу в PostgreSQL;
    - отримання списку;
    - редагування запису;
    - видалення запису;
    - перевірка API-статусів;
    - перевірка авторизації;
    - перевірка прав власника.

### 26.4. E2E-тести

    - реєстрація та вхід;
    - створення розкладу;
    - перегляд розкладу;
    - редагування;
    - видалення;
    - вихід із системи.

### 26.5. Ручні перевірки

    - зрозумілість форм;
    - робота клавіатурної навігації;
    - адаптивність;
    - видимість повідомлень;
    - читабельність тексту;
    - загальний користувацький досвід.

### 26.6. Перед розгортанням

    - критичні тести проходять;
    - production-збірка успішна;
    - конфігурація перевірена;
    - секрети не потрапили до репозиторію;
    - доступ до приватних даних перевірений;
    - основні сценарії працюють у production-середовищі.

Ця стратегія достатньо проста для першої версії та може розширюватися в міру розвитку проєкту.

## 27. Приклад тест-плану для функції створення розкладу

    # Test Plan: Create Schedule

    ## Goal
    Перевірити, що авторизований користувач може
    створити приватний розклад.

    ## Preconditions
    - сервер працює;
    - тестова база даних доступна;
    - користувач авторизований.

    ## Test Cases

    ### TC-01: Valid input
    Input:
    title = "Недільний розклад"

    Expected:
    - запит успішний;
    - запис створено;
    - власник визначений правильно.

    ### TC-02: Empty title
    Input:
    title = ""

    Expected:
    - запит відхилено;
    - запис не створено.

    ### TC-03: Missing authentication
    Input:
    Запит без авторизації.

    Expected:
    - запит відхилено;
    - запис не створено.

    ### TC-04: Invalid title type
    Input:
    title = 123

    Expected:
    - вхідні дані відхилено;
    - сервер повертає очікувану помилку.

    ### TC-05: Ownership
    Input:
    Користувач A створює розклад.

    Expected:
    - розклад належить користувачу A;
    - користувач B не отримує доступ до цього запису.

    ## Completion Criteria
    - критичні сценарії перевірено;
    - помилки обробляються;
    - приватність даних підтверджена;
    - результати тестів задокументовані за потреби.

## 28. Як організувати тести у файловій структурі

Структура залежить від фреймворків і архітектури.

Один із можливих варіантів для TypeScript-застосунку:

    project/
    ├── src/
    │   ├── modules/
    │   │   └── schedules/
    │   │       ├── schedule.service.ts
    │   │       ├── schedule.validation.ts
    │   │       └── schedule.validation.test.ts
    │   └── ...
    ├── tests/
    │   ├── integration/
    │   │   └── schedules.test.ts
    │   └── e2e/
    │       └── schedule-workflow.spec.ts
    ├── docs/
    │   └── testing-strategy.md
    ├── package.json
    └── README.md

У цьому варіанті:

- unit-тести розміщені поряд із кодом;
- інтеграційні тести зібрані в окремому каталозі;
- E2E-тести перевіряють сценарії користувача;
- стратегія тестування описана в документації.

Інший проєкт може зберігати всі тести в окремому каталозі. Обирай одну зрозумілу структуру та дотримуйся її послідовно.

Не потрібно створювати всі ці каталоги заздалегідь, якщо відповідних тестів поки немає.

## 29. Як планувати тестування перед реалізацією

Для кожної функції бажано визначити перевірки ще на етапі планування.

Наприклад, для функції редагування розкладу:

### Крок 1. Визначити очікувану поведінку

    Авторизований власник може змінити назву та вміст
    власного розкладу.

### Крок 2. Визначити позитивні сценарії

    - назва змінюється;
    - вміст змінюється;
    - зміни зберігаються після повторного читання.

### Крок 3. Визначити негативні сценарії

    - неавторизований користувач не може редагувати;
    - інший користувач не може редагувати;
    - невалідні дані відхиляються;
    - неіснуючий запис обробляється коректно.

### Крок 4. Вибрати рівень тестування

    Unit:
    Перевірка правил валідації.

    Integration:
    Перевірка API, бази даних та прав доступу.

    E2E:
    Перевірка сценарію редагування через браузер.

### Крок 5. Визначити критерії завершення

    - критичні сценарії перевірені;
    - результат відповідає контракту;
    - дані зберігаються правильно;
    - перевірки доступу проходять.

Так тестування стає частиною розробки, а не окремою діяльністю, яку згадують лише наприкінці.

## 30. Часті помилки під час побудови стратегії тестування

### Помилка 1. Тестувати лише успішні сценарії

Перевірка тільки правильних даних не виявляє багатьох помилок.

Потрібно також тестувати некоректні дані, відсутність авторизації, неіснуючі записи та заборонені дії.

### Помилка 2. Вважати, що ручної перевірки достатньо

Ручне тестування корисне, але повторювати всі перевірки після кожної зміни складно.

Критичні та стабільні сценарії варто поступово автоматизувати.

### Помилка 3. Писати багато тестів без перевірки результату

Тест, який лише викликає функцію, але нічого не перевіряє, має обмежену цінність.

Тест повинен мати зрозумілий очікуваний результат.

### Помилка 4. Перевіряти лише frontend-валідацію

Frontend можна обійти. Backend повинен незалежно перевіряти вхідні дані та права доступу.

### Помилка 5. Використовувати production-базу для тестів

Автоматичні тести можуть створювати, змінювати або видаляти дані. Потрібне окреме тестове середовище.

### Помилка 6. Прагнути до 100% coverage будь-якою ціною

Відсоток покриття не гарантує якості тестів. Важливіше перевірити критичну поведінку та граничні випадки.

### Помилка 7. Створювати лише E2E-тести

E2E-тести корисні, але можуть бути повільними й складними для налагодження. Їх варто доповнювати unit- та інтеграційними тестами.

### Помилка 8. Ігнорувати нестабільні тести

Тести, які випадково падають, зменшують довіру до всієї тестової системи. Причину нестабільності потрібно знаходити та виправляти.

### Помилка 9. Тестувати реалізацію замість поведінки

Тест не повинен ламатися після кожного внутрішнього рефакторингу, якщо зовнішня поведінка залишилася правильною.

Переважно перевіряй результати, контракти та важливі взаємодії, а не внутрішні деталі, які не є частиною вимог.

### Помилка 10. Не запускати тести перед інтеграцією

Навіть якщо тести існують, вони не допомагають, коли їх ніхто не запускає.

Автоматичний запуск через CI зменшує ризик пропустити помилку.

## 31. Мінімальна стратегія тестування для Junior Full Stack Developer

На початку не потрібно відразу створювати складну тестову інфраструктуру.

Для невеликого застосунку можна почати так:

### Рівень 1. Unit-тести

Перевіряти:

    - валідацію;
    - бізнес-правила;
    - перетворення даних;
    - важливі умовні гілки.

### Рівень 2. Інтеграційні тести

Перевіряти:

    - основні API endpoints;
    - роботу з PostgreSQL;
    - обробку помилок;
    - авторизацію;
    - права власника.

### Рівень 3. E2E-тести

Автоматизувати найважливіші сценарії:

    - вхід;
    - створення розкладу;
    - редагування;
    - видалення.

### Рівень 4. Ручні перевірки

Перевіряти:

    - візуальний вигляд;
    - адаптивність;
    - клавіатурну навігацію;
    - зрозумілість повідомлень;
    - роботу на опублікованому сайті.

### Рівень 5. CI

Налаштувати автоматичний запуск доступних перевірок перед інтеграцією змін.

Для початку цього достатньо, щоб сформувати практичне розуміння тестування без надмірної складності.

## 32. Інструменти тестування в JavaScript / TypeScript

Вибір залежить від технологічного стеку.

### Unit та Integration

- **Vitest** — тестовий runner, який часто використовують у TypeScript- і frontend-проєктах.
- **Jest** — поширений тестовий runner.
- **Node.js test runner** — вбудований інструмент тестування Node.js.
- **Supertest** — інструмент для HTTP-тестування Node.js-застосунків.

### React

- **React Testing Library** — перевірка поведінки React-компонентів.
- **Vitest** або **Jest** — виконання тестів.

### E2E

- **Playwright** — автоматизація браузера та наскрізні тести.
- **Cypress** — автоматизоване тестування вебзастосунків.

### API та контракти

- HTTP-клієнти для ручної перевірки API;
- схеми валідації для перевірки запитів і відповідей;
- OpenAPI для документування контрактів;
- автоматизовані тести API.

Не потрібно використовувати всі інструменти одночасно. Для навчального проєкту краще обрати мінімальний набір і добре зрозуміти його.

## 33. Testing Strategy та Code Quality — не одне й те саме

Тестування — лише одна частина забезпечення якості коду.

Інші практики:

    Type Checking:
    Виявлення помилок типів до виконання програми.

    Linting:
    Виявлення потенційних помилок і проблем стилю.

    Formatting:
    Єдиний формат коду.

    Code Review:
    Перевірка змін іншою людиною або самим розробником.

    Static Analysis:
    Аналіз коду без його звичайного виконання.

    Testing:
    Перевірка поведінки програми за конкретних умов.

Ці практики доповнюють одна одну.

Наприклад, TypeScript може виявити неправильний тип аргументу, але не гарантує, що користувач не отримає доступ до чужого розкладу. Для цього потрібні перевірки логіки та прав доступу.

## 34. Чекліст перед завершенням функції

Для кожної важливої функції можна використовувати такий короткий чекліст.

    [ ] Визначені критерії прийнятності.
    [ ] Перевірені основні позитивні сценарії.
    [ ] Перевірені негативні сценарії.
    [ ] Перевірені граничні значення.
    [ ] Backend перевіряє вхідні дані.
    [ ] Права доступу перевіряються на сервері.
    [ ] API відповідає погодженому контракту.
    [ ] Дані правильно зберігаються.
    [ ] Помилки обробляються передбачувано.
    [ ] Необхідні автоматизовані тести проходять.
    [ ] Перевірено інтеграцію з іншими компонентами.
    [ ] Критичний сценарій перевірений у застосунку.
    [ ] Документація оновлена за потреби.

Не кожен пункт однаково важливий для кожної функції, але для роботи з приватними даними перевірки доступу та збереження мають особливе значення.

## 36. Мінішпаргалка

    Testing Strategy
        Загальний підхід до перевірки якості застосунку.

    Test Plan
        План перевірок для конкретної функції або етапу.

    Test Case
        Конкретний сценарій із передумовами та очікуваним результатом.

    Test Suite
        Набір пов'язаних тестів.

    Unit Testing
        Перевірка окремої одиниці логіки.

    Integration Testing
        Перевірка взаємодії компонентів.

    E2E Testing
        Перевірка повного користувацького сценарію.

    Manual Testing
        Перевірка людиною без обов'язкової автоматизації.

    Regression Testing
        Перевірка, що нові зміни не зламали стару функціональність.

    Smoke Testing
        Швидка перевірка базової працездатності системи.

    Negative Testing
        Перевірка некоректних даних і заборонених дій.

    Boundary Testing
        Перевірка значень на межах допустимого діапазону.

    Test Coverage
        Показник того, яка частина коду або логіки
        виконувалася під час тестів.

    Flaky Test
        Тест, результат якого нестабільний за однакових умов.

    CI
        Автоматичний запуск перевірок під час інтеграції змін.

    Основний принцип
        Перевіряй не лише те, що повинно працювати,
        а й те, що система повинна відхиляти.

## 37. Що потрібно запам'ятати

- Стратегія тестування визначає, як систематично перевіряти якість застосунку.
- Unit-тести допомагають перевіряти окрему логіку.
- Інтеграційні тести перевіряють взаємодію компонентів.
- E2E-тести перевіряють повні сценарії користувача.
- Ручне тестування залишається корисним для інтерфейсу, доступності та дослідницьких перевірок.
- Позитивні сценарії потрібно доповнювати негативними та граничними.
- Для приватних даних особливо важливо перевіряти авторизацію й права власника.
- Test coverage допомагає оцінювати охоплення коду, але не замінює якісних перевірок.
- Автоматизація та CI допомагають виявляти регресії.
- Тестування потрібно планувати разом із реалізацією, а не залишати на завершення проєкту.
- Не потрібно одразу будувати складну тестову інфраструктуру: починай із критичної логіки, API та основних сценаріїв.

**Головна думка:** хороша стратегія тестування визначає не кількість тестів, а те, які ризики потрібно перевірити, яким способом і з якими очікуваними результатами.
