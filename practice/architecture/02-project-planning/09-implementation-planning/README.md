# Implementation Planning — Планування реалізації

> **Implementation Planning** — це процес перетворення вимог, моделей даних, архітектурних рішень та API-контрактів на конкретний план розробки: які завдання потрібно виконати, у якій послідовності, які компоненти створити, як перевірити результат і як поступово отримати готовий продукт.

Планування реалізації відповідає на запитання:

- Що саме потрібно розробити?
- На які невеликі завдання розділити роботу?
- У якій послідовності виконувати завдання?
- Які компоненти залежать від інших?
- Як перевіряти кожен етап?
- Як зрозуміти, що функція готова?
- Що реалізувати спочатку, а що залишити на потім?

Головна мета — не просто написати список завдань, а створити **реалістичний і зрозумілий шлях від задуму до працюючого застосунку**.

---

## 1. Навіщо потрібне планування реалізації

Після визначення вимог і приблизної архітектури ще не завжди зрозуміло, з чого починати програмування.

Наприклад, для застосунку Worship Schedule потрібно реалізувати:

- реєстрацію та вхід користувачів;
- створення розкладів;
- редагування розкладів;
- збереження даних у PostgreSQL;
- перегляд власних розкладів;
- захист приватних даних;
- розгортання застосунку.

Якщо одразу почати програмувати, можна зіткнутися з проблемами:

- інтерфейс створений раніше, ніж визначено структуру даних;
- frontend очікує API, якого ще немає;
- різні компоненти використовують несумісні формати даних;
- функція реалізована, але її складно перевірити;
- важливі вимоги безпеки згадуються лише наприкінці;
- другорядні можливості забирають час, необхідний для основного функціоналу.

План реалізації допомагає уникнути хаотичної розробки.

### Основні переваги

- ✔ Робота поділяється на невеликі зрозумілі завдання.
- ✔ Визначається логічна послідовність розробки.
- ✔ Залежності між завданнями стають очевидними.
- ✔ Ризики виявляються раніше.
- ✔ Легше оцінювати прогрес.
- ✔ Простіше тестувати окремі функції.
- ✔ Менше непотрібної роботи та переробок.
- ✔ Легше продовжити проєкт після перерви.

## 2. Місце Implementation Planning у розробці

Планування реалізації пов'язане з попередніми етапами проєктування.

    Requirements
        ↓
    User Stories and Use Cases
        ↓
    User Flows and Screen Planning
        ↓
    Domain and Data Modeling
        ↓
    Application Architecture
        ↓
    API Contracts
        ↓
    Implementation Planning
        ↓
    Development
        ↓
    Testing
        ↓
    Deployment

Це спрощена схема, а не обов'язково сувора послідовність. У реальному проєкті етапи часто повторюються: під час реалізації можуть виявитися нові вимоги, проблеми архітектури або необхідність змінити API.

### Що вже має бути відомо

До початку детального планування бажано мати:

- основні вимоги до продукту;
- перелік користувацьких сценаріїв;
- приблизний список екранів;
- модель основних сутностей і зв'язків;
- обрану архітектуру застосунку;
- основні API-контракти;
- вимоги до безпеки та доступу до даних.

Не обов'язково мати повністю готову документацію. Достатньо визначити ключові рішення, без яких неможливо правильно розбити роботу на завдання.

## 3. Основні поняття

### 3.1. Feature — функціональна можливість

**Feature** — це можливість, яку застосунок надає користувачу.

Приклади для Worship Schedule:

- реєстрація;
- вхід до облікового запису;
- створення розкладу;
- редагування розкладу;
- видалення розкладу;
- перегляд списку розкладів;
- вихід з облікового запису.

Feature описує результат для користувача, а не конкретний файл або функцію в коді.

Наприклад:

    Feature: Створення розкладу

    Користувач може:
    - відкрити форму створення;
    - ввести назву;
    - додати вміст;
    - зберегти розклад;
    - побачити створений розклад у списку.

Одна feature зазвичай складається з кількох технічних завдань.

### 3.2. Task — завдання

**Task** — конкретна одиниця роботи, яку можна виконати та перевірити.

Наприклад, feature «Створення розкладу» можна розділити на такі завдання:

    1. Створити таблицю schedules.
    2. Реалізувати функцію створення розкладу в сервісному шарі.
    3. Створити API endpoint для створення розкладу.
    4. Додати перевірку вхідних даних.
    5. Створити форму на frontend.
    6. Підключити форму до API.
    7. Показувати повідомлення про успіх або помилку.
    8. Перевірити збереження даних і права доступу.

Кожне завдання має зрозумілий результат.

### 3.3. Subtask — підзавдання

Велике завдання можна поділити на менші підзавдання.

    Task: Реалізувати створення розкладу

        Subtasks:
        - визначити поля розкладу;
        - перевірити вхідні дані;
        - додати запис до бази даних;
        - повернути створений об'єкт;
        - обробити помилки;
        - написати тести.

Підзавдання корисні, якщо без них складно оцінити обсяг роботи або зрозуміти порядок дій.

Не потрібно розбивати кожне завдання на десятки дрібних пунктів. План має допомагати роботі, а не створювати зайву бюрократію.

### 3.4. Milestone — контрольний етап

**Milestone** — важливий результат або контрольна точка проєкту.

Приклад:

    Milestone 1: Налаштоване середовище.
    Milestone 2: Працює база даних.
    Milestone 3: Реалізована автентифікація.
    Milestone 4: Працює створення та перегляд розкладів.
    Milestone 5: Реалізоване редагування.
    Milestone 6: Пройдена перевірка перед запуском.

Milestone допомагає оцінити прогрес на рівні всього проєкту, а не окремих файлів.

### 3.5. Deliverable — результат роботи

**Deliverable** — конкретний результат, який можна показати, використати або перевірити.

Приклади:

- схема бази даних;
- робочий endpoint;
- форма реєстрації;
- реалізований модуль авторизації;
- автоматизовані тести;
- розгорнута версія застосунку;
- документація з інструкціями запуску.

Завдання описує роботу, а deliverable — результат цієї роботи.

## 4. Від вимог до технічних завдань

Одна з найважливіших навичок планування — вміти перетворити загальну вимогу на послідовність конкретних дій.

Розглянемо приклад.

### Початкова вимога

    Користувач повинен мати можливість створювати приватні розклади.

Це зрозуміло з погляду продукту, але недостатньо конкретно для реалізації.

### Крок 1. Визначити поведінку користувача

    1. Користувач входить до системи.
    2. Відкриває сторінку розкладів.
    3. Натискає кнопку створення.
    4. Вводить назву та вміст.
    5. Натискає «Зберегти».
    6. Система перевіряє введені дані.
    7. Система зберігає розклад.
    8. Розклад відображається у списку користувача.

### Крок 2. Визначити технічні частини

    Database:
    - таблиця schedules;
    - зв'язок розкладу з користувачем.

    Backend:
    - перевірка вхідних даних;
    - отримання ідентифікатора авторизованого користувача;
    - створення запису;
    - повернення результату.

    API:
    - POST /api/schedules.

    Frontend:
    - форма створення;
    - обробка відправлення;
    - індикатор завантаження;
    - повідомлення про помилку;
    - оновлення списку.

    Testing:
    - валідні дані;
    - некоректні дані;
    - відсутність авторизації;
    - перевірка власника розкладу.

### Крок 3. Визначити критерії готовності

    Функція готова, якщо:
    - авторизований користувач може створити розклад;
    - обов'язкові поля перевіряються;
    - запис зберігається в PostgreSQL;
    - розклад пов'язується з поточним користувачем;
    - інший користувач не може отримати доступ до цього
      приватного розкладу;
    - інтерфейс коректно показує результат або помилку.

Тепер вимогу можна перетворити на конкретні завдання.

## 5. Вертикальний і горизонтальний поділ роботи

Є два поширені способи розбивати функціональність.

### 5.1. Горизонтальний поділ

Робота розбивається за технічними шарами.

    Етап 1: Вся база даних.
    Етап 2: Весь backend.
    Етап 3: Весь frontend.
    Етап 4: Тестування всього застосунку.

Наприклад, спочатку створюються всі таблиці, потім усі API endpoints, а після цього — інтерфейси.

**Перевага:** можна послідовно зосередитися на одному технічному шарі.

**Недолік:** до пізнього етапу може не бути жодної повністю готової користувацької функції.

### 5.2. Вертикальний поділ

Робота розбивається на функції, кожна з яких проходить через усі необхідні шари.

    Feature: Перегляд розкладів

        Database:
        - отримання розкладів із бази.

        Backend:
        - сервіс отримання розкладів;
        - перевірка власника.

        API:
        - GET /api/schedules.

        Frontend:
        - сторінка списку розкладів;
        - відображення результатів;
        - стани завантаження та помилки.

        Testing:
        - перевірка результатів;
        - перевірка приватності.

Після цього можна перейти до наступної функції.

**Переваги:**

- швидше з'являється працюючий результат;
- простіше перевіряти інтеграцію;
- легше виявляти проблеми між шарами;
- зручніше демонструвати прогрес.

Для невеликого навчального full-stack проєкту вертикальний поділ часто є найзручнішим підходом.

Водночас це не означає, що треба ігнорувати залежності. Наприклад, структуру таблиці та формат API доцільно визначити до початку реалізації відповідної функції.

## 6. Визначення залежностей між завданнями

**Dependency** — це залежність, за якої одне завдання не можна повноцінно завершити до виконання іншого.

Наприклад:

    Створити таблицю users
            ↓
    Реалізувати реєстрацію
            ↓
    Реалізувати вхід
            ↓
    Отримувати поточного користувача
            ↓
    Створювати приватні розклади

Якщо задача B залежить від задачі A, це потрібно врахувати в плані.

### Приклад залежностей Worship Schedule

| Завдання | Залежить від |
|---|---|
| Налаштувати PostgreSQL | Конфігурації середовища |
| Створити таблицю users | Налаштованої бази даних |
| Реалізувати реєстрацію | Таблиці users, правил валідації |
| Реалізувати вхід | Користувачів і механізму перевірки пароля |
| Реалізувати приватні розклади | Ідентифікації користувача та моделі schedules |
| Створити форму розкладу | Визначеного API-контракту |
| Перевірити повний сценарій | Інтегрованих frontend, backend і database |

### Що варто пам'ятати

Не всі завдання обов'язково виконувати послідовно.

Наприклад, після визначення API-контракту можна окремо підготувати:

- frontend-компоненти;
- backend-сервіс;
- тести валідації.

Але повну інтеграцію потрібно перевірити після того, як необхідні частини будуть готові.

## 7. Пріоритети: що робити спочатку

Не всі функції однаково важливі.

Під час планування варто враховувати:

- цінність для користувача;
- необхідність для основного сценарію;
- залежності;
- технічні ризики;
- складність;
- вартість помилки;
- час на реалізацію.

### 7.1. MVP — мінімально життєздатний продукт

**MVP (Minimum Viable Product)** — найменша версія продукту, яка дозволяє перевірити основну цінність і сценарій використання.

Для Worship Schedule можливий такий MVP:

    1. Користувач може зареєструватися.
    2. Користувач може увійти.
    3. Користувач може створити розклад.
    4. Користувач може переглянути власні розклади.
    5. Користувач може відредагувати розклад.
    6. Користувач може видалити розклад.
    7. Дані зберігаються в базі даних.
    8. Приватні розклади захищені від інших користувачів.

Можливості, які можна залишити на пізніше:

    - складний редактор форматування тексту;
    - вибір кольору для окремих фрагментів;
    - спільне редагування;
    - ролі організацій;
    - історія змін;
    - розширені шаблони;
    - імпорт та експорт;
    - сповіщення.

Важливо: MVP не означає відсутність безпеки, перевірки даних або базового тестування. Ці вимоги є частиною якісної реалізації основного функціоналу.

### 7.2. MoSCoW — простий спосіб пріоритизації

Метод MoSCoW поділяє вимоги на чотири категорії.

- **Must have** — обов'язково для першої версії.
- **Should have** — важливо, але можна тимчасово обійтися без цього.
- **Could have** — корисне додаткове покращення.
- **Won't have now** — свідомо не реалізується зараз.

Приклад:

    Must have:
    - реєстрація та вхід;
    - створення і перегляд розкладів;
    - редагування та видалення;
    - приватність даних.

    Should have:
    - пошук розкладів;
    - фільтрація;
    - зручні повідомлення про помилки.

    Could have:
    - вибір кольору тексту;
    - додаткові шаблони;
    - розширені налаштування відображення.

    Won't have now:
    - спільне редагування в реальному часі;
    - складна система ролей;
    - історія версій.

Категорії залежать від цілей конкретного проєкту. Якщо форматування є основною цінністю продукту, воно може перейти до Must have.

## 8. Оцінювання складності та часу

На етапі планування не завжди можливо точно визначити, скільки триватиме завдання.

Особливо це стосується навчального проєкту, коли технології ще вивчаються.

### 8.1. Оцінюємо не лише написання коду

Для кожного завдання потрібно врахувати:

    - вивчення незнайомої технології;
    - проєктування;
    - написання коду;
    - тестування;
    - налагодження;
    - інтеграцію;
    - документацію;
    - виправлення виявлених помилок.

Наприклад, endpoint може вимагати небагато коду, але його перевірка на правильність авторизації та ізоляцію даних потребуватиме додаткової роботи.

### 8.2. Оцінювання за розміром

На початку зручно використовувати приблизні категорії.

| Розмір | Значення |
|---|---|
| XS | Дуже маленька, зрозуміла зміна |
| S | Невелике завдання з відомим рішенням |
| M | Кілька пов'язаних кроків |
| L | Велике завдання з невизначеністю |
| XL | Надто велике або недостатньо зрозуміле завдання |

Наприклад:

    S: Додати поле title до форми.
    M: Реалізувати створення розкладу через API.
    L: Реалізувати безпечну автентифікацію.
    XL: Побудувати повний редактор документів.

Завдання XL краще дослідити та розділити на менші частини.

### 8.3. Оцінка через діапазон

Замість твердження «це займе дві години» можна записати:

    Оптимістична оцінка: 2 години.
    Реалістична оцінка: 4 години.
    Песимістична оцінка: 8 годин.

Це лише приклад діапазону, а не універсальна норма. Оцінка залежить від досвіду, складності та невизначеності.

Для навчання краще фіксувати фактичний час після завершення роботи. Так поступово формується власне розуміння швидкості розробки.

## 9. Definition of Done — визначення готовності

**Definition of Done (DoD)** — узгоджений набір умов, за яких завдання вважається завершеним.

Сам факт, що код написано, ще не означає, що функція готова.

Наприклад, для створення розкладу Definition of Done може містити:

    - вхідні дані перевіряються;
    - авторизація перевіряється;
    - розклад зберігається в PostgreSQL;
    - власник визначається на backend;
    - помилки обробляються;
    - frontend показує результат;
    - основний сценарій перевірений;
    - перевірено доступ іншого користувача;
    - код не містить відомих критичних помилок;
    - документація оновлена, якщо це необхідно.

### Definition of Done і Acceptance Criteria — не те саме

**Acceptance Criteria** описують умови прийнятності конкретної функції з погляду вимог.

    Feature: Створення розкладу

    Acceptance Criteria:
    - авторизований користувач може створити розклад;
    - назва не може бути порожньою;
    - після успішного створення розклад доступний у списку;
    - неавторизований користувач не може його створити.

**Definition of Done** описує загальні вимоги до завершення роботи.

    Definition of Done:
    - код перевірений;
    - необхідні тести пройшли;
    - помилки обробляються;
    - зміни інтегровані;
    - документація оновлена за потреби.

Acceptance Criteria відповідають на запитання «Чи працює функція так, як потрібно?», а Definition of Done — «Чи завершено розробку на прийнятному рівні якості?».

    Завдання:

    Завдання:
    - реалізувати реєстрацію;

### Етап 4. Основний CRUD

CRUD — чотири базові операції з даними:

    Create — створити.
    Read   — прочитати.
    Update — оновити.

### Етап 5. Frontend

Результат: функції доступні через інтерфейс.

    - перевірити валідацію;

Результат: працює перша версія, доступна для використання.

## 11. Вертикальний план для однієї функції

Розглянемо, як організувати розробку функції «Перегляд власних розкладів».

### Крок 1. Підготувати дані

Приклад спрощеної структури таблиці:

    CREATE TABLE schedules (
        id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        user_id BIGINT NOT NULL REFERENCES users(id),
        title VARCHAR(200) NOT NULL,
        content TEXT NOT NULL DEFAULT '',
        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
        updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    );

Таблиця зберігає ідентифікатор власника, назву, вміст і час створення та оновлення.

Це приклад, а не повна схема production-бази. Остаточна структура залежить від вимог до застосунку.

### Крок 2. Реалізувати backend-логіку

Спрощений приклад функції отримання розкладів користувача:

    async function getSchedulesByUserId(db, userId) {
        const result = await db.query(
            `SELECT id, title, content, created_at, updated_at
             FROM schedules
             WHERE user_id = $1
             ORDER BY updated_at DESC`,
            [userId]
        );

        return result.rows;
    }

Зверни увагу:

- `userId` передається окремим параметром SQL-запиту;
- використовується параметризований запит;
- результати обмежуються розкладами конкретного користувача;
- порядок сортування визначено явно.

У реальному застосунку `userId` має надходити з перевіреного контексту автентифікації, а не довільно прийматися з запиту клієнта.

### Крок 3. Визначити API-контракт

    GET /api/schedules

    Успішна відповідь:
    200 OK

    [
        {
            "id": 1,
            "title": "Недільний розклад",
            "content": "08:00 — Літургія"
        }
    ]

Формат наведений для прикладу. У реальному API потрібно визначити повний контракт відповіді, включно з обробкою помилок та авторизацією.

### Крок 4. Реалізувати frontend

    - отримати список через API;
    - показати індикатор завантаження;
    - відобразити список;
    - показати повідомлення, якщо список порожній;
    - обробити помилку запиту;
    - надати посилання на перегляд або редагування.

### Крок 5. Перевірити сценарії

    Сценарій 1:
    Користувач має три розклади.
    Очікування: показано лише його розклади.

    Сценарій 2:
    Користувач не має розкладів.
    Очікування: показано порожній стан.

    Сценарій 3:
    Користувач не авторизований.
    Очікування: API відхиляє запит.

    Сценарій 4:
    Користувач має власні розклади, а інший користувач —
    окремі розклади.
    Очікування: дані не змішуються.

Таке планування дозволяє перевіряти функцію від бази даних до інтерфейсу.

## 16. Ризики та невизначеність

Планування — це не спроба передбачити абсолютно все. Його завдання — вчасно помітити проблеми, які можуть суттєво вплинути на реалізацію.

Для Worship Schedule можливі ризики:

| Ризик | Чому важливий | Що зробити |
|---|---|---|
| Неправильна модель даних | Переробка схеми пізніше | Перевірити основні сценарії до реалізації |
| Помилки автентифікації | Ризик доступу до чужих даних | Протестувати ізоляцію користувачів |
| Незрозумілий формат вмісту | Проблеми під час редагування | Визначити формат збереження заздалегідь |
| Надто складний редактор | Відсуває готовність MVP | Почати з простого текстового поля |
| Проблеми розгортання | Локально працює, у production — ні | Перевірити розгортання до завершення всіх функцій |

### Spike — дослідницьке завдання

**Spike** — обмежене за часом дослідження, яке допомагає зменшити невизначеність перед повною реалізацією.

Наприклад:

    Spike: Перевірити спосіб зберігання форматованого тексту.

    Питання:
    - Чи достатньо простого textarea?
    - Чи потрібен rich-text editor?
    - Який формат зберігати в PostgreSQL?
    - Як безпечно відображати збережений вміст?

    Результат:
    - короткий опис варіантів;
    - обране рішення;
    - невеликий прототип за потреби.

Spike не повинен перетворюватися на нескінченне дослідження. Його мета — відповісти на конкретне питання, необхідне для прийняття рішення.

## 17. Планування з урахуванням тестування

Тестування не варто залишати на останній день перед запуском.

Його потрібно враховувати під час планування кожної важливої функції.

### Основні рівні перевірки

**Unit tests**

Перевіряють окремі функції або невеликі одиниці логіки.

    Наприклад:
    - перевірка правил валідації;
    - форматування даних;
    - обчислення значень.

**Integration tests**

Перевіряють взаємодію компонентів.

    Наприклад:
    - API працює з PostgreSQL;
    - сервіс правильно обробляє результат запиту;
    - авторизація застосовується до endpoint.

**End-to-end tests (E2E)**

Перевіряють повний сценарій користувача.

    Наприклад:
    - користувач входить;
    - відкриває список;
    - створює розклад;
    - бачить його після збереження.

На початку не обов'язково автоматизувати всі можливі сценарії. Важливо передбачити перевірку критичних функцій, особливо тих, що стосуються приватності та збереження даних.

## 18. Часті помилки під час планування

### Помилка 1. Планувати лише за файлами

Невдалий план:

    - створити page.tsx;
    - створити route.ts;
    - створити service.ts;
    - створити schema.ts.

Це описує структуру коду, але не пояснює, яку користувацьку функцію потрібно реалізувати та як перевірити результат.

Краще:

    Feature: Створення розкладу

    - визначити контракт;
    - перевірити вхідні дані;
    - реалізувати збереження;
    - створити форму;
    - обробити результат;
    - перевірити права доступу.

Назви файлів можуть бути додатковими технічними деталями.

### Помилка 2. Завдання занадто великі

    Погано:
    - Зробити backend.
    - Зробити frontend.
    - Додати авторизацію.
    - Завершити застосунок.

Такі завдання складно оцінити й перевірити.

Краще розділити їх на конкретні результати, які можна виконувати та перевіряти окремо.

### Помилка 3. Надмірна деталізація

Протилежна проблема — створити сотні дрібних завдань ще до початку роботи.

Наприклад, не обов'язково створювати окрему задачу для кожного CSS-відступу або рядка коду.

Плануй детально найближчі кроки, а далекі етапи залишай на рівні функцій і контрольних точок.

### Помилка 4. Ігнорування залежностей

Не можна повноцінно реалізувати приватні розклади, якщо ще не визначено, як система ідентифікує користувача.

Перед плануванням перевіряй, які дані, компоненти та рішення потрібні кожному завданню.

### Помилка 5. Додавання функцій без оцінки впливу

Нова можливість може вимагати змін у:

    - моделі даних;
    - API-контрактах;
    - frontend;
    - backend;
    - тестах;
    - документації.

Перед додаванням нової функції варто оцінити не лише обсяг її власного коду, а й вплив на вже реалізовані компоненти.

### Помилка 6. Відсутність критеріїв готовності

Завдання «Реалізувати редагування» може означати дуже різні речі.

Потрібно визначити, чи передбачено:

    - завантаження поточних даних;
    - перевірку змін;
    - збереження;
    - повідомлення про помилку;
    - захист від редагування чужого запису;
    - перевірку успішного результату.

### Помилка 7. Надто точні оцінки

На початку проєкту багато невідомого. Оцінки потрібно уточнювати після появи нової інформації.

План — це робочий інструмент, а не незмінний контракт із самим собою.

### Помилка 8. Відкладення безпеки

Авторизація, перевірка прав власника, валідація та безпечне збереження даних мають входити до плану основних функцій від самого початку.

## 19. Як планування пов'язане з Agile, Kanban і Scrum

Для невеликого особистого проєкту не обов'язково використовувати повну методологію керування розробкою. Проте корисно розуміти кілька понять.

### Agile

**Agile** — сімейство підходів, які наголошують на поступовій розробці, зворотному зв'язку та адаптації до змін.

Практичне застосування:

    1. Реалізувати невелику функцію.
    2. Перевірити її.
    3. Оцінити результат.
    4. Уточнити наступні кроки.
    5. Повторити цикл.

### Kanban

**Kanban** допомагає візуалізувати потік завдань.

Приклад колонок:

    Backlog → Todo → In Progress → Review → Done

Для особистого проєкту можна використовувати GitHub Projects або звичайний Markdown-список.

Корисне правило: не починай одночасно надто багато завдань. Завершення розпочатої роботи часто корисніше, ніж постійне переключення між функціями.

### Scrum

**Scrum** — фреймворк командної розробки з ролями, подіями та короткими спринтами.

Для індивідуального навчання не потрібно копіювати весь Scrum. Можна запозичити ідею короткого циклу:

    План → Реалізація → Перевірка → Оцінка → Наступний цикл

Наприклад, на початку тижня визначити одну невелику функцію, а наприкінці перевірити, що реально завершено.

## 20. Практичний алгоритм планування функції

Для кожної важливої функції можна використовувати один і той самий алгоритм.

### Крок 1. Визначити мету

Що користувач повинен уміти робити після реалізації?

### Крок 2. Описати сценарій

Які дії виконує користувач і як реагує система?

### Крок 3. Визначити дані

Які дані потрібно отримати, створити, змінити або видалити?

### Крок 4. Визначити компоненти

Які частини системи беруть участь?

    Frontend
        ↓
    API
        ↓
    Backend service
        ↓
    Database

Це типова схема, але конкретна структура залежить від архітектури застосунку.

### Крок 5. Перевірити залежності

Що повинно бути готове раніше?

### Крок 6. Розділити роботу

Створити невеликі завдання з конкретним результатом.

### Крок 7. Визначити критерії прийнятності

Як зрозуміти, що функція поводиться правильно?

### Крок 8. Запланувати перевірки

Які позитивні та негативні сценарії потрібно перевірити?

### Крок 9. Визначити пріоритет

Чи потрібна функція для MVP, чи її можна відкласти?

### Крок 10. Оновлювати план

Після реалізації перевірити, чи залишаються попередні припущення правильними.

## 21. Приклад повного плану MVP для Worship Schedule

Нижче — один із можливих варіантів. Це не єдиний правильний порядок, але він враховує залежності між даними, автентифікацією та функціями розкладів.

### Milestone 1. Підготовка

    - [ ] Створити репозиторій.
    - [ ] Налаштувати проєкт і команди запуску.
    - [ ] Налаштувати змінні середовища.
    - [ ] Підготувати інструкцію запуску.
    - [ ] Перевірити локальний запуск.

### Milestone 2. База даних

    - [ ] Створити базу даних.
    - [ ] Створити таблицю users.
    - [ ] Створити таблицю schedules.
    - [ ] Додати зв'язок schedules.user_id → users.id.
    - [ ] Перевірити обмеження та SQL-запити.

### Milestone 3. Автентифікація

    - [ ] Реалізувати реєстрацію.
    - [ ] Реалізувати безпечне зберігання паролів.
    - [ ] Реалізувати вхід.
    - [ ] Реалізувати вихід.
    - [ ] Захистити приватні API-маршрути.
    - [ ] Перевірити неавторизовані запити.

### Milestone 4. Читання розкладів

    - [ ] Отримувати список розкладів поточного користувача.
    - [ ] Отримувати один розклад за ідентифікатором.
    - [ ] Перевіряти власника запису.
    - [ ] Створити сторінку списку.
    - [ ] Створити сторінку перегляду.
    - [ ] Обробити порожній список та помилки.

### Milestone 5. Створення розкладів

    - [ ] Визначити правила валідації.
    - [ ] Реалізувати endpoint створення.
    - [ ] Реалізувати форму.
    - [ ] Підключити форму до API.
    - [ ] Показувати результат збереження.
    - [ ] Перевірити створення з різними вхідними даними.

### Milestone 6. Редагування та видалення

    - [ ] Реалізувати оновлення розкладу.
    - [ ] Реалізувати форму редагування.
    - [ ] Реалізувати видалення.
    - [ ] Додати підтвердження видалення за потреби.
    - [ ] Перевірити права доступу.
    - [ ] Перевірити помилки та граничні випадки.

### Milestone 7. Якість і розгортання

    - [ ] Перевірити повний сценарій користувача.
    - [ ] Перевірити ізоляцію даних різних користувачів.
    - [ ] Перевірити валідацію на backend.
    - [ ] Перевірити обробку помилок.
    - [ ] Налаштувати production-змінні.
    - [ ] Розгорнути застосунок.
    - [ ] Перевірити роботу production-версії.
    - [ ] Оновити README.md.

### Після MVP

    - [ ] Додати форматування тексту.
    - [ ] Додати шаблони розкладів.
    - [ ] Додати пошук і фільтрацію.
    - [ ] Додати експорт.
    - [ ] Розглянути історію змін.
    - [ ] Розглянути спільну роботу.

Такий план дозволяє отримати корисну версію продукту до реалізації складніших можливостей.

## 22. Як використовувати Implementation Planning у навчанні

Під час навчання програмування важливо не просто закривати завдання, а розуміти, чому вони виконуються саме в такій послідовності.

Для кожної функції спробуй відповісти на п'ять запитань:

    1. Що повинен робити користувач?
    2. Які дані для цього потрібні?
    3. Які компоненти мають взаємодіяти?
    4. Які залежності потрібно реалізувати раніше?
    5. Як перевірити, що все працює правильно?

### Рекомендований порядок роботи

    1. Спочатку коротко спланувати функцію.
    2. Визначити необхідні зміни в базі даних.
    3. Визначити або уточнити API-контракт.
    4. Реалізувати backend-логіку.
    5. Перевірити backend.
    6. Реалізувати frontend.
    7. Перевірити повний сценарій.
    8. Оновити план і документацію.

Це не означає, що кожна функція обов'язково повинна реалізовуватися строго за такою схемою. Для простих завдань кроки можна об'єднувати, а frontend-прототип іноді створюють раніше. Важливо не втрачати залежності та можливість перевірити результат.

## 23. Рівні володіння навичкою

### Core — базове розуміння

Ти повинен уміти:

- пояснити, навіщо потрібен план реалізації;
- розрізняти feature, task і milestone;
- розділити велику вимогу на менші завдання;
- визначити основні залежності;
- скласти простий список робіт.

### Junior — практичне застосування

Ти повинен уміти:

- перетворити user story на технічні завдання;
- планувати роботу по шарах застосунку;
- визначати критерії прийнятності;
- враховувати тестування;
- визначати MVP;
- вести список завдань і відстежувати прогрес;
- оновлювати план у міру появи нової інформації.

### Middle — системне планування

Ти повинен уміти:

- оцінювати технічні ризики;
- виявляти приховані залежності;
- порівнювати альтернативні способи реалізації;
- планувати інтеграцію кількох компонентів;
- оцінювати вплив змін на існуючу архітектуру;
- обирати між швидким рішенням і довгостроковою підтримуваністю;
- коригувати план на основі результатів розробки.

### Senior — планування на рівні системи

Ти повинен уміти:

- пов'язувати технічний план із цілями продукту;
- враховувати операційні, безпекові та масштабувальні ризики;
- планувати поступове впровадження великих змін;
- визначати критичний шлях;
- розподіляти роботу між командами;
- зменшувати ризики через прототипи та експерименти;
- підтримувати актуальність плану без надмірної бюрократії.

## 25. Мінішпаргалка

    Implementation Planning
        Перетворення вимог на план конкретних робіт.

    Feature
        Можливість, яку отримує користувач.

    Task
        Конкретна одиниця роботи.

    Subtask
        Менша частина великого завдання.

    Milestone
        Важлива контрольна точка проєкту.

    Deliverable
        Конкретний результат роботи.

    Dependency
        Залежність одного завдання від іншого.

    MVP
        Мінімальна версія продукту для перевірки основної цінності.

    MoSCoW
        Must / Should / Could / Won't have now.

    Acceptance Criteria
        Умови, за яких функція відповідає вимогам.

    Definition of Done
        Загальні умови завершення завдання.

    Spike
        Обмежене дослідження для зменшення невизначеності.

    Vertical Slice
        Реалізація функції через усі необхідні шари застосунку.

    Backlog
        Список запланованої роботи.

    Kanban
        Візуалізація потоку завдань.

    Основний принцип
        Плануй результат, залежності та перевірку,
        а не лише файли, які потрібно створити.

## 26. Що потрібно запам'ятати

- Implementation Planning перетворює архітектурні рішення та вимоги на послідовність конкретних робіт.
- Хороше завдання має зрозумілу мету й перевірюваний результат.
- Великі завдання потрібно розділяти, але не доводити деталізацію до абсурду.
- Порядок реалізації визначається не лише пріоритетом, а й залежностями.
- Вертикальний поділ часто допомагає швидше отримати працюючі функції.
- MVP зосереджується на основній цінності продукту, але не скасовує вимоги до безпеки та якості.
- Acceptance Criteria визначають, що повинна робити функція; Definition of Done — що потрібно для завершення роботи.
- Тестування, інтеграцію та розгортання потрібно враховувати в плані заздалегідь.
- План має змінюватися разом із новими знаннями.
- Для невеликого особистого проєкту достатньо простого плану в Markdown, якщо він допомагає працювати послідовно.

**Головна думка:** не намагайся спланувати кожен рядок майбутнього коду. Визнач основні функції, розділи їх на керовані завдання, врахуй залежності та критерії готовності — а потім реалізовуй і уточнюй план у міру розвитку проєкту.
