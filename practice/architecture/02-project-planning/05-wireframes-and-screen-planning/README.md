# Wireframes and Screen Planning

## 1. Що таке Wireframes and Screen Planning

**Wireframe** (каркас екрана) — це спрощене схематичне представлення сторінки або екрана застосунку, яке показує розташування основних елементів, структуру контенту та взаємодію з користувачем без детального візуального оформлення.

**Screen Planning** (планування екранів) — це процес визначення того, які екрани потрібні застосунку, яку мету має кожен екран, які елементи на ньому розташовані та як користувач переходить між екранами.

Наприклад, у проєкті Worship Schedule потрібно спланувати сторінку створення розкладу богослужінь.

До початку програмування варто визначити:

- де розташована назва сторінки;
- які поля містить форма;
- які поля обов'язкові;
- де розташована кнопка збереження;
- як користувач скасовує створення;
- де показуються повідомлення про помилки;
- що відбувається після успішного збереження.

Wireframe допомагає побачити структуру майбутнього інтерфейсу ще до написання HTML, CSS або React-компонентів.

### Для чого це потрібно

- Спланувати структуру сторінок до програмування.
- Визначити основні UI-елементи.
- Продумати ієрархію інформації.
- Узгодити розташування елементів із потребами користувача.
- Виявити відсутні функції до початку розробки.
- Перевірити логіку навігації.
- Зменшити кількість переробок frontend.
- Визначити межі майбутніх компонентів.
- Підготувати основу для UI-дизайну та адаптивної верстки.

### Основна ідея

    User Story:
        Яку потребу має користувач?

    User Flow:
        Якими кроками користувач досягає мети?

    Screen Planning:
        Які екрани потрібні для виконання завдання?

    Wireframe:
        Як організований вміст конкретного екрана?

    UI Design:
        Як екран виглядає візуально?

    Implementation:
        Як реалізувати інтерфейс за допомогою HTML,
        CSS, JavaScript або React?

Ці етапи пов'язані між собою, але кожен вирішує окреме завдання.

## 2. Основні поняття

### ✔ Screen

Екран — окрема сторінка або логічно відокремлений стан інтерфейсу, з яким взаємодіє користувач.

Приклади:

- головна сторінка;
- сторінка входу;
- список розкладів;
- сторінка перегляду розкладу;
- форма створення розкладу;
- сторінка налаштувань.

У вебзастосунку екран часто відповідає маршруту, але не завжди. Наприклад, модальне вікно може бути окремим станом інтерфейсу без переходу на новий маршрут.

### ✔ Wireframe

Схематичне представлення екрана без детального оформлення.

Wireframe зазвичай показує:

- основні блоки;
- заголовки;
- кнопки;
- поля введення;
- списки;
- навігацію;
- приблизну ієрархію елементів.

### ✔ Screen Inventory

Перелік усіх необхідних екранів застосунку.

Наприклад:

    01. Головна сторінка
    02. Реєстрація
    03. Вхід
    04. Список розкладів
    05. Створення розкладу
    06. Перегляд розкладу
    07. Редагування розкладу
    08. Налаштування профілю

Такий перелік допомагає не забути важливі частини інтерфейсу.

### ✔ Layout

Структура розташування елементів на екрані.

Наприклад:

    Header
        ↓
    Main Content
        ↓
    Footer

Або:

    Sidebar | Main Content

### ✔ Content Hierarchy

Ієрархія контенту — порядок, у якому користувач сприймає інформацію.

Зазвичай найважливіші елементи повинні бути помітнішими та розташованими відповідно до логіки завдання.

### ✔ Primary Action

Основна дія, яку користувач найімовірніше повинен виконати на конкретному екрані.

Приклади:

- «Увійти» на сторінці входу;
- «Створити розклад» у списку розкладів;
- «Зберегти» у формі редагування.

### ✔ Secondary Action

Допоміжна дія, яка не є основною метою екрана.

Приклади:

- «Скасувати»;
- «Повернутися до списку»;
- «Очистити форму».

### ✔ Placeholder

Тимчасовий вміст або позначення місця, яке пізніше буде заповнене реальними даними чи візуальним елементом.

### ✔ Responsive Layout

Структура інтерфейсу, яка адаптується до різних розмірів екрана.

### ✔ Component Boundary

Межа компонента — визначення того, які елементи інтерфейсу доцільно об'єднати в окремий компонент.

Wireframe може допомогти помітити повторювані елементи, наприклад картки розкладів, поля форми або навігаційні панелі.

## 3. Навіщо планувати екрани до програмування

Без попереднього планування розробник часто починає створювати компоненти одразу після формулювання вимоги.

Наприклад:

    Потрібно реалізувати розклади.
        ↓
    Створюємо сторінку.
        ↓
    Додаємо форму.
        ↓
    Додаємо кнопки.
        ↓
    Змінюємо структуру.
        ↓
    Додаємо відсутні стани.
        ↓
    Переробляємо компоненти.

Проблема не в тому, що перша версія обов'язково буде неправильною. Проблема в тому, що частину важливих рішень доводиться приймати вже під час написання коду.

Планування дозволяє спочатку визначити основну структуру.

    Вимоги
        ↓
    User Stories
        ↓
    User Flows
        ↓
    Screen Inventory
        ↓
    Wireframes
        ↓
    UI Design
        ↓
    Frontend Implementation

Це не обов'язково сувора послідовність. Під час роботи над проєктом можна повертатися до попередніх етапів і уточнювати рішення.

### Що можна виявити заздалегідь

- На сторінці немає очевидної кнопки основної дії.
- Для завершення сценарію потрібен екран, який ще не запланований.
- Форма містить забагато полів.
- Навігація не відповідає User Flow.
- На мобільному екрані не вистачає місця.
- Не передбачено порожнього стану списку.
- Незрозуміло, де відображати помилки.
- Однакові елементи можна оформити як повторно використовувані компоненти.

## 4. Screen Planning: перелік екранів

Перш ніж малювати Wireframes, корисно скласти список екранів.

### 4.1. Приклад для Worship Schedule

Припустимо, застосунок дозволяє зареєстрованим користувачам створювати та редагувати власні розклади.

Можливий Screen Inventory:

    Public Pages:
        01. Home
        02. Login
        03. Register

    Application Pages:
        04. Dashboard
        05. Schedule List
        06. Schedule Details
        07. Create Schedule
        08. Edit Schedule
        09. Profile Settings

Це лише початковий перелік. Наприклад, сторінка перегляду розкладу може бути доступною публічно або тільки власнику — це залежить від вимог проєкту.

### 4.2. Для кожного екрана визначай мету

Не варто створювати екран лише тому, що він здається звичним для вебзастосунку.

Для кожного екрана потрібно відповісти:

- Хто ним користується?
- Яку мету має користувач?
- Які дані він бачить?
- Які дії може виконати?
- Звідки він потрапляє на цей екран?
- Куди може перейти далі?
- Які стани потрібно передбачити?

Приклад:

    Screen:
        Schedule List

    Мета:
        Дозволити користувачу знаходити та відкривати
        власні розклади.

    Основні елементи:
        Заголовок.
        Кнопка створення.
        Список розкладів.
        Елементи переходу до перегляду та редагування.

    Основна дія:
        Створити розклад або відкрити наявний.

    Можливі стани:
        Loading.
        List.
        Empty.
        Error.

### 4.3. Не плутай сторінки та стани

Не кожен стан інтерфейсу потребує окремої сторінки.

Наприклад, для списку розкладів:

    /schedules

Можливі стани:

    Loading:
        дані завантажуються.

    List:
        розклади знайдено.

    Empty:
        розкладів ще немає.

    Error:
        не вдалося отримати дані.

Це може бути одна сторінка з різними станами, а не чотири окремі маршрути.

Окремий маршрут потрібен тоді, коли цього вимагає логіка навігації або структура застосунку.

## 5. Як побудувати Wireframe

### Крок 1. Визначити мету екрана

Наприклад:

    Екран:
        Створення розкладу.

    Мета:
        Дозволити користувачу ввести дані
        та зберегти новий розклад.

### Крок 2. Визначити основний контент

Запиши інформацію, яку користувач повинен бачити.

    Заголовок:
        Створення розкладу.

    Поля:
        Назва розкладу.
        Основний вміст.

    Дії:
        Зберегти.
        Скасувати.

Додаткові поля потрібно додавати лише тоді, коли вони відповідають вимогам продукту.

### Крок 3. Розставити елементи за пріоритетом

Спочатку розміщуй найважливіші елементи.

Наприклад:

    Header
        ↓
    Page Title
        ↓
    Form
        ├── Title Field
        ├── Content Field
        └── Actions
              ├── Save
              └── Cancel

Не потрібно одразу визначати точні кольори, тіні, шрифти та декоративні деталі.

### Крок 4. Визначити взаємодію

Подумай, що відбувається після кожної важливої дії.

    Натиснути «Зберегти»
        ↓
    Перевірити дані
        ├── Некоректні → показати помилки
        └── Коректні → надіслати запит
                       ↓
                    Успіх?
                       ├── Так → показати результат
                       └── Ні → показати помилку

### Крок 5. Передбачити стани

Для кожного важливого екрана потрібно визначити:

    Initial:
        початковий вигляд.

    Loading:
        очікування даних або відповіді.

    Success:
        операція завершилася успішно.

    Empty:
        немає даних для відображення.

    Error:
        сталася помилка.

Не кожен екран потребує всіх станів. Визначай їх відповідно до його функцій.

### Крок 6. Перевірити адаптивність

Подумай, як зміниться структура на вузькому екрані.

Наприклад:

    Desktop:
        Sidebar | Main Content

    Mobile:
        Header
        Main Content
        Mobile Navigation, якщо потрібна

Не потрібно одразу малювати всі можливі розміри екрана. Почни з основних сценаріїв і перевір найважливіші контрольні ширини.

### Крок 7. Перевірити готовий каркас

Запитай себе:

- Чи зрозуміло, для чого призначений екран?
- Чи помітна основна дія?
- Чи логічно розташовані елементи?
- Чи є зрозуміла навігація?
- Чи передбачені помилки?
- Чи можна виконати завдання без зайвих кроків?
- Чи можна використати повторювані компоненти?
- Чи не надто складна структура?

## 6. Рівні деталізації Wireframes

Wireframes можуть мати різний рівень деталізації.

### 6.1. Low-Fidelity Wireframe

**Low-Fidelity** — простий каркас із мінімальною кількістю деталей.

Зазвичай містить:

- прямокутники;
- підписи;
- умовні поля;
- кнопки;
- основні області сторінки.

Приклад:

    +------------------------------------------+
    | Header                                   |
    +------------------------------------------+
    |                                          |
    | Створення розкладу                       |
    |                                          |
    | Назва                                    |
    | [____________________________________]   |
    |                                          |
    | Вміст                                    |
    | [____________________________________]   |
    | [____________________________________]   |
    | [____________________________________]   |
    |                                          |
    | [Зберегти]  [Скасувати]                  |
    |                                          |
    +------------------------------------------+

Це хороший початок для планування структури.

### 6.2. Mid-Fidelity Wireframe

**Mid-Fidelity** — каркас із точнішим розташуванням, розмірами та структурою елементів.

Він може містити:

- реалістичні заголовки;
- точніші розміри блоків;
- структуру навігації;
- групування полів;
- приблизні відступи;
- логіку розміщення основних дій.

На цьому етапі вже можна обговорювати, чи достатньо місця для форми та чи логічно згруповані поля.

### 6.3. High-Fidelity Wireframe

**High-Fidelity** — дуже деталізований каркас, близький до майбутнього інтерфейсу за структурою та точністю.

Він може містити:

- точніші розміри;
- реальний текст;
- конкретні стани компонентів;
- детальну навігацію;
- реалістичне розташування контенту.

Межа між High-Fidelity Wireframe та UI Mockup не завжди чітка. Якщо макет уже визначає кольори, типографіку, тіні та інші візуальні характеристики, його частіше називають UI Mockup або Visual Design.

### 6.4. Який рівень обрати

Для невеликого навчального проєкту зазвичай достатньо Low-Fidelity або Mid-Fidelity.

Не потрібно витрачати багато часу на деталізовані макети, якщо головні питання структури та поведінки ще не вирішені.

## 7. Layout: основні структури екранів

Wireframe допомагає визначити, як розташовуватимуться основні частини сторінки.

### 7.1. Single Column

Одна основна колонка.

    +----------------------------------+
    | Header                           |
    +----------------------------------+
    |                                  |
    | Page Title                       |
    |                                  |
    | Main Content                     |
    |                                  |
    | Form / Article / List            |
    |                                  |
    +----------------------------------+
    | Footer                           |
    +----------------------------------+

Підходить для:

- форм;
- статей;
- простих сторінок налаштувань;
- сторінок входу;
- невеликих навчальних застосунків.

### 7.2. Sidebar + Main Content

Бічна панель та основна область.

    +------------------------------------------+
    | Header                                   |
    +------------+-----------------------------+
    |            |                             |
    | Sidebar    | Main Content                |
    |            |                             |
    | Navigation | Page Title                  |
    |            | Data / Forms / Cards         |
    |            |                             |
    +------------+-----------------------------+

Підходить для:

- особистих кабінетів;
- адміністративних панелей;
- застосунків із багатьма розділами;
- систем керування контентом.

### 7.3. Grid Layout

Сітка повторюваних елементів.

    +------------------------------------------+
    | Header                                   |
    +------------------------------------------+
    | Page Title                    [Create]    |
    +------------------------------------------+
    |                                          |
    | +--------------+  +--------------+       |
    | | Schedule 1   |  | Schedule 2   |       |
    | +--------------+  +--------------+       |
    |                                          |
    | +--------------+  +--------------+       |
    | | Schedule 3   |  | Schedule 4   |       |
    | +--------------+  +--------------+       |
    |                                          |
    +------------------------------------------+

Підходить для карток, товарів, курсів, розкладів та інших повторюваних елементів.

### 7.4. Split View

Дві пов'язані області.

    +------------------------------------------+
    | Header                                   |
    +------------------+-----------------------+
    | List             | Details               |
    |                  |                       |
    | Item 1           | Selected Item         |
    | Item 2           |                       |
    | Item 3           | Content               |
    |                  |                       |
    +------------------+-----------------------+

Підходить для інтерфейсів, у яких зручно одночасно переглядати список і деталі вибраного елемента.

### 7.5. Form Layout

Структура форми.

    +------------------------------------------+
    | Page Title                               |
    +------------------------------------------+
    | Label                                    |
    | [Input                              ]    |
    |                                          |
    | Label                                    |
    | [Input                              ]    |
    |                                          |
    | Label                                    |
    | [Textarea                           ]    |
    |                                          |
    | [Primary Action] [Secondary Action]      |
    +------------------------------------------+

Під час проєктування форм потрібно враховувати читабельність, зрозумілі назви полів, помилки та логічне групування даних.

## 8. Screen Inventory та Screen Specification

Screen Inventory показує, які екрани потрібні.

Screen Specification (опис екрана) пояснює, як має працювати кожен із них.

### 8.1. Приклад Screen Inventory

    | ID    | Screen             | Purpose                     |
    |-------|--------------------|-----------------------------|
    | SCR-01 | Home              | Публічна інформація         |
    | SCR-02 | Login             | Вхід до системи             |
    | SCR-03 | Register          | Створення акаунта           |
    | SCR-04 | Schedule List     | Перегляд власних розкладів  |
    | SCR-05 | Create Schedule   | Створення розкладу          |
    | SCR-06 | Schedule Details  | Перегляд одного розкладу    |
    | SCR-07 | Edit Schedule     | Редагування розкладу        |

Для маленького проєкту достатньо звичайного Markdown-списку. Таблиця стає кориснішою, коли екранів багато.

### 8.2. Приклад Screen Specification

    Screen ID:
        SCR-04

    Name:
        Schedule List

    Route:
        /schedules

    Purpose:
        Дозволити користувачу переглядати власні розклади.

    User Role:
        Авторизований користувач.

    Main Content:
        Заголовок сторінки.
        Кнопка створення.
        Список розкладів.

    Primary Action:
        Створити розклад.

    Secondary Actions:
        Відкрити розклад.
        Редагувати розклад.
        Видалити розклад.

    UI States:
        Loading.
        List.
        Empty.
        Error.

    Navigation:
        Create Schedule.
        Schedule Details.

Цей опис допомагає зрозуміти призначення екрана до написання коду.

## 9. Wireframes і UI-компоненти

Wireframe може допомогти визначити майбутні компоненти frontend.

Розглянемо список розкладів.

    Schedule List
        ├── Page Header
        ├── Create Schedule Button
        └── Schedule List
              ├── Schedule Card
              ├── Schedule Card
              └── Schedule Card

Якщо картки мають однакову структуру, їх можна реалізувати як повторно використовуваний компонент.

Наприклад, у React:

    function ScheduleCard({ title, updatedAt }) {
        return (
            <article className="schedule-card">
                <h2>{title}</h2>
                <p>Оновлено: {updatedAt}</p>
            </article>
        );
    }

Це спрощений приклад. У реальному TypeScript-проєкті потрібно визначити тип props, наприклад через `type ScheduleCardProps`.

### 9.1. Як виявляти межі компонентів

Під час аналізу Wireframe запитай себе:

- Чи повторюється цей блок на кількох екранах?
- Чи має він власну поведінку?
- Чи має він окремі стани?
- Чи можна змінювати його незалежно від інших блоків?
- Чи має сенс тестувати його окремо?

Приклади потенційних компонентів:

    Header
    Sidebar
    Navigation
    Button
    FormField
    ScheduleCard
    EmptyState
    LoadingIndicator
    ErrorMessage
    ConfirmDialog

Не потрібно створювати окремий компонент для кожного HTML-елемента. Компоненти повинні відповідати логічним частинам інтерфейсу.

### 9.2. Wireframe не визначає остаточну структуру коду

Один блок на схемі не обов'язково повинен відповідати одному React-компоненту.

Wireframe описує структуру інтерфейсу, а архітектура frontend визначає організацію коду.

Наприклад, блок форми на Wireframe може бути реалізований як:

- одна сторінка з кількома простими компонентами;
- окремий компонент форми;
- форма з повторно використовуваними полями;
- набір компонентів, розділених за відповідальністю.

Рішення залежить від складності та потреб проєкту.

## 10. Wireframes і Responsive Design

Wireframe повинен враховувати, що одна сторінка може відображатися на різних розмірах екрана.

### 10.1. Desktop

На широкому екрані може бути достатньо місця для бічної панелі та основного контенту.

    +------------------------------------------------+
    | Header                                         |
    +--------------+---------------------------------+
    | Sidebar      | Main Content                    |
    |              |                                 |
    | Navigation   | Title                           |
    |              |                                 |
    |              | Cards / Form / Data             |
    |              |                                 |
    +--------------+---------------------------------+

### 10.2. Mobile

На вузькому екрані бічна панель може перетворитися на меню або нижню навігацію.

    +------------------------------+
    | Header              [Menu]   |
    +------------------------------+
    |                              |
    | Main Content                 |
    |                              |
    | Title                        |
    |                              |
    | Card                         |
    |                              |
    | Card                         |
    |                              |
    | [Primary Action]             |
    |                              |
    +------------------------------+

### 10.3. Що перевіряти

- Чи залишається основна дія доступною?
- Чи можна читати текст без горизонтального прокручування?
- Чи не стають поля надто вузькими?
- Чи не перекриваються кнопки?
- Чи залишається навігація зрозумілою?
- Чи змінюється кількість колонок?
- Чи не зникає важлива інформація?

### 10.4. Responsive — це не просто зменшення розміру

Адаптивність може вимагати зміни самої структури.

Наприклад:

    Desktop:
        Sidebar + Main Content

    Mobile:
        Header + Main Content + Menu

Або:

    Desktop:
        три картки в ряд.

    Tablet:
        дві картки в ряд.

    Mobile:
        одна картка в ряд.

Конкретна поведінка залежить від контенту, ширини екрана та потреб користувача.

Не потрібно визначати всі breakpoints на етапі першого Wireframe. Спочатку сплануй логічну структуру, а потім уточнюй адаптивну поведінку.

## 11. Wireframes і доступність

Планування екранів — вдалий момент, щоб врахувати доступність, а не намагатися додати її наприкінці розробки.

### 11.1. Ієрархія заголовків

На екрані має бути зрозуміло, який заголовок описує сторінку, а які — окремі секції.

Наприклад:

    H1:
        Мої розклади

    H2:
        Майбутні розклади

    H2:
        Нещодавно оновлені

Це приклад інформаційної структури, а не вимога використовувати саме такі секції.

### 11.2. Форми

Потрібно передбачити:

- видимі підписи полів;
- зрозумілі назви кнопок;
- пояснення обов'язкових полів;
- місце для повідомлень про помилки;
- зрозумілий порядок заповнення;
- можливість користуватися формою з клавіатури.

Placeholder не повинен бути єдиним способом пояснення призначення поля.

### 11.3. Фокус і клавіатура

Під час планування інтерактивних елементів враховуй:

- видимий стан фокуса;
- логічний порядок переходу клавішею Tab;
- можливість виконати основні дії без миші;
- відсутність пасток клавіатурного фокуса.

### 11.4. Touch Targets

На сенсорних екранах інтерактивні елементи повинні бути достатньо великими та розташованими так, щоб ними було зручно користуватися.

На Wireframe можна одразу передбачити достатньо місця для кнопок і проміжків між сусідніми діями.

### 11.5. Доступність не дорівнює візуальному оформленню

Wireframe допомагає спланувати структуру та взаємодію, але не може повністю перевірити доступність.

На наступних етапах потрібно перевірити семантичний HTML, контрастність, клавіатурну навігацію, доступні назви елементів і поведінку допоміжних технологій.

## 12. Форми та повідомлення про помилки

Форми — один із найважливіших типів екранів у вебзастосунках.

Wireframe форми повинен показувати не лише поля та кнопки, а й місце для пояснень і помилок.

### 12.1. Базовий Wireframe форми

    +------------------------------------------+
    | Створення розкладу                       |
    +------------------------------------------+
    | Назва розкладу                           |
    | [____________________________________]   |
    |                                          |
    | Вміст                                    |
    | [____________________________________]   |
    | [____________________________________]   |
    |                                          |
    | [Зберегти] [Скасувати]                   |
    +------------------------------------------+

### 12.2. Стан із помилкою

    +------------------------------------------+
    | Створення розкладу                       |
    +------------------------------------------+
    | Назва розкладу                           |
    | [____________________________________]   |
    | Помилка: введіть назву розкладу.         |
    |                                          |
    | Вміст                                    |
    | [____________________________________]   |
    |                                          |
    | [Зберегти] [Скасувати]                   |
    +------------------------------------------+

### 12.3. Стан збереження

    +------------------------------------------+
    | Створення розкладу                       |
    +------------------------------------------+
    | Назва розкладу                           |
    | [Розклад недільного богослужіння     ]   |
    |                                          |
    | Вміст                                    |
    | [____________________________________]   |
    |                                          |
    | [Збереження...]                          |
    +------------------------------------------+

Ці схеми демонструють різні стани одного екрана. Не обов'язково створювати окрему сторінку для кожного стану.

### 12.4. Що потрібно враховувати

- Де з'являється повідомлення?
- Чи зрозуміло, яке поле має помилку?
- Чи зберігаються введені дані?
- Чи можна повторити спробу?
- Чи заблокована кнопка на час надсилання?
- Що відбувається після успіху?
- Чи можна скасувати операцію?

## 13. Wireframes і дизайн-система

Wireframe допомагає визначити структуру, але не повинен передчасно прив'язуватися до всіх деталей візуального оформлення.

Наприклад, на ранньому етапі достатньо позначити:

    [Primary Button]
    [Secondary Button]
    [Text Field]
    [Card]
    [Page Header]

На етапі UI Design можна визначити:

- кольори;
- типографіку;
- відступи;
- радіуси;
- тіні;
- стани компонентів;
- правила адаптивності.

### 13.1. Повторювані компоненти

Якщо кілька екранів використовують однакові елементи, потрібно врахувати це під час планування.

Наприклад:

    Button:
        Primary
        Secondary
        Danger

    FormField:
        Label
        Input
        Help Text
        Error Message

    Card:
        Header
        Content
        Actions

Це може стати основою майбутньої бібліотеки UI-компонентів.

### 13.2. Чому не потрібно починати з кольорів

Якщо структура екрана незручна, гарні кольори не вирішать проблему.

Спочатку потрібно визначити:

- інформаційну ієрархію;
- основні дії;
- розташування контенту;
- послідовність взаємодії;
- логіку навігації.

Після цього варто переходити до візуального оформлення.

## 16. Як перейти від Wireframe до HTML/CSS

Wireframe задає структуру майбутнього екрана. Під час реалізації ця структура перетворюється на HTML-елементи та CSS-правила.

Наприклад, каркас:

    Header
    Main
        Page Title
        Schedule List
            Schedule Card
            Schedule Card
            Schedule Card

може бути реалізований так:

    <header class="site-header">
        <a href="/">Worship Schedule</a>
        <nav aria-label="Головна навігація">
            <a href="/schedules">Мої розклади</a>
        </nav>
    </header>

    <main class="page">
        <div class="page-header">
            <h1>Мої розклади</h1>
            <a href="/schedules/new">Створити розклад</a>
        </div>

        <section aria-label="Список розкладів" class="schedule-list">
            <article class="schedule-card">
                <h2>Недільний розклад</h2>
                <p>Оновлено: 20 жовтня</p>
                <a href="/schedules/1">Відкрити</a>
            </article>

            <article class="schedule-card">
                <h2>Святковий розклад</h2>
                <p>Оновлено: 18 жовтня</p>
                <a href="/schedules/2">Відкрити</a>
            </article>
        </section>
    </main>

Це статичний приклад структури. У реальному застосунку дані зазвичай формуються на основі відповіді API або серверних даних.

### 16.1. Відповідність Wireframe і HTML

    Wireframe:
        Header
            ↓
        <header>

    Wireframe:
        Основний контент
            ↓
        <main>

    Wireframe:
        Незалежна картка розкладу
            ↓
        <article>

    Wireframe:
        Група пов'язаних елементів
            ↓
        <section>

Вибір HTML-елементів має враховувати їхній зміст і семантику, а не лише візуальне розташування.

### 16.2. Відповідність Wireframe і CSS

Для сітки карток можна використати CSS Grid:

    .schedule-list {
        display: grid;
        grid-template-columns: repeat(2, minmax(0, 1fr));
        gap: 1.5rem;
    }

    .schedule-card {
        padding: 1.25rem;
        border: 1px solid #d1d5db;
        border-radius: 0.75rem;
    }

Для вузьких екранів можна змінити кількість колонок:

    @media (max-width: 640px) {
        .schedule-list {
            grid-template-columns: 1fr;
        }
    }

Це лише приклад. Реальні точки перелому потрібно визначати відповідно до контенту та поведінки макета.

## 17. Як перейти від Wireframe до React

У React структуру екрана можна розділити на компоненти.

Наприклад:

    src/
    ├── app/
    │   └── schedules/
    │       └── page.tsx
    └── components/
        └── schedules/
            ├── ScheduleList.tsx
            └── ScheduleCard.tsx

Можливий розподіл відповідальності:

    page.tsx:
        сторінка;
        отримання або підготовка даних;
        загальна структура.

    ScheduleList.tsx:
        відображення списку;
        обробка порожнього стану.

    ScheduleCard.tsx:
        відображення одного розкладу.

Це лише один із варіантів структури. У невеликому застосунку компоненти можуть бути організовані простіше.

### 17.1. Приклад компонента картки

    type ScheduleCardProps = {
        title: string;
        updatedAt: string;
        href: string;
    };

    export function ScheduleCard({
        title,
        updatedAt,
        href,
    }: ScheduleCardProps) {
        return (
            <article className="schedule-card">
                <h2>{title}</h2>
                <p>Оновлено: {updatedAt}</p>
                <a href={href}>Відкрити</a>
            </article>
        );
    }

Тут використано явний тип props замість `any`.

### 17.2. Не перетворюй кожен блок на компонент

Компонент доцільно створювати, якщо він:

- має окрему відповідальність;
- повторно використовується;
- має власну поведінку;
- має складну структуру;
- може бути корисно перевірений окремо.

Для маленького статичного елемента іноді достатньо звичайного HTML усередині батьківського компонента.

## 18. Інструменти для створення Wireframes

Wireframes можна створювати різними способами.

### 18.1. Папір і олівець

Переваги:

- швидко;
- не потрібно налаштовувати інструменти;
- зручно перевіряти ідеї;
- легко змінювати структуру.

Недоліки:

- складніше підтримувати спільну документацію;
- важче переносити повторювані компоненти між макетами;
- не завжди зручно показувати інтерактивні переходи.

Для першого начерку паперу цілком достатньо.

### 18.2. Figma

<Favicon url="https://www.figma.com" size="24" /> **Figma** — інструмент для створення інтерфейсів, прототипів і спільної роботи над дизайном.

Переваги:

- зручно створювати екрани;
- можна організовувати повторювані компоненти;
- можна пов'язувати екрани в інтерактивний прототип;
- зручно працювати з адаптивними варіантами;
- легко передавати макети іншим учасникам проєкту.

### 18.3. Excalidraw

<Favicon url="https://excalidraw.com" size="24" /> **Excalidraw** — інструмент для швидких схем, начерків і блок-схем.

Підходить для:

- початкового планування екранів;
- схем User Flow;
- обговорення структури;
- швидкого малювання Low-Fidelity Wireframes.

### 18.4. Mermaid

Mermaid підходить для схем, які зберігаються разом із Markdown-документацією.

Особливо корисний для:

- User Flows;
- діаграм переходів;
- простих схем взаємодії;
- документації поруч із кодом.

Mermaid не замінює повноцінний графічний редактор для детальних UI-макетів, але добре працює для текстових діаграм.

### 18.5. Що вибрати для навчального проєкту

Для невеликого проєкту можна почати з паперу або Excalidraw, а потім перенести важливі екрани у Figma.

Не потрібно освоювати всі інструменти одночасно. Важливіше зрозуміти принципи планування, ніж витратити багато часу на вибір програмного забезпечення.

## 20. Як перевірити якість Wireframe

Перед початком реалізації пройдися по основних екранах.

### Структура

    ✔ У кожного екрана є зрозуміла мета.
    ✔ Основні елементи розташовані логічно.
    ✔ Контент має зрозумілу ієрархію.
    ✔ Повторювані елементи організовані послідовно.

### Взаємодія

    ✔ Основна дія помітна.
    ✔ Другорядні дії не заважають основній.
    ✔ Навігація зрозуміла.
    ✔ Передбачені переходи до наступних екранів.
    ✔ Є спосіб скасувати дію, якщо це потрібно.

### Стани

    ✔ Продумано завантаження.
    ✔ Продумано порожній стан.
    ✔ Продумано відображення помилок.
    ✔ Визначено поведінку після успіху.

### Адаптивність

    ✔ Важливий контент не зникає на вузьких екранах.
    ✔ Передбачено зміну кількості колонок.
    ✔ Кнопки та поля залишаються зручними.
    ✔ Навігація має зрозумілий мобільний варіант.

### Доступність

    ✔ Є місце для видимих підписів полів.
    ✔ Передбачена логічна ієрархія заголовків.
    ✔ Інтерактивні елементи мають зрозумілі призначення.
    ✔ Можна передбачити видимий фокус та клавіатурну навігацію.

## 21. Типові помилки під час Wireframing

### Помилка 1. Занадто рано переходити до візуального дизайну

На початковому етапі розробник витрачає час на кольори, тіні, іконки та декоративні деталі, хоча структура екрана ще не визначена.

Краще спочатку вирішити, які елементи потрібні та як користувач ними користуватиметься.

### Помилка 2. Створювати екрани без конкретної мети

Кожна сторінка повинна відповідати певній потребі або сценарію.

Якщо незрозуміло, навіщо потрібен екран, потрібно повернутися до вимог.

### Помилка 3. Планувати тільки успішний стан

Порожні списки, завантаження та помилки часто впливають на структуру сторінки.

Їх краще передбачити до реалізації, а не додавати поспіхом наприкінці.

### Помилка 4. Ігнорувати мобільні екрани

Навіть якщо основна розробка ведеться на комп'ютері, інтерфейс може використовуватися на телефоні.

Потрібно заздалегідь визначити, як змінюватиметься структура.

### Помилка 5. Надто деталізувати кожен елемент

Wireframe не повинен відтворювати весь майбутній CSS.

На ранньому етапі достатньо показати основну структуру, розташування елементів і взаємодію.

### Помилка 6. Плутати Wireframe з готовим UI

Wireframe показує структуру. Він не обов'язково визначає остаточні кольори, шрифти, тіні та декоративні ефекти.

### Помилка 7. Створювати забагато компонентів

Не кожен блок на Wireframe повинен стати окремим React-компонентом.

Спочатку визначай логічну структуру, а потім обирай межі компонентів відповідно до їхніх обов'язків.

### Помилка 8. Не узгоджувати макети з вимогами

Якщо Wireframe показує кнопку або поле, яких немає у вимогах, потрібно з'ясувати, чи справді ця функція необхідна.

Макет повинен допомагати реалізувати продукт, а не безконтрольно розширювати його обсяг.

## 22. Практична вправа

Спробуй спланувати три екрани для Worship Schedule.

### Екран 1. Список розкладів

Мета:

    Користувач може переглядати власні розклади
    та переходити до основних дій.

    - кнопку створення;

    - заголовок;
    - поля введення;
    - основну кнопку збереження;
    - кнопку скасування;
    - місце для помилок;
    - стан збереження.

Мета:

    Користувач може прочитати вміст розкладу
    та перейти до доступних дій.

Передбач:

    - назву;
    - основний вміст;
    - дату оновлення, якщо вона потрібна;
    - кнопку редагування;
    - дію видалення, якщо вона дозволена;
    - перехід до списку.

    1. Прочитати User Stories.
    2. Визначити мету кожного екрана.
    3. Створити Screen Inventory.
    4. Намалювати Low-Fidelity Wireframes.
    5. Позначити основні дії.
    6. Додати важливі UI-стани.
    7. Перевірити User Flows.
    8. Перевірити мобільну структуру.
    9. Перейти до HTML/CSS або React.

Не потрібно прагнути до ідеального макета з першої спроби. Мета вправи — навчитися планувати структуру до програмування.

## 25. Мінішпаргалка

### Основні поняття

    Screen Planning:
        визначення потрібних екранів та їхніх цілей.

        перелік екранів застосунку.

## 26. Головне, що потрібно запам'ятати

Wireframes and Screen Planning допомагають визначити структуру майбутнього інтерфейсу до початку програмування.

Під час планування:

1. Починай із потреб користувача.
2. Визначай мету кожного екрана.
3. Складай перелік необхідних екранів.
4. Розташовуй контент відповідно до його важливості.
5. Визначай основні та другорядні дії.
6. Передбачай стани завантаження, порожніх даних і помилок.
7. Враховуй мобільну версію та доступність.
8. Використовуй Wireframes для виявлення повторюваних UI-елементів.
9. Пов'язуй макети з User Stories та User Flows.
10. Не деталізуй візуальне оформлення, доки не зрозуміла основна структура.

**Ключова думка:** хороший Wireframe показує не те, наскільки гарно виглядатиме застосунок, а те, як буде організований його інтерфейс і як користувач зможе виконати потрібне завдання.
