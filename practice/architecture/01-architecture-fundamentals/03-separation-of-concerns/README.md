
# Separation of Concerns (SoC) — розділення відповідальностей

**Separation of Concerns (SoC)** — це принцип проєктування програмного забезпечення, відповідно до якого різні частини програми повинні відповідати за різні завдання.

Головна ідея: **кожна частина коду повинна мати чітко визначену відповідальність, а різні за своєю природою завдання не потрібно змішувати в одному місці.**

Наприклад, у вебзастосунку можна розділити:
- отримання HTTP-запиту;
- перевірку вхідних даних;
- виконання бізнес-логіки;
- роботу з базою даних;
- формування відповіді;
- відображення даних в інтерфейсі.

Якщо весь цей код розміщений в одній функції, її складно тестувати, змінювати та повторно використовувати. Якщо ж відповідальності розділені, кожну частину можна розвивати незалежніше.

---

## 1. Навіщо потрібен Separation of Concerns?

У невеликих програмах змішування відповідальностей може здаватися зручним. Але зі зростанням застосунку це ускладнює підтримку коду.

### Проблеми змішаних відповідальностей

- Одна функція виконує багато різних завдань.
- Зміна одного правила може вимагати змін у багатьох місцях.
- Бізнес-логіка залежить від деталей HTTP, інтерфейсу або бази даних.
- Код складніше тестувати без запуску всього застосунку.
- Однакову логіку доводиться копіювати.
- Помилки складніше знаходити, оскільки різні завдання переплетені.

### Переваги розділення відповідальностей

✔ Код легше читати й розуміти.

✔ Кожна частина має чітке призначення.

✔ Зміни можна локалізувати в одному модулі.

✔ Бізнес-логіку простіше тестувати окремо.

✔ Компоненти легше повторно використовувати.

✔ Проєкт простіше розширювати без постійного переписування наявного коду.

---

## 2. Основна ідея: одне місце — одна чітка відповідальність

Separation of Concerns не означає, що кожна функція повинна містити лише один рядок або що кожен рядок коду потрібно винести в окремий файл.

Йдеться про **логічне розділення різних типів завдань**.

Наприклад, функція може перевіряти декілька пов'язаних умов, якщо всі вони належать до однієї відповідальності.

    function calculateTotal(price, quantity) {
        return price * quantity;
    }

Ця функція відповідає за обчислення загальної вартості.

Інша функція може відповідати за перевірку даних:

    function validateOrder(price, quantity) {
        return (
            Number.isFinite(price) &&
            Number.isFinite(quantity) &&
            price > 0 &&
            quantity > 0
        );
    }

А третя — за об'єднання цих операцій у процес оформлення замовлення:

    function createOrder(price, quantity) {
        if (!validateOrder(price, quantity)) {
            throw new Error("Invalid order data");
        }

        return {
            price,
            quantity,
            total: calculateTotal(price, quantity),
        };
    }

Тепер кожна функція має зрозуміле призначення:
- `validateOrder()` — перевіряє дані;
- `calculateTotal()` — обчислює суму;
- `createOrder()` — організовує створення замовлення.

**Важливо:** розділення відповідальностей не забороняє функціям взаємодіяти. Навпаки, вони можуть співпрацювати через зрозумілі інтерфейси.

## 3. Поганий приклад: усі відповідальності в одному місці

Розглянемо серверний обробник, який створює користувача.

    async function createUserHandler(req, res) {
        const { name, email } = req.body;

        if (!name || !email) {
            return res.status(400).json({
                error: "Name and email are required",
            });
        }

        const existingUser = await db.query(
            "SELECT id FROM users WHERE email = $1",
            [email]
        );

        if (existingUser.rows.length > 0) {
            return res.status(409).json({
                error: "Email already exists",
            });
        }

        const result = await db.query(
            "INSERT INTO users (name, email) VALUES ($1, $2) RETURNING id, name, email",
            [name, email]
        );

        console.log("User created:", result.rows[0].id);

        return res.status(201).json({
            user: result.rows[0],
        });
    }

У цьому обробнику змішані різні відповідальності:

1. Отримання даних із HTTP-запиту.
2. Перевірка вхідних даних.
3. Перевірка бізнес-правила щодо унікальності email.
4. Виконання SQL-запитів.
5. Логування.
6. Формування HTTP-відповідей.

Це не означає, що такий код ніколи не працюватиме. Проблема в тому, що зі зростанням функціональності його буде дедалі складніше підтримувати.

Наприклад:
- якщо зміниться база даних, потрібно редагувати обробник;
- якщо зміниться правило створення користувача, потрібно редагувати обробник;
- якщо бізнес-логіку потрібно протестувати окремо, це буде незручно;
- якщо створення користувача знадобиться з іншого місця, код може почати дублюватися.

## 4. Кращий підхід: розділяємо відповідальності

Для невеликого Node.js-застосунку можна використати три основні частини:

    src/
    ├── users/
    │   ├── users.controller.js
    │   ├── users.service.js
    │   └── users.repository.js
    ├── app.js
    └── server.js

У цьому прикладі:
- `controller` працює з HTTP;
- `service` організовує бізнес-логіку;
- `repository` працює з базою даних.

### 4.1. Controller — HTTP-відповідальність

    // users.controller.js

    import { createUser } from "./users.service.js";

    export async function createUserHandler(req, res) {
        try {
            const user = await createUser(req.body);

            return res.status(201).json({ user });
        } catch (error) {
            if (error.message === "Email already exists") {
                return res.status(409).json({
                    error: error.message,
                });
            }

            if (error.message === "Invalid user data") {
                return res.status(400).json({
                    error: error.message,
                });
            }

            return res.status(500).json({
                error: "Internal server error",
            });
        }
    }

Контролер відповідає за взаємодію з HTTP: отримання запиту та формування відповіді.

У реальному проєкті обробку помилок часто централізують у middleware або окремому механізмі обробки винятків, щоб не дублювати `try/catch` у кожному контролері.

### 4.2. Service — бізнес-логіка

    // users.service.js

    import {
        findUserByEmail,
        insertUser,
    } from "./users.repository.js";

    export async function createUser(data) {
        const { name, email } = data;

        if (
            typeof name !== "string" ||
            name.trim() === "" ||
            typeof email !== "string" ||
            email.trim() === ""
        ) {
            throw new Error("Invalid user data");
        }

        const normalizedEmail = email.trim().toLowerCase();

        const existingUser = await findUserByEmail(normalizedEmail);

        if (existingUser) {
            throw new Error("Email already exists");
        }

        return insertUser({
            name: name.trim(),
            email: normalizedEmail,
        });
    }

Сервіс відповідає за процес створення користувача:
- перевіряє необхідні дані;
- нормалізує email;
- перевіряє наявність користувача;
- викликає операцію збереження.

Тут розміщена прикладна бізнес-логіка, а не деталі HTTP-відповідей.

У виробничому коді варто використовувати окремі класи або типи помилок замість порівняння `error.message`.

### 4.3. Repository — доступ до даних

    // users.repository.js

    import { pool } from "../database.js";

    export async function findUserByEmail(email) {
        const result = await pool.query(
            "SELECT id, name, email FROM users WHERE email = $1",
            [email]
        );

        return result.rows[0] ?? null;
    }

    export async function insertUser({ name, email }) {
        const result = await pool.query(
            `INSERT INTO users (name, email)
             VALUES ($1, $2)
             RETURNING id, name, email`,
            [name, email]
        );

        return result.rows[0];
    }

Репозиторій відповідає за запити до бази даних.

Він не повинен знати, який HTTP-статус потрібно повернути клієнту. Його завдання — отримати або зберегти дані.

**Результат:** кожна частина має власну відповідальність, а весь процес працює завдяки їхній взаємодії.

## 5. Separation of Concerns у NestJS

У NestJS розділення відповідальностей є важливою частиною типового підходу до організації застосунку.

Наприклад:

    src/
    ├── users/
    │   ├── dto/
    │   │   └── create-user.dto.ts
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   ├── users.repository.ts
    │   └── users.module.ts
    ├── app.module.ts
    └── main.ts

Призначення файлів:

| Файл | Відповідальність |
|---|---|
| `users.controller.ts` | Обробка HTTP-запитів |
| `users.service.ts` | Бізнес-логіка |
| `users.repository.ts` | Доступ до бази даних |
| `create-user.dto.ts` | Форма та правила вхідних даних |
| `users.module.ts` | Об'єднання компонентів модуля |
| `main.ts` | Запуск застосунку |

Це типовий варіант організації, а не обов'язкова структура для кожного проєкту. Наприклад, окремий репозиторій може бути непотрібним у дуже простому застосунку.

### 5.1. DTO — форма вхідних даних

    // create-user.dto.ts

    import { IsEmail, IsNotEmpty, IsString } from "class-validator";

    export class CreateUserDto {
        @IsString()
        @IsNotEmpty()
        name: string;

        @IsEmail()
        email: string;
    }

DTO описує структуру даних, які приймає застосунок.

Щоб перевірка декораторів працювала, у NestJS потрібно налаштувати `ValidationPipe`, наприклад глобально.

    // main.ts

    import { ValidationPipe } from "@nestjs/common";
    import { NestFactory } from "@nestjs/core";
    import { AppModule } from "./app.module";

    async function bootstrap() {
        const app = await NestFactory.create(AppModule);

        app.useGlobalPipes(
            new ValidationPipe({
                whitelist: true,
                forbidNonWhitelisted: true,
                transform: true,
            })
        );

        await app.listen(3000);
    }

    bootstrap();

DTO не замінює бізнес-логіку. Він допомагає визначити та перевірити формат вхідних даних, а бізнес-правила залишаються у відповідному шарі.

### 5.2. Controller

    // users.controller.ts

    import { Body, Controller, Post } from "@nestjs/common";
    import { CreateUserDto } from "./dto/create-user.dto";
    import { UsersService } from "./users.service";

    @Controller("users")
    export class UsersController {
        constructor(private readonly usersService: UsersService) {}

        @Post()
        create(@Body() dto: CreateUserDto) {
            return this.usersService.create(dto);
        }
    }

Контролер не повинен самостійно виконувати SQL-запити або реалізовувати складні бізнес-правила.

Його основна роль — прийняти запит і передати роботу відповідному компоненту.

### 5.3. Service

    // users.service.ts

    import {
        ConflictException,
        Injectable,
    } from "@nestjs/common";
    import { CreateUserDto } from "./dto/create-user.dto";
    import { UsersRepository } from "./users.repository";

    @Injectable()
    export class UsersService {
        constructor(
            private readonly usersRepository: UsersRepository
        ) {}

        async create(dto: CreateUserDto) {
            const email = dto.email.trim().toLowerCase();

            const existingUser =
                await this.usersRepository.findByEmail(email);

            if (existingUser) {
                throw new ConflictException(
                    "Email already exists"
                );
            }

            return this.usersRepository.create({
                name: dto.name.trim(),
                email,
            });
        }
    }

Сервіс керує сценарієм створення користувача.

У реальному застосунку остаточну унікальність email потрібно також забезпечити обмеженням `UNIQUE` у базі даних. Перевірка в сервісі сама по собі не захищає від одночасних запитів.

### 5.4. Чому це важливо?

Якщо завтра потрібно змінити спосіб збереження користувачів, не обов'язково переписувати контролер.

Якщо зміниться HTTP-маршрут, це не повинно вимагати зміни SQL-запитів.

Якщо потрібно протестувати бізнес-правило, сервіс можна тестувати окремо від HTTP-сервера.

Саме так розділення відповідальностей допомагає підтримувати застосунок у міру його розвитку.

## 6. Separation of Concerns на різних рівнях

Розділяти відповідальності можна не лише між функціями або файлами.

### 6.1. На рівні функцій

Кожна функція виконує зрозуміле завдання.

    function calculateAverage(total, count) {
        if (count <= 0) {
            throw new Error("Count must be positive");
        }

        return total / count;
    }

### 6.2. На рівні класів

Клас об'єднує поведінку та дані, які логічно належать до однієї відповідальності.

Не варто створювати один клас, який одночасно обробляє HTTP-запити, надсилає email, виконує SQL-запити та формує HTML.

### 6.3. На рівні модулів

Модуль об'єднує компоненти, що працюють із певною функціональною областю.

    src/
    ├── users/
    ├── courses/
    ├── lessons/
    └── auth/

Наприклад, у навчальному застосунку модуль `courses` може відповідати за курси, а модуль `users` — за користувачів.

### 6.4. На рівні шарів

Різні шари виконують різні технічні або прикладні ролі.

    HTTP Controller
          |
          v
       Service
          |
          v
      Repository
          |
          v
       Database

Це спрощена схема. Реальна архітектура може мати додаткові шари, інтерфейси, сервіси інтеграції або інші компоненти.

### 6.5. На рівні інтерфейсу та сервера

Frontend відповідає за взаємодію з користувачем, а backend — за серверну обробку, бізнес-правила та доступ до даних.

Наприклад:
- React-компонент відображає форму;
- frontend перевіряє дані для зручності користувача;
- backend повторно перевіряє дані;
- серверна бізнес-логіка виконує потрібну операцію;
- база даних зберігає результат.

Перевірки на frontend не замінюють серверну валідацію, оскільки клієнтський код можна обійти.

## 7. Separation of Concerns і Single Responsibility Principle

Ці поняття пов'язані, але не тотожні.

### Separation of Concerns (SoC)

Загальний принцип: різні типи відповідальностей потрібно розділяти між відповідними частинами системи.

Наприклад, відображення інтерфейсу, бізнес-логіка та доступ до бази даних не повинні бути без потреби змішані.

### Single Responsibility Principle (SRP)

Принцип SOLID, який вимагає, щоб модуль або клас мав одну відповідальність у сенсі однієї причини для зміни.

Наприклад, клас, який одночасно генерує звіт і надсилає його електронною поштою, може мати дві незалежні причини для зміни:
- змінилися правила формування звіту;
- змінився механізм надсилання email.

Це сигнал, що відповідальності, можливо, варто розділити.

### Головна відмінність

- SoC — ширший принцип організації системи.
- SRP — конкретніший принцип проєктування модулів і класів.

SRP допомагає реалізовувати SoC на рівні окремих програмних компонентів.

## 8. Separation of Concerns і Code Organization

Розділення відповідальностей впливає на організацію файлів, але ці поняття не означають одне й те саме.

**Code Organization** — це те, як код організовано у файлах, теках, модулях і пакетах.

**Separation of Concerns** — це те, як відповідальності розподілені між цими частинами.

Наприклад, можна створити окремі файли, але все одно змішати відповідальності:

    src/
    ├── users.js
    ├── courses.js
    └── reports.js

Якщо `users.js` одночасно відповідає за HTTP, SQL, надсилання листів і складні бізнес-правила, сама наявність окремого файлу не вирішує проблему.

І навпаки, невеликий модуль може містити кілька пов'язаних функцій і при цьому мати чітку відповідальність.

**Важливо:** хороша структура файлів повинна відображати логічну структуру програми, а не просто збільшувати кількість тек.

## 9. Separation of Concerns і Coupling

Coupling — це ступінь залежності одного компонента від іншого.

Коли компонент безпосередньо залежить від багатьох деталей інших компонентів, зміни можуть поширюватися по всій системі.

Наприклад, сервіс, який сам створює SQL-запити, відкриває HTTP-з'єднання та формує відповіді, тісно пов'язаний із конкретними технологіями.

Краще розділити ролі та визначити зрозумілі способи взаємодії між компонентами.

Однак SoC не означає, що всі компоненти мають бути повністю незалежними. Вони повинні взаємодіяти, але робити це через зрозумілі контракти.

Наприклад, сервіс може залежати від методу репозиторію:

    const user = await usersRepository.findByEmail(email);

Сервісу важливо знати, яку операцію надає репозиторій, а не обов'язково знати всі деталі виконання SQL-запиту.

Для великих застосунків таку залежність можна додатково ізолювати через інтерфейси та Dependency Injection.

## 10. Separation of Concerns і Cohesion

Cohesion — це те, наскільки добре елементи одного модуля пов'язані між собою за призначенням.

У добре спроєктованому модулі функції та класи об'єднані спільною метою.

Наприклад, модуль `users` може містити операції створення користувача, пошуку за email і зміни профілю.

Натомість розміщення в цьому модулі не пов'язаних із користувачами операцій обробки платежів або формування розкладу може свідчити про недостатню узгодженість відповідальностей.

Корисний орієнтир:

- **High cohesion** — елементи модуля логічно пов'язані.
- **Low coupling** — компоненти не залежать надмірно від деталей один одного.

Ці цілі часто допомагають реалізувати Separation of Concerns, хоча самі по собі не замінюють аналізу вимог і меж модулів.

## 11. Як визначити, що відповідальності змішані?

Звертай увагу на такі ознаки.

### Ознака 1. Функція виконує багато різних завдань

Наприклад, функція одночасно:
- перевіряє форму;
- обчислює суму;
- записує дані в базу;
- надсилає email;
- формує HTML.

Не обов'язково розділяти кожну операцію, але варто перевірити, чи не змішані тут незалежні причини для зміни.

### Ознака 2. Назва функції занадто загальна

Наприклад:

    function processData(data) {
        // Багато різних операцій
    }

Назва не пояснює, що саме робить функція.

Зрозуміліші назви можуть бути такими:

    validateUserData(data);
    calculateOrderTotal(items);
    saveUser(user);
    sendWelcomeEmail(user);

### Ознака 3. Зміна однієї технології зачіпає багато компонентів

Якщо перехід із PostgreSQL на іншу базу даних вимагає змінювати React-компоненти, це може свідчити про невдале розділення відповідальностей або порушені межі між frontend і backend.

### Ознака 4. Код важко протестувати окремо

Якщо для перевірки обчислення потрібно запускати HTTP-сервер, підключатися до реальної бази даних і надсилати email, можливо, деякі відповідальності варто ізолювати.

### Ознака 5. Одна й та сама логіка дублюється

Якщо однакове бізнес-правило реалізоване в кількох місцях, варто визначити, який компонент повинен бути відповідальним за нього.

Водночас не вся схожість коду означає, що його треба об'єднувати: різні частини системи можуть мати різні вимоги й незалежно змінюватися.

## 12. Типові помилки під час застосування SoC

### Помилка 1. Один великий компонент для всього

Коли контролер виконує SQL-запити, перевіряє всі бізнес-правила й надсилає повідомлення, його важко змінювати.

**Краще:** розподілити відповідальності між контролером, сервісом і компонентом доступу до даних там, де це справді виправдано.

### Помилка 2. Надмірне розділення

Не варто створювати окремий клас або файл для кожного простого виразу.

Надмірна декомпозиція призводить до:
- великої кількості файлів;
- складної навігації;
- зайвих рівнів абстракції;
- труднощів у розумінні простого процесу.

**Краще:** розділяти логічно різні відповідальності, а не механічно розбивати код.

### Помилка 3. Плутати кількість файлів із якістю архітектури

Десять файлів не гарантують кращої архітектури, ніж три.

Важливіше, щоб кожен компонент мав зрозуміле призначення, а залежності між компонентами були виправданими.

### Помилка 4. Дублювати бізнес-правила на різних рівнях

Наприклад, правило визначення вартості замовлення може бути реалізоване в React, контролері та сервісі незалежно одне від одного.

Краще визначити одне авторитетне місце для серверної бізнес-логіки. Frontend може повторювати прості перевірки для зручності, але сервер повинен залишатися джерелом істини.

### Помилка 5. Переносити весь код у Service

Створення сервісу саме по собі не розділяє відповідальності.

Якщо `UsersService` містить HTTP-статуси, SQL-запити, HTML-шаблони та логіку надсилання email, проблема залишається.

### Помилка 6. Вважати, що кожному проєкту потрібна складна архітектура

Для маленького навчального застосунку може бути достатньо кількох модулів і функцій.

Архітектура має відповідати складності проєкту, а не створювати додаткову складність без практичної користі.

### Помилка 7. Розділяти код лише за технічними типами

Структура `controllers/`, `services/`, `repositories/` часто корисна, але зі зростанням застосунку може бути зручніше групувати код за функціональними областями: `users/`, `courses/`, `payments/`.

Вибір залежить від масштабу, складності та способу розвитку застосунку.

## 13. Практичний приклад: розклад занять

Уявімо застосунок для створення розкладу занять.

Користувач хоче:
1. Створити розклад.
2. Додати заняття.
3. Зберегти дані.
4. Побачити результат на сторінці.

Без розділення відповідальностей усі операції можуть опинитися в одному компоненті або обробнику.

Краще визначити відповідальності заздалегідь.

| Компонент | Відповідальність |
|---|---|
| React-компонент | Відображення розкладу та взаємодія з користувачем |
| API-клієнт | Надсилання HTTP-запитів до backend |
| Controller | Обробка HTTP-запитів на сервері |
| DTO | Опис і валідація вхідних даних |
| Service | Правила створення та редагування розкладу |
| Repository | Збереження та отримання даних |
| PostgreSQL | Постійне зберігання даних |

Спрощена схема:

    Користувач
        |
        v
    React UI
        |
        v
    API-клієнт
        |
        v
    NestJS Controller
        |
        v
    DTO Validation
        |
        v
    NestJS Service
        |
        v
    Repository
        |
        v
    PostgreSQL

Ця схема не є єдино правильною. Вона показує один зі способів відокремити інтерфейс, транспорт, бізнес-логіку та зберігання даних.

### Що зміниться, якщо потрібно додати PDF-експорт?

Якщо експорт PDF реалізований окремим компонентом, його можна додати без суттєвого переписування логіки створення розкладу.

Наприклад, сервіс експорту може отримати дані розкладу та сформувати документ. Контролер може надати окремий маршрут для завантаження PDF.

Це приклад того, як чіткі відповідальності полегшують розширення застосунку.

## 14. Практичні правила для щоденної роботи

Перед тим як створювати нову функцію, клас або модуль, постав собі кілька запитань.

1. **Яку конкретну відповідальність він виконує?**
2. Чи є в нього декілька незалежних причин для зміни?
3. Чи не виконує він роботу іншого шару?
4. Чи можна протестувати його основну поведінку окремо?
5. Чи залежить він від деталей, які йому не потрібні?
6. Чи справді потрібен новий файл або клас?
7. Чи зрозуміло, як цей компонент взаємодіє з іншими?

Не потрібно механічно вимагати позитивної відповіді на кожне запитання. Це орієнтири для оцінювання структури, а не суворий набір правил.

### Простий алгоритм рефакторингу

1. Знайди функцію або модуль, у якому змішані різні відповідальності.
2. Визнач окремі завдання, які він виконує.
3. Вибери відповідні межі між компонентами.
4. Перенеси пов'язану поведінку в окремі функції або модулі.
5. Визнач, які дані передаються між компонентами.
6. Перевір, що код продовжує працювати.
7. Додай або онови тести.
8. Переконайся, що нова структура стала зрозумілішою, а не просто більшою.

---

## 15. Як перевірити розділення відповідальностей тестами?

Добре розділені компоненти зазвичай простіше тестувати окремо.

Наприклад, функцію обчислення вартості можна протестувати без HTTP-сервера та бази даних.

    import { describe, expect, it } from "vitest";

    function calculateTotal(price, quantity) {
        return price * quantity;
    }

    describe("calculateTotal", () => {
        it("calculates the total price", () => {
            expect(calculateTotal(100, 3)).toBe(300);
        });
    });

Такий тест перевіряє конкретну поведінку без зайвих залежностей.

Сервіс, який використовує репозиторій, можна тестувати окремо, підставивши тестову реалізацію репозиторію або mock.

А контролер можна перевіряти на рівні HTTP-тестів, щоб упевнитися, що маршрути, статуси та відповіді працюють правильно.

**Важливо:** розділення відповідальностей не означає, що всі тести повинні бути ізольованими. Інтеграційні та наскрізні тести теж потрібні, щоб перевіряти взаємодію компонентів.

## 16. Що варто запам'ятати

✔ Separation of Concerns — це розділення різних відповідальностей між частинами програми.

✔ Основна мета — зменшити складність і зробити код легшим для змін, тестування та підтримки.

✔ Розділення можна застосовувати на рівні функцій, класів, модулів, шарів і всієї системи.

✔ У типовому NestJS-застосунку контролер відповідає за HTTP, сервіс — за прикладну логіку, а репозиторій — за доступ до даних.

✔ DTO допомагає описувати та перевіряти форму вхідних даних, але не замінює бізнес-правила.

✔ SoC пов'язаний із SRP, coupling і cohesion, але це різні поняття.

✔ Хороша архітектура не вимагає максимальної кількості файлів або класів.

✔ Компоненти можуть взаємодіяти — важливо, щоб їхні ролі та межі були зрозумілими.

✔ Бізнес-логіка не повинна без потреби залежати від HTTP, UI або деталей бази даних.

✔ Структура має відповідати реальним потребам застосунку.

## 19. Мінішпаргалка

| Поняття | Коротке пояснення |
|---|---|
| Separation of Concerns | Розділення різних відповідальностей |
| Single Responsibility Principle | Одна відповідальність у сенсі однієї причини для зміни |
| Controller | Обробка HTTP-запитів і відповідей |
| Service | Виконання прикладної та бізнес-логіки |
| Repository | Доступ до даних |
| DTO | Опис структури вхідних або вихідних даних |
| Coupling | Ступінь залежності компонентів |
| Cohesion | Наскільки логічно пов'язані елементи одного модуля |
| Refactoring | Зміна внутрішньої структури без зміни зовнішньої поведінки |

### Головна думка

**Розділяй код за відповідальностями, а не просто за кількістю функцій або файлів.**

Кожен компонент повинен мати зрозуміле призначення. Інші компоненти мають взаємодіяти з ним через чіткі межі. Це допомагає змінювати одну частину застосунку, не переписуючи без потреби решту системи.

Separation of Concerns — не вимога зробити архітектуру максимально складною. Це спосіб керувати складністю та зберігати код зрозумілим у міру зростання проєкту.
