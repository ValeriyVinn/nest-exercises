## 02. Code Organization

Code Organization (організація коду) — це спосіб структурування програмного коду у файлах, папках, модулях, класах і функціях, щоб система була зрозумілою, послідовною, підтримуваною та зручною для подальшого розвитку.

Організація коду визначає, де розміщується певна функціональність, як пов'язані між собою частини програми та як розробник знаходить, змінює й тестує потрібний код.

Code Organization використовується, коли потрібно:

- організувати файли та папки проєкту;
- розділити код за функціональністю;
- групувати пов'язані компоненти;
- визначити місце для бізнес-логіки;
- відокремити frontend, backend і database;
- розділити відповідальності між класами та функціями;
- уникнути надмірно великих файлів;
- зменшити дублювання коду;
- зробити залежності між компонентами зрозумілими;
- спростити тестування та рефакторинг;
- підготувати проєкт до зростання;
- підтримувати єдиний стиль організації коду в команді.

### Що потрібно пам'ятати

• Code Organization визначає, як код розподілено між файлами, папками, модулями та іншими структурними елементами.

• Хороша організація коду допомагає швидко знаходити потрібну функціональність.

• Структура папок повинна відображати логіку проєкту, а не бути випадковим набором директорій.

• Один файл не повинен автоматично містити всю функціональність застосунку.

• Не потрібно створювати окремий файл для кожного рядка коду або кожної дрібної операції.

• Пов'язані компоненти доцільно групувати разом.

• Код різних відповідальностей бажано розділяти.

• Модуль повинен мати зрозуміле призначення.

• Назви файлів, папок, функцій і класів повинні пояснювати їхнє призначення.

• Повторне використання коду може зменшити дублювання, але надмірна універсалізація також ускладнює систему.

• Існують різні підходи до організації коду: за шарами, функціональністю та предметною областю.

• Не існує єдиної структури папок, яка найкраще підходить для всіх проєктів.

• Структура невеликого застосунку може бути простою, а зі зростанням проєкту її можна поступово вдосконалювати.

• Хороша організація коду допомагає підтримувати архітектуру, але сама по собі не гарантує її правильності.

• Організація коду повинна полегшувати зміни, тестування та розуміння системи.

# Code Organization

## Що таке організація коду

Code Organization — це спосіб розміщення та групування коду, щоб розробник міг зрозуміти структуру програми й знайти потрібну функціональність.

Наприклад, у невеликому Node.js-застосунку можна почати з такої структури:

    my-app/
    ├── package.json
    ├── server.js
    └── README.md

Для простого навчального прикладу цього може бути достатньо.

Коли функціональність зростає, структура може стати такою:

    my-app/
    ├── package.json
    ├── src/
    │   ├── server.js
    │   ├── routes/
    │   ├── controllers/
    │   ├── services/
    │   └── repositories/
    ├── tests/
    └── README.md

Тепер код розподілений за призначенням.

Однак сама наявність папок `routes`, `controllers`, `services` і `repositories` ще не означає, що код правильно організований.

Важливо, щоб:

- кожна частина мала зрозумілу відповідальність;
- назви відповідали призначенню;
- залежності були логічними;
- код можна було знаходити без зайвих пошуків;
- зміни не вимагали безпідставного редагування багатьох файлів.

# Code Organization vs Software Architecture

Code Organization і Software Architecture пов'язані, але не тотожні.

## Code Organization

Відповідає переважно на запитання:

    Де розміщений код?
    Як називаються файли?
    Як згруповані модулі?
    Де зберігаються тести?
    Де розташована конфігурація?

Наприклад:

    src/
    ├── users/
    │   ├── users.controller.ts
    │   └── users.service.ts
    └── products/
        ├── products.controller.ts
        └── products.service.ts

## Software Architecture

Відповідає на ширші запитання:

    За що відповідає кожен компонент?
    Як компоненти взаємодіють?
    Які залежності дозволені?
    Як ізольована бізнес-логіка?
    Як організована робота з даними?
    Як система повинна розвиватися?

Наприклад, дві системи можуть мати однакову структуру папок, але різну архітектуру залежностей.

У першій системі сервіси залежать від чітко визначених контрактів.

У другій сервіси безпосередньо залежать від конкретних баз даних, HTTP-запитів та зовнішніх API.

Отже:

    Code Organization
        → організація коду

    Software Architecture
        → фундаментальна структура системи,
          її межі, компоненти та залежності

Хороша Code Organization допомагає реалізувати хорошу Software Architecture.

# File Organization

File Organization — організація коду за окремими файлами.

У JavaScript і TypeScript файли часто використовуються для групування пов'язаних функцій, класів, типів та інших елементів.

Наприклад, не варто без потреби розміщувати всю функціональність застосунку в одному файлі.

Проблемний приклад:

    // app.js

    function createUser() {
        // ...
    }

    function deleteUser() {
        // ...
    }

    function createCourse() {
        // ...
    }

    function deleteCourse() {
        // ...
    }

    function sendEmail() {
        // ...
    }

    function connectDatabase() {
        // ...
    }

Для дуже маленького навчального прикладу така організація може бути прийнятною. Проте зі зростанням програми знайти потрібну функціональність буде складніше.

Можна розділити код:

    src/
    ├── users/
    │   ├── create-user.js
    │   └── delete-user.js
    ├── courses/
    │   ├── create-course.js
    │   └── delete-course.js
    ├── email/
    │   └── send-email.js
    └── database/
        └── connect-database.js

Це лише один варіант. Якщо функції тісно пов'язані між собою, їх можна групувати в одному модулі, а не створювати окремий файл для кожної.

## Коли створювати окремий файл

Окремий файл доцільний, коли:

- код має чітке призначення;
- компонент використовується в кількох місцях;
- файл став занадто великим;
- компонент має власну відповідальність;
- його потрібно тестувати окремо;
- він належить до іншої функціональної області;
- його реалізацію потрібно приховати за публічним інтерфейсом.

Не потрібно механічно ділити код за кількістю рядків. Розмір файлу — лише один із сигналів.

Головний критерій — зрозумілість і логічність структури.

# Folder Structure

Folder Structure — організація файлів у директоріях.

Папки допомагають групувати код за спільним призначенням.

Наприклад:

    src/
    ├── users/
    ├── courses/
    ├── authentication/
    ├── database/
    └── common/

У цьому прикладі:

    users/
        → функціональність користувачів

    courses/
        → функціональність курсів

    authentication/
        → автентифікація

    database/
        → компоненти роботи з базою даних

    common/
        → спільні компоненти

Папка `common` потребує особливої уваги. Не варто перетворювати її на місце для будь-якого коду, який незручно розмістити деінде.

Краще, щоб кожна папка мала зрозуміле призначення.

## Приклад структури невеликого застосунку

    src/
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.module.ts
    ├── courses/
    │   ├── courses.controller.ts
    │   ├── courses.service.ts
    │   └── courses.module.ts
    ├── app.module.ts
    └── main.ts

Це приклад організації NestJS-застосунку за функціональними модулями.

## Не варто створювати зайві рівні вкладеності

Наприклад:

    src/
    └── application/
        └── backend/
            └── modules/
                └── users/
                    └── services/
                        └── implementation/
                            └── users.service.ts

Така структура може бути виправдана в окремих складних проєктах, але для невеликого застосунку вона часто створює зайві переходи між папками.

Краще починати з простої структури та додавати рівні лише тоді, коли вони справді потрібні.

# Project Structure

Project Structure — загальна організація всього проєкту, включно з вихідним кодом, тестами, конфігурацією, документацією та іншими файлами.

Приклад Node.js / TypeScript-проєкту:

    my-app/
    ├── src/
    │   ├── users/
    │   ├── courses/
    │   └── main.ts
    ├── tests/
    ├── docs/
    ├── .env.example
    ├── .gitignore
    ├── package.json
    ├── tsconfig.json
    └── README.md

Призначення основних елементів:

    src/
        → вихідний код застосунку

    tests/
        → автоматизовані тести

    docs/
        → додаткова документація

    .env.example
        → приклад необхідних змінних середовища

    .gitignore
        → файли, які Git не повинен відстежувати

    package.json
        → метадані проєкту, scripts і залежності

    tsconfig.json
        → налаштування TypeScript

    README.md
        → опис проєкту та інструкції

Це лише поширений приклад. Точна структура залежить від мови, framework, інструментів і вимог проєкту.

## Source Code vs Configuration

Важливо розрізняти вихідний код і конфігурацію.

    Source Code
        → реалізація функціональності

    Configuration
        → параметри роботи застосунку

Наприклад:

    src/
        → TypeScript-файли

    package.json
        → залежності та scripts

    tsconfig.json
        → налаштування компіляції

    .env
        → локальні значення змінних середовища

Файли із секретами, наприклад паролями та API-ключами, не повинні потрапляти в Git-репозиторій.

# Основні підходи до Code Organization

Існує кілька поширених підходів до організації коду.

## 1. File-Based Organization

Код групується переважно за типом файлів або компонентів.

Приклад:

    src/
    ├── controllers/
    │   ├── users.controller.ts
    │   └── courses.controller.ts
    ├── services/
    │   ├── users.service.ts
    │   └── courses.service.ts
    ├── repositories/
    │   ├── users.repository.ts
    │   └── courses.repository.ts
    └── main.ts

Тут контролери, сервіси та репозиторії розміщені в окремих папках.

Переваги:

- легко зрозуміти загальне призначення папок;
- структура відповідає технічним ролям компонентів;
- підхід простий для невеликого застосунку.

Недоліки:

- компоненти однієї функціональної області розкидані по різних папках;
- зі зростанням проєкту пошук усієї функціональності певного модуля може ускладнитися.

Наприклад, для роботи з користувачами потрібно перейти до кількох папок:

    controllers/users.controller.ts
    services/users.service.ts
    repositories/users.repository.ts

Це не означає, що такий підхід неправильний. Він може добре працювати, коли технічні шари є основним способом організації системи.

---

## 2. Feature-Based Organization

Feature-Based Organization — організація коду за функціональними можливостями застосунку.

Пов'язані компоненти групуються разом.

Приклад:

    src/
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   ├── users.repository.ts
    │   └── users.module.ts
    ├── courses/
    │   ├── courses.controller.ts
    │   ├── courses.service.ts
    │   ├── courses.repository.ts
    │   └── courses.module.ts
    └── main.ts

У цьому випадку:

    users/
        → функціональність користувачів

    courses/
        → функціональність курсів

Переваги:

- пов'язаний код розташований поруч;
- простіше знаходити компоненти конкретної функції;
- легше розвивати окремі функціональні області;
- простіше визначати межі модулів.

Недоліки:

- потрібні правила організації спільного коду;
- між функціональними модулями можуть виникати небажані залежності;
- для маленьких застосунків така структура іноді може бути надмірною.

Feature-Based Organization часто зручна для backend-застосунків, зокрема NestJS.

---

## 3. Layer-Based Organization

Layer-Based Organization — організація коду за технічними шарами.

Приклад:

    src/
    ├── controllers/
    ├── services/
    ├── repositories/
    ├── entities/
    └── main.ts

Кожен шар виконує певну технічну роль.

Наприклад:

    Controller Layer
        → приймання запитів

    Service Layer
        → бізнес-операції

    Repository Layer
        → доступ до даних

    Database
        → збереження інформації

Переваги:

- легко зрозуміти роль кожного шару;
- зручно навчатися розділяти відповідальності;
- структура добре підходить для багатьох традиційних backend-застосунків.

Недоліки:

- компоненти однієї функції розташовані в різних папках;
- технічні шари можуть стати занадто великими;
- не завжди легко визначити межі предметної області.

Layer-Based Organization часто використовується разом із Feature-Based Organization.

Наприклад:

    src/
    ├── users/
    │   ├── controllers/
    │   ├── services/
    │   └── repositories/
    └── courses/
        ├── controllers/
        ├── services/
        └── repositories/

Це поєднання двох підходів.

---

## 4. Domain-Based Organization

Domain-Based Organization — організація коду за предметною областю, тобто за поняттями та правилами, що належать до бізнесу або задачі застосунку.

Наприклад, у навчальній системі:

    src/
    ├── students/
    ├── teachers/
    ├── courses/
    ├── lessons/
    └── enrollments/

Тут структура відображає основні поняття навчальної системи.

Domain-Based Organization може використовуватися разом із Domain-Driven Design, але це не одне й те саме.

Організація папок за предметними поняттями ще не означає, що застосунок побудований за принципами DDD.

Переваги:

- структура відображає предметну область;
- пов'язані бізнес-правила можна організувати разом;
- простіше визначати відповідальності модулів;
- зручно працювати зі складними бізнес-процесами.

Недоліки:

- потребує розуміння предметної області;
- межі доменів не завжди очевидні;
- надто складна доменна структура може бути зайвою для простого застосунку.

---

# Feature-Based vs Layer-Based Organization

Це два важливі підходи, які варто вміти порівнювати.

## Layer-Based

    src/
    ├── controllers/
    │   ├── users.controller.ts
    │   └── courses.controller.ts
    ├── services/
    │   ├── users.service.ts
    │   └── courses.service.ts
    └── repositories/
        ├── users.repository.ts
        └── courses.repository.ts

Групування відбувається за технічною роллю.

## Feature-Based

    src/
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.repository.ts
    └── courses/
        ├── courses.controller.ts
        ├── courses.service.ts
        └── courses.repository.ts

Групування відбувається за функціональністю.

## Порівняння

    Layer-Based
        → спільна технічна роль

    Feature-Based
        → спільна функціональність

Layer-Based підхід може бути зручним для маленьких систем із невеликою кількістю компонентів.

Feature-Based підхід часто полегшує розвиток великих функціональних областей, оскільки пов'язаний код розташований поруч.

На практиці їх часто поєднують.

# Modularity

Modularity — організація системи у вигляді окремих модулів із визначеними відповідальностями та взаємозв'язками.

Модуль повинен мати зрозуміле призначення.

Наприклад:

    UsersModule
        → користувачі

    CoursesModule
        → курси

    NotificationsModule
        → сповіщення

Модулі допомагають розділяти систему на частини, які можна розуміти та змінювати окремо.

## Хороший модуль

Хороший модуль зазвичай має:

- чітке призначення;
- пов'язані між собою компоненти;
- зрозумілий публічний інтерфейс;
- контрольовані залежності;
- приховані внутрішні деталі реалізації.

## Приклад

    users/
    ├── users.module.ts
    ├── users.controller.ts
    ├── users.service.ts
    └── users.repository.ts

Ця папка групує компоненти, що належать до функціональності користувачів.

Проте модульність визначається не тільки структурою папки.

Якщо `UsersService` безпосередньо змінює внутрішні дані `CoursesService`, межі модулів можуть бути погано визначені.

Краще, щоб взаємодія відбувалася через зрозумілі контракти.

---

# Single Responsibility

Single Responsibility — ідея, за якою компонент повинен мати чітко визначену відповідальність.

Це пов'язано з принципом Single Responsibility Principle (SRP), який детальніше розглядається в розділі SOLID.

Проблемний приклад:

    class UserManager {
        createUser() {
            // ...
        }

        sendWelcomeEmail() {
            // ...
        }

        generatePdfReport() {
            // ...
        }

        connectToDatabase() {
            // ...
        }
    }

Клас виконує різні задачі, які можуть змінюватися з різних причин.

Можна розділити функціональність:

    UsersService
        → бізнес-операції користувачів

    EmailService
        → надсилання email

    PdfReportService
        → створення PDF-звітів

    UsersRepository
        → доступ до даних користувачів

Це не означає, що кожна операція обов'язково потребує окремого класу.

Мета — згрупувати відповідальності так, щоб код залишався зрозумілим і підтримуваним.

---

# Separation of Concerns

Separation of Concerns (SoC) — розділення різних аспектів функціональності між компонентами.

Наприклад, у backend:

    Controller
        → HTTP handling

    Service
        → business logic

    Repository
        → data access

Якщо контролер одночасно обробляє HTTP-запит, виконує SQL-запити, перевіряє бізнес-правила та надсилає повідомлення, різні відповідальності змішуються.

Краще розділяти їх відповідно до ролі кожного компонента.

Separation of Concerns допомагає:

- локалізувати зміни;
- зменшувати дублювання;
- тестувати компоненти окремо;
- полегшувати читання коду;
- зменшувати небажані залежності.

Важливо: SoC не означає, що кожна дрібна операція повинна бути винесена в окремий файл.

---

# Encapsulation

Encapsulation — приховування внутрішніх деталей компонента та контроль доступу до них.

Компонент повинен надавати зрозумілий спосіб взаємодії, не розкриваючи без потреби всі деталі своєї реалізації.

Наприклад:

    class Counter {
        #value = 0;

        increment() {
            this.#value += 1;
        }

        getValue() {
            return this.#value;
        }
    }

Використання:

    const counter = new Counter();

    counter.increment();

    console.log(counter.getValue());
    // 1

Поле `#value` є приватним полем класу JavaScript.

Зовнішній код може змінювати лічильник через `increment()`, але не може безпосередньо звернутися до `counter.#value`.

У більших системах encapsulation також означає приховування внутрішньої структури модуля за його публічним інтерфейсом.

# Public API vs Internal Implementation

Public API модуля — це функції, класи, типи або інші елементи, які модуль навмисно надає для зовнішнього використання.

Internal Implementation — внутрішня реалізація, яку не потрібно використовувати безпосередньо з інших модулів.

Наприклад:

    users/
    ├── index.ts
    ├── users.service.ts
    ├── users.repository.ts
    └── users.types.ts

Умовний файл `index.ts` може визначати публічний інтерфейс:

    export { UsersService } from './users.service';
    export type { User } from './users.types';

Зовнішній код може імпортувати елементи через публічну точку входу:

    import { UsersService } from './users';

Це приклад організації публічного інтерфейсу через barrel file.

Однак barrel files не завжди потрібні. У великих застосунках необережні реекспорти можуть ускладнювати залежності або створювати циклічні імпорти.

Головна ідея:

    Public API
        → що дозволено використовувати зовні

    Internal Implementation
        → як модуль працює всередині

Чіткий публічний інтерфейс зменшує залежність інших компонентів від внутрішньої структури модуля.

# Naming Conventions

Naming Conventions — правила найменування файлів, папок, функцій, класів, змінних та інших елементів коду.

Зрозумілі назви допомагають розуміти призначення елемента без необхідності читати всю реалізацію.

## Назви папок

Приклад:

    users/
    courses/
    authentication/
    notifications/

Назви відображають призначення функціональних областей.

## Назви файлів

У TypeScript-проєкті можуть використовуватися такі назви:

    users.controller.ts
    users.service.ts
    users.module.ts
    users.repository.ts

Суфікси допомагають визначити роль файлу.

## Назви функцій

Не дуже зрозуміло:

    function process(data) {
        // ...
    }

Зрозуміліше:

    function calculateCourseDuration(lessons) {
        // ...
    }

Назва повинна описувати дію або призначення функції.

## Назви класів

Класи зазвичай називають іменниками або назвами ролей:

    UsersService
    CoursesController
    EmailSender
    PaymentRepository

## Послідовність важливіша за особисті вподобання

Якщо в проєкті використовується `kebab-case` для назв папок, краще дотримуватися цього стилю послідовно.

Наприклад:

    user-profile/
    course-management/
    email-notifications/

У різних мовах і framework можуть бути різні поширені домовленості.

Важливо дотримуватися правил конкретної екосистеми та не змішувати стилі без причини.

# Dependency Direction

Dependency Direction — напрямок залежностей між компонентами.

Правильна організація коду передбачає не тільки групування файлів, а й розуміння того, хто від кого залежить.

Наприклад:

    Controller
        ↓
    Service
        ↓
    Repository

Це типовий напрямок залежностей у простому backend-застосунку.

Контролер викликає сервіс, а сервіс використовує компонент доступу до даних.

Проблемний приклад:

    UsersService
        ↓
    CoursesController
        ↓
    CoursesService

Якщо бізнес-сервіс користувачів залежить від HTTP-контролера курсів, межі відповідальностей можуть бути визначені неправильно.

Зазвичай краще, щоб компоненти бізнес-логіки взаємодіяли з іншими компонентами бізнес-логіки або через відповідні контракти, а не через контролери.

У складніших архітектурах напрямок залежностей визначається додатковими принципами, наприклад Dependency Inversion Principle.

# Shared Code

Shared Code — код, який використовується в кількох частинах застосунку.

Наприклад:

    common/
    ├── utils/
    ├── types/
    └── constants/

Спільний код може містити:

    Date utilities
    String utilities
    Shared types
    Common constants
    Reusable validation helpers

Проте не весь код, який використовується двома модулями, потрібно автоматично переносити до `common`.

Наприклад, функція `calculateCoursePrice()` може належати саме до предметної області курсів, навіть якщо її використовують кілька компонентів.

Краще зберігати бізнес-логіку поруч із відповідною предметною областю.

## Приклад утиліти

    // common/utils/format-date.ts

    export function formatDate(date: Date): string {
        return date.toISOString().slice(0, 10);
    }

Використання:

    import { formatDate } from './common/utils/format-date';

    console.log(formatDate(new Date()));
    // Наприклад: 2026-10-20

Це простий приклад функції, яку можна використовувати в різних частинах системи.

Варто пам'ятати, що `toISOString()` форматує дату в UTC. Якщо потрібна локальна календарна дата користувача, необхідно врахувати часовий пояс.

# Code Duplication vs Code Reuse

Code Duplication — повторення однакового або дуже схожого коду в кількох місцях.

Code Reuse — повторне використання наявної функціональності замість її дублювання.

## Приклад дублювання

    function calculateStudentDiscount(price) {
        return price * 0.9;
    }

    function calculateTeacherDiscount(price) {
        return price * 0.9;
    }

Якщо обидві функції реалізують однакове правило, можна використати спільну функцію:

    function applyDiscount(
        price: number,
        discountRate: number,
    ): number {
        return price * (1 - discountRate);
    }

Використання:

    const studentPrice = applyDiscount(1000, 0.1);
    const teacherPrice = applyDiscount(1000, 0.1);

    console.log(studentPrice);
    // 900

Однак не будь-який схожий код потрібно об'єднувати.

Дві операції можуть виглядати однаково сьогодні, але представляти різні бізнес-правила, які згодом змінюватимуться незалежно.

Тому важливо розрізняти:

    Accidental Duplication
        → зайве повторення реалізації

    Independent Business Rules
        → різні правила, навіть якщо код схожий

Повторне використання коду корисне, коли воно зменшує дублювання без створення небажаних залежностей.

# Entry Point

Entry Point — точка входу, з якої починається виконання програми або певної частини системи.

У Node.js-застосунку точкою входу може бути файл:

    src/main.ts

Наприклад, у NestJS:

    import { NestFactory } from '@nestjs/core';
    import { AppModule } from './app.module';

    async function bootstrap(): Promise<void> {
        const app = await NestFactory.create(AppModule);

        await app.listen(process.env.PORT ?? 3000);
    }

    void bootstrap();

Це спрощений приклад точки входу NestJS-застосунку.

Файл `main.ts` відповідає за запуск застосунку, а `AppModule` організовує його основні модулі.

Точка входу допомагає зрозуміти, як запускається програма та з якого місця починається ініціалізація її компонентів.

У різних типах застосунків точкою входу можуть бути:

    main.ts
    index.js
    server.js
    main.py
    index.html

Конкретний варіант залежить від середовища виконання та інструментів.

# Tests Organization

Tests Organization — організація автоматизованих тестів.

Тести можна розміщувати поруч із вихідним кодом або в окремій папці.

## Підхід 1 — тести поруч із кодом

    src/
    ├── users/
    │   ├── users.service.ts
    │   └── users.service.spec.ts
    └── courses/
        ├── courses.service.ts
        └── courses.service.spec.ts

Перевага — тести легко знайти поруч із відповідною реалізацією.

## Підхід 2 — окрема папка тестів

    src/
    ├── users/
    │   └── users.service.ts
    └── courses/
        └── courses.service.ts

    test/
    ├── users/
    │   └── users.service.spec.ts
    └── courses/
        └── courses.service.spec.ts

Перевага — вихідний код і тести фізично розділені.

Обидва підходи можуть бути правильними.

Вибір залежить від framework, інструментів тестування та структури проєкту.

У NestJS часто використовуються файли `*.spec.ts` для unit-тестів і `*.e2e-spec.ts` для end-to-end тестів.

# Code Organization in NestJS

NestJS має власні механізми організації коду:

    Modules
    Controllers
    Providers
    Services
    Dependency Injection

Ці механізми допомагають будувати модульний backend-застосунок.

## Controllers

Контролери відповідають за обробку HTTP-запитів і формування відповідей.

Приклад:

    @Controller('courses')
    export class CoursesController {
        constructor(
            private readonly coursesService: CoursesService,
        ) {}

        @Get()
        findAll() {
            return this.coursesService.findAll();
        }
    }

Контролер делегує бізнес-операцію сервісу.

## Services

Сервіси зазвичай містять або координують бізнес-логіку.

Приклад:

    @Injectable()
    export class CoursesService {
        findAll() {
            return [
                { id: 1, title: 'JavaScript Basics' },
                { id: 2, title: 'TypeScript Basics' },
            ];
        }
    }

Це демонстраційний приклад із даними в пам'яті.

## Modules

Модулі об'єднують компоненти та визначають їх доступність у межах системи NestJS.

Приклад:

    @Module({
        controllers: [CoursesController],
        providers: [CoursesService],
    })
    export class CoursesModule {}

## Приклад feature-based структури

    src/
    ├── app.module.ts
    ├── main.ts
    ├── users/
    │   ├── users.module.ts
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.service.spec.ts
    └── courses/
        ├── courses.module.ts
        ├── courses.controller.ts
        ├── courses.service.ts
        └── courses.service.spec.ts

Тут код згрупований за функціональними модулями.

Це зручна відправна точка для навчального NestJS-проєкту.

Зі збільшенням функціональності всередині окремих модулів можна додавати DTO, entities, repositories, interfaces та інші компоненти, якщо вони справді потрібні.

# Example — Worship Schedule

Розглянемо організацію коду для застосунку Worship Schedule.

Застосунок дозволяє користувачам:

    Register
    Login
    Create Schedule
    View Schedule
    Edit Schedule
    Delete Schedule

Кожен користувач має власні приватні розклади.

## Варіант 1 — організація за технічними шарами

    src/
    ├── controllers/
    │   ├── auth.controller.ts
    │   ├── users.controller.ts
    │   └── schedules.controller.ts
    ├── services/
    │   ├── auth.service.ts
    │   ├── users.service.ts
    │   └── schedules.service.ts
    ├── repositories/
    │   ├── users.repository.ts
    │   └── schedules.repository.ts
    └── main.ts

Цей варіант групує компоненти за технічною роллю.

## Варіант 2 — організація за функціональністю

    src/
    ├── auth/
    │   ├── auth.controller.ts
    │   ├── auth.service.ts
    │   └── auth.module.ts
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.module.ts
    ├── schedules/
    │   ├── schedules.controller.ts
    │   ├── schedules.service.ts
    │   ├── schedules.repository.ts
    │   └── schedules.module.ts
    ├── app.module.ts
    └── main.ts

Цей варіант групує компоненти за функціональними областями.

Для навчального NestJS-проєкту другий варіант часто зручніший, оскільки пов'язаний код розташований поруч.

## Варіант 3 — поєднання функціональності та шарів

    src/
    ├── auth/
    │   ├── controllers/
    │   ├── services/
    │   └── auth.module.ts
    ├── users/
    │   ├── controllers/
    │   ├── services/
    │   ├── repositories/
    │   └── users.module.ts
    ├── schedules/
    │   ├── controllers/
    │   ├── services/
    │   ├── repositories/
    │   ├── dto/
    │   └── schedules.module.ts
    ├── app.module.ts
    └── main.ts

Цей варіант може бути корисним, коли функціональність окремих модулів стає складнішою.

Не потрібно відразу створювати всі ці підпапки. Якщо в модулі є лише один сервіс і контролер, додаткові рівні можуть бути непотрібними.

## Що важливо для приватних розкладів

Організація коду повинна допомагати підтримувати правила доступу.

Наприклад:

    schedules/
        ├── schedules.controller.ts
        ├── schedules.service.ts
        └── schedules.repository.ts

Можливий розподіл відповідальностей:

    SchedulesController
        → HTTP-запити та параметри

    SchedulesService
        → бізнес-правила й перевірка доступу

    SchedulesRepository
        → читання та збереження розкладів

У реальному застосунку перевірка доступу може бути розподілена між guards, сервісами та запитами до бази даних. Важливо, щоб кожна операція виконувалася лише за наявності належних прав.

Наприклад, пошук розкладу можна організувати так, щоб відразу враховувався власник:

    findByIdAndUserId(scheduleId, userId)

Це допомагає не покладатися лише на ID розкладу та зменшує ризик доступу до чужих даних.

Конкретна реалізація залежить від ORM, структури бази даних і моделі авторизації.

# Refactoring Code Organization

Refactoring — зміна внутрішньої структури коду без навмисної зміни його зовнішньої поведінки.

Рефакторинг організації коду може включати:

- перенесення файлів;
- перейменування модулів;
- розділення великих компонентів;
- об'єднання дубльованої функціональності;
- виділення спільних типів;
- зміну структури папок;
- уточнення меж між модулями;
- видалення невикористовуваного коду;
- виправлення циклічних залежностей.

## Приклад

Початкова структура:

    src/
    ├── app.controller.ts
    ├── app.service.ts
    └── app.module.ts

Згодом `app.service.ts` може містити функціональність користувачів, курсів і розкладів.

Можливий рефакторинг:

    src/
    ├── users/
    │   ├── users.service.ts
    │   └── users.module.ts
    ├── courses/
    │   ├── courses.service.ts
    │   └── courses.module.ts
    ├── schedules/
    │   ├── schedules.service.ts
    │   └── schedules.module.ts
    ├── app.module.ts
    └── main.ts

Після зміни потрібно перевірити:

    Imports
    Module declarations
    Dependency injection
    Tests
    Application behavior

Переміщення файлів може зламати імпорти або конфігурацію. Тому варто виконувати рефакторинг невеликими кроками та перевіряти результат тестами.

# Типові помилки Code Organization

## 1. Один великий файл для всього застосунку

    app.ts
        → HTTP
        → business logic
        → database
        → validation
        → email
        → configuration

Для маленького навчального прикладу це може бути прийнятно, але зі зростанням функціональності підтримувати такий файл стає складніше.

## 2. Надмірне дроблення коду

Створення окремого файлу для кожного маленького виразу або тривіальної функції може зробити структуру незручною.

Кількість файлів сама по собі не є показником якості.

## 3. Неузгоджені назви

Наприклад:

    userService.ts
    users-controller.ts
    UserModule.ts
    course.service.ts

Різні стилі без причини ускладнюють навігацію.

Краще дотримуватися єдиних правил найменування.

## 4. Змішування відповідальностей

Наприклад, сервіс одночасно виконує бізнес-логіку, формує HTTP-відповіді та працює з файлами.

Варто визначити, чи належать ці задачі до однієї відповідальності.

## 5. Надмірна папка common

Якщо в `common` потрапляє будь-який код, який не має очевидного місця, папка перетворюється на неструктуроване сховище.

Спільний код повинен мати справді спільне призначення.

## 6. Дублювання коду

Копіювання однакової логіки в різні модулі збільшує ризик неузгоджених змін.

Проте перед об'єднанням потрібно переконатися, що логіка справді має однакове призначення.

## 7. Неправильні межі модулів

Якщо один модуль безпосередньо змінює внутрішній стан іншого модуля, організація може створювати сильне зчеплення.

Краще визначати чіткі способи взаємодії між модулями.

## 8. Циклічні залежності

Приклад:

    UsersModule
        ↓
    CoursesModule
        ↓
    UsersModule

Циклічні залежності можуть ускладнювати ініціалізацію, тестування та розуміння системи.

У NestJS існують механізми роботи з певними циклами залежностей, але за можливості краще спочатку перевірити, чи не можна змінити структуру модулів.

## 9. Передчасна складна структура

Не варто створювати десятки папок та абстракцій лише на випадок майбутнього зростання.

Структуру потрібно розвивати разом із реальними потребами.

## 10. Відсутність тестів після рефакторингу

Переміщення файлів і змінення імпортів можуть порушити поведінку програми.

Після рефакторингу варто запускати тести та перевіряти основні сценарії.

# Практичні правила організації коду

## Правило 1 — починай із простого

Для невеликого застосунку достатньо кількох зрозумілих папок.

Не потрібно відразу будувати складну багаторівневу структуру.

## Правило 2 — групуй пов'язаний код

Якщо компоненти належать до однієї функціональної області, розглянь можливість розмістити їх поруч.

## Правило 3 — визначай відповідальність

Кожен модуль повинен мати зрозуміле призначення.

## Правило 4 — використовуй зрозумілі назви

Назви папок, файлів і компонентів повинні пояснювати їхню роль.

## Правило 5 — контролюй залежності

Не дозволяй компонентам без потреби залежати від внутрішньої реалізації інших модулів.

## Правило 6 — не дублюй бізнес-правила

Якщо одне правило реалізоване в кількох місцях, розглянь можливість винести його в компонент із чіткою відповідальністю.

## Правило 7 — не створюй абстракції без потреби

Спочатку зрозумій проблему, а потім вирішуй, чи потрібні додаткові інтерфейси, фабрики або модулі.

## Правило 8 — дотримуйся послідовності

Використовуй узгоджені назви файлів, структуру папок і правила імпорту.

## Правило 9 — організовуй тести

Тести повинні бути пов'язані з відповідними компонентами та легко знаходитися.

## Правило 10 — змінюй структуру поступово

Коли проєкт зростає, переглядай організацію коду й виконуй рефакторинг за потреби.

# Головне

• Code Organization визначає, як код розподілено між файлами, папками та модулями.

• Хороша структура допомагає знаходити потрібний код, розуміти його призначення та безпечніше виконувати зміни.

• Code Organization підтримує Software Architecture, але не замінює її.

• Основні підходи до організації коду — File-Based, Feature-Based, Layer-Based і Domain-Based.

• Feature-Based Organization групує компоненти за функціональністю.

• Layer-Based Organization групує компоненти за технічними ролями.

• Domain-Based Organization відображає предметну область застосунку.

• На практиці можна поєднувати кілька підходів.

• Модуль повинен мати зрозуміле призначення та контрольовані залежності.

• Separation of Concerns допомагає розділяти різні аспекти функціональності.

• Encapsulation дозволяє приховувати внутрішні деталі та надавати зрозумілий публічний інтерфейс.

• Shared Code потрібно організовувати обережно, щоб не створювати неструктуровану папку `common`.

• Повторне використання коду корисне, але не кожен схожий фрагмент потрібно об'єднувати.

• Зрозумілі назви файлів, папок і компонентів полегшують навігацію.

• У NestJS модулі, контролери та провайдери допомагають організувати backend.

• Структура папок сама по собі не гарантує правильної архітектури — важливі відповідальності та напрямки залежностей.

• Циклічні залежності можуть ускладнювати розвиток системи.

• Рефакторинг допомагає поступово покращувати структуру коду без навмисної зміни його поведінки.

• Не потрібно створювати складну структуру до появи реальної потреби.

• Хороша організація коду — це баланс між зрозумілістю, простотою, повторним використанням і можливістю розвитку.

## Модель для запам'ятовування

    APPLICATION
         ↓
    FEATURES / DOMAINS
         ↓
    MODULES
         ↓
    COMPONENTS
         ↓
    FILES AND FUNCTIONS

    COMPONENT
         ↓
    RESPONSIBILITY
         ↓
    PUBLIC INTERFACE
         ↓
    DEPENDENCIES
         ↓
    IMPLEMENTATION

**Головна ідея:** організовуй код так, щоб кожна функціональна частина мала зрозуміле місце, кожен компонент — чітке призначення, а залежності між модулями були контрольованими. Починай із простої структури й удосконалюй її в міру зростання проєкту.
