## 01. What Is Software Architecture

Software Architecture (програмна архітектура) — це сукупність фундаментальних структурних рішень, принципів і правил, які визначають, як організована програмна система, з яких частин вона складається, як ці частини взаємодіють і як система розвивається з часом.

Архітектура визначає не тільки те, як працює код сьогодні, але й те, наскільки легко його буде змінювати, тестувати, розширювати та підтримувати в майбутньому.

Software Architecture використовується, коли потрібно:

- спроєктувати структуру нового застосунку;
- розділити систему на модулі та компоненти;
- визначити відповідальність кожної частини системи;
- організувати взаємодію між frontend, backend і database;
- зменшити залежність між компонентами;
- зробити код зрозумілим і придатним до тестування;
- підготувати застосунок до майбутніх змін;
- вибрати відповідні архітектурні підходи;
- визначити межі між різними частинами системи;
- забезпечити підтримуваність і масштабованість застосунку.

### Що потрібно пам'ятати

• Software Architecture визначає фундаментальну структуру програмної системи.

• Архітектура описує основні компоненти, їхні обов'язки, взаємодію та залежності.

• Архітектура і програмна реалізація — не одне й те саме.

• Архітектура визначає загальну організацію системи, а implementation — конкретний код, який реалізує її поведінку.

• Software Architecture не обмежується структурою папок і файлів.

• Правильна структура проєкту допомагає реалізувати архітектурні принципи, але сама по собі не гарантує хорошої архітектури.

• Архітектурні рішення впливають на підтримуваність, тестованість, продуктивність, надійність і можливість розширення системи.

• Не існує універсальної архітектури, яка найкраще підходить для кожного проєкту.

• Архітектуру потрібно вибирати відповідно до вимог, складності, обмежень і очікуваного розвитку застосунку.

• Простий застосунок не обов'язково потребує складної архітектури.

• Надмірна архітектура створює зайву складність, додаткові абстракції та витрати на підтримку.

• Хороша архітектура полегшує зміни, а не просто робить код формально структурованим.

• Архітектурні рішення завжди мають компроміси — trade-offs.

• Архітектура може змінюватися разом із вимогами до програмної системи.

• Для початку важливо навчитися розділяти відповідальність, керувати залежностями та створювати зрозумілі межі між компонентами.

# Software Architecture

## Що таке архітектура програмного забезпечення

Software Architecture — це організація системи на рівні її основних структур і взаємозв'язків.

Наприклад, backend-застосунок може складатися з таких частин:

    Client
       ↓
    Controller
       ↓
    Service
       ↓
    Repository
       ↓
    Database

Кожна частина виконує свою роль:

    Client      → надсилає запити
    Controller  → приймає HTTP-запити
    Service     → реалізує бізнес-логіку
    Repository  → організовує доступ до даних
    Database    → зберігає дані

Це приклад простої layered architecture — шарової архітектури.

Архітектурне рішення полягає не тільки в тому, щоб створити п'ять файлів. Потрібно визначити:

- за що відповідає кожен компонент;
- які компоненти можуть викликати інші;
- як передаються дані;
- де реалізується бізнес-логіка;
- де відбувається робота з базою даних;
- як тестувати окремі частини;
- як змінити один компонент без переписування всієї системи.

Саме такі питання стосуються Software Architecture.

# Architecture vs Software Design

Архітектура та програмний дизайн тісно пов'язані, тому їхні межі не завжди можна провести абсолютно чітко.

Проте на початковому етапі навчання корисно розрізняти їх.

## Software Architecture

Software Architecture зосереджується на фундаментальних рішеннях щодо організації системи.

Наприклад:

    Чи розділяємо застосунок на модулі?
    Чи використовуємо layered architecture?
    Де розташована бізнес-логіка?
    Як компоненти залежать один від одного?
    Як організувати доступ до database?
    Як ізолювати зовнішні сервіси?
    Як забезпечити testability?

## Software Design

Software Design зосереджується на тому, як реалізувати конкретну частину системи.

Наприклад:

    Які методи повинен мати клас?
    Які параметри приймає функція?
    Яку структуру має об'єкт?
    Як реалізувати validation?
    Як обробити помилку?
    Який алгоритм використати?

## Приклад

Архітектурне рішення:

    Бізнес-логіка повинна бути відокремлена
    від HTTP-контролерів і бази даних.

Рішення на рівні design:

    Створити UsersService
    з методом createUser().

Реалізація:

    export class UsersService {
        createUser(name: string) {
            return {
                id: crypto.randomUUID(),
                name,
            };
        }
    }

У цьому прикладі архітектура визначає принцип організації, дизайн — структуру конкретного компонента, а код реалізує його поведінку.

Важливо: архітектура та дизайн утворюють континуум рішень. Деякі рішення можуть одночасно впливати на обидва рівні.

# Architecture vs Code Organization

Code Organization — це спосіб організації коду у файлах, папках, модулях і пакетах.

Наприклад:

    src/
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.module.ts
    ├── products/
    │   ├── products.controller.ts
    │   ├── products.service.ts
    │   └── products.module.ts
    └── main.ts

Це приклад організації файлів NestJS-застосунку.

Однак структура папок не гарантує правильної архітектури.

Наприклад, якщо `UsersService` напряму залежить від HTTP request, SQL-запитів, стороннього API та логіки авторизації, він може мати занадто багато відповідальностей навіть за ідеальної структури папок.

Тому важливо розрізняти:

    Code Organization
        → де розташований код

    Software Architecture
        → як організована система,
          які має межі та залежності

Хороша організація коду допомагає підтримувати архітектуру, але не замінює її.

# Main Architectural Elements

## Components

Component — компонент системи, який виконує певну роль і взаємодіє з іншими частинами.

Приклади:

    UsersController
    UsersService
    UsersRepository
    EmailService
    PaymentService
    AuthenticationService

Компонентом може бути клас, модуль, підсистема або інша логічно відокремлена частина системи.

Конкретний рівень залежить від контексту.

Наприклад, `UsersService` може бути компонентом усередині backend-модуля, а весь backend — компонентом більшої системи.

---

## Modules

Module — логічно організована частина програми, яка об'єднує пов'язані компоненти.

Наприклад:

    UsersModule
        ├── UsersController
        ├── UsersService
        └── UsersRepository

Модуль Users відповідає за функціональність, пов'язану з користувачами.

Інший модуль:

    ProductsModule
        ├── ProductsController
        ├── ProductsService
        └── ProductsRepository

Модулі допомагають розділяти систему за функціональними напрямами.

У NestJS модуль також є конкретним механізмом framework для організації компонентів та їхніх залежностей.

---

## Responsibilities

Responsibility — відповідальність компонента, тобто те, за що він повинен відповідати.

Наприклад:

    UsersController
        → HTTP-запити та HTTP-відповіді

    UsersService
        → правила роботи з користувачами

    UsersRepository
        → отримання та збереження даних користувачів

Якщо один компонент виконує занадто багато різних задач, його може бути важко підтримувати та тестувати.

Приклад проблемного компонента:

    UsersService
        ├── обробляє HTTP-запити
        ├── перевіряє бізнес-правила
        ├── формує SQL-запити
        ├── надсилає email
        └── формує HTML

Краще розглянути можливість розподілити ці відповідальності між відповідними компонентами.

Не потрібно створювати окремий клас для кожної дрібної операції. Мета — зрозумілі межі відповідальності, а не максимальна кількість файлів.

---

## Dependencies

Dependency — залежність одного компонента від іншого.

Наприклад:

    UsersController
        ↓ depends on
    UsersService
        ↓ depends on
    UsersRepository

Якщо `UsersController` використовує `UsersService`, контролер залежить від сервісу.

Залежності можуть бути:

- прямими — компонент безпосередньо використовує інший;
- непрямими — компонент залежить від іншого через проміжні компоненти;
- внутрішніми — між компонентами одного модуля;
- зовнішніми — від бібліотек, API, баз даних або інших систем.

Надмірні залежності ускладнюють зміну та тестування коду.

Наприклад, якщо кожен модуль безпосередньо звертається до бази даних, стороннього API та конфігурації, зміни цих механізмів можуть вимагати виправлень у багатьох місцях.

---

## Interfaces

Interface — визначений контракт взаємодії між компонентами.

Контракт визначає, які операції доступні та як ними користуватися.

Наприклад, у TypeScript:

    interface UserRepository {
        findById(id: string): Promise<User | null>;
        save(user: User): Promise<User>;
    }

Компонент, який працює з таким контрактом, може не знати, чи дані зберігаються у PostgreSQL, іншій базі даних або тестовому сховищі.

Приклад:

    class UsersService {
        constructor(
            private readonly usersRepository: UserRepository,
        ) {}

        async getUser(id: string): Promise<User | null> {
            return this.usersRepository.findById(id);
        }
    }

Тут `UsersService` залежить від контракту `UserRepository`, а не обов'язково від конкретної реалізації бази даних.

Це спрощений приклад. Для повноцінного застосунку типи `User` і реалізацію репозиторію потрібно визначити окремо.

Важливо пам'ятати:

- interface описує контракт;
- implementation реалізує контракт;
- interface може зменшувати залежність від конкретної реалізації;
- interface сам по собі не гарантує хорошої архітектури.

---

## Boundaries

Boundary — межа між компонентами, модулями, шарами або зовнішніми системами.

Межі допомагають визначити:

- де закінчується відповідальність одного компонента;
- де починається відповідальність іншого;
- які дані дозволено передавати;
- які операції доступні зовні;
- які деталі потрібно приховати.

Наприклад:

    HTTP Boundary
        ↓
    Controller

    Application Boundary
        ↓
    Service

    Persistence Boundary
        ↓
    Repository

    External System Boundary
        ↓
    Third-party API

Якщо межі визначені правильно, зміна внутрішньої реалізації одного компонента не повинна автоматично вимагати зміни всіх інших компонентів.

# Separation of Concerns

Separation of Concerns (SoC) — принцип розділення відповідальностей.

Ідея полягає в тому, щоб різні аспекти програми були організовані так, аби кожен компонент мав зрозумілу сферу відповідальності.

Наприклад:

    Controller
        → HTTP

    Service
        → business logic

    Repository
        → data access

    Logger
        → logging

    EmailService
        → email delivery

Переваги:

- код легше читати;
- зміни локалізуються в конкретних компонентах;
- спрощується тестування;
- зменшується дублювання;
- легше повторно використовувати код;
- компоненти простіше замінювати.

Приклад порушення Separation of Concerns:

    class UsersController {
        async createUser(name: string) {
            // HTTP handling
            // business validation
            // SQL query
            // password processing
            // email sending
            // response formatting
        }
    }

У такому компоненті змішані різні відповідальності.

Краще розділити їх відповідно до реальних потреб застосунку.

# Coupling and Cohesion

Coupling — ступінь залежності одного компонента від інших компонентів.

Cohesion — ступінь пов'язаності елементів усередині одного компонента навколо спільної відповідальності.

Зазвичай прагнуть до:

    Low Coupling
        → менше зайвих залежностей

    High Cohesion
        → компоненти з чіткою спільною метою

Приклад високого coupling:

    UsersService
        ↓
    PostgreSQL implementation
        ↓
    конкретні SQL-запити
        ↓
    зовнішній email API

Якщо бізнес-логіка безпосередньо залежить від багатьох конкретних технологій, її складніше змінювати й тестувати.

Приклад кращого розділення:

    UsersService
        ├── UserRepository interface
        └── EmailSender interface

Конкретні реалізації можуть бути підключені окремо.

Це не означає, що потрібно створювати інтерфейс для кожного класу. Абстракції варто вводити тоді, коли вони допомагають керувати залежностями або відокремлювати важливі межі.

# Quality Attributes

Quality Attributes — характеристики якості програмної системи.

Архітектурні рішення впливають не тільки на те, що система робить, але й на те, наскільки добре вона це робить.

Основні характеристики:

## Maintainability

Maintainability — підтримуваність.

Наскільки легко зрозуміти код, виправити помилку, внести зміни та розвивати систему.

Приклад:

    Зміна правила реєстрації користувача
        ↓
    Зміни потрібні лише в UsersService

Це бажаний результат, якщо правило справді належить до відповідальності цього сервісу.

## Extensibility

Extensibility — можливість розширення.

Наскільки легко додати нову функціональність без масштабного переписування наявного коду.

Наприклад:

    Email notifications
        ↓
    SMS notifications
        ↓
    Push notifications

Якщо механізм сповіщень має добре визначений контракт, додавання нового способу доставки може бути простішим.

## Testability

Testability — тестованість.

Наскільки легко перевіряти поведінку системи та її компонентів.

Наприклад, сервіс, який залежить від абстракції репозиторію, можна тестувати з підставною реалізацією без підключення до справжньої бази даних.

## Scalability

Scalability — масштабованість.

Здатність системи обробляти збільшення навантаження або обсягу даних завдяки відповідним змінам ресурсів чи архітектури.

Масштабованість може передбачати:

    Database indexing
    Caching
    Query optimization
    Horizontal scaling
    Background jobs
    Load balancing

Не кожен застосунок потребує всіх цих механізмів.

## Reliability

Reliability — надійність.

Здатність системи стабільно виконувати свої функції протягом часу.

На надійність можуть впливати:

    Error handling
    Data integrity
    Timeouts
    Retries
    Monitoring
    Backup and recovery

Retries, наприклад, потрібно реалізовувати обережно, щоб повторні запити не спричиняли дублювання операцій.

## Performance

Performance — продуктивність.

Характеризує швидкість виконання операцій і використання ресурсів.

На продуктивність можуть впливати:

    Database queries
    Network latency
    Algorithms
    Caching
    Memory usage
    CPU usage

Перед оптимізацією бажано виміряти продуктивність і знайти реальне вузьке місце.

## Security

Security — безпека системи.

Архітектурні рішення можуть визначати:

    Authentication
    Authorization
    Access boundaries
    Secret management
    Input validation
    Data protection
    Audit logging

Безпека не повинна бути лише додатковою функцією, яку додають наприкінці розробки.

---

# Architectural Decisions

Architectural Decision — рішення, яке впливає на фундаментальну організацію системи або її важливі властивості.

Приклади:

    Використовувати PostgreSQL
    Розділити застосунок на модулі
    Застосувати layered architecture
    Зберігати бізнес-логіку в services
    Відокремити доступ до даних
    Використовувати dependency injection
    Зберігати конфігурацію в environment variables
    Винести довгі операції у background jobs

Архітектурне рішення потрібно приймати не тільки на підставі популярності технології.

Потрібно враховувати:

- вимоги проєкту;
- складність реалізації;
- досвід команди;
- вартість підтримки;
- безпеку;
- продуктивність;
- можливість тестування;
- майбутні зміни;
- обмеження інфраструктури.

## Trade-offs

Trade-off — компроміс між різними властивостями або витратами.

Наприклад:

    More abstraction
        ↓
    Easier replacement of implementations
        ↓
    More interfaces and indirection

Абстракція може спростити заміну реалізації, але водночас додати складність.

Інший приклад:

    Monolith
        ↓
    Simpler deployment and development

    Microservices
        ↓
    Independent deployment possibilities
        +
    Network communication and operational complexity

Мікросервіси не є автоматично кращими за моноліт.

Для невеликого навчального проєкту моноліт часто буде простішим і практичнішим рішенням.

## Architecture Decision Record (ADR)

ADR — короткий документ, який фіксує важливе архітектурне рішення.

Приклад:

    # ADR-001: Use PostgreSQL

    ## Status
    Accepted

    ## Context
    The application needs persistent relational data.

    ## Decision
    Use PostgreSQL as the primary database.

    ## Consequences
    - Relational data can be modeled using tables.
    - SQL is used for data queries.
    - Database migrations must be managed.
    - Database configuration must be maintained.

ADR допомагає зрозуміти не тільки те, яке рішення було прийнято, а й чому.

Для невеликого проєкту не потрібно документувати кожну дрібницю. ADR корисний насамперед для рішень, які складно змінити або які мають помітні наслідки для системи.

---

# Architecture Constraints

Architecture Constraints — обмеження, які впливають на вибір архітектури.

Вони можуть бути технічними, організаційними або бізнесовими.

Приклади:

    Programming language
        → TypeScript

    Backend framework
        → NestJS

    Database
        → PostgreSQL

    Hosting
        → конкретна платформа

    Budget
        → обмежені фінансові ресурси

    Team size
        → один розробник

    Development time
        → обмежений термін

    Security requirements
        → правила доступу до приватних даних

    Existing infrastructure
        → наявні сервіси та системи

Архітектура повинна враховувати реальні обмеження.

Наприклад, якщо застосунок розробляє одна людина, складна розподілена система може створити більше проблем, ніж користі.

Обмеження не завжди є недоліком. Вони допомагають звузити кількість можливих рішень.

---

# Monolith vs Microservices

## Monolith

Monolith — архітектурний підхід, за якого основна функціональність застосунку реалізується та розгортається як одна система.

Приклад:

    Application
        ├── Users
        ├── Authentication
        ├── Courses
        ├── Lessons
        └── Notifications

Усередині моноліту можна мати багато модулів із чіткими межами.

Моноліт не обов'язково означає погано організований або нерозділений код.

### Переваги

- простіше почати розробку;
- простіше локально запускати застосунок;
- менше інфраструктурних компонентів;
- простіше налагоджувати взаємодію між модулями;
- зазвичай простіше розгортання.

### Недоліки

- окремі частини складніше незалежно розгортати;
- погано організовані модулі можуть перетворитися на тісно пов'язану систему;
- зростання застосунку може ускладнювати розробку й тестування.

## Microservices

Microservices — архітектурний підхід, за якого система складається з окремих сервісів, що взаємодіють через визначені межі.

Наприклад:

    Users Service
         ↕
    API / Messaging
         ↕
    Courses Service
         ↕
    Notifications Service

Конкретна організація зв'язків залежить від системи.

### Переваги

- можливість незалежного розгортання сервісів;
- можливість масштабувати окремі компоненти;
- незалежний розвиток частин системи;
- можливість вибирати різні технології там, де це виправдано.

### Недоліки

- складніша інфраструктура;
- мережеві помилки та затримки;
- складніша діагностика;
- складніша робота з розподіленими транзакціями;
- складніший моніторинг;
- більше вимог до автоматизації розгортання.

## Monolith vs Microservices

    Monolith
        → одна основна система розгортання

    Modular Monolith
        → одна система розгортання
          з чітко розділеними модулями

    Microservices
        → окремі сервіси з незалежним розгортанням

Для початкового навчання NestJS зазвичай достатньо добре організованого modular monolith.

Важливіше навчитися створювати зрозумілі модулі та керувати залежностями, ніж одразу будувати розподілену систему.

---

# Architecture and the Backend

У backend-застосунку архітектура допомагає визначити, як організувати обробку запитів, бізнес-правила, доступ до даних і взаємодію із зовнішніми системами.

Наприклад, користувач створює курс у навчальній системі.

Типовий потік:

    Client
       ↓
    HTTP Request
       ↓
    Controller
       ↓
    Service
       ↓
    Repository
       ↓
    PostgreSQL
       ↓
    Response

Кожен рівень виконує свою функцію.

## Controller

Контролер відповідає за HTTP-рівень:

    HTTP Request
        ↓
    Route handling
        ↓
    Input DTO
        ↓
    Service call
        ↓
    HTTP Response

Контролер не повинен перетворюватися на місце, де зосереджена вся бізнес-логіка.

## Service

Сервіс реалізує або координує бізнес-операції:

    createCourse()
    enrollStudent()
    publishLesson()
    cancelEnrollment()

Тут можуть виконуватися бізнес-перевірки та координація інших компонентів.

## Repository

Репозиторій відповідає за доступ до даних:

    findById()
    findAll()
    save()
    delete()

Це логічний компонент або абстракція, а не обов'язково вимога використовувати окремий клас для кожної таблиці.

## Database

База даних зберігає інформацію:

    users
    courses
    lessons
    enrollments

Структура бази повинна підтримувати вимоги до даних, зв'язків, цілісності та запитів.

# Приклад архітектури на NestJS

NestJS надає механізми для організації застосунку за допомогою модулів, контролерів, провайдерів і dependency injection.

Приклад структури:

    src/
    ├── app.module.ts
    ├── main.ts
    └── users/
        ├── users.module.ts
        ├── users.controller.ts
        ├── users.service.ts
        └── users.repository.ts

Призначення файлів:

    main.ts
        → запуск застосунку

    app.module.ts
        → кореневий модуль

    users.module.ts
        → організація Users-компонентів

    users.controller.ts
        → HTTP-рівень

    users.service.ts
        → бізнес-операції

    users.repository.ts
        → доступ до даних

Це лише початкова структура. У реальному проєкті репозиторій може бути реалізований через Prisma, TypeORM або інший інструмент.

Також не кожен проєкт потребує окремого репозиторію: архітектуру потрібно пристосовувати до складності задачі.

## Приклад UsersService

    import { Injectable } from '@nestjs/common';

    @Injectable()
    export class UsersService {
        private readonly users = [
            { id: 1, name: 'Anna' },
            { id: 2, name: 'John' },
        ];

        findAll() {
            return this.users;
        }

        findById(id: number) {
            return this.users.find((user) => user.id === id) ?? null;
        }
    }

Цей сервіс використовує масив у пам'яті замість бази даних.

Це спрощений навчальний приклад. У production-застосунку дані зазвичай потрібно зберігати в постійному сховищі.

## Приклад UsersController

    import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';
    import { UsersService } from './users.service';

    @Controller('users')
    export class UsersController {
        constructor(
            private readonly usersService: UsersService,
        ) {}

        @Get()
        findAll() {
            return this.usersService.findAll();
        }

        @Get(':id')
        findById(
            @Param('id', ParseIntPipe) id: number,
        ) {
            return this.usersService.findById(id);
        }
    }

Контролер делегує роботу сервісу.

Він не повинен знати, як саме реалізоване зберігання користувачів.

## Приклад UsersModule

    import { Module } from '@nestjs/common';
    import { UsersController } from './users.controller';
    import { UsersService } from './users.service';

    @Module({
        controllers: [UsersController],
        providers: [UsersService],
    })
    export class UsersModule {}

Модуль повідомляє NestJS, які компоненти належать до цього модуля.

Цей приклад демонструє базову організацію компонентів, але не повноцінну систему збереження даних, обробки помилок або авторизації.

# Architecture Is About Decisions

Архітектура — це не набір обов'язкових папок, класів або популярних патернів.

Архітектура полягає у виборі структури системи відповідно до конкретних потреб.

Наприклад, для невеликого застосунку можна вибрати:

    Modular Monolith
        +
    NestJS
        +
    PostgreSQL
        +
    Dependency Injection
        +
    Automated Tests

Це може бути цілком достатньою архітектурою.

Не обов'язково додавати:

    Microservices
    Event Sourcing
    CQRS
    Distributed Messaging
    Multiple Databases
    Complex Abstractions

якщо немає конкретних вимог, що виправдовують їхню складність.

## YAGNI

YAGNI — You Aren't Gonna Need It.

Сенс принципу: не реалізовувати складну функціональність лише тому, що вона може знадобитися колись у майбутньому.

Наприклад, якщо застосунок поки що не потребує окремого сервісу сповіщень, не обов'язково відразу будувати систему з чергами повідомлень і кількома мікросервісами.

Водночас YAGNI не означає, що потрібно ігнорувати безпеку, цілісність даних або вже відомі вимоги.

## KISS

KISS — Keep It Simple, Stupid.

Сенс принципу: віддавати перевагу простішому рішенню, якщо воно належним чином задовольняє вимоги.

Простота не означає відсутність структури.

Наприклад:

    Simple and organized
        → чіткі модулі та відповідальності

    Overengineered
        → зайві рівні абстракцій
          без реальної користі

Хороша архітектура не обов'язково складна.

---

# Technical Debt

Technical Debt — технічний борг, тобто майбутні витрати, що виникають через певні технічні рішення або компроміси.

Наприклад:

    Дублювання бізнес-логіки
        ↓
    Зміна правила в кількох місцях
        ↓
    Ризик неузгодженої поведінки

Інший приклад:

    Один великий service
        ↓
    Змішані відповідальності
        ↓
    Складніше тестування
        ↓
    Повільніші зміни

Технічний борг не завжди є результатом поганого рішення. Іноді свідомий компроміс допомагає швидше перевірити ідею або виконати термінове завдання.

Проблема виникає, коли борг не усвідомлюють, не контролюють і постійно накопичують.

Архітектурні рішення мають враховувати не тільки швидкість початкової розробки, а й подальшу вартість підтримки.

---

# Architecture Evolution

Software Architecture не є незмінною.

На початку проєкт може мати просту структуру:

    src/
    ├── users/
    └── main.ts

Зі збільшенням функціональності можуть з'явитися нові модулі:

    src/
    ├── users/
    ├── authentication/
    ├── courses/
    ├── notifications/
    └── main.ts

Пізніше може виникнути потреба розділити бізнес-логіку, зовнішні інтеграції та доступ до даних.

Архітектура розвивається під впливом:

- нових вимог;
- зростання кількості користувачів;
- появи нових функцій;
- зміни технологій;
- вимог до безпеки;
- проблем із продуктивністю;
- досвіду розробки та експлуатації.

Важливо не намагатися передбачити всі можливі майбутні потреби. Краще будувати систему так, щоб обґрунтовані зміни можна було виконувати без зайвого ризику.

---

# Як аналізувати архітектуру застосунку

Коли відкриваєш новий проєкт, спробуй відповісти на такі запитання.

## 1. Яку проблему вирішує система?

Наприклад:

    Worship Schedule
        → створення та редагування розкладів
          богослужінь

## 2. Які основні функціональні частини існують?

Наприклад:

    Authentication
    Users
    Schedules
    Schedule Editor
    Database

## 3. За що відповідає кожна частина?

Наприклад:

    Authentication
        → перевірка особи користувача

    Schedules
        → керування розкладами

    Schedule Editor
        → редагування вмісту розкладу

    Database
        → постійне збереження даних

## 4. Як компоненти взаємодіють?

Наприклад:

    Client
       ↓
    Controller
       ↓
    Service
       ↓
    Repository
       ↓
    Database

## 5. Які залежності існують?

Потрібно визначити, які компоненти використовують інші компоненти та наскільки вони залежать від конкретних реалізацій.

## 6. Де розташована бізнес-логіка?

Бізнес-правила не повинні випадково дублюватися в контролерах, frontend-компонентах і запитах до бази даних.

Критичні правила необхідно забезпечувати на відповідному довіреному рівні backend.

## 7. Як перевіряти правильність роботи?

Потрібно визначити, які компоненти можна тестувати окремо та які інтеграційні перевірки необхідні.

## 8. Що відбудеться, якщо зміниться одна частина?

Наприклад:

    PostgreSQL
        ↓ replace
    Another data storage

Чи доведеться змінювати всі бізнес-сервіси, чи можна обмежити зміни компонентом доступу до даних?

Повна заміна сховища може потребувати значної роботи, але хороші межі допомагають локалізувати її.

# Practical Example — Worship Schedule

Розглянемо навчальну модель застосунку Worship Schedule.

Користувач може:

    Register
    Login
    Create Schedule
    View Schedule
    Edit Schedule
    Delete Schedule

Кожен користувач має власні приватні розклади.

## Початкова структура

    Client
       ↓
    Backend API
       ↓
    PostgreSQL

Це загальна структура системи.

Щоб краще організувати backend, можна розділити його на модулі:

    src/
    ├── auth/
    ├── users/
    ├── schedules/
    ├── schedule-editor/
    ├── database/
    └── app.module.ts

Це лише один можливий варіант організації. Окремий `schedule-editor` може бути зайвим, якщо редагування є невеликою частиною модуля `schedules`.

## Приклад відповідальностей

    AuthModule
        → реєстрація та вхід

    UsersModule
        → дані користувачів

    SchedulesModule
        → створення, перегляд,
          редагування та видалення розкладів

    Database
        → збереження інформації

## Важлива архітектурна вимога

Оскільки розклади приватні, backend повинен перевіряти, чи має поточний користувач право працювати з конкретним розкладом.

Наприклад, недостатньо просто отримати розклад за його ID:

    GET /schedules/123

Потрібно також перевірити власника або відповідні права доступу.

Спрощена логіка:

    const schedule = await repository.findById(scheduleId);

    if (!schedule) {
        throw new NotFoundException();
    }

    if (schedule.userId !== currentUser.id) {
        throw new ForbiddenException();
    }

Це лише ілюстрація. Реальна реалізація залежить від способу автентифікації, моделі доступу та політики обробки помилок.

Головний висновок: приватність даних — не тільки функція інтерфейсу, а вимога, яку потрібно забезпечити архітектурою та backend-логікою.

## Можливе архітектурне рішення

    Modular Monolith
        ↓
    NestJS Modules
        ↓
    Services
        ↓
    Data Access Layer
        ↓
    PostgreSQL

Чому це може бути доречно:

- проєкт має відносно зрозумілу предметну область;
- функціональність можна розділити на модулі;
- один backend простіше розробляти та розгортати;
- PostgreSQL підходить для структурованих даних і зв'язків між користувачами та розкладами;
- за потреби архітектуру можна поступово розвивати.

Мікросервіси або складні розподілені механізми на старті не є обов'язковими.

# Типові архітектурні помилки

## 1. Вважати архітектуру лише структурою папок

    src/
    ├── controllers/
    ├── services/
    └── repositories/

Наявність таких папок не гарантує правильного розділення відповідальностей.

Важливо, як компоненти взаємодіють і які залежності мають.

## 2. Змішувати різні відповідальності

Наприклад, один клас одночасно приймає HTTP-запити, виконує бізнес-перевірки, формує SQL і надсилає email.

Такий клас складніше змінювати та тестувати.

## 3. Створювати занадто великі компоненти

Великий сервіс, який знає майже про всі частини системи, може стати центральним вузлом залежностей.

Це ускладнює розвиток застосунку.

## 4. Створювати занадто багато абстракцій

Не кожен клас потребує інтерфейсу, фабрики, окремого адаптера та додаткового рівня посередників.

Абстракції повинні вирішувати конкретну проблему.

## 5. Використовувати складну архітектуру без потреби

Мікросервіси, CQRS та Event Sourcing мають свої сфери застосування, але створюють додаткову складність.

Спочатку варто зрозуміти вимоги й обрати найпростіше достатнє рішення.

## 6. Ігнорувати напрямок залежностей

Якщо бізнес-логіка безпосередньо залежить від конкретного HTTP framework або способу зберігання даних, зміна технологій може стати складнішою.

Важливо розуміти, які залежності є необхідними, а які можна ізолювати.

## 7. Дублювати бізнес-правила

Якщо одне правило реалізоване в кількох незалежних місцях, зростає ризик неузгодженої поведінки.

Важливі бізнес-правила потрібно розташовувати в чітко визначених компонентах.

## 8. Не враховувати безпеку

Приховування кнопки в frontend не замінює перевірку прав доступу на backend.

Авторизація повинна виконуватися на довіреному серверному рівні.

## 9. Передчасно оптимізувати архітектуру

Не варто будувати складну систему масштабування без підтвердженої потреби.

Спочатку потрібно зрозуміти навантаження, вимоги й реальні обмеження.

## 10. Не документувати важливі рішення

Через деякий час може бути незрозуміло, чому було вибрано певну технологію або спосіб організації компонентів.

Короткий ADR може зберегти важливий контекст.

# Міні-шпаргалка

## Software Architecture

    Software Architecture
        → структура системи
        → компоненти
        → відповідальності
        → залежності
        → межі
        → архітектурні рішення

## Architecture vs Design

    Architecture
        → фундаментальна організація системи

    Design
        → організація та реалізація конкретних частин

    Implementation
        → конкретний код

## Основні елементи

    Component
        → частина системи

    Module
        → логічно організована частина програми

    Responsibility
        → за що відповідає компонент

    Dependency
        → від чого залежить компонент

    Interface
        → контракт взаємодії

    Boundary
        → межа між частинами системи

## Основні принципи

    Separation of Concerns
        → розділення відповідальностей

    Low Coupling
        → менше зайвих залежностей

    High Cohesion
        → чітка спільна мета компонента

    KISS
        → прості рішення без зайвої складності

    YAGNI
        → не створювати те, що поки не потрібно

## Quality Attributes

    Maintainability
        → підтримуваність

    Extensibility
        → можливість розширення

    Testability
        → тестованість

    Scalability
        → масштабованість

    Reliability
        → надійність

    Performance
        → продуктивність

    Security
        → безпека

## Architecture Styles

    Monolith
        → одна основна система розгортання

    Modular Monolith
        → моноліт із чіткими модульними межами

    Microservices
        → окремі сервіси з незалежним розгортанням

## Backend

    Controller
        → HTTP

    Service
        → бізнес-логіка

    Repository
        → доступ до даних

    Database
        → постійне зберігання

## Architectural Decisions

    Requirements
        ↓
    Constraints
        ↓
    Alternatives
        ↓
    Trade-offs
        ↓
    Decision
        ↓
    Implementation
        ↓
    Evaluation

## Technical Debt

    Short-term shortcut
        ↓
    Future maintenance cost

## Architecture Evolution

    Requirements change
        ↓
    Re-evaluate decisions
        ↓
    Refactor or extend
        ↓
    Test
        ↓
    Document important changes

# Головне

• Software Architecture визначає фундаментальну організацію програмної системи.

• Архітектура охоплює компоненти, відповідальності, залежності, інтерфейси та межі.

• Архітектура не зводиться до структури папок.

• Software Design і Implementation тісно пов'язані з архітектурою, але описують інші рівні рішень.

• Хороша архітектура допомагає локалізувати зміни, підтримувати код і тестувати компоненти.

• Separation of Concerns допомагає розділяти різні відповідальності.

• Low Coupling і High Cohesion — корисні орієнтири для організації компонентів.

• Інтерфейси можуть допомогти відокремити контракти від конкретних реалізацій.

• Архітектура повинна враховувати Maintainability, Testability, Security, Performance та інші важливі характеристики якості.

• Кожне архітектурне рішення має переваги, недоліки та компроміси.

• Monolith не обов'язково означає погану архітектуру.

• Modular Monolith часто є практичним вибором для навчальних і невеликих backend-проєктів.

• Мікросервіси мають сенс тоді, коли їхні переваги виправдовують додаткову складність.

• KISS і YAGNI допомагають уникати зайвого ускладнення.

• Technical Debt може бути свідомим компромісом, але його потрібно контролювати.

• Архітектура розвивається разом із вимогами до системи.

• Для NestJS важливо розуміти, як модулі, контролери, сервіси та dependency injection допомагають організувати застосунок.

• Бізнес-логіка, HTTP-обробка та доступ до даних повинні мати зрозумілі межі відповідальності.

• Безпека приватних даних повинна забезпечуватися backend-логікою, а не лише frontend-інтерфейсом.

• Архітектурне рішення варто приймати на підставі вимог, обмежень і реальних потреб, а не популярності технології.

• Хороша архітектура — це не максимально складна система, а система, структура якої відповідає задачам і полегшує подальший розвиток.

    REQUIREMENTS

         ↓
    COMPONENTS
         ↓
    RESPONSIBILITIES
         ↓
    DEPENDENCIES
         ↓
    IMPLEMENTATION
         ↓
    TESTING
         ↓
