
# Composition over Inheritance — композиція замість наслідування

**Composition over Inheritance** — це принцип проєктування програмного забезпечення, який рекомендує віддавати перевагу композиції об'єктів замість побудови складних ієрархій наслідування, коли це робить код гнучкішим і простішим для підтримки.

Головна ідея:

**Inheritance (наслідування) описує відношення «є різновидом», а Composition (композиція) дозволяє створювати поведінку об'єкта шляхом поєднання інших об'єктів або функцій.**

Наприклад, замість того щоб створювати класи `FlyingBird`, `SwimmingBird`, `FlyingSwimmingBird` і `WalkingBird`, можна визначити окремі можливості — літати, плавати та ходити — і комбінувати їх для різних видів птахів.

Це допомагає уникати жорстких ієрархій класів, зменшує залежність від батьківських класів і полегшує повторне використання поведінки.

---

## 1. Навіщо потрібен Composition over Inheritance?

У невеликій програмі наслідування часто здається природним способом повторного використання коду.

Наприклад, можна створити базовий клас `Animal`, а потім класи `Dog`, `Cat` і `Bird`, які наслідують його властивості та методи.

Але зі зростанням застосунку виникають складніші вимоги:
- одні тварини вміють літати, інші — ні;
- одні можуть плавати, інші — ні;
- поведінка може змінюватися залежно від ситуації;
- різні класи можуть потребувати однакової поведінки, не будучи спорідненими за ієрархією;
- зміни в базовому класі можуть впливати на багато дочірніх класів.

Якщо намагатися розв'язувати всі ці проблеми лише наслідуванням, ієрархія може стати надто складною.

Композиція пропонує інший підхід: створювати об'єкти з незалежних компонентів, які виконують конкретні завдання.

### Переваги композиції

✔ Поведінку можна повторно використовувати в різних класах.

✔ Компоненти можна комбінувати в різних конфігураціях.

✔ Заміна однієї поведінки не обов'язково потребує зміни ієрархії класів.

✔ Залежності можна передавати об'єктам ззовні.

✔ Код часто простіше тестувати окремо.

✔ Архітектура може бути гнучкішою, коли вимоги часто змінюються.

**Важливо:** це не означає, що наслідування потрібно повністю заборонити. Наслідування залишається корисним, коли між типами справді існує стабільне відношення «є різновидом» і дочірній тип коректно відповідає контракту батьківського типу.

---

## 2. Inheritance — наслідування

Наслідування дозволяє створити клас на основі іншого класу.

Дочірній клас отримує доступ до доступних властивостей і методів батьківського класу та може додавати власну поведінку або перевизначати успадковані методи.

### Приклад

    class Animal {
        constructor(name) {
            this.name = name;
        }

        eat() {
            return `${this.name} is eating`;
        }
    }

    class Dog extends Animal {
        bark() {
            return `${this.name} is barking`;
        }
    }

    const dog = new Dog("Rex");

    console.log(dog.eat());
    console.log(dog.bark());

У цьому прикладі `Dog` наслідує `Animal`.

Собака є твариною, тому наслідування тут природне.

Клас `Dog` отримує метод `eat()` від `Animal` і додає власний метод `bark()`.

### Коли наслідування доречне?

Наслідування може бути хорошим рішенням, якщо:

- існує справжнє відношення «є різновидом»;
- базовий клас визначає стабільний контракт;
- дочірні класи можуть коректно замінювати батьківський тип;
- ієрархія залишається простою та зрозумілою.

Проблема виникає тоді, коли наслідування використовують переважно для повторного використання коду, хоча логічного відношення між типами немає.

---

## 3. Composition — композиція

Композиція дозволяє створювати об'єкт, поєднуючи його з іншими об'єктами або функціями, які надають потрібну поведінку.

Замість того щоб успадковувати всі можливості від одного батьківського класу, об'єкт використовує окремі компоненти.

### Приклад із функціями

    function eat() {
        return "Eating";
    }

    function sleep() {
        return "Sleeping";
    }

    function fly() {
        return "Flying";
    }

    function createBird(name) {
        return {
            name,
            eat,
            sleep,
            fly,
        };
    }

    const bird = createBird("Eagle");

    console.log(bird.eat());
    console.log(bird.fly());

Функції `eat`, `sleep` і `fly` можна повторно використовувати в інших об'єктах.

Проте в цьому прикладі всі створені птахи отримують здатність літати. Якщо це не відповідає вимогам, потрібно комбінувати поведінку вибірково.

### Композиція не обмежується класами

У JavaScript композицію можна реалізувати через:
- функції;
- об'єкти;
- модулі;
- передавання залежностей;
- невеликі класи-компоненти;
- функції вищого порядку.

У TypeScript можна додатково використовувати інтерфейси для опису контрактів компонентів.

---

## 4. Проблема надмірного наслідування

Розглянемо приклад із птахами.

    class Bird {
        eat() {
            return "Eating";
        }

        fly() {
            return "Flying";
        }
    }

    class Eagle extends Bird {}

    class Penguin extends Bird {}

На перший погляд, структура проста.

Але пінгвіни не літають. Метод `fly()` у базовому класі не відповідає поведінці всіх птахів.

Можна перевизначити метод:

    class Penguin extends Bird {
        fly() {
            throw new Error("Penguins cannot fly");
        }
    }

Але це не найкраще рішення. Базовий клас обіцяє поведінку, яку деякі дочірні класи не можуть підтримати.

Інший варіант — створити кілька проміжних класів:

    class Bird {
        eat() {}
    }

    class FlyingBird extends Bird {
        fly() {}
    }

    class SwimmingBird extends Bird {
        swim() {}
    }

Але що робити з птахом, який і літає, і плаває? А якщо з'явиться поведінка пірнання, бігу чи іншої спеціалізованої дії?

Ієрархія може почати ускладнюватися.

**Висновок:** не кожна спільна характеристика означає, що її потрібно реалізовувати через спільний базовий клас.

---

## 5. Кращий підхід: композиція поведінки

Замість того щоб визначати всі можливості в базовому класі, можна створити незалежні функції поведінки.

    function eat() {
        return "Eating";
    }

    function fly() {
        return "Flying";
    }

    function swim() {
        return "Swimming";
    }

    function createBird(name, behaviors) {
        return {
            name,
            ...behaviors,
        };
    }

Тепер можна створювати різних птахів:

    const eagle = createBird("Eagle", {
        eat,
        fly,
    });

    const penguin = createBird("Penguin", {
        eat,
        swim,
    });

    console.log(eagle.fly());
    console.log(penguin.swim());

У цьому прикладі:
- орел отримує поведінку харчування та польоту;
- пінгвін отримує поведінку харчування та плавання;
- поведінка не нав'язується всім об'єктам через один базовий клас.

Це простий приклад композиції через об'єкти та функції.

У реальному застосунку потрібно також враховувати типи, стан, залежності та правила предметної області.

---

## 6. Композиція об'єктів

Композиція може поєднувати не лише функції, а й окремі об'єкти, кожен із яких має власну відповідальність.

Наприклад, автомобіль використовує двигун.

    class Engine {
        start() {
            return "Engine started";
        }
    }

    class Car {
        constructor(engine) {
            this.engine = engine;
        }

        start() {
            return this.engine.start();
        }
    }

    const engine = new Engine();
    const car = new Car(engine);

    console.log(car.start());

Клас `Car` не повинен самостійно реалізовувати всі деталі роботи двигуна.

Він делегує цю операцію об'єкту `Engine`.

### Що тут важливо?

- `Engine` відповідає за запуск двигуна.
- `Car` відповідає за поведінку автомобіля.
- Автомобіль використовує двигун як залежний компонент.
- Реалізацію двигуна можна замінити, якщо інтерфейс взаємодії залишається сумісним.

Це приклад композиції через передавання залежності.

**Примітка:** у програмуванні слово «композиція» іноді використовують у вузькому сенсі — як відношення володіння частиною об'єкта. У принципі Composition over Inheritance поняття часто використовують ширше: як побудову поведінки з окремих компонентів.

---

## 7. Composition over Inheritance у TypeScript

TypeScript дозволяє описувати можливості через інтерфейси.

Наприклад, визначимо контракти для польоту та плавання.

    interface Flyable {
        fly(): string;
    }

    interface Swimmable {
        swim(): string;
    }

    interface Eatable {
        eat(): string;
    }

Тепер можна реалізувати окремі компоненти:

    class BirdEatingBehavior implements Eatable {
        eat() {
            return "Eating";
        }
    }

    class FlyingBehavior implements Flyable {
        fly() {
            return "Flying";
        }
    }

    class SwimmingBehavior implements Swimmable {
        swim() {
            return "Swimming";
        }
    }

І використати їх у різних класах:

    class Eagle {
        constructor(
            private readonly eating: Eatable,
            private readonly flying: Flyable
        ) {}

        eat() {
            return this.eating.eat();
        }

        fly() {
            return this.flying.fly();
        }
    }

    const eagle = new Eagle(
        new BirdEatingBehavior(),
        new FlyingBehavior()
    );

У цьому прикладі `Eagle` не наслідує реалізацію поведінки від великого базового класу. Він отримує потрібні компоненти через конструктор.

### Переваги

- залежності видно в конструкторі;
- поведінку можна замінювати;
- компоненти можна тестувати окремо;
- клас не мусить знати всі деталі реалізації залежностей.

### Недоліки

Композиція також може стати надмірно складною, якщо для кожної простої операції створювати окремий клас без реальної потреби.

Не обов'язково використовувати інтерфейси та класи для всього. Для простої поведінки часто достатньо функцій.

## 8. Композиція та Dependency Injection

**Dependency Injection (DI)** — це передавання компоненту залежностей ззовні, замість того щоб компонент самостійно створював їх усередині.

DI часто допомагає реалізувати композицію.

Розглянемо сервіс, який надсилає повідомлення.

Поганий варіант:

    class NotificationService {
        constructor() {
            this.emailClient = new ConcreteEmailClient();
        }

        async send(message) {
            return this.emailClient.send(message);
        }
    }

Сервіс сам створює конкретний клієнт. Через це його складніше тестувати з іншою реалізацією.

Краще передавати залежність:

    class NotificationService {
        constructor(emailClient) {
            this.emailClient = emailClient;
        }

        async send(message) {
            return this.emailClient.send(message);
        }
    }

Тепер можна передати різні реалізації клієнта.

    const emailClient = new ConcreteEmailClient();

    const notificationService =
        new NotificationService(emailClient);

А під час тестування — підставну реалізацію:

    const testEmailClient = {
        async send(message) {
            return {
                success: true,
                message,
            };
        },
    };

    const notificationService =
        new NotificationService(testEmailClient);

Тепер тест не залежить від реального постачальника email.

### Зв'язок між поняттями

- **Composition** — спосіб поєднання компонентів у систему.
- **Dependency Injection** — спосіб передавання залежностей компонентам.
- **Low Coupling** — бажаний результат, коли залежності залишаються контрольованими.

Ці поняття пов'язані, але не є синонімами.

## 9. Composition over Inheritance у NestJS

У NestJS композиція та Dependency Injection є звичними способами організації застосунку.

Наприклад, сервіс користувачів може використовувати репозиторій.

    import { Injectable } from "@nestjs/common";

    @Injectable()
    export class UsersRepository {
        async findById(id: number) {
            // Отримання користувача з бази даних
            return null;
        }
    }

Сервіс отримує репозиторій через конструктор:

    import { Injectable } from "@nestjs/common";

    @Injectable()
    export class UsersService {
        constructor(
            private readonly usersRepository: UsersRepository
        ) {}

        async findById(id: number) {
            return this.usersRepository.findById(id);
        }
    }

Контролер використовує сервіс:

    import { Controller, Get, Param } from "@nestjs/common";

    @Controller("users")
    export class UsersController {
        constructor(
            private readonly usersService: UsersService
        ) {}

        @Get(":id")
        findById(@Param("id") id: string) {
            return this.usersService.findById(Number(id));
        }
    }

Спрощена схема:

    UsersController
          |
          v
      UsersService
          |
          v
     UsersRepository
          |
          v
       Database

Це композиція компонентів через залежності.

Кожен компонент виконує окрему роль:
- контролер працює з HTTP;
- сервіс організовує прикладну логіку;
- репозиторій відповідає за доступ до даних.

### Чому не потрібно наслідувати сервіси?

Не варто створювати `UsersService`, який наслідує `DatabaseService`, лише для того, щоб отримати методи доступу до бази.

Краще передати компонент доступу до даних як залежність.

Наслідування доречне для справжнього відношення «є різновидом», а не лише для отримання готових методів.

## 10. Композиція в React

У React композиція є одним із базових принципів побудови інтерфейсу.

Замість створення великої ієрархії компонентів через наслідування React зазвичай використовує компоненти, які вкладаються один в одного та передають поведінку через props.

Наприклад:

    function Card({ title, children }) {
        return (
            <section className="card">
                <h2>{title}</h2>
                <div>{children}</div>
            </section>
        );
    }

Використання:

    function SchedulePage() {
        return (
            <Card title="Розклад богослужінь">
                <p>Неділя — Божественна літургія о 9:00.</p>
            </Card>
        );
    }

Компонент `Card` не повинен знати, який саме вміст у нього вкладено. Він відповідає за структуру картки, а батьківський компонент визначає її вміст.

### Композиція через props

Можна передавати також окремі елементи:

    function PageLayout({ header, content, footer }) {
        return (
            <div className="page-layout">
                <header>{header}</header>
                <main>{content}</main>
                <footer>{footer}</footer>
            </div>
        );
    }

    function App() {
        return (
            <PageLayout
                header={<h1>Worship Schedule</h1>}
                content={<p>Тут розміщується розклад.</p>}
                footer={<p>© 2026</p>}
            />
        );
    }

Це приклад композиції інтерфейсу.

**Важливо:** Composition over Inheritance у React не означає, що треба уникати будь-якого повторення коду. Для повторного використання можуть бути доречними компоненти, власні hooks, функції або контексти — залежно від конкретного завдання.

## 11. Наслідування проти композиції

| Критерій | Inheritance | Composition |
|---|---|---|
| Основна ідея | Розширення базового класу | Поєднання незалежних компонентів |
| Відношення | «Є різновидом» | «Використовує» або «складається з» |
| Повторне використання | Через ієрархію класів | Через компоненти та делегування |
| Заміна поведінки | Часто потребує зміни ієрархії або перевизначення | Часто можлива через заміну компонента |
| Залежність від базового класу | Може бути сильною | Може бути меншою за належних меж |
| Гнучкість | Добра для стабільних ієрархій | Часто краща для комбінування поведінки |
| Складність | Може зростати зі складністю ієрархії | Може зростати через надмірну кількість компонентів |
| Типове використання | Стабільне відношення «є різновидом» | Змінні можливості та незалежні відповідальності |

Не слід сприймати цю таблицю як доказ того, що композиція завжди краща. Правильний вибір залежить від моделі предметної області та вимог до змін.

## 12. Коли композиція доречніша за наслідування?

Композицію варто розглянути, якщо:

- потрібно комбінувати різні можливості в різних об'єктах;
- поведінка має змінюватися незалежно від типу об'єкта;
- ієрархія класів стає занадто глибокою;
- дочірні класи перевизначають багато методів базового класу;
- базовий клас містить методи, які деякі дочірні класи не можуть коректно реалізувати;
- компонент має використовувати інший компонент, а не бути його різновидом;
- залежність від конкретної реалізації ускладнює тестування або заміну технології.

### Приклад

Потрібно створити різні типи сповіщень:
- email;
- SMS;
- push-повідомлення.

Не обов'язково створювати базовий клас `MessageService`, а потім будувати складну ієрархію для всіх сценаріїв.

Можна визначити спільний контракт і передавати потрібний канал сповіщення сервісу, який організовує надсилання.

    interface NotificationChannel {
        send(message: string): Promise<void>;
    }

    class EmailChannel implements NotificationChannel {
        async send(message: string) {
            // Надсилання email
        }
    }

    class SmsChannel implements NotificationChannel {
        async send(message: string) {
            // Надсилання SMS
        }
    }

    class NotificationService {
        constructor(
            private readonly channel: NotificationChannel
        ) {}

        async notify(message: string) {
            await this.channel.send(message);
        }
    }

Це приклад композиції та залежності від контракту.

## 13. Коли наслідування залишається хорошим рішенням?

Наслідування не є помилкою саме по собі.

Воно може бути доречним, коли:

1. Існує справжнє відношення «є різновидом».
2. Базовий клас визначає стабільну поведінку та контракт.
3. Дочірній клас може виконувати всі очікування базового типу.
4. Ієрархія не створює надмірної складності.
5. Наслідування відображає модель предметної області або корисну абстракцію.

Наприклад, якщо різні типи платіжних помилок мають спільний базовий тип, спеціалізовані класи помилок можуть бути виправданими.

    class PaymentError extends Error {
        constructor(message) {
            super(message);
            this.name = "PaymentError";
        }
    }

    class PaymentDeclinedError extends PaymentError {
        constructor() {
            super("Payment was declined");
            this.name = "PaymentDeclinedError";
        }
    }

Тут `PaymentDeclinedError` є конкретним різновидом `PaymentError`, а наслідування дозволяє обробляти різні спеціалізовані помилки через спільний базовий тип.

**Правило:** не замінюй наслідування композицією механічно. Обирай підхід, який найкраще виражає відношення між компонентами та спрощує їхній розвиток.

## 14. Зв'язок із SOLID

Composition over Inheritance пов'язаний із кількома принципами SOLID.

### Single Responsibility Principle (SRP)

Кожен компонент повинен мати чітку відповідальність.

Композиція дозволяє будувати складну поведінку з менших компонентів, кожен із яких виконує конкретне завдання.

### Open/Closed Principle (OCP)

Програмні компоненти мають бути відкритими для розширення та закритими для непотрібної зміни.

Якщо новий спосіб надсилання сповіщень можна додати через нову реалізацію контракту, не переписуючи бізнес-логіку, це може допомогти дотримуватися OCP.

### Liskov Substitution Principle (LSP)

Дочірній тип повинен коректно замінювати базовий тип, не порушуючи очікувань від його контракту.

Проблеми виникають, коли наслідування використовується для типів, які не можуть підтримати поведінку базового класу.

### Dependency Inversion Principle (DIP)

Важливі компоненти не повинні без потреби залежати від конкретних деталей реалізації.

Композиція разом із контрактами та Dependency Injection може допомогти зробити залежності гнучкішими.

Ці принципи доповнюють один одного, але не є тотожними Composition over Inheritance.

## 15. Типові помилки

### Помилка 1. Вважати наслідування забороненим

Наслідування корисне для стабільних ієрархій типів.

Проблема — не в самому `extends`, а в неправильному моделюванні відношень між класами.

### Помилка 2. Створювати надто багато дрібних компонентів

Якщо кожна операція має власний клас, навіть коли це не додає ясності чи гнучкості, архітектура може стати складнішою.

**Краще:** використовувати композицію там, де вона спрощує заміну поведінки, тестування або повторне використання.

### Помилка 3. Використовувати композицію без чітких контрактів

Якщо компоненти взаємодіють через незрозумілі об'єкти та неузгоджені методи, композиція сама по собі не зробить систему якісною.

**Краще:** визначати зрозумілі інтерфейси та відповідальності.

### Помилка 4. Створювати базовий клас лише для повторного використання коду

Два класи можуть мати схожі методи, але не обов'язково повинні наслідувати один одного.

Якщо вони не є різновидами одного типу, композиція або спільна функція можуть бути кращими.

### Помилка 5. Вважати, що композиція автоматично забезпечує Low Coupling

Компонент може бути побудований через композицію, але при цьому залежати від багатьох конкретних класів.

Потрібно окремо оцінювати напрямки залежностей і контракти між компонентами.

### Помилка 6. Дублювати поведінку замість її повторного використання

Якщо кілька компонентів реалізують однакову складну поведінку незалежно, зміни можуть потребувати редагування багатьох місць.

Варто визначити, чи можна винести спільну поведінку в компонент або функцію.

### Помилка 7. Застосовувати абстракції без потреби

Не кожен клас потребує інтерфейсу, а не кожна залежність повинна бути змінною.

Спочатку визнач реальну проблему, а потім обирай відповідну абстракцію.

## 16. Практичні правила

Перед тим як використовувати наслідування, запитай себе:

1. Чи справді дочірній клас є різновидом батьківського?
2. Чи може дочірній клас коректно підтримувати контракт базового класу?
3. Чи не доведеться перевизначати багато методів базового класу?
4. Чи не стає ієрархія надто глибокою?
5. Чи не використовую я наслідування лише для повторного використання кількох методів?

Якщо наслідування створює зайві обмеження, розглянь композицію.

Перед тим як створювати композицію, запитай себе:

1. Яку конкретну поведінку потрібно винести в компонент?
2. Хто повинен відповідати за її реалізацію?
3. Які дані компоненту потрібні?
4. Який контракт потрібен для взаємодії?
5. Чи справді новий компонент полегшить зміни або тестування?
6. Чи не додає він зайвого рівня абстракції?

### Простий алгоритм вибору

1. Визнач відповідальність класу.
2. Перевір, чи існує справжнє відношення «є різновидом».
3. Якщо так, розглянь наслідування.
4. Якщо клас лише використовує іншу поведінку, розглянь композицію.
5. Визнач необхідні контракти та залежності.
6. Перевір, чи можна замінити компонент без значних змін у решті системи.
7. Оціни, чи стала архітектура простішою для розуміння.

## 17. Мініпрактика

### Завдання 1. Транспорт

Є класи `Car`, `Boat` і `AmphibiousVehicle`.

Подумай:
- які можливості спільні;
- чи потрібне наслідування;
- як комбінувати рух по землі та воді;
- чи не створює ієрархія зайвої складності.

### Завдання 2. Сповіщення

Потрібно підтримати email, SMS і push.

Спроєктуй:
- спільний контракт каналу сповіщення;
- окремі реалізації;
- сервіс, який використовує переданий канал;
- тестову реалізацію для перевірки сервісу без зовнішнього постачальника.

### Завдання 3. Розклад богослужінь

У застосунку Worship Schedule потрібно:
- зберігати розклад;
- редагувати текст;
- формувати PDF;
- надсилати посилання на документ.

Подумай:
- які компоненти повинні мати окремі відповідальності;
- які компоненти можна комбінувати;
- які залежності слід передавати через конструктор;
- чи потрібно використовувати наслідування взагалі.

### Завдання 4. Рефакторинг

Знайди клас, який:
- виконує декілька різних завдань;
- створює всі залежності самостійно;
- має багато перевизначених методів;
- складно тестується.

Спробуй винести одну відповідальність у компонент і передати її через конструктор.

Порівняй код до і після рефакторингу.

## 20. Мінішпаргалка

| Поняття | Коротке пояснення |
|---|---|
| Inheritance | Створення класу на основі іншого класу |
| Composition | Поєднання об'єктів або компонентів для створення поведінки |
| «Is-a» | Відношення «є різновидом» |
| «Has-a» / «Uses-a» | Відношення «має» або «використовує» |
| Dependency Injection | Передавання залежностей компоненту ззовні |
| Interface | Контракт, що описує необхідну поведінку |
| SRP | Принцип однієї відповідальності |
| OCP | Принцип відкритості для розширення та закритості для зміни |
| LSP | Принцип підстановки Лісков |
| DIP | Принцип інверсії залежностей |

### Головне правило

**Віддавай перевагу композиції, коли потрібно поєднувати або замінювати поведінку незалежних компонентів. Використовуй наслідування, коли воно точно відображає стабільне відношення між типами.**

Не використовуй наслідування лише для повторного використання коду. І не створюй композицію з десятків дрібних компонентів без практичної потреби.

Мета — не вибрати один механізм на всі випадки, а створити систему, у якій компоненти мають зрозумілі відповідальності, контрольовані залежності та можуть розвиватися без зайвої складності.
