
# Coupling and Cohesion — зв'язність і зчеплення компонентів

**Coupling and Cohesion** — це два важливі поняття програмної архітектури, які допомагають оцінювати якість організації коду та взаємодії між його частинами.

- **Coupling (зчеплення, ступінь залежності)** — показує, наскільки один компонент залежить від інших компонентів.
- **Cohesion (зв'язність, внутрішня узгодженість)** — показує, наскільки добре елементи одного компонента пов'язані спільною метою.

Головна ідея хорошої архітектури:

**Low Coupling + High Cohesion = компоненти з чіткими відповідальностями та мінімально необхідними залежностями.**

Це не абсолютне правило, яке автоматично гарантує якісну архітектуру, але дуже корисний орієнтир під час проєктування та рефакторингу.

---

## 1. Навіщо потрібні Coupling і Cohesion?

У невеликому застосунку можна розмістити багато логіки в одній функції або класі. Спочатку це здаватиметься зручним, але зі зростанням проєкту зміни ставатимуть складнішими.

Наприклад, у вебзастосунку для створення розкладу потрібно:

- приймати HTTP-запити;
- перевіряти вхідні дані;
- застосовувати правила створення розкладу;
- зберігати дані в PostgreSQL;
- формувати відповіді для frontend;
- надсилати сповіщення.

Якщо всі ці операції тісно переплетені, зміна одного механізму може вплинути на багато інших частин застосунку.

Coupling і Cohesion допомагають оцінити, наскільки добре розподілені ці відповідальності.

### Ознаки хорошої організації

✔ Компонент має зрозуміле призначення.

✔ Пов'язані операції розміщені разом.

✔ Компонент не залежить від зайвих деталей інших компонентів.

✔ Зміни локалізуються в тих частинах системи, яких вони стосуються.

✔ Компоненти можна тестувати окремо, коли це доцільно.

✔ Структуру проєкту можна розширювати без постійного переписування наявного коду.

## 2. Coupling — залежність між компонентами

**Coupling** показує, наскільки один компонент залежить від інших компонентів для виконання своєї роботи.

Наприклад, `UsersService` може залежати від `UsersRepository`, щоб отримувати дані користувачів.

    class UsersService {
        constructor(usersRepository) {
            this.usersRepository = usersRepository;
        }

        async findUser(id) {
            return this.usersRepository.findById(id);
        }
    }

Ця залежність сама по собі не є проблемою. Сервісу потрібен спосіб отримувати дані.

Питання в тому, **наскільки сильна залежність і скільки деталей одного компонента відомо іншому**.

Якщо сервіс знає лише потрібний метод репозиторію, залежність може бути відносно слабкою.

Якщо сервіс знає внутрішню структуру бази даних, створює SQL-запити, керує з'єднаннями та залежить від конкретної бібліотеки, він може бути значно сильніше пов'язаний із деталями зберігання.

### High Coupling — сильна залежність

Сильне зчеплення виникає, коли компоненти надмірно залежать від внутрішньої реалізації один одного.

Можливі наслідки:

- зміна одного компонента вимагає змін в інших;
- компоненти складніше тестувати ізольовано;
- повторне використання коду стає складнішим;
- помилки або зміни поширюються на значну частину системи;
- заміна технології може вимагати масштабного рефакторингу.

### Low Coupling — слабка залежність

Слабке зчеплення означає, що компоненти мають лише необхідні залежності та взаємодіють через зрозумілі контракти.

Переваги:

- компоненти легше змінювати незалежно;
- тестування стає простішим;
- реалізації можна замінювати з меншим впливом на інші частини системи;
- межі між компонентами зрозуміліші.

**Важливо:** Low Coupling не означає повну відсутність залежностей. Програма складається з компонентів, які повинні співпрацювати.

## 3. Приклад сильного Coupling

Розглянемо сервіс, який безпосередньо залежить від конкретного способу роботи з PostgreSQL.

    import { Pool } from "pg";

    class UsersService {
        constructor() {
            this.pool = new Pool({
                connectionString: process.env.DATABASE_URL,
            });
        }

        async findUser(id) {
            const result = await this.pool.query(
                "SELECT id, name, email FROM users WHERE id = $1",
                [id]
            );

            return result.rows[0] ?? null;
        }
    }

Цей приклад має кілька проблем:

1. Сервіс сам створює підключення до бази даних.
2. Він безпосередньо залежить від бібліотеки `pg`.
3. Він знає SQL-запит і структуру таблиці.
4. Його складніше тестувати без реальної бази або додаткових налаштувань.
5. Заміна способу зберігання даних може вимагати зміни самого сервісу.

Для невеликого навчального скрипту такий код може бути прийнятним. Але для застосунку, що зростає, варто подумати про розділення відповідальностей.

## 4. Приклад слабшого Coupling

Винесемо доступ до бази даних в окремий компонент.

    class UsersRepository {
        constructor(database) {
            this.database = database;
        }

        async findById(id) {
            const result = await this.database.query(
                "SELECT id, name, email FROM users WHERE id = $1",
                [id]
            );

            return result.rows[0] ?? null;
        }
    }

Сервіс використовує репозиторій:

    class UsersService {
        constructor(usersRepository) {
            this.usersRepository = usersRepository;
        }

        async findUser(id) {
            return this.usersRepository.findById(id);
        }
    }

Тепер:

- `UsersService` відповідає за логіку роботи з користувачами;
- `UsersRepository` відповідає за отримання даних;
- створення підключення до бази даних відбувається окремо;
- сервіс не повинен знати, як саме виконується SQL-запит.

Залежність залишилася, але стала зрозумілішою.

### Що змінилося?

Раніше сервіс сам створював підключення та виконував SQL.

Тепер сервіс знає лише про операцію `findById()`.

Це приклад того, як розділення відповідальностей може зменшити непотрібну залежність.

## 5. Cohesion — внутрішня узгодженість компонента

**Cohesion** показує, наскільки елементи одного компонента пов'язані між собою за призначенням.

Висока Cohesion означає, що функції, методи й дані компонента допомагають реалізувати спільну відповідальність.

Наприклад, модуль `users` може містити:

- створення користувача;
- пошук користувача;
- оновлення профілю;
- перевірку правил, пов'язаних із користувачем.

Ці операції логічно пов'язані між собою.

Натомість розміщення в тому самому компоненті незалежних операцій надсилання email, обчислення вартості товарів і генерації PDF може свідчити про низьку Cohesion.

### High Cohesion — висока внутрішня узгодженість

Компонент має одну чітку функціональну мету, а його елементи працюють на її досягнення.

Переваги:

- компонент легше зрозуміти;
- відповідальність простіше описати;
- зміни краще локалізуються;
- компонент легше тестувати;
- його поведінку простіше повторно використовувати.

### Low Cohesion — низька внутрішня узгодженість

Компонент містить багато слабо пов'язаних функцій.

Наприклад:

    class ApplicationService {
        createUser() {
            // Створення користувача
        }

        calculateOrderTotal() {
            // Обчислення вартості замовлення
        }

        sendEmail() {
            // Надсилання email
        }

        generatePdf() {
            // Формування PDF
        }
    }

Назва `ApplicationService` дуже загальна, а методи виконують різні завдання.

Це не означає, що кожен метод обов'язково повинен бути окремим класом. Але варто визначити, які операції мають спільну відповідальність і чи потрібно розділити цей компонент.

## 6. Приклад високої Cohesion

Розглянемо модуль роботи з користувачами.

    class UsersService {
        constructor(usersRepository) {
            this.usersRepository = usersRepository;
        }

        async findById(id) {
            return this.usersRepository.findById(id);
        }

        async findByEmail(email) {
            return this.usersRepository.findByEmail(email);
        }

        async updateProfile(id, data) {
            const user = await this.usersRepository.findById(id);

            if (!user) {
                throw new Error("User not found");
            }

            return this.usersRepository.updateProfile(id, data);
        }
    }

Методи належать до однієї функціональної області — роботи з користувачами.

Це ознака високої Cohesion, хоча остаточна оцінка залежить від реальних обов'язків сервісу та правил застосунку.

### Чи означає High Cohesion, що всі методи повинні бути в одному класі?

Ні.

Якщо логіка користувачів стає складною, її можна розділити на кілька компонентів, наприклад:

- `UsersService` — сценарії роботи з користувачами;
- `UserProfileService` — правила профілю;
- `UserPermissionsService` — правила доступу.

Головне — щоб кожен компонент мав чітку відповідальність, а не щоб усі пов'язані методи обов'язково містилися в одному файлі.

## 7. Як Coupling і Cohesion працюють разом?

Ці поняття доповнюють одне одного.

- Coupling оцінює зв'язки **між** компонентами.
- Cohesion оцінює зв'язність елементів **усередині** компонента.

Зазвичай хорошим орієнтиром є слабкі непотрібні залежності між компонентами та висока внутрішня узгодженість кожного компонента.

| Coupling | Cohesion | Типова оцінка |
|---|---|---|
| Low | High | Бажаний напрямок проєктування |
| High | High | Компоненти мають чіткі ролі, але сильно залежать один від одного |
| Low | Low | Компонент мало залежить від інших, але має нечітке призначення |
| High | Low | Часто ознака заплутаної структури |

Ця таблиця є орієнтиром, а не автоматичним способом оцінювання архітектури. Наприклад, деякі компоненти закономірно мають більше залежностей, ніж інші.

### Випадок 1. Low Coupling + High Cohesion

`UsersService` відповідає за сценарії користувачів і взаємодіє з репозиторієм через зрозумілі методи.

Це бажаний напрямок.

### Випадок 2. High Coupling + High Cohesion

Компонент має чітку відповідальність, але залежить від багатьох конкретних компонентів.

Наприклад, сервіс замовлень може мати логічно цілісну відповідальність, але безпосередньо залежати від конкретних платіжного сервісу, email-клієнта, файлового сховища та бази даних.

Потрібно оцінити, які залежності необхідні, а які можна ізолювати.

### Випадок 3. Low Coupling + Low Cohesion

Компонент майже не залежить від інших, але містить багато не пов'язаних між собою функцій.

Наприклад, утилітарний модуль із функціями обчислення податків, форматування дат, обробки користувачів і генерації звітів.

Відсутність залежностей не компенсує нечітку відповідальність.

### Випадок 4. High Coupling + Low Cohesion

Один великий сервіс одночасно обробляє користувачів, платежі, email, SQL-запити та HTTP-відповіді.

Він має багато залежностей і нечітку внутрішню структуру.

Такий компонент часто потребує рефакторингу.

## 8. Coupling і Separation of Concerns

**Separation of Concerns** — це принцип розділення різних відповідальностей.

**Coupling** допомагає оцінити, наскільки сильно компоненти залежать один від одного після такого розділення.

Наприклад, можна розділити серверний код на:

    src/
    ├── users/
    │   ├── users.controller.ts
    │   ├── users.service.ts
    │   └── users.repository.ts
    └── database/
        └── database.module.ts

Але саме створення цих файлів не гарантує Low Coupling.

Якщо `UsersController` безпосередньо керує SQL-запитами, а `UsersService` залежить від деталей HTTP, відповідальності все ще можуть бути змішані.

Потрібно не лише розділяти код, а й визначати межі взаємодії між компонентами.

## 9. Coupling і Dependency Injection у NestJS

Dependency Injection (DI) — це спосіб передавання компоненту залежностей, які потрібні йому для роботи.

У NestJS DI допомагає не створювати залежні об'єкти безпосередньо всередині кожного сервісу.

Наприклад:

    import { Injectable } from "@nestjs/common";

    @Injectable()
    export class UsersRepository {
        async findById(id: number) {
            // Тут виконується доступ до даних
            return null;
        }
    }

Сервіс отримує репозиторій через конструктор:

    import { Injectable } from "@nestjs/common";
    import { UsersRepository } from "./users.repository";

    @Injectable()
    export class UsersService {
        constructor(
            private readonly usersRepository: UsersRepository
        ) {}

        async findById(id: number) {
            return this.usersRepository.findById(id);
        }
    }

NestJS створює та передає залежності відповідно до налаштування модулів і провайдерів.

### Як це допомагає?

- Залежність оголошена явно в конструкторі.
- Сервіс не створює репозиторій самостійно.
- Тестування сервісу можна організувати з тестовою реалізацією залежності.
- Управління створенням компонентів бере на себе контейнер NestJS.

**Важливо:** Dependency Injection не гарантує Low Coupling автоматично. Сервіс усе одно може залежати від конкретного класу та його деталей. DI допомагає керувати залежностями, але якість меж між компонентами потрібно проєктувати окремо.

## 10. Залежність від інтерфейсу замість конкретної реалізації

У TypeScript можна визначити контракт, який описує необхідну поведінку репозиторію.

    export interface User {
        id: number;
        name: string;
        email: string;
    }

    export interface UsersRepositoryPort {
        findById(id: number): Promise<User | null>;
    }

Сервісу потрібна лише операція `findById()`:

    export class UsersService {
        constructor(
            private readonly usersRepository: UsersRepositoryPort
        ) {}

        async findById(id: number) {
            return this.usersRepository.findById(id);
        }
    }

Тепер сервіс залежить від опису необхідної поведінки, а не від деталей SQL-запитів.

Цей підхід корисний, коли потрібно:
- мати кілька реалізацій доступу до даних;
- тестувати сервіс із підставною реалізацією;
- ізолювати бізнес-логіку від інфраструктури;
- контролювати напрямок залежностей.

У TypeScript інтерфейси існують лише під час перевірки типів і не доступні як значення під час виконання JavaScript. Для DI в NestJS зазвичай використовують runtime-токени, наприклад рядки, символи або абстрактні класи.

    export const USERS_REPOSITORY = Symbol("USERS_REPOSITORY");

Провайдер може бути зареєстрований під цим токеном, а сервіс отримувати його через `@Inject(USERS_REPOSITORY)`.

Не потрібно додавати інтерфейс для кожного класу автоматично. Він виправданий тоді, коли справді допомагає визначити контракт або ізолювати залежність.

## 11. Як розпізнати надмірний Coupling?

Звертай увагу на такі ознаки.

### Ознака 1. Компонент знає забагато деталей іншого компонента

Наприклад, сервіс знає назви таблиць, структуру SQL-запитів і спосіб створення підключення до бази.

### Ознака 2. Зміна одного компонента змушує редагувати багато інших

Наприклад, перейменування внутрішнього поля в репозиторії змушує змінювати багато сервісів, хоча це поле не повинно було бути частиною їхнього контракту.

### Ознака 3. Складно протестувати компонент окремо

Для тестування простого бізнес-правила потрібно запускати всю інфраструктуру.

Це може вказувати на надмірні залежності, хоча інколи інтеграційний тест справді потребує реальної інфраструктури.

### Ознака 4. Залежності утворюють заплутані цикли

Наприклад:

    UsersService -> CoursesService
         ^               |
         |_______________|

Якщо два сервіси безпосередньо залежать один від одного, потрібно перевірити, чи не змішані їхні відповідальності.

Циклічні залежності не завжди означають помилку, але часто ускладнюють розуміння архітектури та можуть свідчити про невдало визначені межі.

### Ознака 5. Технологію складно замінити

Якщо бізнес-правила безпосередньо залежать від деталей конкретної бази даних, заміна способу зберігання може бути дорожчою, ніж потрібно.

## 12. Як розпізнати низьку Cohesion?

### Ознака 1. Компонент має занадто загальну назву

Наприклад:

    CommonService
    GeneralHelper
    ApplicationManager
    Utils

Такі назви не обов'язково неправильні, але можуть приховувати змішування різних відповідальностей.

### Ознака 2. Методи виконують не пов'язані між собою завдання

Наприклад, `UsersService` одночасно формує PDF, обчислює вартість товарів і змінює профіль користувача.

### Ознака 3. Компонент змінюється з багатьох незалежних причин

Якщо один клас доводиться змінювати через правила оплати, інтерфейс користувача та механізм надсилання листів, варто перевірити його відповідальності.

### Ознака 4. Частина методів використовує зовсім інші залежності

Якщо кожна група методів потребує власного набору незалежних залежностей, це може бути ознакою того, що клас об'єднує кілька різних завдань.

### Ознака 5. Важко коротко пояснити призначення компонента

Якщо для пояснення класу потрібен довгий перелік не пов'язаних між собою можливостей, можливо, його варто розділити.

---

## 13. Як покращувати Coupling і Cohesion?

### Крок 1. Визначити відповідальності

Знайди, які завдання виконує компонент.

Наприклад, сервіс замовлень:
- перевіряє склад замовлення;
- обчислює суму;
- зберігає замовлення;
- списує оплату;
- надсилає email.

### Крок 2. Згрупувати пов'язані операції

Обчислення суми та перевірка правил замовлення можуть належати до логіки замовлень.

Надсилання email може бути окремою відповідальністю.

Робота з платіжним провайдером може потребувати окремого компонента інтеграції.

### Крок 3. Визначити межі між компонентами

Наприклад:

    OrdersService
        |
        +--> OrdersRepository
        |
        +--> PaymentGateway
        |
        +--> NotificationService

Це лише приклад. Конкретні залежності мають відповідати вимогам системи.

### Крок 4. Зменшити залежність від деталей

Замість того щоб передавати між компонентами цілі внутрішні об'єкти, передавай лише необхідні дані та використовуй зрозумілі контракти.

### Крок 5. Перевірити результат

Після рефакторингу переконайся, що:
- поведінка застосунку не змінилася випадково;
- компоненти мають чіткі призначення;
- кількість непотрібних залежностей зменшилася;
- тести залишилися зрозумілими;
- структура не стала надмірно складною.

## 14. Практичний приклад: застосунок Worship Schedule

Уявімо застосунок для створення та редагування розкладів богослужінь.

Користувач може:
1. Створити власний розклад.
2. Додати текстові блоки.
3. Змінити форматування тексту.
4. Зберегти розклад.
5. Відкрити його пізніше.

Для такого застосунку можна визначити функціональні компоненти:

    src/
    ├── schedules/
    │   ├── schedules.controller.ts
    │   ├── schedules.service.ts
    │   ├── schedules.repository.ts
    │   └── dto/
    ├── editor/
    │   ├── editor.service.ts
    │   └── editor.types.ts
    ├── users/
    └── database/

### Як застосувати Cohesion?

Модуль `schedules` повинен містити операції та правила, пов'язані з розкладами.

Модуль `users` відповідає за користувачів.

Модуль `editor` може відповідати за структуру документа та правила форматування, якщо цей функціонал справді достатньо складний для окремого модуля.

Не обов'язково створювати модуль `editor` лише через те, що форматування має кілька кнопок. Структура повинна відповідати реальній складності.

### Як застосувати Low Coupling?

`SchedulesService` не повинен знати, як саме React відображає кнопку жирного шрифту.

React-компонент не повинен самостійно виконувати SQL-запити.

Сервіс не повинен довіряти користувацькому ідентифікатору, отриманому безпосередньо з тіла запиту, як доказу права доступу. Він повинен працювати з перевіреним контекстом користувача та застосовувати правила доступу.

### Що станеться, якщо зміниться редактор?

Якщо правила форматування відокремлені від зберігання розкладу, можна змінити інтерфейс редактора, не переписуючи весь механізм роботи з базою даних.

Це приклад того, як висока Cohesion і контрольоване Coupling допомагають розвивати застосунок.

## 15. Coupling, Cohesion і тестування

Хороша структура компонентів зазвичай полегшує тестування, оскільки дозволяє перевіряти поведінку окремо від непотрібних залежностей.

Наприклад, сервіс обчислення вартості може не потребувати ані HTTP-сервера, ані бази даних.

    export function calculateTotal(price, quantity) {
        if (price < 0 || quantity < 0) {
            throw new Error("Values cannot be negative");
        }

        return price * quantity;
    }

Тест:

    import { describe, expect, it } from "vitest";
    import { calculateTotal } from "./calculate-total.js";

    describe("calculateTotal", () => {
        it("calculates the total", () => {
            expect(calculateTotal(50, 4)).toBe(200);
        });

        it("rejects negative values", () => {
            expect(() => calculateTotal(-50, 4)).toThrow();
        });
    });

Функція має чітке призначення, а її поведінку легко перевірити.

Для сервісів із залежностями можна використовувати підставні реалізації, моки або інтеграційні тести — залежно від того, що саме потрібно перевірити.

Однак **можливість ізольованого тестування не є єдиним критерієм якості**. Деякі операції найкраще перевіряти через інтеграцію кількох компонентів.

## 16. Типові помилки

### Помилка 1. Намагатися повністю усунути всі залежності

Будь-який нетривіальний застосунок складається із залежних компонентів.

Мета — не відсутність залежностей, а контрольовані, зрозумілі та виправдані залежності.

### Помилка 2. Створювати інтерфейс для кожного класу

Інтерфейси корисні, коли вони визначають важливий контракт або ізолюють реалізацію.

Якщо інтерфейс не додає гнучкості чи ясності, він може стати зайвим рівнем абстракції.

### Помилка 3. Вважати, що один клас завжди повинен містити лише один метод

Висока Cohesion не означає мінімальну кількість методів.

Клас може містити багато методів, якщо вони належать до спільної відповідальності.

### Помилка 4. Розділяти код лише за назвами файлів

Окремі файли не гарантують низького Coupling або високої Cohesion.

Важливі фактичні залежності та призначення компонентів.

### Помилка 5. Перетворювати просту програму на складну систему абстракцій

Для маленького застосунку інколи достатньо простої функції та невеликого модуля.

Архітектура повинна вирішувати реальні проблеми, а не створювати нові.

### Помилка 6. Вважати, що будь-яка залежність від конкретного класу погана

Залежність від конкретної реалізації може бути цілком нормальною, особливо в невеликих застосунках або на межах системи.

Варто ізолювати ті залежності, заміна або тестування яких справді мають значення.

### Помилка 7. Змішувати бізнес-логіку та інфраструктуру

Якщо правила предметної області без потреби залежать від HTTP, SQL або деталей конкретного постачальника послуг, зміни інфраструктури можуть зачіпати бізнес-логіку.

Варто визначити, які залежності є необхідними, а які можна відокремити.

## 19. Мінішпаргалка

| Поняття | Коротке пояснення |
|---|---|
| Coupling | Ступінь залежності між компонентами |
| Low Coupling | Мінімальні необхідні залежності |
| High Coupling | Надмірна залежність від інших компонентів |
| Cohesion | Внутрішня узгодженість елементів компонента |
| High Cohesion | Елементи компонента працюють на спільну мету |
| Low Cohesion | Компонент об'єднує слабко пов'язані завдання |
| Dependency Injection | Передавання залежностей компоненту ззовні |
| Interface | Контракт, який описує необхідну поведінку |
| Separation of Concerns | Розділення різних відповідальностей |
| Refactoring | Поліпшення внутрішньої структури без зміни зовнішньої поведінки |

### Головне правило

**Прагни до High Cohesion і Low Coupling: компоненти повинні мати чіткі відповідальності та залежати один від одного лише настільки, наскільки це потрібно для їхньої взаємодії.**

Не намагайся усунути всі залежності або створити якомога більше класів. Визначай логічні межі, використовуй зрозумілі контракти та вибирай рівень абстракції, який відповідає реальній складності проєкту.

Саме це допомагає створювати архітектуру, яку легше тестувати, підтримувати та розвивати.
